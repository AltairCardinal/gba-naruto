battle-start-control-flow-20260713战斗系统 · 20260713
scenario 41 开始任务控制流（2026-07-13）
本轮从 scenario 41 story-only 脚本结束后的“队伍·装备”页面继续，静态追踪：
- 0x0200A882、0x0200A884、0x0200A885 的写入者；
- 原先称作 0x08097C78 SetBattle 的来源；
- 队伍/装备 UI 返回后，怎样才会进入真实“开始任务”链路。
结论如下。
1. 0x0200A884..85 是一个 16-bit 过滤后输入位图，不是两个相互独立的 UI
状态字节。ROM 内没有 0x0200A885 的独立字面量引用；高字节变化来自对
0x0200A884 的 strh。因此曾观察到的 A885=0xFC 只是该 halfword 的高 8 位，
不能解释成队伍已就绪或任务可开始。
2. 0x0200A882 是共享 modal/menu result。通用确认路径写 1，取消路径写 2；
它不是持久的章节状态，也不能单独证明已选中“开始任务”。
3. 0x08097C78 不是函数入口，不能寻找它的 BL caller。它只是章节解释器 opcode
0x1A handler 0x08097C6C..94 中间的 ldrb。真正来源是
0x0808F544 -> 0x0808F5D0 BL 0x080977B8 -> opcode jump table[0x1A]。
4. 队伍/装备页是外层战前菜单的一个嵌套子流程，不会在内部直接开战：归一化 selector
2 进入 0x0808ECD0；退出后回到同一外层菜单。归一化 selector 4 才返回
result 2，令外层状态机进入真正的“开始任务”控制器 0x08086A54。
5. **scenario 41 的真实开战不要求出现新的 selector hit，也不要求命中 opcode
0x1A / 0x08097C78。** scenario 41 primary script 已把 ID 留在
0x020311D4[+0x16]。开始任务流程成功后，0x080871BE..C4 直接把
+0x16/+0x19 复制到 battle control 0x02026805/+06。因此把“新 selector 或
SetBattle hit”设为第二战必要门禁会错误拒绝正常路径。

原版连续攻击选择与结算入口
原版的“连续攻击”不是预制截图或单一技能按钮，而是同一动作草稿内的有序两组件事务：
1. 玩家从真实角色术/忍具目录选择第一组件。
2. 多重影分身术（动作 9）不能单独选目标；确认后显示“请选择要使用连续攻击的攻击术・忍具”，返回同一列表并暂存动作 9。
3. 可单独执行、同时允许联携的攻击术会先显示“继续使用连续攻击进行攻击吗？”的是/否分支。选择“否”直接进入该术的普通目标选择；选择“是”返回同一列表并暂存第一组件。
4. 暂存不会提交 BattleSession，但 UI 会显示资源预留。按 B 撤销第一组件后仍留在术列表。
5. 选择第二个攻击术或攻击忍具后才进入共同的目标选择。
6. ROM 在 0x08075B58 接收组件计数与有序组件数组。计数为 2 时先扫描 0x0853DFB0 的五条配方：命中则把两个组件替换为一个派生动作；未命中则保留两个组件并分别初始化两个动作事件。
静态绑定由 tools/analyze_battle_action_combinations.py 复算，结果在
notes/battle-action-combination-bindings-20260725.json。其边界是：该函数证明两组件构建和结算分流，不单独证明菜单提示文本或所有角色的首组件许可集合。

战斗结算、经验与成长链（2026-07-25）
原 ROM 的战后页面不是关卡脚本中的固定截图。它由四类独立数据和三个阶段组成：

formation unit +0x0C
    -> battle unit +0xCE carried EXP
    -> 击败/关联单位结算给实际归属角色
    -> result preview（任务 / 回合奖励 / 战斗 EXP）
    -> apply experience
    -> level settlement（阈值、修炼点、七项成长差）
Butano 版现按同一边界实现：
- 编队记录的 battle_experience 进入 battle_unit_instance::carried_experience；
- 伤害 resolver 只在目标真正被击败时把携带经验转移给攻击归属角色；
- battle_result_system::preview() 不修改持久进度；
- 结果页确认后 apply_experience() 写入经验；
- settle_levels() 再按角色阈值扣除经验、升级、增加修炼点并计算属性差；
- 通用 battle_scene_controller 负责
outcome -> result -> level_up -> complete，renderer 只显示快照。
这条链同时被旧 scenario 41 兼容入口和当前 ROM 主路径
battle_runtime_scene 使用，关卡不再直接写 100/50/150/2/+14。

战斗技能状态、修炼与等级成长证据（2026-07-26）
原作的角色等级、技能解锁和技能习得是三个不同状态，不能用“角色达到等级”直接生成
可战斗技能。每个角色持久保存 15 个主技能槽和 24 个副技能槽；每槽的四字节记录为
技能 ID / 状态 / 解锁等级 / 保留。
状态机为：

0xFF 锁定
  │ 角色等级达到解锁等级
  ▼
0 未习得
  │ 消耗 1 修炼点
  ▼
1 级 ──消耗 1 点──> 2 级 ──消耗 1 点──> 3 级
- 0xFF 与 0 都不能进入战斗动作目录；
- 只有 1..254 会被原作战斗目录构建器接受；
- 等级阈值只执行 0xFF → 0，不会自动习得；
- 战斗动作模板按持久技能等级物化数值成长，公式为
base + per_level_growth × (action_level - 1)，结果保存为 u8。
公开攻略关于“角色每升一级获得一点修炼点、每点提升一项忍术、多数忍术最高三级”的
说明只用于补充玩家可见描述和三级上限；状态转换、扣点和数值成长均以 ROM 控制流为
主要证据。
