## 1. 尝试记录（含走过的弯路）

1. **先信题面「条目 16 字节」** —— 直接十六进制 dump `0x59EAE0`，16 字节步进下
   `0x59EB20` 会解出 `gold = 0x0C01 = 3073`，而金币实际取值域是 50..500；
   24 字节步进则每条都干净对齐。→ 步长疑点，转去消费者代码里找证据。
2. **复用 `tools/extract_rewards.py`（第三方推导的 24 字节布局）** —— 它把尾部当成
   `(忍具 id << 8) | 小整数`，并把低字节标成「数量或档位待定」。本任务要判定的正是
   这个低字节，所以不能直接引用它的结论。
3. **全 ROM 线性 Thumb 反汇编找消费者** —— 用 `md.disasm(rom, 0x08000000)` 一次扫全盘时，
   **指令边界会漂移**：在 `0x0807785x` 一带整体错位 2 字节，导致「按指令列表下标回溯
   前后指令」全部对不上（当时 `cmp r0,#8` 被解到了 `0x08077858`）。
   → 改用「从已知地址定点反汇编 + 原始半字预筛」，见 §2。
4. **ARM / Thumb 双模式找字面量引用** —— `0x0859EAE0` / `0x08594758` 各有两个字面量池
   槽（`0x08089554`/`0x08089FA4`、`0x08075284`/`0x08077870`），用 `ldr rX,[pc,#imm]`
   反查得到 4 + 2 个消费点。全 ROM 扫描里 ARM 代码会被 Thumb 解码器误认成
   「4 路跳转表」，一度把 `0x08064C98` 当成规则调度点 → 增加了「同一函数内必须出现
   规则表指针装载」和「`subs #1` / `cmp` / `lsls #2` 形状」两条约束后排除。
5. **跳转表基址差 4 字节的坑** —— `ldr r1,[pc,#0x10]` 取到的 `0x08077878` 是**表的
   首地址**（不是表头指针），表项从 `0x08077878` 开始；把 `0x08077874` 当基址会让
   type1 的入口变成 `0x08077878`（数据地址），据此确认表基址。
6. **找 `0x0202680C`（type-2 用的状态字节）的写入者** —— 直接基址写、
   `adds` 偏移写都扫不到（该地址其实是一个 **0x3B4+ 字节的计数块基址**，
   战斗内写入都带偏移，如 `0x080770BE` 写的是 `0x02026A56`）。
   → 放弃追写入者，改用**消费者自身的语义**定位：
   `0x08077BB6` 的兜底路径在同一个比较成立时弹出 `0x0812F1E4 = '结束该回合'`
   并返回 1 —— 这就证明了该比较是「回合上限到达」判定。
7. **核对 `0x0202680A`（回合上限）与 `0x0202680C` 的含义**：
   `0x0202680A` 在战斗初始化时由 `0x080751C6` 从规则表 `entry+0` 写入，
   另有两处写 `v*5+5` 与 `15`（`0x0808724A` / `0x08086C0C`）；
   `0x0202680C` 是计数块首字节。二者相等即回合用尽 → **推断**前者是回合上限、
   后者是当前回合计数（见 §5 的 L2 缺口）。

## 2. 方法

`tools/reward_rules_semantics.py` 全部**从 ROM 自己重新发现**，不写死任何代码地址：

1. **找字面量池**：全 ROM 搜 `u32 == 0x0859EAE0` / `0x08594758`。
2. **找消费指令**：用 capstone 反查 `ldr rX,[pc,#imm]` 的字面量地址是否等于池地址。
3. **从消费指令里反推记录步长**：在消费点附近找
   `lsls rX,rY,#1` → `adds rX,rX,rY` → `lsls rZ,rX,#k` 的形状，得到
   `步长 = 3 << k`。三个消费点独立给出 **24**。
4. **反推下标公式**：消费点附近同时装载 `0x08348DAC`（任务下标表），
   `ldrb` 取 `stage` / `sub` 后相加。
5. **找尾部字节的分派器**：在消费点窗口里枚举 `bl` 目标，要求被调函数内部存在
   「同一寄存器与 0/1/2/3 比较」的四路分派，且调用点前两条指令是两次 `ldrb`
   （分别取尾字节与 id）。再用一个**具体的分派模拟器**（把寄存器绑定成 0..3 后
   顺着真实分支走）求出 4 个 arm 的入口地址。
6. **找规则类型的跳转表**：用原始半字预筛 `ldr r0,[r0]` + `mov pc,r0`，
   再从该点定点反汇编，验证 `subs #1` / `cmp` / `lsls #2` / `adds` / `ldr` 形状，
   并要求同一函数附近存在规则表指针装载。
7. **arm 边界**：arm 在 ROM 里紧挨着排列，所以每个 arm 的指令窗口用「下一个 arm 的
   地址」截断（否则 30 字节的 type-2 arm 会把 type-3 的指令一起吞进来）。
8. **（本轮新增）类别 → 名字表**：不满足于「每个 arm 各挂一张名字表」，
   另外去找 ROM 自带的映射表 —— 找到 `0x0859F5E0`（4 槽 u32 指针表），
   `0x0808A02A` 用「尾部低字节」做行号、「物品 id」做列号查它。
   这条与 arm 无关的通用路径把「低字节 = 类别标签」从推断变成证明。
9. **（本轮新增）取值域 × 容量**：把 112 条记录**逐条**解析，
   按类别分组统计 ID 域，再与对应名字表的**实际容量**（连续 ROM 指针个数）比较。

自检（`validate()`）：任何一条断言不成立，工具 `exit 1`。

## 3. 奖励表尾部字节

### 3.1 已定的语义

**尾部低字节 = 奖励类别标签（1-of-4 判别式），既不是数量也不是档位。**

奖励条目 **24 字节**，共 **112 条**（`0x59EAE0..0x59F55F`）：

```
entry = REWARDS + index*24              index = MISSION_INDEX[stage] + sub
  +0x00 u16  金币
  +0x02 u16  强化点
  +0x04 u16  档位/上限（与 0x0202680C 的计数比较后决定是否发放强化点）
  +0x06 ..   尾部槽位，每槽 2 字节（8 个）：
               高字节 = 该类别下的物品 ID
               低字节 = 类别标签 0/1/2/3
  +0x16 u8   恒为 0（语义未解）
  +0x17 u8   恒为 0（语义未解）
```

- 尾部槽位共 8 个（消费者只扫 `r6 = 0..7`）。高字节为 0 表示列表结束。
- **条目数 112 是从数据推出来的**：`MISSION_INDEX`（`0x348DAC`）在
  stage 1..46 / sub 0..2 上的取值域是 `0..111`，且**没有空洞**，
  所以 `0x59EAE0 + 112*24 = 0x59F560`，正好是下一张表的起点。
- `+0x16 / +0x17` 在全部 112 条里都是 0，**没有任何消费者读它们**，
  因此按仓库规则记为「未知字节原样拷贝」。

### 3.1.1 类别 → 名字表：ROM 自带一张指针表（**本轮新增的通用证据**）

旧版本只能靠「每个 arm 各自挂一张名字表」来证明类别与名字表的对应关系。
本轮找到一条**与 arm 无关**的通用路径：

```
0x0808A024  ldr  r1,[pc,#0x88]   ; =0x0859EAE7  (= 奖励表 + 7, 槽 0 的高字节地址)
0x0808A026  adds r0,r0,r1       ; &槽的高字节
0x0808A028  ldrb r1,[r0]         ; r1 = 物品 ID（高字节）
0x0808A02A  ldr  r2,[pc,#0x88]   ; =0x0859F5E0  类别->名字表指针表
0x0808A02C  lsls r0,r7,#2       ; r7 = 尾部低字节 = 类别标签
0x0808A02E  adds r0,r0,r2       ; &表[类别]
0x0808A030  ldr  r0,[r0]        ; 该类别的名字表
0x0808A032  lsls r1,r1,#2       ; 物品 ID * 4
0x0808A034  adds r1,r1,r0
0x0808A036  ldr  r0,[r1]        ; 名字指针
```

ROM 里 `0x0859F5E0` 这张 4 槽指针表的内容就是：

| 类别标签 | 名字表 | 条数 | 前几个名字 |
|---|---|---|---|
| 0 | `0x08599634`（忍具） | 94 | 																	 / 十字手里剑 / 八方手里剑 |
| 1 | `0x085A7E8C`（强化素材） | 18 | 铁翼 / 铁翼 / 铝罐 |
| 2 | `0x08599280`（认识卡） | 150 | 没有 / 漩涡鸣人 / 宇智波佐助 |
| 3 | `0x085A7060`（技术） | 45 | 锻炼 / 锻炼 / 修炼 |

**结论**：尾部低字节是「这张表的行号」，高字节是「该行的列号」。
这张表是 ROM 自带的权威映射，与四个 arm 各自挂的字面量完全一致
（工具 `validate()` 断言两者必须相等）。


### 3.2 消费者指令

**（a）下标与步长**（`0x08089E90`）：

```
0x08089E90: ldr      r2, [pc, #0x108]   ; =0x08348DAC   任务下标表
0x08089E92: ldr      r0, [pc, #0x10c]   ; =0x020311D4   章节结构体
0x08089E94: ldrb     r1, [r0, #0x16]    ; stage
0x08089E9A: ldrb     r1, [r1]           ; mission base = MISSION_INDEX[stage]
0x08089E9C: adds     r0, r0, r1        ; index = base + sub
0x08089EA2: ldr      r2, [pc, #0x100]   ; =0x0859EAE0   奖励表
0x08089EA4: lsls     r0, r7, #1
0x08089EA6: adds     r0, r0, r7        ; index*3
0x08089EA8: lsls     r1, r0, #3        ; index*24   ← 步长 24 的直接证据
0x08089EAA: adds     r0, r1, r2
0x08089EAC: ldrb     r0, [r0, #7]      ; 槽位 0 的高字节 = 物品 ID
```

**（b）取尾部低字节并调用分派器**（`0x08089F80`）：

```
0x08089F86: ldrb     r0, [r5]          ; 尾字节（低字节）→ 参数 0
0x08089F8C: ldrb     r1, [r1]          ; 高字节（物品 ID）→ 参数 1
0x08089F8E: bl       #0x80972f8        ; dispatch(tail_byte, id, ctx)
```

**（c）四路分派**（`0x080972F8` 函数内的 `0x0809731E`）：

```
0x0809731E: cmp      r4, #1
0x08097320: beq      #0x8097414        ; 类别 1
0x08097322: cmp      r4, #1
0x08097324: bgt      #0x809732c
0x08097326: cmp      r4, #0
0x08097328: beq      #0x809733a        ; 类别 0
0x0809732A: b        #0x809750e        ; 其它 → 默认
0x0809732C: cmp      r4, #2
0x0809732E: bne      #0x8097332
0x08097330: b        #0x809747c        ; 类别 2
0x08097332: cmp      r4, #3
0x08097334: bne      #0x8097338
0x08097336: b        #0x80974d4        ; 类别 3
0x08097338: b        #0x809750e        ; 默认
```

**（d）每个 arm 用不同的名字表**（名字表基址是 arm 内的 `ldr` 字面量，工具自动提取）：

|---|---|---|---|---|
| 0 | `0x0809733A` | `0x0846445C` =「忍具」 | `0x08599634`（94 条：十字手里剑…超万能丸） | **忍具** |

| 2 | `0x0809747C` | `0x08464500` =「认识卡」 | `0x08599280`（150 条：漩涡鸣人、宇智波佐助…） | **认识卡**（人物卡） |
| 3 | `0x080974D4` | `0x08464508` =「技术」 | `0x085A7060`（45 条：锻炼、跑步练习…） | **技术 / 修行** |

### 3.3 取值域 × 名字表容量（**本轮逐条核对**）

按**表里实际的 112 条**（不是按场景重复计数的 138 行）统计：

| 尾字节 | 类别 | 槽位数 | 出现的记录数 | 不同 ID 数 | ID 取值域 | 名字表 | 名字表容量 | 越界 ID |
|---|---|---|---|---|---|---|---|---|
| 0 | 忍具 | 110 | 110 | 8 | **1..73** | `0x08599634` | 94 | **0** |
| 1 | 强化素材 | 179 | 179 | 18 | **0..17** | `0x085A7E8C` | 18 | **0** |
| 2 | 认识卡 | 39 | 39 | 38 | **2..61** | `0x08599280` | 150 | **0** |
| 3 | 技术 | **0** | 0 | — | **（本 ROM 数据未使用）** | `0x085A7060` | 45 | — |

- **328 个尾部槽位，ID 全部落在各自类别的名字表容量内**（0 越界）。
- 类别 1 的 ID 域 `0..17` **正好等于**它 18 条名字表的全部下标。
- 类别 2 的 ID 域 `2..61` 落在「已拥有人物」位图（`0x020240AC`，
  `0x08068EA4` / `0x08068E5C`）可寻址的范围内（位图下标 = id）。
- **类别 3（技术）在原版数据里一次都没用到**：分派支持它、
  名字表存在（45 条），但 112 条记录里没有任何一个槽位的低字节是 3。
  因此**类别 3 的取值域无法用本 ROM 的数据界定**——它只能由代码给出上界
  （名字表 45 条，即 ID 必须 < 45）。
- 槽位位置分布也没有「某个类别只出现在固定位置」的假象：
  - 尾字节 0：slot0 57 次、slot1 48、slot2 14、slot3 6、slot4 3
  - 尾字节 1：slot0 14、slot1 16、slot2 43、slot3 42、slot4 37、slot5 31
  - 尾字节 2：slot0 4、slot1 6、slot2 9、slot3 8、slot4 8、slot5 7、slot6 3
- 边界情况：**有 2 个槽位的高字节（ID）= 0**（stage 4 sub0 slot2、stage 4 sub1 slot1，
  类别均为 1）。由于消费者用高字节 == 0 判列表结束，这两处会提前截断列表——
  再次印证「高字节是 ID、0 为终止符」，而不是「低字节是 ID」。

> 旧版本这里的计数（128 / 183 / 45 / 356）是**按 46 场景 × 3 配置 = 138 行**重复
> 统计的，同一条记录被数了 2~3 次。本表改成**按表里实际的 112 条**统计，
> 数字更小但是去重后的真值。


### 3.4 可证伪检验

- **F1（代码级，最强）**：把 stage 1 sub 0 奖励条目槽位 0 的尾字节由 `0x00` 改成 `0x01`，
  游戏弹出的获得提示必须从「忍具 + 忍具名」变成「强化素材 + 素材名」。
  若仍显示忍具名 → 本结论被推翻。
- **F2（数据级）**：全表尾字节只允许 0/1/2/3，且每个尾字节必须映射到**各自不同**的
  名字表；328 个 ID 必须全部落在对应表内。工具 `validate()` 已把这三条写成断言，
  任一不成立即 `exit 1`。
- **F3（步长）**：把奖励条目按 16 字节解释必然解出 `gold=3073` 这类越界值；
  消费者代码三处独立给出 `index*24`。若能找到任何一处 `index*16` 的算式，
  本结论被推翻。
- **F4（取值域 × 容量，本轮新增）**：把类别 0 的某个槽位高字节改成 `>= 94`
  （忍具名表容量），或者把类别 1 的改成 `>= 18`，游戏就必须显示出**乱指针**
  的名字（`0x08089DDC lsls r1,r1,#2` 没有任何边界检查），
  轻则显示错名字、重则崩溃。若改成越界 id 仍显示正常名字 →
  说明「高字节 = 名字表下标」被推翻。
  反向检验（数据级）：工具 `validate()` 已把「每个类别的每个 ID 都必须落在
  自己名字表的容量内」写成断言，越界即 `exit 1`。
- **F5（类别 → 名字表映射，本轮新增）**：把 `0x59F5E0` 这张指针表的第 0 项
  改成类别 1 的名字表 `0x085A7E8C`，奖励提示里的「忍具」必须变成
  「强化素材」的名字。若不变 → 映射被推翻。
- **F6（条目数 112，本轮新增）**：把 `MISSION_INDEX` 的某个字节改大，
  索引就会越过 `0x59F560` 进入下一张表；若游戏仍正常显示奖励，
  则「112 条」或「下标公式 `MISSION_INDEX[stage]+sub`」被推翻。

## 4. 胜负条件类型 2 / 3

### 4.1 规则表与分派

```
entry = 0x594758 + stage*0xCC + sub*0x44
  +0x00 u8   回合上限
  +0x04 组 0（胜利条件）：4 条 × 8 字节
  +0x24 组 1（失败条件）：4 条 × 8 字节
单条：type u8, a u8, b u8, c u8, 说明文字指针 u32
```

条件类型在 `0x080777FC` 的评估函数里用 **9 项跳转表** 分派（表基址 `0x08077878`）：

```
0x08077856: ldrb     r0, [r5]          ; rule.type
0x08077858: subs     r0, #1
0x0807785A: cmp      r0, #8
0x0807785C: bls      #0x8077860
0x08077860: lsls     r0, r0, #2
0x08077862: ldr      r1, [pc, #0x10]   ; =0x08077878  跳转表基址
0x08077864: adds     r0, r0, r1
0x08077866: ldr      r0, [r0]
0x08077868: mov      pc, r0
```

`5→0x080779B4`、`6→0x080779D4`、`7→0x080779EC`、`8→0x08077A78`、`9→0x08077AFC`。

### 4.2 类型 3：指定角色已离场 ✅

**语义**：`rule.a` = 阵营（0 = 我方 / 1 = 敌方），`rule.b` = 角色 ID；
**当场上不再存在「该阵营的该角色」时，条件成立**（胜利组 = 敌人被打败，
失败组 = 我方保护目标阵亡/离场）。

消费者指令（`0x08077924`）：

```
0x08077924: ldrb     r4, [r5, #1]      ; rule.a  = 阵营
0x08077928: ldr      r0, [pc, #0x64]   ; =0x020240C0  战斗单位数组（步长 0x1D4）
0x0807792E: adds     r2, r0, r1        ; &unit[1]
0x08077930: ldrb     r1, [r2]          ; unit[1].占用标志，0 = 空位
0x0807793E: ldrb     r0, [r0]          ; unit[1]+0xBC = 角色 ID
0x08077940: ldrb     r1, [r5, #2]      ; rule.b  = 角色 ID
0x08077942: cmp      r0, r1
0x08077944: bne      #0x8077954        ; 不是这个角色 → 下一个单位
0x0807794C: ldr      r0, [r0]          ; unit[1]+0xC0 标志字
0x0807794E: ands     r0, r3            ; bit0 = 阵营
0x08077950: cmp      r0, r4            ; 与 rule.a 比较
0x08077952: beq      #0x8077988        ; 命中 → 条件**不成立**（继续找下一个条件）
0x08077988: cmp      r3, #0xd
0x0807798A: beq      #0x807798e        ; 12 个单位槽扫完 → 条件成立
0x0807798C: b        #0x8077b3a
```

**交叉表（18/18 全中）**：

|---|---|---|---|---|---|
| 1 / 0, 2 | 1 | 0 | 31 | slot3 达兹纳 (side0) | 没能保护达兹纳…… |
| 3 / 0,1,2 | 0 | 1 | 20 | slot4,5 桃地再不斩 (side1) | 解开再不斩的《水牢术》了 |
| 3 / 0,1,2 | 1 | 0 | 31 | slot3 达兹纳 (side0) | 没能保护达兹纳…… |

（工具 `validate()` 断言，18/18、18/18）。这同时反向确认了 type-1 的 `a` 语义

**可证伪检验**：

- **F1**：在 stage 1 里让达兹纳（角色 31 / 我方）离场（把单位槽清空或置为死亡），
  失败组的 type-3 条件必须成立、游戏必须显示「没能保护达兹纳……」。
  若该条件不成立 → 「离场」语义被推翻。
- **F2**：把 type-3 行的 `rule.b` 从 31 改成 30（该场景里 30 不在我方），
  条件必须不再成立。
- **F3**：把 `rule.a` 从 0 改成 1，条件必须不再成立。
- **F4（数据级）**：全部 18 行的 `rule.b` 必须在该场景角色表内、`rule.a` 必须等于其阵营；

### 4.3 类型 2：出货代码不读 `rule.a/rule.b` ⚠️

**已证实的执行语义**（arm `0x08077904`，工具自动断言「该 arm 对规则记录的读取次数 = 0」）：

```
0x08077904: mov      r0, r8           ; 评估函数入参（0 = 常规检查 / 1 = 结算检查）
0x08077906: cmp      r0, #0
0x08077908: bne      #0x807790c
0x0807790A: b        #0x8077b3a        ; 入参 = 0 → 条件永不成立
0x0807790C: ldrb     r1, [r6, #6]     ; r6 = 0x02026804 → 0x0202680A（回合上限）
0x0807790E: cmp      r1, #0
0x08077910: bne      #0x8077914
0x08077912: b        #0x8077b3a        ; 上限为 0 → 永不成立
0x08077914: ldr      r0, [pc, #8]     ; =0x0202680C（战斗计数块首字节）
0x08077916: ldrb     r0, [r0]
0x08077918: cmp      r1, r0
0x0807791A: beq      #0x807791e       ; 上限 == 计数 → 条件成立
0x0807791C: b        #0x8077b3a
0x0807791E: b        #0x8077b28
```

即：**type 2 = 「回合用尽」判定**（与 type 7/8/9 的比较类条件共用同一段前置：
入参必须为 1、`0x0202680A != 0`、`0x0202680A == byte[0x0202680C]`）。
同一个比较在**没有任何条件命中**的兜底路径 `0x08077BB6` 里会弹出
`0x0812F1E4 = '结束该回合'` 并返回 1 —— 这从语义上确认了它是回合上限判定。

**type 2 在这段前置之后没有任何别的判定**（`0x0807791E: b 0x08077B28` 直接进成功路径）。
对照 **type 4** 的 arm `0x08077994`：它有**完全相同**的前置，之后才接自己的判定

```
0x080779B4: ldr      r0, [pc, #0x14]  ; =0x0202680C
0x080779B6: ldr      r1, [pc, #0x18]  ; =0x000003B6
0x080779B8: adds     r0, r0, r1      ; 0x02026BC2 = 收集物计数块
0x080779BA: ldrb     r1, [r5, #1]    ; rule.a
0x080779BC: adds     r0, r0, r1
0x080779BE: ldrb     r0, [r0]        ; collected[rule.a]
0x080779C0: ldrb     r1, [r5, #2]    ; rule.b
0x080779C2: cmp      r0, r1
0x080779C4: bhs      #0x80779c8      ; collected[a] >= b → 成立
```

也就是说：**前置 = 「回合用尽 / 结算时点」是公共门，type 4 = 门 + 收集物阈值，
type 2 = 只有门、没有内容。** type 4 在原版数据里出现 0 次。

**但数据是矛盾的**（工具自动断言）：

- 11 条 type-2 行的 `rule.a` / `rule.b` 与 type-3 完全同构：**11/11** 行的
  `rule.b` 命中该场景角色表，**11/11** 行的 `rule.a` 等于该角色阵营。
- **11/11** 条 type-2 行都能在**另一组**找到 `stage/sub` 与 `(a,b)` 完全相同的
  type-3 行（即两条互为反面，分处胜利组与失败组）。
- 典型对照：

  | stage/sub | type-2（组, a, b, 文字） | type-3（组, a, b, 文字） |
  |---|---|---|
  | 1 / 0 | 组0, 0, 31, 保护了达兹纳 | 组1, 0, 31, 没能保护达兹纳 |
  | 3 / 0 | 组1, 1, 20, 解开再不斩的《水牢术》了 | 组0, 1, 20, 解开再不斩的《水牢术》了 |
  | 10 / 0 | 组1, 1, 1, 打败冒牌货鸣人了 | 组0, 1, 1, 打败冒牌货鸣人了 |
  | 14 / 0 | 组0, 0, 30, 赶走蜜蜂了 | 组1, 0, 30, 没能很好保护木叶丸 |

- 也就是说：**设计意图显然是「指定角色仍在场」= type 3 的反面**，
  但这版 ROM 的 type-2 arm 实现的是「回合用尽」，根本没有单位扫描。
- 佐证：11 条 type-2 行里有 **9 条所在场景的回合上限为 0**
  （`0x0202680A` 会被写成 0 → arm 直接 `b 0x08077B3A` 永不成立），
  只有 stage 1（上限 15）那 2 条有机会命中。

**可证伪检验**：

- **F1（对「arm 不读 a/b」结论）**：把某条 type-2 行的 `rule.b` 改成另一个角色 ID，
  观察战局结果是否**完全不变**。若结果会变 → 我对 arm 的读指令统计有误，
  说明存在我没找到的 type-2 消费路径。
- **F2（对「回合用尽」语义）**：在 stage 1（回合上限 15）里把回合上限改成别的值，
  或让 `0x0202680C` 与 `0x0202680A` 不相等，type-2 条件必须不再成立；
  两者相等时必须以「保护了达兹纳」这段文字结算。
- **F3（对 type 3）**：见 §4.2。
