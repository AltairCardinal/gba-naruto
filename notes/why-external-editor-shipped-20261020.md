# 复盘：为什么对方以更低成本产出了可用成果（2026-10-20）

**触发问题**：本项目早期尝试做剧情/战斗编辑器未获可用成果；转向逆向工程后仍残留
一批"无法解明的字节"。第三方包（木叶工房 v0.4.4）却以明显更低的成本给出了
可用的剧情编辑器 + 26 场可玩 DEMO。差距在哪？

**关联**: `notes/external-konoha-workshop-gap-20261020.md`（差集清单）

---

## 0. 结论

**差距不在逆向深度，而在三处方法论选择**：

1. **写回模型**：我们是"抽取→命名→重建"，他们是"复制原生条目→只改已知字段"。
   前者要求每个字节都有名字，后者不要求——这直接消灭了"无法解明的字节"这个问题的存在。
2. **验收标准**：我们用"32 个结构全量运行时证明"当门禁，且用自指的 6 项静态检查当完成度。
   他们用"ROM 能不能跑起来 + 字节是否可复现"当门禁。
3. **工程形态**：我们造的是带登录/多用户/WebSocket 的 Web 服务；他们造的是
   一个能双击打开的离线文件夹。

诚实的限定：对方的**总工时**未必比我们少（其源码里有 v0.1.2 三人替代项目作前置，
包内文件时间戳 2026-10-18~19 只是打包日）。差别不在工作量，在**工作顺序与验收标准**。

## 2. 六个具体原因

### 原因 1｜写回模型：重建 vs 复制+最小改写（最关键）

**我们的模型**（`tools/import_battle_config.py` 头部即体现）：
```
ROM → 抽取条目 → 拆成语义字段 → 存 SQLite/JSON → 用户编辑 → 由字段重新组装 → patch
```
它要求**每个字节都有名字**。没有名字的字节就是缺陷，就是必须追查的对象——
这正是"残留无法解明的字节"的来源。

**他们的模型**（`editor/core.js` `setActor`）：
```js
const t = 0x54241c + values.id*0xb4;      // 角色模板
for (let i=0;i<0x9c;i++) this.put(p+0x10+i, this.rom[t+0xc+i]);  // 整块复制 0x9C 字节
for (let i=0;i<9;i++)   this.put(p+0xac+i, this.rom[t+0xa8+i]);  // 再复制 9 字节
// 然后只覆盖 6 个已知字节：id / side / x / y / facing / level
```
**他们从不删除没理解的字节。** 战斗配置那一整套（`0x5461C4 + stage*0x1AAC + sub*0x8E4`，
每组 0x8E4 字节）也是同样的手法：先整块复制原版 sub 配置，再逐条覆盖。

结果：他们不需要理解那 0x9C 字节是什么，就能做出"以已有战斗为模板增加场次"的功能。
我们则必须理解它，否则重建出来的结构就是错的。

> **实证**：我们的 32-byte 地图表布局是**错的**（palette 位置错、flags 错），
> 单位 stride 写成 234（实为 468）——这些不是"没找到"，而是"重建模型算错了"。
> 对方直接给出 468 和正确的字段顺序。

### 原因 2｜"无法解明的字节"是我们自找的问题

一个条目里有 0x9C 字节没有名字时：
- 我们的处理：视为待解谜题 → 建 issue → 写工具 → 追查 → 追不到就标 `unknown`。
- 他们的处理：原样保留，编辑器不碰它。

这不是他们更聪明，而是**他们的数据流里没有"必须命名"这个约束**。
我们的约束来自"抽取→入库→重建"这条链；链的形状决定了我们必须给每个字节起名。

### 原因 3｜完成度指标是自指的，而门禁过严 → 两种指标同时锁死

我们有两套验收，方向相反：
- `re-completion-audit.md` 的 6 项检查：offset 非空、format 非空、entries 非空、
  有验证标签、文档有提及、字节与基准一致。
  —— 这套检查**只要把格式写下来就通过**。它把"写下 0x596D5C 是图块描述符表"
  判为 ✅（后来的实测证明是错的，但审计当时无法发现）。
- `runtime-verification-gates-20260710.md` 的门禁：要求每个字段都有运行时消费证据
  （断点命中 PC/LR、ROM 源地址落入已声明表项、字段与可见行为对应）。
  —— 这套门禁写得**极高质量**，但要求 32 个结构逐个动态证明。

两套一起 = 必须先把整个游戏理解到能动态证明，才允许产出。
实际结果是 `1 dynamic / 6 code / 24 static / 1 none`，
且静态阶段就已经错了 2 处（`0x596D5C`、`0x599634`）。

他们的门禁只有一条：**生成的 ROM 能不能跑**。`交付核对.json` 记录
"source_rebuild: byte_identical"、"browser_demo_generation: 重生成的 ROM 与实测 ROM 完全一致"。

**他们用"可运行"换掉了"可证明"**。这是一次明确的取舍：
产出物更弱（自陈"未完整打通 26 场"），但有东西可以玩。

### 原因 4｜我们的地面真值闭环从一开始就是断的

`notes/battle-config-format.md` 写着：
> **Blocked**: mGBA headless debugger does not support key input injection.

我们把这个**工具层限制**当成了**逆向层障碍**，于是用静态工具替代动态观察：
vendored 整套 capstone/keystone 头文件、自己写 disasm_thumb、找指针引用、
profile 表列、OCR、puppeteer、WASM 探针……几十个工具都在补"看不见游戏在干什么"这个洞。

他们的解法是**换一个能驱动的模拟器接口**：`gba_probe.c` 链接 mGBA 0.11 头文件与库，
`-DENABLE_DIRECTORIES`，在 C 层直接跑模拟器、注入按键，6KB 一个文件。
同样的问题，他们用 1 个文件解决，我们用几十个工具绕。

而且他们的闭环是**先有可跑基线**：`源码/source`（v0.1.2 三人替代，13 个 hook，
每个带原字节前像）已经是能跑的 ROM，战役扩展是在这个基线上做的（v0.1.5）。
我们没有基线，只有一堆笔记。

### 原因 5｜工作顺序反了

我们的因果链是：
> 想做编辑器 → 发现不懂游戏 → 先做逆向 → 逆向没做完 → 编辑器更做不了。

他们的因果链是：
> 想做"三人替代"这个 hack → 边改边发现结构 → 顺手做出编辑器 → 编辑器反过来暴露更多结构。

逆向是**副产品**而不是**前置条件**。这解释了为什么我们"始终残留一部分无法解明的字节"
仍然是致命的——按我们的顺序，未解明的字节就是阻塞项；按他们的顺序，未解明的字节
可以一直不解，因为功能不依赖它。

### 原因 6｜工程形态选错

我们的 `web-editor/`：FastAPI + SQLite + Vue3 + JWT 登录 + 用户管理 + WebSocket + i18n。
目标是什么？"多人协作、ROM 在服务端操作"的 Web 平台（见 `docs/sequel-roadmap.md`）。

但真实需求是"我要一个能改 ROM 的工具"。对方交付的是：
`editor/index.html` + 20 个 JS 文件，双击打开，操作内存里的 ROM 缓冲区，
`edits` Map 记录改动 + 原字节校验 + `append()` 追加新数据 → 直接导出 ROM。

我们**造了一个平台，需求是一个工具**。认证、多用户、协作、服务端部署，
在"一个人改一个 ROM"的场景里全是纯成本，而且是零收益成本。

## 3. 对方也没有做到的事（不能神化）

诚实地看，对方成果的边界：

1. **自陈未完整验证**：`00_先看这里.txt` 明写"本次没有重新完整打通两版各26场，
   硬件、全部换人组合及所有路线未测"；数值与剧情是"功能演示"。
2. **条件类型语义未公开**：原版条件类型 0..9 的逐条含义对方没给（只给了参数占用规律），
   类型 10（撤离）是**他们用运行时 hook 新加的**，不是原版能力。
3. **扩展方式脆弱**：整表搬迁到 ROM 尾部 + 批量改写 ROM 内所有指针，
   换 ROM 版本即失效；且吃掉了大量尾部空间。
4. **其自身基线是另一份**：`源码/source` 是 v0.1.2 项目，基线 SHA 不同
   （`52a33419…`），与 v0.4.4 战役扩展**不能混用**。
5. **他们的 ROM 结构知识也有边界**：例如他们没解决"同一张地图换底图"这类问题，
   地图尺寸不扩展、素材必须符合模板与颜色限制。

所以结论不是"他们做得更好"，而是**"我们的验收标准与工程形态，使得一个可用成果的成本被放大了一个数量级"**。

## 4. 可执行教训（按收益排序）

| # | 教训 | 具体动作 |
|---|---|---|
| L1 | **写回模型换成"复制+最小改写"** | bank/编辑器保留原生条目 raw bytes 兜底；只对已确认字段做覆盖；未命名字段默认不触碰。这一条直接消灭"无法解明的字节"这个阻塞项 |
| L2 | **要一个能注键的模拟器** | 移植 mGBA C API 探针（对方 `gba_probe.c` 6KB 可直接参考）。没有它，一切动态验证无从谈起 |
| L3 | **先做能跑的一小步闭环** | 挑一个最窄目标（例如"只改一场战斗的敌方阵容"），做到 ROM 跑起来 + 画面变化可见，再横向扩展 |
| L4 | **按需触发门禁，不做全量门禁** | `runtime-verification-gates` 的质量保留，但只对**本次改动涉及的结构**要求动态证据；不再要求 32 个结构先全绿 |
| L5 | **降级工程形态** | 编辑器走"单文件夹离线工具"路线，暂停 Web 服务/认证/多用户方向；把 FastAPI+Vue 的投入降到零 |
| L6 | **逆向降级为副产品** | 不再把"理解全部 32 个结构"设为开工条件；由具体功能需求驱动，按需逆向 |
| L7 | **每次调查必须包含一次证伪** | 我们的 `0x596D5C` 链条（scan→refs→table→profile）每一步都在加固同一假设，没有任何一步可能推翻它。规定：每条结论都要设计一个能判死的实验 |

---

## 5. 反面教训：我们的强项不要丢

- `runtime-verification-gates-20260710.md` 的证据标准（断点命中 PC/LR、源地址落入
  已声明表项、字段与可见行为对应、A/B ROM 单变量）**质量很高**，是对方没有的。
  问题是把它当成了**开工前置**而不是**按需门禁**。
- 仓库的"结论必须落到 notes/docs/tools"规则（见 AGENTS.md）让 105 次提交没有丢失信息。
  对方则把大量 RE 结论直接埋进了构建脚本常量里（`0x5461C4`、`0x594758`、
  `0x1AAC`、`0x8E4`、`0xB8`……散落在 JS/C 里，没有独立文档）。
  **他们用可运行性换走了可追溯性**——这正是我们要避免的。

> 合理的合成目标：**保留我们的证据标准 + 采用他们的写回模型与工程形态**。

## 6. 下一步建议（对应 L1/L2/L3）

1. 把 `notes/external-konoha-workshop-gap-20261020.md` 的 P0-1（剧情脚本 VM）做成
   第一个真实目标：实现 VM 解码器 → 能在编辑器里看到"这一场有哪些对白"。
   验证标准 = **产物可见**，不是"32 结构全绿"。
2. 同时把 `web-editor` 的写回路径改成 L1 形态：所有 table 保留 raw 兜底 + 覆盖式写回，
   取消"必须命名"的约束。
3. 同步做 L2：移植 mGBA C API 探针（这是对方唯一明确优于我们的**工具能力**）。
4. 在 `docs/sequel-roadmap.md` 里把"逆向工程 100% 完成后启动编辑器"这条
   （现行路线的核心假设）标记为**已证伪并推翻**。
