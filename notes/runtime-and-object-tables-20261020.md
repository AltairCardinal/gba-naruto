## 1. 运行时状态（`tools/runtime_state.py`）

### 1.1 原生字段：ROM 字面量池引用核验

ARM 字面量池存绝对地址，所以"游戏代码里出现这个地址"是可静态核验的。
工具对每个地址做**直接引用**与**块内引用**（地址落在某个被引用块的
±32 字节内）两种检查。

| 字段 | 地址 | 直接 | 块内 | 含义 |
|---|---|---:|---:|---|
| `scene_id` | `0x020311EA` | 0 | 86 | 当前场景/章节 ID。**2026-10-20 运行时证实**：开场剧情里同一个字节依次读出 54 → 50 → 40，正好是剧情 VM 报的场景号。注意：它**没有原生读者**（游戏由剧情脚本写它），所以「0 个原生读者」不等于「不是场景号」——`notes/mgba-probe-runtime-20261020.md` §4.1 的推论已被本轮运行时读数修正。 |
| `story_progress` | `0x020311E4` | 0 | 86 | 剧情进度 u16。370 = 原版通关，385 = 另一通关态。**仍无运行时读数**（本轮读到的块里这些字节恒为 0） |
| `story_branch` | `0x020311EC` | 0 | 86 | 剧情分支字节，新游戏清零。**仍无运行时读数** |
| `story_config`×3 | `0x020311ED..EF` | 0 | 86 | 剧情配置字节，新游戏清零。**仍无运行时读数** |
| `battle_stage` | `0x02026805` | 0 | 89 | 当前战场 stage（块基址 `0x02026804`）。**2026-10-20 运行时证实**：选「练习移动」任务并确认后被游戏写成 40 (0x28) |
| `battle_sub` | `0x02026806` | 0 | 89 | 战场 sub（三套配置）。**运行时读到 0** |
| `battle_result` | `0x02026807` | 0 | 89 | 上一场战斗结果，新游戏清零 |
| `clear_flag` | `0x0203150F` | 1 | 9 | 标志字节，bit7 = 已通关。运行时读到 0（新游戏清零） |
| `party_slot_base` | `0x02022E34` | 15 | 71 | 队员结构数组，槽 n = base + n×**188**，n = 1..23。**运行时证实**：槽 1（`0x02022EF0`）= 角色 ID 1、等级 1 |
| `battle_unit_base` | `0x020240C0` | 140 | 155 | 战斗单位槽，槽 n = base + n×**468**，n = 1..12。**本轮运行时全 0**（stage 40 的移动教学任务不实例化战斗单位） |

**结论：这些是原版游戏自己的状态，我们此前只记了其中 3 个。**

### 1.1.1 运行时读数闭环（2026-10-20）

`notes/evidence/runtime-state-l3-20261020.md` 用无头 mGBA 探针
（`tools/runtime_capture.py`）把这些字段**在真实 ROM 里读了出来**：

```
[story]   scene id byte   0x020311EA = 40 (0x28)
          scene id during the intro story: 25:54 ... 150:50 ... 325:40
          party slot 1     0x02022EF0 = 01010e0d0803050505000f0050005000...
[mission] battle control  0x02026804 = 002800000000000000000100000000000000...
          ctrl[1]=stage=40  ctrl[2]=sub=0  ctrl[6]=turn limit=0
          counter block   0x0202680C = 00000100000000000000000000000000
          unit array      0x020240C0 = 0000... (全 0)
```

由此闭合/收窄：

- **`scene_id` 成立**：同一字节随剧情 54 → 50 → 40，与剧情 VM 报的场景号一致。
- **`battle_stage` / `battle_sub` 成立**：任务确认后由游戏写入 40 / 0。
- **`party_slot_base` 成立**：槽 1 = 角色 ID 1（漩涡鸣人）、等级 1。
- **`battle_unit_base` 仍无读数**：stage 40 的「练习移动」是移动教学，
  不实例化战斗单位 → `0x020240C0` 全程为 0。
- **`story_progress` / `story_branch` / `story_config` 仍无运行时读数**：
  本轮读到的 `0x020311D4` 块里这些字节恒为 0，字段名目前**只有静态依据**。

复现：

```powershell
python tools/runtime_capture.py rom/base.gba
```

## 2. 奖励表 `0x59EAE0`（`tools/extract_rewards.py`）

```
表 0x59EAE0   条目 24 字节   原版 112 条（77 条有内容，35 条全零）
第三方扩展到 256 条
```

### 2.1 布局（由 ROM 数据自证，非照抄对方源码）

| 偏移 | 含义 | 实测分布 |
|---|---|---|
| +0 | u16 金币 | 50..500，众数 200 |
| +2 | u16 奖励/强化点 | 25..400，众数 200 |
| +4 | u16 档位/类型 | 1..15，众数 8 |
| +6… | u16[] `(忍具 id << 8) \| 小整数` | 高字节 = 忍具名表 `0x599634` 的 id |

### 2.2 尾部布局的证据

| 检验 | 结果 |
|---|---|
| 尾部 u16 总数 | 328 |
| 高字节落在 1..93（忍具表 id 范围） | **326** |
| 低字节 ∈ {0,1,2} | **328** |
| 不同忍具 id 数 | 48（0..73） |
| 第三方写入方式 `put(reward+6,[1,73])` | = item 73 × 1，与该编码完全吻合 |

样本：

```
[  0] gold=200 bonus=100 tier=10  十字手里剑x0 | 微型卷轴x0 | 超八方手里剑x1 | 毒飞镖x2 | 强力毒飞镖x2
[  5] gold=200 bonus=200 tier=8   引爆牌x0 | 飞镖x0 | 八方手里剑x1 | 羽翅手里剑x1 | 毒手里剑x1 | 超毒手里剑x1
[ 12] gold=200 bonus=100 tier=8   十字手里剑x0 | 八方手里剑x1 | 超毒飞镖x2 | 无限飞镖x2 | 猛烈弹x2 | 强力软气弹x2
```

**低字节语义仍未定**：0/1/2 可能是数量，也可能是档位；
第三方只写 `5`（tier）与 `[1,73]`，没有解释低字节。
这是本表唯一未解的部分。

## 3. 战场物件系统（`tools/object_tables.py`）

### 3.1 8 类记录（战场配置尾部 `+0x8A4`，16 条 × 4 字节 `type, target, x, y`）

| type | 含义 | target 指向 |
|---|---|---|
| 0 | 空位 | — |
| 1 | 忍具 | 忍具名表 `0x599634`（93 条） |
| 2 | 强化素材 | 强化素材名表 `0x5A7E8C`（16 条） |
| 3 | 专属修行卷轴 | 人物（1..21） |
| 4 | 认识卡（人物图鉴） | 人物 `0x599280`（62 条） |
| 5 | 机关宝箱 | 机关 id |
| 6 | 特殊机关（卷轴外观） | 机关 id |
| 7 | 剧情物件 | 机关 id |

**type 3 / 4 是条件生成**（所属人物是否入队、是否已解锁修行、是否已领取），
所以游戏报的"物品编号"**不等于**记录行号 —— 后面的编号会提前。

### 3.2 原生拾取分派表 `0x815E4`（**新发现**）

```
[0] 0x08081600   [1] 0x0808173C   [2] 0x0808180C
[3] 0x080818E4   [4] 0x08081984   [5] 0x08081984   [6] 0x08081984
[7] 起不再是 ROM 指针
```

**原生有 7 个拾取处理程序**（索引 = 记录 type − 1），且 type 5/6/7
（机关宝箱 / 特殊机关 / 剧情物件）**共用同一个** `0x08081984`。

> ⚠️ **2026-10-20 晚更正**：本节原先写"对方那 13 种机关只是叠加命名层"——
> **不准确**。原生确实有 **13 项机关效果表 `0x0808136C`**
> （索引 = target − 1，入口 `0x080812DC` 用 `cmp #0xc` 卡死上限 13），
> 外加 7 个建立期分支（`0x0806E868`，按 type）。
> 准确说法：**原生 = 7 个拾取处理程序 + 7 个建立期分支 + 13 个机关效果分支**；
> 13 是原生数字，只是它是**按 target 索引的效果表**，不是 13 个拾取程序。
> 详见 `notes/mechanisms-20261020.md`。

### 3.3 剧情底图表 `0x59903C + id*16`（**新发现**）

| 偏移 | 含义 |
|---|---|
| +0 | gfx（LZ77，解压 3072..19264 字节，首字节=宽 16） |
| +4 | palette（LZ77，解压 384 字节 = 16 色 × 2 字节） |
| +8 | tilemap（LZ77，解压 640 字节 = 320 项） |
| +12 | 8bpp 标志（字节值 0 / 1；实测只有这两种值） |

有效 id：**1..7（4bpp）与 9..13（8bpp）**。
id 0、8 为空；**id 14、15 不是本表的条目**——它们的 flags 字
（`0x083409D0` / `0x08342340`）不是 0/1，说明 `0x59903C + id*16` 这张表
到 id 13 为止，id 14 起已经是**另一张表**。（旧记录把 14/15 写成"有效 id"是误判。）
与地图表 `0x53D910` 的 `+0x1C`「剧情底图 ID」字段对应。

#### 3.3.1 原生加载器 `0x08088348` 与 32×32 图（2026-10-20 补）

每个条目被原生代码变成**一张完整的 32×32 硬件 BG 图**：

| 资源 | 去向 | 证据 |
|---|---|---|
| gfx | `0x06000000 + charblock*0x4000` | `0x0808837C` / `0x08088384` |
| palette | `0x05000000`（BG 调色板 RAM，bank 0，192 色） | `0x08088390` / `0x08088392` |
| tilemap | `0x06000000 + screenblock*0x800` | `0x0808839E` / `0x080883A4` |
| 其余 704 项 | `CpuFastSet` 写常数：4bpp=`0x00000000`、8bpp=`0x001E001E` | `0x080883B0` / `0x080883CC` / `0x080883D2` |
| BG 调色板第 0 项 | 清 0（色 0 透明） | `0x080883E2` |
| DISPCNT | 影子在 `0x0300004C`，开 `0x100 << bg_index` | `0x080883E4..0x080883F0` |
| BG 控制寄存器 | `REGBG{arg1}CNT` = arg4 \| (charblock<<2) \| (screenblock<<8) \| (8bpp ? 0x80 : 0) | `0x080883F4..0x08088418` |

尺寸自证：tilemap 640 字节 + 填充 1408 字节（`0x160` 个 32 位字）= **2048 字节
= 1024 项 = 32×32**，正好一个 2 KB 的 BG 屏幕块。
运行时实证：`notes/newgame-2160-vram.bin` 的 `0x06000000` 起逐字节等于 bg 9 的
tilemap，紧接 `0x06000280` 起连续 **704 个 u16 全是 `0x001E`**，一直到 `0x06000800`。

**⇒ 4bpp 与 8bpp 剧情底图是互斥的替代品，不是叠加层**：两者共用同一加载器、
同一组 VRAM 槽位、同一调色板 bank 0，差别只有填充常数与 BG 控制寄存器的 `0x80` 位。
真正的"层叠"是"剧情底图 BG"与"战场地图 layer0/layer1"之间的关系。

**仍未闭合**：8bpp 条目最终走哪个硬件 BG、是否开 256 色（BGxCNT bit8）。
见 `notes/evidence/mechanism-sprite-background-20261020.md` §3.6。

## 4. 事件队列预算（`tools/event_queue_budget.py`）

### 4.1 算法

在剧情 logic 脚本上按 (回合, 相位, sub) 组合做静态遍历，取最深的
事件入队链：

| 指令 | 处理 |
|---|---|
| `0x00` 结束 | 回到栈上的调用点 |
| `0x07` 跳转 / `0x06` 二分支 | 取各分支最大值 |
| `0x13` 调用 | 进入子脚本 |
| `0x34` 回合/相位条件 | 按比较器决定走分支还是顺序 |
| `0x39` 配置匹配 | sub 匹配则走分支 |
| `0x33` | **计 1 个入队事件** |
| 其它 | 计 0，取顺序执行与分支的最大值 |

`0x34` 的比较器：`0`=等于 `1`=不等于 `2`=大于 `3`=大于等于 `4`=小于
`5`=小于等于 `0xFF`=恒真（与 `notes/story-script-vm.md` 一致）。

### 4.2 实测结果

```
46 个战场 logic 脚本，0 个解码问题，46 个全部收敛
最深的原版场景：stage 20 -> 静态深度 17
stage 1 -> 静态深度恰好 16
```

**stage 1 恰好等于 16，是"队列上限 16"的独立实证**：
我们没有采信对方的说法，而是从原版脚本自己算出了这个上限被顶满。

**stage 20 的 17 说明静态分析是过近似**：原版内容本身就超过 16，
所以"16"是**运行时**上限，不是静态可达上限。任何照搬"静态 >16 就拒绝编译"
的做法，都会在原版 stage 20 上误判。

### 4.3 使用规则

> 一个战场最多还能加 **16 − 该战场自身基线深度** 条条件事件；
> 静态深度是上界，不是真值。

各战场基线深度：2..17 不等；stage 1 与 20 最满，stage 40/41/42 只有 2。

## 5. 头像素材（`tools/portrait_assets.py`）

```
头像表  0x5A4DEC + id*40 + expr*8  -> (gfx ptr, palette ptr)
拼块表  0x4643C0 + j*20             -> (tile u32, x u16, y u16, w u16, h u16)
```

- 拼块表共 **6 块**，恰好拼成 **80 × 80**：
  `(64,64,16,16) (64,32,16,32) (64,0,16,32) (32,64,32,16) (0,64,32,16) (0,0,64,64)`
- 有数据的头像 id：**1..63**
- gfx：LZ77 压缩，解压长度恒为 **6400** 字节（80×80 4bpp）
- **palette 是原始 128 字节**（64 色 × BGR555），不是 LZ 压缩 —— 310/314 个表情项符合

> ⚠️ 第三方编辑器把 palette 也当压缩数据处理过（其 `load` 走 `decompress`）。
> 按本仓库的复核结论，palette 应按原始 128 字节读取。

## 6. 与对方说法不一致的三处

| # | 对方说法 | 本仓库实测 |
|---|---|---|
| 1 | `0x02022EA0` "NKT3"、两个 RAM 镜像是可用的运行时状态 | **ROM 里 0 引用**，是第三方自造簿记，不应作为原版状态引用 |
| 2 | 机关有 13 种 | 原生确有 **13 项效果表 `0x0808136C`**（按 target 索引），但**拾取处理程序只有 7 个**且 5/6/7 共用一个；13 这个数字是原生的，"13 个拾取程序"不是（详见 `notes/mechanisms-20261020.md`） |
| 3 | 静态队列 >16 即拒绝编译 | 原版 stage 20 静态值就是 17，**静态分析是过近似**；上限 16 由 stage 1 的原始脚本顶满而得到实证 |

## 2026-10-21 追加：`story_progress` / `story_branch` / `story_config` 的地址与语义

三个字段都在**剧情标志块 `0x020311D4`** 里，本轮把地址与读写点全部钉死。

| 字段 | 地址 | 偏移 | 读点 | 写点 | 语义（由原生代码证明） |
|---|---|---|---|---|---|
| `story_progress` | `0x020311E4` | +0x10 (u16) | `0x0808F5E0`、`0x08095338`、`0x08097BCA` | `0x0808F696`（新游戏清 0）、**`0x08097BD4`（剧情 VM 写绝对值）** | 剧情进度计数；剧情 VM 的一个 opcode 把它**置成绝对值**；调度器拿它跟 **360** 比 |
| `story_branch` | `0x020311EC` | +0x18 (u8) | `0x0808F5A0`、`0x0808F5D4`、`0x0808F67E` | `0x0808F5CC`、`0x0808F5DC`、`0x0808F670` | **分支选择器**：非 0 时调度器改用「after」根表；用完即清 |
| `story_config` ×3 | `0x020311ED..EF` | +0x19..0x1B | `0x0808F67A` 附近 | `0x0808F5C8` 把分支值抄进 `+0x19` | `+0x19` = 分支 id（**同时就是战斗 sub-config 字节**）；`+0x1A/+0x1B` 本轮未见写入 |

关键代码：

```
; 剧情 VM 的「设进度」opcode（0x08097BC8）
0x08097BC8  ldr  r1, [pc, #0x24]     ; 0x020311D4
0x08097BCA  ldrh r0, [r1, #0x10]    ; 旧进度
0x08097BCC  cmp  r0, r4             ; r4 = 操作数（目标进度）
0x08097BCE  bne  0x8097bd2
0x08097BD0  b    0x8097e2c          ; 已经是目标值 -> 不做事（幂等）
0x08097BD4  strh r4, [r1, #0x10]    ; 进度 = 目标值   <<< 唯一的进度写入点
0x08097BDA  bl   0x809c32c           ; 进度变化时的后续处理

; 调度器（0x0808F5A0）
0x0808F5A0  ldrb r1, [r6, #0x18]     ; story_branch
0x0808F5A2  cmp  r1, #0
0x0808F5A4  beq  0x808f5c0          ; 0 -> 用 before 根表
0x0808F5C8  strb r1, [r6, #0x19]     ; 抄进 story_config[0]
0x0808F5CC  strb r5, [r6, #0x18]     ; 分支用完清零

; 调度器（0x0808F5E0）
0x0808F5E0  ldrh r1, [r7, #0x10]     ; story_progress
0x0808F5E2  movs r0, #0xb4 / lsls r0, r0, #1   ; 360
0x0808F5E6  cmp  r1, r0
0x0808F5E8  beq  0x808f604          ; 进度 == 360 -> 特殊分支
```

> 旧笔记写「370 = 原版通关」；**原生代码比的是 360**（`0xB4 << 1`），
> 两者不一致，**以代码为准 = 360**。

### 运行时读数

`tools/closure_story_probe.py`（逐次按键读整个块）：

- **`story_branch` 变了**：55 个剧情场景里只有**场景 31** 读到
  `story_branch = 1`（其余全 0），而且它在 20 次按键里稳定为 1
  ⇒ 该字段**确实是活的**，不是常量。
- `story_progress` 与 `story_config` 在**直接调度**的场景里恒为 0：
  进度只有剧情 VM 的那个 opcode 会写，而直接调度不会跑到它；
  `story_config[0]` 只在分支被消费的那一刻被写入，而那之后立刻被清零。
