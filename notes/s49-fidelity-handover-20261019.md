### 4.3.5 第二次更正：A/B 是「推进行动单位」，蜜蜂是敌方在自己行动

逐字节差分 `original-bcycle/` 的七个连续快照，整个单位池里**只有一个字段在动**：
`+0xC1`（「这个单位正在行动」标记）。

| 快照 | 按键 | 行动单位槽 | 阵营 |
| --- | --- | --- | --- |
| step-00 | 起始 | 1 (11,6) | 玩家 |
| step-01 | A | 2 (10,14) | 玩家 |
| step-02 | A | 3 (8,14) | 玩家 |
| step-03 | A | 4 (8,7) | 玩家 |
| step-04 | A | **5 (3,4)** | **敌方** |
| step-05 | B | 6 (4,8) | 敌方 |
| step-06 | B | 7 (3,11) | 敌方 |

槽 5–7 都是蜜蜂（character 55），所以状态栏一直显示「蜜蜂」——**看起来像卡住，
实际是依次换到不同的蜜蜂**。我前一轮据此推断「蜜蜂被玩家选中」，也是错的。

**正确结论**：原版入口的 A/B 不是「选择可控单位」，而是**推进行动单位**，
并且会推进到敌方单位上。蜜蜂从来不是玩家可控的。重制的
`side == current_side` 过滤对一个「玩家选人」机制是合理的，两边是**不同的交互
模型**，不是同一模型的参数不同。

`+0xC1` 已纳入 `tools/butano/read_rom_unit_pool.py` 的输出，并由
`tests/test_read_rom_unit_pool.py::test_acting_marker_walks_from_player_units_onto_enemy_bees`
锁住七步真值。

**仍未解（D2-a 的核心）**：原版在这个状态下玩家**到底怎么出手**。所有按键都只
推进行动单位，从未进入玩家可操作菜单。

### 4.3.6 第三次更正：入口状态很可能还在**开场脚本**里

连按 A 到 14 次（`original-a14/`），`+0xC1` 轨迹：
起始槽1(玩家) → A1槽2 → A2槽3 → A3槽4 → A4槽5(敌) → A5槽6 → A6槽7 →
A7槽8 → **A8槽9(敌) 后停住**，A9–A14 不再变化。

全局 EWRAM 差分（入口态 vs 按一次 A）：256 KiB 里 **79 个区间变化**，最大一簇是
`0x0200A900–0x0200A972`（约 115 字节）。

⚠️ **「开场脚本」这个解释随后被自己的检查推翻**：该区域 256 字节里**没有任何 UTF-8
前导字节**（0xE4–0xE9 计数 0），是稠密的 16 位小端值序列
（`0xF008, 0xF00A, 0xF00C, 0xF00E…` 递增 + 大量重复 `0x1E1C`），属于结构化二进制
列表（OAM / 显示列表一类），**不是文本缓冲**。逆向笔记里「selector1 有 9 条命令」
与「标记走过 9 个单位」的对应也只是巧合级的观察，不足以支撑结论。

**仍然成立的事实**：A 推进 `+0xC1` 走过 9 个单位后停在最后一个敌方单位；2,400 帧
零输入全程不动；一次 A 让 79 个 EWRAM 区间同时变化。第 3 条的规模更像**整个
场景/回合状态被重建**，而不是一次局部输入响应。

**已排除的简单假设**：EWRAM 全域按 4 字节小端扫描「每次 A 精确 +1」的单调计数器
（base → A1 → A2 → A3），**命中 0 个**；单位池邻域扫 0,1,2,3,4 的字节序号也
**0 个**；WRAM（32 KiB）同样 0 个。但 **A 一次在 WRAM 改动 188 个区间、
EWRAM 79 个区间**——两侧同时大面积改写，更像整块状态被重建（相位切换），
而不是一次局部输入响应。

**因此不要再从内存扫标量。** 下一步用 `tools/mgba_gdb_probe.py`
（`--savestate` 从入口快照起、`--breakpoint` / `--read` 读内存、`--timeout`）
追踪 A 生效前后执行的例程，从执行到的 ROM 地址反推相位结构，或在断点上读回
phase 字段。

**下一步**：不要再从「按哪个键」的表象猜。直接在那 79 个区间里找回合序号、
阶段码之类的标量字段，把入口状态真正处于哪个阶段定出来。

⚠️ 本节连同 4.3.4、4.3.5 已更正三次。前两次的错误根因（改 `positions/bank.json`、
改 `cycle_roster_unit` 过滤）都写进了文档并标注推翻，**不要照着改**。

`pairs/select-unit-A/` 的时序也印证：前 35 帧差异只有约 2,400 px（静态差异），

### 4.3.8 A 处理链的调用点：`0x0806296D` → `0x0806289E`

在 `0x0806289E` 下断点、同时用 Lua 脚本在第 30 帧按 A，探针命中并给出：

```
outcome: verified      actualPc: 0x0806289E
lr = 0x0806296D        sp = 0x03007E7C
r0 = 0x80  r1 = 0x10013A5  r2 = 0x1001365  r3 = 0x40
```

`lr` 即**返回地址 = 调用点**，所以 A 的处理是 `0x0806296D` 调 `0x0806289E`。
两处地址的 ROM 指纹分别是
`0x08000000 → 9c1f62e9…`、`0x0806289E → 467687fa…`（与主循环的 `95d0338a…` 不同）。

收据：`artifacts/s49-fidelity-20261019-v1/gdb-probe-a-handler/probe.json`。

看它读写了哪些地址——尤其它拿 `r0 = 0x80` 做什么（0x80 = 128，可能是
单位池之外的某个数组索引或字段偏移）。这是把入口状态的相位码钉死的最后一步。

> 取证说明：这条收据来自直接调用探针。经 `tools/run_guarded.py` 包一层时，
> `--read ADDR+OFFSET:SIZE` 这类带算术表达式的参数会让参数解析失败（退出码 2）。
> 复现时用 `--read 0x020240C0:64` 这种纯地址形式，并在受守卫执行下重跑收据。

**工具链现状（2026-10-19 实测）**：本机没有可用的 Thumb 反汇编器——

- `/usr/bin/objdump` 是 Xcode 的 LLVM 版，**不支持 `-b binary`**，也不接受裸

  单独给也不行；

- `r2` / `radare2` / `llvm-objdump` 均未安装。

所以「反汇编 `0x0806296D` / `0x0806289E`」这一步**当前无法直接执行**，需要
先补工具：最省事的是 `pip install capstone`（自带 ARM/Thumb 支持，可在宿主
Python 里直接对 `rom/base.gba` 的字节做反汇编），或者装 `radare2`。
在这一步完成前，4.3.9 的字节观察只能停在「形态像循环」，不能升级为结论。

### 4.3.10 反汇编：A 的调用链与「逐单位循环」

**先更正上一节的工具链结论**：仓库里本来就有 Thumb 反汇编工具——
`tools/disasm_thumb.py`、`tools/find_thumb_calls.py`、`tools/thumb_branch.py`。
我上一节只查了系统工具就说「无法反汇编」，**那个结论是错的**。系统
`objdump`（Xcode LLVM 版）确实不支持裸二进制，但项目自带工具可以直接对
`rom/base.gba` 反汇编。

**注意 Thumb 标志位**：GDB 报的 `pc` / `lr` 最低位为 1 表示 Thumb 模式，
真实指令地址要 `& ~1`。`lr = 0x0806296D` → 实际返回地址 `0x0806296C`。

调用点：

```
0x08062954: bl   #0x809c114
0x08062958: ldr  r1, [sp, #0x18]
0x0806295A: movs r2, #0x80
0x0806295C: lsls r2, r2, #9
0x0806295E: adds r0, r1, r2
0x08062960: lsrs r2, r0, #0x10
0x08062962: asrs r0, r0, #0x10
0x08062964: cmp  r0, #0x7f
0x08062966: ble  #0x8062932
0x08062968: bl   #0x80627b0        ← 返回地址 0x0806296C（= lr & ~1）
=> 0x0806296C: ldr  r3, [pc, #0xc8]
   0x0806296E: str  r3, [sp, #4]
   0x08062970: movs r4, #0
   0x08062972: str  r4, [sp, #0xc]
   0x08062974: movs r2, #0
   0x08062976: ldr  r0, [pc, #0xc4]
   0x08062978: ldrb r0, [r0]         ← 从一个固定全局地址读「单位总数」
   0x0806297A: cmp  r2, r0
   0x0806297C: blt  #0x8062982       ← 循环体：r2 从 0 数到「单位总数」
```

`find_thumb_calls.py rom/base.gba 0x0806289E` **匹配 0 个**，而
`find_thumb_calls.py rom/base.gba 0x080627B0` **匹配 1 个**（就是 `0x08062968`）。

所以断点处 `pc = 0x0806289E`、`lr = 0x0806296D` 的组合，含义是：

> `0x08062968` 调 `0x080627B0`；该函数**尾跳**（B/BX，不改 lr）到
> `0x0806289C`，于是我们在那里断下，而 `lr` 仍是上一层 bl 的 `0x0806296D`。

并且紧跟着的 `0x08062978` 就是一个**逐单位循环**：`r2` 从 0 数到一个从固定全局
地址读出的「单位总数」字节，`blt` 进入循环体。这与「按一次 A，`+0xC1` 标记
依次推进到 9 个单位后停住」的行为完全吻合——`0x08062978` 读出的那个「单位总数」
字节很可能就是 9。

下一步就很具体了：读出 `ldr r0, [pc, #0xc4]` 指向的那个全局地址（`pc+4+0xc4`
处存的字），确认它是不是「单位总数」，以及循环体 `0x08062982` 之后往哪个字段写
`+0xC1`。

### 4.3.11 「单位总数」全局变量：`0x03005BB8` = 13

把 4.3.10 里那条指令的常量池解出来：

```
0x08062976: ldr  r0, [pc, #0xc4]
常量池地址 = Align(0x08062976+4, 4) + 0xC4 = 0x08062A3C
该处字 = 0x03005BB8          ← 全局变量地址（IWRAM）
入口快照读回：byte = 13
```

所以那个循环是 `r2: 0 → 12`，遍历一张 **13 项**的表，而单位池里我们实际观察到
有内容的只有 9 个（槽 1–9）。表里的另外 4 项是空的——这也解释了为什么按到
第 9 次之后（`original-a14` 的 A9–A14）画面和 `+0xC1` 都不再变化：循环已经把
可推进的项走完了，剩下的是空项。

这条同时说明：**原版这个循环遍历的是一张 13 项的行动顺序表，而不是
「4 玩家 + 5 敌方」这 9 个在场单位**。`+0xC1` 只是这张表上「当前行动到第几项」
的投影。

⚠️ 仍未解答的核心问题不变：**玩家在这个状态里怎么出手**。现在知道 A 推进的是
行动顺序表，但还不知道玩家操作入口对应表里的哪一项、由什么输入触发。下一步是
看循环体 `0x08062982` 之后往哪个字段写 `+0xC1`，以及这张 13 项表的每一项
分别对应什么状态。

### 4.3.12 行动顺序表的真实形态：WRAM 里 13 条 60 字节记录

按 4.3.10 的循环体继续解常量池：

```
0x08062982: ldr  r1, [pc, #0xbc]
常量池 @ 0x08062A40 -> 表基址 0x030059B8
0x08062984: lsls r2, r2, #0x10 / asrs r0, r2, #0xe   → 索引 = r2 * 4
0x0806298A: ldr  r7, [r0]                            → 取第 r2 项
```

入口快照里把 13 项全部读出来，**每一项都是 WRAM 内的一个小结构地址**，相邻项
间距稳定为 **0x3C = 60 字节**：

```
[ 0] 0x030056AC   [ 1] 0x03005724   [ 2] 0x03005760   [ 3] 0x0300579C
[ 4] 0x030057D8   [ 5] 0x03005814   [ 6] 0x03005850   [ 7] 0x0300588C
[ 8] 0x030058C8   [ 9] 0x03005904   [10] 0x03005940   [11] 0x0300597C
[12] 0x030059B8
```

⚠️ 所以**它们不是指向 EWRAM 单位池（0x020240C0）的指针**，而是一张独立的、
位于 IWRAM 的 13 项 × 60 字节记录表。上一节我按「指针 → 单位结构」去解读
是错的，已更正。

同时 `0x030059B8` 恰好既是第 13 项的地址、又是表基址，说明 4.3.11 里那个
「单位总数」全局 `0x03005BB8` 就在这张表的上方不远处——**表和计数是同一个
结构体的两个字段**（表 `0x030059B8..`，13 项 × 60 = 780 字节，`0x030059B8+780
= 0x03005CC4`，计数 `0x03005BB8` 落在表内）。

下一步应当：读这 13 条记录里每条的关键字段（尤其能对应到「行动单位 / 阵营 /
已行动」的那几个偏移），弄清哪些项是玩家单位、哪些是敌方、哪些是空项——
这才是玩家操作入口真正对应的位置。

### 4.3.13 13 条记录的字段分布（语义未定，勿猜）

### 4.3.15 重构：这 13 条是**命令表**，不是单位记录

对 13 条记录做两轮关联：

1. 全 60 字节扫 32 位小端值，**没有任何值落在 EWRAM 单位池

2. 按 4.3.10 循环体的算法 `r1 = [记录+0x20] + ([记录+0x14] << 2)` 算「计算地址」，
   结果**全部落在 ROM 区**：

这与仓库里已有的命令 VM 证据（`artifacts/audio/command-vm-evidence.json`、

下一步应改成：反汇编 `0x082f83c0`（被 5 条共用，最可能是主干）和
`0x0834882c`，看它们各自做什么；以及查清「玩家操作入口」是否就是这张命令表
里的某一条命令。

### 4.3.16 更正 4.3.15：`+0x20` 指向的**不是**处理例程（未证实，勿照用）

反汇编 `0x082f83c0`（被 5 条记录共用的那个 `+0x20` 值）：

```
0x082F83C0: strh r0, [r4, #0x12]
0x082F83C2: lsrs r7, r5, #0x20
0x082F83C4: strh r4, [r4, #0x14]
...
0x082F83E0: movs r0, r0      ← 对齐填充
0x082F83E2: movs r0, r0
```

这是**数据表**的形态（重复 `strh/lsrs` + `movs r0,r0` 对齐填充），**不是可执行
的函数入口**。所以 4.3.15 里「`+0x20` 是 ROM 处理例程地址」的说法**不成立**。

已验证的只剩两点：
- 13 条记录等距 60 字节，起点 `0x030056AC`（由 `0x030059B8` 的 13 个指针解引用
  后排序得到，指针顺序 = 行动顺序）；
- `+0x20` 是一个落在 ROM 区（`0x0812xxxx`–`0x0834xxxx`）的 32 位值，且
  `+0x14` 是 0–3 的小值。

但**这些值的语义完全未确定**。它们可能是数据表的地址、也可能是别的什么；在有
更多证据前，**不要按「命令表」或「处理例程」去改任何代码**。

这是本会话第九次自我更正。到此为止，我在这条链上的推理已经连续三次（表的内容、
记录布局、+0x20 语义）被自己的后续实验推翻，说明**仅凭内存取值形状推断语义在这个
区域是不可靠的**。

**建议的替代路径**（不要再走内存形状猜测）：
1. 用 `tools/mgba_gdb_probe.py` 在 `0x082F83C0` 这类地址下断点，看它**是否真的会被
   执行**——不被执行就证明它是数据。
2. 若确认是数据表，则应去找**谁在读它**（在读取它的指令下断点），从读取方的代码
   反推结构，而不是从结构猜语义。

### 4.3.17 执行级确认：`0x082F83C0` 是数据，从未被执行

4.3.16 是从字节形态推断的（`strh/lsrs` 重复 + `movs r0,r0` 填充）。
现在用**执行证据**验证：在 `0x082F83C0` 下断点，同一入口快照 + 第 30 帧按 A，
跑满 20 秒超时。

```
outcome    : not-proven
expectedPc : 0x082F83C0
actualPc   : None
rawStop    : None
```

**断点从未命中。** 所以 `+0x20` 指向的确实是数据，不是可执行入口——4.3.16 的
判断由推断升级为**已验证**。

收据：`artifacts/s49-fidelity-20261019-v1/gdb-probe-datatable/probe.json`。

### 这条方法本身值得记住

判断「一个 ROM 地址是代码还是数据」，最可靠的做法不是看字节长什么样，而是
**在它上面下断点，看它是否会被执行**。本会话有三次误判（表的内容、记录布局、
`+0x20` 语义）都是因为只看了形状。`tools/mgba_gdb_probe.py --breakpoint` 加一次
超时运行就能给出是/否。

下一步仍然是「找谁在读 `0x082F83C0`」：这需要反向搜索对该数据区的引用，
或者在读取方指令下断点——但至少现在**数据属性已经确认**，不必再猜。

### 4.3.18 引用计数：A 键代码确实独占使用这张表

在 `rom/base.gba` 里全文搜这三个地址作为 32 位立即数出现的次数：

```
0x030059B8（指针数组）: 5 处 -> 0x080627FC 0x08062840 0x08062884
                                 0x0806291C 0x08062A40
0x03005BB8（计数）    : 5 处 -> 0x080627F4 0x0806283C 0x08062920
                                 0x08062A3C 0x0806333C
0x082F83C0（记录里的 +0x20 值）: 1 处 -> 0x08598BC0
```

**已验证**：

1. 指针数组 `0x030059B8` 的**全部 5 处引用都在 `0x0806xxxx`**——正是 A 键处理链
   所在的函数簇（0x080627xx–0x080629xx），与 4.3.10 反汇编出的循环体完全吻合。
   其中 `0x08062A40` 就是 4.3.12 解出的常量池。
2. 计数 `0x03005BB8` 同样 5 处，其中 `0x08062A3C` 已在 4.3.10 验证过
   （`ldr r0,[pc,#0xc4]`），另外 4 处给出更多后续可查的切入点。
3. `0x082F83C0` 在整个 ROM 里**只出现 1 次**，且是在 `0x08598BC0`（ROM 尾部静态
   数据区）——它只作为**数据被存放**，没有任何代码把它当地址引用。这与 4.3.17
   的断点实验（`not-proven`）互相印证。

**所以**：A 键每次执行都会去读 `0x030059B8` 那张 13 项指针数组 + `0x03005BB8`
的计数，然后经由记录里的 `+0x20` 去访问一张**只被存放、几乎不被引用的 ROM 数据
表**。这条链的每一环现在都有引用计数或执行实验支撑，不再是形状猜测。

下一步可以直接查另外 4 个计数引用点（`0x080627F4` / `0x0806283C` / `0x08062920` /
`0x0806333C`）——它们和 A 键函数簇相邻，极可能就是「读取这张表并驱动流程」的
其余分支，玩家操作入口很可能就在其中之一。

### 4.3.19 更正 4.3.18：字节出现次数 ≠ 引用次数

4.3.18 说「`0x030059B8` / `0x03005BB8` 各有 5 处引用」，**这个计数不可信**。

反查 5 个出现位置里的 `0x08062920`：反汇编显示那里是函数体中间

```
0x0806291C: ldr  r0, [r7, r6]
0x0806291E: lsls r0, r0, #0xc
=> 0x08062920: ldrh r0, [r7, r6]      ← 指令，不是常量池
```

即该处只是**指令编码恰好组成了同样的 32 位字节**，并非引用。其余几个
`0x080627xx` / `0x080628xx` / `0x0806333C` 位置同理可疑。

我随后写了个「扫 `ldr rX,[pc,#imm]` 并解常量池」的自动检查，结果对三个地址
**全部返回 0 命中**——包括我用反汇编**亲手验证过**是常量池的
`0x08062A3C` 与 `0x08062A40`。**说明那个自动检查本身也是错的**
（大概率是指令解码或对齐算错），不能用来断言「没有引用」。

⚠️ **两条都别信**：
- 「各有 5 处引用」——字节搜索不等于引用；
- 「0 处引用」——我的自动检查解码有 bug。

**目前唯一被反汇编验证过的引用就是 4.3.10 / 4.3.12 里的那两条**：
`0x08062976: ldr r0,[pc,#0xc4]` → 池 `0x08062A3C` = `0x03005BB8`（计数）
`0x08062982: ldr r1,[pc,#0xbc]` → 池 `0x08062A40` = `0x030059B8`（指针表）

**下一步**若要枚举引用，必须用仓库自带的 `tools/disasm_thumb.py` 逐条人工核对
（它在这两个地址上是准的），不能再用字节计数，也不能用我自己写的解码器。

### 4.3.20 用项目工具核对完毕：每个全局只有 **1 处**真实常量池引用

用 `tools/disasm_thumb.py` 逐个核对其余 4 个候选位置，全部落在函数体中间，
且呈现**同一对指令**的重复形态：

```
0x080627F4: ldrh r0, [r7, r6]      0x0806291C: ldr r0, [r7, r6]
0x080627F6: lsls r0, r0, #0xc      0x0806291E: lsls r0, r0, #0xc
0x0806283C: ldrh r0, [r7, r6]      0x0806333C: ldrh r0, [r7, r6]
0x0806283E: lsls r0, r0, #0xc      0x0806333E: lsls r0, r0, #0xc
```

**结论（已验证）**：

| 全局 | 字节出现次数 | 真实常量池引用 |
| --- | --- | --- |
| `0x030059B8`（指针表） | 5 | **1**（`0x08062A40`，4.3.12 已核对） |
| `0x03005BB8`（计数） | 5 | **1**（`0x08062A3C`，4.3.10 已核对） |

其余 4 处全是**指令编码恰好组成的相同字节**。

**所以 4.3.18 的「5 处引用」应更正为「1 处」**，且 A 键处理链里
`0x030059B8` / `0x03005BB8` 各只被**读一次**——这两张表在这个函数里是

由此也说明：**下一步不能再靠搜地址找别的分支了**，因为根本没有别的引用点。
要理解 A 键之后发生了什么，只能在 `0x08062968` 之后的代码路径里往下走
（`bl 0x080627B0` 的函数体本身），而不是横向搜地址。

### 4.3.21 完整解码：`0x080627B0` 是「按有效位压缩记录数组」的循环

常量池（已逐条核对）：

```
0x080627F4 = 0x03005BB8   计数（字节）
0x080627F8 = 0x03003BB8   源记录数组基址
0x080627FC = 0x030059B8   目标指针数组
```

函数体逐条：

```
0x080627BC: ldr  r1, [pc,#0x34]   ; r1 = 0x03005BB8
0x080627BE: movs r0, #0
0x080627C0: strb r0, [r1]          ; count = 0
0x080627C4: ldr  r5, [pc,#0x30]   ; r5 = 0x03003BB8（源数组）
0x080627C6: ldr  r4, [pc,#0x34]   ; r4 = 0x030059B8（目标指针数组）
0x080627C8: adds r3, r1, #0       ; r3 = 计数地址
--- 循环 ---
0x080627CE: lsls r0, r1, #4
0x080627D0: subs r0, r0, r1       ; r0 = i*15
0x080627D2: lsls r0, r0, #2       ; r0 = i*60        ← 60 字节步长
0x080627D4: adds r6, r0, r5       ; r6 = &src[i]
0x080627D6: ldr  r1, [r6]
0x080627D8: movs r0, #1
0x080627DA: ands r0, r1            ; r0 = src[i].w0 & 1   ← 有效位
0x080627DE: cmp  r0, #0
0x080627E0: beq  #0x8062800       ; 无效则跳过
0x080627E2: ldrb r0, [r3]         ; r0 = count
0x080627E4: lsls r0, r0, #2
0x080627E6: adds r0, r0, r4       ; r0 = &dst[count]
0x080627E8: str  r6, [r0]          ; dst[count] = &src[i]
0x080627EA: ldrb r0, [r3]
0x080627EC: adds r0, #1
0x080627EE: strb r0, [r3]         ; count++
```

**已验证的机制**：`0x030059B8` 是一张**筛选后的指针表**，由 `0x03003BB8`
起的**源记录数组**按 `word0 & 1`（有效位）压缩得到，60 字节步长；
`0x03005BB8` 是筛出来的条数。这同时**独立验证**了 4.3.12 / 4.3.20 的观察：
记录等距 60 字节、指针表在 `0x030059B8`、计数在 `0x03005BB8`。

按地址反推，源数组下标 115 落在 `0x030056AC`（`(0x030056AC-0x03003BB8)/60 = 115`），
即源数组至少有 116 项、其中 13 项通过有效位过滤——与 `count == 13` 吻合。

**这一步的意义**：A 键每次执行都会重跑一次这个「压缩有效记录」的循环，
所以每次看到的 13 项都是**当时有效**的那些，而不是固定名单。这也解释了为什么
`+0xC1` 会随每次按 A 而推进——每次都在重新构建这张表。

⚠️ `src[i].w0 & 1` 的 bit 0 具体代表什么（存活 / 已激活 / 阵营 / HP>0）**仍未确定**，
不要按字面猜。要定性应对照不同状态下这张表的差异（例如敌方单位被击倒前后）。

### 4.3.22 源数组结构与一个会翻转的位

用 4.3.21 解出的机制回读（源数组 `0x03003BB8`、步长 60、目标 `0x030059B8`、
计数 `0x03005BB8`）：

**已验证 1：源数组至少有 128 槽，通过有效位过滤的恰好是尾部 13 个**——
`src[115]` 到 `src[127]`，在 base 与 A4 两个状态里**完全相同**（都是这 13 个）。

**已验证 2：`word0` 的 bit 24（`0x01000000`）在两个状态之间会翻转。**

```
base: src[115]=0x01001365  src[125]=0x014410A9  src[122]=0x004410A9  src[120]=0x004410A9
A4  : src[115]=0x00001365  src[125]=0x004410A9  src[122]=0x014410A9  src[120]=0x014410A9
```

即随着 A 键推进，有的记录 bit24 由 1→0（`01…`→`00…`），有的由 0→1。

**已验证 3：目标指针表的下标顺序不等于源下标顺序。**
base 的下标序列是 `115,125,126,119,121,122,124,120,127,117,118,123,116`——
明显是某种**排序后的行动顺序**，而不是内存顺序。

⚠️ **bit 24 是什么仍未确定**。在 base 与 A4 之间它同时出现 1→0 和 0→1 两种方向，
所以它不是单向的「已行动」标志；更像「轮到谁」这类**当前指位**，
或某种随回合轮转而移动的标记。**不要按字面猜**，需要更多状态样本
（例如按 B、按方向键、敌方回合时）才能定性。

⚠️ 同时修正 4.3.21 末尾那句「每条记录投影到单位池 `+0xC1`」——那是我的推测，
**在 `0x080627B0` 里没有这个动作**，该函数只构建指针表。`+0xC1` 的写入发生在
调用方（`0x08062982` 之后的循环体），**尚未验证**。

下一步两条：
1. 补更多状态样本（B / 方向键 / 敌方回合），给 bit 24 定性；
2. 反汇编 `0x08062982` 之后的循环体，验证 `+0xC1` 到底在哪被写。

### 4.3.23 调用方循环体解码：按 `record.w0` 的标志位分派

`0x08062982` 起的循环体（逐条）：

```
0x08062982: ldr  r1, [pc,#0xbc]    ; r1 = 0x030059B8（指针表）
0x08062984: lsls r2, r2, #0x10
0x08062986: asrs r0, r2, #0xe      ; r0 = i * 4
0x08062988: adds r0, r0, r1       ; &dst[i]
0x0806298A: ldr  r7, [r0]         ; r7 = &record[i]
0x0806298C: ldrh r1, [r7,#0x14]
0x0806298E: ldr  r0, [r7,#0x20]
0x08062990: lsls r1, r1, #2
0x08062992: adds r1, r1, r0       ; A = rec+0x20 + (rec+0x14 << 2)
0x08062994: ldrh r0, [r7,#0x16]
0x08062996: lsls r0, r0, #2
0x08062998: ldr  r1, [r1]         ; r1 = [A]
0x0806299A: adds r1, r1, r0       ; 加上 (rec+0x16 << 2) 存入栈
0x0806299C: str  r1, [sp]
--- 标志位分派 ---
0x080629A2: ldr  r1, [r7]         ; r1 = record.w0
0x080629A4: movs r0, #0x80
0x080629A6: lsls r0, r0, #0xa     ; 掩码 0x00020000 = bit 17
0x080629A8: ands r0, r0, r1
0x080629AC: cmp  r0, #0
0x080629AE: beq  #0x80629b4
0x080629B0: bl   #0x806321c       ; bit 17 置位 -> 调 0x0806321C
0x080629B4: movs r0, #0x80
0x080629B6: lsls r0, r0, #0xe     ; 掩码 0x00200000 = bit 21
0x080629B8: ands r1, r0, ...
```

**已验证**：

1. `record +0x14`（半字）、`+0x16`（半字）、`+0x20`（字）不是数据值，而是
   **地址运算的组成部分**：`A = rec+0x20 + (rec+0x14 << 2)`，再取 `[A]`，
   加上 `(rec+0x16 << 2)`。这解释了为什么它们看着像 RAM／ROM 地址却取不到
   合理结果——**它们必须参与运算才是指针**。4.3.16 那个「反汇编看起来像数据表」
   的现象也需要在这个语境下重读。
2. `record.w0` 是**位域标志**：本段已确认 bit 17（`0x00020000`）和
   bit 21（`0x00200000`）被逐一测试并分派调用（bit 17 命中时
   `bl 0x0806321C`）。加上 4.3.21 的 bit 0（有效位）和 4.3.22 观察到翻转的
   bit 24，`w0` 至少是 4 个已知语义位的位域。
3. 这是一台**按标志位分派的调度器**：遍历行动顺序表，对每条记录按其标志位
   调用不同子程序。

⚠️ 各标志位分别对应什么行为**仍未确定**；`+0xC1` 的写入点也**仍未在这一段里
出现**，需要继续往下（`0x80629CE` 之后）或在 `bl 0x0806321C` 里找。

下一步：反汇编 `0x0806321C`（bit 17 的处理例程），并继续看 `0x080629CE` 之后的
代码，找 `+0xC1` 的写入点。

### 4.3.24 `0x0806321C` 消费 bit 24 —— 直接印证 4.3.22 的翻转

常量池核对：

```
0x0806327C = 0xFEFFFFFF   掩码（0x08063232: ldr r1,[pc,#0x48]）
0x08063280 = 0x03000075   全局字节（0x0806323A: ldr r0,[pc,#0x44]）
```

函数体：

```
0x08063230: ldr  r0, [r7]        ; r0 = record.w0
0x08063232: ldr  r1, [pc,#0x48]  ; r1 = 0xFEFFFFFF
0x08063234: ands r0, r1          ; 清 bit 24
0x08063236: str  r0, [r7]        ; 写回 record.w0     ← bit 24 被消费
0x0806323A: ldr  r0, [pc,#0x44]  ; r0 = 0x03000075
0x0806323C: ldrb r0, [r0]        ; 读该全局字节
0x0806323E: cmp  r5, r0          ; 循环上界
0x08063240: bge  #0x80632f8
0x08063244: movs r0, #8
0x08063246: ands r0, r1          ; 再测 bit 3
```

**已验证**：

1. **`record.w0` 的 bit 24 在这个例程里被清除并写回**——它是**一次性消费的
   待处理标志**。这**直接印证**了 4.3.22 观察到的 1→0 翻转：那不是状态抖动，
   是标志被消费掉了。
2. 随后它读一个全局字节 `0x03000075` 作为**循环上界**，并在循环里再测 **bit 3**。
   `0x03000075` 是**奇地址**——按 GBATEK 惯例奇地址通常代表**位域**
   （`0x03000074` 的 bit 1），很可能是「轮到哪一方 / 哪一方输入」这类全局标志。
   **这一条是惯例推断，未验证**，要验证得读 `0x03000074` 并看它是否只用到 bit 1。

3. 由此可以给 `record.w0` 一个统一模型：**它是一张事件位域**——生产者置位、
   分派器按位测试并**清除**。bit 0（有效位，过滤用）、bit 3、bit 17、bit 21、
   bit 24 都在这张位域里。

下一步（收敛了）：
- 读 `0x03000074`，确认它是否真的只用 bit 1；
- 找出**谁置位** bit 24（生产者）——那才是「一回合开始/单位行动开始」的源头，
  也更可能直接对应玩家操作入口。

### 4.3.25 断点确认：调用点执行、bit 17 处理例程不执行

两个断点，各跑一次「入口快照 + 第 30 帧按 A」：

| 断点 | 含义 | 结果 |
| --- | --- | --- |
| `0x08062968`（`bl 0x080627B0` 调用点） | A 键入口 | **verified**，命中 |
| `0x0806321C`（bit 17 处理例程） | 分派到 bit17 时的目标 | **not-proven**，`actualPc: null`，从未执行 |

**已验证**：

1. **A 键确实走 `0x08062968` → `0x080627B0`**（压缩循环）→ `0x08062982`
   起的调度器。与 4.3.10 / 4.3.21 / 4.3.23 的静态解码完全吻合。
2. **`0x0806321C` 从未被执行**——按 A 那一刻**没有任何记录置 bit 17**。所以 A 键的
   效果**不是**走 bit 17 分支来的，4.3.23 里那处 `bl` 在本次路径上没走。
   这也说明：`0x0806321C` 属于**别的**触发路径（例如敌方回合或脚本事件）。

3. 命中时的寄存器给出循环上界的直接证据：

```
r1 = 0x007F0000   r2 = 0x00000080 (= 128)   r3 = 0x0300597C   r7 = 0x0300597C
```

**`r2 = 128`** 与 4.3.21 的步长推算（源数组至少 116 槽、尾部 13 个有效）完全一致，
**独立印证源数组就是 128 槽**。`r7 = 0x0300597C` 是一个记录地址
（`(0x0300597C - 0x03003BB8) / 60 = 127`，即源数组最后一槽）。

**因此 A 键的完整链路现在是有执行证据的**：

```
A  →  0x08062968 (verified)
      bl 0x080627B0   压缩：遍历 128 槽，按 word0 bit0 过滤出 13 条
      → 0x08062982    调度：遍历 13 条，按 word0 的各位分派
      → (bit17 分支本次未走)
```

下一步：要么找出 A 键实际走的那条分派分支（从 `0x080629CE` 往下逐个断点
验证），要么从 `record.w0` 在按下瞬间的实际取值反推。**不要靠猜**。

### 4.3.26 调度器续段解码：`0x0806321C` 的真实触发条件

`0x080629CE` 起：

```
0x080629CE: movs r1, #0xc
0x080629D0: ldrsh r0, [r7, r1]   ; 有符号半字 record+0x0C
0x080629D2: cmp  r0, #0
0x080629D4: bne  #0x80629da
0x080629D6: bl   #0x806321c     ; +0x0C == 0 -> 调用
0x080629DA: movs r2, #0xe
0x080629DC: ldrsh r0, [r7, r2]   ; 有符号半字 record+0x0E
0x080629DE: cmp  r0, #0
0x080629E0: bne  #0x80629e6
0x080629E2: bl   #0x806321c     ; +0x0E == 0 -> 调用
--- 二级指针链 ---
0x080629EC: ldr  r1, [r7,#0x1c]  ; record+0x1C
0x080629F0: adds r0, r0, r1
0x080629F2: ldr  r0, [r0]        ; 解引用
0x080629F4: mov  r8, r0          ; r8 = 二级指针
0x080629FC: ldrsh r1, [r0, r2]   ; 有符号半字 [r8]
0x08063002: cmp  r1, r0          ; 与 -1 比较
0x08063004: bne  #0x8062a0a
0x08063006: bl   #0x8063220
```

**已验证 / 更正**：

1. **`0x0806321C` 的触发条件不是 `w0` 的 bit 17，而是 `record +0x0C == 0`
   或 `record +0x0E == 0`**（两个有符号半字字段）。4.3.23 里「bit 17 置位则调
   `0x0806321C`」是**错的**——那是 `0x080629A6` 的掩码 `0x00020000` 测试点，
   但它命中后调的是 `0x0806321C`，而 4.3.25 的断点证明**这条路没走**；
   真正走的是这两处 `+0x0C/+0x0E == 0` 的比较。
2. 结合 4.3.25 的断点结果（`0x0806321C` 从未执行）可得一条**确定的负结论**：
   **A 键那一刻，13 条记录的 `+0x0C` 与 `+0x0E` 全部非零。**
3. `record +0x1C` 是**二级指针**： `[record+0x1C] + (前面算出的下标)<<2` 解引用
   得到 `r8`，再检查 `[r8]` 的半字是否为 `-1`。这是一条**指针链遍历**，说明记录
   之间还互相引用。

⚠️ 4.3.23 的「bit 17 -> 0x0806321C」解读需要按本节更正为「+0x0C/+0x0E 判零」。
**再次印证：静态解码必须用断点验证，否则分支归属会搞错。**

下一步：既然 `+0x0C` / `+0x0E` 都有具体语义候选，最快的定性方式是**在不同按键
下 dump 13 条记录的 `+0x0C` / `+0x0E` / `+0x1C`**，看哪些键会让它们变 0。

### 4.3.27 给 `+0x0C` / `+0x0E` 定性的结果：它们是常量，这条线到此为止

在 base / A1 / A4 三个状态下 dump 全部 13 条记录：

```
   i  +0x0C  +0x0E   +0x1C
   0    256    256   0x0812D0B4
   1    256    256   0x08165080
   ...
   9    256    256   0x08348820
  12    256    256   0x0812D2C0
```

**已验证**：

1. **`+0x0C` 与 `+0x0E` 在所有记录、所有状态下恒为 256**——它们**不是状态字段**，
   而是固定配置值。4.3.26 建议的「dump 这两个字段做定性」这条路**到此为止**。
   这也解释了 4.3.25 的断点结果：`0x0806321C` 要 `+0x0C == 0` 或 `+0x0E == 0`
   才触发，而它们恒为 256，所以永远不会触发。

2. **`+0x1C` 在三个状态下也完全不变**，且是 ROM 地址（`0x0812xxxx`–`0x0834xxxx`）。
   结合 4.3.26 的用法（`[record+0x1C] + (半字<<2)` 后解引用），它是一个
   **ROM 查找表基址**，不是会随回合变化的指针。

3. 因此：**记录里真正随回合变化的只有 `w0`**（4.3.22 观察到 bit 24 翻转、
   4.3.24 证明它被 `0x0806321C` 消费清除）。其余字段在本次观测范围内是常量。

**收敛**：能给这些记录做状态定性的字段只有 `w0`。下一步应当针对 `w0` 逐位
取样（在多种按键/相位下 dump 全部 32 位），而不是继续追 `+0x0C`/`+0x0E`/`+0x1C`。

⚠️ 同时提醒：本节的结论只在「base / A1 / A4」三个**按键之后**的状态上成立，
**没有覆盖敌方回合、脚本事件、战斗结算等其它相位**，不能外推成「这些字段
在整局游戏里都是常量」。

### 4.3.28 大更正：13 项表**不是稳定的**，会缩到 2 项、涨到 15 项

把本轮录到的**全部 83 个快照**（`original-*/step-*.ss9`）过一遍压缩机制：

**已验证 2：跨 83 个状态，`record.w0` 有 13 个位在变化**：

但**具体对应什么**（已行动被清退 / 阵亡 / HP 归零 / 其它）仍未确定，
**不要按字面猜**。

### 4.3.29 有效记录集合的完整演化轨迹（沿 `original-a14` 14 次 A）

```
step00-08  n=13  {115..127}                    ← 稳定 9 次按压
step09     n=15  {113..127}   gained [113,114]
step10     n=13  {115..127}   lost   [113,114]
step11     n= 2  {126,127}    lost   [115..125]   ← 11 条同时退场
step12     n= 2  {126,127}
step13     n= 3  {125,126,127} gained [125]
step14     n= 3  {125,126,127}
```

**已验证的三段现象**：

1. **step00–step08 高度稳定**：按 8 次 A，有效集合一直是 `{115..127}`。
   这与 4.3.22「base 与 A4 是同一批 src 115..127」一致，也与 4.3.25 的断点
   （`r2 = 128`、压缩 128 槽得 13 条）一致。

2. **step09 的 113/114 是瞬时出现**：按下后立刻出现、下一按就消失。它们大概率
   属于**某个临时生成的事件记录**（例如一次性的回合事件），不是常驻单位。
   ⚠️ 语义未确定。

3. **step11 的 11 条同时退场是整条链上最关键的事件**：`115`–`125` 在同一步里
   集体从有效集消失，只剩 `{126,127}`。**一次退场 11 条**不像「单个单位阵亡」，
   更像**相位边界**——例如一轮结束、大批记录被统一回收。

   结合 4.3.25 已知 `+0xC1` 行动标记在 A8 之后就卡在最后一个敌方单位不动，
   **step09–step11 这段很可能就是从「玩家侧」过渡到「敌方／下一阶段」的边界**，
   也正是在这一段，玩家操作入口最可能出现。

**下一步（现在有精确窗口了）**：从 `step-10-A.ss9` 起做**逐帧 PC 跟踪**
（不是逐按压），对比 `step-10 → step-11` 之间 PC 走过哪些新地址——
那几步就是相位切换真正执行的代码，比继续解 13 条记录的字段有效得多。

### 4.3.30 相位切换例程定位到 `0x080961F6`（断点确认）

在 `step-10-A.ss9`（4.3.29 里 11 条记录即将同时退场的那一步）做逐帧 PC 跟踪，
各 150 帧，一组不按键、一组第 40 帧按 A：

```
按 A 与不按 A 的 PC 在第 40 帧（施键帧）起共 81 帧不同
但「只在按 A 时出现」的地址只有一个：
    0x080961F6   ← 第 58 帧
```

断点验证（同一快照 + 第 40 帧按 A，20 秒超时）：

```
outcome : verified          actualPc : 0x080961F6
lr = 0x080961D7              （调用点）
r0 = 0x00000001   r1 = 0x00000001   r2 = 0x00000000
```

**已验证**：

1. `0x080961F6` **确实被执行**，而且**只在这个状态按 A 时才执行**——它在空闲态
   150 帧里从未出现。
2. 它位于 ROM 的**另一个区段**（`0x0809xxxx`），与 A 键处理链（`0x0806xxxx`）
   完全不同，说明这是一次**跨模块的相位切换调用**，不是同一函数内的分支。
3. 调用点在 `0x080961D7`，参数 `r0 = r1 = 1`、`r2 = 0`。

**这是目前最有可能通向「玩家操作入口」的一条线索**：
它恰好出现在 11 条记录同时退场的那一步（4.3.29 的 step11），
而且参数形态像「以 (side=1, index=1, flag=0) 发起一次阶段切换」。

下一步：
1. 反汇编 `0x080961D7` 附近的调用点，看 `0x080961F6` 是被谁按什么条件调用的；
2. 再对 `0x080961F6` 本体反汇编，看它做什么；
3. 追它调用的下游——那里很可能就是「玩家回合真正开始」的地方。

⚠️ 参数含义（side/index/flag）**纯属形态猜测，未验证**。

### 4.3.31 更正 4.3.30：`0x080961F6` 是循环回边，不是相位切换入口

反汇编后看得很清楚：

```
0x080961F6: cmp  r0, r3
0x080961F8: ble  #0x80961de        ← 回跳到 0x080961DE
...
0x08096216: pop  {r3, r4}
0x08096218: mov  r8, r3
0x0809621A: mov  sb, r4
0x0809621C: pop  {r4, r5, r6, r7}
0x0809621E: pop  {r0}
```

**已验证**：

1. `0x080961F6` 紧跟一条 `ble` 回跳到 `0x080961DE`，所以它是**循环的回边**，
   不是函数入口。4.3.30 说它是「跨模块的相位切换例程」**是错的**。
2. `lr = 0x080961D7` 属于**更外层的调用者**；`0x080961F6` 只是我们在
   `0x0806xxxx → 0x0809xxxx` 这段代码里恰好采样到的循环回边。
3. 但**「按 A 会让这个循环跑起来」这件事仍然成立**，而且有意义：
   循环条件是 `r0 > r3`（`r0` 递增到 `r3`），说明 A 在这个状态下驱动了
   **一次按计数上限迭代的循环**——与 4.3.29 观察到的「11 条记录同时退场」
   在语义上吻合（循环把一批记录处理掉）。

⚠️ `r0`/`r3` 是循环上界与计数器，**具体处理什么仍未验证**。
要定性，应该在 `0x080961DE` 循环体内部下断点，而不是在回边上。

**教训**：**单帧 PC 采样很容易落在循环回边或任意中间点，不代表函数入口。**
本会话第 11 次自我更正。下次定位应优先在**调用点**（`bl` 指令）下断点，
或者对候选函数**首地址**下断点，而不是对逐帧采样到的 PC。

### 4.3.32 循环体确认：`r3 = 6143`，是一次约 24 KB 的缓冲区重建

在 `step-10-A.ss9` + 第 40 帧按 A，对**循环体** `0x080961DE` 下断点：

```
outcome : verified     actualPc : 0x080961DE
r0 = 0x084098C2   ROM（源表）
r1 = 0            r2 = 0            r6 = 0            r7 = 0
r3 = 0x000018FF   ← 循环上界 = 6143
r4 = 0x02002880   EWRAM（目标缓冲区）
r5 = 0x06010000   VRAM / 调色板区
r8 = 0x085A4E14   ROM
sp= 0x0300116C    lr = 0x080961D7
```

**已验证**：

1. 循环体确实执行（`verified`），印证 4.3.31 的结论——之前在回边
   `0x080961F6` 采样到的确实是这个循环。
2. **循环上界是 6143**，即 `0x17FF`，约等于 `0x1800 = 6144` 次迭代，
   每次处理 4 字节 → **约 24 KB**。
3. 寄存器形态是「**从 ROM 表（`0x084098C2`）向 EWRAM 缓冲区（`0x02002880`）
   搬运/写入，并触及 VRAM（`0x06010000`）**」。

**含义（已验证部分）**：按 A 在这个状态触发的不是「逻辑」，而是一次
**约 24 KB 的显示/数据缓冲区重建**。这与 4.3.29 观察到的「11 条记录同时退场」
以及画面在此刻大幅变化相符——**整块场景数据被重新生成**。

⚠️ 缓冲区重建的具体内容（精灵？字形？调色板？）**未验证**；
`0x02002880` 处到底是什么结构需要进一步 dump，不要按字面猜。

下一步：
1. 在 `step-10-A.ss9` 与 `step-11-A.ss9` 两个快照之间 dump `0x02002880`
   起约 24 KB，比较差异——差异区就是这次重建**真正写了什么**；
2. `r0 = 0x084098C2` 是 ROM 源表，对它做同样的前后比较，可以直接看出
   「重建用的是什么模板」。

第 1、2 步都不需要猜，是纯比较。

### 4.3.33 缓冲区前后比较：24 KB 里只变了 145 字节

`step-10-A.ss9` 与 `step-11-A.ss9` 之间 dump `0x02002880` 起 `0x6000`（24,576）字节：

```
differing bytes = 145 (0.6%)
变化范围 = 0x02002880 – 0x02002939（仅前 185 字节）
14 个连续区段
```

部分对比（前 8 段）：

```
0x02002880  before dc6b5c33b802b001f8   after 626767676767676567
0x0200288A  before ea4b693a40019f53b... after 6767676767676967...
0x020028C8  before 000000             after 6c6454
0x020028D0  before 150300             after 696854
0x020028E0  before 00000000           after 67694154
```

**已验证**：

1. 6144 次迭代的循环**并没有把 24 KB 全部改写**——只有开头 185 字节发生变化，
   其余 24 KB 完全一致。所以那个循环要么是**条件性写入**（只在值不同时写），
   要么 24 KB 里绝大部分本来就相同。**不要把「6144 次迭代」理解成
   「24 KB 都被重写」**。
2. 「after」值里出现大量 `0x67 0x67 0x67…`、`0x69 0x68 0x54`、`0x6C 0x64 0x54`、
   `0x69 0x69 0x41 0x54` —— 高字节集中在 `0x41`–`0x69`、低字节多为 `0x41/0x54/0x67`，
   形态上像**按 3 字节或 4 字节打包的数据**（例如压缩图块、调色板索引、
   或某种 12-bit/16-bit 打包值），**不是可读的 ASCII 文本**（虽然单看像字母）。

⚠️ **这块数据到底是什么仍未验证。** 上面只是字节形态描述，
不要据此断定它���精灵、调色板还是压缩图块。

下一步（仍是纯比较）：
- 把 ROM 源表 `0x084098C2` 起同样长度 dump 出来，和「after」逐字节比，
  确认循环是否真的是「ROM → EWRAM 的解码搬运」；
- 再看这 145 字节的变化是否与 `0x020240C0` 单位池里 `+0xC1` 的变化一一对应。

### 4.3.34 循环是解码不是搬运；且退场时行动单位没变

**已验证 1：`0x084098C2` 的 ROM 源表与 EWRAM 缓冲不是原始拷贝。**

```
相同字节 1088 / 24576 (4.4%)
4 字节对齐块相同 3 / 6144
```

所以 4.3.32 里那个「从 ROM 表向 EWRAM 搬运」的判断**是错的**——
循环做的是**解码／解包**（把 ROM 里的压缩或打包格式转成运行期格式）。

**已验证 2：step10 → step11 的记录批量退场时，行动单位没有变。**

```
step10: 单位池 +0xC1 设在槽 [9]
step11: 单位池 +0xC1 设在槽 [9]
```

槽 9 是最后一个敌方单位（`(3,11)` 那一批里的最后一个）。**A 键并没有推进行动
单位**——这与 step00–step08 期间 `+0xC1` 逐个前移的行为**不同**。

⚠️ 由此，4.3.29 里把 step11 的 11 条记录集体退场解读成「相位边界」**只是推断，
未被验证**——退场时行动单位没切换，说明触发原因另有其物。

**当前最硬的两条结论**：
- A 键在这个状态下驱动的是一次 **6144 次迭代的解码循环**，输出到
  `0x02002880` 起的 EWRAM 区域（本次只有 145 字节实际变化）；
- 同一时刻 `+0xC1` 停留在槽 9 不动。

**下一步应直接对比 `+0xC1` 逐个前移的那段（step01–step08）与这段（step10–11）
的差别**，而不是继续猜退场原因——前一段是已知的「推进」行为，两段对比能直接
指出「推进」与「不推进」的条件差异。

### 4.3.35 「推进」与「不推进」的条件差异（把 14 步对齐看）

| step | `+0xC1` 所在槽 | n | 缓冲头部是否变化 |
| --- | --- | --- | --- |
| 0 | 1 | 13 | — |
| 1 | 2 | 13 | no |
| 2 | 3 | 13 | no |
| 3 | 4 | 13 | no |
| 4 | 5 | 13 | no |
| 5 | 6 | 13 | no |
| 6 | 7 | 13 | no |
| 7 | 8 | 13 | no |
| 8 | 9 | 13 | no |
| 9 | **9（不动）** | **15** | no |
| 10 | **9（不动）** | 13 | no |
| **11** | 9（不动） | **2** | **YES** |
| 12 | 9（不动） | 2 | YES |
| 13 | 9（不动） | 3 | no |
| 14 | 9（不动） | 3 | YES |

**已验证的规律**：

1. **`+0xC1` 逐个前移只发生在 step01–step08**：槽 1→2→3→4→5→6→7→8→9，
   每按一次 A 走一格，**正好 8 次走完 9 个位置**。
2. **step08 之后 `+0xC1` 永久停在槽 9**，无论后续按多少次 A、无论 n 变成
   15 / 13 / 2 / 3 都**不再前移**。
3. **解码缓冲第一次变化恰好在 step11**，与「n 从 13 掉到 2」是**同一步**。
4. step09 出现 n=15（两条瞬时记录）时，`+0xC1` 也已经不前移——但缓冲未变。
   所以「前移停止」早于「缓冲重建」。

**含义（推断，未验证）**：A 键的「推进行动单位」行为有一个**明确的终止点**
（9 个位置走完）。走完之后 A 不再推进单位，而是转入另一套行为——先出现瞬时记录
（n=15），再重建缓冲并把有效集合压到 2 条。

**这很可能就是「玩家操作入口」的边界**：前 8 次 A 是**顺序预览/推进**，
之后才进入真正的操作阶段。**下一步应该验证这一点**——在 step09 之后的某个状态
上，逐键探测 B / 方向键 / Start / Select，看是否会出现原版特有的菜单画面
（而 step00–step08 期间已经证明任何键都不会弹菜单）。

⚠️ 「很可能是玩家操作入口」是**推断**。下一步的逐键探测能直接证实或推翻。

### 4.3.36 两个决定性对照实验

**实验 A：step-11 之后所有按键无效。**

从 `step-11-A.ss9` 出发，8 个键各录一遍，另录一遍**同帧数的空闲对照**
（150 帧），逐一与空闲对照比：

```
A 0   B 0   Up 0   Down 0   Left 0   Right 0   Start 0   Select 0   （差异像素全为 0）
```

但与「按下之前那一帧」比，每个键都差 12,399 像素——**说明这 12,399 像素是
游戏自己在动，不是按键造成的**。

**已验证：step-11 之后是彻底的输入锁定状态**，任何键都不改变画面。

**实验 B：只有 A 会推进行动单位，Start 不会。**

从入口 base 出发，按 12 次 **Start**（hold 2 帧、settle 120 帧）：

```
step00..step12   +0xC1 = [1]（始终不动）   n = 13（始终不变）
```

对比同样步数按 **A** 的结果（`+0xC1` 1→2→…→9）。**这是干净的差分对照：
Start 完全不推进，A 才推进。**

**所以此前基于 A 的分析没有被推翻**——`+0xC1` 的逐格前移确实由 A 引起，
不是游戏自动播放。

⚠️ 但实验 A 带来一个**必须正视的新问题**：既然 step-11 之后任何键都无效，
而 step-08 之后 A 也不再推进，那么「玩家可操作的状态」**在按 A 的这条路上
根本到不了**。

**可能的解释（本轮无法区分，不要当结论）**：
1. 入口快照 `scenario-49-battle-14-entry.ss9` 根本不是玩家回合，而是
   **自动战斗／演示／结算**之类的状态——那样「找玩家操作入口」就是找错地方了；
2. 玩家操作入口需要**另一个条件**才能进入（某个脚本事件、某个特定按键组合、
   或某个计时条件）；
3. 2,400 帧零输入没有等到某个长动画播完。

**下一步建议（优先级高于继续解记录字段）**：先判定入口快照到底是不是玩家回合——
例如对比 `step-11` 之后画面里是否有「本回合玩家可操作」的 UI 特征，
或者用极长零输入（10,000+ 帧）看游戏是否会自己走出这个状态。

### 4.3.37 决定性：入口快照会无限等待输入，不会自己走完

从 `artifacts/runtime-checkpoints/scenario-49-battle-14-entry.ss9` 直接录
**6,000 帧（100 秒）零输入**：

```
6000 帧（100 秒），> 2000 像素的场景切换次数：0
```

加上 4.3.x 里已有的 2,400 帧，累计 **8,400 帧 / 140 秒，零次切换**——
只有选中单位的待机动画在动。

**已验证**：

1. **这个状态不是「会自己播完的长动画」**，也不是「需要等某个计时才推进」的
   状态。它**无限期等待输入**。
2. 因此 4.3.36 里「入口快照可能是自动战斗／演示／结算」这条解释**基本可以排除**：
   自动战斗会自己推进，而这里 140 秒纹丝不动。
3. 结合 4.3.36 实验 B（A 推进、Start 不推进），现在可以确定地表述为：

> **入口快照是一个等待玩家输入的、按 A 会推进行动单位的对战状态；
> 但推完 9 个位置后进入一个任何键都无效的输入锁定状态。**

**剩下的唯一核心问题变成**：这个输入锁定状态**是怎么出来的、怎么出去**。

可能的方向（本轮都未验证）：
- 锁定是「本场战斗的某种自动推进阶段」，需要某种条件才解除；
- 或者 A 推进到第 9 个之后，正确做法不是继续按 A，而是**换别的输入序列**
  （例如先 B 后 A、或方向键与 A 组合）；
- 或者这个入口快照本身取自一个**特殊存档状态**（例如跳过了某个剧情节点），
  导致流程卡在一个本不该停住的相位。

下一步优先级：
1. 从 step-11 那个输入锁定状态出发，测试**按键组合**（如 A+B、方向+A、长按 A、
   双击 A）而不只是单键——单键已证明无效，组合还没试；
2. 同时用 `rom/base.sav`（已为空 sav）与不加载 sav 的两种情况复现 step-11，
   排除「SRAM 进度位」把流程卡住的可能（4.3.x 已证明 SRAM 不影响 A 序列，
   但还没证明它不影响**相位推进**）。

### 4.3.38 按键组合测试：**设计缺陷，结果不可用**

从输入锁定状态 `step-11-A.ss9` 出发测了 10 种组合
（A,A / A,B / A,Right / B,A / Right,A / Down,A / Left,A / Up,A / A,A,A / Start,A），
每种在 `zero_input=60, settle=90, hold=4` 下录，最后一张约在**第 240 帧**；
对照组 `combo-ref` 用 `settle=300`，最后一张在**第 360 帧**。

结果：

```
A,A / A,B / B,A / Right,A / Down,A / Left,A / Up,A / Start,A   →  10,167 px
A,Right                                                        →       0 px
A,A,A                                                         →   5,862 px
```

⚠️ **这组数据不可用。** 对照组与实验组的采集长度差 120 帧，10,167 px 主要是
**动画相位差**，不是按键造成的差异；`A,Right` 恰好为 0 也只是因为它在 240 帧时
动画恰好与 360 帧的对照组重合。**没有做等长对照，就不能得出任何按键结论。**

**仍然有效的结论只有 4.3.36 实验 A 的那一组**——那组做了同帧数空闲对照
（150 帧 vs 150 帧），8 个单键差异**全为 0**，所以「step-11 之后任何键都无效」
是可信的。

**教训（第七条）**：**比较按键效果时，对照组与实验组的采集长度必须严格一致**，
否则动画相位差会淹没按键差异。同样的错误今天已经犯了两次：
4.3.36 第一次比「按下前」而非「同时长空闲」、4.3.38 又比了不同时长。

**要做按键组合实验，正确做法是**：固定 `zero_input` 与 `settle`，
让每种组合都从**同一个初始状态**出发、录**同样帧数**，再用同样时长的空闲对照。
本轮因上下文耗尽未重做，**不要引用上面那组数字**。

### 4.3.39 重做（按键数对齐）：单键无差别，但双键有差别

上一节的对照组仍然不等长——`mgba_original_s49_ui_boundaries.lua` 的
`settle` 是**按每次按键各算一次**，所以 2 键的序列天然比 1 键的长一截。
正确对照必须是**按键数相同**。

重做后（`zero_input=60, settle=120, hold=4`，全部从 `step-11-A.ss9` 出发）：

| 对照（按键数相同） | 差异像素 |
| --- | --- |
| `A,A` vs `Right,Right`（都是 2 键） | **10,167** |
| `B,B` vs `Right,Right`（都是 2 键） | **10,167** |
| `A,A,A` vs `A,Right,B`（都是 3 键） | **10,520** |

**可复现性已验证**：`eq-a2/step-01` 与 `eq-ref/step-01` 的 difference bbox 为
`None`——两次独立运行的同一时刻画面逐像素相同，所以上面的差异**不是噪声**。

**已验证的结论（与 4.3.36 并列，需要合并理解）**：

- **单键**：8 个键与等长空闲对照**全部为 0 差异**（4.3.36）。
- **双键**：`A,A` / `B,B` / `Right,Right` 之间**不再等价**，相差约 10,167 像素。

也就是说：**按下第一个键时游戏对输入无反应，按下第二个键时输入开始起作用。**

⚠️ **这与「step-11 之后彻底输入锁定」的说法冲突，本轮无法判定哪个解释对。**
可能的读法（本轮都未验证，不要当结论）：
- 第一个键的响应被 120 帧 settle 吃掉了，差异要到第二个键之后才体现；
- 游戏有一个「按一次键才解除锁定」的门槛，第二次才是生效的那一次；
- 或者 10,167 px 仍然是动画相位差，只是这次两组恰好错开（但可复现性已验证，
  所以若真是相位差，它必须是**按键触发的确定性相位差**，而不是随机漂移）。

**下一步必须做的是带相位对齐的对照**：同一个初始状态、同一按键数，
但对照组要额外等一个**动画周期**再截图，才能区分「按键真的改变了状态」与
「按键只是让动画提前/推后」。在此之前，**不要引用「输入锁定」这个说法**。

### 14.2 更正：左侧单位精灵 1196 像素**不是调色板问题**

上一轮写的「原版把佐助画成灰阶、重制是彩色」**不成立**。
定量判定：取命令菜单帧左侧单位区域 `(78,46)-(116,104)`，
统计每个差异像素的 `(原版色 → 重制色)` 映射。
纯调色板差异要求每个原版色**只对应一个**重制色；实测 29 个原版色里
**25 个指向多个重制色**（`(33,33,33)` → `(74,107,181)` 36px / `(49,49,115)` 19px /
`(255,255,255)` 17px …），映射多义 ⇒ 不是换调色板。

剪影叠加显示红绿像素**在同一剪影内交错** ⇒ 占同一块地盘但内部结构不同。

### 15.22 **修好一个真正的 AI 逻辑 bug**（纯移动朝向）

**坐标先解出来**：镜头 (240,24) + 场景网格 15 宽而地图 30 列 ⇒
**场景格 → 地图格 +10 列**。于是原版木叶丸屏幕 x80..111 = 场景格 **(10,7)**，
与重制版调试输出 (10,7) **完全一致** ⇒ **站位从来不是差异**。

**根因**（`battle_ai.h` 纯移动分支）：
`candidate.facing = has_focus_position ? facing_toward(destination, focus, ...) : facing_toward(origin, destination, ...)`
——**有焦点位置时朝向取「从终点看向焦点」**。
木叶丸 focus (12,3)、终点 (10,7) ⇒ |dy|>|dx| ⇒ 判成 `up`；
原版给的是 `right`（**走了两格向东就面朝东**）。

**改法**：纯移动的朝向一律取移动方向
（`facing_toward(acting_unit.position, destination, acting_unit.facing)`），
焦点位置只决定往哪走、不决定看哪。
**范围**：全仓库只有 battle 14（S49）给 AI 设了 `has_focus_position` ⇒ 只影响 S49。

**实测**（收据 `region-diff-moveface/`）

| 基线 | 改前 | 改后 |
| --- | --- | --- |
| 对白 ×3 | 0 | **0** |
| 动作菜单 21↔21 | 0 | **0** |

## 20. 2026-10-20 第 19 轮：**移动网格——撤回一条旧结论，并把原版的 GPU 结构钉出来**

### 20.1 撤回 4.3.90 的「不是切调色板」

上一轮 4.3.90 用「在原版 step-19 的 PRAM 里搜那 9 个暗化色，全部无命中」
推出「暗化罩不是切调色板」。**这个论证方法上不成立**，本轮撤回：

- 仓库里归档的 **PNG** 与 **PRAM/VRAM dump 来自不同的 mGBA 构建**
  （PNG 来自 `2cc5c36d…`，dump 来自 `d1a9c231…`），而且**不是同一帧**；
- 更狠的是：**同一帧内**截图与调色板也不在一个色彩空间——移动网格帧 162 色里
  **97 色不在该帧调色板里**；⚠️ **第 19 轮更正**：`BLDCNT` 实为 `0x1744`（**alpha 混合**，EVA=EVB=10/16）⇒ **混合结果色本来就不属于任何调色板** ⇒ 「GBA 画不出这种颜色」的论证**作废**。

⇒ 「不是切调色板」只能算**未被证明**。教训：
**拿 PNG 的颜色去搜调色板 RAM，前提是二者同帧同空间**。

### 20.2 新证据：同帧收据

新增 `tools/butano/mgba_frame_palette_sequence.lua` +
`tools/butano/capture_s49_frame_palette.py`：**一次运行、同一帧**同时落

### 20.3 原版移动网格的 GPU 结构（可复算）

| 项 | 移动网格（step-19） | 回合横幅（step-15） |
| --- | --- | --- |
| `DISPCNT` | `0x1D40` | `0x1940` |
| 差异 | **bit 10** ⇒ BG3 字符基址 `0x00000` ⇄ `0x10000` | — |
| `BLDCNT` | `0x1744` | `0x1744` |（⚠️ **第 19 轮更正**：旧值是 IO 偏移读错）
| BG3 tilemap（`VRAM 0x1800`） | **1024 格全填**，主图块 `57792`×764、`448`×140 ⇒ 整屏一层 | — |
| 镜头 | `BG0HOFS=240 / VOFS=24` | 同 |

⇒ **本轮把这一版解读也撤回了**（用本机 mGBA 源码 + VRAM 实测）：
- mGBA 渲染器里背景的字符基址**只来自 BGxCNT**
  （`video-software.c`：`charBase = BGCNT.CharBase << 14`）⇒ mode 0 下
  DISPCNT 不参与字符基址 ⇒ **bit 10 不改变画出来的东西**；
- BG3 引用的图块在**两帧里都是空的**（主图块 `0xE1C0` 全 0）⇒ **BG3 什么都没画**。

⇒ bit 10 只是游戏自己写的**软件标志位**，不是机制。

**真正在变的是 BG2**：逐层比两帧的 tilemap ⇒
BG0（地图）只差 **1** 格、BG1 差 **0** 格、**BG2 差 706** 格（BG3 差 175 但图块为空）。
BG2 优先级 2 高于 BG0 的优先级 3 ⇒
**移动网格的覆盖层与「暗化」都是 BG2 的一层图块画在地图之上，不是给 BG0 调色板染色**。

**再进一步**：BG0（地图）的**调色板（PRAM bank 0–3）与图块数据（VRAM `0x4000`）
在两帧之间**逐字节相同**（0 项 / 0 字节变化）⇒ **地图层画出来必然一样**
⇒ **「不可达区被蒙冷色 = 给底色加冷色」在硬件层被否证**；
冷色只能来自**另一个层**（两帧之间被重写 706 字节的那一层）。
这也解释了 4.3.90「单一 (T, alpha) 无解」：不是同一批底色的颜色混合，而是**空间上的一层覆盖**。
**⇒ 并行调查后，撤回上一版「覆盖层 = 3 个精灵」**（笔记
`notes/s49-dispcnt-bit10-layer-20261020.md`）：

- `DISPCNT` bit 10 在**普通 GBA** 上是 **BG2 使能**（不是 CGB 语义的「BG3 字符基址」）；
- 变的是 **BG2**（212/1024 格 tilemap 改写，图块 256–281，调色板 bank 12，字符区 `VRAM 0x06002000`）；
  **地图层 BG0 逐字节相同** ⇒ 「换一套暗化地图图块」被否证；
- ROM 资源：图块 **LZ77 `0x080B9E94`**（198 B → 1024 B）→ `VRAM 0x06002000`；
  调色板 **LZ77 `0x080B9F5C`**（32 B）→ `PRAM 0x05000180`；装载 `0x080694C4`；
- 那 3 个多出来的 OAM 槽位 = **移动了的护送单位 + 它的两个标记**（tile 138→136、标记 110→112），
  **不是覆盖层**；两侧都是 visual **slot 0**，原版在该帧是 **frame 010**、重制是 **frame 011**
  ⇒ 差的是 **idle 时间线错开一步（8 帧）**。

**另一条已闭合的规则：战后经验**（`notes/s49-post-battle-exp-rule-20261020.md` 同名新笔记）
`gain = mission_exp(全员) + round_bonus(全员, 回合 ≤ limit) + carried_exp(该角色击败/关联到的单位)`；

## 22. 2026-10-20 第 20 轮续：**「每帧重绘」的机制查清——是描边调色板被逐帧改写；覆盖层接线确认存在**

### 22.1 最重要的一条：第 13/14 轮的定性被推翻

第 13/14 轮写下的「原版每帧重绘 ⇒ 帧序未知 ⇒ 重制侧的 field 动画模型不对」**是错的**。
第 15 轮用「变化像素集 ⊆ 单一调色板索引的像素集」这个判别式查清：

- 191 次跃迁的**最佳整体位移恒为 (0,0)**，109/191 次**剪影掩码完全不变** ⇒ **不是位移**；
- `t=0→1` 变化 **137** 像素，颜色对只有 `(0,189,189)→(0,206,206)`，而该区域该色像素**正好 137 个**
  ⇒ 变化集恰是**单一索引**的像素集 ⇒ **是调色板改写**；
- 该索引 = 该帧美术的 **index 15**（1 px 描边，ROM 值 `0x0813E070+30` = BGR555 `0x0421`）；
  屏上逐帧为 `(0, g, g)`，`g` = 1,3,…,31 的**三角波、周期 32 帧**
  ⇒ **运行期每帧改写该单位 OBJ 调色板的第 15 项**；
- **帧序本身完全等于 ROM 的 animation 3**（`0x08142AFC` `[(9,8),(10,8),(11,8),(10,8)]`，周期 32）
  ⇒ **重制侧的帧序本来就是对的**。

⇒ **新的最小缺口 = 一个调色板项的每帧写入**（不是动画表、不是帧序）。
⇒ 逆向侧下一步已定位到链条：PRAM 目标 `0x05000200 + bank*32 + 0x1E`，
值 `(v<<10)|(v<<5)`；该链**不在 copy queue 上**（14 个 caller 全是整块拷贝）⇒ 只能直接 `STRH`
⇒ 建议对 PRAM `0x05000200..0x050003FF` 做「直接半字写入」全 ROM 清单。
详见 `notes/s49-field-frame-order-20261020.md` 与 S49 文档 4.3.96。
