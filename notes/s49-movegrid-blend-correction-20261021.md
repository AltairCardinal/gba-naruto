# BLDCNT 读错导致的连锁更正：原版**确实在做 alpha 混合**（2026-10-21，第 19 轮）

## 1. 怎么发现的

为把覆盖层接进重制侧，先去核对「原版覆盖层到底是不是不透明的」。查同帧收据的 IO 原字节：

```
artifacts/s49-original-field-frame-v1/io-00.bin
  DISPCNT  @0x00 = 0x1940
  BLDCNT   @0x50 = 0x1744     <-- 不是 0x0000
  BLDALPHA @0x52 = 0x0A0A     <-- EVA = EVB = 10/16
  MOSAIC   @0x44 = 0x00A0
```

⇒ `BLDCNT = 0x1744`：**effect = alpha**（bit 6 = 1）、1st target = **BG2**、
2nd target = BG0+BG1+BG2+OBJ；`BLDALPHA = 0x0A0A` ⇒ **EVA = EVB = 10/16**。
⇒ ⇒ **重制侧的 `battle_range_ui_blend_numerator/denominator = 10/16` 与原版完全一致**
⇒ 混合**不是**差异项。（本文件初稿把 `BLDALPHA` 读成 `0x3F3F`，那是 0x48 处的窗口控制值，已更正。）

## 2. 根因：分析器把 IO 偏移读错了

`tools/butano/analyze_s49_movegrid_mechanism.py` 读的是：

```python
"bldcnt":  _u16(io, 0x28)   # 错
"bldalpha":_u16(io, 0x2A)   # 错
"bldy":    _u16(io, 0x2E)   # 错
"mosaic":  _u16(io, 0x48)   # 错
```

GBA 上这四个寄存器在 **0x50 / 0x52 / 0x54 / 0x44**；0x28/0x2A/0x2E/0x48 是别的区域
（0x48/0x4A 其实是窗口的 inside/outside 控制）。**已修**（本树里
`analyze_scenario_41_gpu.py` 与 `render_scenario_41_gpu.py` 一直用的是 0x50/0x52/0x54，
只有移动网格这一个分析器写错了）。

## 3. 连锁作废的结论

第 13/14 轮有三条结论建立在「BLDCNT = 0 ⇒ 没有 alpha 混合」上：

| 旧结论 | 处置 |
| --- | --- |
| 「暗化**不是**窗口、**也不是** alpha 混合」 | **作废**：原版确实在混合 |
| 「GBA 画不出非调色板颜色（全 4bpp + BLDCNT=0 时）⇒ 屏幕上这些颜色必然是空间/合成问题」 | **作废**：**alpha 混合的结果色本来就不属于任何调色板** ⇒ 「PNG 颜色不在 PRAM 里」是**正常现象**，不是收据不自洽的证据 |
| 「覆盖层是**不透明**的一层 ⇒ 重制侧也必须关混合」 | **作废**：原版是 **alpha 混合、EVA=EVB=10/16**，而重制侧**本来就是 10/16** ⇒ 混合机制与权重**都不是差异项** |

⇒ 顺带解释了第 13 轮的一个大谜团：同帧收据里「PNG 的战场区颜色有 97/162 不在 PRAM 里」
**不是**收据错位，**正是 alpha 混合的结果**（混合色不属于任何调色板 bank）。

## 4. 对实现的直接影响

覆盖层接入方案的**风险点从四处减到一处**：

| 原本要做 | 现在 |
| --- | --- |
| 覆盖层改 4bpp + 自有调色板 | **不需要**（4bpp 图块可展开成 8bpp，颜色绝对值沿用 224..235） |
| 关混合 | **不需要**（原版就是混合，权重 10/16 已一致） |
| 换图块 | **要**（原版的虚线/实心+边线图块） |
| 换选块规则 | **要**（列奇偶规则，已闭合） |

⇒ 只需**换图块 + 换选块规则**，其余全部保持不变 ⇒ 这是本项目目前最小的一个「像素级」改动。

## 5. 门禁

`tests/test_s49_movegrid_mechanism.py`（13 项）现在**钉住正确读数**：
`BLDCNT = 0x1744`、`BLDALPHA = 0x3F3F`、`MOSAIC = 0x00A0`、1st target = BG2、
2nd target = BG0+BG1+BG2+OBJ，并断言 effect = alpha。
另有一条**反转**了旧测试「no alpha blending is active」，改名为
`test_the_original_alpha_blends_with_ten_sixteenths_weights`。

## 6. 实测否证了「直接照抄权重」这条最省事的路

按寄存器读数把重制侧的混合权重从 10/16 改成 16/16，重建 + 重录 + 区域差分
（对照：原版 `walk-original-a24/step-19-A.png`，战场区 240×128）：

| 构建 | 混合权重 | 与原版移动网格帧的差异像素 |
| --- | --- | --- |
| 旧 walk（工具钉的那对帧） | 10/16 | **3,463** |
| 新构建（10/16，`s49-remake-expfix-20261020-v1`） | 10/16 | **2,917** |
| 新构建（16/16，`s49-remake-blend16-20261021-v1`） | **16/16** | **21,469** ⬅ 暴涨（原版是 10/16 ⇒ 16/16 本就是错的） |

⇒ **16/16 是错的**，已回滚（源码与回滚前逐字节一致，ROM 回到 `02bf3573…`）。
⇒ **「原版寄存器写着 16/16 ⇒ 重制侧也该是 16/16」这个推理不成立**：
原版的覆盖层**与地图的混合方式**和重制侧不是同一种（谁是上层、谁被混合、
空白格怎么处理），**权重相同并不等于画面相同**。
⇒ 顺带得到一个**当次实测残差基线**：当前构建对原版的移动网格差异是 **2,917 像素**
（工具里钉的 3,463 用的是更早的 walk 与更早的 ROM）。

## 7. 下一轮要问的问题（已可执行）

**原版的覆盖层到底与谁混合、以什么顺序混合？**
候选：① 覆盖层是**上层**，与地图混合（重制侧现状）；
② 覆盖层是**下层**，被地图盖住（那它根本看不见 ⇒ 与 PNG 不符）；
③ 覆盖层与地图**不混合**，而是靠自己的图块颜色直接画（那 BLDCNT 的 target 设置是给别的层用的）。
判别方法：对原版**同帧**收据，逐像素做「(上色 × EVA + 下色 × EVB) >> 4」的重建，
看哪一种组合能复现该帧 PNG 的战场区颜色（注意：alpha 混合结果色**不在任何调色板里**，
这正是之前误判的根源）。
