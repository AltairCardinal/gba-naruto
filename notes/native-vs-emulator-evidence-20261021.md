# 如何证明「静态重编译」不是模拟器：证据、方法与实测对照

日期：2026-10-21
性质：技术笔记。为「静态重编译 vs 模拟器 vs 反编译」提供**可复现的判据**，
并给出一组在木叶战记上的实测数据。
关联：`notes/static-recompilation-native-port-20261020.md`（三条路线总览）、
`notes/gba-static-recomp-feasibility-20261020.md`（本次移植实测）。

## 0. 先破一个误解

**「运行 exe 仍然需要 ROM 和 BIOS」不能证明它是模拟器，也不能证明它不是。**

静态重编译与模拟器**都需要**这两个文件，原因是不同的：

| | ROM 的角色 | BIOS 的角色 |
|---|---|---|
| **模拟器** | **被模拟的对象**——代码和数据都在里面，运行期随时要取指令来解码 | 被模拟的对象（GBA 底层服务） |
| **静态重编译** | **数据源**——代码已在编译期翻译成 x86-64 并链接进 exe，运行期只读它的数据部分 | 服务也被静态重编译进 exe，但框架仍要求提供文件做哈希校验与部分数据读取 |
| **反编译** | 源头（反编译出原始 C 源码，编译后运行期完全不需要 ROM） | 同上 |

静态重编译 ≠ 反编译：你没有原始源码，翻译必须**从 ROM 字节出发**。
翻译完成后代码就脱离 ROM 了，但**资产不能翻译**——图形、文本、音频、表仍在 ROM 里，
运行期必须读 ROM 文件。

→ **能区分两者的不是「要不要 ROM」，而是「运行期有没有发生翻译/解读」。**

## 1. 五条结构性判据（可复现）

### 判据 1：exe 里有没有 ROM 的字节？

把 exe 和 ROM 都读进内存，检索 ROM 的若干 256 字节片段。

木叶战记实测（exe 22,903,808 B / ROM 6,291,456 B）：

| 检索的 ROM 片段 | 在 exe 中 |
|---|---|
| `0x040000` 的 256 字节 ARM 码 | **不存在** |
| `0x060000` 的 256 字节 ARM 码 | **不存在** |
| `0x080000` 的 256 字节 ARM 码 | **不存在** |
| `0x0B9F80` 的 256 字节数据（LZ77 图块） | **不存在** |
| ROM 头部 256 字节（标题/校验） | **不存在** |

→ exe **一个 ROM 字节都没有**。它不是"带 ROM 的模拟器"，也没有把 ROM 打包进去。

### 判据 2：exe 里有没有 guest 函数的原生实现？

`dumpbin /symbols gbarecomp_game.lib` → 96,086 个 `gf_` / `tfunc_` 符号。
静态库 58.2 MB → exe 22.9 MB。

### 判据 3：调用是「函数指针」还是「opcode handler」？

生成的 `dispatch_table.cpp`：

```c
struct DispatchEntry { uint32_t addr; uint8_t thumb; uint8_t resume; void (*fn)(void); };
extern "C" const DispatchEntry kDispatchTable[] = {
    {0x03000680u, 0u, 0u, gf_iwram_trampoline_080004C8},
    {0x03000684u, 0u, 1u, gf_iwram_trampoline_080004C8},
    ...
```

112,263 条 **guest PC → 原生函数指针**。
模拟器的对应物是「opcode → handler」或 JIT 编译的代码；这里是**编译期就定死的直接调用**。

### 判据 4：运行期解释了多少条 guest 指令？

`interpreted_insns=0`。模拟器**数学上不可能**为 0——它必须逐条解码 ARM 指令。

### 判据 5：exe 依赖了哪些 DLL？

`dumpbin /dependents`：WS2_32 / SDL2 / COMDLG32 / USER32 / WINMM / KERNEL32 + MSVC CRT。
**没有任何模拟器核心库**。

## 2. 最强的一条：受控对照

框架自带 `GBARECOMP_FORCE_INTERP=1`：让**同一个 exe** 走纯解释执行路径
（框架注释里称其为「recomp-vs-interp first-divergence oracle」的 interp 侧）。
于是可以在**同机、同 ROM、同 BIOS、同 exe** 的条件下只切一个环境变量。

木叶战记实测（2000 帧，无窗口）：

| 指标 | A. 静态重编译路径 | B. 纯解释路径 | 比值 |
|---|---|---|---|
| `cpu_backend` | `static-recompiled` | `interpreter (GBARECOMP_FORCE_INTERP)` | — |
| 耗时 | **2.78 s** | **132.77 s** | **47.8×** |
| `guest_fps` | **720.2** | **15.1** | 47.8× |
| `steps` | 755 | 116,676,315 | — |
| **`interpreted_insns`** | **0** | **117,649,148** | ∞ |
| `self_heal_coverage` | `FULLY_STATIC` | `NOT_STATIC` | — |

同一份游戏代码，**48 倍速度差**；解释指令数 0 vs 1.18 亿。

## 3. 一个诚实的补充：它不是「真机寄存器映射」

生成的代码仍然是操作**软件寄存器文件**的。实测 `recompiled_000.cpp` 片段：

```c
void gf_iwram_trampoline_080004DC(void) {
    ...
    /* 03000694  03000694 A ldr r2,[r15,#0x30] */
    {
    g_cpu.R[15] = 0x03000694u;
    uint32_t _ea_03000694 = _base_03000694 + _off_03000694;
    { uint32_t _w = bus_read_u32(_ea_03000694 & ~3u); ... }
    g_cpu.R[2] = _v_03000694;
    g_cpu.R[15] = 0x03000698u;
    runtime_tick(_cyc_03000694);
    }
```

即：一条 ARM `ldr` 被降级成一小段**操作 `g_cpu.R[]` 结构体的 C++**，
再由 MSVC 编译成 x86-64。

所以准确的说法是：
- **是**「编译期翻译」——运行期没有解码/分派 opcode 的动作；
- **不是**「指令级零开销」的真机寄存器直接映射方案。

这不影响「它不是模拟器」的结论，但会影响性能预期：
每条 guest 指令仍要付「读写软件寄存器 + 访存 + tick」的代价。

## 4. 两条路径在同一帧点画面不同——是采样点差异，不是行为分叉

2000 帧处静态路径与解释路径的 PNG **不相同**：差异 1,344 / 38,400 像素（3.5%），
集中在 **x 144..200, y 0..38**（顶部标题文字区）。

用 `--dump-state` 导出两条路径的完整内存状态（GBAS 二进制格式）逐字节比对：

| 段 | 长度 | 差异字节 | 占比 |
|---|---|---|---|
| `SAV0`（存档/静态 RAM） | 41,026 | **0** | 0% |
| `BUS0`（总线可见内存） | 395,428 | **62** | **0.0157%** |
| `CPU0`（CPU 寄存器快照） | 184 | 50 | 27% |
| `PPU0`（PPU 内部状态） | 115,223 | 4,032 | 3.50% |
| `AUD0`（音频状态） | 33,042 | 1,596 | 4.83% |
| `IO_0` | 1,169 | 28 | 2.40% |
| `META` | 24 | 4 | 16.7% |

**解读**：
- **游戏可见的总线内存只差 0.0157%**（39.5 万字节里 62 字节）；
- 存档区 **0 差异**；
- 差异集中在 `CPU0`——寄存器快照记录的是「当前停在哪」，
  静态路径停在 `ppu_vcount=161`，解释路径停在 `ppu_vcount=0`。
  测试框架「跑满 N 帧就停」，而帧内位置取决于执行速度；
  顶部标题字是**逐扫描线绘制**的，所以那一小块文字的绘制进度不同。

**这不是逻辑分叉，是采样点不同。** 佐证：静态路径自己跑两次，
PNG **逐字节一致**、状态差异 ≤ 2 字节（BUS0 1 字节、AUD0 2 字节，属音频时间相关量）。

## 5. 方法论小结：想证明「不是模拟器」，按这个顺序查

1. **检索 exe 里有没有 ROM 字节** —— 排除"打包了 ROM 的模拟器"。
2. **`dumpbin /symbols` 数 guest 原生函数** —— 证明代码在 exe 里。
3. **看 dispatch 表结构** —— 是函数指针还是 opcode handler。
4. **看运行日志的 `interpreted_insns`** —— 模拟器不可能为 0。
5. **`dumpbin /dependents`** —— 有没有模拟器核心库。
6. **`GBARECOMP_FORCE_INTERP=1` 受控对照** —— 同 exe 切解释路径，比 fps 与解释指令数。

第 6 条最有说服力，因为它把"静态 vs 动态"这个变量单独隔离了出来。
