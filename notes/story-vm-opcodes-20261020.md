## 1. 尝试记录（走过的路与死路）

1. **先找四张根表的引用**。用 `tools/find_pointer_refs.py` 的思路在 ROM 里扫 32 位字面量，
   命中两处：
   - `0x0808F5B8` / `0x0808F5BC` → `0x08060D54`（after 表）/ `0x08060C74`（before 表）
   - `0x0808A578` / `0x0808A5E4` → `0x08060E34`（logic 表）/ `0x08060EF0`（events 表）
   这两个位置都是**字面量池**，不是代码，所以从这里读不出语义，只能定位「谁在用表」。

2. **顺着调用点找 VM**。两处引用所在的函数都出现 `bl 0x80977b8`：
   - `0x0808F5D0`（剧情调度器：在 before/after 之间二选一，索引 = `scene >> 14`）
   - `0x0808A54C` / `0x0808A566` / `0x0808A5FC` / `0x0808A67C`（战斗事件调度器）
   → **VM 入口 = `0x080977B8`**。

3. **误判：以为分发表是 compare/branch 链**。在 `0x080977D8` 附近看到
   `ldrb r0,[r7]` / `cmp r0,#0x39` / `bls`，一度以为是 `cmp` 链；
   实际上后面紧跟 `lsls r0,r0,#2` / `ldr r1,[pc,#imm]` / `adds r0,r0,r1` / `ldr r0,[r0]` /
   `mov pc,r0` —— 是**标准跳转表**。死路记录：只看 `cmp` 链会数出 58 个分支。

4. **误判：以为 `0x08097B20` 是循环头**。它是「跳到 r5」的公共尾巴
   （`adds r7, r5, #0` → `b 0x08097E2C`），很多 handler 都跳到它，
   用「最常见 `b` 目标」统计会选错。真正的循环头是**分发表之外的默认分支目标**，
   也就是 `0x08097E2C`（`movs r0,#1` / `cmp r0,#0` / `beq` / `b 0x080977D8` 重新取指）。
   它同时也是 14 个空槽（`0x24`..`0x31`）的 handler —— **空指令会让 VM 原地死循环**。

5. **误判：以为每个 handler 独占一段代码**。`0x080979E8` 同时服务 `0x08` 和 `0x0E`；
   `0x08097AB4`/`0x08097ABA`（`0x09`/`0x0A`）共用尾部 `0x08097ABE`；
   `0x08097D20` 是 `0x07` 与 `0x15/0x34..0x39` 共用的「读 u32 目标并跳转」尾巴。
   所以长度不能靠「到下一个 handler 的距离」算，必须**符号执行** handler。

6. **误判：`0x13` 双段文本的第二个正文起点**。按 `0x08097B8C adds r7,#1` 推，
   第二段正文在「第一段 NUL 之后**再跳 1 字节**」处。
   少算这 1 字节会让整条脚本错位 1 字节（表现为在文本里遇到 `unknown opcode 0x7C`）。

7. **误判：根表扫描遇到 0 就停**。根表第 0 项是哑元（场景号从 1 开始），
   中间还有若干「该场景无脚本」的 0 项。按「遇到 0 即停」会把 55 项的表只认成 1 项。

8. **误判：把 `0x085A143C` 当成第五张根表**。它满足「每场景一个指针」的外形，
   但解出来的全是字模数据。判据：**根表 = 其脚本能全部走通的表**。

## 2. 方法（怎么找到解释器与分发表）

工具 `tools/story_vm_ops.py` 全部自推，步骤如下：

1. **扫分发表**：在 ROM 里搜字节串 `40 18 00 68 87 46`
   （`adds r0,r0,r1` / `ldr r0,[r0]` / `mov pc,r0` —— 跳转表尾巴）。
   对每个命中点回溯 2/4/6 字节找 `ldr rX,[pc,#imm]`，
   读它的**字面量值**（= 表基址 `0x080977F4`），
   再从分发表往前找 `cmp r0,#0x39` 得到最大 opcode。
   多个候选时取「表项去重后最多」的那个。

2. **找解释器入口**：从分发表代码往前回溯最近的 `push {...,lr}` → `0x080977B8`。

3. **找循环头**：在分发表代码窗口里找那条无条件 `b`，其目标若正好是某个 handler
   → `0x08097E2C`（表外 opcode 的默认落点，也就是「重新取指」）。

4. **找根表**：扫全 ROM 的 Thumb `bl`，取指向解释器入口的调用点
   （`0x0808A54C 0x0808A566 0x0808A5FC 0x0808A67C 0x0808F5D0`），
   在这些调用者所在函数的字面量池里找「每场景一个指针」的表，
   再用「脚本能全部走通」筛掉伪表。

5. **推导长度**：对每个 handler 做**符号执行**（`tools/story_vm_ops.py:execute_handler`）。
   关键点：`ldrb rX,[r7]` 读到的就是 opcode 本身，所以
   `0x08`/`0x0E` 共用 handler 时可以按 opcode 分别求值，得到 2 与 3 两个不同长度。
   执行到循环头时的 `r7` 偏移即为指令长度；`r7` 由函数返回值决定时（跳转/文本）
   改用「u32 操作数偏移 + 4」或文本扫描规则。

6. **交叉验证**（全部自动化，见第 5 节）。

### 3.1 比较器表（`0x08097230`，由 `0x8097210` 分发）

| 比较器 | 语义 | 证据指令 |
|---|---|---|
| 0 | `==` | `cmp r3, r2` / `bne` |
| 1 | `!=` | `eors r1, r2` / `rsbs` / `lsrs r4, r0, #0x1f` |
| 2 | `>` | `cmp r3, r2` / `bls` |
| 3 | `>=` | `cmp r3, r2` / `blo` |
| 4 | `<` | `cmp r3, r2` / `bhs` |
| 5 | `<=` | `cmp r3, r2` / `bhi` |

比较是**无符号**的（`bls/blo/bhs/bhi` 均为无符号分支），
两个操作数都按 `u8` 取值（`lsls #0x18 / lsrs #0x18` 零扩展）。
> 注：`notes/story-script-vm.md` 旧版把比较器表写成「由第三方编辑器实现与原版数据共同确定」，
> 现在它已经是本仓库自己的代码级结论。

### 3.2 三套互不相同的标志位空间（本次新发现）

| 数组 | 寻址 | 写 | 读 | 用在 |
|---|---|---|---|---|
| `0x020314F0` | byte = id>>3, bit = (id>>16)&7 | `0x08097050` | `0x080970A0` | 0x09 / 0x0A / 0x0B / 0x0C |
| `0x02031510` | byte = i>>3, bit = i&7 | `0x080970C0` | `0x08097110` | 0x19 / 0x15 / 0x34 |
| `0x020311D4` | word = id>>29, bit = id&0x1F | `0x0808A490` | `0x0808A4D8` / `0x0808A504` | 0x37 / 0x38 |

三套数组都在存档代码（`0x080688A8` 起）里被读写，所以都是持久化状态。
**未解**：0x09/0x0A/0x0B/0x0C 写读 `0x020314F0`，而 0x19 写 `0x02031510`（相差 0x20 字节），
两者不是同一片标志区；这是刻意的分区还是游戏自身的疏漏，需要动态证据才能定。

### 2026-10-21：探针取数方法（三条坑，已写进 `tools/mgba_probe/story_vm_capture.py`）

1. **按 B 才推进剧情**（A 只能过标题/教学界面）；
2. **每次按键之间必须插「松键帧」** —— 宿主的 `frames` 命令在窗口结束才松键，
   下一个窗口立刻又按下，中间没有一帧是松键状态，游戏只认到第一次按键沿；
3. **断点命中会吃掉那一次按键沿** —— 命中后要先跑几帧松键、用 mGBA 的 `frame`
   把被打断的那一帧跑完，再 `delete` + 重新 `b`。
