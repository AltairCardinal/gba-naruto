## 0. 结论摘要

第三方包（无 ROM 版）实际上是一套**完整的剧情编辑器 + 可运行的剧情脚本编译器**，

### 2.1 地图表 0x53D910 的 32 字节字段顺序 —— 修正我们现有笔记

对方布局（**实测确认**）：

| 偏移 | 含义 | 实测证据（entry 0） |
|---|---|---|
| +0x00 | u16 原始宽 | 92 → 92/4 = 23 图块宽 |
| +0x02 | u16 原始高 | 64 → 64/2 = 32 图块高 |
| +0x04 | tile gfx（LZ77） | 解压 21504 字节 |
| +0x08 | palette（LZ77） | 解压 384 字节 |
| +0x0C | 图层 0 tilemap（LZ77） | 解压 2944 字节 |
| +0x10 | 图层 1 tilemap（LZ77） | 解压 2944 字节（仅部分地图存在） |
| +0x14 | metatiles（LZ77） | 解压 6160 = 770 × 8 字节 ✓ |
| +0x18 | terrain（LZ77） | 解压 **1472 = 23 × 32 × 2** ✓ 精确吻合 |
| +0x1C | 剧情底图 ID（u8） | = 1 |

**决定性证据**：terrain 解压长度 = 图块宽 × 图块高 × 2，与"每格 u16 通行值"完全一致；
metatiles 解压长度 = 8 的倍数，与"每 metatile 8 字节"一致。entry 1 / entry 3 同样吻合。

> 我们的 `notes/battle-config-format.md` 与 `notes/chapter-flow-format.md` 给出的字段顺序
> （palette 在 +0x10、flags 在 +0x18、dims 在 +0x1C）**是错的**，且两份笔记彼此还互相矛盾。
> 尺寸记录同样有误：我们写 entry 0 = 60×30，实测是 **23×32**。

### 2.2 0x596D5C 不是"图块描述符表"，而是精灵动作表的 id=1 行

对方：`0x596CCC + id*144 + action*16` → 4 个指针
`(frames, animations, gfx, palette)`。

实测：`0x596CCC + 1*144 = 0x596D5C`，其四个 u32 正是
`08142A70 / 08142BA0 / 0813E090 / 0813E070` —— 与我们 `notes/map-format.md` 记录的
"col0..col3"**完全同址**。也就是说我们那套"嵌套描述符 + 调色板"的解释，
其实是 frames / animations / gfx / palette 四个指针。
palette 32 字节解出 16 个 BGR555 色值，其中含 `0x7FFF`（透明），与精灵调色板一致。

> `notes/map-format.md` 的"Tile Descriptor Table 0x596D5C, 312 条目"应重写为
> "精灵动作表 0x596CCC，60 角色 × 9 动作 × 16 字节"。

## 3. 差集清单：对方有、我们没有

### P0 —— 剧情与战斗的可玩性主干

#### P0-1 剧情脚本 VM 图解码器（`E.graph`）
对方实现了一个带回溯的字节码图遍历器：把脚本解析成带 `op / length / targets / text / offset`
的节点图，可用于**枚举一段剧情里的所有对白、跳转目标、子调用**。
配套还有 `scanText`（SJIS 文本扫描，含控制码与全角空格 `0x81 0x40`）与
`decode`（按字形映射还原字符）。

**对我们意味着**：剧情编辑器"按场景浏览对白 / 改对白 / 加分支"的前提能力。

#### P0-2 战斗胜负判定条件表 `0x594758`
结构（对方 `rules()` 解析，实测表头全 0 = stage 0 未使用）：

```
entry = 0x594758 + stage*0xCC + sub*0x44
+0x00  u8   回合上限（turn limit）
+0x04  group0 × 4 条，每条 8 字节：type, a, b, c, u32 说明文字指针
+0x24  group1 × 4 条，同上
```

- 条件类型 **0..9 为原版**，**10 为对方新增**（"到达指定位置并结束行动"= 撤离规则，
  其编辑器明确要求 `capabilities.arrivalRules` 才允许使用）
- 参数占用规律（对方 `setRule` 校验）：类型 1/3/5/7/8/9 的 `a` 是阵营（0/1）；
  类型 6 的 `a` 是物品序号（0..15）；类型 3 的 `b` 是人物编号
- 每个条件都带一条说明文字（战斗内 Conditions 页显示）
- 对方做到了"以已有战斗为模板增加场次"并复制条件块

#### P0-3 战场配置(sub) 三维结构
`actorBase = 0x5461C4 + stage*0x1AAC + sub*0x8E4`，每 stage 3 组（sub 0/1/2）：

- 每组 **12 个角色槽**，每槽 `0xB8` 字节：+0 id、+1 阵营、+2 x、+3 y、+4 朝向、+15 等级
- 角色槽后紧跟 **16 个地图物件**（4 字节/个：type, target, x, y），位于 `base+0x8A4`
- 物件类型 0..7：空位 / 忍具 / 强化素材 / 专属修行卷轴 / 认识卡 / 机关宝箱 / 特殊机关 / 剧情物件

#### P0-4 奖励表 `0x59EAE0`
每条 24 字节：`u16 金币, u16 奖励, u16 …`（实测 entry 0 = `C8 00 64 00 0A 00 …`）。
对方据此实现"每场战斗的战利品"。

#### P2-3 扩展 ROM 的实现范式
对方把剧情/战斗扩展的做法是**搬迁整表 + 改指针 + 追加新代码段**：
- 把地图表扩到 104 项、奖励表扩到 256 项、角色表扩到 104 项、任务文本扩到 256 项，
  全部搬到 ROM 尾部新区域，再把 ROM 里所有指向旧表的指针批量改写

### 9.1 物证：原始 MCP 调用转录
