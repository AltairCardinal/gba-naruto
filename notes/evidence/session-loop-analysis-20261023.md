## 1. S1：单轮内的「工具调用死循环」

### 1.1 形态

| 指标 | 值 |
|---|---|
| 消息总数 | 949（`assistant` 445 / `toolResult` 463 / `user` 8 / `custom` 32 / `compactionSummary` 1） |
| `stopReason` | **`toolUse` 444 / `stop` 1** |
| 工具调用总数 | 463（bash 170、edit 133、read 56、grep 37、mcp_browser 23、write 19、task_output 11、todowrite 7、task 4、…） |
| 落盘的最后一条消息 | 2026-10-23 **02:28:41** |
| runtime 记下的中断时刻 | 2026-10-23 **02:53:59**（`status: interrupted`，`errorSource: crash-recovery`） |

**444 / 445 条 assistant 消息以 `toolUse` 收尾** ⇒ 整场会话**几乎一次都没有以「给出答复」结束**。
一轮接一轮，每一轮都还在调工具。

### 1.2 循环长什么样

最后 23 分钟（02:05 → 02:28）里有 **71 次工具调用**，全是同一类动作：
反复在**同一批断点地址**上重跑 mGBA 探针、反复重新反汇编**同一片代码**：

```
0x08097A0A / 0x08097A0C / 0x08097A0E / 0x08097A10 / 0x08097A12 / 0x08097A1C
0x0806626C（文本渲染器入口）   0x080978DC
```

思考文本里反复出现 `HYPOTHESIS 1 … HYPOTHESIS 6` 的编号枚举，
以及大段 `⇒⇒⇒⇒⇒` 箭头串（同一段箭头串在一条思考里出现 **11 次**）。

### 1.3 触发原因（三层叠加）

1. **可观测信号是二值的、且不动。**
   探针只会回答「这个断点没命中」或「停在同一个 PC」。
   这种信号**无法证伪**当前假设 ⇒ 模型除了「再提一个新假设」没有别的动作可选。
   **这是死循环的直接机械原因。**

2. **没有任何东西会在「看起来没进展」时叫停。**
   S1 **没有 active Goal**（`local_runtime_thread_goals` 表里没有它的行）。
   它的 8 条 user 消息里 7 条是 `<background-task-finished>` 通知，
   剩下 1 条（`#485`）才是真人提的 4 条要求（跟在 system-reminder 后面）。
   没有 Goal ⇒ 既没有续跑机制，**也没有「叫停」机制** —— 只要模型还在调工具，循环就继续。

3. **思考预算与行动预算的比例失配。**
   `effort=max`，最后一段每条思考 3k–13k 字符，
   模型把预算花在「再想一遍」而不是「改一处再测一次」。
   而一次可验证的动作（跑一次 mGBA）只要几十秒。

### 1.4 结局

**不是模型收敛，是 runtime 崩了。** 02:28:41 之后还有约 25 分钟没有落盘，
runtime 在 02:53:59 记录了崩溃中断。

## 2. S2：Goal 续跑提示 × 模型输出退化 ⇒ 自激循环

S2 是带着 Goal `tg_qtuqa3zan3mvjw9ggy` 接手的（2026-10-23 02:48 → 14:51）。
它的循环形态和 S1 **不一样**，是三件事叠在一起。

### 2.1 模型输出退化：工具调用被当成普通文本吐出来

S2 有 **10 条 assistant 消息一条结构化 `toolCall` 都没有**，
`stopReason` 全是 `stop`（而不是 `toolUse`）：

```
#335 #339 #341 #347 #351 #354 #356 #358 #367 #377
```

其中 **5 条**把**工具调用的信封原样吐进了 `text` 字段**，形如：

```
…</new_string>…</invoke>
…</invoke>
```

（外层还包着模型自己的 `</…>` 包装标记，里面夹着零宽字符。）
runtime 认不出这是工具调用 ⇒ **这一轮等于什么都没做**。

同时思考长度爆炸：

| 消息 | 思考长度 | output tokens |
|---|---|---|
| `#356` | 50,572 字符 | 49,076 |
| `#377` | **107,113 字符** | **105,364** |

而 `llm-call.json` 里 `maxTokens = 128000`、`thinkingLevel = max`
⇒ **`#377` 是在输出上限边缘被截断的**：思考还没写完就没了，
本该是结构化 `toolCall` 的部分退化成了文本残渣。

### 2.2 Goal 续跑提示自我复制

每出现一次「零工具调用 + `stop`」的回合，runtime 就重新注入一条：

```xml
<archon_internal_context source="goal">
Continue working toward the active thread goal from the current conversation state.
Reinspect the current evidence, make concrete progress, and follow the goal contract …
</archon_internal_context>
```

S2 落盘里这样的**续跑提示共 9 次**（`#338 #340 #342 #353 #355 #357 #359 #369 #379`；
另有 `#0 #102` 两条是开跑时的 kickoff）。

**关键点：这 9 条提示彼此只差一个时间戳。** 我把 `#338` 和 `#379` 做了 diff，
唯一差异是 system-reminder 里的 `date:` 行：

```
-  date: Fri Oct 23 2026 03:20 GMT+0800 (中国标准时间)
+  date: Fri Oct 23 2026 14:51 GMT+0800 (中国标准时间)
```

⇒ **模型每次看到的是几乎一模一样的上下文** ⇒ 重新进入同一个推理状态
⇒ 再次退化输出 ⇒ 再次被判定「这轮没进展」⇒ 再次续跑。**这是一个闭环。**

### 2.3 runtime 的防循环计数器没有生效

Goal 记录（`local_runtime_thread_goals`）：

```
goal_id           = tg_qtuqa3zan3mvjw9ggy
session_id        = mvs_39e499d2896644f1b9be05346e12f193
status            = paused
status_reason     = paused(user_requested)
turns_used        = 10
tokens_used       = 1,166,147
time_used_seconds = 3,820
no_progress_streak = 0        ← 该涨没涨
no_tool_streak     = 0        ← 该涨没涨
```

10 轮里有 10 轮**没调任何工具、也没产生可验证的进展**，这两个计数器却一路是 0
⇒ **runtime 自带的防线下没有拦住它**。这是 runtime 侧的一个真实缺口，值得查判定逻辑。

### 2.4 触发原因

1. **它接手的正是 S1 已经陷进去的那个坑**（说话人名表真机验收失败），
   而要求第 1 条恰恰是「用模拟器去真机验收」—— 落进了同一个不可证伪的循环。
2. **输出退化 → 被判无进展 → 续跑 → 同一状态重来**，形成正反馈：
   越想越久 → 越容易在 `maxTokens` 边缘被截断 → 工具调用退化成文本 → 被判无进展 → 续跑。
3. **`thinkingLevel=max` + `maxTokens=128000`** 给了一轮足够的空间把预算全烧在思考里，
   同时**给续跑机制喂了燃料**。

## 3. 两个会话的共同根因与差异

| | S1 | S2 |
|---|---|---|
| 有没有 Goal | **没有** | 有（`tg_qtuqa3zan3mvjw9ggy`） |
| 循环的载体 | 工具调用（`stopReason=toolUse` 一路到底） | 零工具调用回合（`stopReason=stop`）+ Goal 续跑 |
| 触发器 | 探针信号不可证伪 + 无人叫停 | 继承同一个坑 + **输出退化** + **续跑提示自我复制** |
| runtime 保险 | 无 | 有 Goal，但 `no_progress_streak` / `no_tool_streak` 没计数 |
| 结束方式 | runtime 崩溃（02:53:59） | 用户把 Goal 置为 paused（14:51） |

**四条共同根因：**

1. **追了一个「静态可证伪、真机不可证伪」的目标。**
   说话人名表变长化必须改 ROM 里的机器码；改完之后唯一的验收手段是跑起来看，
   而跑起来只会给出「卡住了」这种**弱信号** ——
   它能证伪「这一处改动是对的」，却不能告诉你「错在哪」。

2. **没有中间可提交的成果，也没有收敛式迭代。**
   两场会话都做了大量工作（补丁清单、指针表、串池、门禁、十几个探针），
   但**没有一次「改一处 → 跑 → 看结果 → 记下来」的循环** ——
   两场都是「再想一个假设」驱动的。

3. **思考预算 ≫ 行动预算。**
   `effort=max` 下单轮思考可达 107k 字符（≈ 10 万 token），
   而一次可验证的动作只要几十秒。预算配比完全反了。

4. **两边都没有「该停了」的信号源。**
   S1 无 Goal ⇒ 无续跑也无叫停；S2 有 Goal，但两个防循环计数器没涨
   ⇒ **runtime 的两道保险都没接上**。

## 4. 结论：怎么不再发生

### 4.1 立刻能做的（针对本项目）

0. **【新增】先装一个「我是不是在打转」的机器判据** ——
   `tools/loop_guard.py` 把这种形态变成能跑出来的结论：

   ```powershell
   python tools/loop_guard.py "<会话目录>\messages.jsonl"
   ```

   五条规则：R1 同址重入（同一个 ROM 地址 / 构建产物扎堆）·
   R2 空转回合率（最近 15 回合里「一条工具都没调」的占比）·
   R3 原地推演（相邻思考又长又像）· R4 同参数命令重复 · R5 思考爆炸（单条 >30k 字符）。

   **它对着两个事故会话都报警，对着健康片段不报警**：

   | 输入 | 结果 |
   |---|---|
   | S1 完整 | ⚠️ R1 `speaker-test.gba`（最近 40 次调用里 40%，之前 1.7%） |
   | S2 完整 | ⚠️ R2 空转回合率 46.7%（7/15）+ R5 单条思考 107,113 字符 |
   | S1 前 320 条（健康期） | ✅ 未触发 |
   | S2 前 150 条（健康期） | ✅ 未触发 |
   | 本次会话全程（健康期） | ✅ 未触发 |

   ⇒ 「我好像在打转」变成「工具说我确实在打转」。**这比自我感觉可靠。**

   **⚠️ 用它盯子代理时踩到的一个坑（2026-10-23 当天修正）**：
   第一版 R5 是「单条思考 > 30k 字符就报警」，结果**误杀了一个健康的 worker** ——
   它写了一条 78,067 字符的规划型思考（「Key tasks: 1..4 / Approach A..D」），
   后面紧跟着 7 次有效工具调用，是**正常推进**。
   区分点不在长度，在**有没有动作**：
   - 长思考 **+ 接着调工具** = 深度规划，正常；
   - 长思考 **+ 一条工具都没调** = 烧光预算、什么也没产出，危险。

   ⇒ R5 已改成「>30k 字符**且该回合没有工具调用**」。
   回归验证：S2 仍然报警（R5 命中 `#356`/`#377`），四个在跑的 worker 全部不报警。

   **第二个同族误报（同一天）**：R1 的锚点集合里原本把**构建产物**（`.gba`/`.png`…）算进去，
   结果 `rom/base.gba` 成了最优锚点 —— 因为**任何 ROM 考证的探针都要读它**，
   反复提到它是**正常工作**，不是循环。⇒ 已把「源 ROM」从锚点里排除
   （`SOURCE_ROM` 正则）。回归：S1 仍报警（`speaker-test.gba`），S2 仍报警，四个 worker 全不报警。

   **第三个同族误报（同一天）**：R4「同名工具 + 同参数重复 4 次」把
   `task_output(wait_ms=30000)` 连调 4 次判成了循环 —— 那是**轮询等待后台任务**，
   每次都返回「还在跑」。⇒ 已把**带 `wait_ms` 的轮询**排除。
   回归：S1 / S2 仍报警，四个 worker 全不报警。

   **第四个同族误报（用它盯子代理时）**：R1 报「反复用同一个测试 ROM」——
   但那个 ROM **正是被调查的对象**，反复用是正常的；
   而且那个 worker 在同一窗口里**新写了 10 个诊断脚本**（每个回答一个新问题），
   是**深入排查**，不是打转。
   ⇒ 我试过「窗口里有新产物就压制 R1」，**结果把真正的事故会话 S1 也压掉了**
   （S1 的窗口里同样写过文件）。
   ⇒ **最终设计：判据只负责「把可疑点标出来 + 给出人工判据」，不负责自动下结论。**
   R1 命中时会把「窗口内新写了几个文件」一并打出来，供人判断
   （新产物多 ⇒ 更可能是在深挖；没有新产物 ⇒ 更像原地打转）。
   **这条是本项目最重要的元教训**：
   > **自动判据用来「提醒」，不用来「下结论」。**
   > 误杀的代价（砍掉正在推进的工作）远大于漏报（多看一次明细）。

   **第五个同族误报（同一天）**：R2 原口径是「最近 15 条里有几条没调工具」，
   结果把**写汇总报告时的空转回合**判成了循环（实测：某个 worker 的空转回合
   之间夹着真实工作，被报成「连续 3 次空转」）。
   ⇒ 已改成「**连续**的空转回合有多长」（按助手回合序比较，用户消息不算打断）：
   - 真循环是**一串接一串**的空转（Goal 续跑提示夹在中间也算连续）⇒ S2 仍报（连续 4 回合）；
   - 空转之后又接着干活的 ⇒ 不报。
   回归：S1 仍报（R1）、S2 仍报（R2+R5）、健康片段与在跑的 worker 全不报。

   **五条误报合起来是同一条教训**：
   1. **「重复」不等于「循环」** —— 等待（轮询）、读输入（源 ROM）、长思考后接着行动、
      反复用「被调查的那个对象」、写汇总时的空转回合，都是**正常形态**；
      循环的特征是「重复**且没有新信息**」。
   2. **任何自动判据都必须先在「已知坏样本」和「已知好样本」上双向验证过**，
      否则它会开始误杀 —— 而**误杀的代价（砍掉正在推进的工作）比漏报更大**。
   3. 所以本项目的规矩是：**先看细节再动手，绝不因为一条规则命中就砍人**。

1. **把「验收」拆成可证伪的小步，并留下结论表。**
   一次只改**一处**（一处补丁 / 一条名字 / 一个断点），跑一次，记一行
   「改动 → 屏幕 diff → 是否卡」。工具已经齐了
   （`tools/mgba_probe/speaker_bisect.py`、`build/conv-base.png` / `conv-test.png`），
   **缺的是那张表** —— S2 做了二分却没留下结论。
   ⇒ 这张表已经落成 `notes/evidence/speaker-names-hypothesis-ledger.md`：
   **一行一个假设（判定方法 / 结果 / 状态）**，已证伪的 5 条、待验的 5 条都写在里面了，
   下一个会话从 U1/U5 开始就行，**不用重推一遍**。

2. **给思考设上限。**
   这类「机器码级」任务把 thinking effort 降到 medium/high，
   或在任务里写死：**「一次只验一个假设；同一探针连续 3 次给同样结果 ⇒ 停，换方法，并写下来」**。

3. **不要用 Goal 续跑扛长任务。**
   Goal 的续跑提示会**逐字重复**（只差时间戳），
   对「陷在同一个坑里」**毫无帮助**，反而把循环固化下来。
   陷住了应该**换方法 / 换会话 / 收窄目标**，而不是让它继续。

4. **每个回合都要留下可提交的东西。**
   一个假设被证伪 ⇒ 写进 **假设台账**（`notes/evidence/speaker-names-hypothesis-ledger.md`），
   一行一个假设，带判定方法和状态。
   这样下一个会话不用重走同一段路。
   **叙述性笔记（「我试了 X，不行」）不够** —— 它不能被勾选、不能被交接。

### 4.2 值得上报给 runtime 的两个缺口

1. **Goal 续跑提示不区分「这轮没进展」和「换个方法继续」。**
   现在的续跑语义是「再试一次」，
   而陷死在同一个坑里时需要的是「**换方向**」。
   建议：续跑提示里带上「上一轮做了什么、为什么没成」的摘要，或者允许 Goal 声明退出条件。

2. **`no_progress_streak` / `no_tool_streak` 在整场 S2 里都是 0。**
   10 轮里 10 轮零工具调用，这两个字段却没涨 ⇒ 判定逻辑要么没接上，
   要么阈值算错了。**这是 runtime 侧可以直接查的。**

### 4.3 一个附带发现

`llm-call.json` 里带着 `outputRevisionInstruction`：

> "Please attempt to answer the user's question once more, aiming for a helpful response.
> If you determine that this particular topic is one you cannot reasonably address,
> simply reply with something brief like …"

这是 runtime 在**输出被判为不合格**时用的重试指令。
S2 的 `#377`（10.5 万 output tokens、零工具调用）几乎肯定触发了这条路。
⇒ **「一轮输出用光预算却什么都没产出」会被当成『答得不好』而重试**，
而不是被当成「模型卡住了」而熔断 —— 这也是 S2 能循环 10 轮的原因之一。

## 5. 一句话

> **两个会话都不是「想不出来」，是「没有能证明自己错了的东西」。**
> S1 的探针只会说「还是卡」，S2 的续跑提示只会说「再来一次」——
> 于是一个不停提假设，一个不停重开同一轮。
> 真正的修法是**让每一次尝试都产出一个可判定的结果**，
> 并且在连续几次结果相同时**主动换方向**，而不是把同一件事再想一遍。
