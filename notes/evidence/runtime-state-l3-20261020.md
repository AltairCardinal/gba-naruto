## 0. 结论

用真实 ROM 在无头 mGBA 里跑起来，把游戏**自己写过的**字段读回来：

| 字段 | 地址 | 运行时读数 | 静态结论是否成立 |
|---|---|---|---|
| `scene_id` | `0x020311EA` | 随剧情变化 **54 → 50 → 40** | ✅ 成立（并与 `notes/evidence/story-vm-l2-20261020.md` 的场景号一致） |
| `battle_stage` | `0x02026805` | 任务开始时写入 **40 (0x28)** | ✅ 成立 |
| `battle_sub` | `0x02026806` | **0** | ✅ 成立 |
| `party_slot_base` | `0x02022E34` + 0xBC | 槽 1 = **角色 ID 1、等级 1** | ✅ 成立（ID 1 = 漩涡鸣人） |
| `battle_unit_base` | `0x020240C0` | **全 0**（演习场任务不实例化战斗单位） | ⚠️ 本轮未取得读数（见 §4） |
| `clear_flag` | `0x0203150F` | **0** | ✅ 成立（新游戏清零） |
| 回合上限 | `0x0202680A` | **0**（stage 40 的规则表回合上限就是 0） | ✅ 成立 |
| 计数块首字节 | `0x0202680C` | **0**（紧邻的 `+1` 字节为 1） | ⚠️ 语义未闭合（见 §3） |

外加两条**写入方向**的运行时事实（不是读数，是观察到的写）：

- 新游戏时游戏**自己**把 `0x02022E34` / `0x020240C0` / `0x02026804` /
  `0x020311D4` / `0x0203150C` 全部清零（写监视点命中）。
- 剧情推进中游戏**自己**写 `0x020311D4` 起的剧情 flag 块
  （写监视点命中；写者的 PC 在一次手工探针会话里定位到剧情 VM 的
  `0x0808C1A2` / `0x0808C182` / `0x0808C20C`，当时 `r1 = 0x020311D4`）。

## 1. 复现命令

```powershell
$env:PYTHONIOENCODING='utf-8'

python tools/runtime_capture.py rom/base.gba
python tools/runtime_capture.py rom/base.gba --json build/runtime-state.json
```

工具自己完成：启动 ROM → 30 次 START → 400 次 A（走完开场剧情）→
`B, B`（退出到修行场菜单）→ `UP`×6（选中「练习移动」）→ `A, A`（确认任务）
→ 读回所有字段；另外起一个**独立**探针会话挂写监视点，收集「谁在写」的证据。

> 为什么写监视点要单独开会话：挂上监视点后 mGBA 走 debugger 路径，
> 帧时序会变，菜单光标会落到别的条目上（`notes/mgba-probe-runtime-20261020.md`
> §6.1 记过同一个坑）。读数要可靠就不能挂断点，写证据可以另外开会话。

### 2.1 `scene_id`（`0x020311EA`）——本轮最硬的运行时闭环

开场剧情推进过程中，**同一个字节**依次读出 54、50、40，
正好是剧情 VM 自己报的三个场景号（`notes/evidence/story-vm-l2-20261020.md`
记的断点命中 `r0 = 0x36 = 54`）。

> ⚠️ 与 `notes/mgba-probe-runtime-20261020.md` §4.1 的关系：
> 那条笔记说「`0x020311EA` 没有原生读者，所以它不是场景号」。
> **本轮的运行时读数把它的结论改掉了**：这个字节**没有原生读者**（游戏自己
> 用别的方式写它），但它**在运行时确实等于当前场景号**。
> 结论从「不是场景号」修正为「**是场景号，但是由剧情脚本写、
> 不是由原生代码读**」。这条修正只影响
> `notes/runtime-and-object-tables-20261020.md`（本轮已同步）。

**可证伪检验**：在场景 54 时该字节必须读出 54；
若在剧情推进时它保持不变（或与剧情 VM 报的场景号不同），
「scene_id」这个字段名就被推翻。

### 2.2 `battle_stage` / `battle_sub`（`0x02026805` / `0x02026806`）

选「练习移动」任务并确认之后，游戏把 `0x02026805` 写成 **40 (0x28)**，
`0x02026806` 保持 0。40 与这个任务在战斗规则表里的 stage 一致
（stage 40 sub 0 = 「得到宝箱！」）。

**可证伪检验**：把 `0x02026805` 改成别的 stage，编成矩阵的选择必须跟着变
（`0x0806E3C2` 的消费者用 `ctrl[1]*0x1AAC + ctrl[2]*0x8E4` 选组）；
若不变，该字节就不是 stage。

### 2.3 队员槽（`0x02022E34 + 0xBC`）

槽 1 的运行时内容：`01 01 0e 0d 08 03 05 05 05 00 0f 00 50 00 50 00 ...`

- `+0x00 = 0x01` → 角色 ID 1 = 漩涡鸣人（与屏幕上的鸣人一致）
- `+0x01 = 0x01` → 等级 1
- `+0x0E/+0x0F = 0x0102` → 体力上限 258

**可证伪检验**：换掉队长后该字节必须跟着换；
若一直不变，它就不是角色 ID。

## 3. `0x0202680C` 的现状（本轮收窄）

静态侧本轮查到的新事实：

1. 战斗初始化例程 **`0x08068BA4`** 把它所在的块从 WRAM
   **`0x02024068`** 复制过来：
   `[0]`/`[1]`/`[2]` → `0x0202680C[0..2]`，
   `[3]` → `+0x26C`，`[4]` → `+0x26D`，`[5..9]` → `+0x3B4..+0x3B8`。
2. 全 ROM 扫描**找不到任何直接写 offset 0** 的原生代码；
   已知写入点都带偏移：`0x080770BE`/`0x08077202` 写 `+0x24A`，
   `0x0806C838` 写 `+0x249`，`0x0806B20C` 写 `+0x3B6+side`。
3. 读它的只有三处规则 arm 与一处兜底路径
   （`notes/reward-and-rules-semantics-20261020.md` §4.3）。
   兜底路径 `0x08077BB6` 在「回合上限 == 该字节」时弹
   `0x0812F1E4 =「结束该回合」`。

运行时侧本轮拿到：任务开始后 `0x0202680C = 00`，`0x0202680D = 01`；
回合上限 `0x0202680A = 0`（stage 40 的规则就是 0）。

**因此现在的准确说法是**：
`0x0202680C` 是**每场战斗的计数/标志块**的首字节，
只在**结算时**被当成「回合计数」与回合上限比较；
**它是不是随回合递增，本轮没有证据**（既没找到写入者，也没进到有回合的战斗里）。

**可证伪检验（未做）**：在 stage 1（回合上限 15）的战斗里逐回合读
`byte[0x0202680C]`：每回合 +1 且第 15 回合等于上限 → 「当前回合计数」成立；
若它是常数 → 收窄结论成立。

## 4. 本轮走过的弯路（按 `AGENTS.md` 记录）

1. **按网页 WASM 探针的路线找战斗**：`B, Down, Down, A, A`（`notes/wasm-formation-probe-result-20260710.md`）
   在 ROM 探针里走不通——A 键按到 9000 次剧情也不再前进。
2. **只按 A 键**：开场剧情只能从场景 54 走到 40，
   然后停在「人物信息」页（漩涡鸣人 LV1），A 键无效。
3. **挂断点再走菜单**：菜单光标会落到别的条目（时序被断点改变），
   `0x02026805` 就不再被写成 40。→ 读数与写证据必须分两个会话。
4. **进「演习场」任务**：能进，画面变成战斗 UI
   （「距离敌人 / 本体 / 技 / 体力・忍力 / HP 8/8」），
   但 **`0x020240C0` 战斗单位数组仍然是全 0**——
   这个任务（stage 40 sub 0「得到宝箱！」）是**移动教学**，
   不会实例化战斗单位，所以 `positions` 的原生消费者
   （`0x0806E41E`/`0x0806E71E`）**不会被执行**。
   → `positions` 的运行时命中仍然缺（见 §5）。
5. **写监视点的 PC 读不出来**：命中后立刻 `status` 得到的是
   `pc=0x00000240` 之类的垃圾值；把 `next` 放在 `status` 之前也一样。
   写者的 PC 是在一次**手工**探针会话里定位的
   （剧情 VM，`r1 = 0x020311D4`），本轮工具无法自动复现这一点。
