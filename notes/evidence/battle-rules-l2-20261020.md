**工具**: `tools/battle_rules_runtime.py`（本轮新增）
**探针**: `tools/mgba_probe/`（无头 mGBA，`build/mgba-probe/mgba-probe.exe`）
**ROM**: `rom/base.gba`
**对应审计条目**: `notes/completion-audit-20261020.md` #3「战斗胜负条件表」

## 0. 结论

| 问题 | 本轮结论 | 等级 |
|---|---|---|
| 类型 2 的代码判据 | **确证 = 「回合上限到达」**：比较 `0x0202680A`（回合上限）与 `0x0202680C` 的首字节 | L2（原生代码在模拟器内执行 + 寄存器读数） |
| 类型 2 是否读 `rule.a/rule.b` | **确证不读**：把 `r5` 指向另一条规则记录或全 0xFF 的 RAM，判定完全不变 | L2 |
| 类型 2 与类型 3 是否互为反面 | **确证不是**：类型 3 的判定随「指定角色是否在场」翻转，类型 2 完全不随角色在场与否变化 | L2 |
| 类型 3 的语义 | **确证 = 「指定角色已离场」**：角色在场 → 条件不成立；角色不在场 → 条件成立 | L2 |
| `0x0202680C` 是什么 | **收窄**：它是「每场战斗的计数/标志块」的首字节，**只在结算时**与回合上限比较；本轮仍**没有找到它的直接写入者** | 见 §5 |

> 本文件的等级是 **L2（原生断点定点 + 寄存器读数）**，不是 L3：
> 上下文是**注入的**（探针用 `w/1`/`w/4`/`w/r` 写入 WRAM 并跳进原生代码），
> 不是在一场真实战斗里自然发生。L3 仍缺的证据见 §5。

## 2. 捕获到的寄存器

### 2.1 原生分派器命中类型 2 arm（`0x08077904`）

工具把 `0x02026804` 的 stage/sub 设成 `1/0`（stage 1 的回合上限是 15），
把 `0x0202680A` 设成 15、`0x0202680C` 设成 15，然后**从 `0x080777FC`
（分派函数入口）进入**，让 ROM 规则表自己决定走到哪个 arm。
在 `0x08077904` 断点上捕获到的寄存器：

```
r0  = 0x08077904      <- 被跳转表装入的 arm 地址
r1  = 0x08077878      <- 9 项跳转表基址
r5  = 0x08594830      <- 当前规则记录（ROM，stage1/sub0 组0 第1条：type=2 a=0 b=31）
r6  = 0x02026804      <- 战斗控制块
r8  = 0x00000001      <- 结算检查标志（mode = 1）
r7  = 0x00000001      <- 组内规则下标
sp  = 0x0203FECC
lr  = 0x08500000      <- 返回陷阱（注入用）
ctrl[6] = 15          0x0202680A
byte[0x0202680C] = 15
```

**要点**：`r5` 指向的就是 ROM 规则表里那条 type=2 的记录，
`r8=1` 说明这条判定是**结算时**（mode=1）才做的。→ 类型 2 是原生代码路径，
不是数据巧合。

### 2.2 arm 内的判定矩阵（直接进 arm，单步到分支）

判定口径：分派器的「条件成立」续点是 `0x08077B28`，
「条件不成立 / 下一条规则」续点是 `0x08077B3A`。

| 用例 | 终态地址 | 判定 |
|---|---|---|
| type2：mode=1，上限 15，计数 15 | `0x08077B28` | **成立** |
| type2：mode=1，上限 15，计数 14 | `0x08077B3A` | 不成立 |
| type2：mode=0，上限 15，计数 15 | `0x08077B3A`（提前从 `0x0807790A` 跳出） | 不成立 |
| type2：mode=1，上限 0，计数 0 | `0x08077B3A`（从 `0x08077912` 跳出） | 不成立 |
| type2：mode=1，上限 15，计数 15，**角色不在场** | `0x08077B28` | **仍然成立** |
| type3：角色在场（unit[1] 角色 ID 31、阵营 0） | `0x08077B3A` | 不成立 |
| type3：角色不在场 | `0x08077B28` | **成立** |

type2 成立时的完整指令路径（`next` 单步，非推测）：

```
0x08077906 -> 0x08077908 -> 0x0807790C -> 0x0807790E -> 0x08077910
-> 0x08077914 -> 0x08077916 -> 0x08077918 -> 0x0807791A -> 0x0807791E -> 0x08077B28
```

对应源码（`notes/reward-and-rules-semantics-20261020.md` §4.3 已静态记录）：

```
0x0807790C: ldrb r1, [r6, #6]      ; r1 = 0x0202680A 回合上限
0x08077914: ldr  r0, [pc, #8]      ; r0 = 0x0202680C
0x08077916: ldrb r0, [r0]          ; r0 = 计数块首字节
0x08077918: cmp  r1, r0            ; 回合上限 vs 计数
0x0807791A: beq  0x0807791E        ; 相等 -> 条件成立
```

### 2.3 arm 里的寄存器读数（进 arm 时的现场）

```
type2 arm 入口：r0=0x00000001  r5=0x08594830  r6=0x02026804  r8=0x00000001  pc=0x08077906
type3 arm 入口：r0=0x00000001  r5=0x08594850  r6=0x02026804  r8=0x00000001  pc=0x08077926
```

单步到 `0x0807790E` 之后可以读到 **r1 = 0x0000000F**（= 回合上限 15），
单步到 `0x08077916` 之后 **r0 = 0x0202680C**（计数块指针）。

## 3. 「type-2 不读 rule.a/rule.b」的证据

### 3.1 读监视点（本轮失败，已记录）

工具给规则记录挂 `watch/r`：

```
type 2 record    0x08594830: 0 watchpoint hit(s) - expected no hit
type 3 record    0x08594850: 0 watchpoint hit(s) - expected hit      <- 对照组也 0
WRAM control     0x0202680C: 0 watchpoint hit(s) - expected hit      <- 对照组也 0
```

**结论：mGBA 0.10.5 的读监视点在本探针里对 ROM 和 WRAM 都不上报**
（连一定被读过的 `0x0202680C` 也没有命中），所以这条路径**不能**当证据用。
这是本轮的一个**死路**，记录在案。

### 3.2 行为学检验（替代证据，成立）

把 `r5`（规则记录指针）分别指向三种东西，其余状态不变：

```
type-2 arm with r5 = rule record of the type-2 row    -> satisfied
type-2 arm with r5 = rule record of the type-3 row    -> satisfied
type-2 arm with r5 = RAM buffer full of 0xFF          -> satisfied
```

**判定一次都没有变**。如果 type-2 arm 读了 `rule.a/rule.b`，
把 `r5` 指向 type-3 那条记录或全 0xFF 的 RAM 至少会改变结果。

### 3.3 与静态证据的一致性

`notes/reward-and-rules-semantics-20261020.md` §4.3 已断言
「type-2 arm 对规则记录的读取次数 = 0」。本轮的运行时结果与它一致。

## 4. 「type-2 不是 type-3 的反面」的证据

- type-2：角色**在场 / 不在场**都判「成立」（只取决于计数块与回合上限）。
- type-3：角色**在场**判「不成立」，**不在场**判「成立」。
- 两者对「角色在场」的反应**方向相反且不相关**。

所以 11 条 type-2 数据行（`a/b` 与 type-3 兄弟行一一成对）的
`a/b` 字段**没有被这版 ROM 的 type-2 arm 使用**：
数据表达的是「指定角色仍在场」，代码执行的是「回合用尽」。

## 6. 本轮走过的弯路（按 `AGENTS.md` 记录）

1. **直接 `w/r pc` 跳进 Thumb 代码**：CPU 变成 ARM 模式在跑，
   `ldrb` 根本没执行，`r1` 一直是 `0x04000054`。
   原因：mGBA 用 `cpu->cpsr.t` 决定 `writeRegister` 走 `ThumbWritePC` 还是
   `ARMWritePC`，而探针里的 `w/r cpsr` 会把值掩成 `0xF00000FF`，
   写 `0x1F` 会**清掉 T 位**。修法：先 `w/r cpsr 0x3F`（Thumb + system）再写 PC。
2. **拿 `w/r r5` 写文件偏移**：规则记录指针必须给 **ROM 地址**
   （`0x08594850`），给文件偏移（`0x594850`）时 type-3 arm 读到的是
   WRAM 垃圾，两条 type-3 用例都判成 `other(...)`。
3. **读监视点**：见 §3.1，对 ROM/WRAM 都不上报，改用 §3.2 的行为学检验。
4. **单步步数不够**：type-3 arm 要扫 12 个单位槽（≈130 条指令），
   `next` 的步数上限从 24 提到 240 才跑完。
5. **进真实战斗**：见 `notes/evidence/runtime-state-l3-20261020.md` §4
   （能进「演习场」任务，但该任务不实例化战斗单位）。

## 7. 可证伪检验（下一轮要做的）

- **F1（对「不读 a/b」）**：把 stage 1 sub 0 那条 type-2 记录的 `b`（31）
  改成 30（同一场景里 30 不在我方），跑同一串按键，
  结算文字必须**完全不变**（仍按「回合用尽」判）。
  若结算变成「保护了达兹纳」→ 本轮结论被推翻。
- **F2（对「回合用尽」）**：在 stage 1（上限 15）里把 `0x0202680A` 改成 14，
  并让 `0x0202680C` 保持 15（或反过来），type-2 必须**不再成立**；
  两者相等时必须以「保护了达兹纳」这段文字结算。
- **F3（对 type 3）**：让达兹纳离场（清掉单位槽），失败组的 type-3 必须成立、
  游戏必须显示「没能保护达兹纳……」。
- **F4（对 `0x0202680C`）**：在一场 stage 1 的战斗里逐回合计数
  `byte[0x0202680C]`，若它每回合 +1 且在第 15 回合等于回合上限，
  则「当前回合计数」成立；若它是常数，则本轮的收窄结论成立。
