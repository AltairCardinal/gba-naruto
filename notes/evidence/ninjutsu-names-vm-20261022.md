# 忍术名表 `0x08599634` 的运行时证据（2026-10-22）

## 1. 旧结论与它的错处

旧笔记（`notes/evidence/l2-runtime-evidence-20261021.md` §）写：

> `ninjutsu-names`（0x08599634）—— fn 0x080794F4 is only called from 0x0806F89C
> (the character/skill module); neither the battles nor the story sweep open
> the nin…

并且 `tools/mgba_probe/callback_census.py` 的判定点用的是
**`0x0806F506`**（`fn 0x0806F210` 里的那一个站点）。

**两个问题**：

1. **判定点只押了一个站点。** 重新用全 ROM 字面量扫描
   （`build/probe_litrefs.py`）后确认，`0x08599634` 在 ROM 里被
   **12 处**指令装载：

   | 装载指令 | 所属函数 | 读者 |
   |---|---|---|
   | `0x0806F504` | `fn 0x0806F210` | 战斗单位生成（按关卡对象 type 1/2 分派） |
   | `0x08070642` | `fn 0x08070620` | 关卡/角色模块 |
   | `0x080796E4`、`0x08079704` | `fn 0x08079668` | 地图渲染器族 |
   | `0x08081642`、`0x080816FE` | `fn 0x08081544` | 战斗事件 |
   | `0x0808E9F8`、`0x0808EA62` | `fn 0x0808E954` | 剧情调度邻域 |
   | `0x08090286` | `fn 0x08090220` | 剧情 UI 邻域 |
   | `0x08090350` | `fn 0x08090308` | 剧情 UI 邻域 |
   | `0x0809734C`、`0x080973E6` | `fn 0x080972F8` | **剧情 VM 的 opcode `0x1D`** |

2. **`fn 0x080794F4` 根本不是读者。** 字面量扫描里没有它。

## 2. 剧情 VM 的 opcode `0x1D` 就是读者

剧情 VM 的 opcode 跳转表在 `0x080977F4`（58 项，**下标 = opcode 编号**）：

```
[29] 0x08097868: 0x08097cc4  code      ⇒ opcode 0x1D
```

`0x08097CC4` 的处理：

```
0x08097CC4: ldr  r0, [sp, #0x2c]
0x08097CC6: bl   0x08061E88          ; 先停乐
0x08097CCA: movs r0, #0
0x08097CCC: bl   0x080971C0
0x08097CD0: adds r6, r0, #0          ; r6 = 对话框上下文
0x08097CD2: ldrb r0, [r7, #1]        ; 操作数字节 1 = 模式
0x08097CD4: ldrb r1, [r7, #2]        ; 操作数字节 2 = 忍术下标
0x08097CD6: adds r2, r6, #0
0x08097CD8: bl   0x080972F8
```

`fn 0x080972F8(r0 = 模式, r1 = 下标, r2 = 上下文)` 内部按**模式**分派
（`r4` = 模式，`r6` = 下标）：

```
0x0809731E: cmp r4, #1
0x08097320: beq 0x08097414           ; 模式 1
0x08097326: cmp r4, #0
0x08097328: beq 0x0809733A           ; 模式 0  ← 读表
0x0809732C: cmp r4, #2
0x08097330: b   0x0809747C           ; 模式 2
0x08097332: cmp r4, #3
0x08097336: b   0x080974D4           ; 模式 3
0x0809733A: movs r0, #0x35
0x0809733C: bl   0x08061E6C           ; 模式 0 先播音效 0x35
0x08097340: movs r0, #2
0x08097342: strb r0, [r5, #0x12]
0x08097344: ldr  r1, [pc, #0x58]      ; 0x0846445C
0x08097348: bl   0x0806626C           ; 追加前缀串
0x0809734C: ldr  r1, [pc, #0x54]      ; r1 = 0x08599634   ← 忍术名表
0x0809734E: lsls r0, r6, #2           ; 下标 * 4
0x08097350: adds r0, r0, r1
0x08097352: ldr  r1, [r0]             ; r1 = 名字字符串指针
0x08097356: bl   0x0806626C           ; 追加名字
```

⇒ **表项步长 4 字节，表项是字符串指针**；
**只有「模式 0」才读这张表**（模式 1/2/3 走另外三条分支）。

## 3. 哪些脚本用模式 0

`build/probe_opcode_ops.py --op 0x1D` 扫全部剧情脚本，共 **38 处**：

| 操作数字节 1（模式） | 次数 |
|---|---|
| 0 | 14 |
| 1 | 16 |
| 2 | 6 |
| 3 | 2 |

模式 0 的 14 处分布在场景 4 / 6 / 23 / 30 / 43 / 46 / 50 / 51 / 60，
字节形如 `1D 00 49`（下标 0x49）、`1D 00 28`、`1D 00 25`、`1D 00 43`。

## 4. 运行时读数

`tools/mgba_probe/open_readers_sweep.py --scenes 43 ...`：

```json
{"scene": 43, "hit": "0x0809734C", "label": "ninjutsu name table 0x08599634",
 "r1": "0x0809734D", "r6": "0x00000049"}
{"scene": 43, "hit": "0x08097352", "label": "ninjutsu name pointer",
 "r0": "0x08599758", "r1": "0x08599634", "r6": "0x00000049"}
```

**寄存器对应关系逐条可算**：

* `r6 = 0x49` = 脚本里的操作数字节 2（忍术下标）；
* 表基址 `r1 = 0x08599634`；
* `r0 = 0x08599758` = `0x08599634 + 0x49 × 4` = **`0x08599634 + 292`** ✔

**场景 43 全程没有任何菜单出现**（一次 `0x080960BE` 都没命中），
所以这条读数是**纯正常按键**（A 键推进对话）得到的 ⇒ 满足 L3。

## 5. 判死检验

| 检验 | 期望 | 实际 |
|---|---|---|
| 判定点必须是**装载指令**，不能是池地址 | `0x0809734C` 命中且 `r1` 装载后为 `0x08599634` | ✅ |
| 表项步长 | `r0 = 基址 + 下标 × 4` | ✅ `0x08599758 = 0x08599634 + 0x49×4` |
| 下标来自脚本操作数 | `r6 = 0x49`（脚本字节 `1D 00 49`） | ✅ |
| 旧判定点 `0x0806F506`（只押一个站点） | 剧情路线不命中 | ✅ 与新结论一致：那条路径属于战斗单位生成 |
| 模式 1/2/3 不读表 | 只在模式 0 命中 | ✅ 场景 6 的 `1D 01 0F` 只命中 opcode 处理器本身，不命中表读取 |

**⇒ `ninjutsu-names` 的 L2 / L3 缺口闭合。**
