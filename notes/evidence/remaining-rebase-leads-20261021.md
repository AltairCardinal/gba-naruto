# 剩余 legacy 基址：三条已定位到候选的线索（2026-10-21）

**本文不是结论，是线索。** 三条都还没到「可裁决」的程度，所以对应的 bank
**仍然是**审计里的 `rebase` 缺口。本文把已经查实的东西写下来，
让下一个人不用从头再来。

工具：`tools/legacy_rebase.py`（全量字面量索引 + 符号化步长推导）。

---

## 0. 这一轮的通用规律

已经落地的 10 个 bank 全部是同一个形状：**旧基址是某张真表的错位窗口**。
错位量分两类：

| 类型 | 例 | 旧基址 |
|---|---|---|
| 字段级错位 | `character-stats` | `0x54507A = 0x545068 + 1*16 + 2` |
| 记录级错位 | `character-stats-b` | `0x545200 = 0x545068 + 25*16 + 8` |
| 记录级错位 | `levels` | `0x5459D4 = 0x5459C8 + 1*12` |
| 记录级错位 | `items`/`skills` | `0x546100 = 0x545BE4 + 81*16 + 12` |
| 字段级错位 | `story`×5 | `0x53636C = 0x536368 + 4`（`voicegroup_ptr` 字段） |

**所以下一步的做法是**：对每个候选基址 L，
验 `旧基址 − L = k*stride + 字段偏移`，
再验 `L + 条数*stride` 是不是**正好**落在另一个已知结构上
（这是最强的收口证据：`0x545068+63*16 = 0x545458`、`0x5459C8+45*12 = 0x545BE4`、
`0x545BE4+94*16 = 0x5461C4`、`0x536368` 是 sound-ID 表第 1 行的指向）。

## 1. `battle-handlers`：候选 `0x53E698`，步长 8

```
$ python tools/legacy_rebase.py rom/base.gba --target 0x53E6D8
     -0x3c  0x0853E69C  0x53E69C  1  0x0807F958 0x0807F414 indexed  8
     -0x40  0x0853E698  0x53E698  2  0x0807F934 0x0807F414 indexed  8
```

`0x53E698` 有 **2 个原生读者**、步长 **8**；旧基址
`0x53E6D8 = 0x53E698 + 8*8`（第 8 条记录的第一个字）。

内容形态（8 字节 = 一对代码指针）：

```
[ 0] 0x53E698 00000000 00000000
[ 1] 0x53E6A0 0807E071 00000000
[ 2] 0x53E6A8 0807E649 00000000
[ 3] 0x53E6B0 00000000 00000000
[ 4] 0x53E6B8 0807E775 00000000
[ 5] 0x53E6C0 0807E86D 0807F065
[ 6] 0x53E6C8 00000000 0807F1B1
[ 7] 0x53E6D0 0807E1C9 00000000
[ 8] 0x53E6D8 0807EFFD 0807F065   ← 旧基址
```

旧 bank 记录的 14 个 u32 恰好就是从第 8 条开始的 7 条记录（前半 + 后半），
其内容与旧 bank 抽到的「14 个 Thumb 代码指针」完全吻合。

**还缺的证据**：这张表**有多少条**。下一个活的字面量是 `0x53EE98`
（+0x800 = 256 条），但那已经是**另一张表**（10 字节步长的帧描述符表）。
所以条目数必须从读者代码里取下标上界 ——
读者 `0x0807F934` / `0x0807F958`（fn `0x0807F414`）。
我 disassemble 了 `0x0807F414` 的开头 45 条指令，**没有**看到它对 `0x53E698`
的索引 —— 说明这两个读者**可能**是按别的基址算的（`0x0807F420` 的字面量
被加到一个 WRAM 基址上），需要把整个函数读完才能定位。
**别把「2 个读者 + 步长 8」当成已证**。

## 2. `fonts`：候选 `0x53E496`，步长 1（字节表）

```
     +0x11e  0x0853E496  0x53E496  5  0x0807BB70 0x0807B8B8 indexed  1
     +0x1e   0x0853E596  0x53E596  1  0x0807F0FC 0x0807EE50 indexed  1
```

`0x53E496` 起是**字节表**（取值域 0 / 120..125 / 130..144 —— 正是像素宽度
那类小整数），旧基址 `0x53E5B4 = 0x53E496 + 286`。
但 `0x53E496 + 256 = 0x53E596`，而 `0x53E596` **自己**也是一个候选
（stride 1）—— 所以这里其实是**两张连续的字节表**，
旧基址落在**第二张**里（`0x53E5B4 = 0x53E596 + 30`）。

**还缺的证据**：
（a）两张字节表各自的长度与边界；
（b）`0x53E496` 与 `0x53E596` 的读者代码（`0x0807BB70` 有 **5 个读者**，
`0x0807F0FC` 1 个）分别怎么用它们。
另外 `0x53E5B4` 起往后 0x100 字节里混着别的数据（`0x53E6B4` 之后能看到
`71 e0 07 08` 这种代码指针），所以「256 字节宽表」这个假设本身要验。

## 3. `battle-encounters`：**已裁决**（真基址 `0x54229C`，24 条 × 16 字节）

`0x542384` 没有读者，但内容形态非常明确。候选 `0x54229C` 有 2 个读者，
用法是 `ldr r0, [r0, #0xc]` —— 读记录的**第 4 个字**。

按 **16 字节记录 `(u32 ptr, u32 ptr, u32 ptr, u32 id)`** 排列时，每个记录的
第 4 个字都是一个小整数编号：

```
0x54229C  0812FF50 08130268 08130290 00000004
0x5422AC  081303E8 08130D30 08130D58 0000000A
0x5422BC  08130F50 08131794 081317BC 0000000E
...
```

而且 **`0x54229C + 24*16 = 0x54241C`** —— 正好是角色模板的起点。
（若按 12 字节记录排列，编号字段的位置会漂移 —— 这就是必须用 16 字节
对齐才能看清的原因。）

旧基址 `0x542384 = 0x54229C + 14*16 + 8`（第 14 条 + 8 字节）。

**可证伪判据**：`0x54229C + 24*16` 必须仍等于 `0x54241C`；
2 个读者的用法必须仍是 `ldr r0,[r0,#0xc]`；旧 bank 的条目必须逐字节等于
ROM 在 `0x54229C + 16*i + 8` 处的字节。

**已落地**：bank.json、registry（`battle_encounter_records`）、
`tools/legacy_rebase.py::REBASED_TABLES`、完成度审计（L1，只读参考）。
