## 1. 方法

* **基址不许手写**：基址来自 `tools/table_registry.py` 的 `TABLES`（加
  `ROM_BASE`）；读者来自 `tools/consumer_locate.py` 的 `LiteralIndex`
  （全 ROM 字面量索引）。工具每次运行都会重新索引，并断言
  “本结构声明的消费者地址 ∈ 索引给出的读者集合”。
* **新增“间接指针表”结构（`via_pointer`）**：5 个 `story*` 结构
  **没有任何字面量读者** —— 它们的地址不是被 `ldr rX,[pc]` 装载的，
  而是**作为 u32 指针存放在声音 id 表 `0x08465B70` 里**，由 `ldr rX,[rN]`
  间接取出。工具因此新增 `via_pointer` 规格，静态检查改成三条机械断言：
  1. 那个指针表**有**原生字面量读者；
  2. 本结构的基址**确实是**该指针表里存着的那个 u32（并给出槽号）；
  3. 指针表的声明范围落在 ROM 内。
  这是**加严**而不是放松：表地址来自 registry，读者集合来自 `LiteralIndex`。
* **新增捕获的 `role` 机制**：一个结构的“证明”可以有多段（“声音 id 表
  指到这个 SongHeader” / “m4a 引擎读了它的字段”）。每段捕获带一个
  `role`，结构只有在**每个必需 role 至少有一条通过的捕获**时才算 L2。
  没有 `role` 的捕获共用默认 role，所以旧结构的判定语义
  （“任意一条通过即可”）**完全不变**。
* **新增捕获的 `match` 预筛**：m4a 播放入口**每首歌都会被命中**，
  所以一个判定点上的几百次命中里只有一次是本结构的。工具在评价之前
  先做一次廉价的寄存器比较（`match: {reg, value}`），不匹配的命中
  **直接跳过、不消耗预算**。没有这一层，粘性断点的预算会被别的歌吃光
  （本轮第一版就踩了这个坑：`story-c` 在战斗路线里 256 条预算被
  别的歌耗尽而漏掉）。
* **逐判定点的粘性断点预算**：预算从“每个结构 24 条”改成
  “**每个判定点** 256 条”。
* **⚠ 新发现的方法学陷阱：多挂断点会改变剧情的推进。**
  mGBA 的 `frames N <key>` 命令**在断点命中时提前返回**，而**按键仍然按着**
  （`keyoff` 要等命令正常走完才执行）。于是：一条路线上多挂几个“每首歌都会
  命中”的断点，按键被按住的总帧数就变长，剧情推进的节奏随之改变，
  **同一条路线、同一个场景编号，触发的事件序列可以完全不同**。
  本轮实测到的具体后果：
  * `story-c` 的“链接”捕获（读者 `0x0809AAC6`）单独跑时会在
    `sweep` 场景 10 / 20 / 26 / 41 / 52 命中（`r1 = 0x08538FEC`）；
    但和三个引擎断点（`0x0809B244` / `0x0809B284` / `0x0809B25E`）
    一起挂上时，**那几个命中就消失了** —— 因为引擎断点每首歌都命中，
    把按键按得更久，剧情在场景里走得更快/更慢。
  * 修法有两条：(a) 把“链接”捕获换成**该结构实际被播放的那条路径**
    （`story-c` 在战斗路线里是被 fn `0x0809AB38` 播放的，于是链接捕获也用
    fn `0x0809AB38` 的判定点 `0x0809AB54`，两条证据落在**同一条路线、同一次
    命中**上）；(b) 给每个组挑**尽量少**的断点。
  * 这条经验对仓库里的其它断点普查同样成立：**“没命中”必须是**在**与被判死
    的那条路线相同的断点集合**下**测出来的**，否则不能作为判死依据。
* **判定点的选法**（沿用前几批）：mGBA 的断点在目标指令**执行前**命中，
  所以判定点必须下在“基址、下标、字段值都已经在寄存器里”的那条指令上。

## 2. 本轮对旧结论的更正

1. **`battle-config` 的任务书基址 `0x545458` 与它给的六个读者对不上，
   但 `0x545458` 自己**确实有**原生读者。**
   任务书给的六个读者（`0x0806D6E6` / `0x0806D786` / `0x0806DB14` /
   `0x0806DC4C` / `0x0806DDD6` / `0x080932CA`）装载的是 **`0x085459C8`**
   （`character_perks`，逐角色特性表），**不是** `0x08545458`。
   但按任务书的提示去查 `LiteralIndex`，**`0x08545458` 有 8 个字面量读者**：

   ```
   0x0806D866  0x08078776  0x080922D0  0x08092324
   0x08093296  0x08093352  0x08094550  0x08094A36
   ```

   ⇒ 任务书那六个读者属于 `0x085459C8`（第三批已证明的 `levels`）；
   `0x08545458` 是**另一张表**，它有自己的消费者。本轮把它作为新结构
   `ninjutsu-records` 登记（`registry = skill_table`）。
   两张表是**相邻**的：

   ```
   0x08545458  skill_table       87 x 16 = 0x570 字节  ->  0x085459C8
   0x085459C8  character_perks   45 x 12 字节
   ```

   （`battle-config` 这个 key 本身保持第三批已经证明的 `battle_actors`
   `0x085461C4`，不动。）
2. **对象类型记录表的真基址是 `0x0853EF30`、步长 24。** 本轮独立地从
   消费者自己的数据流重新推导了一遍，结论与
   `notes/evidence/callback-dispatch-tables-20261021.md` §2.4 一致：
   `0x0853EF70` 起按 20 字节读是**错位读**（会跨过 24 字节记录边界）。
   本轮的推导（fn `0x0807FE2C`）：

   ```asm
   0807FE56  ldr  r4, [pc, #0x58]   ; r4 = 0x0853EF30
   0807FE58  ldr  r0, [sp]          ; r0 = 对象类型 id
   0807FE5A  lsls r3, r0, #1        ; r3 = id*2
   0807FE5C  adds r0, r3, r0        ; r0 = id*3
   0807FE5E  lsls r0, r0, #3        ; r0 = id*24   <- 步长 24
   0807FE60  adds r0, r0, r4        ; r0 = base + id*24
   0807FE62  ldr  r0, [r0]          ; r0 = 记录 +0
   ```

   边界交叉验证：`0x0853EF30 + 21*24 == 0x0853F140`，
   而 `0x0853F140` 正是 `object_descriptor_table`（`map-sprites`）的基址 ——
   两张表**首尾相接**。
3. **`fonts` 的消费者不是 fn `0x0807EE50`。** fn `0x0807EE50` 读的是
   **`0x0853E328`**（新发现的字形度量表，6 字节/字形，7 个读者）；
   `0x0853E596` 的消费者是 `0x0807F0FC` 起的代码。
   两条是**不同的表**。本轮的工具里 `fonts` 用的读者 `0x0807F0FC` 是对的。

## 3. 闭合的结构（逐个）

### 3.0 `story`（`0x08536368`）——❌ 未达到（链接拿到了，引擎没读）

**结构**：m4a SongHeader（sound id 1，8 轨）。

**原生读者 / 派发点**

| 段 | 指令 | 作用 |
|---|---|---|
| 链接 | `0x0809AB92`（fn `0x0809AB8C`，**停止**路径） | `ldr r0,[r0]` 取出 SongHeader 指针（`0x0809ABA6`） |
| 引擎 | `0x0809B242`（fn `0x0809B1F4`） | `ldr r0,[r7,#4]` 读序列/轨道指针 |

**运行时读数**：**链接侧命中了** —— `title` 路线里 sound id 1 被请求，
`0x0809ABA8` 处 `r0 = 0x08536368`（与 `audio_song_1` 的 registry 基址相等）。
**引擎侧一次都没命中**。

**为什么引擎侧到不了（精确阻塞点）**：能真正播放一首曲子的只有两条
“播放路径” fn `0x0809AAC0`（读者 `0x0809AAC6`）与 fn `0x0809AB38`
（读者 `0x0809AB3E`）。本轮在**全部 9 个声音 id 表读者**上挂断点，
跑 `title` + `sweep`（55 场景）后统计到：

| 读者 | 路径 | 运行时被请求的 sound id |
|---|---|---|
| `0x0809AAC6` | 播放 | 4, 5, **8**, 13, 102, 111, 143 |
| `0x0809AB3E` | 播放 | 2 |
| `0x0809AB92` | **停止** | **1** |

⇒ sound id 1 **只**从停止路径进来，所以 fn `0x0809B1F4` 从未拿到
`r1 = 0x08536368`，引擎自然不会读这个 header 的字段。

**门控条件**：需要一个会**播放** sound id 1 的场景（章节主题曲）。
三条现有路线（`title` / `battle` / `sweep` / `save`）都不播它。

**判死检验**：工具里 `story` 显式声明 `"l2": False` 并带上面的理由；
`--self-test` 不会把它算成通过。

### 3.1 `story-b`（`0x08536BC4`）——✅ L2

**结构**：m4a SongHeader（sound id 2，10 轨）。
字段：`+0x00` u8 轨数、`+0x04` u32 序列指针、`+0x08` 起每轨一个 u32 指针。

**原生读者 / 派发点**

| 段 | 指令 | 作用 |
|---|---|---|
| 链接 | `0x0809AB3E`（fn `0x0809AB38`，**播放**路径） | 从声音 id 表取出 SongHeader 指针 |
| 引擎 | `0x0809B242`（fn `0x0809B1F4`，m4a 播放入口） | `ldr r0,[r7,#4]` 读**序列/轨道指针** |

**运行时读数**（`sweep` 路线，场景 32..38 / 47 / 55 播这首）

```
0x0809B244  r7=0x08536BC4  r0=0x08464854  r1=0x00000000  r4=0x020311D4
```

**寄存器 ↔ 字段对应**

| 寄存器 | 字段 | ROM 交叉核对 |
|---|---|---|
| `r7` | SongHeader 基址 | `0x08536BC4`（= `audio_song_2` 的 registry 基址） |
| `r0` | `SongHeader[+4]` 序列指针 | `u32(0x08536BC8) = 0x08464854` ✅ |
| `r1`（`0x0809B25C` 判定点） | `SongHeader[+0]` 轨数 | `u8(0x08536BC4) = 10` ✅ |
| `r0`（`0x0809B284` 判定点） | `SongHeader[+8+轨*4]` 轨指针 | `u32(0x08536BCC+4*轨)` ✅ |

**判死检验**：改坏 `r7`（`corrupt: r7 = value + 4`）后
“the register holds this SongHeader's address” 立刻失败 ⇒ 门禁会咬人。

**试过什么**：`title` / `battle` / `sweep` / `save` 四条路线都挂了
`0x0809AB54` 与 `0x0809B244` 两个断点；`sweep` 路线命中。

### 3.2 `story-c`（`0x08538FEC`）——✅ L2

**结构**：m4a SongHeader（sound id 8，9 轨）。

| 段 | 指令 | 作用 |
|---|---|---|
| 链接 | `0x0809AB3E`（fn `0x0809AB38`，**播放**路径） | 从声音 id 表取出 SongHeader 指针（`0x0809AB52`） |
| 引擎 | `0x0809B242`（fn `0x0809B1F4`） | `ldr r0,[r7,#4]` 读序列/轨道指针 |

**运行时读数**：链接侧与引擎侧**在同一条路线（`battle`）的同一次播放里**
都命中了 —— 引擎侧那次命中的返回地址 `lr = 0x0809AB61` 正是
fn `0x0809AB38` 里 `bl #0x0809B1F4` 的下一条指令，说明这一首确实是
fn `0x0809AB38` 播放的（battle25 把 `0x08538FEC` 交给 m4a 播放入口）。

> 为什么链接侧不用 fn `0x0809AAC0`：那条路径（sound id 8 在 `sweep`
> 场景 10 / 20 / 26 / 41 / 52 被请求）**只在单独挂断点时**命中；和引擎
> 断点一起挂时会被“多挂断点改变按键时长”的副作用吃掉（见 §1 的方法学
> 陷阱）。换成 fn `0x0809AB38` 之后，两段证据落在同一条路线上。

**寄存器 ↔ 字段对应**：`r7` = `0x08538FEC`；`r0` = `u32(0x08538FF0)`；
`u8(0x08538FEC) = 9` = 轨数。

**判死检验**：同 §3.1（改坏 `r7`）。

### 3.3 `story-d`（`0x0853AB74`）——✅ L2

**结构**：m4a SongHeader（sound id 11，10 轨）。
**引擎判定点**：`0x0809B284`（fn `0x0809B1F4` 的**每轨指针**那条）：

```asm
0809B27A  lsls r1, r6, #2       ; r1 = 轨序号 * 4
0809B27C  adds r0, r7, #0
0809B27E  adds r0, #8           ; r0 = SongHeader + 8
0809B280  adds r0, r0, r1
0809B282  ldr  r0, [r0]         ; r0 = 该轨的 u32 指针
0809B284  str  r0, [r4, #0x40]
```

**运行时读数**：`battle` 路线命中（battle5 / battle28 把 `0x0853AB74`
交给 m4a 播放入口）。

**寄存器 ↔ 字段对应**：`r7` = `0x0853AB74`；`r1` = 轨序号 × 4；
`r0` = `u32(0x0853AB74 + 8 + r1)`。

**判死检验**：改坏 `r7` ⇒ 失败。

### 3.5 `mission-text`（`0x08348DAC`）——✅ L2（从 L1 升上来）

**原生读者**：`0x080884F8`（fn `0x080884E0`）。这是任务书列出的六个读者里
**第三个分支之外**的一个 —— 第三批只试了三个，全都在没被走到的分支里；
本轮把六个读者全挂上断点，**它被走到了**。

```asm
080884F8  ldr   r2, [pc, #0x6c]  ; r2 = 0x08348DAC (mission index)
080884FA  ldr   r1, [pc, #0x70]  ; r1 = 0x020311D4 (story state)
080884FC  ldrb  r0, [r1, #0x16] ; r0 = state[0x16] (场景号)
080884FE  adds  r0, r0, r2      ; r0 = base + 场景号
08088500  ldrb  r4, [r0]        ; r4 = 索引字节
08088502  ldrb  r1, [r1, #0x19] ; r1 = state[0x19]
```

**判定点**：`0x08088502`（`ldrb` 之后，索引字节已在 `r4` 里）。

**运行时读数**：`sweep` 路线命中 1 次。

**寄存器 ↔ 字段对应**

| 检查 | 内容 |
|---|---|
| `r2` | 任务索引表基址 `0x08348DAC` |
| `r0` | `base + 场景号`（场景号取自 WRAM `0x020311EA`，与 `r0 - base` 相等） |
| `r4` | 该下标处的 u8，与 ROM 字节相等 |

**判死检验**：改坏 `r2`（`corrupt: r2 = base + 4`）⇒ “a register holds the
mission index table's base” 失败。

**试过什么**：六个读者（`0x080731DA` / `0x0808675C` / `0x080874FE` /
`0x080884F8` / `0x080893E4` / `0x08089E90`）全部挂上断点，跑
`title` / `battle` / `sweep` / `save`；只有 `0x080884F8` 被命中。

### 3.6 `tile-assets`（`0x085A320C`）——✅ L2（从 L1 升上来）

**原生读者**：`0x0809845C`（fn `0x080983B8`）。第三批只试了 `0x0809881E`，
它藏在对象派发后面；本轮换成九个读者里的另一个。

```asm
08098448  ldr   r2, [pc, #0xcc]  ; r2 = 0x0203120C (the index slot)
0809844C  strb  r1, [r2]        ; 消费者把记录序号存进这里
08098456  lsls  r0, r1, #4
08098458  adds  r0, r0, r1      ; r0 = 序号 * 17
0809845A  lsls  r0, r0, #2      ; r0 = 序号 * 68
0809845C  ldr   r1, [pc, #0xbc] ; r1 = 0x085A320C (tile assets)
0809845E  adds  r0, r0, r1      ; r0 = base + 序号*68
08098460  mov   r8, r0          ; r8 = 记录
08098462  strb  r4, [r2, #2]
```

**判定点**：`0x08098462`（**不是** `0x08098460`）。

> 判定点为什么必须再往后挪一条：mGBA 的断点在目标指令**执行前**命中。
> 下在 `0x08098460` 时 `mov r8, r0` 还没执行，`r8` 还是旧值；下在
> `0x08098462` 时 `r0` 与 `r8` 才都等于 `base + 序号*68`。
> 同时，在 `0x08098462` 处**缩放过的序号已经被折进地址**（`r0` 变成
> `base + 序号*68`），所以序号要**从地址反推**
> （`序号 = (r0 - base) / 68`），再拿消费者自己写进 WRAM `0x0203120C`
> 的那个字节做独立交叉核对。

**运行时读数**：`sweep` 路线命中，`r1 = 0x085A320C`（表基址）、
`r8 = r0 = 0x085A40EC`（= `base + 56*68`，即序号 56）。

**寄存器 ↔ 字段对应**

| 检查 | 内容 |
|---|---|
| `r1` | 表基址 `0x085A320C` |
| `r0` / `r8` | `base + 序号*68`，且 `(r8 - base) % 68 == 0`、`序号 < 79` |
| WRAM `0x0203120C` | 消费者写入的序号字节，与反推出来的序号相等 |
| 记录 `+0x0C` | 六个 u32 全部是 0 或 ROM 地址 |

**判死检验**：改坏 `r1`（`corrupt: r1 = base + 4`）⇒ “a register holds the
tile asset table's base” 失败。

**试过什么**：`battle` 与 `sweep` 两条路线；九个读者里的 `0x0809845C`
被命中（第三批试的 `0x0809881E` 仍然够不到）。
`r0=0x5D8`（= 22 × 68）、`r8 = 0x085A320C + 22*68`。

**寄存器 ↔ 字段对应**：`r1` = 表基址；`r0` / `r8` = `base + 序号*68`；
记录 `+0x0C` 起六个 u32 全部是 0 或 ROM 地址。

**判死检验**：改坏 `r1`（`corrupt: r1 = base + 4`）⇒ 失败。

### 3.7 `ninjutsu-records`（`0x08545458`）——❌ 未达到（读者存在但够不到）

**结构**：忍术记录表，16 字节/条，87 条（下标 = 忍术 id）。

**原生读者**（`LiteralIndex` 重新索引得到，**8 个**）：

```
0x0806D866  0x08078776  0x080922D0  0x08092324
0x08093296  0x08093352  0x08094550  0x08094A36
```

本轮选用的判定点（两个形态不同，所以有两个 derive 参数组）：

```asm
; fn 0x08078770, reader 0x08078776, decision 0x0807877E
08078776  ldr  r1, [pc, #0xb0]  ; r1 = 0x08545458
08078778  lsls r0, r5, #4       ; r0 = id * 16
0807877A  adds r0, r0, r1       ; r0 = base + id*16
0807877C  ldrh r0, [r0, #2]     ; r0 = 记录的 +2 u16
0807877E  movs r1, #0xc0

; fn 0x0806D860, reader 0x0806D866, decision 0x0806D874
0806D866  ldr  r2, [pc, #0x20]  ; r2 = 0x08545458
0806D868  lsrs r0, r0, #0x14    ; r0 = id * 16
0806D86C  adds r0, r0, r2       ; r0 = base + id*16
0806D86E  ldm  r0!, {r2, r6, r7}; 记录的 +0/+4/+8 -> r2/r6/r7
0806D870  stm  r1!, {r2, r6, r7}; ... -> 运行时结构
0806D872  ldr  r0, [r0]         ; r0 = 记录的 +12 u32
0806D874  str  r0, [r1]
```

**判死检验**：改坏字段寄存器 ⇒ “the register holds the u16/u32 the record
stores at +N” 失败。

**试过什么**：`battle` / `sweep` / `title` 三条路线，
两个读者同时挂断点 —— **两个读者都没被命中**。

**阻塞点（精确）**：读者 `0x08078776` 所在的 fn `0x08078770` 与读者
`0x0806D866` 所在的 fn `0x0806D860` 都在**忍术 / 角色模块**里。
这三条路线只经由**角色模板加载器**（fn `0x0806D964`）进这个模块 ——
**忍术列表本身从来没被打开**。所以这张表有原生读者，但读者所在的代码
在现有路线下不可达。

**门控条件**：需要一个会**打开忍术列表**的界面 / 事件（技能选择、
升级、商店之类）。剧情、战斗、存档三种模式都进不去。

**静态判死检验（仍然成立）**：`LiteralIndex` 给出 8 个读者 ⇒ 这张表**不是**
“没有原生消费者的死表”；它的死因是**运行时不可达**，不是静态无读者。
工具里它被显式声明为 `"l2": False`，并附上上面这段理由。

### 3.8 `mechanism-effects`（`0x0808136C`）——❌ 未达到

**结构**：13 项代码指针表，**在代码区**（`tools/table_registry.py` 的
`mechanism_effect_table`）。

**原生读者**：`0x08081350`（fn `0x080812DC`，13 路效果派发器）：

```asm
08081346  subs  r0, r5, #1        ; r0 = 目标号 - 1
08081348  cmp   r0, #0xc
0808134A  bls   #0x808134e
0808134C  b     #0x80814cc        ; 越界 -> 默认效果
0808134E  lsls  r0, r0, #2        ; r0 = (目标号-1)*4
08081350  ldr   r1, [pc, #0x14]   ; r1 = 0x0808136C (效果表)
08081352  adds  r0, r0, r1        ; r0 = base + (目标号-1)*4
08081354  ldr   r0, [r0]          ; r0 = 效果的代码指针
08081356  mov   pc, r0            ; 派发
```

**判定点**：`0x08081356`。

**阻塞点（精确）**：fn `0x080812DC` 只在**地图上的机关触发机制**时运行，
也就是“关卡 / 过场模式”。这正是回调普查（§4.1）判定三条现有路线
（剧情 / 战斗 / 存档）都进不去的那种模式。

**门控条件**：一条会加载带机关的地图的路线。

**静态判死检验**：读者存在（`LiteralIndex` 给出 `0x08081350`），
基址落在 ROM 内，表范围 `0x0808136C + 13*4 = 0x080813A0` 也在 ROM 内。
工具里显式声明 `"l2": False` 并附上理由。

### 4.3 一个可能的突破口（留给下一轮）

`0x02027350` 这个 u8 **同时**索引 `0x0853E596`（字宽，1 字节粒度）和
`0x0853E698`（处理程序，8 字节粒度）。它没有字面量引用，只能通过
`0x02026BE0 + 0x770` 的相对寻址找到它的**写入点**。
一旦能控制这个字节，就能让游戏自己派发到表里**任意**一条记录
（包括 195..200 的字宽/字形路径），那就会同时解开
`fonts` / `battle-handlers` / `map-events` 三张表。
