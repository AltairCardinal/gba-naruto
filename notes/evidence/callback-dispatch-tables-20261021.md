# 回调表派发：把「不可达的消费者」变成可定位的指令

日期：2026-10-21
范围：`rom/base.gba`（`0x08000000` 基址）
方法：全 ROM 32 位字面量扫描 → capstone 反汇编 → 指令级派发点定位。

> ## ⚠️ 本文的「派发点 0 命中」结论已被推翻（2026-10-21 当晚）
>
> 本文 §5 与 `docs/re-completion-criteria.md` §5.2 曾写下：
> 「断点普查在 battle / save / sweep 三条路线上哨兵命中、派发点 **0 命中**，
> 所以缺的不是『按某个键』，而是**一条会执行到该派发点的路线**（关卡/过场模式）」。
>
> **作废。** 正确的结论见
> **`notes/evidence/callback-dispatch-runtime-20261021.md`**：
>
> * 派发点**在剧情战斗里就可达**（`fn 0x0806DF88` → `0x0806DE18` →
>   `0x0807AB34` → `0x0807AA8C` → `fn 0x0807F414` → `0x0853E698`）；
> * 那次「0 命中」是**工装 bug**：`frames 120 0x000`（松手）只在「本轮没命中
>   任何断点」时才执行，而哨兵断点每次都命中 ⇒ 键一直按着 ⇒ 游戏收不到按下沿 ⇒
>   战斗过场不推进 ⇒ 单位永远不建 ⇒ 门控条件永远不成立；
> * 门控 `fn 0x0806DF88` 还有一个**结构性死因**：
>   `unit[0xC0] & 1` 与 `ctrl[10]` 原值比较，而战斗中 `ctrl[10]` 是
>   `0x0E`/`0x0F` 交替 ⇒ 永不相等；
> * 本文的**指令级定位本身全部成立**（表基址、步长、派发点都对），
>   被推翻的只是「这些派发点不可达」这一句。
>
> **2026-10-22 追加**：本文把 `0x0853E6C4` 说成「关卡对象行为处理函数表」，
> 这一条**也作废** —— 全 ROM 字面量扫描显示 `0x0853E6C4` **没有任何字面量读者**，
> 它自己是被别的指针表间接引用的；真正的按类型分派是 `fn 0x0806F210` 里的
> Thumb-2 switch 跳转表 `0x0806F4EC`，而 `fn 0x0806F210` 是**战斗单位生成**函数。
> 更正与当前状态见
> **`notes/evidence/open-structures-status-20261022.md`**。

## 0. 为什么要做这件事

L2 第四批（21 个结构）卡在同一个根因上：这些结构的原生读者
**只经由 ROM 里的回调表被调用**，而此前跑过的所有路线（开机 / 剧情 / 战斗 /
存档 / 55 场景扫描）**从来没有让这些表被派发过**。
本轮换了个角度：**不再找「什么路线会走到读者」，而是先把「表被谁读、怎么读」
在指令级钉死**，再看派发点需要什么前置状态。

## 1. 尝试过什么 / 怎么做的

1. `build/probe_cbread.py`：在 ROM 里搜 `0x0853ECB0` / `0x0853EF70` 的 32 位
   字面量 —— **0 命中**。说明基址不是字面量，而是算出来的。
2. `build/probe_litrange.py`：扫出 ROM 里**所有**指向
   `0x0853E000..0x0853F400` 的字面量（19 个不同值），把「表在哪被引用」
   和「表在哪被读」分开。
3. `build/probe_cbptrs.py`：反查回调函数地址本身在 ROM 里的落点 ——
   函数指针**只出现在数据区**，唯一的例外是
   `0x080808BC` 在 `0x080801FC`、`0x080808C4` 在 `0x08080200`
   （字面量池），说明**分派代码就在 `0x0807FExx..0x080802xx` 这一段**。
4. `build/probe_dis.py`：带 PC 相对字面量解析的 Thumb 反汇编器。
5. `build/probe_cbtables.py` / `build/probe_objtype2.py`：按候选步长 dump 表，
   用「表后紧跟已知表」作为边界交叉验证。

## 2. 学到了什么

### 2.1 `0x0853E698`（256 × 8 字节）——「battle-handlers」的真实派发点

```
0x0807FD28: ldr  r1, [pc, #0x5c]   ; r1 = 0x0853E698   <- 表基址
0x0807FD2A: movs r0, #0xee
0x0807FD2C: lsls r0, r0, #3        ; r0 = 0x770
0x0807FD2E: add  r0, sb            ; sb = 0x02026BE0
0x0807FD30: ldrb r0, [r0]          ; r0 = *(0x02027350)   <- 索引字节
0x0807FD32: lsls r0, r0, #3        ; 索引 * 8
0x0807FD34: adds r0, r0, r1        ; 表基址 + 索引*8
0x0807FD36: ldr  r1, [r0]          ; r1 = 处理程序指针
0x0807FD38: mov  r0, sb
0x0807FD3A: bl   #0x809C114        ; 间接调用
```

**索引字节 = `0x02027350`（= `0x02026BE0 + 0x770`）**。
表内 256 条记录的去重形态（`(word0, word1)`）：

| 5..86 | `0x0807E86C` | `0x0807F064` |
| 7..73 | `0x0807E1C8` | 0 |
| 8..79 | `0x0807EFFC` | `0x0807F064` |
| 9..38 | `0x0807EFFC` | `0x0807F148` |
| 19..77 | `0x0807F038` | `0x0807F064` |
| 22 | `0x0807EFFC` | `0x0807E8A8` |
| 23..80 | `0x0807EFFC` | `0x0807F17C` |
| 28..103 | `0x0807F038` | `0x0807F148` |
| 33 | `0x0807E340` | 0 |
| 54 | `0x0807E4C4` | 0 |
| 62 | `0x0807EFFC` | `0x0807EA00` |
| 129..179 | `0x0807EA7C` | `0x0807F064` |
| 142..144 | `0x0807EAF8` | `0x0807F064` |
| 156..158 | `0x0807EBA0` | `0x0807F064` |

> 存的是偶地址 `0x0807EE50` 等。

### 2.2 `0x0853E596`（256 × 1 字节，字宽表）——消费者钉死在 `0x0807F0FC`

```
0x0807F0FC: ldr  r1, [pc, #0x14]   ; r1 = 0x0853E596   <- 字宽表基址
0x0807F0FE: movs r2, #0xee
0x0807F100: lsls r2, r2, #3        ; r2 = 0x770
0x0807F102: adds r0, r4, r2        ; r0 = r4 + 0x770
0x0807F104: ldrb r0, [r0]          ; r0 = 字符码
0x0807F106: adds r0, r0, r1        ; r0 = 表基址 + 字符码
0x0807F108: ldrb r1, [r0]          ; r1 = 字宽
0x0807F10A: movs r0, #1
0x0807F10C: bl   #0x807C5E8
```

**和 2.1 用的是同一个索引字节 `0x02027350`**（`r4` 与 `sb` 都是 `0x02026BE0`）。
所以这张表是「**按同一个字节索引的两张表**」：1 字节粒度（字宽）、
8 字节粒度（处理程序）。

### 2.3 `0x0853E328` ——**新发现的字形度量表**（6 字节 / 字形）

```
0x0807EE98: ldr  r5, [pc, #0xe0]   ; r5 = 0x0853E328
0x0807EE9A: ldrb r1, [r3, #2]
0x0807EE9C: lsls r1, r1, #1
0x0807EE9E: ldrb r0, [r3, #4]
0x0807EEA0: lsls r0, r0, #2
0x0807EEA2: adds r4, r1, r0        ; r4 = [r3+2]*2 + [r3+4]*4
0x0807EEA4: adds r1, r4, r5
0x0807EEA8: ldrb r1, [r1]          ; +0: 宽度
0x0807EEBA: adds r0, r5, #1
0x0807EEBC: adds r0, r4, r0
0x0807EEBE: ldrb r0, [r0]          ; +1: 另一侧偏移
```

- 记录步长 **6 字节**，基址 `0x0853E328`；
- 数据形态是像素宽（`0x12`=18 … `0x1C`=28，全角字 24 px = `0x18`）；
- 全 ROM 有 **7 个字面量读者**：`0x0807EAF4` / `0x0807EB9C` / `0x0807EC44` /
  `0x0807ED1C` / `0x0807EE4C` / `0x0807EF7C` / `0x0807EFF8`。

> **旧结论更正**：旧笔记说「`fonts` 的消费者是 fn `0x0807EE50`」——**不对**。
> fn `0x0807EE50` 读的是 `0x0853E328`；`0x0853E596` 的消费者是
> `0x0807F0FC` 起的代码。这两条是**不同的表**。

### 2.4 `0x0853EF30` ——**对象类型记录表：步长是 24，不是 20**

fn `0x0807FE2C`（**67 个 `bl` 调用点**）的读法：

```
0x0807FE56: ldr  r4, [pc, #0x58]   ; r4 = 0x0853EF30   <- 记录表基址
0x0807FE58: ldr  r0, [sp]         ; r0 = 类型 id
0x0807FE5A: lsls r3, r0, #1
0x0807FE5C: adds r0, r3, r0       ; id*3
0x0807FE5E: lsls r0, r0, #3       ; id*24   <- 步长 24
0x0807FE60: adds r0, r0, r4
0x0807FE62: ldr  r0, [r0]         ; 记录的 +0
0x0807FE66: cmp  r0, #0
0x0807FE68: bne  #0x807FE6C
0x0807FE6A: b    #0x8080058       ; id 非法 -> 失败返回
...
0x0807FE7A: ldr  r0, [r0]         ; 记录 +0x04 + counter*4
0x0807FE7C: lsls r0, r0, #3
0x0807FE7E: ldr  r1, [pc, #0x34]  ; r1 = 0x0859911C
0x0807FE80: adds r7, r0, r1       ; 0x0859911C + 索引*8
```

记录布局（6 个 u32 = 24 字节）：

| 偏移 | 含义 |
|---|---|
| +0x00 | u32 表索引（0 = 该 id 不可用；否则索引进 `0x0859911C`） |
| +0x04 | u32 备用槽 0 |
| +0x08 | u32 备用槽 1 |
| +0x0C | u32 备用槽 2 |
| +0x10 | u32 **初始化函数** |
| +0x14 | u32 **更新函数** |

21 条记录（id `0x01`..`0x15`），`+0x00` 依次是
`1,2,3,4,1,5,0x12,6,7,8,9,0x0A,0x0B,0x0C,0x0D,0x0E,0x0F,0x12,0x10,0x11,0x02`。

**边界交叉验证**：这 21 条记录正好占
`0x0853EF30 .. 0x0853F140`，而 `0x0853F140` 正是已裁决的
`object_descriptor_table`（43 × 8）——两张表**首尾相接**，
步长 24 得到独立确认。

> **旧结论更正**：旧笔记说「`0x0853EF70` 起是 20 字节对象类型记录（id 3）」——
> 这是**错位读**：20 字节窗口从 `0x0853EF70` 起会跨过 24 字节记录边界，
> 于是「init / update / id」看起来刚好对齐。真实基址是 `0x0853EF30`，步长 24。

### 2.6 `0x0853EE98` / `0x0853F140` / `0x0853F298` 的读者位置

- `0x0853EE98`（sprite-frame-descriptors）：字面量池条目在
  `0x08080744` / `0x080807F0` / `0x08080898`，
  引用它的 `ldr` 落在 fn `0x08080670`（对象类型 id 3 的更新函数）内部，
  决策点 `0x080806BC` —— 与既有探针一致。
- `0x0853F140`（object_descriptor_table）：`0x08080B54`，
  `0x0853F298`（units 重映射）：`0x08080B5C`，
  两者同在 fn `0x08080B08`；该函数被 fn `0x08080BA0` 在
  `0x08080BD2` / `0x08080C10` 调用。

## 4. 可判死的检验

- **表边界**：`0x0853EF30 + 21×24 == 0x0853F140`（下一张已知表的基址）。
  步长若错（如 20 或 28），这个等式不成立。
- **派发点**：`0x0853EF30` / `0x0859911C` / `0x0853E328` 在 ROM 里
  **零字面量读者**；只有把 `0x0807FE56` / `0x0807FE7E` / `0x0807EE98`
  的 `ldr` 逐条解出来，基址才唯一确定。
- **旧结论的证伪**：`0x0807EE50` 的字面量池在 `0x0807EF78` 起，
  里面**没有** `0x0853E596`；`0x0853E596` 全 ROM 只出现 1 次
  （`0x0807F114`），因此「fn `0x0807EE50` 是 fonts 消费者」不可能成立。

## 5. 还没闭合的

- 三个字面量读者（`0x0853E328` / `0x0853EF30` / `0x0859911C`）对应的
  **运行时读数**还没取到：需要一条会执行到 `0x0807F108` /
  `0x080806BC` / `0x08080B3C` 的路线。
- `0x02027350` 的**写入点**还没定位（它没有字面量引用，
  只能通过 `0x02026BE0 + 0x770` 的相对寻址找到）。
  一旦能控制这个字节，就能让游戏自己派发到表里**任意**一条记录
  （包括 195..200 的字体/字形路径）—— 这就是打通 L2 第四批的最短路径。

## 6. 调用链：把「表」接到「游戏流程」上

### 6.1 派发函数

| 表 | 派发点 | 索引来源 |
|---|---|---|
| `0x0853E698`（256×8） | `0x0807FD28`（`ldr r1,[pc]` → `ldrb` → `*8` → `ldr` → `bl 0x0809C114`） | u8 @ `0x02027350` |
| `0x0853E596`（256×1） | `0x0807F0FC`（`ldr r1,[pc]` → `ldrb` → 相加 → `ldrb`） | 同一个 u8 @ `0x02027350` |
| `0x0853E328`（6B/字形） | `0x0807EE98`（`ldr r5,[pc]` → `[r3+2]*2 + [r3+4]*4`） | 字形描述符 |
| `0x0853EF30`（24B/记录） | `0x0807FE56`（`ldr r4,[pc]` → `id*24`） | 参数 id |
| `0x0859911C`（8B/条） | `0x0807FE7E`（`ldr r1,[pc]` → `值*8`） | 记录 +0x00 |
| `0x0853F140`（8B/条） | `0x08080B12`（`ldr r5,[pc]`） | fn `0x08080B08` 的参数 |
| `0x0853F298`（2B/条） | `0x08080B2C`（`ldr r1,[pc]` → `id*2`） | 同上 |
| `0x0853F310`（4B/条） | `0x08080E44`（`ldr r1,[pc]` → `命令号*4`） | 命令字**最高字节** |

`0x0853F310` 是一张 **13 项**（id 1..13，id 0 为 0）的**实体生成跳表**，
每一项是一个 thunk，thunk 调 `fn 0x08080BA0`（生成）或 `fn 0x08080B08`
（读 `0x0853F140` / `0x0853F298`）。

`fn 0x08080E30` 是生成入口：命令字 `r0` 的最高字节就是实体类型号，
`0x0853F310 + 类型号*4` 取 thunk。它有 11 个调用点
（`0x0806CD3E`…`0x0806D104`、`0x080725DC`、`0x080726D6`）。

### 6.2 战斗包装里的门控

```
0x080736DC: ldrb r0, [r4, #2]      ; r4 = 0x0202680C -> ctrl[10]（0/1 交替）
0x080736DE: bl   #0x0806DF88       ; 遍历 12 个战斗单元槽
```
`fn 0x0806DF88` 对每个非空槽的三个条件才调 `fn 0x0806DE18`：

| 条件 | 位置 | 含义 |
|---|---|---|
| `unit[0xC0] & 1 == ctrl[10]` | `0x0806DFC0` | 阵营（敌/我） |
| `fn 0x0806DDA4(unit,0x1D,…) != 0xFF` | `0x0806DFD4` | 外观解析成功 |
| `unit[0xBE] == 0` | `0x0806DFE0` | 未被占用 |
| **`unit[0x0C] <= 9`** | **`0x0806DFE6`** | **槽内编号必须 <= 9** |

`fn 0x0806DE18` → `0x0807AB34` → `fn 0x0807AA8C` → `fn 0x0807F414`
（`0x0807ABD4`）→ **处理程序表**。

`fn 0x0806DF88` 的唯一调用点是 `0x080736DE`，位于战斗包装
`fn 0x080732B4` 内（`fn 0x080732B4` 的调用点：`0x08068DEC`、
`0x08087328`、`0x0808F952`）。

**实测**（`tools/mgba_probe/unitslot_probe.py`）：在 `0x080736DC` 命中的
那一刻，**12 个单元槽全是空的** —— 战斗单位是在这之后才被创建的，
所以 `fn 0x0806DF88` 在战斗里遍历不到任何单元，这条路径在战斗里
实际是**死代码**。

## 7. 实测：三条现有路线都够不到回调派发

`tools/mgba_probe/callback_census.py` 一次性在**所有已知派发点与消费者**
上挂断点，然后跑现有路线。哨兵点（`0x080732B4` 战斗包装、
`0x0806D98C` 角色属性读数、`0x08069040` 地图载入读数）都会命中，
所以「没命中」是**真结论**，不是工装坏了。

| 路线 | 哨兵命中 | 回调派发点命中 |
|---|---|---|
| `battle`（group 0..3） | `0x080732B4`×4、`0x0806D98C`×16、`0x08069040`×4 | **0** |
| `battle`（group 0..5，40 次按键） | 见上 | **0** |
| `save`（相位 `0x0018`） | `0x0806D98C`×1 | **0** |
| `sweep`（场景 1..55） | 无（剧情场景不进战斗） | **0** |

被证明「连函数入口都没进」的地址：
`0x0807EE50`、`0x0807F064`（字宽消费者所在函数）、
`0x0807F414`、`0x0807AA8C`、`0x0807AB34`、`0x0806DF1E`、
`0x08080B08`、`0x08080BA0`、`0x08080E30`、`0x080806BC`、
`0x0807FE2C`。

> **方法学警告（第四批实测出来的坑，必须一起记）**：
> `frames N<key>` 在**断点命中时会提前返回，而且不会释放按键** ——
> 所以**多挂一个断点就会改变剧情节奏**，可能让本来会命中的点**静默地不命中**。
> 第四批就踩过这个坑：多挂断点后 `tile-assets` 的命中从 1 次掉到 0 次，
> 加上判定点选早了一条指令，症状是「读者明明在，工具却说没到」。
> ⇒ 普查里「哨兵命中、派发点 0 命中」这个结论要这样读：
> **它证明的是「在这条路线 + 这组断点下不会发生」，不是「在任何断点配置下都不会发生」。**
> 但它仍然足以否定「多按几次键就能走到」这个假设 ——
> 因为第四批**用不同的断点组合**（只挂该结构自己的读者）也独立得到同样结论。

`0x0859911C` / `0x0853F140` / `0x0853F298` 这 7 张表只能被
**游戏里另一个模式**（关卡/过场模式，见
`notes/evidence/runtime-closures-20261021.md` 的 D 项）读到；
剧情、战斗、存档三种模式都进不去。

### 7.1 回调簇的**完整门控链**（2026-10-21 晚定位）

这批表**不是**「没有消费者」，而是**消费者都在同一条事件链的末端**。
链条如下（全部是原生代码，括号里是判定点）：

```
fn 0x080732B4  战斗/事件总控（**7.5 KB 的巨型函数**，整个事件 switch 都在里面）
  └─ 0x08073702  bl fn 0x0808A534          <- **剧情 VM 入口**
  │     └─ 0x0808A56C  ldrb r0,[r0,#0x1B]   <- 读 state[0x1B] = 0x020311EF

                    （0 ⇒ 战斗结束）。所以这段会**自旋**，直到该字节为 0。

                ├─ case 0x4080  -> 0x08074190
                │      0x08074192  bl fn 0x08070DF8   <- **items/skills 读者**
                │      0x080741A8  r6 = 0x6000 ; bl fn 0x0807504E

                       0x080743DC  ctrl[0xCC] -> 单元槽号
```

**同一 switch 里还挂着 items/skills 的另外两个读者**：
`0x0807425A` / `0x0807434E` → `fn 0x080851F8` → 读 `0x08545BE4`。

**关键**：选到 case 0x4080（也就是「读 items 表 + 派发 0x6000 → 生成」那条）
还要满足 **byte @ `0x0200A880` == 1**（`0x08073AC0`..`0x08073AC8`），
且 `r3 >> 18 ∈ {4,6}`（`0x08073AB8`）。

### 7.1b 状态机有**两条**进 `fn 0x080732B4` 的分支

| 分支 | 入口 | 守卫 | 设置 |
|---|---|---|---|
| **任务事件** | `0x0808F640` → `fn 0x08068DE4` | **`fn 0x08088F10` != 0** | `0x03000075 = 1`（模式标志）、`ctrl[0]=0`、`ctrl[1]=场景`、`ctrl[2]=子配置` |
| **战斗** | `0x0808F952` | 相位 == `0x0110` | `ctrl[0]=0`、`ctrl[1]=组`、`ctrl[2]=子` |

**⇒ 回调簇在「任务事件」分支上**（战斗分支进不去，因为 case 0x1210 会自我重派发）。

**⇒ 路线 = 让 `fn 0x08088F10` 返回非 0。**
`fn 0x08088F10` 是一个按 `r4`（0..0x10，共 16 项）分派的任务/事件处理函数，
读 `state 0x020311D4`。它的返回值来自 `r7`（**初值 1**）：

| 位置 | 行为 |
|---|---|
| `0x08088F1E` | `r7 = 1`（默认返回 1 ⇒ 走**事件分支**） |
| `0x08088F98`..`0x08088FB2` | r4=1 的 case：`bl fn 0x080884DC(r6)`；**若返回 −1** ⇒ `r7 = 0` ⇒ 返回 0 ⇒ **跳过**事件分支 |
| `0x08088FE2` | 另一处 `r7 = 0` |

**⇒ 路线 = 让 `fn 0x080884DC(0)` 不返回 −1，即「有一个已激活的任务」。**

而 `fn 0x080884DC` 读的就是**任务索引表**：

```
0x080884F8: ldr  r2, [pc, #0x6c]  ; r2 = 0x08348DAC   <- 任务索引表（每场景 3 条 u8）
0x080884FA: ldr  r1, [pc, #0x70]  ; r1 = 0x020311D4   <- 剧情状态
0x080884FC: ldrb r0, [r1, #0x16]  ; r0 = state[0x16]  （场景号）
0x080884FE: adds r0, r0, r2
0x08088500: ldrb r4, [r0]        ; r4 = 任务索引[场景]
0x08088502: ldrb r1, [r1, #0x19]  ; r1 = state[0x19]  （第几条任务）
0x08088504: ldr  r0, [pc, #0x68]  ; r0 = 0x0859AA5C   <- 任务标题表
0x08088506: adds r4, r4, r1      ; 任务号 = 索引 + state[0x19]
0x08088508: lsls r4, r4, #2
0x0808850A: adds r0, r4, r0
0x0808850C: ldr  r0, [r0]        ; 任务标题指针
```

任务索引表 `0x08348DAC`：**56 个场景 × 3 条 u8**，**每个场景都有合法索引**
（没有 0xFF），例如场景 1 = `{6, 9, 12}`、场景 39 = `{237, 129, 72}`。
配套表：任务标题 `0x0859AA5C`、任务说明 `0x0859D214`、任务提示 `0x0859E920`
（每条 4 字节指针）。

**⇒ 缺的不是「哪个场景有任务」，而是「任务怎么变成**已激活**状态」** ——
`fn 0x080884DC` 在扫描到**已激活**的任务之前一直返回 −1。
这是下一轮要查的**唯一**问题：`fn 0x080884DC` 里哪一步把 r6 置成 0x10
（`0x0808854E: movs r6, #0x10`，命中即代表找到了一条任务）。

**实测**：55 场剧情 × 10 按键（**小断点集**，避免断点扰动节奏）——
`fn 0x080732B4` **一次都没进** ⇒ 这些场景里任务始终没被激活。

### 7.1c 章节流程的触发条件（最终收敛）

`fn 0x0808F650`（= 「跑一场场景」）的循环体里藏着章节分发的判据：

```
0x0808F664: cmp  r1, #1
0x0808F666: bne  #0x0808F66E
0x0808F668: bl   #0x0808F618      ; **章节初始化**
0x0808F66E: movs r0, #0
0x0808F670: strb r0, [r5, #0x18]  ; state[0x18] = 0
0x0808F676: bl   #0x0808F544      ; 剧情分发器
0x0808F67A: ldrb r0, [r5, #0x16]  ; state[0x16] = 场景号
0x0808F67E: ldrb r1, [r5, #0x18]  ; state[0x18] = 分支标记
0x0808F680: cmp  r1, #0
0x0808F682: bne  #0x0808F664      ; 分支标记非 0 -> 继续循环
```

⇒ **`state[0x18]`（story_branch）**：

| 值 | 含义 |
|---|---|
| **3** | 「下一场」标记 —— L4 场景图用的就是它（写 3 之后调度器换场） |
| **1** | **「进章节」标记** ⇒ `0x0808F618` ⇒ `fn 0x08068DE4`（置 `0x03000075=1`）⇒ `fn 0x080732B4` ⇒ **事件链** |
| 其它 | 清零后继续 |

⇒ **回调簇住在「章节 / 关卡」流程里**，而章节流程由 `state[0x18] == 1` 触发。
L4 笔记早就记下「`story_branch` 在**场景 31** 读出 **1**」——**场景 31 就是章节场景**。

### 7.1d 为什么现有路线都进不去

* `fn 0x0808F650`（跑场景 / 章节分发的宿主）**没有任何 `bl` 调用者**、
  **没有数据指针**、**没有分支指向它** ⇒ 它只能被**剧情 VM 的 opcode
  间接调用**（寄存器分支）。
* L4 的 sweep 路线是**直接 poke 场景字节 + 相位 `0x0030`**，
  绕过了 `fn 0x0808F650` ⇒ 章节初始化（`0x0808F618`）**永远不会被调用**。
  实测：55 场 × 40 按键（小断点集），`fn 0x080732B4` **0 命中**，
  `fn 0x08088F10` **6 命中但全部返回 0**（没有已激活的任务）。
* 强制战斗路线（相位 `0x0110`）走的是**战斗分支**（`0x0808F952`），
  它把 `ctrl[0] = 0`，于是事件 case `0x1210` 只会**自我重派发**（实测 31 次），
  **结构上就到不了** 0x4080/0x6000 那条链。

**⇒ 真正的路线 = 让游戏自己把 `state[0x18]` 写成 1**，
也就是**一个真正带章节（关卡）的剧情场景**，并且这一场要**不 poke 场景号**地播。
这与 L4 笔记里那句「从 1 连打到 55 的完整通关录像属于玩法脚本」是同一件事：
**这批回调表只在连续通关（章节模式）里才会被派发。**

### 7.1e 剧情 VM 的「章节交接」opcode（**新发现，2026-10-21 深夜**）

VM 的 opcode 分派是**跳转表**：`0x080977F4` 起 58 项 × 4 字节，
`0x080977E8: mov pc, r0` 间接跳转。

| opcode | 语义 | 关键代码 |
|---|---|---|
| `0x19` (25) | 循环/重复 | `0x08097C48` |
| **`0x1A` (26)** | **换场 + 分支标记** | `0x08097C6C` |

**`0x1A <场景> <标志>`**（3 字节）的语义（`0x08097C6C`）：

```
0x08097C6C: ldrb r0, [r7, #2]      ; 标志
0x08097C70: cmp  r0, #0
0x08097C72: beq  #0x08097C78
0x08097C74: adds r0, #1
0x08097C76: strb r0, [r4, #0x18]   ; state[0x18] = 标志 + 1
0x08097C78: ldrb r0, [r7, #1]
0x08097C7A: strb r0, [r4, #0x16]   ; state[0x16] = 新场景号
```

⇒ **`标志 = 0` ⇒ `state[0x18] = 1`（章节交接）；
`标志 = 2` ⇒ `state[0x18] = 3`（普通换场）**。

**哪些场景用了「章节交接」**（用 `tools/decode_story_script.py` 的
`walk()` 扫全部 55 场 × 4 个根表）：

| 场景 | `0x1A` 的标志 | 目标场景 |
|---|---|---|
| **1** | 0 | 2 |
| **3** | 0 | 51 |
| **50** | 0 | 31 |
| **51** | 0 | 5, 50 |
| **52** | 0 | 24 |
| **53** | 0 | 50 |
| 39 | 2（×6） | 40, 41, 42, 43, 44, 45 |

**⇒ 场景 1（开场）就有一条章节交接路径**，
而且场景 1 的 before-root 第一条指令就是 `0x0B`（无条件跳转）
跳到 `0x0800B158` 的任务对话，末尾就是 `1A 02 00` → 章节场景 2。

### 7.1f 状态机怎么选根表

`fn 0x0808F544`（剧情分发器）：

```
0x0808F598: sb = 0x08060D54   ; after 根表
0x0808F59C: r8 = 0x08060C74   ; before 根表
0x0808F5A0: ldrb r1, [r6, #0x18]   ; state[0x18]
0x0808F5A2: cmp  r1, #0
0x0808F5A4: beq  #0x0808F5C0      ; 0 -> before 根表
                                    ; 非 0 -> after 根表
0x0808F5C8: strb r1, [r6, #0x19]   ; story_config[0] = 标记
0x0808F5CC: strb r5, [r6, #0x18]   ; **state[0x18] = 0**（跑 VM 前清零）
0x0808F5D0: bl   0x080977B8        ; 跑 VM
0x0808F5D4: ldrb r0, [r6, #0x18]
0x0808F5D6: cmp  r0, #3
0x0808F5D8: bne  #0x0808F5E0        ; 3 -> 回环换场；其它 -> 进度检查
```

**⇒ `state[0x18] == 0` 选 before 根表，非 0 选 after 根表。**

### 7.1g 谁把 `state[0x18] == 1` 变成章节初始化

**全 ROM 只有一处**按字节读 `state[0x18]`（通过 `state` 基址 + 偏移）：

```
0x0808F67E: ldrb r1, [r5, #0x18]   ; state[0x18]
0x0808F680: cmp  r1, #0
0x0808F682: bne  #0x0808F664
```
（位于 `fn 0x0808F654` 内，循环体 `0x0808F664` 里
`cmp r1,#1 ; bne` → `0x0808F668: bl 0x0808F618` = 章节初始化。）

**⇒ `fn 0x0808F654` 是 `state[0x18] == 1` 的唯一消费者；
而它没有任何 `bl` 调用者、没有数据指针、也没有分支指向它**
（四张根表 `0x060C74/0x060D54/0x060E34/0x060EF0` 都是**脚本指针**，
55/55/46/46 项，扫过 0x060C00..0x061400 没有函数指针表命中它）。

**⇒ 章节初始化这条路径在当前 ROM 构建里是「静态不可达」的** ——
要么它由某个计算出来的地址调用（寄存器分支），
要么这个构建的**关卡/章节模式根本没有接上**。
这是 45 条回调派发缺口最可能的最终解释，也是下一轮唯一要回答的问题。

### 7.1h 方法学教训（我自己的工装犯过一次）

### 7.1j 剩下的最后一步是**输入/游戏状态**，不是逆向

场景 1 的 before-root 里，章节交接 `1A 02 00` 之前有两处**菜单选择**：

|---|---|---|

### 7.1k VM 的「条件标志」系统（op `0x0B` / `0x0C`）——**已解开并实测生效**

`0x0B` 与 `0x0C` 是**同一个标志数组**上的取反分支：

```
0x08097AC4: ldrb r0, [r7, #1]     ; 条件 id
0x08097AC6: bl   0x080970A0      ; 读标志值
0x08097ACA: lsls r0, r0, #0x10
0x08097ACC: asrs r4, r0, #0x10
0x08097ACE: cmp  r4, #1
0x08097AD0: beq  #0x08097AD4     ; op 0x0B: 标志 == 1 -> 跳
0x08097AD2: b    #0x08097E0A     ;          否则顺序执行
0x08097AD4: adds r0, r7, #2       ; 目标在 payload+2
0x08097AD6: b    #0x08097D22
```
（op `0x0C` 在 `0x08097AD8`：判 **`== 0`** 才跳。）

**标志数组的位布局（单步追踪实测，`build/probe_flagstep.py`）**：

```
+1  r1 = 0x020314F0        ; 数组基址
+3  r2 = id << 16
+4  r0 = r2 >> 19 = id >> 3   ; 字节下标
+5  r0 = 0x020314F0 + 字节下标
+6  r0 = 该字节              ; ldrb
+9  r1 = (id << 16) & 0x70000
+10 r1 = id & 7
+11 r0 = 字节 >> r1          ; 按位取
+13 r0 = r0 & 1              ; 得到 0/1
```

⇒ **条件 id n ⇒ 字节 (n >> 3) 的第 (n & 7) 位**（每字节 8 个条件，用 bit 0..7）。
**条件 1 = 字节 0 的 bit 1**（不是 bit 0 —— 静态解码会看错，
因为 `lsrs r0, r0, r1` 用的是寄存器移位）。

**实测生效**：在 `0x08097AC4`（读标志的那一刻）把 `0x020314F0` 置成 **0x02**，
VM 游标立刻从 `0x08009F2E`（`0x0B` 节点）跳到 **`0x0800B158`**（任务对话）——
**门控被打开**。探针：`tools/mgba_probe/chapter_route.py --cond 2`。

### 7.1l 菜单 opcode `0x05` 与「认识卡多」分支

`op 0x05`（`0x080979D6`）= **menu-text**：

```
0x080979D6: ldr  r0, [pc, #0xC]   ; = 0x0200A880
0x080979D8: ldrb r0, [r0]         ; 菜单行数
0x080979DA: lsls r0, r0, #2
0x080979DC: adds r0, #1
0x080979DE: adds r0, r7, r0       ; 菜单数据跟在脚本里
0x080979E0: b    #0x08097D22      ; 解码文本
```

**⇒ `0x0200A880` = 当前菜单的行数**，而它**同时**是事件 switch 选 case 的依据
（`0x08073AC0` 读同一个字节、判 `== 1`）—— 两处共用，说明「菜单结构」
同时决定「事件分支」。

场景 1 的任务对话里有两处菜单，**「认识卡多」那条分支才通向章节交接**：

```
0x0800B7FF  op=0x05 menu-text   「佐助　不认识卡多／认识卡多」
0x0800B840  op=0x06 branch2  -> 0x0800B899, 0x0800B849
0x0800B849  「卡多……听说过，……」→ 0x0800B894  op=0x07 jump -> 0x0800BBF4
0x0800BFBC  op=0x1A  raw=1a 02 00   -> 场景 2（章节交接）
```

**实测**：纯按 A 会**自动选中第一项**（不认识卡多，游标落在 `0x0800B899`），
于是永远走不到 `0x0800BFBC`。
方向键（UP/DOWN/LEFT/RIGHT）在当前按键方案下**没有改变选择**。
⇒ 菜单的**选择键 / 光标机制**尚未解开（下一轮的唯一剩余项）。

### 7.2 一共四道门，逐一列出

| # | 门 | 判定点 | 判据 | 实测 |
|---|---|---|---|---|
| 1 | 状态机走哪条分支 | `0x0808F61E` | `fn 0x08088F10` != 0 ⇒ 任务事件分支（**回调簇在这里**） | 55 场 × 10 按键：0 命中（`fn 0x080732B4` 都没进） |
| 2 | 战斗包装走哪条路 | `0x080736FE` / `0x08073708` | `ctrl[0] != 0` ⇒ 事件链；`== 0` ⇒ 开战 | **已实测**：`ctrl[0] = 1` 时 `0x080737C8` / `0x080737CA` / `0x080737CC` / `0x08075054` 全部命中 **31 次**（事件链确实进了，而且在 0x1210 上自旋） |

### 7.3 下一轮要做的（可直接执行）

**入口条件已经全部钉死，剩下的是「怎么把游戏玩到那一步」。**

1. **选一个候选场景 + 正确的根表**（`tools/mgba_probe/chapter_route.py --branch`）：
   | 场景 | `--branch` |
   |---|---|
   | 1 | 0 |
   | 51 | 0 |
   | 50 / 53 | 任意 |
   | 3 / 52 | 1 |
2. **走到那两处菜单**。场景 1 的两处选择是「鸣人　没有／好了」与
   「佐助　不认识卡多／认识卡多」；**「认识卡多」那条分支才通向 `1A 02 00`**。
   已知 VM 的 opcode 轨迹（`0x50` → 18 × `0x01` → 结束）说明
   **纯按 A 走不到菜单**——要么对话推进需要别的键，
   要么菜单需要光标移动 + 确认的特定组合，
   要么需要先满足前置剧情状态。
   建议用 `--keys` 扫组合，或先解出 `0x01`（对话）/`0x05`（菜单）
   两个 opcode 的等待条件（见 `tools/story_vm_ops.py`）。
3. 一旦 `1A <场景> 0` 执行 ⇒ `state[0x18] = 1` ⇒
   `fn 0x0808F654` ⇒ `fn 0x08068DE4`（`0x03000075 = 1`）⇒
   `fn 0x080732B4` ⇒ 事件链 case **0x4080**（读 **items 表 `0x08545BE4`**）
   ⇒ case **0x6000** ⇒ 生成门控 ⇒ `fn 0x080722A8` ⇒ `fn 0x08080E30`
   ⇒ `fn 0x08080B08` ⇒ 读 **`0x0853F140` / `0x0853F298`**。
   **7 张表、9 个结构**一次性拿下。
4. 途中还要过：分支选择字节 `0x0200A880 == 1`、
   战斗结束标志 IWRAM `0x03005D44 == 0`（`fn 0x08064A48`）、
   生成门控 `unit[0xCD] == 0xFF`（或 `ctrl[0xCC] == 0`）。
   探针 `tools/mgba_probe/spawn_forcer.py` 已能现场改写其中几项。

> **仍未回答的最后一个静态问题**：`fn 0x0808F654`（`state[0x18] == 1` 的唯一消费者）
> **没有任何 `bl` 调用者、没有数据指针、也没有分支指向它**；
> 四张根表（55/55/46/46 项）全是**脚本指针**，扫过 0x060C00..0x061400 没有
> 函数指针表命中它。⇒ 它要么被某个**计算出来的地址**调用，
> 要么这个构建的**关卡/章节模式根本没接上**。
> 这是 45 条回调派发缺口最可能的最终解释。

## 10. 修正的旧结论
| 旧结论 | 新结论 | 依据 |
|---|---|---|
| 「`fonts` 消费者是 fn `0x0807EE50`」 | fn `0x0807EE50` 读的是 **`0x0853E328`**；`0x0853E596` 的消费者是 `0x0807F0FC` 起的代码 | `0x0853E596` 全 ROM 只出现 1 次（`0x0807F114`） |
| 「`0x0853EF70` 起是 20 字节对象类型记录（id 3）」 | 基址 **`0x0853EF30`**、步长 **24**、21 条记录 | `0x0853EF30 + 21×24 == 0x0853F140`（下一张已知表） |
| 「`0x0853E698` 的消费者是 fn `0x0807F414`」 | `0x0807F414` **不读**这张表；读它的是 `0x0807FD28`（另一个派发点，索引同一个 u8） | `0x0853E698` 的字面量池条目在 `0x0807FA38` / `0x0807FD88` |
| 「`0x0853F298` 是 units 重映射表（步长 8）」 | 实际是 **u16 数组、步长 2**（`id*2`），读者 `0x08080B2C` | `0x08080B2E: lsls r0, r3, #1` |
