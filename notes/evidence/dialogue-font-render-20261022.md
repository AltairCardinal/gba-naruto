# 对白字形渲染：从正文 token 流到屏幕像素（2026-10-22）

**范围**：`0x0806626C` 正文渲染器往下追出的**对白字形来源 / 格式 / 缩放 / 配色**全链路。
**方法**：静态反汇编（`tools/disasm_thumb.py`）+ ROM 字节核对 + mGBA 真机运行时抓取
（VRAM / PALRAM / 显示寄存器）+ 与 `notes/evidence/story-scene-l3.png` **逐像素比对**。
**产物**：`notes/evidence/dialogue-font-scene54-20261022.png`（本轮渲染）。

---

## 0. 一句话结论

> 对白里的汉字就是 ROM 字形段表 **`0x0853D644`**（内容包里的 `font_segments`）里的字形，
> 但**格式不是旧笔记写的「8×8 4bpp」**，而是
> **8 宽 × 16 高、每像素 2 bit、每字形 32 字节**（每字节 4 像素、每行 2 字节）。
> 渲染时把它**展开成 4bpp 的两个 8×8 字符块**，写进 VRAM 字块 **`0x06002000`**，
> 通过 **BG tilemap（`0x06001800`）** 上屏，**1:1 无任何缩放**。
> 屏幕上一个汉字占 **8 px 宽 × 16 px 高**，字距就是 **8 px**。

关键地址一览：

## 1. 完整链路（每步带地址与字节证据）

### 1.1 剧本字节 → 字形码

场景 54 第 5 句在 ROM 的节点是 `0x08049FC5`（`op=0x01`，长度 50）：

```
01 81 67 95 c4 88 9f 81 43 95 c4 97 cf 9b ac 8c f3 88 de 9c 62
94 cb 96 98 8a 6e 94 cc 8b 62 91 ec 81 49 81 68 81 40 81 40 81 40
81 40 81 40 81 40 00
```

- `0x01` 是 opcode，后面是**双字节字形码**（lead 0x80–0x9F + trail）：
  `8167 95C4 889F 8143 95C4 97CF 9BAC 8CF3 88DE 9C62 94CB 9698 8A6E 94CC 8B62 91EC 8149 8168 8140×6`，最后 `00` 结束。
- 解码文本（`tools/text_codec.py` 的映射）：`“是啊，是我这个班主任所承认的嘛！”` + 6 个全角空格。
- 注意 lead=0x81 的码（`8167` `8143` `8149` `8168` `8140`）就是**中文标点与全角空格**，
  它们**同样走 CJK 字形**，不是 ASCII 字形。

### 1.2 `0x0806626C` 分派

`0x0806627E` 取一个字节，`lsls r0,r0,#0x18` 把 bit7 提到符号位：

- 字节 ≤ 0x1F → 控制码，函数内联处理：
  - `0x01`（`0x080662A2`）：`strb r0,[r6,#0x12]` → 设**颜色**；
  - `0x02`（`0x080662AC`）：`strh` 到 `[r6+0x0c]`（列）、`[r6+0x0e]`（行）→ **定位**；
  - `0x03`（`0x080662BC`）：跳过 1 字节，置 `sb=2`；
  - `0x0A`（`0x080662C6`）：`[r6+0x0c]=0`（列归零）、`[r6+0x0e]+=2`（**行 +2 = 16 px**）、`[r6+0x10]+=2` → **换行**。
- 字节 ≥ 0x80（`r0` 符号位为 1 → `cmp r0,#0; bge` 不成立）→ 双字节字形码路径：
  - lead ≤ 0x9F → 直接走 `0x080662F8`；
  - lead > 0x9F → 先 `bl 0x8065e80` 查段表，查不到就跳过该字符。
- 字节 0x20–0x7F → `0x080663B4` → `bl 0x80661f8`（模式匹配器）→ 默认走 `0x08066444` → `bl 0x8066144`（ASCII）。

### 1.3 CJK 字符 → VRAM 图块

`0x080662F8` 把 16 位字形码、颜色、输出缓冲交给 `0x08065F84`：

```
0x080662F8: ldr  r0,[sp,#0x1c]   ; 取两字节
0x080662FC: lsls r1,r1,#8
0x080662FE: ldrb r0,[r0,#1]
0x08066300: orrs r0,r1           ; r0 = 16 位字形码
0x08066302: ldrb r1,[r6,#0x12]   ; 颜色
0x08066304: add  r2,sp,#0x14     ; 输出（2 个 u16 表项）
0x08066306: bl   #0x8065f84
```

`0x08065F84` 内部：

1. `cmp r4,r0`（`0x08065F94`，r0 = 字面量 `0x08066004` = **`0x00008140`**）
   → 若字形码 == `0x8140`（**全角空格**）→ 走 `0x08066014`，写入**空白图块** `0x1C1`
   （`ldr r0,[r3]` 取 `0x0201BD58` = `0x01C0`，`+1` → `0x1C1`），属性 `|0xE000`。
2. `bl 0x8065df8`（`0x08065F9E`）：从 `0x0201BD4C` 的位图里**分配 2 个图块位**，
   图块号 = `bank*32 + slot`（`lsls r1,r6,#5` + `r5`），返回值写进 `sp[0]`/`sp[2]`。
3. `ldrh` 取出这两个图块号 → `lsls #5` → `glyphA = base + idxA*32`、`glyphB = base + idxB*32`
   （`base` = `*0x0201BD48` = **`0x06002000`**，VRAM 字块第 0x100 号）。
4. `bl 0x8065eb8`（`0x08065FBE`）：把 ROM 字形展开成 4bpp 写进这两个图块。
5. `0x08065FDC`–`0x08065FFE`：把两个图块号 + 属性写成**两个 tilemap 表项**
   （`base=*0x0201BD64=0x100` 加图块号，再 `| 0xE000 | (color>>1)<<12`）。

`0x08065EB8`（展开核心，逐位可核对）：

```
0x08065EC4: lsls r0,r0,#0x10 ; lsrs r5,r0,#0x10   ; r5 = 字形码
0x08065ED0: movs r0,#1 ; ands r0,r4 ; adds r0,#2   ; k = (color&1)+2  (2 或 3)
0x08065EDA: bl   #0x8065e80                      ; 段表查找
0x08065EF0: ldrh r0,[r0]                          ; entry.start_code
0x08065EF2: subs r0,r5,r0
0x08065EF4: lsls r0,r0,#5                         ; (code-start)*32  ← 每字形 32 字节
0x08065EF6: ldr  r1,[r1]                          ; entry.glyph_offset
0x08065EF8: adds r5,r1,r0                        ; r5 = ROM 字形地址
```

随后是**像素搬运循环**（`0x08065F1C`–`0x08065F4C`）：每次读 ROM 的 1 字节，
把它拆成 **4 个 2-bit 场**，写成 VRAM 的 **1 个半字（4 个 4-bit 像素）**：

```
movs r1,#3 ; ands r1,r2        ; 源 bits[1:0] → 目标 nibble0
movs r0,#0xc ; ands r0,r2      ; 源 bits[3:2] → 目标 nibble1
movs r0,#0x30 ; ands r0,r2     ; 源 bits[5:4] → 目标 nibble2
movs r0,#0xc0 ; ands r0,r2     ; 源 bits[7:6] → 目标 nibble3
```

每个 nibble 再 `| (k*4) / (k*16) / (k*64) / (k*256)`（`sl`/`sb`/`r8`/`ip` 四个常量，
分别落在 nibble 的最高位）⇒ **目标像素值 = 源 2-bit 值 + 8（k=2）或 + 12（k=3）**。

外层循环跑 **2 轮**（`0x08065F52`–`0x08065F66`：轮号 `r1` ≤ 1 才继续），
每轮 16 次内层迭代（`cmp r6,#0xf`）⇒ 读满 **32 字节**源字形，
写 **2 个 8×8 图块**（各 16 个半字 = 32 字节）。

### 1.4 ASCII 字符 → VRAM 图块

`0x08066144`：`cmp r4,#0x20` → 空格走空白图块；否则 `bl 0x8065df8` 只分配 **1** 个图块位，
再 `bl 0x80660a4`（`0x080660DA`：`lsls r0,r0,#4` ⇒ **16 字节/字形**），
源来自 `0x0853D73C` 的 ASCII 段表（`[u8 start][u8 count][u16 pad][u32 ptr]`）：

| 段 | start | count | 字形基址 | 覆盖 |
|---|---|---|---|---|
| 0 | `0x20` | `0x60` | `0x0809CD54` | 0x20–0x7F |
| 1 | `0xA0` | `0x60` | `0x0809D354` | 0xA0–0xFF |

### 1.5 字形数据格式（8×16 2bpp）

**推定 + 已用像素级验证**：字形 = **8 宽 × 16 高**，每像素 **2 bit**，
每字节 **4 个像素**、每行 **2 字节**，共 32 字节。

ROM 实测（`0x0853D644` 段表）：

## 2. 到底用哪套字形？（问题 1）

**结论**：对白汉字 = `0x0853D644` 那张字形段表（内容包里的 `font_segments`）里的字形。

**证明**（三条独立证据）：

1. **运行时 VRAM 命中**：把 ROM 字形按 §1.5 的格式 + §1.3 的展开规则算成 4bpp，
   与场景在场时 VRAM `0x06002000` 里的图块**逐字节相同**：
   是（`+0x40`/`+0x60`）、啊（`+0x80`/`+0xA0`）、我（`+0x140`/`+0x160`）、班（`+0x200`/`+0x220`）。
2. **tilemap 引用**：VRAM `0x06001800` 的表项 `0xE102/0xE104/0xE108/0xE110…`
   正好指向这些图块，且**上/下半成对**。
3. **屏幕像素**：把 ROM 字形按该格式渲染，与 `notes/evidence/story-scene-l3.png`
   上那一句**逐像素相同**（2304/2304，见 §7）。

⇒ **旧笔记「对话字形是 16×16、来源尚未定位」作废**：
`0x53D644` 就是对话字形的来源，只是**格式被记错了**（不是 8×8 4bpp，是 8×16 2bpp）。

## 3. 字符块（tiles）还是精灵（OBJ）？（问题 1）

**结论：是 BG 字符块，不是 OBJ。**

证据：

- 运行时 OAM（`0x07000000`，128×8B）里**没有任何一条**的图块号落在字块区间
  （`0x100`–`0x1FF`）。场景里的 13 条有效 OAM 是立绘与图标
  （图块号 0/8/24/40/56/72/200/208/224/240/256/272/243），
  其余 115 条是标准的关闭态（`a0=0x0200`）。
- DISPCNT = `0x1940`（Mode 0，BG0+BG3 使能，OBJ 使能，OBJ 1D 映射=1），
  但对白文字走的是 **tilemap**（`0x06001800` 里全是 u16 表项），OBJ 没有 tilemap。
- 字形被写进**字符块** `0x06002000` 并由 tilemap 表项引用，这是 BG 的标准做法。

## 4. 缩放是几倍？（问题 1）

**结论：1:1，没有任何缩放。**

- 屏幕上汉字实际是 **8 px 宽 × 16 px 高**（不是 16×16）。
  实测（`notes/evidence/story-scene-l3.png` 的对白行，y=121…135）：
  墨迹列起点 = 27, 32, 40, 48, 56, 64, 72, 80, 88, 96, 104, 112, 120, 128, 136, 144, 152…，
  **相邻格距恰好 8 px**；行高 14–15 px 的墨迹落在 16 px 的格子里。
- ROM 字形本身就是 8×16，展开后是 2 个 8×8 图块上下拼，
  所以「放大 2 倍」既不在取数时、也不在写 VRAM 时、也不是 BG/OBJ 缩放寄存器 ——
  **根本没有缩放这一层**。
- ⇒ **`notes/evidence/story-scene-l3-20261020.md` §6 的「16×16」「字距约 12 px =
  汉字 16 px + 标点 8 px」两条都测错了**：
  - 字距是 **8 px**，不是 12 px；
  - 「汉字 16 px + 标点 8 px = 12 px」本身就算不通（16+8=24）；
    实际是**每个格子都 8 px**，中文标点（`，`「，`！`「`”`）是**全角 CJK 字形**，
    墨迹窄（2–4 px）但**格子仍是 8 px**，所以「标点 8 px」是把「墨迹窄」误当成「格子窄」。

## 5. 字形怎么画：bpp / 调色板 / 「描边」（问题 2）

### 5.1 源是 2bpp，VRAM 里是 4bpp

- ROM 字形：**2 bit/像素**（4 像素/字节，8 像素 = 2 字节/行）。
- VRAM 图块：**4 bit/像素**（GBA 4bpp 图块），像素值 = **源值 + 8**（`color&1==0`）
  或 **+12**（`color&1==1`）。所以只有 4 个色号可用：8/9/10/11（或 12/13/14/15）。

### 5.2 调色板

- ROM 里就有一份对白调色板：**`0x0809C87E`**，16 个 u16 小端 BGR555。
  运行时它被整块拷到 **PALRAM `0x050001C0`**（BG 调色板块 14，颜色 224–239），
  两边逐项一致（`0x7E18, 0x6BDC, 0x4B70, 0x3AEC, 0x2E6D, 0x2DCC, 0x335C, 0x1EB7,
  0x6BDC, 0x4ED5, 0x35EE, 0x1D07, 0x6BDC, 0x46BC, 0x219C, 0x007C`）。
- 对白用的 4 个色号 = 该块的颜色 **8–11**：

  | 像素值 | 源 2-bit 值 | 颜色 | 展开 RGB（mGBA 口径 `(v<<3)|(v>>2)`） | 用途 |
  |---|---|---|---|---|
  | 8 | 0 | `0x6BDC` | `(231,247,214)` | 透明 / 对白框底色 |
  | 9 | 1 | `0x4ED5` | `(173,181,156)` | 浅色笔画 |
  | 10 | 2 | `0x35EE` | `(115,123,107)` | 少用（全字库 564480 像素里只有 7257 个） |
  | 11 | 3 | `0x1D07` | `(57,66,57)` | 深色笔画（主笔画） |

### 5.3 没有「描边」，是**双色字形**

- 源字形里存的**就是**字形本身（不是外描边层）：
  「是」的第 1 行是 `00000310`，深色 3 在左、浅色 1 在最右一列 ——
  浅色是**笔画右侧的一像素高光**，即字体自带**立体/浮雕效果**。
- ⇒ 真机画面里对白是**深色字 + 浅色高光**、画在**浅色对白框**上；
  旧笔记「白色带深色描边」的描述与小图观感相反，**以本文件的像素测量为准**
  （`0x06001800` 同区域实测：底 `E7F7D6`、笔画 `394239`、高光 `ADB59C`）。

### 5.4 ASCII 标点用哪套字形？

- 正文里 **0x20–0x7F** 的单字节字符走**另一套 8×8 字形**：
  段表 `0x0853D73C`，字形数据 `0x0809CD54`（0x20–0x7F）/ `0x0809D354`（0xA0–0xFF），
  **16 字节/字形，8×8 2bpp**（每行 2 字节、4 像素/字节），同样展开成 4bpp、占 **1 个图块**。
- 渲染实测（8×8，`.`=透明、`+`=浅、`#`=深）：

  ```
  ' ' 0x20            '!' 0x21            'A' 0x41            '0' 0x30
  ........            ........            ........            ........
  ........            ...++#..            ..+++#..            .++++#..
  ........            ...++#..            .++#++#.            ++#.++#.
  ........            ...++#..            .++#++#.            ++#.++#.
  ........            ...++#..            .+++++#.            ++#.++#.
  ........            ...++#..            ++#..++#            ++#.++#.
  ........            ........            ++#..++#            ++#.++#.
  ........            ...++#..            ++#..++#            .++++#..
  ```

- 但**本仓库剧情正文里的标点全是全角 CJK 码**（`“`=0x8167、`，`=0x8143、
  `！`=0x8149、`”`=0x8168），走的是 CJK 8×16 字形；
  也就是说：**对白里没有 ASCII 标点**，ASCII 字形只在别的文本（数字/拉丁字母）里出现。

## 6. 浏览器端复现算法（纯函数建议）

### 6.1 要读的 ROM 地址

| 用途 | 地址 | 读法 |
|---|---|---|
| 字形段表 | `0x53D644`（ROM 文件偏移） | 31 × 8B：`start_code` u16 LE、`count` u8、`pad` u8、`glyph_offset` u32 LE（GBA 绝对地址） |
| ASCII 段表 | `0x53D73C` | 2 × 8B：`start` u8、`count` u8、pad u16、`ptr` u32 LE |
| 对白调色板 | `0x0809C87E`（**文件偏移 `0x9C877`**，见下面的订正） | 16 × u16 LE（BGR555），用颜色 8–11 |
| 正文文本 | 剧情脚本节点 | 双字节字形码流，控制码 0x00/0x01/0x02/0x03/0x0A |

> 内容包里的 `font_segments` **可以直接用**：`tools/export_content_pack.py`
> （常量 `FONT_SEGMENT_BASE=0x53D644`、`FONT_SEGMENT_STRIDE=8`、`FONT_SEGMENT_COUNT=31`；
> 字段 `start_code`@0x00 u16、`count`@0x02 u8、`pad`@0x03 u8、`glyph_offset`@0x04 ptr）
> 导出的就是上面这张表，浏览器端只要
> `addr = glyph_offset - 0x08000000 + (code - start_code) * 32` 就能取到字形字节。
> `font_width_table`（`0x53E596`，按**单字节字符码**索引）与对白排版**无关**：
> 对白是固定 8 px 格，`0x0806626C` 全函数没有对 `0x0853E596` 的引用。

### 6.2 字形码 → N×N 位图（逐像素算法）

```
glyphBytes(code):
    段 = font_segments 中满足 start_code <= code < start_code+count 的那一段
    if 无此段 -> 返回 null（游戏画空白/跳过）
    if code == 0x8140 -> 返回 null（全角空格，渲染成空白图块 0x1C1）
    off = (glyph_offset - 0x08000000) + (code - start_code) * 32
    return rom[off .. off+32]              # 32 字节

bitmap8x16(code) -> 16 行 × 8 列的 0..3 值:
    for row in 0..15:
        for col in 0..7:
            byte = glyphBytes[row*2 + col//4]
            bit  = (col % 4) * 2
            value = (byte >> bit) & 0x3        # 每字节 4 个像素，低位在前
    # 注意：像素顺序是「每字节 4 像素、每行 2 字节、行优先」

rgba(code) -> 16×8 的 RGBA:
    for 每个像素 v:
        idx = 8 + v                    # 调色板颜色号 8..11
        c   = palette[idx]             # 0x6BDC/0x4ED5/0x35EE/0x1D07
        if v == 0: 输出透明 (alpha=0)   # 索引 8 与对白框底色同色，游戏用同色做“透明”
        else:      输出 c 的 RGB
```

mGBA 的 5→8 bit 展开是 `(v<<3)|(v>>2)`，浏览器端照抄即可与真机完全一致：
`0x6BDC→(231,247,214)`、`0x4ED5→(173,181,156)`、`0x35EE→(115,123,107)`、`0x1D07→(57,66,57)`。

### 6.3 一段正文 → 若干行

排版规则（来自 `0x0806626C`）：

- **每个 CJK 字符 = 1 格 = 8 px 宽、16 px 高**（占 2 个 8×8 图块，上下排列）；
- **每个 ASCII 字符 = 1 格 = 8 px 宽、8 px 高**（占 1 个图块）；
- 行高 = **16 px**（tilemap 行 +2）；
- 换行：
  - 正文里的 `0x0A` ⇒ 列归零、行 +2；
  - 自动换行：列到达 `pitch-2`（若状态字 bit `0x400` 置位则是 `pitch-6`）时自动换行
    （`0x080664D2`–`0x08066500`）；
- 起始位置由状态结构算出（`0x08066C88`–`0x08066CAC`）：
  `x = ((L + (L & 0x1F)) >> 1) - 1`，`L = pitch-2`（或 `pitch-6`），`y = [state+0x0a] - 6`。
  **场景 54 实测**：首格在屏幕 x=24 px（第 3 格），首行基线 y=120 px。

渲染时把每个格子画成 8 px 宽、16 px 高（ASCII 只占上面 8 px）的矩形即可。

### 6.4 最小实现骨架（伪码）

```
function renderDialogue(rom, codes, opts):
    pal   = readPalette(rom, 0x9C877)          # 16 × u16
    segs  = readSegments(rom, 0x53D644)        # 31 × 8B
    canvas = transparent or boxColor
    x = opts.x0; y = opts.y0; col = 0
    for code in codes:
        if code == 0x0A: x = opts.x0; y += 16; col = 0; continue
        if code is control (0x01/0x02/0x03): handle; continue
        if code == 0x8140: x += 8; continue          # 全角空格 = 空白图块
        if code >= 0x8140 and inSegment(segs, code):
            bmp = bitmap8x16(segs, code)
            draw(canvas, x, y, bmp, pal)              # 8×16
        else:
            bmp = bitmap8x8Ascii(code)                # 16 字节/字形
            draw(canvas, x, y, bmp, pal)              # 8×8
        x += 8; col += 1
        if col == limit: x = opts.x0; y += 16; col = 0
```

## 13. 2026-10-22 追加：对白调色板的**文件偏移**订正 + 浏览器端独立复现

### 13.1 文件偏移是 `0x9C877`，不是 `0x9C87E`

本文件 §5.2 与 §6.4 写的 `0x9C87E` **偏了 7 字节**。

- 实测：颜色 8–11 那一段（`0x6BDC / 0x4ED5 / 0x35EE / 0x1D07`，4 个 u16 小端）
  在 ROM 文件偏移 **`0x9C887`**。
- 反推基址 = `0x9C887 − 8×2 = ` **`0x9C877`**。
- 用 `0x9C87E` 读出来的是这一段的前 4 个字（`0x2E6D / 0x2DCC / 0x335C / 0x1EB7`），
  颜色 8–11 会读成 `0xDC00 / 0xD56B / 0xEE4E / 0x0735` —— 全错。

> ROM **地址** `0x0809C87E` 没写错（它指向这段数据的中间），
> 错的是**文件偏移**这个换算。浏览器端实现
> `rom-editor/js/dialoguefont.js::DIALOGUE_PALETTE_OFFSET` 已按实测改成 `0x9C877`。

### 13.2 浏览器端独立复现（本仓库自己的实现）

`rom-editor/js/dialoguefont.js` 是**按本文件的描述独立写的**（没有抄对方的脚本）：

- 汉字：段表 `0x53D644`（31×8B）→ `off = glyph_offset − 0x08000000 + (code − start_code) × 32`
- 像素：`byte = rom[off + row×2 + (col>>2)]`，`v = (byte >> ((col&3)×2)) & 3`
- 调色板：文件偏移 `0x9C877`，用颜色 8–11；`v == 0` 透明
- 5→8 bit 展开：`(v<<3)|(v>>2)`
- ASCII：段表 `0x53D73C` → `0x0809CD54`，8×8 2bpp、16 字节/字形
- 排版：CJK 8×16、ASCII 8×8（占上半）、行高 16、字距 8、起点 x=24 / y=120
