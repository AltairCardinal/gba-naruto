# 剧情选择菜单的作答通道 + `state[0x18]==1` 的消费者（2026-10-21）

> 目标：打通 45 条回调派发缺口的最后一道门 —— 让场景 1 的「认识卡多」菜单被选中，
> 从而走进 `fn 0x080732B4` 的事件 switch，拿到 `0x0853E698` / `0x0853E596` /
> `0x08545BE4` / `0x0853F140` / `0x0853F298` 等表的运行时读数。
>
> 本文记录**方法 + 结果 + 关键地址**，可判死的检验随文给出。

## 0. 结论速览

| 项 | 旧结论 | 新结论（本文） |
|---|---|---|
| 菜单答案在哪 | `0x0200A898`（文本框 choice 槽） | **`0x0200A880` = 选中行**（u8） |
| `0x0200A880` 是什么 | 「菜单行数」 | **菜单的作答通道**（A 键按下时写入当前行） |
| 菜单完成标志 | 未记录 | **`0x0200A882` = 1**（A 键按下时写入） |
| `state[0x18]==1` 的消费者 | `fn 0x0808F654` | **`0x0808F904`**（在 phase `0x30` 处理器里） |
| `fn 0x0808F654` | 剧情驱动 | **死代码**（全 ROM 无 BL、无函数指针指向它） |
| 章节链 | `0x0808F654 → 0x08068DE4 → 0x080732B4` | **phase `0x30` → `0x0808F904` → phase `0x100` → `fn 0x08088F10` → phase `0x110` → `0x0808F92E` → `bl 0x080732B4`** |

## 1. 菜单 UI `fn 0x08095F58` 的逐指令解剖

函数入口 `0x08095F58`，对象指针 `r0`（消息框对象）。以下是**逐条核对过的指令**
（地址、半字、`probe_bl.py` 独立解码的分支目标）：

```
0x08095F72: strb r5,[r6,#0x16]     ; obj[0x16] = 0   (当前行 current row)
0x08095F74: strb r5,[r6,#0x14]     ; obj[0x14] = 0   (锚行 anchor row)
0x08095FB4: bl  0x080626B4         ; 算光标
0x08095FBA: str  r0,[0x0200A890]   ; 0x0200A890 = 行结构指针 (u32)  ← 不是答案
0x08095FBE: strb r5,[0x0200A882]   ; 0x0200A882 = 0   ("菜单已结束" 标志)
0x08095FC0: ldr  r0,[0x0200A884]   ; 缓存按键状态
0x08095FCA: ldrh r1,[0x0300000C]   ; 当前按住
0x08095FCE: ldrh r2,[r6,#0x1C]
0x08095FD0: cmp  r1,r2
0x08095FD2: bne  0x0809601A        ; 按住状态变了 -> 刷新缓存
   ... 0x0809601A: strh r1,[r6,#0x1C]
       0x08096024: strh r1,[0x0200A884]   ; 缓存 = 0x0300000E (本帧新按下)
0x0809602C: ldrh r1,[r4]           ; 取缓存按键状态
0x0809602E: movs r5,#0x40          ; *** 0x40 = UP    ***
0x08096038: ldrb r0,[r6,#0x16]     ; 当前行
0x0809603E: subs r0,#1
0x08096066: strb r0,[r6,#0x16]     ; 上移
0x0809604C: movs r5,#0x80          ; *** 0x80 = DOWN  ***
0x08096064: adds r0,r1,#1
0x08096066: strb r0,[r6,#0x16]     ; 下移
0x08096078: ldrh r1,[0x0300000E]   ; *** 直接读「本帧新按下」 ***
0x0809607E: movs r4,#1             ; *** 0x01 = A（确认） ***
0x08096082: ands r0,r1
0x08096086: beq  0x080960A0
0x08096088: ldr  r0,[0x0200A882]
0x0809608A: strb r2,[r0]           ; 0x0200A882 = 1     ("菜单已结束")
0x0809608C: ldr  r1,[0x0200A880]
0x0809608E: ldrb r0,[r6,#0x16]     ; 当前行
0x08096090: strb r0,[r1]           ; 0x0200A880 = 当前行  ★★★ 作答通道 ★★★
0x080960BE: ldr  r0,[0x0200A882]
0x080960C0: ldrb r0,[r0]
0x080960C2: cmp  r0,#0
0x080960C4: bne  0x080960C8        ; 已完成 -> 退出循环
0x080960C6: b    0x08095FC4        ; 否则回到循环头
0x080960CA: bl   0x08062788        ; 收尾
```

**要点**

1. `0x40` 是 **UP**、`0x80` 是 **DOWN**、`0x01` 才是 **A**。
   之前把 `0x40` 当成 A 是错的 —— 这就是「按 A 反而上移光标」的根因。
2. **A 的判定读的是 `0x0300000E`（本帧新按下）**，不是缓存的 `0x0200A884`。
   `0x0300000E` 全 ROM 只有 `fn 0x080615E4` 一个写者（`0x08061606`），
   而该函数只被 `0x08061082`（主循环）和 `0x080612F8` 调用。
   菜单 UI 是**模态自循环**（`0x080960C6` 直接跳回 `0x08095FC4`），
   期间主循环拿不到控制权 ⇒ 按键更新在菜单期间**可能不运行**。
3. 作答只有两个字节：`0x0200A880`（行号）+ `0x0200A882`（完成标志）。

**可判死的检验**：`tools/mgba_probe/menu_probe.py` 在 `0x0809602C`（菜单轮询）
读 `0x0300000E`；若菜单期间该值恒定，则按键更新确实没在跑。

## 2. VM opcode `0x06` 的分支表布局

`0x080979D6`（op `0x06` 处理器）：

```
0x080979D6: ldr  r0,[0x0200A880]
0x080979D8: ldrb r0,[r0]          ; 读作答（u8）
0x080979DA: lsls r0,r0,#2         ; *4
0x080979DC: adds r0,#1            ; +1
0x080979DE: adds r0,r7            ; r7 = 当前 opcode 地址
0x080979E0: b    0x08097D22
0x08097D22: bl   0x08096EA4       ; 读游标处的 u32 当作新游标
0x08097D26: adds r7,r0,#0
```

即 **新游标 = op 地址 + 4*作答 + 1**，该处的 u32 就是跳转目标。

### 场景 1 的分支表（ROM 字节直接验证）

`0x0800B855` = `06`，其后是 u32 跳转表：

| 槽 | 表项地址 | 表项值 (LE u32) | 含义 |
|---|---|---|---|
| row 0 | `0x0800B856` | `0x0800B899` | 不认识卡多 |
| row 1 | `0x0800B85A` | `0x0800B849` | **认识卡多** → `0x07 jump` → `0x0800BBF4` → `0x0800BFBC` = `1A 02 00` |

ROM 原始字节（`0x0800B7F0` 起 0x70 字节）：
`... 00 06 99 B8 00 08 49 B8 00 08 08 02 01 81 67 ...`
（`99 B8 00 08` = 0x0800B899；`49 B8 00 08` = 0x0800B849）

**可判死的检验**：`0x080979D6` 命中后读 `0x0200A880`，
若为 1 且新游标落在 `0x0800B849`，则通道判定成立。

## 3. 怎么把菜单答上：直接在作答通道写值

`tools/mgba_probe/chapter_route.py --force-row N` 的做法：

* 在 `0x080960BE`（**`ldrb` 读完成标志之前**）断点；
* 写 `0x0200A880 = N`、`0x0200A882 = 1`。

这与 A 键在 `0x0809608A` / `0x08096090` 做的两次写**完全等价**，
区别只是省掉了「等一个按键沿」。

> ⚠️ 断点落在 `0x080960C2`（`cmp`）会**无效** —— 那一拍 `r0` 已经装载完毕，
> 再改内存来不及。必须落在装载之前。

### 之前几种写法为什么无效（全部记此留痕）

| 试法 | 为什么无效 |
|---|---|
| 写 `0x0200A898`（choice 槽） | 那个地址根本不在作答路径上 |
| 写 `0x0200A890`（光标索引） | 它是**行结构指针**，不是答案；而且每轮被 `fn 0x080626B4` 覆盖 |
| 写 `0x03005E64`（对象 `+0x14`） | `+0x14` 是**锚行**（首屏行），不是当前行；当前行在 `obj[0x16]` |
| 往 `0x0200A884` 注入 `DOWN` | 该缓存只在「按住状态变化」时刷新；按键沿被 `frames N mask` 的释放时机吃掉 |
| 只按 A | A 判定读 `0x0300000E`（本帧新按下）；模态菜单期间按键更新未必运行 |

## 4. `state[0x18]==1` 的真正消费者（推翻旧结论）

旧结论：`fn 0x0808F654` 是 `state[0x18]==1` 的唯一消费者。
**作废**。逐指令读 `0x0808F654`：

```
0x0808F654: push {r4,r5,lr}
0x0808F658: lsrs r4,r0,#0x10
0x0808F65A: ldr  r5,[0x020311D4]      ; 剧情状态块
0x0808F676: bl   0x0808F544          ; 跑脚本
0x0808F67A: ldrb r0,[r5,#0x16]
0x0808F67E: ldrb r1,[r5,#0x18]       ; state[0x18]
0x0808F680: cmp  r1,#0
0x0808F682: bne  0x0808F664
0x0808F664: cmp  r1,#1
0x0808F666: bne  0x0808F66E
0x0808F668: bl   0x0808F618          ; 章节初始化
0x0808F672: bl   0x0808F544          ; 再跑一次
```

**但 `fn 0x0808F654` 是死代码**：全 ROM 没有任何 `bl` 指向它，
也没有任何 32 位指针（`0x0808F654` 或 `0x0808F655`）指向它。
（`build/probe_blscan.py` 用原始半字自行解码 BL，扫全 ROM 16 MB。）

真正活着的消费者在**状态机 `fn 0x0808F73C`** 的 phase `0x30` 处理器里：

```
0x0808F8DC: ldrb r0,[r4,#0x16]     ; 场景
0x0808F8DE: bl   0x0808F544        ; 跑该场景脚本
0x0808F8E2: ldrh r1,[r4,#0x10]     ; story_progress
0x0808F8E4: cmp  r1,#0x3E7         ; 通关?
0x0808F8EA: strh r6,[r4,#0x12]     ; phase = 0x10
0x0808F8F4: cmp  r1,#0x168
0x0808F8FC: strh 0x8000,[r4,#0x12]
0x0808F904: ldrb r0,[r4,#0x18]      ; ★ state[0x18]
0x0808F906: cmp  r0,#0
0x0808F908: bne  0x0808F90C
0x0808F90A: b    0x0808FA20         ; state[0x18]==0 -> phase 0x20
0x0808F90C: cmp  r0,#1
0x0808F90E: bne  0x0808F922         ; 其它值 -> state[0x18] = 0
0x0808F910: ldrb r0,[r4,#0x16]
0x0808F912: cmp  r0,#0x34           ; 场景 52?
0x0808F916: strh 0x210,[r4,#0x12]   ; phase = 0x210
0x0808F91E: strh r5,[r4,#0x12]      ; phase = 0x100   (r5 = 0x80<<1)
```

**所以完整章节链是：**

```
op 0x1A <场景> 00  ->  state[0x16]=场景, state[0x18]=1
state machine phase 0x30 (0x0808F8DC)
   -> 0x0808F904 读 state[0x18]==1  ->  phase = 0x100
state machine phase 0x100 (0x0808F928)
   -> bl 0x08088F10  (章节初始化)   ->  0x0808FA10: 返回非 0 -> phase = 0x110
state machine phase 0x110 (0x0808F92E)  ← 完整战斗入口
   -> bl 0x08075184 (战斗前准备)
   -> bl 0x0808A490(1,0x7F) (置战斗运行标志)
   -> bl 0x080732B4  ★★ 事件 switch：回调表在这里 ★★
```

`fn 0x0808F73C` 本身没有 `bl` 调用者，它作为**函数指针**存放在
`0x0806107C` 与 `0x080859B4`（`0x0808F73D`）。

**可判死的检验**：断在 `0x0808F904` 读 `state[0x18]`；
若读到 1 且下一拍 `state[0x12]` 变成 `0x0100`，则链路成立。

## 5. 任务面板 `fn 0x080884DC`（章节设置的第二道门）

`fn 0x08088F10`（章节初始化）是个状态机，靠 `fn 0x080884DC` 的返回值决定下一步：

```
0x08088F9A: bl 0x080884DC        ; 问任务面板
0x08088FA2: asrs r0,r0,#0x10     ; 有符号
0x08088FA4: cmp r0,sb            ; sb = -1
0x08088FA6: bne 0x08088FB8       ; 不是 -1 -> 按答案分流
0x08088FA8: r0=5; bl 0x08061E88  ; -1 -> 放弃，退出
0x08088FB8: lsls r0,r5,#0x10
0x08088FBC: cmp r0,#0 ; 0 -> r4=0x10
0x08088FD4: cmp r0,#1 ; 1 -> r4=0x20  ★ 进战斗 ★
0x08088FDE: cmp r0,#2 ; 2 -> 取消
0x08088FEC: cmp r0,#3 ; 3 -> r4=0x40
```

`fn 0x080884DC` 本身：

```
0x080884F2: r0 = 0x08009C35
0x080884F4: bl 0x08067158         ; 显示任务标题
0x080884F8: r2 = 0x08348DAC       ; 任务索引表（56 场 x 3 条 u8）
0x080884FC: ldrb r0,[0x020311EA]  ; state[0x16] = 场景
0x08088500: ldrb r4,[r0]          ; 该场的任务号
0x08088502: ldrb r1,[0x020311ED]  ; state[0x19] = 子配置
0x08088504: r0 = 0x0859AA5C       ; 任务标题表
0x08088518: r0 = 0x0859D214       ; 任务说明表
0x0808852A: r0 = 0x0859E920       ; 任务提示表
0x0808854E: movs r6,#0x10         ; ★ 命中标志（arg0 != 0 的分支）
0x0808857C: ldrh r1,[0x0300000E]  ; 等 A（本帧新按下）
0x08088582: ands r0,#1
0x08088596: movs r6,#0x10
0x080885BA: bl 0x08067158(0x08009C4B)   ; 打开任务自己的菜单
0x080885C0: r5 = 0x0200A882
0x080885C2: ldrb r0,[r5]          ; 读完成标志
0x080885C8: r4 = 0x0200A880
0x080885CA: ldrb r1,[r4]          ; ★ 读答案（与剧情菜单同一个通道）★
0x080885CC: mov r8,r1             ; 返回值 = 答案
0x08088622: bl 0x0809C574         ; 等待跳板（菜单 UI 也调它）
```

**要点**：任务面板的菜单**不是** `fn 0x08095F58`（那个函数只有 3 个调用者：
`0x08091332` / `0x08091492` / `0x080979D0`），但它**读同一个作答通道**
`0x0200A880` / `0x0200A882`。所以代答点选在 **`0x080885C0`**（读完成标志之前）。

**可判死的检验**：断在 `0x080885C2`，读 `0x0200A882` 应为 1、
`0x0200A880` 应为 1（= 「开始战斗」），且 `fn 0x08088F10` 随后走
`r4 = 0x20` 分支。

## 6. 完整章节链（实测逐环命中）

```
场景 1（story branch 0）
  op 0x0B 条件位在 0x08097AC4 被补写 -> 进任务对话
  剧情菜单 op 0x05 -> 代答 row 1（「认识卡多」0x0800B849）
  op 0x1A 0x08097C6C 命中：state[0x16]=2, state[0x18]=1
  状态机 phase 0x30 (0x0808F8DC)
    -> 0x0808F904 读 state[0x18]==1 -> 0x0808F91E: phase = 0x100
  状态机 phase 0x100 (0x0808F928)
    -> fn 0x08088F10（章节初始化）
       -> fn 0x080884DC（任务面板）-> 代答 row 1 -> 返回 1
       -> r4 == 0x20 -> 0x08089008（关卡战斗入口）
          -> bl 0x08075184（战斗前准备）
          -> bl 0x0807509C  ★ 关卡模式战斗设置 ★
             -> 0x08080EF0 / 0x08080FA0 / 0x08080F18
                （对象描述符表 0x0853F140 / 单位重映射 0x0853F298 的读者区段）
```

**注意**：关卡模式的战斗入口是 **`fn 0x0807509C`**，不是剧情战斗的
`fn 0x080732B4`。两者共用 `bl 0x08075184`（战斗前准备）。

## 7. 任务面板的表读数（`mission-text` 的 L3 证据）

`fn 0x080884DC`（任务面板）在显示任务时读四张表，下面的地址是**游戏自己的
读表指令**，读数由探针在命中那一刻 dump 出来：

| 读表指令 | 表 | 命中时寄存器 | 运行时读数 |
|---|---|---|---|
| `0x08088500` | **任务索引表 `0x08348DAC`**（56 场 × 3 条 u8） | `r0 = 0x08348DAE`（= 基址 + 2） | `00 00 03 06 09 0c 0f 12 15 18 1b 1e 21 …` —— **步长 3** 的等差数列；`r4 = 1`（读出的任务号） |
| `0x0808850C` | 任务标题表 `0x0859AA5C` | `r0 = 0x0859AA68`（= 基址 + 12） | u32 指针 `bc a1 59 08 b8 a1 59 08 …` |
| `0x0808851C` | 任务说明表 `0x0859D214` | `r0 = 0x0859D220` | u32 指针 `20 ac 59 08 1c ac 59 08 …` |
| `0x0808852E` | 任务提示表 `0x0859E920` | `r0 = 0x0859E920` | u32 指针 `d8 d3 59 08 d4 d3 59 08 …` |

复现命令：

```
python tools/mgba_probe/chapter_route.py rom/base.gba \
    --scene 1 --branch 0 --cond 2 --force-row 1 --force-mission 1 \
    --keys A --presses 2000 --lean --json build/chapter-mission-text.json
```

同一轮里命中的站点（完整章节链，逐环可见）：

```
0x08097C6C op 0x1A      0x0808F904 读 state[0x18]   0x0808F91E phase=0x100
0x0808F928 phase 0x100   0x08088F10 章节初始化      0x08088F9A 问任务面板
0x080884DC 任务面板      0x0808857C 等 A            0x080885BA 开菜单
0x080885C0 读答案        0x08088622 等待循环        0x08089008 r4==0x20
0x0808A490 战斗标志      0x08075184 战斗前准备      0x0807509C 关卡战斗设置
```

**边界声明**：这条路线用 A 键正常推进剧情，但两个菜单是**代答**的
（`0x0200A880` / `0x0200A882`，理由见 §1–§2），
所以它证明的是「**任务面板的读表指令执行了，并把 ROM 里的真实字节读了出来**」，
不宣称「正常游玩会打开这两个菜单」。

| `build/probe_timeline.py` | 把探针 JSON 汇成事件时间线 |
| `build/probe_lit32.py` | 全 ROM 扫 32 位立即数出现位置 |

> 方法要点：**不要只信 capstone 的分支解码**。本 ROM 上 capstone 把
> `0x080960BE` 附近的 `bl` 目标算错过一次（手译时我把第二半字的
> `J1/J2` 位位序搞反了，`imm11` 看成 1365 实为 725）。
> 可靠做法：读原始半字 → 自己按 `S:I1:I2:imm10:imm11:'0'` 解码 →
> 再用 `probe_bl.py` 与 capstone 交叉核对。
>
> 另一个教训：`probe_callers.py` 用 capstone 找调用者，
> 漏掉了「通过函数指针调用」和「根本没有调用者」两种情况的区别。
> 判定死代码要用 `probe_blscan.py`（原始半字全 ROM 扫描）**加** 32 位指针扫描。
