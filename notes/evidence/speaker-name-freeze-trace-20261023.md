## 0. 一句话结论（本轮已定位到具体指令）

**CPU 不是「卡在渲染器拿着坏指针」，而是死在剧情 VM 的 op 0x08 处理器里那条补出来的
填充指令 `nop`（`0xBF00`）上 —— `0xBF00` 在 ARMv4T（GBA 的 ARM7TDMI）上是
**未定义指令**，不是 NOP。**

- 转换版 `0x08097A14` = `00 bf`（`nop`）→ 一执行就抛 **Undefined Instruction 异常**
  （CPSR mode = `0x1B`）；
- mGBA 的 BIOS 异常处理程序会**回到出错的指令**，于是同一条指令再次出错
  ⇒ **4 条指令的死循环**：
  ```
  0x00000008   BIOS 未定义指令向量 (ARM, mode=0x1B, sp=0)
  0x000001A8   BIOS 异常返回
  0x08097A14   op 0x08 handler 的 0xBF00  <-- 出错点
  0x08097A16   adds r0, r6, #0
  → 0x00000008（再次异常）→ 无限循环
  ```
- **14 处补丁全部以 `nop` 结尾**（见 §3.3）⇒ 每一个被补丁过的取名读者，
  **只要被执行到就会立刻炸**。#12（op 0x08）只是这段剧情里**最先被执行到**的那一个
  ⇒ 这解释了上一轮二分「只有 #13 有可观测影响」的表象：**不是 #13 特殊，是它跑得最早**。
- 修法：把 14 处补丁末尾的 `0xBF00` 换成一条 **ARMv4T 合法、且不改标志位**的 Thumb 指令
  （推荐 `0x46C0` = `mov r8, r8`）。**长度不变（2 字节），不用挪任何代码。**
- **✅ 已实测验证**（§4.1）：只把这 14 个 `0xBF00` 换成 `0x46C0`，别的什么都不动 ——
  **转换版从「卡死（画面恒为 `fa4fd7206ccc`）」变成「能跑（按 14 次 A，画面变化 13 步，全程不冻结）」。**

> ⚠️ 本报告是**增量写**的：第 1 条查完写一条，后面的章节随时可能被补进去。

## 1. 判定口径（沿用上一轮，已复核有效）

- **判定「能跑 / 卡死」只看画面是否还推进**：每按一次 A 截一张 mGBA 渲染缓冲（`rawshot`），
  比相邻两张的哈希；**最后 3 张相同 ⇒ 卡死**。
- 判定用的运行**只挂一个永远不会命中的断点** `0x08FFFFFE`（它只是把 `frames` 逼到
  mGBA 的调试器路径 —— 快速路径在「等输入」时会永不返回，原版 ROM 也一样）。
- 辅助断点**只用来取寄存器快照，不参与判定**。
- 「`0x08097A1C` 永远不命中 ⇒ 渲染器拿着坏指针」是 **mGBA 调试器假象**，
  **原版 ROM 上同样不命中**（上一轮 §1.1）。

## 3. 三个待查问题的答案

### 3.1 「第二次解引用是谁做的？」—— **没有人做第二次解引用**

- 渲染器 `0x0806626C`（文本绘制）**逐字节**读字符串：
  ```
  0x0806627A  adds r2, r1, #0      ; r2 = 字符串首地址
  0x0806627E  ldrb r0, [r2]        ; 逐字节读
  0x08066280  lsls r0, r0, #0x18
  0x08066282  lsrs r1, r0, #0x18
  0x08066284  cmp  r1, #0x1f       ; >0x1f 才是普通字符
  ```
  ⇒ **渲染器不把 r1 当「指向指针」**，它把 r1 直接当字符串首地址。
- 原版语义：`r1 = 0x085A57C4 + id*12` = **内联槽（字形码）的地址**；
  转换版语义：`r1 = *(0x085A57C4 + id*4)` = **串池条目的地址**。
  **两者对渲染器是同一种东西（字符地址）⇒ 补丁的语义是对的。**
- 上一轮看到的「解引用链」`0x085A5874 → 0x085DFCD6 → 0x0079E999 → 0x301C301C → 0x1C301C30`
  **不是游戏在解引用**，而是 **mGBA 调试器把同一条 `ldr r1,[r1]` 反复执行**：
  mGBA 的断点是**软件断点**（它把指令原地改成 `BE00: bkpt`），
  每次命中后恢复原指令再执行一遍，r1 就多解一层。
  ⇒ **那条链是观测假象，不能当作「游戏多解了一层」的证据。**

### 3.2 「CPU 是不是进了 ARM 状态？」—— **处理器里是 Thumb；ARM 状态是异常入口造成的**

- op 0x08 handler 入口（`0x080979E8`）实测 CPSR = `0x3F`/`0x2000003F` ⇒ **T=1（Thumb）**。
- 冻结现场的 T=0 是**异常入口**的结果（ARM 异常一定切到 ARM 状态），不是「Thumb 掉进 ARM」。
- 但**「`0xBF00` 会被解成 ARM 的 `udf`」这个猜测方向是对的、只是反过来了**：
  真正的事实是 —— **在 ARMv4T 的 Thumb 状态里，`0xBFxx` 本身就是未定义指令**
  （`NOP/YIELD/WFE/WFI/SEV` 这些 hint 指令是 ARMv5T 才有的）。
  GBA 的 CPU 是 ARM7TDMI = ARMv4T ⇒ `0xBF00` 直接抛 **Undefined Instruction**。
  mGBA 自己的反汇编器在 `0x08097A14` 打出来的就是 **`BF00: ill`**。

### 3.3 「`lr = 0x08097A16` 是怎么来的？」—— **异常入口的返回地址，不是 `bl`**

- Thumb 的未定义指令异常：`LR = 出错指令地址 + 2`。
- 出错指令在 `0x08097A14`（那条 `nop`）⇒ `LR = 0x08097A16` ✔ **完全吻合**
  （断点 `0x08097A14` 的首次命中快照里 `lr` 就是 `0x08097A16`）。
- （上一轮猜「有一条 `bl` 在 `0x08097A14`」不成立：那一格在两版里都不是 `bl`；
  handler 里真正的 `bl` 是 `0x08097A18` → `bl 0x0806626C`，它把 `lr` 设成 `0x08097A1C`。）
- 同一份 `lr` 也解释了为什么两次断点运行里 `lr` 恒为 `0x08097A16`：它是被异常入口
  写进去的常数，与游戏逻辑无关。

### 3.4 「`sp` 何时变成 0」—— **在异常入口就被换成 0（Undefined 模式的 SP）**

- 冻结现场 `sp = 0x00000000` 且 mode = `0x1B`（Undefined）⇒ 这是**异常模式下的
  banked SP**（SP_und），**不是用户栈**。
- 用户模式的栈在冻结前后一直是 `0x030011F8`（正常）—— 单步显示：异常入口时 `sp` 变成 0，
  异常返回后立刻恢复成 `0x030011F8`。
- ⇒ **`sp = 0` 是 mGBA 的 BIOS 异常处理程序在 SP=0 的情况下跑**（它把寄存器压到
  `0xFFFFFFE0` 一带的无效地址），**不是游戏把栈写坏了**。
- 顺带排除：冻结时 `0x03007FF8`（BIOS irq flags）= `0x00000001`、`0x03007FFC`
  （用户 irq 入口）= `0x0300007C`、游戏自己的 irq 处理程序 `0x03000080` 的机器码
  **与原版 ROM 逐字节相同** ⇒ **中断向量、BIOS 区、游戏的中断处理程序都没被破坏**。

### 4.0 ✅ 实测结论：只改 `nop` 就够了（**病灶确认**）

对照实验（`build/trace_fixnop.py` 与工具的 `--fix-nop`，
**只**把 14 处补丁末尾的 `00 bf` 换成 `c0 46`，其它一个字节都不动）：

（工具输出：`build/trace_fixnop_report.json` / `.md`，
`sp-bisect-all.gba: 卡死 变化 6 步 冻结 6` / `trace_fixnop.gba: 能跑 变化 13 步 冻结 None`）

⇒ **「`0xBF00` 在 ARMv4T 上是未定义指令」这一条已被实测证实**：
把它换成合法指令，卡死立刻消失。
⇒ **同时也证明：指针表布局、串池、12 个字面量、渲染器语义都不是病灶。**

### 4.1 主修法：把 14 处补丁末尾的 `nop` 换掉

- **症状**：`0xBF00` 在 ARMv4T 上是未定义指令 ⇒ 每次执行到被补丁过的取名读者就抛
  Undefined Instruction ⇒ BIOS 异常处理程序回到同一条指令 ⇒ 死循环 ⇒ 画面冻结。
- **改法**：14 处补丁 `after_hex` 的**最后 2 字节**（`00 bf`）换成
  **`c0 46`（`0x46C0` = `mov r8, r8`）**：
  - 是 ARMv4T 合法的 Thumb 高寄存器 MOV；
  - **不写任何标志位**（原指令末尾是 `adds`，会写标志；补丁后原本就没有写标志的指令，
    用不写标志的填充最保险）；
  - **不改变任何寄存器的值**（r8 写回自己）；
  - **长度不变（2 字节）** ⇒ 不用挪动任何后续代码，12 处字面量地址也不用动。
- **适用范围**：14 处**全部**要改，不能只改 #12 —— 其余 13 处只要被执行到就会同样炸。
- 备选填充：`0x0000`（`movs r0,r0`，**会写标志**）、`0x46C0`（**推荐**）、`0xBF00`（**禁用**）。
- 填充指令的编码已双向核对：**capstone 与 mGBA 自己的反汇编器都把 `0x46C0` 解成
  `mov r8, r8`**（mGBA 对 `0xBF00` 打印的是 `ill`）⇒ 它在 ARMv4T 上合法、
  **不写标志位**、**不改变任何寄存器的值**。
- **落地位置（本轮无权限改，留给改这些文件的人）**：
  - `tools/data/speaker_name_code_patches.json` 里 14 处 `after_hex` 的**最后 2 字节**
    （`00bf` → `c046`）；
  - `rom-editor/js/rom.js::applyInlineToPointer()` 里生成这 14 段补丁字节的代码
    （填充指令不能写死成 `0xBF00`）；
  - 门禁 `rom-editor/tools/verify_speaker_conversion.mjs` 应当加一条断言：
    **补丁窗口里不允许出现 `0xBF00`**（ARMv4T 未定义指令）。

### 4.2 顺带要核对的一件事（补丁语义，ledger U3）

原序列最后一条是 `adds rX, rX, rY`（**会写标志**），新序列最后一条是 `ldr`（**不写标志**），
标志位的「最后一次写入者」变了。好在两版参与 `adds` 的量只差 `id*12` vs `id*4`，
和都是 `0x085A57C4 + 小数` ⇒ **N/Z/C/V 的取值都相同**（C 无进位、N=0、Z=0），
**实际不影响后续的条件分支**；但换填充指令时**不要再引入写标志的指令**。

### 4.3 修完之后还要验的东西（不在本轮范围）

- 12 处读者在**战斗消息 / 命令消息 / 战斗日志**等场景下也会被执行 ⇒ 修完 `nop` 后，
  那些场景要单独验（这一轮只跑到剧情开场的 op 0x08）。
- 指针表放在 `0x085A57C4`（旧名字表 footprint 内）**不要动**：本轮已证明
  「指针表占旧表地址」不是病灶（搬家后卡得一模一样）。

## 6. 方法学沉淀（mGBA 调试器的五个坑，下个会话别再踩）

| 坑 | 现象 | 正确做法 |
|---|---|---|
| **断点是软件断点** | mGBA 把目标指令原地改成 `BE00: bkpt`；命中后那条指令会被**再执行一遍**。上一轮据此得出的「r1 一层层多解」其实是**观测假象** | 命中后用 `next` **恰好单步一条**再重新挂断点（工具已改）；或读 ROM 原始字节自己解码 |
| **`trace N` 会追一整帧** | 死循环时一帧 ≈ 28 万条指令 ⇒ 输出巨大、Python 端内存暴涨、几分钟出不来 | 不要用 `trace`；直接读 ROM 文件 + capstone 解码当前指令（工具已改） |
| **死循环里一帧要跑满 2M 步上限** | 宿主 `host_main.c` 的 `FRAME_STEP_CAP = 2000000`：帧计数器不前进时放弃这一帧。冻结之后**每按一次 A 要 18 秒**（且挂了断点时更慢） | 一检测到冻结/死锁就**立刻停止按 A**（工具已加「冻结即停」与「死循环检测」） |
| **`Probe.send()` 的 token 会重复** | `story_vm_capture.Probe.send()` 的 token = 「命令文本 hash + stderr 行数」，而 stderr 行数是**异步更新**的 ⇒ 同样的命令文本可能拿到同一个 token ⇒ 上一次 `send()` 把本次 token 读走 ⇒ 下一次 `send()` **永远等不到 token（挂死）** | 工具内改用**全局自增序号**做 token（`speaker_freeze_trace.py::send()`） |
| **mGBA 的 `frame` 命令在死循环里不返回** | 「跑一帧」永远跑不完 ⇒ 每个按键多花 18 秒 | 不要发 `frame`；`frames` 命令结束时已经 `setKeys(core, 0)` 松开按键了 |

另外两个判定口径上的提醒：
- 「`0x08097A1C` 永远不命中 ⇒ 渲染器拿着坏指针」是**调试器假象**（原版同样不命中）。
- 断点**只用于取快照，不参与「能跑 / 卡死」的判定**；判定只看画面哈希。
