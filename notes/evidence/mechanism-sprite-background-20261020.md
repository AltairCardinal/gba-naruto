# 四个开放项的原生代码裁决（2026-10-20）

**对象**: T1 机关效果表 target 9/11 + type 5/6/7 落到哪条原版关卡脚本；
T2 精灵动作表 `0x25A8E5` 单字节 + 「一帧最多 32 片」；
T3 剧情底图 8bpp 条目的层叠关系；
T4 战场地图描述符的 metatile 容量 + 「没有 layer 1」的判据。

**ROM**: `rom/base.gba`，SHA-256 `1198ece781aaf629db1f0c6628b4f9f1849ecc4a2eac6a55d32748c2a459d05b`
（仓库根目录的原始汉化 ROM 与它逐字节相同 ⇒ 下面所有"ROM 损坏"都是**随 ROM 发货的**，
不是本仓库工具链引入的）。

**状态**: T1 全部闭合；T2-A 闭合（正确值 0xFF，可判死）、T2-B 闭合（真实上限 5 片）；
T3 主体闭合（tilemap 几何 / VRAM / 调色板 / 4bpp-8bpp 关系），仅剩「8bpp 是否走 256 色硬件 BG」
一个子问题未闭合；T4 全部闭合。

**方法**: 只用 `tools/consumer_locate.py`（机器生成的原生消费者索引 +
`notes/evidence/consumer-evidence.json`）、`tools/mechanism_map.py`（Capstone 反汇编 + CFG 走查）、
`tools/extract_tileset.py`（LZ77 解压 + 长度自证），以及**运行时 VRAM 转储**
（`notes/newgame-2160-vram.bin` 等，只读）。

## 1. T1 — 机关效果表：target 9 / target 11 / type 5-6-7

### 1.1 表与分派链（原生代码）

```
0x08081346: subs r0, r5, #1      ; r5 = target
0x08081348: cmp  r0, #0xc       ; target 必须 1..13
0x0808134a: bls  #0x0808134e
0x0808134c: b    #0x080814cc     ; 越界 → 通用端点
0x0808134e: lsls r0, r0, #2      ; (target-1)*4
0x08081350: ldr  r1, [pc, #0x14] ; = 0x0808136C（表基址）
0x08081354: ldr  r0, [r0]
0x08081356: mov  pc, r0          ; 尾调用到该 target 的分支
```

表内容（`0x0808136C` 起 13 项，索引 = target−1）：

```
index  0 (t1)  0x080813A0    index  7 (t8)  0x08081458
index  1 (t2)  0x080813B0    index  8 (t9)  0x080814CC   <- 通用空操作端点
index  2 (t3)  0x080813E4    index  9 (t10) 0x080814C0
index  3 (t4)  0x080813F4    index 10 (t11) 0x080814CC   <- 通用空操作端点
index  4 (t5)  0x08081404    index 11 (t12) 0x08081498
index  5 (t6)  0x08081438    index 12 (t13) 0x080814A8
index  6 (t7)  0x08081448
```

**两个"封闭性"事实**（都是可机械复核的）：

1. 表基址 `0x0808136C` 作为 u32 字面量在**整个 ROM 里只出现 1 次**（`0x08081368` 的字面量池）。
   ⇒ 只有 `0x080812DC` 这个分派器读这张表。
2. `0x080812DC` 的 Thumb `bl` 调用点**全 ROM 只有 1 个**：`0x08081AE0`，
   它位于拾取处理程序 `0x08081984` 内；而 `0x080815E4` 的第 4/5/6 项（记录 type 5/6/7）
   **全部指向 `0x08081984`**。

⇒ 任何 target 想进效果表，必须先经过 `0x08081984`。

### 1.2 target 9 —— 计数机关，**进不了效果表**

```
0x08081984: ldrh r0, [r7, #6]   ; r7 = 运行时物件槽，+6 = 配置的 target
0x08081986: cmp  r0, #9
0x08081988: beq  #0x0808198c    ; ← target 9 走计数分支
0x0808198a: b    #0x08081a8c    ; ← 其余 target 走通用分支 → 0x08081AE0 → 效果表
```

计数分支 `0x0808198C..0x08081A6A` 的原生行为：

```
0x080819A2: bl   #0x8061e88        ; 播 config[0] 的音乐
0x08081A08: bl   #0x80814fc        ; 按运行时物件类型取音效（3→0x6B 4→0x6A 6→0x75）
0x08081AAC: movs r0, #0x35 ; bl #0x8061e6c   ; 音效 0x35
0x08081B4 : bl   #0x8081084        ; 把这个物件从地图上移除
0x080819C4: movs r0, #0xed ; lsls r0, #2   ; 948
0x080819C8: adds  r5, r7, r0                ; 计数区 0x02026BC0
0x080819CA: adds  r1, r1, r5                ; 按单位标志 bit0 选 0x02026BC0 / 0x02026BC1
0x080819CC: ldrb  r0, [r1]
0x080819CE: adds  r0, #1
0x080819D0: strb  r0, [r1]                  ; 计数 +1
0x080819DA: ldr   r1, [pc, #0x4c]            ; 0x0200A88C
0x080819DC: ldrb  r0, [r5]
0x080819DE: str   r0, [r1]                  ; 计数另存一份到 0x0200A88C
0x080819E0: ldr   r0, [pc, #0x48]            ; 0x080016C3
0x080819E2: bl    #0x8067158                 ; 跑剧情 VM 脚本 0x080016C3（首字节 0x01 = 文本）
0x08081A06: adds  r1, r4, #0 ; adds r1, #0xce
0x08081A0A: ldrh  r0, [r1]
0x08081A0C: adds  r0, #0x19                 ; +25
0x08081A0E: strh  r0, [r1]                  ; 单位 +0xCE += 25
0x08081A44: ldr   r0, [pc, #0x30]            ; 0x08001725
0x08081A46: bl    #0x8067158                 ; 跑剧情 VM 脚本 0x08001725
```

**该分支里的全部 `bl` 目标**（机械枚举 `0x0808198C..0x08081A6B`）：
`0x08061E5C / 0x08061E6C / 0x08061E88 / 0x08067158 / 0x08081084 / 0x080814FC`
—— **没有 `0x0808A638`**。

⇒ 精确表述：target 9 **不跑**效果表那 13 套里的任何一条"原版关卡脚本"
（`0x0808A638`），它跑的是**两段剧情 VM 脚本**（`0x080016C3` 首字节 `0x01` = 文本、
`0x08001725` 首字节 `0x04`；`0x08067158` 按首字节查 14 项跳转表分派），
外加计数 +1 与单位 `+0xCE += 25`。

**结论**：target 9 = **收集计数型机关**（第三方叫"甘薯"）；它在效果表里的那一格
（`0x0808138C` → `0x080814CC`）是**不可达的死代码**。

**判死检验**：若 target 9 真能进效果表，则 `0x080812DC` 至少要有 2 个调用点，
或表基址 `0x0808136C` 至少要有 2 个字面量引用。两者都已机械复核为 1。

### 1.3 target 11 —— 空操作（不跑关卡脚本）

`0x08081394` 里存的就是 `0x080814CC`，而 `0x080814CC` 是**所有效果共用的收尾**：

```
0x080814CC: movs r0, #0
0x080814CE: bl   #0x806fd00        ; 关掉消息窗口
0x080814D2: adds  r0, r4, #0        ; r4 = config[0]（战场音乐/场景 id）
0x080814D4: bl   #0x8061e5c        ; 播 BGM
0x080814D8: b    #0x080814ea
0x080814EA: bl   #0x8064a48        ; 等按键
0x080814F4: add  sp, #0x18 ; pop {r4,r5} ; pop {r0} ; bx r0
```

它**不含** `bl 0x0808A638`（跑原版关卡脚本的那个调用），也不含任何
`ldrh r1, [pc, ...]` 取脚本指针的动作 ⇒ **target 11 不触发任何关卡脚本**，
效果就是"关窗 + 放战场 BGM + 等玩家确认"。

**数据侧佐证**：`tools/mechanism_map.py --stats` 扫 stage 1..46 × sub 0..2 的
165 条物件记录，target 分布为

```
type 5 机关宝箱   count=28  targets={1:2, 2:4, 3:2, 4:2, 5:6, 6:2, 7:2, 8:6, 12:1, 13:1}
type 7 剧情物件   count=63  targets={9:45, 10:18}
type 6 特殊机关   count=0
```

⇒ target 9 只与 type 7 同现（45 条），target 10 只与 type 7 同现（18 条），
**target 11 在原版里一次都没被使用**。

### 1.4 type 5 / 6 / 7 落到哪条原版关卡脚本

建立期分派表 `0x0806E868`（7 项，索引 = 记录 type−1）：

```

type 6 → 0x0806E8F8 : movs r0, #4 ; bl 0x08081024      → 运行时物件类型 4
```

## 2. T2 — 精灵动作表

### 2.1 结构（不变）

动作表在 ROM 文件 `0x596CCC`，`id*144 + action*16` 每项 4 个 u32
（frames / animations / gfx / palette），id 1..62 有效。原生消费者：

* `0x0806A826`：`adds r2, #0xc` → 取第 4 个指针（palette），`CpuFastSet` 拷 8 个字。
* `0x0807AF1C` / `0x0807AF64` / `0x0807AFA4` / `0x0807AFE4`：分别取 4 个指针。

帧描述符 = **20 字节一条拼块记录**（8 个 u16 字段：`tile, flags, x, y, w, h, scale_x, scale_y`
+ 4 字节尾巴），列表以一条 **4 字节终止符 `FF FF 00 00`** 结束
（u16 `tile` = `0xFFFF` + u16 `0x0000`）。

### 2.2 机械扫描结果（这是本节全部结论的依据）

对 id 1..62 × action 0..8 共 342 个有素材的动作、2674 个帧，按
"从 `frames` 起连续合法 ROM 指针的个数 = 帧数"取帧，再按 20 字节步长读拼块，
遇 `tile == 0xFFFF` 停：

```
BEFORE（ROM 原样）
  拼块数分布 : {1: 2561, 2: 70, 3: 26, 5: 16, 65: 1}      <- 第 65 片是失控读出来的垃圾
  终止符直方图: {'ffff0000': 2673, 'RUNAWAY': 1}
  最大 tile  : 64511 (0xFBFF)
  失控帧     : (id 26, action 2, frame 2)

AFTER（把文件 0x25A8E5 从 0xFB 改成 0xFF）
  拼块数分布 : {1: 2562, 2: 70, 3: 26, 5: 16}
  终止符直方图: {'ffff0000': 2674}                          <- 2674/2674 全部逐字节吻合
  最大 tile  : 768 (0x300)
  失控帧     : 无
```

坏帧的原始字节（ARM `0x0825A8D0` 起）：

```
0825A8D0  40 00 00 00 f0 ff c8 ff 20 00 40 00 00 01 00 01   拼块 0（合法）
0825A8E4  ff fb 00 00                                         终止符 ← 高字节被改成 0xFB
0825A8E8  60 00 00 00 f0 ff c8 ff 40 00 40 00 00 01 00 01   下一帧的拼块 0
```

### 2.3 T2-a 结论：`0x25A8E5` 必须是 `0xFF`

三条互相独立的理由：

1. **结构不变量**：全 ROM 2674 个帧的终止符里，2673 个逐字节等于 `FF FF 00 00`；
   唯一的例外正是这个字节。改回 `0xFF` 后 2674/2674 全部吻合，异常归零。
2. **取值域**：这个 u16 是**图块索引**（相对该 action 的 gfx 块）。合法拼块里
   出现过的最大 tile 索引是 **768**；`0xFBFF` = **64511**，超出 84 倍。
   任何"它是别的什么字段"的解释都必须自洽地产生 64511 这个值，没有这种结构。
3. **邻域一致**：终止符后两个字节已经是 `00 00`，与其它 2673 个终止符的
   后半段完全一致 ⇒ 只有 tile 的高字节被破坏。

**⇒ 正确值 = `0xFF`（一个字节的修复）。**

**尚未闭合的子问题（本轮未做）**：*游戏自己的*解析器是按 `tile == 0xFFFF`（u16）
判定终止，还是只判低字节 `0xFF`？这决定了这一帧在原版里到底会不会画错。
判死办法：在 `0x0807xxxx` 一带定位读拼块 `tile` 字段并比较的那条指令
（ROM 里没有任何 `cmp.w #0xFFFF`；`0xFFFF` 只以 u32 字面量出现在
`0x08063ECA / 0x0807504E / 0x080892A4 / 0x0808C752 / 0x0808C76C / 0x0808F494`
等处，需要逐个排除用途）。**这不影响"这个字节应该是 0xFF"的结论**，
只影响"原版运行时是否可见地出错"。

### 2.4 T2-b 结论：「一帧最多 32 片」不是 ROM 约束

* 每帧拼块数分布：**{1: 2562, 2: 70, 3: 26, 5: 16}**，**真实最大值 = 5**。
* **命中 32 的条目数 = 0**（一个都没有）。
* 唯一一个"看起来超过 32"的帧，是坏帧在缺终止符后失控读出来的（读满 65 片后
  被扫描上限截断），它不是真实数据。

⇒ 第三方的 32 是**扫描窗口**，不是 ROM 约束；用显式终止符解析时根本用不到它。

## 3. T3 — 剧情底图 8bpp 的层叠关系

### 3.1 原生加载器 `0x08088348`

```
0x08088372: ldr  r4, [pc, #0x4c]      ; r4 = 0x0859903C（剧情底图表）
0x08088374: lsls r5, r0, #4           ; r5 = bg_id * 16
0x0808837A: ldr  r0, [r0]             ; entry.gfx
0x0808837C: lsls r1, r2, #0xe         ; charblock * 0x4000
0x08088380: lsls r6, r6, #0x13        ; r6 = 0x06000000
0x08088384: bl   #0x809c0e8           ; LZ77UnCompVram(gfx → 0x06000000+cb*0x4000)
0x0808838C: ldr  r0, [r0]             ; entry.palette
0x08088390: lsls r1, r1, #0x13        ; r1 = 0x05000000
0x08088392: bl   #0x809c0e8           ; LZ77UnCompVram(palette → 0x05000000)
0x0808839A: ldr  r0, [r5]             ; entry.tilemap
0x0808839E: lsls r4, r1, #0xb         ; screenblock * 0x800
0x080883A4: bl   #0x809c0e8           ; LZ77UnCompVram(tilemap → 0x06000000+sb*0x800)
0x080883AA: ldrb r0, [r2, #0xc]       ; entry+0x0C 的 flags 字节
0x080883AC: cmp  r0, #0
0x080883AE: bne  #0x080883cc          ; flags != 0 → 8bpp 支路
0x080883B0: str  r0, [sp]             ; 4bpp：栈上放 u32 0x00000000
0x080883B2: ldr  r1, [pc, #0x10]       ; 0x06000280
0x080883B4: adds r1, r4, r1           ; + (screenblock<<11)
0x080883B6: ldr  r2, [pc, #0x10]       ; 0x01000160（CpuFastSet 控制字）
0x080883BA: bl   #0x809c0dc           ; CpuFastSet(src=sp, dst, ctrl)
...
0x080883CC: ldr  r0, [pc, #0x5c]       ; 0x001E001E
0x080883CE: str  r0, [sp]             ; 8bpp：栈上放 u32 0x001E001E
0x080883D0: ldr  r1, [pc, #0x5c]       ; 0x06000280
0x080883D8: bl   #0x809c0dc           ; CpuFastSet(src=sp, dst, ctrl)
0x080883E2: strh r0, [r1]             ; r1 = 0x05000000 → BG 调色板第 0 项 = 0（透明）
0x080883E4: ldr  r2, [pc, #0x50]       ; 0x0300004C（游戏自己的 DISPCNT 影子）
0x080883EA: lsls r0, r7               ; 0x100 << bg_index
0x080883F0: strh r0, [r2]             ; DISPCNT |= 0x100 << bg_index（开 BG）
0x080883F4: ldr  r5, [pc, #0x44]       ; 0x04000008 = REGBG0CNT
0x080883F6: adds r4, r0, r5           ; r4 = REGBG{arg1}CNT
0x080883FA: lsls r2, r0, #2           ; arg2 << 2  → 字符基块位
0x080883FE: lsls r3, r1, #8           ; arg3 << 8
0x08088408: ldrb r0, [r0, #0xc]       ; flags
0x0808840E: movs r0, #0x80 ; orrs r3, r0   ; 8bpp 时额外置位 0x80
0x08088414: ldr  r0, [sp, #8]         ; arg4（优先级等）
0x08088418: strh r0, [r4]             ; 写 REGBG{arg1}CNT
```

`0x809c0dc` / `0x809c0e8` 是 BIOS SVC 跳板：`svc #0x0C` = **CpuFastSet**、
`svc #0x12` = **LZ77UnCompVram**。

### 3.2 结论一：tilemap 尺寸是 **32×32**，不是 32×10

* 条目自带的 LZ77 tilemap 一律解压成 **320 项（640 字节）**。
* `CpuFastSet` 的目标地址是 `0x06000280 + (screenblock<<11)`，比 tilemap 起始地址
  `0x06000000 + (screenblock<<11)` 晚 **0x280 = 640 字节**，
  控制字 `0x01000160` = 固定源 + **0x160 = 352 个 32 位字 = 1408 字节**。
* 640 + 1408 = **2048 字节 = 1024 项 = 32×32**，正好填满一个 2 KB 的 BG 屏幕块。

⇒ **每张剧情底图 = 一张完整的 32×32 硬件 BG 图**：第 0..9 行是条目自带的 320 项，
第 10..31 行是被常数填充的地面。GTA 屏幕 240×160 = 30×20 图块，完全落在这张 32×32 图内。

**运行时实证**（只读 `notes/newgame-2160-vram.bin` / `notes/dialogue-*.vram.bin`）：
VRAM `0x06000000` 起逐字节等于 bg 9 的 tilemap（0,1,2,…,0x12D,0x1E,0x1E），
紧接着从 `0x06000280` 起 **连续 704 个 u16 全是 `0x001E`**，一直到 `0x06000800` 整。
⇒ 8bpp 填充常数 = tile **30**，4bpp 填充常数 = tile **0**（`0x00000000`）。

### 3.3 结论二：VRAM / 调色板占用

| 资源 | 去向 | 证据 |
|---|---|---|
| 图形 gfx | `0x06000000 + charblock*0x4000`（arg2） | `0x0808837C/0x08088384` |
| 调色板 | `0x05000000`（**BG 调色板 RAM，bank 0**，384 字节 = 192 色） | `0x08088390/0x08088392` |
| tilemap | `0x06000000 + screenblock*0x800` | `0x0808839E/0x080883A4` |
| BG 调色板第 0 项 | 清 0（色 0 透明） | `0x080883E2` |
| DISPCNT | 影子在 `0x0300004C`，开 `0x100 << bg_index` | `0x080883E4..0x080883F0` |
| BG 控制寄存器 | `REGBG{arg1}CNT` = arg4 \| (charblock<<2) \| (screenblock<<8) \| (8bpp ? 0x80 : 0) | `0x080883F4..0x08088418` |

### 3.4 结论三：4bpp 与 8bpp 是**互斥的替代品**，不是叠加层

* 两者**共用同一个加载器**、同一组 VRAM 槽位、**同一个调色板 bank 0**。
* 两者唯一的差别只有两处：填充常数（`0x00000000` vs `0x001E001E`）与
  BG 控制寄存器的 `0x80` 位。
* 表本身也把两者分开：flags 字节为 0 的 id 1..7 与 flags 字节为 1 的 id 9..13，
  **没有任何一条记录同时带 4bpp 与 8bpp 资源**。

⇒ 所谓"层叠关系"不是"4bpp 底图 + 8bpp 底图叠在一起"，而是
**"一个背景 BG（底图）+ 战场自己的 layer0/layer1"**：
剧情底图占一个硬件 BG，战场地图的 layer0/layer1 占另一个（`0x08069040` 那条路径
把地图层写进 WRAM `0x0201BE2C`，走的是软件/另一套 BG）。
两个 BG 之间的先后由 DISPCNT 的优先级位（BGxCNT bit0-1）决定，
本轮**没有**取到运行时 DISPCNT，故这一层的 Z 序**未闭合**。

### 3.5 工具修正

`tools/extract_tileset.py` 原来把 tilemap 当 32×10 铺开。现在改成：

* 按原生布局渲染 **32×32**（320 真实项 + 704 填充项）；
* 填充项用条目自己的 bpp 决定（4bpp → tile 0，8bpp → tile 30）；
* 跳过 id 14/15：它们的 flags 字（`0x083409D0` / `0x08342340`）不是 0/1，
  说明 `0x59903C + id*16` 这张表到 id 13 为止，id 14 起已经是**另一张表**。
  （原笔记把 14/15 记成"有效 id"是误判。）

### 3.6 T3 唯一未闭合的子问题

**8bpp 条目是否走 256 色的硬件 BG（BG2/BG3）？**

已证：加载器把 `arg3` 同时当作"tilemap 的 2 KB 块号"（`arg3<<11`）与
"BG 控制寄存器的 bit8-9"（`arg3<<8`）。BG2/BG3 的 bit8 才是"256 色模式"，
但对 BG0/BG1 这两位是未定义位；而已观察到的 4 个调用点里
`arg1`（BG 序号）分别是 0、0、1、3，`arg3` 是 0 或 1。
8bpp 的 bg 9 是在 `0x08091716` 被加载的，`arg1 = 0`（BG0）、`arg3 = 0`，
于是 `BG0CNT = 3 | (1<<2) | 0x80`，**bit8（256 色）没有置位**，
而 BG0 在硬件上不可能开 256 色。

**下一探针**：在 `0x08091716` 所在场景抓一次运行时 I/O（DISPCNT `0x04000000`、
BG0CNT `0x04000008`、BG1CNT `0x0400000A`、BG2CNT `0x0400000C`、BG3CNT `0x0400000E`），
看 8bpp 底图最终落在哪个 BG、是否开了 256 色。
工具侧已有 `tools/mgba_probe/`（只读使用）与 `notes/mgba-probe-runtime-20261020.md`；
本轮**未运行**（另一代理持有探针二进制）。

## 4. T4 — 战场地图描述符

### 4.1 表长：**47 条**（不是 8 条）

`0x0853D910` 起 32 字节/条，索引 = `arg0 & 0xFF`（`0x08069002/0x08069004`），
步长 `index<<5`（`0x08069044`）。

* **entry 0..46 全部自洽**（见 §4.3 的长度自证表）；
* entry 47 起是垃圾（`raw_width = 513`，指针落在 ROM 之外）。

⇒ `notes/battle-config-format.md` 里"8 valid entries (0–7)"是**旧误判**，本轮更正为 47。

### 4.2 T4-a：metatile 缓冲与容量

原生读法（`0x0806909E` 起）：

```
0x080690A4: ldr  r0, [r0]              ; entry+0x14 = metatile_ptr
0x080690A6: ldr  r1, [pc, #0x3c]       ; r1 = 0x0201DE2C
0x080690A8: bl   #0x809c0ec            ; LZ77UnCompWram(metatile → 0x0201DE2C)
```

条目步长（访问器 `0x08068F08`）：

```
0x08068F20: lsrs r0, r0, #0xc          ; metatile 序号
0x08068F38: lsls r0, r0, #3           ; 序号 * 8   ⇒ 每个 metatile 8 字节
0x08068F2C: ldrh r0, [r3]             ; 取出 4 个 u16 之一（2x2 图块）
```

⇒ metatile = **8 字节**（4 个 u16 GBA 图块描述符 = 2×2 图块）。

缓冲的两端都由**原生代码写过的其它结构**夹出：

```
0x0201BE2C  layer0 平面区起点（0x08069076 LZ77UnCompWram 目标）
0x0201BE2C + 0x1000 = 0x0201CE2C   layer1 平面区（0x08069096 adds r1,r4,r7，r7=0x1000）
0x0201DE2C  metatile 缓冲起点（0x080690A6）
0x02021E2C  地图格表起点（0x08080FC8 / 0x08080FD4 写入）
```

⇒ metatile 缓冲 = `0x0201DE2C .. 0x02021E2C` = **0x4000 = 16384 字节**
⇒ **容量 = 16384 / 8 = 2048 个 metatile**。

* 实测最大用量：entry 0 的 6160 字节 = **770 个 metatile**（占 37.6%）。
* 47 条记录的 metatile 解压长度**全部是 8 的整数倍**（自证条目大小）。

### 4.3 T4-b：「没有 layer 1」的判据

```
0x0806907A: adds r0, r5, #0 ; adds r0, #0x10
0x08069080: ldr  r2, [r0]        ; entry+0x10 = layer1_ptr
0x08069082: cmp  r2, #0
0x08069084: beq  #0x0806909e     ; ← NULL ⇒ 整个 layer 1 分支被跳过
0x08069086: ldrh r0, [r7]        ; 非 NULL：DISPCNT 影子 |= 0x200（多开一层 BG）
0x08069092: movs r7, #0x80 ; lsls r7, #5   ; 0x1000
0x08069096: adds r1, r4, r7      ; layer1 目标 = 0x0201BE2C + 0x1000
0x0806909A: bl   #0x809c0ec      ; LZ77UnCompWram(layer1 → 0x0201CE2C)
```

⇒ **判据 = `layer1_ptr` 是 NULL 指针（0）**。没有别的哨兵：
47 条里 14 条非空（entry 0,7,8,9,10,11,12,21,22,23,31,32,34,35），33 条为 0。

## 6. 本轮**没有**闭合的项（明确列出）

1. **T3 子问题**：8bpp 剧情底图最终用哪个硬件 BG、是否开 256 色
   （BGxCNT bit8）。下一步：抓 `0x04000000/08/0A/0C/0E` 的运行时值。
2. **T3 子问题**：剧情底图 BG 与战场地图 BG 之间的 Z 序（DISPCNT 优先级位）。
3. **T2 子问题**：游戏自身的拼块终止判定到底比 `tile == 0xFFFF` 还是只比低字节
   `0xFF`（决定坏帧在原版里是否可见地出错）。
   注意：这**不影响**"`0x25A8E5` 应为 `0xFF`"这一结论。
4. **T4**：metatile 缓冲容量 2048 是**由上下两块原生结构夹出来的上界**，
   而不是从一条显式的分配语句读出来的；本轮没有找到对该缓冲做
   `memset` / 显式分配的那条代码。
