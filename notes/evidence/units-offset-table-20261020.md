# `units` 偏移表语义定案 + 相邻新表发现（2026-10-21）

**一句话**：`0x53F298` 不是「角色 ID 表」，而是一张 **43 项的 u16 重映射表**；
它的值被 **加上一个运行时基址**（WRAM `0x0202CA24` 的 u16）后 **掩到 16 位**，
即一个 64 KB 窗口内的索引。
2026-07-11 笔记 `notes/units-unsafe-table-fix-20260711.md` 提出的
「若能证明它把读出的 u16 **加到某个基址上**」这条可证伪判据，本轮**被证实**。

附带发现：紧邻的 `0x53EE98` 是一张此前**完全没被登记**的活表 ——
**3 个原生读者、10 字节步长、15 条记录**。

---

## 1. 消费者（唯一读者）

`0x0853F298` 在整个 ROM 里只有**一处**字面量引用（`0x08080B5C` 的常量池）。
读者指令在 `0x08080B2C`，属于函数 **`0x08080B08`**（它与 `fn 0x08080814`
共用同一个常量池，所以旧的工具把读者归到 `0x08080814` 名下）。

```asm
08080B08  push   {r4, r5, lr}
08080B0A  sub    sp, #0x18
08080B0C  adds   r4, r0, #0            ; r4 = 对象
08080B0E  lsls   r1, r1, #0x18
08080B10  lsrs   r3, r1, #0x18         ; r3 = 入参 & 0xFF   （槽下标）
08080B12  ldr    r5, [pc, #0x40]       ; r5 = 0x0853F140     （86 项对象描述符表）
08080B14  ldr    r1, [r4, #4]          ; 对象 +0x04
08080B16  adds   r0, #0x90
08080B18  ldr    r0, [r0]              ; 全局 0x90
08080B1A  lsls   r0, r0, #3
08080B1C  adds   r1, r1, r0
08080B1E  lsls   r1, r1, #0x10
08080B20  asrs   r1, r1, #0x10         ; r1 = 对象 +0x04 的 16 位值
08080B22  str    r1, [sp]
08080B24  movs   r1, #8
08080B26  ldrsh  r0, [r4, r1]          ; 对象 +0x08
08080B28  str    r0, [sp, #4]
08080B2A  ldr    r2, [pc, #0x2c]       ; r2 = 0x0202CA24
08080B2C  ldr    r1, [pc, #0x2c]       ; r1 = 0x0853F298    ← 本表
08080B2E  lsls   r0, r3, #1            ; r0 = (入参 & 0xFF) * 2
08080B30  adds   r0, r0, r1            ; r0 = 0x0853F298 + 下标*2
08080B32  ldrh   r0, [r0]              ; V = 本表的 u16
08080B34  ldrh   r2, [r2]              ; B = WRAM 0x0202CA24 的 u16
08080B36  adds   r0, r0, r2            ; r0 = V + B
08080B38  lsls   r0, r0, #0x10
08080B3A  lsrs   r0, r0, #0x10         ; r0 = (V + B) & 0xFFFF
08080B3C  str    r0, [sp, #8]
08080B3E  ldr    r0, [pc, #0x20]       ; 0x0202CA26
08080B40  ldrb   r0, [r0]
08080B42  str    r0, [sp, #0xc]
```

函数把这 5 个字段（`sp+0` / `sp+4` / `sp+8` / `sp+0xC` …）组装成一个
**渲染参数结构**再交给下游。同一个函数还读 `0x0853F140`（86 项对象描述符表）
和对象的 `+0x90` / `+0x98` —— 所以这张表与「对象/精灵」是配套使用的。

### 判据的结论

| 判据（2026-07-11 笔记 §2.10 提出） | 结论 |
|---|---|
| 「把读出的 u16 **加到某个基址上**」？ | **是**：加的是 WRAM `0x0202CA24` 里的 u16（**运行时**值，不是 ROM 常量） |
| 「目标区间上界」？ | 结果被 `lsls #0x10 / lsrs #0x10` **掩回 16 位** ⇒ 目标落在**一个 64 KB 窗口**内，索引范围 0..0xFFFF |

> 因此这张表是**偏移表**（offset table），判定成立；
> 但**基址是运行时量**，所以「表值 + 固定常量 = 某个 ROM 地址」不成立，
> 写回仍然必须限制在**原生出现过的取值**内 —— 这一点 2026-07-11 的安全修正是对的。

## 2. 表的内容与真实边界

旧 bank 写的是「`0x53F298`，128 字节，`u16[64]`」。实测**这个框架横跨了三张不同的表**：

| 区段 | 范围 | 内容 | 归属 |
|---|---|---|---|
| A | `0x53F298`..`0x53F2EE`（**43 项 u16**） | `0,1,2,…,9,25,…,34,37,…,46,10,11,35,36,47,48,12,13,18,21,22,23,24` —— 恰好是 **{0..48} 去掉 {14,15,16,17,19,20}** 的一个**排列** | **本表**：单位 id → 内部槽位的**重映射** |
| B | `0x53F2EE`..`0x53F30E`（16 项 u16） | `65532,0,65530,4,65529,7,65528,9,65530,9,65532,7,65534,4,0,0`（= −4,0,−6,4,−7,7,−8,9,…，**有符号增量**） | **另一张表**，独立读者 `0x08080AE0` |
| C | `0x53F318` 起 | `0x08080C4D, 0x08080C5D, 0x08080C6D, …` —— 代码指针 | **第三张结构** |

⇒ 结论：
1. 表 A 是**重映射表**（不是连续的角色 ID 表），43 个槽位；
   6 个 id（14/15/16/17/19/20）**没有条目**。
2. 旧 bank 的「u16[64]」把 A、B、C 混成了一张 —— 必须拆开。
3. 取值域：表 A 的值域是 **0..48**；消费者按下标读
   `0x53F298 + (入参 & 0xFF) * 2`，**下标可达 255**，
   所以调用方传入的下标必须自己限制在 0..42（或由它自己的语义保证）。

### 可证伪判据

| # | 判据 | 怎样算被推翻 |
|---|---|---|
| U1 | `0x0853F298` 只被 `0x08080B2C` 一处字面量引用 | 在 ROM 里搜 u32 `0x0853F298`，命中数 ≠ 1（字面量池 `0x08080B5C` 之外的命中） |
| U2 | 消费者把表值**加**到 `0x0202CA24` 的 u16 | 反汇编 `0x08080B34..0x08080B3A` 不再是 `ldrh r2,[r2]` / `adds` / `lsls #0x10` / `lsrs #0x10` |
| U3 | 表 A 恰好 43 项，且是 {0..48}−{14,15,16,17,19,20} 的排列 | `0x53F298` 起第 44 个 u16（= `0x53F2EE`）不是 `65532`，或 43 项里出现重复值 |
| U4 | `0x53F2EE` 是**独立**表 | 读者 `0x08080AE0` 不存在（`consumer_locate.py --target 0x53F2EE` 的 consumers = 0） |
| U5 | `0x53EE98` 是 10 字节步长的活表 | `consumer_locate.py --target 0x53EE98` 的 consumers ≠ 3，或三处读者不都是 `idx*10` |

## 3. 附带发现：`0x53EE98` —— 一张此前完全没被登记的活表

`0x0853EE98` 有 **3 个原生读者**，三处都用 **10 字节步长**索引
（`lsls r0,r1,#2` → `adds r0,r0,r1` → `lsls r0,r0,#1` = `idx*10`）：

| 读者指令 | 所属函数 |
|---|---|
| `0x080806BA` | `fn 0x08080670` |
| `0x0808077E` | `fn 0x08080764` |
| `0x0808082E` | `fn 0x08080814` |

记录布局（5 个 u16，偏移 +0/+2/+4/+6/+8）：

| 偏移 | 值域（实测 15 条记录） | 作用 |
|---|---|---|
| +0 | `0` / `1` / `2` / `−1` | `−1` = **链表结束** |
| +2 | −28 .. +12 | 有符号量（坐标？） |
| +4 | −68 .. +5 | 有符号量（坐标？） |
| +6 | 0 / 1 / 2 | 类别 |
| +8 | 0 / 4 | `≠ 0` = 本次遍历结束；`= 0` = 续到下一条（`adds r4,#0xa`） |

实测 15 条记录（`0x53EE98`..`0x53EF2E`），第 15 条是 `ffff 0000 0000 0000 0000`（+0 = −1 收尾）。

> **注意**：`notes/evidence/consumer-evidence.json` 里**查不到** `0x0853EE98` ——
> 因为那份证据文件只存了 **54 张**表（审计关心的那些），
> 而字面量索引有 **18051** 个值、其中 **1196** 个是活的。
> **任何「哪个活字面量离这个地址近」的问题都必须查全量索引**，
> 否则候选集会被静默截断 —— 本轮第一遍调查就栽在这里。

## 4. 顺带收窄：`0x53F140` 对象描述符记录是**变长自描述**的

`0x53F140` 是 **86 项 u32 记录指针**（每项指向一条记录），而
`0x53F138` 起的前两项是**代码指针**（`0x080808BD` / `0x08080965`）——
所以整个数组是 **88 槽**（0x53F138..0x53F298），正好接上 `0x53F298` 的重映射表。
这解释了「旧框架横跨三张表」的第三张：`0x53F318` 起的代码指针表其实是
**对象描述符数组自己的尾段**（88 槽的最后几项），不是独立结构。

记录的**长度是可变的**（自描述）：前 12 个目标地址的间距是
`0xC, 0x1C, 0xC, 0x1C, 0xC, 0x1C, ...`，即 **12 或 28 字节**两种长度交替。
第 0 条记录（`0x0812F5B0`）的 12 字节是：

```
+0x00 u32  0x0812F598     （另一个指针）
+0x04 u16  0x0001
+0x06 u16  0x0000
+0x08 u16  0xFFFF
+0x0A u16  0x0000
+0x0C u32  0x0812F5B4     （下一条记录自己的地址）
```

⇒ 旧笔记「记录含 u32 指针 + 成组 u16 标志位」的方向对，但
**「11 个字」**的框架是错的：记录是变长的，边界由记录内部的自描述字段决定，
不是固定 11/12/16 字。字段的业务名仍未定，但**结构边界规则**已经收窄。

## 6. 仍然开放

1. `0x0202CA24` / `0x0202CA26` 这两个 WRAM 字到底是什么（**运行时**基址与标志）——
   需要一次运行时读数（本轮探针由另一条工作线占用，未做）。
2. 表 A 的 6 个缺失 id（14/15/16/17/19/20）对应哪些角色；
   以及「单位 id → 内部槽位」这个重映射的**业务含义**（为什么不是恒等）。
3. `0x53EE98` 的五个字段名（+2/+4 是不是坐标、+6/+8 的类别与终止语义）。
4. `0x53F140` 记录的自描述边界规则（12 / 28 字节交替的判定条件）与其字段名。
5. `sequel/content/units/bank.json` 仍写着「`0x53F298`，128 字节，`u16[64]`」——
   按本轮结论应当拆成三张表。**本轮没有改**：该 bank 与
   `tools/populate_bank_json.py` 的生成逻辑同源，改一处要一起改，
   留给 owner 统一处理（本轮不碰，避免与并行工作线冲突）。
