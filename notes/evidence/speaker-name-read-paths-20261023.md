## 3. 算址路径污点分析（S6）——怎么算的

这是唯一一条**不依赖「基址必须是 `0x085A57C4` 字面量」**的搜索，所以它是专门用来证伪 U1 的。

### 3.1 抽象域

每个寄存器的抽象值是一组**仿射形式**：

```
form = (C, d, S, v, w)      值 = C + d + S * U_v ,   U_v ∈ [0, 2^w - 1]
```

- `C`：锚点常量（字面量基址等）；`C == 0` 表示「没有已知基址」
- `d`：相对 `C` 的偏移
- `S`：步长（`S == 0` ⇒ 值是精确常量 `C + d`；`S > 0` ⇒ 值里含一个未知下标）
- `v`：未知量的来源编号（同一个未知量在不同指令间保持同一编号）
- `w`：未知下标的**位宽**（`ldrb` ⇒ 8 位、`ldrh` ⇒ 16 位、调用返回值 ⇒ 32 位）

命中判据：形式 `C + d + S*U` 在 `0 ≤ U ≤ 2^w-1`（且 `U ≤ 4096`）时能落进 `[0x085A57C4, 0x085A5AB8)`。
位宽这一项很关键：它把「别的表 + 字节下标」这类假阳性自动排掉（见 §3.4）。

### 3.2 分析方式

- **函数级、流敏感**：对每个含锚点字面量的函数，从函数入口出发做前向数据流（工作列表 + 状态合并，到不动点）。
- 入口参数 `r0..r7` 记为 32 位未知量；`bl` 之后 `r0` 记为 32 位未知（返回值）。
- 跳表 handler（VM 的 `op` handler、UI 状态机分支）不是 `bl` 目标，DFS 走不到 ⇒ 对「函数内未被走到的连续段」额外从段首再跑一遍。
- 三种记录：**算址点**（某个寄存器第一次形成能落进区域的形式）、**读点**（以该形式做访存基址）、**实参逃逸**（该形式作为 `bl` 的 r0..r3 实参传出）。

### 3.3 命中结果

- 窄窗口（±4 KB，38 个锚点字面量、24 个函数）：命中 **38 条路径 / 26 个站点**
  - 13 个 A 类（`0x085A57C4 + 12*U`）= 12 个读者里的 13 处算址点（读者 8、12 各 2 处）
  - 25 个 B 类（地址精确落在区内）= 12 个 `ldr` 字面量载入点 + 读者 7 循环里常量折叠出的 10+ 个具体槽地址
- 宽窗口复查（±64 KB，151 个不同常量 / 335 个站点）：命中 3 条，**其中 A/B 类相对窄窗口新增 0 条**

### 3.4 人工核验过的假阳性（3 条，都已排除）

| 站点 | 形式 | 人工核验结论 |
|---|---|---|
| `0x0808B006` | `0x085A1530 + 8*U` | 别的表（步长 8）。下标是 `ldrb r0,[r6,#3]` ⇒ 0..255，最大只爬到 `0x085A1D08`，离区域差 46 KB |
| `0x0808B118` | `0x085A1560 + 6*U` | 别的表（步长 6）。下标 `ldrb r1,[r6,#0xd]` ⇒ 0..255，最大到 `0x085A1B12` |
| `0x0809615A` | `0x085A4DEC + 8*U` | 别的表（步长 8）。下标是函数参数，代码用 `<<24 >>24` 截成 1 字节 ⇒ 0..255，最大到 `0x085A55C4`，**仍在区域下方 0x1F8 字节** |

## 4. 「说话人全名表」3 个读者的核实（`0x085A5AB8` 是不是「说话人 id 63」？）

**结论：地址上确实是「旧表 id 63 的位置」，但语义上不是 id 63。**

| 项 | 值 |
|---|---|
| 旧 12 字节表 id 62 槽地址 | `0x085A5AAC` |
| 旧 12 字节表 id 63 槽地址 | `0x085A5AB8` ← **恰好等于全名表基址** |
| 全名表第 0 条地址 | `0x085A5AB8` |
| 旧表 id 0 字节 | `92 59 9a 9a 00 00 …`（「没有」） |
| 旧表 id 62 字节 | `88 b4 89 5d 00 00 …` |
| 全名表第 0 条字节 | `92 59 9a 9a 00 00 …`（与旧表 id 0 相同） |

- 旧表真实条目是 **id 0..62（63 条）**，**没有 id 63**；`0x085A5AB8` 上的字节属于**全名表第 0 条**。
- 两张表「首尾相接」：旧表最后一条（id 62）结束于 `0x085A5AB7`，全名表从 `0x085A5AB8` 开始。内容相同是巧合（两张表第 0 条都是「没有」），**不是**「同一个说话人」。
- 三个读者的步长都是 **19 字节**（`0x0808B036` 处：`id*4 → +id = id*5 → *4 = id*20 → -id = id*19`；
  `0x080939D6` 同一算法；`0x08077EE2` 用预置的 `sl = 4*id` 写成 `(id + sl)*4 - id = 19*id`）。
- **关键**：这 3 个读者的地址 = `0x085A5AB8 + 19*id`，`id ≥ 0` ⇒ 地址 **≥ 区域末端**，**永远不会读进旧槽区**，因此它们**不需要**被 14 处补丁改动，也不构成 U1。

### 5.2 解码器的可信度（这一步不能省）

自写解码器的位域划分（ARMv4T）全部按 capstone 逐槽核对过。**2 760 199 个可解槽中只剩 5 类不一致，全部是 ARMv4T 与 ARMv7 的语义差异**（GBA 是 ARM7TDMI＝ARMv4T，必须以 ARMv4T 为准）：

| capstone（ARMv7） | 数量 | ARMv4T 实际语义（本探针采用） |
|---|---|---|
| `cmp` | 5 172 | `010001 01` = **SUB (reg) T2**（ARMv4T 里高位寄存器 CMP 尚不存在） |
| `orrs` | 4 066 | `010000 1100` = **MUL** |
| `muls` | 2 058 | `010000 1101` = **MLA** |
| `bics` | 1 628 | `010000 1110` = **NEG** |
| `add` | 1 503 | 映射表缺 `add sp,#imm`（非解码错误） |

调试过程中被这套校验抓出来、随后修正的**真实解码错误**（记录在案，避免以后重犯）：

1. `0001101` 被我当成 `ADD (imm3)`，实际是 **`SUB (reg) T1`**（全名表读者 `0x0808B034` 的 `subs r0,r0,r1` 因此解错）。
2. `011xxxxx` / `1000xxxx` / `1001xxxx` / `1010xxxx` 四组的 `g5` 区间整体差 2（`0x6000/0x8000/0x9000/0xA000` 的边界）。
3. `1100xxxx`/`1101xxxx`/`11100xxx`/`11101xxx` 四组的区间同样差 2。
4. SP 相对读写的 `STR`/`LDR` 判反（`b` 应用 `bits12:11`，我误用了 `bits11:10`）。
5. 高位寄存器 `ADD/SUB (reg) T2` 的操作数位序：ARMv4T 是 **2 操作数**形式 `Rd = Rd op Rn`（`Rn` = bits 6:3，4 位），不是 3 操作数形式 —— 第三个全名表读者 `0x08077EE2` 的 `add r0,sl` 正是这一形态。

### 5.3 污点分析的局限（明确写出来）

1. **锚点窗口**：只有**字面量常量**落在 `[0x085A47C4, 0x085A67C4]`（窄）或 `±64 KB`（宽）内时才会被跟踪成锚点。
   理论上「基址在 64 KB 之外 + 一个大偏移」也能算到区域，静态无法覆盖；实际游戏里没有这种写法。
2. **跨函数参数传递未建模**：本分析不把「调用者把锚点传进被调函数」传播成被调函数的参数污点；
   只记录「区域地址被当作实参传出」这一逃逸（`arg` 类）。若某个读者是「被调函数内部用自己的基址算地址」，
   需要靠 E4（步长普查）而不是 E5 抓到 —— 事实上 E4 抓到了全部 14 处。
3. **内存模型只跟踪栈**：push/pop 的栈槽会跟踪；写到 RAM 全局/结构体的指针会丢失。
   ROM 数据里指向该区域的 u32 已全查（0 处），运行时才写进 RAM 的指针无法静态追（列为遗留风险）。
4. **抽象域是仿射 + 位宽**：非线性（`mul` 两个未知量相乘、`udiv` 等）一律降级为未知量；这会**漏报**而不是误报。
5. **假设未知下标 `U ≥ 0`**：负下标只会让地址更小。本报告里所有相关锚点都在区域下方或区域内，
   所以负下标只会离区域更远，不会漏掉读者。
6. **may 分析有假阳性**：本轮出现 3 条，已人工核验排除（§3.4），且现在能被位宽模型自动排除。
7. **函数归属是启发式**：跳表 handler 用「ROM 里指向代码区的 u32」识别；
   若某 handler 的入口既不是 `bl` 目标、也不以 u32 形式出现在 ROM 里，它会被并进外层函数 —— 
   对本次结论无影响（探针对「未被走到的连续段」会从段首重跑，覆盖了 VM handler 这类情形）。

### 5.4 这次没做的（留给下一步）

- 没有跑补丁后的 ROM 做动态验证（本次是纯静态普查）。
- 没有核对「指针表 + 串池」的**新表内容**（64 项指针 + 变长串池）是否正确生成 —— 
  既然读者侧已全覆盖，卡死更可能出在**新表内容**或**补丁本身的正确性**上。
- 没有核对 14 处补丁的寄存器活跃性（尤其 `variant D` 两处：基址在 r4/r5 里跨 `bl` 存活）。

**踩过的坑（写下来防止重犯）**：
- 抽象域里「未知量 + 锚点常量」相加时，锚点会掉进偏移字段里 —— 合并规则必须保证**非零的那个基址留在 C 字段**。
- `f_scale` 对**精确常量**左移时必须保持「精确」，否则常量会被当成「未知量 × 系数」。
- 32 位溢出必须显式处理（`lsls #24` 之后再 `lsrs #24` 这种符号扩展技巧会溢出），否则循环里的
  `r7 = r7 + 1` 会被算成错误常量，真实的「`基址 + 12*id`」路径就丢了（读者 7 就是这么丢的）。
