# 字形码反向映射：规范化码位的证明（2026-10-20）

**结论**：8 个字符各有两个码位，**编码器必须输出"基准段码位"**（GB2312 一级字表
按拼音序排列的那一段里的码位），而不是扩展段里的那个冗余码位。

**实现**：`tools/text_codec.py`（`EXTENSION_BLOCK_RANGES` +
`build_canonical_reverse_mapping()`）
**机器校验**：`tools/font_roundtrip.py`（24 项断言全通过）
**状态**：✅ 已证明 + 已强制

---

## 0. 一句话规则

> **一个字符用它在"基准段"里的码位编码。**
>
> 基准段 = 字形码空间中按 GB2312 一级字表拼音序排列的那一段（`0x889F..0x9CC3`）。
> 扩展段（`0x9873..0x989E` 与 `0x9CC4..0x9D3E`）是字库打包者补进去的生僻字；
> 其中 8 个字在基准段里本来就有，扩展段那一份是**冗余重复拼写**，不是规范码位。

---

## 1. 方法

1. **读字形段表**：文件偏移 `0x53D644`，31 槽 × 8 字节
   （u16 起始码 / u8 字数 / u32 字形偏移）。
2. **取码位→汉字映射**：`tools/konoha_font.py` 的 `build_mapping()`，
   段指纹 FNV-1a 26/26 全匹配，4261 个码位、0 个未解析。
3. **切分码位空间**：把 4410 个字形槽（4261 个有标签 + 149 个无标签）按码位排序，
   找出"哪些槽的字符是 GB2312 一级字表按拼音序"、哪些是"插进来的"。
   参考顺序用标准库的 `gb2312` 编码器枚举（**只作独立参照排序**，
   从不用它解码 ROM 文本 —— ROM 文本一律走 `tools/text_codec.py`）。
4. **统计游戏自身用码**：全 ROM 扫文本段（规则见 `notes/font-encoding.md` §2），
   统计每个码位出现在多少条文本里。

## 2. 码位空间的结构（本次新查明）

```
0x8140..0x889E   符号 / 假名 / 拉丁 块          418 个有标签
0x889F..0x9CC3   基准段：GB2312 一级字表拼音序   3754 个有标签
0x9873..0x989E   扩展段 A（插在基准段中间）      44 槽 / 39 个有标签
0x9CC4..0x9D3E   扩展段 B（接在基准段后面）     283 槽 / 50 个有标签 + 73 填充
```

要点：

* 基准段里 **GB2312 一级字表 3755 个字中有 3754 个按拼音序原样出现**，
  只有 **编**（U+7F16）不在基准段 —— 它被挪到了扩展段 B 的 `0x9CC4`。
* 基准段里 **旋**（U+65CB）的槽位上放的却是 **漩**（U+7019）。
* 扩展段 A/B 一共 89 个字，**除"编"以外全部不在 GB2312 一级字表里**
  —— 它们本来就是为生僻字补的。
* 扩展段 A 是**插进基准段中间的**：它把 `0x9840` 那一行（189 槽）从
  `0x9873` 处劈成两半（`0x9840..0x9872` + `0x989F..0x98FC`），
  段表因此多出一条从 `0x9873` 起的非行边界段（seg21）。
* 扩展段 B 溢出 `0x9C40` 那一行：seg25 计数 255 > 189。

> **注意**：先前一份"基础 GB2312 段槽位与 GB2312 预测完全一致"的说法**不成立** ——
> 基准段里至少有一处槽位被替换（旋→漩），而且段内有 18 个 `0x??7F` 的空槽
> （有字形、无标签）。真正成立的是"**基准段的字符按 GB2312 一级字表拼音序排列**"。

### 3.2 计数口径与假阳性

上表的"文本段数"用的是一条**机械可复算**的判据（`tools/font_roundtrip.py`
的 `scan_text_runs()`）：一段文本要同时满足

1. 至少 3 个字形码，且**全部**都能在映射表里查到；
2. 可见字符里 CJK/全角（含 `“ ” … 　`）占比 ≥ 70%。

第 2 条是必要的：`0x8CBF`（嘎）在全 ROM 有 14 次裸字节命中，
`0x9880`（嘎）有 34 次，但绝大多数落在 ARM 代码、指针表和
**ROM 自带的 GB2312 编码数据区**里（如 `0x4DDB00`、`0x4C0C90`）——
那些不是句子。唯一被口径误判的残余例子是 `0x335E46` 的
`孜杉1:f嘎`，CJK 占比 50%，已被第 2 条排除。

> **附带发现**：ROM 里除了字形码文本，**还有一段 GB2312 编码的中文数据**
> （例：`0x4DDB00` 起 `c8 f5 d3 d7 c0 eb ...` 解作 `弱幼离…排群…`）。
> 这解释了为什么"按字节对全 ROM 扫"会得到大量假命中。
> 该区域与字形码文本是两套东西，**不要**用字形码去解它。

### 3.3 字形位图不是判据

两套码位的 8×8 4bpp 位图**逐字节不同**（例如 `0x8A51` @ `0x0A4774`
与 `0x987B` @ `0x5AE900`），是同一字的不同栅格化。
在 8×8 分辨率下无法据此判断"哪个才是对的字"，
互为最近邻的位图距离检验也**不成立**（`0x8A51` 的最近邻是 `0x954E`「砂」，
距离 517，而它与自己那张 `0x987B` 的距离是 2301）。
**因此位图不作为判据**，判据只用"段结构 + 游戏自身用码"。

## 4. 规则（可机械套用）

> **规范码位 = 基准段码位。**
>
> 机械实现：
> 1. `EXTENSION_BLOCK_RANGES = ((0x9873, 0x989E), (0x9CC4, 0x9D3E))`
>    —— 两个生僻字扩展段；
> 2. 一个字符的候选码位里，**不属于**扩展段的那个就是规范码位；
> 3. 若一个字符的所有候选码位都在扩展段里（本次不存在），取其中最小者并上报。

8 个重复字符里，"基准段码位"与"最小码位"**恰好一致**（8/8）。
所以旧实现（`konoha_font.build_reverse_mapping()` 取最小码位）
**结果上没错，但理由是错的** —— 它是碰巧对的，不是被证明对的。
新的实现把理由固定下来，并且能被机器复核。

## 5. 可证伪检验（这条规则什么时候是错的）

以下任一条成立，规则即被推翻：

| 编号 | 证伪条件 | 当前实测 |
|---|---|---|
| **F1** | 从 ROM 重新推导结构时，基准段不再是 GB2312 一级字表拼音序（匹配数 < 3754，或缺失的不止 `编` 一个） | 3754 匹配，恰好缺 `编` |
| **F2** | 8 个字里有任何一个的**基准段码位数值大于**其扩展段码位 —— 此时"优先基准段"与"取最小"分道扬镳，基准段规则才是决定性证据 | 8/8 基准段码位都更小 |
| **F3** | 8 个字里有任何一个，扩展段码位是游戏文本中**用得更多**的那个，或是在基准段码位覆盖不到的场景里**唯一**被游戏使用的拼写 | 扩展段用量 4/27/2/2/4（吵/哼/吱/嘻/鸣）远低于基准段 35/237/32/3/456；摸/嘎/吨 为 0 |
| **F4** | 某个字的**基准段字形在 ROM 里是空白/缺失**，而扩展段字形存在 —— 此时基准段码位根本画不出这个字 | 16 个字形全部存在且非零（偏移见 §3 表） |
| **F5** | 存在第 9 个重复字符 | 4261 码位 → 4253 个不同字符 → 恰好 8 个重复 |

`tools/font_roundtrip.py` 把 F1/F3/F5 做成**每次运行都会执行**的断言；
F2/F4 属于一次性核查（见 §3 表）。

## 6. 实现与机器校验

### 6.1 `tools/text_codec.py`

* `EXTENSION_BLOCK_RANGES` —— 两个扩展段的码位区间。
* `is_extension_block_code(code)` —— 判定某码位是否落在扩展段。
* `build_canonical_reverse_mapping(mapping)` → `(char→code, report)`
  —— 规则实现；`report["duplicates"]` 给出每个重复字的候选码位、
  哪个是基准段、哪个是扩展段、选的是哪个。
* `canonical_mapping(mapping)` → 只保留规范码位的 code→char 表。
  把它交给 `konoha_font.encode_text()`，编码器自然就只会吐规范码位。
* `encode()` 改走 `canonical_mapping()`。
* `roundtrip_report()` —— 4261 个码位逐个往返自检。
* **公开 API 不变**：`load_mapping()` / `decode()` / `encode()` /
  `decode_bounded()` / `encode_tokens()` 签名与行为都兼容。

### 6.2 `tools/font_roundtrip.py`（24 项断言，失败即 exit 1）

| 断言 | 内容 |
|---|---|
| (a) | 4261 个码位**逐个** `decode(encode(char)) == char` → **4261/4261** |
| (b) | 反向映射无歧义：4253 个字符 → 4253 个互不相同的规范码位 |
| (c) | 每个重复字**恰好**一个基准段码位 + 一个扩展段码位；规范码位是基准段那个；旧"取最小"行为与规范规则**逐字一致** |
| (5) | 从 ROM **重新推导**扩展段，必须与 `text_codec.EXTENSION_BLOCK_RANGES` 推出的码位集合**完全相同**（89 个码位） |
| (5) | 基准段恰好缺 1 个 GB2312 一级字（`编`） |
| (3) | 62 个角色名用到的字符 100% 可编码 |

脚本会打印一张逐字证据表（基准段/扩展段码位 + 游戏文本用量），
最后打印 `checks passed` / `checks failed` 与 `RESULT: PASS|FAIL`，
**任何一条断言失败就以非零码退出**。

## 8. 遗留与边界

* **字节级一致性不是 100%**：8 个字里有 5 个（吵/哼/鸣/嘻/吱）**游戏自身
  两种拼写都在用**，所以"字符 → 码位"这种单值映射**在原理上无法**对它们
  做到 `encode(decode(bytes)) == bytes`。**改写已有文本必须走 token 流**
  （`text_codec.encode_tokens()`），它原样保留码位，字节级一致。
  纯字符串编码只适用于**全新文本**。
* `编` 被字库打包者挪到了扩展段 B（`0x9CC4`）—— 这是基准段唯一缺的一级字。
* `旋` 的槽位上放的是 `漩`（`0x9968`）—— 基准段唯一的槽位替换。
* 16×16 对话字形的来源仍未定位（见 `notes/font-encoding.md` §1.2），
  本文件的结论只涉及**码位**层，不涉及对话字形位图。
