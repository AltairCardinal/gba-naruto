## 1. 方法：把状态机的相位分派当「读者入口表」

剧情状态机 `fn 0x0808F73C`（循环头 `0x0808F752`）按 `state[0x12]`（u16 相位）分派。
**每个相位处理器都是一个薄包装，调用一个子系统** —— 而**好几张还没找到读者的表，
就是从这种处理器里被读的**。

对白指针表 `0x08461CE8` 是第一个例子：它**既没有字面量读者、也不在剧情对话路径上**，
但 `fn 0x080914D8`（它的读表准备函数）**只有两个调用者，都在相位分派里**
（相位 `0x0210`）。于是「找不到读者」变成了「找哪个相位会调它」。

**相位 → 处理器**（直接从分派代码读出）：

| 相位 | 处理器 | 相位 | 处理器 |
|---|---|---|---|
| `0x0000` | `0x0808F80E` | `0x0110` | `0x0808F92E` |
| `0x0010` | `0x0808F814` | `0x0118` | `0x0808F94A` |
| `0x0018` | `0x0808F872` | `0x0120` | `0x0808F9C0` |
| `0x0020` | `0x0808F892` | `0x0200` | `0x0808F9E2` |
| `0x0030` | `0x0808F8DC` | `0x0210` | `0x0808F9EC` |
| `0x0100` | `0x0808F928` | `0x0300` | `0x0808FA04` |
| `0x0700` | `0x0808FA26` | `0x1000` | `0x0808FA0A` |
| `0x1100` | `0x0808FA1C` | `0x8000` | `0x0808FA2C` |

**工具**：`tools/mgba_probe/phase_sweep.py` —— 逐个相位 poke `state[0x12]`、
按 A 键让状态机分派它、记录所有命中的读者点与表内容。

```
python tools/mgba_probe/phase_sweep.py rom/base.gba --json build/phase-sweep.json
```

## 3. 两条新 L2/L3 的运行时读数

### 3.1 `data-table-a`（`0x085A143C`）—— 相位 `0x0300`

相位 `0x0300` 的处理器 `0x0808FA04` 调 `fn 0x0808B58C`，它再调
`fn 0x0808A6AC`（`0x0808B5FE`），后者在 `0x0808A6BA` 装载表基址：

```
0x0808A6BA: ldr  r7, [0x085A143C]    ; ★ 表基址
0x0808A6BC: ldrb r0, [r6,#1]          ; 另一个表的字节
0x0808A6BE: bl   0x08068EA4
0x0808A6C4: lsls r2, r5, #0x10        ; 步长 16 字节
```

**命中时的寄存器**（相位 `0x0300`，20 次按键内 **40 次命中**）：

| 寄存器 | 值 |
|---|---|
| `r7` | **`0x085A143C`**（表基址 ✓） |
| `r0` | **1, 2, 3 …**（逐次递增的**下标** ✓） |
| `r1` | `0x00010000`（另一个表的字段） |
| `r3` | `0x020240AC` |
| `r4` | `0x02002880`（WRAM 暂存缓冲） |

命中瞬间 dump 出的表内容（`0x085A143C` 起 32 字节）：

```
88 f9 59 08  18 fa 59 08  bc fa 59 08  60 fb 59 08  0c fc 59 08  b0 fc 59 08
54 fd 59 08
```

**每 4 字节一个 u32 指针**（`0x0859F988` / `0x0859FA18` / `0x0859FABC` / …）。

### 3.2 `battle-encounters`（`0x0854229C`）—— 相位 `0x8000`

相位 `0x8000` 的处理器 `0x0808FA2C` 走 `fn 0x0808A69E` → `fn 0x08087C9C`，
它在 `0x08087D00` / `0x08087DE0` 装载表基址。

**命中时的寄存器**（相位 `0x8000`）：

| 寄存器 | 值 |
|---|---|
| `r0` | **`0x0854229C`**（表基址就在 r0 ✓） |
| `r1` | `0x0400000E` |
| `r2` | `0x0000030C` |
| `r3` | `0x00000003` |

命中瞬间 dump 出的表内容（`0x0854229C` 起 32 字节）：

```
50 ff 12 08  68 02 13 08  90 02 13 08  04 00 00 00  e8 03 13 08  30 0d 13 08
```

**混合表**：u32 代码指针（`0x0812FF50` / `0x08130268` / `0x08130290` / `0x081303E8` / …）

### 3.3 `data-table-b`（`0x085A2034`）—— 相位 `0x0000` / `0x0010` / `0x0700`

### 3.4 `function-pointers`（`0x0853D5F0`）—— 相位 `0x0110`（战斗相位）/ `0x0118`

`fn 0x08061DD4` 装载表基址（判定点 `0x08061DD6`）。
它在**战斗相位 `0x0110`** 与 `0x0118` 上都会跑到。

**命中时的寄存器**：

| 寄存器 | 值 |
|---|---|
| `r3` | **`0x0853D5F0`**（表基址 ✓） |
| `r0` | `0x0000004C`（**下标 76**） |
| `r2` | `0x00000098` |
| `r6` | `0x0806E959`（取到的**代码指针** ✓） |

命中瞬间 dump 出的表内容（`0x0853D5F0` 起 32 字节）：

```

```

`0x08061C8D` 起每槽 +12 字节等距」）。

### 3.5 `reward-table`（`0x0859EAE0`）—— 相位 `0x0120`

`fn 0x0808A0F0`（被相位 `0x0120` 的处理器 `0x0808F9C0` 调用）里有一个
按模式分派的 switch：`r4 == 0` → `bl 0x08089310`（奖励表读者，
判定点 `0x080893F2`），`r4 == 0x20` → `bl 0x08089E84`（另一个奖励表读者），
`r4 == 0x10` → 遍历 3 个槽（`fn 0x08089964` / `fn 0x08089AE0`）。

**命中时的寄存器**（相位 `0x0120`）：

| 寄存器 | 值 |
|---|---|
| `r2` | **`0x0859EAE0`**（表基址 ✓） |
| `r1` | `0x0000009C`（下标） |
| `r3` | `0x00000170` |
| `r7` | `0x00000003` |

命中瞬间 dump 出的表内容（`0x0859EAE0` 起 32 字节）：

```
c8 00  64 00  0a 00  00 01  00 25  01 04  02 19  02 1a  00 00
00 00  00 00  00 00  00 00  00 00  00 00  00 00  00 00
```

**每 2 字节一个 u16**（`0x00C8` / `0x0064` / `0x000A` / `0x0100` / `0x2500` / …），
与 `reward-table`「尾部字节是奖励类别标签、112 条」的既有描述一致。

### 3.6 一个必须记下来的教训：寄存器要在**每次 `frames` 之后立刻**捕获

第一次扫相位时，相位 `0x0120` 报了 40 次 `reward-table` 命中 ——
但用 pc 归属判据复核，**那些记录全是错位归档**。

**根因不是「按报告地址归档」，而是更基础的一条**：
工具先发两次 `frames`（一次按键、一次松手），**之后才捕获寄存器** ——
而第二次 `frames` 会把调试器推进到**下一个停靠**，
所以寄存器永远属于**最后一次停靠**，而不是这次报告的地址。

**修法**：
1. **每次 `frames` 之后立刻捕获**寄存器（不要把两次调用合并后再捕获）；
2. 再用 `|pc - addr| <= 4` 判定这条记录是不是真的属于该地址。

修完这一步，`phase_sweep.py` 的 40 条记录**全部变成真命中**，
`reward-table` 也就真的拿到了读数。

**这条同样适用于 `callback_census.py`** —— 它原来也是「两次 `frames` 后才捕获」，
只不过因为同一个断点会**反复重新命中**，所以大部分记录碰巧是对的；
已按同样方式修好（逐次 `frames` 立刻捕获 + pc 判据）。

## 4. 边界声明

* 进入这些相位需要 **poke `state[0x12]`**（等价于「请求这个相位」，
  与 L4 战斗矩阵请求一场战斗的三次内存写同型）。
* 这些相位在**自然流程**里由状态机自己设置（例如 `0x0210` 由「章节交接且
  目标场景为 52」产生）。本次是把那个请求直接写进去，省掉重跑整条剧情。
* 因此这批证据证明的是「**游戏自己的读表指令执行了，并把 ROM 里的真实字节
  读了出来**」；**不**宣称「任意一场战斗都会读这些表」。
