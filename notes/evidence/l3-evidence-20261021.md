## 2. 两个场景与按键配方

游戏只认**按下沿**（GBA 按键掩码 `0x0300000E`），所以配方是
**按住 8 帧 → 静默 120 帧**（这条配方在 `notes/evidence/l4-playthrough-20261021.md` §「按键配方」里已钉死）。

### 2.1 `battle` 场景

| 步骤 | 动作 | 说明 |
|---|---|---|
| 1 | `START` ×8 帧、`A` ×8 帧 ×4 | 走到剧情状态机循环头 `0x0808F752` |
| 2 | 三处内存写：`state[0x16]`←组号、`state[0x19]`←子配置号、`state[0x12]`←`0x0110` | **选**哪一场战斗（仓库已有的 L4 机制） |
| 3 | `A` ×8 帧 + 静默 120 帧，循环 40 轮 | 战斗开场，**全部靠正常按键** |
| 4 | `A` ×8 帧 + 静默 120 帧，再循环 6 轮 | 推进到战斗页 |

> 第 2 步是**选择**而不是**生效**：战斗一旦被选中，之后地图装载、单位实例化、
> 头像解包、规则表读取、音效播放全部是游戏自己的代码在跑，
> 推进它的每一个动作都是正常按键。
> 这条机制已被 `notes/evidence/l4-battle-matrix-20261021.md` 证明（85/85 战斗、47/47 地图）。

本轮用的是**组 1 / 子 0**：我方角色 id `1,2,3,31`，敌方 `25,26`。

### 2.2 `story` 场景

| 步骤 | 动作 |
|---|---|
| 1 | `START` ×8 帧、`A` ×8 帧 ×4（走到状态机） |
| 2 | 内存写 `state[0x16]`←54、`state[0x12]`←`0x0030`（分派剧情场景 54） |
| 3 | `A` ×8 帧 + 静默 120 帧 ×8（第一页对白） |
| 4 | `A` ×8 帧 + 静默 120 帧 ×4（下一页对白） |

画面截图：`notes/evidence/l3-story-scene54.png`（名牌「鳴人」+ 中文对白）。

## 3. 逐结构证据

> 所有数值都是**工具从运行中的模拟器读回来的**，不是静态表转述。
> 「表项」一栏是 ROM 里的字节，「运行时」一栏是模拟器内存里的读数。

### 3.1 `character-template`（`0x54241C` / `0x0854241C`，63 条 × `0xB4`）

* **场景**：battle
* **运行时**：`0x020240C0` 的战斗单位数组（12 槽，步长 `0x1D4`）
* **证据**：单位记录里 `+0x02..+0x07` 的 6 个字节，与角色模板表项 `+0x01..+0x06`
  **逐字节相等**——3 个 1 级队员（角色 id `1,2,3`）全部成立：

  | 角色 id | 运行时记录 `+0x02..+0x07` | ROM 模板 `+0x01..+0x06` | 相等 |
  |---|---|---|---|
  | 1 | `0e 0d 08 03 05 05` | `0e 0d 08 03 05 05` | ✅ |
  | 2 | `0c 08 0c 03 05 04` | `0c 08 0c 03 05 04` | ✅ |
  | 3 | `07 07 0a 03 06 03` | `07 07 0a 03 06 03` | ✅ |

* **限定**：敌方（id `25,26`）是**按等级缩放**的，所以它们的运行时字节不等于模板字节；
  本条结论只对 1 级队员成立，工具的判据也只对 `1,2,3` 取真值。
* **截图**：`notes/evidence/l3-intro.png`
* **可证伪检验**：把 `0x020240C0` 里某个 1 级队员的 `+0x03` 改掉，
  或把 ROM 里 `0x54241C + 1*0xB4 + 2` 的字节改掉，判据必须立刻失败。

### 3.2 `encounter-zones`（`0x53D910` / `0x0853D910`，47 条 × 32 字节）

* **场景**：battle（组 1）
* **运行时**：`state[0x17]`（`0x020311EB`）读回 **1**，即屏幕上那张地图的编号
* **表项**：`0x0853D930` = 基址 + 1×32，宽 `60` × 高 `30`（图块），
  `+0x04` 图形指针 `0x080BF318`（一个 LZ77 块），`+0x1C` 区域字节 `0x01`
* **证据**：该指针解出来的 10240 字节里，**前 1824 字节**与地图装载器写入的
  VRAM 窗口 `0x06004000` **逐字节相等**；该地图画面的 VRAM 指纹是
  `523ee80b500cdf056fdfca6c85f1b0d1b8e01f6f7864bcb1d43150232d38f4c3`
* **为什么只有前缀**：1824 字节之后 VRAM 里的图块已被游戏自己改写
  （逐组验证：组 9/14/5 的地形在 `0x06004000` 处连前 32 字节都对不上，
  差异处的字节呈明显的重排特征）。因此本条**只声明前缀**，不声明整块相等。
* **截图**：`notes/evidence/l3-intro.png`
* **可证伪检验**：改 `state[0x17]` 读出的地图号，或让别的地图号进来，
  描述符地址 / 图形指针 / VRAM 指纹三项必须一起变；反向对照见 §4。

### 3.3 `battle-rules`（`0x594758` / `0x08594758`，索引 `stage*0xCC + sub*0x44`）

* **场景**：battle（组 1 / 子 0）
* **表项**：`0x08594824` = 基址 + 1×`0xCC` + 0×`0x44`，**首字节 `0x0F`**
* **运行时**：战斗控制块 `0x02026804` 的 `ctrl[6]` = **`0x0F`**（回合上限）
* **证据**：整块控制块 `00 01 00 00 00 00 0f 00 01 00 00 00 00 00 00 00`
  —— `ctrl[1]`=组号 1、`ctrl[2]`=子配置 0、`ctrl[6]`=`0x0F`，
  与胜负条件表该条记录的首字节**逐位相等**
* **截图**：`notes/evidence/l3-intro.png`
* **可证伪检验**：换成组 9 / 子 0 重跑，`ctrl[6]` 必须跟着规则表那条记录的首字节变。

### 3.4 `cutscene-scripts`（`0x53DF70` / `0x0853DF70`，4 条 × 8 字节）

* **场景**：battle
* **表项**：第 0 条 = 图形指针 `0x0812D9E4` + 调色板指针 `0x0812DEE4`
* **运行时**：图形指针的 LZ77 载荷与模拟器 VRAM `0x06016000` 处的
  **4096 字节里前 4067 字节逐字节相等**；调色板指针的 LZ77 载荷
  （32 字节 = 16 × BGR555）与调色板 RAM `0x05000380` 处的 **32 字节完全相等**
* **为什么是 4067/4096**：最后一片图块（29 字节）随后被游戏自己改写；
  其余三个块（第 1/2/3 条）在 `0x06016000` 处**完全对不上**，
  所以「第 0 条」这个判定是能区分的，不是空转。
* **截图**：`notes/evidence/l3-intro.png`
* **可证伪检验**：改 ROM 里 `0x53DF70` 第 0 条的图形指针，判据必须失败。

### 3.5 `portrait-table`（`0x5A4DEC` / `0x085A4DEC`，`id*40 + expr*8`）

* **场景**：battle
* **表项**：`id = 1`、`表情 = 2` 的条目 → 拼块 0 = `0x0840A724`、拼块 1 = `0x0840B4F8`
* **运行时**：`0x0840A724` 的 LZ77 载荷与模拟器 OBJ VRAM 起始处
  `0x06010000` 的 **6400 字节完全相等**
* **看得见的结果**：`notes/evidence/l3-intro.png` 画面上方左侧那张脸
  就是 **角色 id 1（漩涡鸣人）**——`id=1` 的头像拼块被逐字节搬进了 OBJ VRAM，
  画出来的正是它
* **截图**：`notes/evidence/l3-intro.png`
* **可证伪检验**：改 ROM 里 `0x5A4DEC + 1*40 + 2*8` 的拼块 0 指针，判据必须失败。

### 3.6 `menu-ui`（`0x5A4DEC` / `0x085A4DEC`）

`menu-ui` 的旧基址 `0x5A5774` 已被裁决为**头像表的第 61..62 行**（不是独立的菜单 UI 表），
所以它的规范地址与 `portrait-table` 同址。证据与 §3.5 **同一条**
（头像拼块 `0x0840A724` → `0x06010000` 的 6400 字节完全相等）。
本条在审计里应当和 `portrait-table` 指向同一条动态证据，或直接标为别名。

### 3.7 `save-state`（`0x53D848` / `0x0853D848`，10 组 `{u32 wram, u32 size}`）

* **场景**：battle
* **表项**（节选）：第 5 组 = `0x02026804` / 8 字节；第 7 组 = `0x020240C0` / 6084 字节；
  第 0/1/3 组 = `0x02022E30` / 4732 字节
* **运行时**：战斗里**活着**的三块区域
  —— 战斗控制块 `0x02026804`、单位数组 `0x020240C0`、队员结构 `0x02022E34`
  —— **全部落在**这张 ROM 表预留的区间里（5 次命中，含重复区间）
* **含义**：这张表不是「存档描述符表」，而是**运行时的 WRAM 分配表**
  （与 `notes/completion-audit-20261020.md` 里 `save-state` 的裁决一致）。
  L3 的对应关系是：**ROM 表说哪些 WRAM 段会被用，运行时读回来那些段确实在被用**。
* **截图**：`notes/evidence/l3-intro.png`
* **可证伪检验**：把表里第 7 组的 wram 地址改成一个不在用的地址，判据必须失败。

### 3.8 `units`（`0x53F298` / `0x0853F298`，43 项 u16）

* **场景**：battle
* **表项**：43 个 u16（`{0..48}` 去掉 `{14,15,16,17,19,20}` 的排列），最大 48
* **运行时**：`0x0202CA24` 的 u16 = `0x0000`
* **证据**：消费者取「表值 + `0x0202CA24` 的 u16，掩到 16 位」；
  运行时这条加法读到 `0x0000`，于是目标集合 = 表里的 43 个值，
  而**战场上站着的每一个角色 id**（`1,2,3,31,25,26`）**都在这个集合里**
* **截图**：`notes/evidence/l3-intro.png`
* **可证伪检验**：改 `0x0202CA24` 的运行时值，目标集合随之平移；
  若某个在场角色 id 落到集合外，判据必须失败。

### 3.9 `story-background-table`（`0x59903C` / `0x0859903C`，id×16）

* **场景**：story（场景 54）
* **表项**：第 13 条 → `0x0833CA94`
* **运行时**：该指针的 LZ77 载荷与模拟器 VRAM `0x06004000` 处的
  **19264 字节完全相等**
* **为什么唯一**：底图表一共 16 条；在这张画面上，只有第 13 条的
  这一块（19264 字节）能在 VRAM 里整块命中，
  其余条目（640 字节的小块）要么对不上、要么指向共用块。
* **看得见的结果**：`notes/evidence/l3-story-scene54.png` 里
  **教室背景**就是这一块图块（剧情场景 54 = 伊鲁卡那一场），
  画面下方的对白框是同一场戏的下一句
* **截图**：`notes/evidence/l3-story-scene54.png`、
  `notes/evidence/l3-story-scene54-p2.png`
* **可证伪检验**：换到别的剧情场景（或改 ROM 里第 13 条的指针），
  命中必须随之改变。

## 5. 未达到 L3 的 30 个结构

| 结构 | 试了什么 / 为什么没到 |
|---|---|
| `text-writeback` 对白文本写回 | 对白字形码已被 `notes/evidence/text-encoding-l3-20261020.md` 证明；本轮**没有**再独立导出一条运行时对应关系（剧情对白来自故事脚本内联，不是 `0x461CE8` 的对白池） |
| `mission-text` 任务文字三表 | 需要一条更长的纯按键路线（标题→修行场→任务列表），本轮未走到 |
| `reward-table` 战斗奖励表 | 需要一场**真的打赢**的战斗；本轮从未触发奖励结算 |
| `sound-id-table` 音频 sound-ID 表 | 战斗期间在 EWRAM/IWRAM 全域扫描不到指向 5 个 SongHeader 的裸指针（0x08536368 / 0x08536BC4 / 0x08538FEC / 0x0853AB74 / 0x0853C3BC），因此无法把 sound id 与运行时读数对上 |
| `story` / `story-b` / `story-c` / `story-d` / `story-e` | 五个 m4a SongHeader（sound id 1/2/8/11/14）：同上，本轮**没有任何运行时读数** |
| `battle-config` 忍术记录表 | 战斗里没打开「技」列表 |
| `skills` 技能 / `items` 道具 / `ninjutsu-names` 忍具名表 | 战斗里没打开「技」列表，这些表的内容没有上屏 |
| `mechanism-effects` 机关效果表 | 没有拾取任何机关，分派表没被查 |
| `sprite-action-table` / `sprite-animations` 精灵动作表 | 动作项是两级间接（记录 → 帧表 → 图块）；本轮无法把**看得见的那个精灵**和它的动作记录一一对应。已排除的办法：动作项里的调色板指针在调色板 RAM 里找不到（引擎会改写调色板） |
| `sprite-frame-descriptors` 精灵帧描述符表 | 用这张表的对象类型在战斗/剧情路线里从没被实例化 |
| `battle-encounters` 战斗遭遇记录表 | 只经由回调跳板 `0x0808A69C` 被读到，而没有任何战斗或剧情场景分派它 |
| `battle-handlers` / `map-events` 事件处理程序分派表 | 只经由回调表 `0x0853ECB0` 被读到，战斗与剧情路线都不会分派它 |
| `character-stats` / `character-stats-b` 逐角色属性表 | 已验证**它不是**运行时单位记录的来源（`0x545068` 的 `64 00 64 00 64 00` 与运行时 `0f 00 50 00 50 00` 对不上），因此没有可宣称的对应关系 |
| `data-table-a` 数据指针表 A | 消费者 `0x0808AFE0` 在战斗路线里不运行 |
| `data-table-b` 数据指针表 B | 消费者在战斗路线里不运行 |
| `fonts` 字宽表 | 唯一原生读者 fn `0x0807EE50` 只经由回调表 `0x0853ECB0` 被调用，战斗与剧情路线都不分派它；对白排版的字宽也不取自这张表 |
| `function-pointers` 函数指针表 | 槽号只有下消费者断点才看得见；本轮刻意不挂断点 |
| `levels` 角色特性表 | 战斗里没有可观测的运行时对应物 |
| `map-sprites` 场景对象描述符表 | 战斗路线没有查它 |
| `resource-pointers` 资源指针表 | 已裁决为精灵动作表 `0x596CCC + 0x240` 的窗口，不能单独观测 |

## 8. 本轮走过的弯路（按 `AGENTS.md` 记录）

1. **只按 A 键进剧情**：能走到场景 54，但战斗那一场停在「人物信息」页，
   `0x020240C0` 的单位数组是空的（与 `notes/evidence/runtime-state-l3-20261020.md` §4 同因）。
   → 必须用仓库已证明的三处内存写**选**战斗。
2. **把地形整块当成相等**：第一次量到 `10240/10240`，重跑后只剩 `1824/10240`。
   逐组验证（组 1/5/9/14）后确认：差异处的字节呈重排特征，
   游戏会改写 VRAM 里的部分图块。**因此本笔记只声明前缀**，不声明整块相等。
3. **精灵动作表用调色板去找**：动作项第 4 个指针是调色板，
   但引擎会把调色板改写后再写进调色板 RAM，原样比中不上了。→ 记为「未达到」。
4. **快照采样时机**：读 VRAM 的时机不同会拿到不同的画面
   （战斗开场 vs 战斗页），所以工具改成**一次运行采两个快照**，判据在所有快照里找最好的那次，
   并把每次的数值都写进报告（`per_snapshot` 字段）。
