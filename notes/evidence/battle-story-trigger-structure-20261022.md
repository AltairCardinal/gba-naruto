# 战场剧情触发的结构（第十一轮的证据）— 2026-10-22

> 这是**事实**笔记：战场地图视图的「剧情触发」卡片要「关联上剧情」，
> 得先知道剧情在 ROM 里到底长什么样。
> 设计在 `notes/specs/battle-story-triggers-20261022.md`。
>
> 复现：`node tools\probe_battle_story_triggers.mjs`（统计）
> 与 `node tools\probe_battle_story_scene.mjs <场景>`（逐指令）。

## 1. 两个根指针各管什么

内容包 `pack.scripts` 共 202 条：

| root | 记录数 | 有剧本的场景 | 指令数（min / 中位 / max） |
|---|---:|---|---|
| `before` 战前剧情 | 55 | 1..55 | 1 / 106 / 2123 |
| `after` 战后剧情 | 55 | 1..55 | 2 / 54 / 2123 |
| `logic` **战场事件逻辑** | 46 | 1..46 | 7 / 41 / 88 |
| `events` **战场事件表** | 46 | 1..46 | 13 / 86 / 201 |

**剧情按【场景】索引，跟战斗变体无关** —— 战斗是 47 关 × 3 变体，
而 `story_logic_root` / `story_events_root` 各只有 47 条记录（场景 1..46 有剧本），
⇒ **同一关的三个变体共用同一份剧情**。

## 2. 全包普查：两个脚本的指令分工**完全不相交**

`tools/probe_battle_story_triggers.mjs` 的输出（46 个场景合计）：

| 指令 | logic 合计 | events 合计 |
|---|---:|---:|
| `0x33` 压入事件队列值 | **407** | **0** |
| `0x32` 事件表项 | 21 | **400** |
| 条件类 `0x34`–`0x39` | **1013** | **0** |
| `0x37` 置/清战斗标志 | 196 | 0 |
| `0x13` 双段文本 | **0** | **0** |
| `0x0D` 调用子脚本 | **0** | **0** |
| 文本指令 `0x01` / `0x20` | 21 | **1118** |

> ⚠️ **标签订正**（设计子代理 2026-10-22 指出）：
> 十六进制 `0x13` 是**双段文本**，**调用子脚本是 `0x0D`**。
> 仓库 `rom-editor/js/storyvm.js` 的 `OPCODE_NAMES` 用的是**十进制**键
> （`19: '双段文本'` / `13: '调用子脚本'`），十六进制与十进制混着看很容易串。
> 两个操作码在 logic / events 剧本里**都是 0 次**，所以普查数字不受影响；
> 但全 202 个剧本里 `0x13`（双段文本）共出现 28 次（全在 before / after 里），
> `0x0D`（调用子脚本）仍是 0。

⇒ **logic 负责「什么条件下推事件 id」，events 负责「第 N 段剧情」**。
两边的条目数几乎一一对应（407 vs 400，中位数都是 10，最多 17）。

**每关的触发项数 = logic 里的 `0x33` 条数**：min 2 / 中位 10 / max 17。
⇒ 做成「列表」完全可行，列表长度不会失控。

## 3. logic 脚本的结构：一串「条件 → 压入事件 id」

第 5 关的 `logic`（指针 `0x0804ED2D`）逐指令（`+1`… 是操作数字节）：

```
0x804ED2D  0x34 回合/相位条件   比较器=3(>=) b=1 c=1  目标=0x0804EDB7
0x804ED35  0x34 回合/相位条件   比较器=3(>=) b=2 c=0  目标=0x0804ED7B
0x804ED3D  0x33 压入事件队列值   值=1                    ← 事件 1
0x804ED3F  0x36 指定人物在场     a=0 b=1 c=28            目标=0x0804ED59
0x804ED47  0x34 回合/相位条件   比较器=3(>=) b=3 c=0    目标=0x0804ED59
0x804ED4F  0x34 回合/相位条件   比较器=5(<=) b=1 c=0    目标=0x0804ED59
0x804ED57  0x33 压入事件队列值   值=2                    ← 事件 2
0x804ED59  0x36 指定人物在场     a=0 b=1 c=27            目标=0x0804ED71
...
0x804EDB5  0x33 压入事件队列值   值=6                    ← 事件 6
0x804EDB7  0x00 结束脚本
```

**条件指令的 u32 目标 @+4 是「条件成立时跳到哪」**（证据：`0x08097D4C` 的 handler ——
`cmp r4,#1 / bne #0x8097d84` 之后 `b #0x8097b20`，`r5` 就是读出来的 u32 目标）。

于是每个 `0x33`（压入事件 id）**前面那一段条件**就是这一段的触发条件：
条件全部**不成立**时，才落到这个 `0x33` 压入事件 id。

⇒ **触发项 = 一组条件（合取）+ 一个事件 id**。

## 4. events 脚本的结构：连续的 `0x32` 就是事件链

**链是 1 基的**（主代理 2026-10-22 独立复核，设计稿 §1.5 与 V2 同源）：

```
0x08097CF8: movs r4, #0        ; 链游标 r4 从 0 起
0x08097D0A: adds r4, #1         ; 每走过一条 0x32，r4 加 1
0x08097D1A: subs r0, #1         ; 半字 0x3801 —— 队列值先减 1
0x08097D1C: cmp  r0, r4         ; 半字 0x42A0 —— 与 0 基游标比
```

⇒ **压入 V 选中链上第 V 段**（1 基）。
（设计稿的 V2 断言 `rom[0x08097D1A]===0x01` / `rom[0x08097D1C]===0xA0` /
`rom[0x08097D1D]===0x42` 与实际字节逐项一致。）

第 5 关的 `events`（指针 `0x0804EDB8`）开头：

```
0x804EDB8  0x32 事件表项   u32@+1 = 0x0804EDD6   ← 第 1 段起点
0x804EDBD  0x32 事件表项   u32@+1 = 0x0804EE5D   ← 第 2 段起点
0x804EDC2  0x32 事件表项   u32@+1 = 0x0804EEEB   ← 第 3 段起点
0x804EDC7  0x32 事件表项   u32@+1 = 0x0804EF14   ← 第 4 段起点
0x804EDCC  0x32 事件表项   u32@+1 = 0x0804EF3B   ← 第 5 段起点
0x804EDD1  0x32 事件表项   u32@+1 = 0x0804EF6E   ← 第 6 段起点
0x804EDD6  0x12 设置对话框尺寸 … 0x08 设置头像与说话人 … 0x01 显示文本 … 0x00 结束脚本   ← 第 1 段
0x804EE5D  0x12 … 0x08 … 0x01 … 0x00 结束脚本                                                   ← 第 2 段
0x804EEEB  0x02 选择对话框 … 0x08 … 0x01 …                                                        ← 第 3 段
```

**每个 `0x32` 的 u32 @+1 就是它自己那一段的起始地址**（第 N 个 `0x32` 对应第 N 段）。
配合 §3 的「队列值 N 选中第 N 段」，**整条链就通了**：

```
logic: 条件组 → 压入事件 id N
events: 第 N 个 0x32 → 第 N 段剧情（设置对话框 / 头像 / 对白 / 结束）
```

## 5. 「事件 id」与「第 N 段」的对应

`0x32` 的语义（`notes/story-vm-opcodes-20261020.md` §3，proved）：
用 `state+0x1D[state[0x1C]]` 的值挑第 N 项后跳其 u32。
`0x33` 压队列值的上限是 **16 项**（`state[0x1B]`）。

⇒ **id 与段号是 1 基对应的**，且队列最多 16 项 ——
每关最多 17 个触发项（logic 里 `0x33` 最多 17 个）与这个上限一致。

## 6. 条件指令的语义（已定案的部分）

`notes/story-vm-opcodes-20261020.md` §3 / §3.1：

| opcode | 长度 | 操作数 | 语义 |
|---|---:|---|---|
| `0x34` | 8 | 比较器@+1, b@+2, c@+3, u32 目标@+4 | 回合/相位条件跳转 |
| `0x35` | 9 | a@+1, b@+2, c@+3, d@+4, u32 目标@+5 | 复合条件跳转 |
| `0x36` | 8 | a@+1, b@+2, c@+3, u32 目标@+4 | 指定人物在场条件跳转 |
| `0x37` | 3 | 模式@+1, 标志@+2 | 置/清战斗标志 |
| `0x38` | 7 | 模式@+1, 标志@+2, u32 目标@+3 | 测战斗标志 |
| `0x39` | 6 | ID@+1, u32 目标@+2 | 子配置匹配 |

**比较器表**（§3.1，仓库自己的代码级结论）：
0 `==` / 1 `!=` / 2 `>` / 3 `>=` / 4 `<` / 5 `<=`，**无符号**，两个操作数按 u8 取值。

`0x34` 的 handler（`0x08097D4C`）：
先 `ldrb r0,[r7,#3]`（c）→ `bl #0x0808A1A4`（阶段/子阶段检查），
**返回 ≠ 1 就直接不成立**；成立才继续取 @+1 的比较器（`0xFF` 是特例），
经 `0x0808A198` 取当前值、与 @+2 的 b 按比较器比。

**三套互不相同的标志位空间**（§3.2）：
`0x020314F0`（剧情标记，0x09/0x0A/0x0B/0x0C）/
`0x02031510`（0x19/0x15/0x34）/
`0x020311D4`（战斗标记，0x37/0x38）—— 三套是分开的。

## 7. 还没解的（**界面里不能说满**）

> **订正（2026-10-22，设计子代理 + 主代理复核）**：本文初版写「`0x34` 的 @+2（b）跟什么比，
> 仓库没定案」—— **那是错的**。设计子代理把这一步做到了字节级：
> `0x0808A198` 的 `ldr r0,[pc,#4]` 取的字面量在 **`0x0808A1A0`，值 = `0x0202680C`**，
> 接着 `ldrb r0,[r0]` 读的就是 `0x0202680C` 的首字节。
> 而 **`0x0202680C` = 回合计数** 是仓库**已定案**的
> （`notes/battle-tables.md` §「2026-10-21 追加：`0x0202680C` **就是回合计数**（旧结论作废）」，
> 运行时证据 `tools/closure_round_probe.py`：回合真的推进时该字节从 1 变 2）。
> ⇒ **b 比的就是回合计数。**

真正没定名的只有 **c 那个字节 `0x0202680E`** —— 仓库只把它叫 **`ctrl[10]`**
（战斗控制块 `0x02026804` 的第 10 字节），
并记着它在战斗主循环里每帧 `eors #1` 翻转一次（`notes/evidence/callback-dispatch-runtime-20261021.md` §3）。
**没有业务名** ⇒ 界面照实说「仓库还没给它起名」。

其余没解的：

- `0x35` 的 f(b,c,d) 到底在算什么、三个参数分别是什么 —— 没解。
- `0x36` 的 a / b / c 怎么分工（a 像「期望结果」、c 像角色 id，b 未解）—— 没解。
- `0x37` / `0x38` 的「模式」@+1（0 = 测 / 1 = 置？）与「标志」@+2 的编号空间 —— 没解。
- `0x39` 的 ID 与「子配置」的关系 —— 没解。

⇒ 界面可以显示「这一段在什么条件下触发」，但**条件的具体含义要照实说没解**。

## 8. 写回约束

- **对白正文内联、分支目标是绝对地址**（**结构事实本身没变**）：正文内联在指令后面，
  分支目标是绝对地址 ⇒ 原地改长改短会移位。
  ⇒ **第十七轮起不再因此拒绝改写**：变长 / 变短由「构建时把整个剧本搬到 ROM 空闲区、
  把它内部的绝对地址全部重基、再改根表指针」兜住
  （`rom-editor/js/rom.js::applyScriptRelocations` + `rom-editor/js/storyvm.js::planRelocation`）。
  仍然**只能等长**的只有**不属于任何剧本**的正文（孤儿代码）—— 后面没有东西能给它让位。
  依据：`notes/evidence/story-script-relocation-20261022.md`。
- **操作数定宽**：`0x34`/`0x35`/`0x36`/`0x38`/`0x39` 的长度都是定长 ⇒ 里面的
  u8 / u32 目标都可以**原地改**。但**改 u32 目标 = 改分支落点** ——
  它合法（分支目标本来就是可改的），但可能把剧情接到别的地方去，界面要提示。
- **脚本正文不在任何结构表 / 文本表的写回范围内** ⇒ 改动只以**补丁**存在，
  界面必须把补丁叠上去看（`scripttext.js::currentBytes` 已经处理）。
