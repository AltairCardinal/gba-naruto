## 1. 我实际做了什么核实（不盲信上游清单）

上游简报给的 12 行清单我**逐条重新反汇编验证**，结果如下：

1. **地址区间全部有偏差**：上游写的是「5 条 × 2 字节」，但它给的闭区间**只有 9 字节**（例：`0x08079086..0x0807908E`），
   实际 5 条指令占 **10 字节**（`0x08079086..0x0807908F`）。本轮清单里用的是**实测的真实 10/8 字节窗口**。
   ⇒ 上游清单的区间端点**不可直接拿来写补丁**（差 1 字节会切掉最后一条指令的后半）。
2. **「12 个读者形状完全一致」这句不准确**：实际有 **4 种形状**（寄存器分配不同），见 §3。
   变换规则统一，但**每处的具体字节不同**，必须逐条生成。
3. **独立重扫全 ROM 的 `ldr [pc,#imm]`**：指向 `0x085A57C4` 的引用**恰好 12 处**（与上游一致）；
   另有 3 处指向 `0x085A5AB8`（全名表），**刻意不碰**。
4. **独立扫全 ROM 的 4 字节原始值** `0x085A57C4`：出现 **12 次**，就是那 12 个字面量池，
   **没有任何数据表指针指向说话人名表**。
5. **独立扫 Thumb ADR / ADD(PC,#imm)**：落在表区内的命中**全部位于表数据自身**（把数据当代码解的假阳性），
   ⇒ **表区之外没有任何代码用 PC 相对寻址指向它**。
6. **ROM 尾部空闲区**：文件 `0x5DFBEC..0x5FFFFF`（132 116 B，全 `0xFF`），ROM `0x085DFBEC` 起 —— 可作新串池。

## 2. 变换规则

### 2.1 统一形态（5 条指令的读者）

```
旧：  lsls rD, rI, #1      ; id*2
      adds rD, rD, rI     ; id*3
      lsls rD, rD, #2     ; id*12
      ldr  rB, [pc, #imm] ; rB = 0x085A57C4
      adds rD, rD, rB     ; rD = 表基址 + id*12  → 这就是「字符串首地址」
新：  lsls rD, rI, #2      ; id*4              ← imm5 由 1 改 2
      ldr  rB, [pc, #imm+4]; rB = 0x085A57C4    ← 指令前移 4 字节，imm8 加 1
      adds rD, rD, rB     ; rD = &表项[id]
      ldr  rD, [rD]       ; rD = 表项[id] = 字符串首地址
      nop                 ; 补齐
```

要点：
- **旧序列的中间那条 `adds`（算 id*3）被删掉**，**加基址那条 `adds` 字节原样保留**（探针逐字节断言）。
- **`ldr` 的 imm8 恰好加 1**（= 偏移 +4 字节）。推导：Thumb `ldr [pc,#imm8*4]` 的目标 =
  `((PC+4) & ~3) + imm8*4`。旧 `ldr` 在窗口第 4 条（地址 L），新 `ldr` 在第 2 条（地址 L−4）：
  旧基准 `((L+4)&~3)`、新基准 `((L)&~3)`，两者**恒差 4 字节**（L 是否 4 字节对齐都成立），所以 imm8 **恒 +1**。
  探针对每一处都重算了新旧目标地址并断言它们仍等于原字面量地址。
- **寄存器安全性**（逐处核对过）：
  - 变体 B 的读者 2 里 **id 也在 r1**，基址也要装 r1 —— 新序列**先 `lsls` 消耗 id、再 `ldr` 覆盖 r1**，顺序与旧代码一致。
  - 读者 8 第一处把基址装在 **r5**，且 r5 要跨 `bl strlen` 活到第二处 ⇒ 依赖 AAPCS「r4–r11 被调用者保存」。
    改后 r5 的装值时机提前 4 字节，**跨 call 的存活关系完全不变**（旧代码本来就依赖这条）。
  - 读者 12 第一处把基址装在 **r4**，要跨 `bl 0x0806626C`（文本渲染器）活到第二处 ⇒ 同上，性质不变。
  - 读者 7 的 **r4 是 id**，且 r4 在窗口之后还要用于另一张表 ⇒ 本补丁**不写 r4**。

### 2.2 4 条指令的读者（8b / 12b 第二处）

基址已经在寄存器里（旧序列没有 `ldr` 字面量），所以只需 4 条：

```
旧：  lsls rD, rI, #1 ; adds rD, rD, rI ; lsls rD, rD, #2 ; adds rD, rD, rB
新：  lsls rD, rI, #2 ; adds rD, rD, rB ; ldr rD, [rD] ; nop
```
**没有 PC 相对寻址要重算** ⇒ 变长方案在这两处零风险。

## 6. 数据侧的硬性要求（本轮**未做**，属下一步）

代码补丁只是把「取名字」改成「取指针再解引用」，**数据侧必须配套**，否则表里全是垃圾：

1. **新指针表**：`0x085A57C4`，64 项 × 4 B（LE 指针）。
   ⚠️ 这会**覆盖旧 12 字节表的前 256 字节**（旧 id 0..20 的槽）⇒ **必须先把旧表内容备份出来**再写。
2. **新串池**：63 条名字共 331 B（含各自 NUL），放在 ROM 尾部空闲区
   （文件 `0x5DFBEC..0x5FFFFF` / ROM `0x085DFBEC` 起，共 132 116 B）。
   **不许放进 `0x085A57C4..0x085A58C3`（指针表）**，也**不许覆盖 `0x085A5AB8` 起**。
3. **旧表残留**：`0x085A58C0..0x085A5AB7`（500 B）会留下 id 21..62 的**旧名副本**。
   它们**不再被任何代码引用**（12 个读者已全部改写），属无害垃圾；可选清零，但清零前要确认没人按旧表地址读数据。
4. **id 63 特别提醒**：旧 id 63 的槽正好是 `0x085A5AB8`（= 全名表第 0 条，内容「没有」），
   变长方案必须把 id 63 的名字放进新串池，**同时绝对不能覆盖 `0x085A5AB8` 起的字节**。

## 7. 没做实的部分

1. **未做运行时验证**。本轮只做了**静态字节级核验**（反汇编 + 位域 + 差异扫描）。
   没有用无头 mGBA 断点确认改后 `r1` 真的等于新串池地址、名牌画出来和改前一致。
   （上游简报 §5 已给出断点方案：断在 `0x08097A16` 读 r1、断在 `0x08066276` 读 r1 并 dump 字符串。）
2. **未生成新指针表与新串池的实际内容**（数据侧，见 §6）。本清单**只改代码**，
   在数据侧做完之前，**这 14 处补丁不能单独打进 ROM**。
3. **读者 4/5（`0x08066EFC` 逐字节抄写）变长后的列数组容量未实测**。
   上游已指出这两处按**字节**（不是字形）遍历名字，列号会随字节数变化 —— 变长后是否越界仍需单独确认。
   （**推定**：每个双字节字形占 2 字节、列数组按字形计列，所以列数不随长度变；但未实测。）
4. **未覆盖 ARM 模式代码**。12 个读者全是 Thumb；本轮扫引用也只扫了 Thumb `ldr`。
   ARM 模式下没有指向 `0x085A57C4` 的引用（4 字节原始值全 ROM 只出现 12 次，即那 12 个 Thumb 字面量池），但这是**间接证据**。
5. **全名表的准确条数仍未闭合**（上游遗留）。本轮发现 `0x0808CE30` 有一个字面量指向 `0x085A5F65`
   = 全名表第 63 条 ⇒ 全名表**至少有 64 条**。这不影响本补丁（该区域不碰），但记录在此。
6. **上游清单里的地址区间不能直接用**（§1 第 1 点，差 1 字节）。本轮清单的地址是重新实测的。
7. `build/` 下留了 3 个临时分析脚本（`_tmp_spk_analysis.py` / `_tmp_spk_refs.py` / `_tmp_spk_enc.py`），
   本机删除被安全策略拦下。它们在 gitignore 的 `build/` 里，不入库，可随手删。
