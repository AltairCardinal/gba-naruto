# 关卡数据块表格式（0x53DF70）证据（2026-10-20）

**一句话结论**：`0x53DF70` **不是**剧情 VM 脚本表，而是**关卡数据块表（战斗关卡图形资源表）**——
4 项 × 8 字节，每项是一对指针 `(LZ77 4bpp 图块, LZ77 16 色调色板)`；
原生读者把这两个块分别用 BIOS `svc 0x12`（`LZ77UnCompVram`）解压进 **VRAM** 和 **调色板 RAM**。
剧情 VM 从头到尾没有碰过这些块。

---

## 1. 被裁决的问题

旧结构库把 `0x53DF70` 记作「过场脚本表（cutscene scripts）」，写回路径只敢停在**指针层**，
并且故意留了一个二选一（见 `notes/evidence/writeback-paths-20261020.md` §2.8 旧版）：

> (1) 若能解出 `0x0812D9E4` 起的数据块格式并证明它是 VM 脚本 → 「过场脚本」身份成立；
> (2) 若块格式证明它**不是** VM 脚本 → 该 bank 的内容身份记为「关卡数据块表」。

本轮把 (1)/(2) 判掉。

---

## 2. 方法

| 步骤 | 工具 | 作用 |
|---|---|---|
| 定位唯一原生读者 | `tools/consumer_locate.py` | 全 ROM literal 索引 → `0x53DF70` 只有 1 个读者 |
| 反汇编读者 | 新增 `tools/cutscene_block.py` | **控制流跟随**的 Thumb 反汇编器（会跳过 literal pool，不把常量池当代码读） |
| 解码块 | `tools/lib/lz77.py`（仓库既有编解码器） | GBA LZ77 |
| 排除 VM 身份 | `tools/decode_story_script.py::LENGTHS` | 仓库已证明的 44 条 VM 指令长度表 |

capstone 用本机 `build/python-deps/capstone/capstone/lib/capstone.dll`
（`tools/story_vm_ops.py`、`tools/consumer_locate.py` 同款自动发现逻辑）。

**踩过的坑（留给下一个人）**：
1. 线性反汇编会把 literal pool 当成指令读（`svc #0x70` 之类），
   必须先算出所有 `ldr rX,[pc,#imm]` 的字面量地址并**跳过**；
2. 控制流跟随**必须用广度优先**。第一版用栈（深度优先），在 `0x08072EDC` 里
   先钻进了后面的无关函数，400 条指令预算耗尽，`0x08073072` 那段分支目标**根本没被解码**；
3. `0x53DF70` 是**文件偏移**语境与**ROM 地址**语境混用的坑：剧情 VM 四根表
   `0x060C74` 等是 **ROM 文件偏移**（`tools/decode_story_script.py` 直接拿它索引 ROM 缓冲区），
   而表里的指针是 ROM 地址。

## 3. 原生代码（决定性证据）

### 3.1 唯一读者

```
$ python tools/consumer_locate.py rom/base.gba --target 0x53DF70
0x53DF70    0x0853DF70  consumers=1
    reader 0x08072F0C (thumb) fn 0x08072EDC
```

读者函数 `0x08072EDC` 的开头（`tools/cutscene_block.py --disasm 0x08072EDC`）：

```
08072EDC  push     {r4, r5, r6, r7, lr}
08072EE8  lsls     r0, r0, #0x18
08072EEA  lsrs     r0, r0, #0x18     ; r0 = 入参 & 0xFF（索引）
08072EEC  mov      r8, r0
```

### 3.2 步长是 8 字节 —— 每项是**一对**指针

```
08072F0C  ldr      r4, [pc, #0x2c]   ; r4 = 0x0853DF70   ← 表基址
08072F0E  mov      r0, r8            ; r0 = 索引
08072F10  lsls     r5, r0, #3        ; r5 = 索引 * 8     ← 步长 8，不是 4
08072F12  adds     r0, r5, r4        ; r0 = 表 + 索引*8
08072F14  ldr      r0, [r0]          ; r0 = 图块指针
08072F16  ldr      r1, [pc, #0x28]   ; r1 = 0x06016000    ← VRAM
08072F18  bl       #0x809c0e8        ; 解压
08072F1C  adds     r4, #4
08072F1E  adds     r5, r5, r4        ; r5 = 表 + 索引*8 + 4
08072F20  ldr      r0, [r5]          ; r0 = 调色板指针
08072F22  ldr      r1, [pc, #0x20]   ; r1 = 0x05000380    ← 调色板 RAM
08072F24  bl       #0x809c0e8        ; 解压
```

**旧结构库「16 项 × u32」是错的**：原生步长是 8 字节，即 **4 项 × (2 个 u32)**。

### 3.3 两个指针的去向：BIOS `svc 0x12`

`0x809C0E8` 的原始字节是 `12 DF 70 47`：

```
0809C0E8  svc      #0x12       ; SWI 0x12 = LZ77UnCompVram（r0=源, r1=目的）
0809C0EA  bx       lr
```

同一函数里的另一次 BIOS 调用 `0x0809C574` 是 `bx pc`（切 ARM 态），`0x08073028` 也调 `svc 0x12`。

* `r1 = 0x06016000` → **OBJ VRAM**（图块像素）
* `r1 = 0x05000380` → **调色板 RAM**（`0x380 / 32 = 第 28 号调色板槽`）

**一个剧情脚本不可能被送进 VRAM 或调色板 RAM。** 这一条就足以否定 VM 身份。

### 3.4 索引域是 0..3

读者里对索引 3 特殊处理：

```
08072F28  mov      r1, r8
08072F2A  cmp      r1, #3
08072F2C  beq      #0x8072f48      ; 索引 3 → r6=0x30, sb=0x30
08072F2E  movs     r6, #0x48       ; 其余 → r6=0x48, sb=0x60
```

四个调用点传的索引正好是 0/1/2/3：

| 调用点 | 传入索引 | 所在函数 |
|---|---|---|
| `0x0807363A` | `r0 = 0`（`0x08073638: movs r0,#0`） | `0x08073620` 附近 |
| `0x08073100` | `r0 = 1`（`0x080730FE: movs r0,#1`） | `0x0807305C`（战斗关卡建立，先在 `0x08073062` 调规则分派 `0x080777FC`） |
| `0x0807314A` | `r0 = 2`（`0x08073148: movs r0,#2`） | 同上 |
| `0x08073196` | `r0 = 3`（`0x08073194: movs r0,#3`） | 同上 |

→ 表项数 = 4。

### 3.5 表的**真实范围**是 `0x53DF70..0x53DF8F`

* `0x53DF70 + 4 项 × 8 字节 = 0x53DF90`；
* `0x0853DF90` 是**另一张表**，被同一个函数在 `0x08072F8C` 读入，
  作为 arg0 传给对象创建函数 `0x080625A4`；后者按**同样 8 字节步长**索引它：

```
08062668  lsls     r0, r7, #3
0806266A  ldr      r1, [sp]          ; arg0 = 0x0853DF90
0806266C  adds     r0, r0, r1
0806266E  ldr      r1, [r0]
08062670  str      r1, [r4, #0x1c]
08062672  ldr      r0, [r0, #4]
08062674  str      r0, [r4, #0x20]
```

* `0x0853DFB0` 是**第三张表**，被**另一个函数**读（`0x08075BD4`，fn `0x08075B58`），
  它是字节表（`09 08 0a 09 05 0b 0c 0c ...`），不是指针表。

所以旧笔记「`0x53DF70..0x53DFAF` 是 16 个 u32 指针」其实是**两张 4 项的 8 字节表**，
中间没有空隙，但**不是同一张表**。

## 4. 解出来的块格式

### 4.1 块头（4 字节）

```
+0x00  u8   0x10                     ← LZ77 魔数（= 压缩类型位 1）
+0x01  u24  解压后长度（小端）
+0x04  ...  LZ77 载荷
```

这正是仓库既有 `tools/lib/lz77.py` 的格式（`compress_literal()` 产出 `0x10` + u24 长度 + 载荷）。
注意 u24 是**小端三字节**，不是 gbatek 常见的「字节 0 高 4 位放长度高 4 位」那种排布。

### 4.2 8 个块实测

| 项 | 指针 | 头 | 解压长度 | 压缩占用 | 解压内容 |
|---|---|---|---|---|---|
| 0 | `0x0812D9E4` | `10 00 10 00` | 4096 | 1112 B（→`0x0812DE3C`） | 4bpp 图块像素（128 张 8×8） |
| 0 | `0x0812DEE4` | `10 20 00 00` | 32 | 22 B（→`0x0812DEFA`） | 16 × BGR555 调色板 |
| 1 | `0x0812DF4C` | `10 00 10 00` | 4096 | 1187 B（→`0x0812E3EF`） | 4bpp 图块像素（128 张） |
| 1 | `0x0812E42C` | `10 20 00 00` | 32 | 22 B（→`0x0812E442`） | 16 × BGR555 |
| 2 | `0x0812E494` | `10 00 10 00` | 4096 | 1113 B（→`0x0812E8ED`） | 4bpp 图块像素（128 张） |
| 2 | `0x0812E948` | `10 20 00 00` | 32 | 22 B（→`0x0812E95E`） | 16 × BGR555 |
| 3 | `0x0812E9B0` | `10 00 08 00` | 2048 | 935 B（→`0x0812ED57`） | 4bpp 图块像素（64 张） |
| 3 | `0x0812ED58` | `10 20 00 00` | 32 | 22 B（→`0x0812ED6E`） | 16 × BGR555 |

* 头里的 u24 长度**逐块等于**标准 GBA LZ77 解码器实际产出的字节数（`lz77_span()` 同时报出压缩占用）。
* 调色板 0 的 16 个 u16 =
  `0x0340, 0x7FFF, 0x5AD6, 0x35AD, 0x1084, 0x03E0 ×10`——典型 BGR555。
* 图块 0 的第 3 张 8×8 4bpp tile 是
  `00…00 | 00 00 00 10 | 11 11 11 21 | 31 44 44 44`——典型的透明底角色像素。
* **索引 3 的图块只有 2048 字节（64 张）**，其余三项是 4096 字节（128 张），
  与 `0x08072F2A` 对索引 3 的特殊分支（尺寸参数不同）吻合。

## 5. 为什么它**不是**剧情 VM 脚本（四条互相独立的证据）

| # | 观测 | 怎么测的 |
|---|---|---|
| E1 | 原生读者把块地址交给 **BIOS `svc 0x12`**，目的地址是 VRAM / 调色板 RAM | §3.2 / §3.3 |
| E2 | 8 个块地址在**整 ROM 里没有任何 literal 引用**（`consumer_locate` 全部 `consumers=0`），只能经这张表到达 | `consumer_locate.py --target 0x0812D9E4` 等 8 次 |
| E3 | 8 个块地址**都不在剧情 VM 四根表**（文件偏移 `0x060C74/0x060D54/0x060E34/0x060EF0`）的 207 个脚本地址里；VM 脚本地址区间是 `0x08009F2E..0x0805C6D3`，与块的 `0x0812xxxx` 段**不重叠** | `tools/cutscene_block.py` 的 `story_root_targets()` |
| E4 | VM 解释器入口 `0x080977B8` **不在读者的调用表里**；读者只调 `0x809C0E8`(svc 0x12)、`0x809C574`、`0x080625A4`、`0x08062788` 等 | `--disasm 0x08072EDC` 的 calls 列表 |

补充：VM 指令表（`tools/decode_story_script.py::LENGTHS`）里**没有任何一条指令带 24 位长度操作数**；
块头那 3 字节在 VM 语境下无处安放。

## 6. 可证伪判据

> **如果我错了**：只要能证明「`0x0812D9E4`（或其余任一块）确实被送进剧情 VM 解释器
> `0x080977B8`，或被剧情 VM 四根表中的某条链路引用」，本结论立即作废。

三条可当场复现的判据：

* **T1（决定性，静态）**：把 `0x08072EDC` 的两条 `bl 0x809C0E8` 追到底，
  其首指令是 `svc #0x12`（`LZ77UnCompVram`），且 r1 分别是 `0x06016000` / `0x05000380`。
  若块是脚本，这里必须是 VM 解释器或 VM 根表的取址路径。**实测：不是。**
* **T2（块头自洽）**：对 8 个块跑标准 GBA LZ77 解码器，
  头里的 u24 必须等于解码器实际产出的长度。**实测：8/8 成立**。
  若块是 VM 脚本，这 3 字节必须是某条指令的操作数——VM 的 44 条指令里没有这种形状。
* **T3（可达性）**：`consumer_locate.py` 对 8 个块地址全部报 `consumers=0`，
  且它们都不在 VM 四根表的 207 个脚本地址里。**实测：8/8 成立**。

> **T4（运行时，本轮未执行）**：把 `0x12D9E5`（gfx0 的 u24 长度字段低字节）改成别的值再跑 mGBA。
> 若块是脚本，表现应是剧情分支错乱；若是 LZ77 图形块，表现应是 VRAM `0x06016000`
> 里的图块数量/内容变化或出现垃圾。本轮没跑 mGBA，**不作为结论依据**，仅作为后续可选复核。

## 7. 对写回范围的影响

1. **「作者往这个 bank 里塞一段新剧情脚本」这条路不存在**——这个 bank 里根本没有脚本内容，
   它装的是关卡图形资源。
2. **`cutscene-scripts` 这个结构名是错的**；内容身份应记为
   **「关卡数据块表（战斗关卡图形资源表：4 项 × (LZ77 图块, LZ77 调色板)）」**。
3. 写回范围**仍然停在指针层**（改「用哪一套图形资源」），但理由从「格式未解」升级为
   **「这里没有脚本可写」**——这是**正面**结论，不是遗留缺口。
4. **新事实（未实施，属另一条线）**：块本身已经解出（LZ77），所以
   *「图形/调色板内容级」*改写在机械上是可行的：
   原地重写 LZ77 载荷（解压后长度必须相同，否则要同时改头并保证不越界），
   或把表项指向另一个原生块。建议单开一个「关卡图形资源」结构条目来做，
   **不要**混在 `cutscene-scripts` 这个 bank 名下。

## 2026-10-21 追加：「这四块对应哪四张原版战斗地图」的前提**被证伪**

先前留下的开放项是「四个块分别对应哪四张原版战斗地图，尚未逐一对照」。
把数据真的对了一遍之后，**这个假设不成立**：

| 事实 | 数值 |
|---|---|
| 四个块的 LZ77 流解压后长度 | **4096 / 4096 / 4096 / 2048** 字节 |
| 换算成 4bpp 图块 | **128 / 128 / 128 / 64** 张（32 字节/张） |
| 47 个战斗地图描述符的原图图块集长度 | **156 – 276** 字节（**4 – 8** 张图块） |
| 把每张地图的图块集逐张（32 字节）去四个块的图块集合里找 | **47 张地图一张都匹配不上** |
| 四个块解压后的内容在 ROM 里有无逐字节副本 | **没有**（本来就是压缩的） |
| 四个块的 16 色调色板 | 前 16 字节完全相同，末 2 字节不同 |

所以这四块是**关卡/过场自己的 4bpp 图块集**（连同各自的 16 色调色板，
由 BIOS `svc 0x12` 解压到 VRAM `0x06016000`、调色板到 `0x05000380`），
**不是**战斗地图的图块集。

顺带排除：剧情底图表 `0x59903C` 的指针都在 `0x0832xxxx`–`0x0834xxxx` 段，
而这四块在 `0x0812D9E4` 段，**不是同一批数据**。

**因此**：开放项从「四块对应哪四张战斗地图」收窄为「这四组图块集具体对应哪四处场景」——
前者已被证伪，后者仍未定位。

**判死检验**：把任一战斗地图的图块集按 32 字节切片，逐片去四个块解压后的
图块集合里查；只要有一张地图的任何一片命中，「这四块是战斗地图图块集」的
说法就还成立（本轮 47 张地图 **0 命中**，故该说法作废）。

## 2026-10-21 追加：四个块的用途进一步钉死（`0x53DF70`）

### 1. 它们的 VRAM/调色板目标属于 **OBJ（精灵）**，不是 BG

- VRAM 目标 `0x06016000` 落在 **OBJ 图块区**（`0x06010000`..`0x06017FFF`），
  不是字符 BG 区（`0x06000000`..`0x0600FFFF`）；
- 调色板目标 `0x05000380` 落在 **OBJ 调色板 RAM**（`0x05000200`..`0x050003FF`），
  不是 BG 调色板（`0x05000000`..`0x050001FF`）。

⇒ 这四块是**四套 OBJ 4bpp 图块集 + 各自的 16 色调色板**，
不是背景图块、也不是剧情底图。

### 2. 加载器 `0x08072EDC`：下标是**硬编码**的 0/1/2/3

```
0x08072EDC  push {r4, r5, r6, r7, lr}     ; 入口：r0 = 块下标
0x08072F0C  ldr  r4, [pc, #0x2c]          ; 0x0853DF70
0x08072F10  lsls r5, r0, #3              ; 下标 * 8  ← 步长 8 字节
0x08072F14  ldr  r0, [r0]                ; LZ77 图块
0x08072F16  ldr  r1, [pc, #0x28]         ; 0x06016000
0x08072F18  bl   0x809c0e8               ; Lz77UnCompVram
0x08072F20  ldr  r0, [r5]                ; LZ77 调色板
0x08072F22  ldr  r1, [pc, #0x20]         ; 0x05000380
0x08072F24  bl   0x809c0e8
```

四个调用点与它们传进去的**常量下标**：

| 调用点 | 下标 | 上下文 |
|---|---|---|
| `0x0807363A` | **0** | 另一个关卡初始化函数里，`bl 0x807504e` 之后 |
| `0x08073100` | **1** | 状态字节 `[r2+3] == 1` 的分支（`0x080730C0`） |
| `0x0807314A` | **2** | 状态字节 `[r2+3] == 2` 的分支（`0x08073130`） |
| `0x08073196` | **3** | 同函数里的第三分支 |

⇒ **下标不是场景号**：它是「关卡/过场资源档位」，由一个**状态字节**选择。
所以「这四块对应哪四处场景」这个提法本身就不成立 ——
表是**按档位索引的资源表**，不是按场景索引的表。

### 3. 运行时负证据

- 55 个剧情场景逐个调度（`tools/closure_scene_sweep.py`）：加载器 `0x08072F0C` **一次都没命中**；
- 开机流程（标题 → 新游戏 → 开场）：`tools/closure_boot_probe.py` **0 命中**；
- 真实战斗（组 9 / 子 0）：**0 命中**。

⇒ 这套块属于**剧情/战斗之外的第四种模式**（关卡/过场模式），
本轮在探针能到达的范围内**没有触发过**，因此仍无法给出「哪四处场景」。

