## 1. 读者与门控条件（逐指令证）

### 1.1 `items` / `skills` —— `0x08545BE4`

读者 `fn 0x0806D910`：

```
0x0806D916: lsls r0, r0, #0x18
0x0806D918: lsrs r0, r0, #0x14    ; r0 = id & 0xFF
0x0806D91A: ldr  r1, [pc, #0x44]   ; r1 = 0x08545BE4
```

⇒ **16 字节/条**（与旧笔记一致，但下标公式之前没钉死）。

12 个直接调用者，其中真正相关的是
**`fn 0x08081B70`（关卡对象处理器）** 与 **`fn 0x080851F8`**：

```
fn 0x08081B70 的 type-1 分支：
0x08081C36: ldrh r0, [r1, #6]    ; 计数器
0x08081C38: subs r0, #1
0x08081C44: cmp  r0, #0          ; 只有原值 == 1 才继续
0x08081CAA: ldrb r1, [r0, #4]    ; 道具 id
0x08081CAE: ands r0, r1, #0x7F
0x08081CB4: bl   fn 0x0806D910    ; ★ 读者
```

```
fn 0x080851F8（剧情战斗的单位扫描调它）：
0x0808540C: ldrb r0, [r0]        ; 计数字节
0x0808540E: cmp  r5, r0
0x08085410: bhs  0x0808546A      ; 计数为 0 就不进循环
0x08085426: ldrb r3, [r2]        ; id 字节
0x08085428: movs r0, #0x80
0x0808542A: ands r0, r3
0x0808542E: bne  0x0808544C      ; ★ bit7 置位才走读者
0x0808544E: ands r0, r3, #0x7F   ; id = 字节 & 0x7F
0x08085456: bl   fn 0x0806D910    ; ★ 读者
```

`fn 0x080851F8` 的**调用点是剧情战斗的单位扫描**（`0x08074200`）：

```
0x0807421E: cmp  r0, #0        ; 单位 id != 0
0x08074228: cmp  r0, #0        ; unit[0xCC] == 0
0x08074236: cmp  r0, #0        ; unit[0xC0] & 0x70 == 0
0x08074240: cmp  r0, #0xFF     ; unit[0xCD] != 0xFF
0x08074244: cmp  r0, #0        ; unit[0xCD] != 0
0x0807425A: bl   fn 0x080851F8 ; ★
```

**实测（场景 10，相位 `0x0110`）：`0x0807425A` 命中**（单位槽 4），
说明这条路径**在剧情战斗里是自然可达的**；
但 `fn 0x080851F8` 在到达 `0x0808540C` 之前就返回了
（实测 `0x0808540C` / `0x08085426` / `0x08085456` 都没命中），
所以还差 `fn 0x080851F8` 内部 `0x0808523C`–`0x080853B0` 那一段的退出条件。

**⇒ 下一步：把 `fn 0x080851F8` 从 `0x0808523C` 到 `0x080853B0` 逐条走一遍，
找出它在 `0x080853B0` 之前返回的那条分支。**
（已排除的猜测：`unit[0xCD] != 0` 这条已被上游过滤保证，不是原因。）

关卡对象那一侧还有第二个入口：`fn 0x08081B70` 的 type-1 分支要求
关卡对象表里有一条 `type == 1` 且 `record[+6] == 1` 的记录；
而**关卡数据脚本只会产出 type 3/4/5/6**，唯一的 type-1 生产点是
`0x08077528`（`movs r0, #1` → `fn 0x08081024`），在**地图事件解释器**里。

### 1.2 `resource-pointers` —— `0x08596F0C`

读者 `fn 0x0807AE04`，表读在 `0x0807B220`：

```
0x0807AE1E: ldr  r0, [pc, #0x30]  ; 0x02026BE0（场景结构）
0x0807AE22: lsls r4, r1, #2
0x0807AE24: adds r0, #0xC4
0x0807AE26: adds r0, r0, r4
0x0807AE28: ldr  r1, [r0]
0x0807AE2A: ldrb r0, [r1, #4]
0x0807AE2C: cmp  r0, #0
0x0807AE2E: bne  0x0807AE32
0x0807AE30: b    0x0807B268      ; ★ 为 0 就整段跳过
...
0x0807AE3E: ldr  r3, [sp, #0x18]  ; 第二个参数
0x0807AE40: cmp  r3, #7
0x0807AE42: bls  0x0807AE46
0x0807AE44: b    0x0807B05A      ; ★ 参数 > 7 就跳过
0x0807AE46: lsls r0, r3, #2
0x0807AE48: ldr  r1, [pc, #8]     ; 8 项跳转表
0x0807AE4C: ldr  r0, [r0]
0x0807AE4E: mov  pc, r0
```

⇒ **两道门控**：`scene[0xC4 + arg0*4]` 指向的对象的 `+4` 字节必须非零；
且 `arg1 <= 7`（8 路 switch）。表读 `0x0807B220` 属于 **case 7**。

37 个调用点里**只有两个传 7**：`0x0807C3D6` 与 `0x0807C4D6`，
都在 `fn 0x0807B8B8` 里，而且要求它自己的子模式 `r2 == 0`。

**「资源读者就在字体读者下游」这条链（本轮钉死）**：

```
fn 0x0807F064（字宽表 0x0853E596 的读者，handler 表条目 159 的 B 槽）
  └─ 0x0807F0D6 / 0x0807F10C → bl fn 0x0807C5E8
       └─ 0x0807C612: ldr r1, [pc, #0x20]   ; 0x0807B8B9
            └─ fn 0x0807B8B8
                 └─ 0x0807C3D6: movs r1, #7 ; bl fn 0x0807AE04
                      └─ case 7 → 0x0807B220 → 读 0x08596F0C
```

**实测（`--force-dispatch` + 下标字节 = 159）**：
`fn 0x0807C5E8` **命中**（`r0 = 0x0853F068`、`r1 = 2`），
`fn 0x0807B8B8` 的 `0x0807B8D4` **命中**（`r0 = 0x9F`，
且 `fn 0x0807B8B8` 的门控 `字节 <= 0xE3` 通过），
但 `0x0807C3D6` 与 `0x0807B220` 没命中
⇒ **`fn 0x0807B8B8` 内部那个 switch 的取值不是 0**。

那个取值来自 `fn 0x08061D8C`（命令记录分发器）：
它把 `(回调, 参数)` 排进 WRAM 命令表
`0x03000CE8 + (index-1)*4`（回调）与 `0x03000D00 + (index-1)*4`（参数），
记录本体在 `0x03000A8C + index*0x4C`。
**⇒ 这些都是 WRAM 字段，可以写** —— 下一步就是把那条命令记录里的
模式字段改成 0。

**最后一层门控（已定位）**：两个 `arg1 = 7` 的调用点都在 `fn 0x0807B8B8` 里，
而它们的进入条件是**同一个变量 `r8`**：

```
0x0807C4CA: mov  r0, r8
0x0807C4CC: cmp  r0, #1
0x0807C4CE: bne  0x0807C514      ; ★ r8 != 1 -> 跳过 arg1=7 的调用
0x0807C4D0: ldrb r0, [r6, #1]
0x0807C4D2: movs r1, #7
0x0807C4D4: movs r2, #0x10
0x0807C4D6: bl   fn 0x0807AE04
```

`r8` 是被调者保存寄存器，在 `fn 0x0807B8B8` 里有 **6 处赋值**：

| 指令 | r8 的值 |
|---|---|
| `0x0807B8E6: mov r8, r0`（`r0` 刚被 `movs r0,#0` 清零） | **0** |
| `0x0807B9D8: mov r8, r1` | 取决于 r1 |
| `0x0807BAE2: mov r8, r2` | 取决于 r2 |
| `0x0807BB14: mov r8, r0` | 取决于 r0 |

**⇒ 只差把「进入循环时 `r8` 为 1」的那条路径找出来**（或把某处
`r8` 的来源改成 1）。因为探针只能写内存、不能改寄存器，
所以这一步要么找到自然路径，要么找到 `r8` 的**内存来源**去改它。

**判死检验**：
* `fn 0x0807C5E8` 命中 ⇒ 字体读者 → 资源读者这条链是通的；
* `fn 0x0807B8B8` 的 `0x0807B8D4` 命中 ⇒ 它的第一道门控（场景字节 ≤ 0xE3）通过；
* `0x0807C3D6` / `0x0807C4D6` 未命中 ⇒ 缺的**只有** `r8 == 1` 这一条。

## 2. 剧情战斗的**事件 ID 大 switch**（剩下 4 个结构的最短路径）

`fn 0x080732B4`（剧情战斗）里有一整段以**事件 ID** 为键的大 switch
（`0x08073400`–`0x080736DC`）。已定位的两个关键分支：

```
0x08073578: movs  r0, #0xe0
0x0807357A: lsls  r0, r0, #8         ; r0 = 0xE000
0x0807357C: cmp   r6, r0
0x0807357E: bne   0x08073580
0x08073580: bl    fn 0x08074988       ; ★ 机制块
```

`fn 0x08074988` 的块里：

```
0x0807498C: bl    fn 0x08081544       ; → 0x08081AE0 → fn 0x080812DC
                                        → 读 13 项跳转表 0x0808136C
```

**⇒ `mechanism-effects` 的门控 = 战斗事件 ID `0xE000`。**

同理，旧笔记记的「事件链 case **`0x4080`**（读 items 表 `0x08545BE4`）」
落在同一段 switch 里 ⇒ **`items`/`skills` 的门控 = 战斗事件 ID `0x4080`**。

这两条是剩下 4 个结构里**最短的路径**：只要找到一场**事件 ID 含 `0xE000` /
`0x4080` 的剧情战斗**，对应的读者就会自然跑起来。
事件表按场景存放（`ROOT_TABLES["events"] = 0x060EF0`），所以下一步是
**把每个场景的战斗事件表解出来，列出事件 ID 集合**。

```
0x080815A8: ldr   r0, [pc, #0x30]   ; 0x02026604  关卡对象表
0x080815AA: adds  r7, r1, r0
0x080815AC: ldrb  r0, [r7]          ; 对象的 type 字节
0x080815AE: subs  r0, #3
```

## 5. 本轮同时钉死的事实（对上面 4 个结构有用）

1. **`0x0853E698` 是 256 条 8 字节的回调记录表 `(handler_A, handler_B)`**，
   不是「一张处理程序表」。条目 N 的 A 在 `0x0853E698 + N*8`、
   B 在 `0x0853E69C + N*8`；派发点在 `0x0807F942`（A）与 `0x0807F95C`（B），
   都经 `bl 0x0809C114` 调用。
2. **下标字节在 `0x02027428`**（运行时实测：断点 `0x0807F93C` 处 `r0` 就是它的地址），
   **不是**旧笔记写的 `0x02027350`。
3. `fn 0x0807F064`（`fonts` 读者）是 **168/256 条**记录的 B 槽 —— 它是通用的
   「带文字标签的对象」绘制回调。
4. 关卡对象表 `0x02026604` 由 `fn 0x08080ED0` **清零**、由 `fn 0x08081024`
   **填充**（type/sub/id + 4 个 u16 参数，落在记录 +4/+6/+8/+10）。
5. 关卡对象列表由 `fn 0x08080F18` **遍历**建精灵（跳过 type 0/5/6），
   由 `fn 0x08080FA0` 清 `+0xC`。
6. `fn 0x08081B70` 的唯一调用者是 `0x08073688`（剧情战斗），
   它按 type 分派：**type 1 → 道具/技能读者**，type 2 → 建单位。
7. 战斗控制块 `ctrl[2]`（`0x0202680E`）**每回合 ^= 1**（`0x080736B6`），
   `ctrl[0]` 计数到 `0x62`。

## 6. 要闭合这 3 个结构，下一步该做什么

1. **`items` / `skills`** —— **路径已经打通到 `fn 0x080851F8`**（场景 10 的
   `0x0807425A` 自然命中）。缺的是 `fn 0x080851F8` 内部
   `0x0808523C`–`0x080853B0` 那一段的**提前返回条件** ——
   它在 `0x0808540C`（计数字节）之前就退出了。
   **⇒ 把那一段逐条走一遍即可**。
   备选路径：`fn 0x08081B70` 的 type-1 分支（需要关卡对象表里有
   `type == 1` 且 `record[+6] == 1` 的记录；关卡数据脚本只产 type 3/4/5/6，
   唯一的 type-1 生产点是 `0x08077528`）。
2. **`resource-pointers`** —— 需要让 `fn 0x0807AE04` 收到 `arg1 = 7`
   （表读在 case 7）且 `scene[0xC4 + arg0*4]` 的对象 `+4` 字节非零。
   已知调用点只传 `arg1 = 1`（`0x0807F5E0`）或 `arg1 = 3`
   （`0x0807E080`，handler 条目 1 的 A 槽 `fn 0x0807E070`）；
   战斗事件 ID 同样可能提供别的调用点。
