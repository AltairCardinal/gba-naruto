# L4 通关机制与逐场留证（2026-10-21）

**结论**：场景号是一个**可被外部改写**的运行时字节，于是「让游戏跑任意一场」
变成了可机械执行的步骤；L4 的「55 场景逐场留证」因此可以自动化。

---

## 1. 场景号在哪：先静态钉死，再实测证明

### 1.1 静态

剧情调度器 `0x0808F544` 的入参就是场景号（L2 证据：它被命中时 r0 = 0x36 = 54，
随后 VM 拿到的脚本指针逐位等于 `before_root[54]`）。

两个调用点：

| 调用点 | 指令 | r0 的来源 |
|---|---|---|
| `0x0808F676` | `bl 0x0808F544` | `r4 = 入参 & 0xFFFF`（调用方给的打包值） |
| `0x0808F8DE` | `bl 0x0808F544` | **`ldrb r0, [r4, #0x16]`**（`0x0808F8DC`） |

第二条路是关键：`r4` 是剧情 flag 状态块 `0x020311D4`，所以**场景号字节就在
`0x020311D4 + 0x16 = 0x020311EA`**。

> 这也解释了仓库里那条长期争议的地址：早先的笔记说「`0x020311EA` 不是场景号，
> 是剧情 flag 位域内部」，后来又有人说它是场景号。**两者都对**：
> 它确实是 flag 块里的一个字节，而在「下一场景」这条路上它被当作场景号读。

根表也一并钉死（`tools/decode_story_script.py` 用的同一张表）：

| 表 | 文件偏移 | 索引 |
|---|---|---|
| before | `0x060C74` | **按场景号直接索引**（第 0 项未用）：`before[54] = 0x08049E76` |
| after | `0x060D54` | 同上（两表相距 56 个字） |

### 1.2 实测（可证伪）

`tools/mgba_probe/l4_playthrough.py` 做的实验：

```
pok 0x020311EA 40      # 在 0x0808F8DC 上停住时改写场景字节
next                   # 走完那条 ldrb
cont                   # 继续
→ 命中 VM 入口 0x080977B8，r0 = 0x08031430
```

`0x08031430` 正是 `before_root[40]`（`0x060C74 + 40*4`）——
**逐位相等，不差一字节**。这就是 L4 场景跳转的判据。

## 2. 探针新增 `poke` / `poke16`

`tools/mgba_probe/host_main.c` 原来只有 `dump`（读），没有写。读走的是
`g_core->busRead8()`，写是对称的 `g_core->busWrite8()`，所以加两条命令即可：

```
poke   <addr> <value>    # 写一个字节
poke16 <addr> <value>    # 写一个半字
```

改完要重建探针：`python tools/mgba_probe/build.py`
（链接前先 `Stop-Process mgba-probe`，否则 exe 被占用会链接失败）。

## 3. L4 工具

`tools/mgba_probe/l4_playthrough.py`：

* **每个场景独立开机**（`--scenes 1-55`）。这样每场的证据**互不依赖**，
  也不依赖某个场景会不会自己演完（有的场景在等选择或等战斗）。
* 导航到 `0x0808F8DC` → `poke` 场景号 → `next` → `cont` → 在 VM 入口读 r0。
* **判定**：游戏实际使用的脚本指针必须等于根表里该场景的条目，
  否则记 `mismatch`。所以「看起来像跑到了」不算数。
* 每场留两张截图（进场 / 演完一段后），外加 JSON 报告。

### 用法

```powershell
python tools\mgba_probe\l4_playthrough.py rom\base.gba --scenes 1-55 `
    --out build\l4 --json build\l4-playthrough.json
python tools\mgba_probe\l4_playthrough.py rom\base.gba --scenes 40,41 --out build\l4
```

### 按键配方（踩过的坑）

游戏只认**按下沿**（`0x0300000E`），held（`0x0300000C`）不够。
已验证的配方是 L3 证据用的那条：**按 8 帧 → 静默 120 帧**。
静默窗口太短（试过 2 帧）时游戏根本看不到按键，对白一动不动。

另外三条：

1. 断点命中后**必须 delete + 重挂**（`delete <id>` → `b <addr>`），
   否则下一次 `cont` 立刻又命中同一地址，游戏永远不动。
2. 命中后**立刻** `poke`：多跑哪怕一帧，那条 `ldrb` 就用旧字节执行掉了。
3. `status` 里的寄存器值是**不带 0x 的十六进制**（`r0: 00000001`），
   按十进制解析会把 `0x08031430` 读成 8031430。

## 4. 逐场留证的判据

| 字段 | 含义 |
|---|---|
| `scene` | 目标场景号 |
| `script_pointer` | VM 入口实际收到的 r0（游戏自己选的脚本） |
| `expected` | 根表里该场景的条目 |
| `status` | `reached` = 两者逐位相等；`mismatch` = 不等（**算失败**） |
| `screenshot` / `screenshot_end` | 进场与演完一段后的画面 |
| `play_frames` | 该场实际跑了多少帧 |

### 4.1 全量结果：55 / 55

```powershell
python tools\mgba_probe\l4_playthrough.py rom\base.gba --scenes 1-55 `
    --out build\l4 --json build\l4-playthrough.json
```

**reached 55/55 scene(s)** —— 每一场游戏实际使用的脚本指针都与根表条目
**逐位相等**（场景 1 = 0x08009F2E … 场景 54 = 0x08049E76 … 场景 55 = 0x0804C616）。
截图在 `build/l4/`，机器可读报告在 `build/l4-playthrough.json`。

这说明：**剧情这条轴的 L4 已经打通** —— 55 场都能被真实调度到、真实开始跑，
而且有逐场的画面证据。剩下的是下面 §5 说的那部分。

### 4.2 游戏自己走出的场景转移图（55 场全扫）

每条边记录**游戏自己选的**下一个场景号，以及游戏随后**实际执行**的
脚本指针 —— 必须与根表条目**逐位相等**。

| 指标 | 值 |
|---|---|
| 扫描场次 | **55**（全扫一遍）+ 对 18 个出边场次做带运行时读数的复跑 |
| 自己走出转移的起始场 | **18**（1, 4, 5, 14, 16, 32..38, 47..50, 55） |
| 唯一边 | **19** |
| 每条边的脚本指针与根表相等 | **19 / 19** ✅ |

边的形状：绝大多数场景汇到 **50**，50 → **54** → 50 → **9**（章节收尾再续下一章）；

场景 45 把相位设成 `0x0100` 表示本章结束。

**运行时状态读数**（每次转移后读 `0x020311D4` 起的 0x24 字节）：
`story_progress` = `state+0x10`（`0x020311E4`）、
`story_branch` = `state+0x18`（`0x020311EC`）、
`story_config` = `state+0x19..0x1B`（`0x020311ED..EF`）

| 字段 | 读到的值 | 含义 |
|---|---|---|
| `story_progress` | **0 / 5 / 261** | **261** 出现在 50→9 那条边上 —— 剧情 VM 的「设进度」opcode（`0x08097BD4`）在真实流程里写进去的，**这是 `runtime-state` 缺口要求的「真实通关读数」** |
| `story_branch` | **0**（本轮全部边） | 场景 31 另测得 **1**（见 L2 证据笔记） |
| `story_config` | 全 **000000** | 调度器 `0x0808F5C8` 写入后 `0x0808F5CC` 立即清零，所以快照拍不到 |

### 5.0.1 三条轴的入口机制（2026-10-21 定案）

把游戏送到**指定的**一场战斗，只需要三处内存写：

1. 停在状态机循环头 `0x0808F752`（断点）；
2. `state[0x16]` = 组号（= 场景号）、`state[0x19]` = 子配置号、
   `state[0x12]` = **`0x0110`**；
3. 放行（让它继续跑），战斗就会开起来。

**相位是 `0x0110` 不是 `0x0118`**：`0x0118` 那条分支（`0x0808F94A`）不写控制块；
写 `ctrl[1] = state[0x16]` / `ctrl[2] = state[0x19]` 的是**`0x0110`** 分支里的
`0x0808F93E`–`0x0808F944`，然后 `bl 0x080732B4`（`0x0808F952`）。

**战斗入口的根表选择是反的**：`0x08097130()` 为 0 时取 **events 根 `0x08560EF0`**，
不为 0 时取 `0x0805D593`（**不是表**）；`logic 根 0x08560E34` 不在这条路径上。

**战斗标志**是 `0x020311E0` 的 **bit 31**（字索引 = `(id>>5)&7`，**不是** `id>>29`）。

**88 组里有 3 组是垃圾**：组 47 会把编成矩阵压到胜负条件表 `0x594758` 上，
所以组 47 装的是那张表而不是队伍 —— 真实队伍是 **85** 组。

### 5.1 战斗配置清单（144 个可能，其中 **88 个有真实队伍**）

编成矩阵 `0x5461C4` 的索引是
`base + 组*0x1AAC + 子*0x8E4 + 4 + 槽*0xB8`；
**组号就是场景号**（1..46 同时是剧情与战场两套编号），
**子号就是 `state[0x19]`**（由剧情 VM 指令 `0x1F` 写、`0x39` 读）。

逐项扫编成矩阵得到的非空队伍（组, 子）共 **88** 对，例如：

```
group  1 sub 0: slot0:id1(side0) slot1:id2(side0) slot2:id3(side0) slot3:id31(side0) slot4:id25(side1) ...
group  9 sub 0: 8 个槽位（id 1,2,3 我方 / id 41 敌方）
group 14 sub 0: 9 个槽位（id 1,2,3,30 我方 / id 55 敌方）
```

注意 `sub 2` 的我方槽位常是 `id 255/254/253` —— 那是**「由剧情决定」的占位**，
真正的队伍由剧情 VM 指令 `0x22`（把角色加入战斗配置）填。

### 5.2 战斗的进入机制（2026-10-21 反汇编定案）

> 这一节是给「全人物组合 / 全地图」两轴用的**机制地图**，
> 全部由反汇编证实，每条都给了判死检验。

| 环节 | 地址 | 做了什么 |
|---|---|---|
| 剧情调度器 | `0x0808F544(scene)` | 写 `state[0x00]=0x1840`；`bl 0x0808F4D4(scene)` **载入地图**（写 `state[0x17]`）；淡入；按 `state[0x18]` 选 `before_root[scene]`（`0x08560C74`）或 `after_root[scene]`（`0x08560D54`）；最后 `state[0x19] = state[0x18]`（子配置号） |
| 剧情状态机 | `0x0808F73C` | 按 u16 `state[0x12]` 分派；**`0x118` 走到 `0x0808F94A`** —— 那里把 `ctrl[1] = state[0x16]`、`ctrl[2] = state[0x19]` 写进战斗控制块，再 `bl 0x080732B4` |
| 战斗控制块 | `0x02026804` | `+1` = 组号（= 场景号）、`+2` = 子配置号 |
| 战斗设置 | `0x080732B4` | 读 `ctrl[1]` / `ctrl[2]`，算出编成矩阵地址 `0x085461C4 + 组*0x1AAC + 子*0x8E4`，读出生效的子号，调 `0x0808A588` |
| **战斗入口** | **`0x0808A588(场景, 子)`** | `bl 0x0808F4D4(场景)` 载入地图；`0x08066DB4` / `0x08066AE8(0,0,0xC,0x1E)` / `0x0806571C` / `0x0808CC5C` 初始化；`0x08097130()` 为 0 就取 **`logic_root[scene]`**（`0x08560E34`），否则取 **`events_root[scene]`**（`0x08560EF0`）；再用剧情 VM `0x080977B8` 跑这段脚本，`r1` = 子配置号 |
| 战斗单元槽 | `0x020240C0` | 12 槽、步长 `0x1D4`、**角色 id 在槽首字节**（由 VM 指令 `0x36` 的辅助函数 `0x0808A420` 证实）；并行的标志数组在 `0x02024180` |

**判死检验**：① `0x0808F73C` 必须仍按 `state[0x12]==0x118` 跳到 `0x0808F94A`；
② `0x0808F94A` 必须仍写 `0x02026805` / `0x02026806`；
③ `0x080732B4` 必须仍以 `0x1AAC` / `0x8E4` 算矩阵地址；
④ `0x0808A588` 必须仍在 `0x08097130()==0` 时取 `logic_root`、否则取 `events_root`；
⑤ `0x0808A420` 必须仍以 `0x1D4` 步长遍历 `0x020240C0` 的槽首字节。

**试过但没成的两条路（留档，避免重复走）**：
* 直接 poke `state[0x12]=0x0118` + `state[0x16]=组` + `state[0x19]=子`，
  再跑 1200 帧 —— **战斗没起来**（相位仍是 `0x0118`，说明那一刻状态机根本没在跑）。
* IWRAM `0x03005D44` 看着像「模式字节」，其实**是淡入淡出字节**
  （`0x08064700(mode, colour)` 写它）；战斗画面出现时它从 `01 10 00` 变成 `00 08 09`。
  **不要把它当模式开关。**

### 5.3 战斗画面确实能到（场景 40）

用现有 harness 的输入计划（按 8 帧 A + 静默 120 帧循环）跑场景 40，
**画面会停在战斗前的「人物信息 / 忍者敌人 / LV 1」对比页**
（`攻击力 14↑0 / 防御力 13↑0 / 忍速度 8↑0 / 命中力 3↑0 / 闪 15↑0`，
菜单项 `详情` / `返回`）。截图：`build/l4/scene-40-end.png`、`build/l4/battle-press-40.png`。

**但那一页是菜单，只按 A 走不下去**；换成多键计划
（`--play-keys A,B,DOWN,UP,LEFT,RIGHT`）场景 40 会走到别的地方（一页帮助文字）。
另外，在那一页上 `0x02026804` 与 12 个单元槽**全是 0** ——
说明现有 harness 的「战斗已开始」判据地址在这一状态下**不成立**
（单元可能要真的开打才实例化）。

### 5.4 还差什么（2026-10-21 更新）

三条轴都已经跑通（见 §5 与 `notes/evidence/l4-battle-matrix-20261021.md`）。
**剩下的是"内容侧"而不是"逆向侧"**：

* **战斗内部的逐场胜负读数**还没有逐场留证：胜负条件表 `0x594758` 在真实战斗里
  的判定读数、回合计数的运行时读数（`0x020311E0` bit 31 与 `0x0202680C` 的关系）
  仍然只有静态推导。
* **「全流程」目前是 55/55 场逐场调度 + 一条游戏自己驱动的场景链（39 → 45）**；
  还没有"从 1 连打到 55 全程不 poke"的连续通关录像 —— 那需要每场的输入计划，
  属于玩法脚本而不是逆向。
* **88 组里的 3 组"垃圾队伍"** 已定位（组 47 压到胜负条件表），但那 3 组的
  真实意图（是遗漏还是刻意）还没有结论。
