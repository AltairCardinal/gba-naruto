## 0. 一句话结论（先看这里）

**13 处（不含任务书已覆盖的 `vm_0x08`）的档位分布**：

| 档位 | 含义 | 处数 | 是哪几处 |
|---|---|---|---|
| **A** | 自然场景跑到并取证 | **4** | `name_cell_count`、`name_len`、`name_draw`、`vm_0x0E_second_name` |
| **B** | 受控触发取证 | **9** | `battle_msg_name`、`cmd_msg_name`、`cmd_msg_name_copy`、`battle_log_name`、`battle_log_name_2`、`cmd_msg_name_copy_2`、`cmd_msg_name_copy_3`、`battle_msg_name_2`、`cmd_msg_name_append` |
| **C** | 只有静态判定 | **0** | （没有「连静态都说不清」的） |

**加上任务书原来就覆盖的 `vm_0x08`（A 档），14 处补丁的总体分布 = A 5 / B 9 / C 0。**

**B 档的强度**：9 处 B 档**不是**「静态推断」——每一处都在**真实 CPU** 上
单步走完了补丁窗口，拿到了精确的寄存器轨迹，并且
**算出的槽位 = `0x085A57C4 + id*4`（14/14 正确）**、
**解引用出的指针落在串池 `0x085DFBEC..0x085DFD3F` 内（14/14）**、
**那个地址的字形码解出来是「鸣人测试」（14/14）** ——
正是转换版把 id 1 改长后的名字。
⇒ **变长化后的 14 处取名代码，在真实 CPU 上语义全部正确。**
剩下没做的是**「这些界面有没有被打开」**（A 档），不是「代码对不对」。

> ⚠️ **本轮最重要的结论（与任务书的前提不同）**：
> **战斗消息里带说话人的那个名字框，走的是剧情 VM 的 `op 0x08`（读者 12），
> 不是任务书假设的「读者 1 / 读者 10」。**

> 而 **读者 1 / 10 的断点一次都没命中**，命中的是 `vm_0x08`。
> ⇒ 「战斗消息 = 读者 1/10」这条前提**不成立**（详见 §3.1）。

（脚本里的 `battle` 路线跑的是这次全扫筛出来的 **10 组**代表性编成。）

**战斗路 / 场景路的配方来源**：`notes/evidence/l2-runtime-evidence-20261021.md` §B.4
与 `tools/mgba_probe/l4_battle_matrix.py`（三次内存写强制进战斗 / 强制进剧情场景）。
**关键点**：战斗单位是在**战斗初始化**时创建的，名字在**消息显示之前**就已经
解析好了 ⇒ **读者断点必须在战斗开始之前就挂上**（否则只会看到 0 命中）。

> ⚠️ **三个踩过的坑**（详见 §4.1）：
> ① `poke16` 的值必须带 `0x` 前缀（`0110` 会被按八进制解析成 `0x48`）；
> ② 受控触发写寄存器必须**先基址后 id**（变体 B/C 的两个角色是同一个寄存器）；
> ③ 受控触发单步前必须**关 IRQ**（否则被 VBlank IRQ 打断，现场被冲掉）。

### 1.2 受控触发（B 档）

在无头 mGBA 里：

1. `load build/l2-states/battle.ss9`（拿到一个干净的 CPU 现场）；
2. `w/r cpsr 0xFF` —— System 模式 + Thumb + **关掉 IRQ/FIQ**
   （⚠️ 不关的话单步途中会被 VBlank IRQ 打断，IRQ 向量在 BIOS `0x00000188`，
   现场会被冲掉；实测踩过）；
3. **先** `w/r <基址寄存器> 0x085A57C4`（变体 D 才需要预设基址；变体 A/B/C 的基址
   由补丁自己的 `ldr rX,[pc,#imm]` 装进去），
   **再** `w/r <id寄存器> 1`（说话人 id）
   —— ⚠️ **顺序不能反**：变体 B/C 的 id 寄存器与基址寄存器是同一个，
   先写 id 会被后面的基址覆盖（算出来的槽位变成 `基址 + 基址*4`，一个越界地址）；
4. `w/r pc <补丁起始地址>` —— 直接跳到**补丁窗口的第一条指令**；
5. `next` 逐条单步，**每一步都读 `status`**（mGBA 的 `next` 是「执行当前指令、
   PC 前移 2」，所以单步后的寄存器**就是那条指令的真实现场**）。

⇒ 这条路拿到的是**真实 CPU 上、补丁后代码的精确寄存器轨迹**，
不依赖断点命中快照（断点命中时的快照**不是**那条指令的现场，见
`notes/evidence/speaker-name-freeze-trace-20261023.md` §3.1）。

## 3. 运行时实测

### 3.1 战斗路：带说话人的战斗消息框 **走的是读者 12（`vm_0x08`）**，不是读者 1/10

本轮真的进了一场战斗（`group=1 sub=0`，战斗单位 6 个：
`id 1/2/3/31/25/26`），并截到了带说话人的战斗消息框：

- 证据截图：`build/speaker-reader-shots/hit_battle_08097A14.png`
  （战斗消息框左上角画着紫色的 **「鸣人测试」**，下面是对白「……什么……！！」）
- 关键证据：战斗消息框里画的是 **「鸣人测试」** —— 这正是转换版把 id 1
  （鸣人）改长后的名字 ⇒ **名字确实是从说话人名表取出来的**；
- 同一时刻的断点统计：`vm_0x08` 命中，**读者 1 / 10 命中 0 次**。

⇒ **任务书的前提「战斗消息 = 读者 1/10」不成立**；战斗消息的名字框由
剧情 VM 的 `op 0x08` 渲染（读者 12）。
（读者 1 / 10 的所属函数 `0x08078E38` / `0x080952C8` 在 ROM 里是
**函数指针表**里的一项 —— `0x08079378` / `0x0808E3E0` / `0x08095814` /
`0x08095C64` —— 属于**别的消息框类型**，本轮三条路线都没实例化到那一种。）

### 3.2 剧情路 / 场景路：读者 8（`name_len` / `name_draw`）能被自然走到

剧情路线推到后面几屏时，**「名字板」那条绘制路径**（`fn 0x0808D230`：
先 `strlen` 再逐字形画）被执行到 ⇒ 读者 8 的两处都被命中。
「剧情场景分派路」（相位 `0x0030` ⇒ 直接进第 N 号场景）里，
**场景 2** 就第一次命中读者 8（每场景 10 次按键时是场景 18 才命中）。

> ⚠️ **踩过的坑**：任务书给的「剧情开场」按键方案（`START` + 连按 `A`）
> 只会命中 `vm_0x08`；要把剧情推得更远（方案重复若干遍、加上菜单键）
> 才会走到读者 8 那条路径。

### 3.3 `op 0x0E`（读者 12 的第二处）：**场景 53 的深处**才出现

剧情场景分派路里，`op 0x0E`（设两个名字）**只在场景 53** 出现，
而且**每个场景要按 40 次 A**（10 次按键只走到场景 53 的前半段）。

首次命中时的截图 `build/speaker-reader-shots/hit_scene_08097A30.png`
⇒ 消息框里画的是 **两个名字：「鸣人测试　小樱」** ——
第一个是转换版改长后的 id 1，第二个是 id 3（小樱，**没改**），
第二个名字的位置比第一个右移 2 格（正是 `op 0x0E` 处理器里
`state[0x0c]`（x）+2 的行为）。

⭐ 这是**「两个名字同时取、其中一个被改长」的直接画面证据** ——
变长化后指针表/串池在**同一条指令序列里连续解引用两次**也没有出问题。

### 3.4 战斗编成矩阵全扫（144 组）：**读者 7（`name_cell_count`）只在一部分编成里被走到**

把 48 组 × 3 个子配置**全部**跑一遍（每组 6 次 A、14 条读者断点全挂），
命中统计：**`vm_0x08` 236 次、`name_cell_count` 9 次、其余 12 处 0 次**。

`name_cell_count` 的 9 次命中分别来自：

| 编成 | 命中位置 |
|---|---|
| `group 1 / sub 1` | press 3 |
| `group 31 / sub 1` | press 3 |
| `group 32..38 / sub 0` | 各 press 3 |

⇒ **`group 1 / sub 0` 走不到读者 7**，`group 1 / sub 1` 走得到。
（`name_cell_count` 属于 `fn 0x08089310` ← `fn 0x0808A0F0` ←
`fn 0x0808F618` ← `fn 0x0808F654`（剧情状态机区），
而 `fn 0x0808F618` 里还有一条 `bl 0x08088F10` 的分支 ——
某些编成才会走到那条分支。）

**首次命中时的截图（脚本自动抓的）**：
`build/speaker-reader-shots/hit_battle_08089364.png`
⇒ 读者 7 所在的界面是**战斗结算画面**（「经验值 / 达人试炼」标签页 +
角色立绘 + 经验值/金钱/回合/合击 统计表），**不是**指令菜单。

### 3.4b 读者 8（`name_len` / `name_draw`）的界面 = **队伍 / 装备画面（队形·装备）的名字板**

首次命中时的截图 `build/speaker-reader-shots/hit_story_0808D29C.png`
⇒ 画面是「队形·装备」页：左上角立绘旁边画着 **「鸣人测试」**，
下面三个成员格显示 LV / 体力 / 忍力 / 查克拉。

⭐ **这是本轮最强的一条 A 档证据**：截图里那个名字框**画的就是转换版改长后的
「鸣人测试」**（原版只有「鸣人」两个字的宽度）⇒
**变长后的名字在自然场景里被正确画出来了**，而且是在**读者 8** 这条

`tools/mgba_probe/speaker_namebox_check.py` 单独验过）。

### 3.5 到不了的 9 处：具体试过什么、卡在哪

三条路线都试过，**0 命中**：

| 路线 | 具体做法 | 结果 |
|---|---|---|
| `story` | 开机 1500 帧 → `START` → 连按 `A`（含 `B/UP/DOWN/LEFT/RIGHT/START/SELECT`，方案重复 12 遍 = 240 次按键） | 只有 `vm_0x08`、`name_len`、`name_draw` 命中 |
| `scene` | 读 `l2-states/battle.ss9` → 相位 `0x0030` → 逐个派发**场景 1..55**（每个场景前重新 load 存档），每个场景按 40 次 `A`（共 2200 次按键） | 只有 `vm_0x08`、`name_len`、`name_draw`、`vm_0x0E_second_name` 命中 |
| `battle` | 读 `l2-states/battle.ss9` → 相位 `0x0110` → 逐个派发**10 组编成**（`group 1/sub 0`、`1/sub 1`、`31/sub 1`、`32..38/sub 0`），每组 6 次 `A` | 只有 `vm_0x08`、`name_cell_count` 命中 |
| `battle`（**144 场全扫**，本轮单独做的探索） | 48 组 × 3 个子配置全部跑一遍，每场 6 次 `A`，14 条读者断点全挂 | 只有 `vm_0x08`（236 次）、`name_cell_count`（9 次）命中 |

**结论（诚实版）**：读者 1/2/3/4/5/6/9/10/11 这 **9 处**在本轮的三条路线
（含 144 场战斗全扫）里**一次都没被执行到** ⇒ 它们的界面**没被打开**，
不是「补丁坏了」。

**已排除的可能**：

- 不是「战斗跑不起来」：战斗确实装载了（6 个单位、地图号 01），战斗消息框
  也确实画出了带说话人的名字（而且那个名字是对的）。
- 不是「断点机制失灵」：同一次运行里 `vm_0x08` / `name_cell_count` /
  `name_len` / `name_draw` 都命中了，**断点挂的是同一种地址**。
- 不是「变长化把读者改死了」：这 9 处的补丁字节与清单逐字节相同，

**踩过的三个坑（写下来给下一个接手的人）**：

1. **变体 B/C 的 id 寄存器与基址寄存器是同一个**（读者 2：id 在 r1，
   而 `ldr r1,[pc,#imm]` 把基址也装进 r1；读者 3/4/5/6/9/11 是 id 与基址都在 r0）。
   ⇒ 写寄存器**必须「先写基址、再写 id」**，否则 id 被基址覆盖，
   算出来的槽位是 `基址 + 基址*4`（一个越界地址）。
2. **单步前必须关掉 IRQ**（`w/r cpsr 0xFF`）：否则单步途中被 VBlank IRQ 打断，
   CPU 进 BIOS 的 IRQ 向量 `0x00000188`，现场被冲掉（实测表现为
   `r0 = 0`、指针读成 `0x00000000`）。
3. **`poke16` 的值必须带 `0x` 前缀**：`0110`（无前缀）会被 mGBA 的 CLI
   按**八进制**解析成 `0x48` ⇒ 相位没设对 ⇒ 战斗根本没开始，
   表现是「画面一步都不动」。

## 5. 判据与纪律（怎么复核）

* **判「能跑 / 卡死」只看画面推进**：每按一次 A 截一张 mGBA 渲染缓冲，
  比相邻两张哈希，**最后 3 张相同** ⇒ 冻结。
  ⚠️ **加了一个交叉验证**（本轮新增）：只有当 CPU **同时确实在 BIOS 异常向量里**
  （PC < `0x10000` 且 CPSR 模式 ∈ {`0x17` Abort, `0x1B` Undefined}），
  才判「卡死」；否则标成「等待输入」——
  游戏停在对话框上等按键时屏幕本来就不推进，那是**正常状态**，不是卡死
  （沿用 `tools/mgba_probe/speaker_freeze_trace.py` 的 `deadlocked()` 判据）。
* **判定用的运行只挂一个永不命中的断点 `0x08FFFFFE`**；
  **辅助断点只用来取命中数与截图，不参与判定**；
  **读者覆盖扫描一次只挂一条读者断点**。
* **寄存器级证据一律用受控触发的单步**，不用断点命中时的快照 ——
  mGBA 的断点是**软件断点**（原地改成 `BE00: bkpt`），
  命中时 CPU 继续跑完那一帧，**快照里的 PC/寄存器不是那条指令的现场**
  （实测首个快照 PC = `0x0806112A`，在剧情 VM 里，不在断点地址）。
