## 0. 结论摘要（先看这个）

| 项 | 结论 |
|---|---|
| 表基址 | ROM `0x085A57C4`（文件 `0x5A57C4`），**12 字节/条** |
| 内容 | **NUL 结尾的字符串**，元素是游戏自己的**双字节字形码**（lead 0x80–0x9F，内存里 lead 在前） |
| 真实条目数 | **63 条（id 0..62）**；`0x085A57C4 + 63*12 = 0x085A5AB8` **不是**本表的第 64 条，而是**另一张 19 字节步长「全名表」的第 0 条** |
| 原生读者 | **恰好 12 个**，**全部是「取名字」读者**，**零个「取调色板颜色」读者** |
| `tools/table_registry.py` 的登记 | 把它登记成 `palette_source_table`（每条 = u32 色值 + 8 字节 0）—— **判定错误**，应改成「说话人简称表」 |
| 名字的实际上限 | 槽里 **最多 5 个字形**（10 B + 1 B NUL = 11 B，12 B 槽还剩 1 B）；**本 ROM 实际最长 4 个字**（id 39/40「大蛇　头/尾」） |
| 变长可行性 | **可行且干净**：12 个读者全都按「NUL 结尾字符串」消费，改成「指针表 + 变长串池」后 **每个读者只多 1 条指令**，且改完代码**每处还少 2 字节**，无代码空间问题 |

## 1. 全部原生读者（12 个）

穷举方法：对全 ROM 做 Thumb-1 `ldr rX,[pc,#imm]` 字面量索引（目标字 = `((A+4)&~3) + imm8*4`），
再筛出值落在 `0x085A57C4..0x085A5AC4` 的字面量。**结果：基址 `0x085A57C4` 恰好 12 个读者**，
表内没有别的偏移被引用。

| # | 读者指令（ROM） | 字面量位置（ROM / 文件） | 所属函数 | 消费方式 | 类型 |
|---|---|---|---|---|---|

**为什么断定「没有取色读者」**：
`0x0809C4DC` 是逐字节复制到 NUL 的 **strcpy**；`0x0809C528` 是 **strlen**；
`0x0806626C` 是文本渲染器（见 §2）；`0x08067110` 是「文本显示格数」计数器；
`0x08066EFC` / `0x0808CE8C` / `0x08068660` 全部按 NUL 终止遍历。
另外，按 u32 读出来的 `0x9A9A5992`、`0xC8949892` 等**根本不是合法 BGR555 颜色**
（bit15..0 全不满足），后 8 字节是 **NUL 填充**而不是调色板数据。

### 1.1 顺带发现：旁边还有一张 **19 字节步长的「全名表」**

- 基址 ROM `0x085A5AB8`（文件 `0x5A5AB8`），**19 字节/条**，3 个读者：
  `0x08077EE2` / `0x0808B036` / `0x080939D6`。
- 步长 19 的算法（`0x0808B036` 处）：
  `id*4 → +id = id*5 → *4 = id*20 → -id = id*19`。
- 内容是**全名**：`漩涡鸣人 / 宇智波佐助 / 春野樱 / 山中井野 / 奈良鹿丸 / 秋道丁次 / 旗木卡卡西 / …`
  最长 **5 个字形**（`宇智波佐助`、`旗木卡卡西`、`第三代火影`、`猿飞阿斯玛`、`桃地再不斩`、`卡多的手下`）。
- **`0x085A5AB8` 同时是 12 字节表的第 64 槽（id 63）的地址**（`0x085A57C4 + 63*12`）。
  两张表在 ROM 里**首尾相接且共用这一条**：`id 63` 与 `id 0` 内容相同（都是「没有」`92 59 9A 9A`）。
  ⇒ **就地改写 12 字节表会毁掉全名表的第 0 条**（见 §4 风险）。

## 2. 取名读者（`0x08097A12`）逐指令解剖

handler `0x080979E8`（`0x08` 与 `0x0E` 共用）：

```
0x080979E8  movs r0, #0
0x080979EA  bl   #0x80971c0      ; r0 = 消息框对象（slot 0）
0x080979EE  adds r6, r0, #0      ; r6 = 框对象
0x080979F0  ldrb r0, [r6, #0x13]
0x080979F2  bl   #0x8066d14
0x080979F6  ldr  r0, [r6]
0x080979F8  movs r1, #0x11
0x080979FA  rsbs r1, r1, #0
0x080979FC  ands r0, r1
0x080979FE  str  r0, [r6]
0x08097A00  movs r0, #0
0x08097A02  strh r0, [r6, #0xc]  ; x = 0
0x08097A04  strh r0, [r6, #0xe]  ; y = 0
0x08097A06  movs r0, #2
0x08097A08  strb r0, [r6, #0x12] ; 颜色 = 2
0x08097A0A  ldrb r0, [r7, #1]    ; ★ 操作数字节 = id
0x08097A0C  lsls r1, r0, #1      ; ★ r1 = id*2
0x08097A0E  adds r1, r1, r0      ; ★ r1 = id*3
0x08097A10  lsls r1, r1, #2      ; ★ r1 = id*12      ← 「12」是移位+加法算出来的
0x08097A12  ldr  r4, [pc, #0x2c]  ; ★ r4 = 0x085A57C4（字面量在 0x08097A40）
0x08097A14  adds r1, r1, r4      ; ★ r1 = 表基址 + id*12  ← 字符串首地址
0x08097A16  adds r0, r6, #0      ;   r0 = 框对象
0x08097A18  bl   #0x806626c      ; ★ 文本渲染器(state, 字符串指针)
```

**结论**：
- 步长 **12 = `(id*2 + id) * 4`**（`lsls`+`adds`+`lsls`，**没有乘法指令**），12 个读者**全都是这同一套算法**。
- 名字**没有**被复制到任何字节缓冲：直接把**指针**交给渲染器 `0x0806626C`，渲染器**当场逐字形画进框的 tilemap**。
- `0x08097A1C..0x08097A3E` 是 `0x0E`（设两个名字）分支，第二个名字用同一套 `id*12` 算法（`0x08097A2A..0x08097A30`），
  并把 `state[0x0c]`（x）+2 让第二个名字往右挪。

### 2.1 渲染器 `0x0806626C` 怎么「读到 0x0000 为止」

```
0x08066276  adds r6, r0, #0      ; r6 = 目标框对象
0x08066278  str  r1, [sp, #0x1c] ; 存源指针
0x0806627A  adds r2, r1, #0      ; r2 = 当前源游标
0x0806627C  b    #0x806671e
...
0x0806627E  ldrb r0, [r2]        ; 取首字节
0x08066280  lsls r0, r0, #0x18
0x08066282  lsrs r1, r0, #0x18
0x08066284  cmp  r1, #0x1f
0x08066286  bhi  #0x80662dc      ; >= 0x20：不是控制码
                                        ; 0x80..0xFF → 双字节字形
0x080662DC  cmp  r0, #0
0x080662DE  bge  #0x80663b4      ; 0x20..0x7F → 单字节 ASCII
0x080662E0  cmp  r1, #0x9f
0x080662E2  bls  #0x80662f8      ; lead <= 0x9F → 游戏字体（lead 0x80..0x9F）
0x080662F8  ldr  r0, [sp, #0x1c]
0x080662FA  ldrb r1, [r0]        ; lead
0x080662FC  lsls r1, r1, #8
0x080662FE  ldrb r0, [r0, #1]    ; trail
0x08066300  orrs r0, r1          ; r0 = (lead<<8)|trail  ← 大端双字节字形码
0x08066302  ldrb r1, [r6, #0x12]
0x08066304  add  r2, sp, #0x14
0x08066306  bl   #0x8065f84      ; 画一个字形
...
0x08066396  ldrh r0, [r6, #0xc]  ; x += 1（每字形一列）
0x0806639C  ldr  r0, [sp, #0x1c]
0x0806639E  adds r0, #2           ; 源游标 += 2（一个双字节字形）
0x0806671C  ldr  r2, [sp, #0x1c]
0x0806671E  ldrb r0, [r2]        ; ★ 终止判定
0x08066720  cmp  r0, #0
0x08066722  beq  #0x8066726       ; ★ 遇到 0x00 → 结束
0x08066724  b    #0x806627e       ; 否则继续下一个字形
```

⇒ **终止符是单个 `0x00` 字节**（不是 `0x0000`）。名字在 ROM 里就是
`[lead trail]×n` 后跟一个 `0x00`，后面是 `0x00` 填充。

### 2.2 名字画到哪儿（框的几何）

- 框对象：`0x08066AE8` 建的文字对象，`obj+0x08` = **宽 30 格**，`obj+0x0A` = **高 8 格**，
  tilemap 在 `obj+0x1E`。
- 名字渲染起点：x = `state[0x0c]`、y = `state[0x0e]`；渲染器实际落格
  `行 = y+1`、`列 = x + 1`（无 0x400 标志）或 `x + 3`（带 0x400 标志，即「带说话人」模式）。
- **实测**（无头 mGBA，断在 `0x08097A4A`，即名字画完之后）：
  框对象 `0x0200A8A4`，宽 30 高 8，名字「伊鲁卡」的 3 个字形落在 **第 1–2 行、第 3–5 列**
  （tile `F130/F132/F134` + `F131/F133/F135`，每个字形 2 格高）。
- `op 0x08` 结束时把光标设成 `(0,2)`，后面的 `op 0x01`（普通对白）就在第 3 行起画；
  `op 0x01`（`0x080978DC`）**沿用当前光标**，所以名字行不会被台词覆盖。
- **屏幕宽度限制**：框宽 30 格，渲染器在第 24 / 28 列处折行（`0x080664E2` / `0x080664F8`）。
  ⇒ 名字实际可显示 **约 24–28 个字形**；再长会折到台词行。**这才是真正的上限，不是 12 字节槽。**

## 3. 名字的存储上限

| 项 | 值 |
|---|---|
| 槽大小 | 12 字节 = 6 个双字节格 |
| 终止符 | **1 字节 `0x00`**（实测：id 8 = `99 8A 00 …`，NUL 在偏移 2） |
| 槽内理论上限 | **5 个字形**（10 B）+ 1 B NUL = 11 B，**还剩 1 B 空闲** |
| 本 ROM 实际最长 | **4 个字形**（8 B）：id 39 = `8A F0 95 7D 81 40 97 55`＝「大蛇　头」；id 40 ＝「大蛇　尾」 |
| 次长 | 3 个字形：id 7/42「卡卡西」、14「我爱罗」、15/58「勘九郎」、29「大蛇丸」、30「木叶丸」、31「达兹纳」、44「伊鲁卡」、45「阿斯玛」、48「惠比斯」、49「伊那里」、52「伊比喜」 |
| 全 63 条名字总长 | **331 字节**（含各自的 NUL） |

各槽尾字节分布：**62 条**尾 6 字节全 `00`；id 39/40 尾 4 字节含一个字形码（`97 55` / `97 AF`）。

### 3.1 脚本实际用到的 id

（`tools/decode_story_script.py` 走查全部 55 个剧情场景）
- `op 0x08`：49 个不同 id，范围 **1..61**。

## 4. 变长改法评估

### 结论先说：**推荐 (C)，具体形态 =「新指针表（步长 4）+ 变长串池」**

改动点只有两类：
1. **12 个字面量字**：`0x085A57C4` → 新指针表基址（零风险：每个字只有唯一读者）。
2. **12 处代码**：把 5 条指令换成 5 条（4 条新指令 + 1 条 `nop`），**字节数不变**，**不挪动任何后续代码**。

统一改法（12 个读者的形状完全一致）：

```
旧：  <3 条算 id*12>            ldr rB,[pc,#imm]   adds rD,rD,rB
新：  lsls rD,id,#2   (id*4)    ldr rB,[pc,#imm+4] adds rD,rD,rB   ldr rD,[rD]   nop
```

| 读者 | 要改的 5 条指令（ROM 地址） | 字面量字（ROM / 文件） |
|---|---|---|
| 1 | `0x08079086/88/8A/8C/8E` | `0x08079108` / `0x079108` |
| 2 | `0x080811CC/CE/D0/D2/D4` | `0x08081224` / `0x081224` |
| 3 | `0x08081238/3A/3C/3E/40` | `0x08081254` / `0x081254` |
| 4 | `0x08086042/44/46/48/4A` | `0x080860C0` / `0x0860C0` |
| 5 | `0x0808880E/10/12/14/16` | `0x08088884` / `0x088884` |
| 6 | `0x08088DAC/AE/B0/B2/B4` | `0x08088E4C` / `0x088E4C` |
| 7 | `0x0808935C/5E/60/62/64` | `0x08089538` / `0x089538` |
| 8 | `0x0808D294/96/98/9A/9C` **＋** `0x0808D2B6/B8/BA/BC`（第二处 id 计算） | `0x0808D338` / `0x08D338` |
| 9 | `0x0809014C/4E/50/52/54` | `0x08090168` / `0x090168` |
| 10 | `0x0809550E/10/12/14/16` | `0x08095598` / `0x095598` |
| 11 | `0x08095CF0/F2/F4/F6/F8` | `0x08095DF0` / `0x095DF0` |
| 12 | `0x08097A0C/0E/10/12/14` **＋** `0x08097A2A/2C/2E/30`（`0x0E` 第二名字） | `0x08097A40` / `0x097A40` |

`0x08097A12` 的样例补丁：

```
0x08097A0C  lsls r1, r0, #2        ; id*4
0x08097A0E  ldr  r4, [pc, #0x30]   ; 基址（imm 0x2c → 0x30，因为指令前移了 4 字节）
0x08097A10  adds r1, r1, r4        ; &entry
0x08097A12  ldr  r1, [r1]          ; 解引用 → 字符串首地址
0x08097A14  nop                    ; 原来占位的 adds
0x08097A16  adds r0, r6, #0        ; 不变
0x08097A18  bl   #0x806626c        ; 不变
```

`0x0E` 第二名字（r4 里已经是基址，不用再取字面量）：

```
0x08097A2A  lsls r1, r0, #2
0x08097A2C  adds r1, r1, r4
0x08097A2E  ldr  r1, [r1]
0x08097A30  nop
```

**新表放哪**：
- ROM 尾部有 **132 116 字节 `0xFF` 填充**：文件 `0x5DFBEC..0x5FFFFF` = ROM `0x085DFBEC..0x085FFFFF`
  （最后一个非 `0xFF` 字节在文件 `0x5DFBEB`）。全 ROM 只有一个 u32 落在这段里（`0x085F5D12`），
  且它所在区域 ARM/Thumb 都解不出合法指令（**推定是数据不是代码**）。
- 建议：新指针表放 ROM `0x085DFBEC`（64 项 × 4 = 256 B → 到 `0x085DEBB`），
  串池紧跟其后。当前 63 条名字只需 **331 B**，尾部还剩 ~131 KB，**长度完全不受限**。
- **旧表 `0x085A57C4..0x085A5AB7` 一个字节都不用动** ⇒ **不会毁掉全名表第 0 条**。

### (A) 槽内改存 u32 指针 —— **可行但更差**

- 优点：步长仍是 12，读者只需 **多 1 条指令**（`ldr rD,[rD]`）。
- **缺点 1（代码空间）**：12 个读者附近 **±0x200 字节内没有任何 ≥8 字节的 `0xFF` 空洞**
  （`tools/probe_speaker_space.py` 实测）⇒ 必须从函数内部「抠」出 2 字节，风险高。
- **缺点 2（数据冲突）**：槽 63 就在 `0x085A5AB8`＝**全名表第 0 条**上。
  就地改写 12 字节表 ⇒ 必须把全名表一起搬走（改它 3 个读者的字面量 + 重排 2 356 B 数据），
  否则 3 个 UI 读者读到的第 0 条会变成乱指针。
- 结论：**同一条路走，C 明显更省事**，因为 C 让每个读者的代码**反而少 2 字节**。

### (B) 保持步长 12、只把基址常量改掉 —— **解决不了用户的需求**

- 步长还是 12 ⇒ 每条仍然是定长 12 B ⇒ **单条不能变长**。
- 只能做到「整表搬迁」（这正是 (C) 的一个副产品）。
- 如果真的只是搬迁而不改步长：12 个字面量字改值即可（零代码改动），
  但要另外腾出 768 B 连续空间（ROM 尾部够）。
- **搬迁后 12 个「调色板读者」怎么办？** —— **前提不成立**：这 12 个读者**全是取名读者**
  （§1），只要新地址里放的还是「NUL 结尾的字形串」，它们照常工作；
  唯一要额外小心的是**全名表 3 个读者**，因为它们的第 0 条与旧表槽 63 重叠。

### (C) 指针表 —— **推荐**

见上。优点：步长 4 让代码**每处少 2 字节**；新表放尾部零冲突；旧表与全名表零改动。

### (D) 有没有「名字本来就能从别处来」？ —— **没有**

- 剧情 VM 里**没有任何**操作码能把说话人名字设成脚本里的任意字符串：
  `0x08`/`0x0E` 只能按 id 从表里取；`0x01`/`0x20` 是正文；`0x05` 是菜单项；`0x1D` 是忍术名
  （走**另一张**指针表 `0x08599634`，步长 4，是游戏里已有的「指针表」先例，可作 (C) 的模板参考）。
- `op 0x20` 的第 2 个操作数字节**恒为 `0x01`**（控制码 = 换色），不是定位码；
  文本流里的控制码 `0x02` 才是「设光标 (x,y)」，所以理论上**脚本可以把任意正文画到第 0 行**覆盖名字，
  但那会同时破坏正文的排版，**不能算「可变长名字」的干净解法**。
- 唯一「名字从别处来」的是**全名表 `0x085A5AB8`**（19 字节/条，全名），但它是**另一张表**、
  另一批读者，且语义是「全名」不是「简称」，步长也不是 12。

## 6. 没有查实的部分

1. **读者 4/5（`0x08066EFC`）的语义**没完全解开：它按**字节**（不是字形）遍历名字，
   把每个字节抄进一个「按列」的数组，遇到字节 `0x01`（换色控制码）会多跳 1 字节。
   这意味着**名字变长后，这两处的「列号」会随字节数变化**——需要单独确认它们的列数组容量。
   （**推定**：这是「每个字形一列」的另一种写法，但未实测。）
2. **全名表 `0x085A5AB8` 的准确条数**没闭合：前 ~120 条是 19 字节步长的名字，
