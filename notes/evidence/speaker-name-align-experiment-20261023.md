## 0. 本轮要回答的问题

**「说话人名表变长化」转换后游戏卡死，是不是因为串池里的名字字符串没有对齐？**

| 变体 | 只改一件事 | 想回答什么 |
|---|---|---|
| **P0** | = V1（基线，已知卡死） | 对照 |
| **P1** | 串池里每条名字**补齐到 2 字节对齐** | 对齐是病灶吗？ |
| **P2** | 串池里每条名字**补齐到 4 字节对齐** | 同上（更强的对齐） |
| **P3** | **指针表指向「原版内联槽」**（`基址 + id*12`），**完全不写串池** | 病灶是「名字被搬进池子」这件事？指针表本身无害？ |
| **P4** | = P3，但名字**确实改长**（id 1 →「鸣人测试」，仍住原位内联槽） | 长度/内容开始起作用了吗？ |

判定口径（**与前两轮一字不差**）：每按一次 A 截一张 mGBA 渲染缓冲，比相邻两张哈希，
**最后 3 张完全相同 ⇒ 卡死**；判定用的运行**只挂一个永不命中的断点** `0x08FFFFFE`。

## 1. 造 ROM 的做法（与上一轮一致）

1. 在**内存里**把 `pack.conversions.speaker_names.base` 改成新基址 `0x085B56E0`
   （**`rom-editor/content/pack.json` 一个字都没改**），把 id 1 的名字改成「鸣人测试」
   （触发「内联槽 → 指针表」转换），调 `buildRom(pack, rom)` 造出底座 `build/align_base.gba`；
   14 处指令补丁在这一步**留空**。
2. Python 侧：把 12 个基址字面量改成新基址 `0x085B56E0`，
   按 `tools/data/speaker_name_code_patches.json` 的 `before_hex`/`after_hex` 逐字节打 14 处指令补丁
   （**长度不变 ⇒ 不挪动任何后续代码**）。
3. P1/P2：读出串池里 64 条记录的正文，按 2 / 4 字节对齐**重排**，并**同步改写 64 个指针**。
   P3/P4：把 64 个指针改成 `0x085A57C4 + id*12`（原版内联槽地址），
   把串池区恢复成 `0xFF`，把旧内联表 `0x5A57C4..0x5A5AB7` **逐字节恢复成原版**；
   P4 再把 id 1 的新名字（**取产品代码写进串池的那份字形码**，保证编码一致）
   写回**原位内联槽**（8 字节正文 + `0x00` + 3 字节填充 = 12 字节）。

**每个 ROM 出炉后自检**（`verify_rom()`）：12 处字面量的值、14 处补丁的字节、
指针表 64 个指针的落点、旧内联表是否逐字节保持原版、串池位置与对齐、
指针表与串池是否重叠、新基址那段在原版里是否全 `0xFF`、与原版的差异区间。

## 4. 明确结论

> ### 对齐**不是**病灶；「名字留在原位」**也不可行**；
> ### 病灶在「把读者改成『取指针再解引用』」这套机制里，而且**与名字的数据完全无关**。

**依据数据**（原始输出片段）：

* **P1**（串池每条名字补齐到 2 字节对齐 ⇒ **奇地址 0/64**）：**卡死**，冻结第 6 步，
  冻结画面哈希 `fa4fd7206ccc`（与 P0 逐帧相同）⇒ 对齐不是病灶。
* **P2**（补齐到 4 字节对齐 ⇒ **奇地址 0/64、非 4 字节对齐 0/64**）：**卡死**，
  冻结第 6 步，同一哈希 ⇒ 对齐不是病灶。
* **P3**（名字**一个字节都没动、仍住原版内联槽**，串池不写，指针表指对）：
  **卡死**，冻结第 6 步，同一哈希
  ⇒ 「名字被搬进池子」不是病灶，**指针表 + 解引用这套机制本身**才是。
* **P4**（P3 + 名字确实改长、仍住原位）：**卡死**，冻结第 6 步，同一哈希
  ⇒ 长度/内容仍然无关。
* **V0**（原版）：**能跑**（15 步全程推进）⇒ 判据有效。
* **静态核对**（`build/align_litscan.py`）：那 12 个基址字面量**每个只被 1 条指令读**
  （全是 14 处补丁里对应的 `ldr rX,[pc,#imm]`），全 ROM 里 `u32 == 0x085A57C4` 的位置
  **恰好 12 个**，**没有第 13 个读者、没有字面量被别的代码路径共享**
  ⇒ 「改字面量顺手改坏别的表」这条**已排除**。

**产品修法该选哪一条？**

| 候选修法 | 判定 | 依据 |
|---|---|---|
| 串池按 2 字节对齐分配 | **✗ 无效** | P1 照样卡 |
| 串池按 4 字节对齐分配 | **✗ 无效** | P2 照样卡 |
| 指针表放别处、名字留在原位 | **✗ 无效** | P3 照样卡 |
| 「名字留原位 + 名字改长」 | **✗ 无效** | P4 照样卡 |
| **查清「取指针再解引用」为什么坏** | **← 下一步** | P0..P4 全部指向这一处 |

⇒ **不要在「串池布局 / 名字长度 / 名字落点」上继续花时间**（本轮已把它们全部排除）；
⇒ 下一轮应该直接盯**读者被改成解引用之后，哪一步算错了**（下面 §5 已经把范围缩到
**一个读者、一段代码**）。

## 5. 本轮追加：把病灶缩到**一个读者、一段代码**

### 5.1 冻结现场逐字节相同 ⇒ 同一个死法

`build/align_frozen.py`（跑到冻结后 dump CPU 状态）：

```
================ build\align_p0.gba ================
    r0 = 0x0000002C   r1 = 0x1C301C30  r2 = 0x000001C1  r3 = 0x00000000
    r4 = 0x085B56E0   r5 = 0x00000000  r6 = 0x0200A8A4  r7 = 0x08049F13
    r12 = 0x00000000  r13 = 0x00000000  r14 = 0x08097A16  r15 = 0x00000008
    cpsr: 0000009B [----I--]        ← T=0 ⇒ **ARM 状态**；PC = 0x00000008（BIOS 的 SWI 向量）
================ build\align_p3.gba ================
    （逐个寄存器完全相同）
```

⇒ **P0 与 P3 的冻结现场逐字节相同**：不只是同一帧，是**同一台机器的同一个状态**
（`sp = 0` ⇒ 栈被写坏；`PC = BIOS SWI 向量` ⇒ 卡在一次 BIOS 调用里；
`LR = 0x08097A16` ⇒ 故障点在 `0x08097A12` 附近）。

### 5.3 病灶的位置已经缩到一段代码

VM 的 op 0x08 处理函数（**原版**反汇编，`0x080979E8` 是入口）：

```
0x08097A0A: ldrb r0, [r7, #1]      ← 从剧本取 id
0x08097A0C: lsls r1, r0, #1        ← 旧：id*3
0x08097A0E: adds r1, r1, r0
0x08097A10: lsls r1, r1, #2        ← id*12
0x08097A12: ldr r4, [pc, #0x2c]    ← r4 = 基址
0x08097A14: adds r1, r1, r4        ← r1 = 基址+id*12 = 名字首地址
0x08097A16: adds r0, r6, #0
0x08097A18: bl 0x0806626C          ← 文本渲染器
0x08097A1C: ldrb r0, [r7]          ← 下一个操作码
0x08097A22: ldrh r0, [r6, #0xc]    ← op 0x0E：列号 += 2
0x08097A28: ldrb r0, [r7, #2]      ← 第二个名字的 id
0x08097A2A: lsls r1, r0, #1        ← 旧：id*3（读者 12 的第二处）
```

打补丁后（`build/align_bisect_r12.gba` 的实际字节，已反汇编核对）：

```
0x08097A0C: lsls r1, r0, #2        ← id*4
0x08097A0E: ldr r4, [pc, #0x30]    ← r4 = 新基址
0x08097A10: adds r1, r1, r4
0x08097A12: ldr r1, [r1]           ← 解引用
0x08097A14: nop
0x08097A16: adds r0, r6, #0
0x08097A18: bl 0x0806626C
```

**逐条断点实测**（`build/align_bp12.py`，一次只挂一个断点）：

| 断点 | 原版 ROM | 转换 ROM（只改读者 12） |
|---|---|---|
| `0x080979E8`（处理函数入口） | 命中，**Thumb**（cpsr `2000003F`） | 命中 |
| `0x08097A0A`（取 id） | 命中，**Thumb** | 命中，**cpsr `0000009B`（T=0 ⇒ ARM 状态！）** |
| `0x08097A0E`（取基址） | — | 命中，**r4 = 0x085B56E0（新基址 ✓）**、r1 = 0xB0 = id\*4 ✓ |
| `0x08097A12`（解引用） | — | 命中，r1 = 0x085B5790（= 基址+id\*4）→ 解引用后 **r1 = 0x085A59D4 ✓＝原版内联槽地址** |
| `0x08097A14`（nop） | — | 命中，**r1 = 0x085A59D4 ✓**、cpsr `0000003F`（Thumb） |
| `0x08097A16`（`adds r0,r6,#0`） | 命中（cpsr Thumb，r1 = 0x085A59D4） | **一次都没命中** |
| `0x08097A18`（`bl` 渲染器） | — | **一次都没命中** |

⇒ **解引用本身是对的**：r1 = 0x085B5790 → **0x085A59D4**，与原版直接算出来的
`基址+id*12` **完全同一个值**。
⇒ **名字渲染那一次调用根本没发生**（`0x08097A18` 从不命中）——
   这与上一轮独立得到的结论（「转换版里名字渲染根本没有发生」）**互相印证**。
⇒ **VM 死在 op 0x08 处理函数里、名字取到之后、调渲染器之前。**

### 5.4 还没解释的那一点（本轮留下的最大线索）

**转换 ROM 的 CPU 状态和原版不一样：**

* 原版在 `0x08097A0A`：`cpsr = 0x2000003F` ⇒ **T=1（Thumb）**；
* 转换 ROM 在 `0x08097A0A`：`cpsr = 0x0000009B` ⇒ **T=0（ARM 状态）**；
  而冻结现场也是 `cpsr = 0x9B`（ARM 状态）、`PC = 0x00000008`（BIOS 的 SWI 向量）、
  `LR = 0x08097A16`。

**⇒ 补丁把 CPU 的工作状态从 Thumb 变成了 ARM。**
`LR = 0x08097A16` 恰好等于「ARM 状态下在 `0x08097A12` 执行一条 `bl`」的返回地址
（`0x08097A12 + 4`）—— 也就是说，**改写后的那两个字（`0x6809` / `0xBF00`）被当成
一条 ARM 指令执行了**（`0x6809 0xBF00` = ARM 的 `0xBF006809` = `BL`）。

**这意味着：问题可能不是「解引用算错了」，而是「这串指令在某些路径上不是按 Thumb 执行的」。**
本轮没能把它查死（下面 §6 说明为什么查不下去），**留给下一轮**。

### 5.5 VM 的分派方式（顺手查实，给下一轮用）

```
0x080977D8: ldrb r0, [r7]        ← 操作码
0x080977DA: cmp r0, #0x39
0x080977E0: lsls r0, r0, #2      ← op*4
0x080977E2: ldr r1, [pc, #0xc]   ← r1 = 0x080977F4（处理函数地址表）
0x080977E4: adds r0, r0, r1
0x080977E6: ldr r0, [r0]
0x080977E8: mov pc, r0           ← 跳到处理函数
```

* 处理函数地址表在 `0x080977F4`（58 项，op 0x00..0x39），
  **op 0x08 与 op 0x0E 都指向 `0x080979E8`**（同一个处理函数）。
* 表里 **58 个入口地址全是偶数**（最低位 = 0）⇒ 若 `mov pc, r0` 走的是
  「按最低位决定状态」那套语义，这些入口全是 **ARM 地址**；
  但原版在 `0x08097A0A` 实测是 **Thumb** ⇒ `mov pc, r0`（ARMv7-M 的
  "Move to PC"）**不切换状态**。
* ⇒ **下一轮要查的就是：为什么补丁会让 CPU 落到 ARM 状态**。

## 6. 为什么「ARM/Thumb 状态」这条线索本轮没查死（留给下一轮）

1. **mGBA 调试器的「命中即重执行」假象**会污染状态观测：
   断点打在 `0x08097A12`（`ldr r1,[r1]`）上时，同一条指令会被反复重入，
   r1 依次变成 `0x085B5790 → 0x085A59D4 → 0xB091E999 → 0x301C301C`
   （= 连续解引用），**所以「在断点处读到的 r1」不能当作取名结果**。
   ⇒ 观测寄存器必须打在**幂等**指令上（`adds`/`nop`/`ldrb`），本轮已照此调整。
2. `0x08097A16` 那个断点**在转换 ROM 里一次都不命中**，而在它前面一条的
   `0x08097A14`（`nop`，幂等）**每次都命中** —— 这两件事同时成立，
   单靠 mGBA 的调试器输出**无法自洽解释**（本轮试过：0x08097A12/0E/14/16/18 五个断点
   逐个单挂）。
3. 因此下一步**不要再靠断点猜**，建议：
   * 用**单步**（`step`）或**指令地址历史**把 `0x08097A14` 之后的真实路径走一遍；
   * 或者反过来做实验：**只把 `0x08097A14` 的 `nop` 换成 `adds r1, r1, r4`
     （恢复旧指令的副作用）**，看卡不卡 —— 如果这样就不卡了 ⇒ 是**标志位/副作用**问题，
     不是地址问题；
   * 再或者：**把解引用挪到别的读者做、唯独读者 12 不改**，
     看读者 12 保持旧逻辑时名字能不能取对（它的字面量可以指向**旧内联表**，
     其它读者指向新指针表 —— 一次只改一处）。
