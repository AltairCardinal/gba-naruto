# `mechanism-effects`（`0x0808136C`）的运行时证据（2026-10-22）

## 1. 它不是数据表，是 **13 项函数指针跳转表**

```
0x08081346: subs  r0, r5, #1        ; r5 = 机制下标
0x08081348: cmp   r0, #0xC
0x0808134A: bls   0x0808134E
0x0808134C: b     0x080814CC        ; 越界
0x0808134E: lsls  r0, r0, #2
0x08081350: ldr   r1, [pc, #0x14]   ; r1 = 0x0808136C   ← 跳转表基址
0x08081352: adds  r0, r0, r1
0x08081354: ldr   r0, [r0]
0x08081356: mov   pc, r0            ; Thumb-2 switch 惯用法
```

⇒ 下标 `r5 - 1` 必须落在 **0..12**，即 `r5 ∈ 1..13`；表项是**代码指针**。
**旧笔记把它当「数据表」是错的。**

## 2. 路线：剧情战斗 → 第二个关卡对象处理器

`fn 0x080732B4`（剧情战斗）里：

```
0x0807357C: bl    fn 0x08074988     ; 事件分派落到「机制块」
...
0x0807498C: bl    fn 0x08081544     ; ★ 第二个关卡对象处理器
```

`fn 0x08081544` 是**按关卡对象表 `0x02026604` 分派**的处理器：

```
0x080815A6: lsls  r1, r0, #4
0x080815A8: ldr   r0, [pc, #0x30]   ; 0x02026604
0x080815AA: adds  r7, r1, r0       ; &对象[下标]
0x080815AC: ldrb  r0, [r7]         ; 对象的 type 字节
0x080815AE: subs  r0, #3
0x080815B4: cmp   r0, #3           ; ★ type ∈ 3..6
0x080815BA: ldrh  r0, [r7, #4]     ; ★ record+4 (u16)
0x080815BC: subs  r0, #1
0x080815BE: cmp   r0, #6           ; ★ record+4 ∈ 1..7
0x080815C6: ldr   r1, [pc, #0x18]  ; 7 项跳转表 0x080815E4
0x080815CC: mov   pc, r0
```

跳转表（`0x080815E4`）：

| 下标 = record+4-1 | record+4 | 落点 |
|---|---|---|
| 0 | 1 | `0x08081600` |
| 1 | 2 | `0x0808173C` |
| 2 | 3 | `0x0808180C` |
| 3 | 4 | `0x080818E4` |
| 4 / 5 / 6 | 5 / 6 / 7 | `0x08081984` |

`0x08081984` 起：

```
0x08081984: ldrh  r0, [r7, #6]
0x08081986: cmp   r0, #9
0x08081988: beq   0x0808198C         ; == 9 -> 另一支
0x0808198A: b     0x08081A8C         ; != 9 -> 落穿到机制调用
...
0x08081ADE: ldrb  r0, [r7, #6]       ; ★ 机制下标 = record[+6]
0x08081AE0: bl    fn 0x080812DC       ; ★ 读 13 项跳转表 0x0808136C
```

**⇒ 完整门控**：
`unit[0xC0] & 0xE ∉ {2,4,6}`；
对象下标 `= (word_0x02021E2C[...] & 0x3C0) >> 6 ∈ 1..15`；
对象 `type ∈ 3..6`；`record+4 ∈ {5,6,7}`；`record+6 ≠ 9` 且 `record+6 ∈ 1..13`。

## 3. 运行时读数

`build/probe_items2.py`（按场景顺序推进，相位 `0x0110`）：

```json
{"scene": 10, "hit": "0x0807498C", "label": "story battle: calls fn 0x08081544"}
{"scene": 10, "hit": "0x080815A8", "r0": "0x00000001"}          ; 对象下标 = 1
{"scene": 10, "hit": "0x08081ADE", "r2": "0x030076B0"}           ; 读 record[+6]
{"scene": 10, "hit": "0x08081350", "r2": "0x00000001",
 "label": "MECHANISM reader fn 0x080812DC (jump table 0x0808136C)"}
```

* 判定点 `0x08081350` 就是 `ldr r1,[pc,#0x14]`（装载 `0x0808136C`），
  紧随其后的 `0x08081352` 会算 `&表[下标]`；
* `r2 = 1` = 机制下标（= `record[+6]`），对应跳转表下标 `0`；
* `r0 = 0` = 下标 - 1。

## 4. 干预说明（写清楚，别让人以为是自然路径）

这条路线**需要三处有记录的 WRAM 干预**（全部在 `build/probe_items2.py` 里，
每处都打印了改前改后的值）：

1. **关卡对象表**：在对象表被游戏填好之后（哨兵 `0x08080FA0`），
   把 1..15 号槽写成 `type = 3`、`record+4 = 5`、`record+6 = 1`
   （关卡数据脚本只会产出 type 3/4/5/6，且 `record+4` 不落在 5..7）。
2. **下标表**：把 `0x02021E2C` 的那一个表项的 bit6..9 置位
   （原来算出的对象下标是 0，而 0 会被 `0x080815A0: cmp r0,#0` 直接跳过）。
3. **`unit[0xC0]`**：清掉 bit1/bit2（`& 0xE` 不为 2/4/6）。

游戏其余部分照常按正常按键运行；被改的都是**游戏自己的字段**，
不是代码。

## 5. 判死检验

| 检验 | 期望 | 实际 |
|---|---|---|
| 跳转表性质 | 表项是代码指针，步长 4 | ✅ `mov pc, r0`（Thumb-2 switch） |
| 下标范围 | `r5 - 1 ∈ 0..12` | ✅ `cmp r0,#0xC / bls` |
| 读者的寄存器对应 | `r2` = 机制下标 | ✅ `r2 = 0x00000001` |
| 类型门控 | `type ∈ 3..6` | ✅ 种植值 3 |
| record+4 门控 | `∈ {5,6,7}` 才到机制分支 | ✅ 种植值 5 → 落穿 `0x08081A8C` → `0x08081ADE` |
| record+6 门控 | `≠ 9` 且 `∈ 1..13` | ✅ 种植值 1 |
| 不改 record+4（用 2） | 走 case 1，不进机制分支 | ✅ 未命中 `0x08081ADE` |
