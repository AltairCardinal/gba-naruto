# 九个剩余 legacy 基址：重定位裁决（2026-10-21）

**工具**：新建 `tools/rebase_resolve.py`。
**对象**：`sequel/content/` 下九个仍被完成度审计判为 `基址无效，需重新定位` 的 bank。
**结果**：八个 bank 拿到了**被证伪判据约束的真实基址**；`sappy-engine`
按既定裁决**退役**（不再找基址）。其中 `menu-ui` 与 `map-events` 的旧结论被
**推翻**。

---

## 0. 方法

沿用本会话已经解决十一个 bank 的形状：**旧基址是某张真表的错位窗口**。
裁决一个候选基址 `L` 需要三条证据同时成立：

1. **活字面量**：`L` 是游戏自己的代码用 `LDR Rn, [pc, #imm]` 载入的地址
   （`tools.consumer_locate.LiteralIndex`，全量 18051 个字面量、1196 个指向
   ROM 映像，**不是**审计子集）；
2. **错位关系**：`旧基址 = L + k*stride + 字段偏移`，其中 `stride` 由读者
   自己的数据流符号化推导（复用 `tools/legacy_rebase.py::analyze_reader`），
   **不是猜的**；
3. **落点**：`L + 条数*stride` 正好落在另一个已知结构的基址上。

本轮相对前一轮新增的两条约束，用来压掉「碰巧对上」的假候选：

4. **旧窗口必须装得下**：旧 bank 记录的那段字节（`旧基址 .. 旧基址 + 条数*条目
   大小`）必须整体落在候选表内部。装不下只扣优先级、不一票否决 —— 因为
   **旧 bank 自己的 `entry_count` 也可能是错的**（`fonts` 就是这种）。
5. **落点取最近的那一个**：候选表必须在**最近的**已知结构处收尾；落到几千条
   记录之外（例如 1920 条）的落点说明那张表会吞掉半个数据区，是噪声。

`stride` 在**全部读者**上取并集，而不是只看第一个读者 —— `menu-ui` 的
`0x5A57C4` 有 12 个读者，`tile-assets` 的 `0x5A320C` 有 10 个读者，只看第一个
会丢信息。

### 0.1 工具

`tools/rebase_resolve.py`（新建）：

* 先校验 ROM 的 SHA-256，钉死为
  `1198ece781aaf629db1f0c6628b4f9f1849ecc4a2eac6a55d32748c2a459d05b`；
  不匹配直接 `exit 3`（本轮实测：喂一个 1 KB 假 ROM → exit 3）。
* 用**全量** `LiteralIndex` 搜索候选（不是审计子集）。
* 对每个候选：打印 **delta / 读者数 / 推导步长 / 错位关系 (k, 字段偏移) /
  落点**，并标注旧窗口是否装得下。
* 对胜出候选打印**记录形态检查**：条目数、非零条目数、指针占比、按类别
  统计（代码指针 / ROM 指针 / RAM 指针 / 零 / 小整数 / 其他）、首尾若干个字。
* 已知结构表是工具内的数据表 `SESSION_FINDINGS`，由
  `tools/table_registry.py::TABLES` 里 `verified=True` 的 36 条种子化，再补上
  本轮新证实的 8 条基址。
* `--bank <名字>` 会读 `sequel/content/<名字>/bank.json`（**只读**），并逐条
  比对旧 bank 记录的条目与 ROM 在旧基址处的字节 —— 用来把「内容对、基址错」
  和「内容也错」两种失败模式分开。
* 所有写文件都走 `tools.lib.io.write_text`（LF、无 BOM）。

## 2. 逐 bank 证据

### 2.1 `battle-handlers` → `0x53E698`（8 字节记录，256 条）

真实基址有**两个**活字面量，正好相差 4 字节 —— 这正是「一条记录里两个代码
指针」的形状。`fn 0x0807F414`：

```
0807F934  ldr      r1, [pc, #0x100]   ; r1 = 0x0853E698   ← 记录第 1 个字
0807F936  movs     r0, #0xee
0807F938  lsls     r0, r0, #3         ; 0xEE*8 = 0x770
0807F93A  add      r0, sb
0807F93C  ldrb     r0, [r0]           ; 事件 id：一个字节
0807F93E  lsls     r0, r0, #3         ; id*8     ← 步长 8
0807F940  adds     r0, r0, r1
0807F942  ldr      r1, [r0]
0807F944  cmp      r1, #0
0807F946  beq      #0x807f94e
0807F948  mov      r0, sb
0807F94A  bl       #0x809c114          ; 调处理程序
...
0807F94E  movs     r0, #0xee
0807F950  lsls     r0, r0, #3
0807F952  add      r0, sb
0807F954  ldrb     r0, [r0]
0807F956  lsls     r0, r0, #3
0807F958  ldr      r2, [pc, #0xe0]     ; r2 = 0x0853E69C   ← 记录第 2 个字
0807F95A  adds     r0, r0, r2
0807F95C  ldr      r1, [r0]
```

**条目数**：下标是一个字节（0..255），`0x53E698 + 255*8 + 8 = 0x53EE98`，
而 `0x53EE98` 正是已注册的 `sprite_frame_descriptors`。所以这张表**正好
256 条**，表尾严丝合缝接上帧描述符表。

**错位**：`0x53E6D8 = 0x53E698 + 8*8 + 0`（第 8 条记录的第 1 个字）。
旧 bank 声明的 `entry_size = 4` 是把 8 字节记录当成了 4 字节条目。

**可证伪判据**

1. `0x53E698 + 256*8 == 0x53EE98` 必须成立；
2. `0x0807F934` 与 `0x0807F958` 载入的字面量必须相差**恰好 4**；
3. `0x53E6D8 - 0x53E698 == 8*8 == 64`；
4. `ROM[0x53E6D8] == 0x0807EFFD`（旧 bank 第 0 条）。

### 2.2 `fonts` → `0x53E596`（字节表，256 B）

这一片是**两张连续的字节表**：

* 表 A：`0x53E496`，5 个读者，步长 1，256 字节，**表尾正好等于表 B 的基址**
  `0x53E496 + 256*1 == 0x53E596`；
* 表 B：`0x53E596`，1 个读者，步长 1，256 字节（`0x53E596..0x53E695`），
  之后 2 字节填充，下一个活字面量（战斗处理程序表）在 `0x53E698`
  —— 工具报出的落点因此是 `+258*1 == 0x53E698`（表本身到 `0x53E696`，
  差 2 字节到下一个活字面量）。

读者代码（`fn 0x0807EE50`）：

```
0807F0FC  ldr      r1, [pc, #0x14]    ; r1 = 0x0853E596
0807F0FE  movs     r2, #0xee
0807F100  lsls     r2, r2, #3
0807F102  adds     r0, r4, r2
0807F104  ldrb     r0, [r0]            ; 同一个 id 字节
0807F106  adds     r0, r0, r1
0807F108  ldrb     r1, [r0]
```

旧基址 `0x53E5B4 = 0x53E596 + 30`（表 B 的第 30 个字节），落在**第二张**表里。

**顺带发现的一个旧 bank 错误**：旧 bank 声明 `entry_count = 256`，
即窗口 `0x53E5B4..0x53E6B3`，**越过了表 B 的表尾 `0x53E696` 整整 30 字节**，
最后 30 条读到的其实是战斗处理程序表。旧 bank 的条目数应改为 **226**。

**可证伪判据**

1. `0x53E496 + 256*1 == 0x53E596`（表 A 表尾正好是表 B 表首）必须成立；
2. `0x0807F0FC` 必须载入 `0x0853E596` 并按字节下标索引；
3. `0x53E5B4 - 0x53E596 == 30`；
4. 旧 bank 记录的 256 个字节必须等于 `ROM[0x53E5B4..0x53E6B3]`（实测全部相符）。

### 2.3 `data-table-a` → `0x5A143C`（u32 指针表，46 条）

```
0x5A143C  0859F988 0859FA18 0859FABC 0859FB60 0859FC0C 0859FCB0 ...
0x5A14F0  ...                             → 表尾 0x5A14F4
```

46 条**全部**是 ROM 指针（指针占比 1.0，无零、无杂值），表尾正好落在下一个
活字面量 `0x5A14F4` 上（`0x5A143C + 46*4 == 0x5A14F4`）。

**错位**：`0x5A14A4 = 0x5A143C + 26*4 + 0`（第 26 条）。旧 bank 声明的 20 条
窗口 `0x5A14A4..0x5A14F3` 正好是这张表的**最后 20 条**，表尾严丝合缝。

**可证伪判据**

1. `0x5A143C + 46*4 == 0x5A14F4`；
2. `0x0808A6BA` / `0x0808B19E` 必须载入 `0x085A143C`；
3. 旧 bank 的 20 个字必须等于 `ROM[0x5A14A4..0x5A14F3]`（实测相符）。

### 2.4 `data-table-b` → `0x5A2034`（u32 指针表，90 条）

90 条里 79 条是 ROM 指针、7 条为零、4 条其它，表尾正好落在下一个活字面量
`0x5A219C`（`0x5A2034 + 90*4 == 0x5A219C`）。

**错位**：`0x5A2120 = 0x5A2034 + 59*4 + 0`（第 59 条）。旧 bank 的 20 条窗口
结束在 `0x5A2170`，比表尾早 `0x2C` 字节。

**可证伪判据**：`0x5A2034 + 90*4 == 0x5A219C`；`0x080985D8` / `0x08099D26`
必须载入 `0x085A2034`；旧 bank 的 20 个字必须等于 `ROM[0x5A2120..0x5A216F]`。

### 2.5 `menu-ui` → `0x5A4DEC`（头像指针表，63 行 × 40 B）

**旧结论被推翻。** `notes/evidence/remaining-rebase-leads-20261021.md` 写
「旧记录说最近候选是 `0x5A57C4`（12 个读者）；**本轮全量索引没复现这个候选**」。

* **复现了**：全量索引里 `0x5A57C4` 确实有 **12 个读者**。「没复现」这句是错的。
* **但这个候选本身是错的**：它的步长是 **12**，`0x080811D2`（`fn 0x080810B0`）
  算的是 `0x5A57C4 + 字节*12`，然后 `bl 0x080667A0`；`0x080667A0` 会写调色板
  RAM（`strh [r0,#0xc]` / `strh [r0,#0xe]` / `strb [r0,#0x12]`）。
  也就是说 `0x5A57C4` 是一张**12 字节的调色板源记录表**，
  **不是** u32 指针表；而且它在旧基址**上方** 80 字节，旧基址不可能是它的窗口。

真正的宿主是注册表里已认证的 `portrait_table` `0x5A4DEC`
（读者 `0x08096158`，`fn 0x08096138`）：

```
08096150  lsls     r0, r2, #2
08096152  adds     r0, r0, r2      ; id*5
08096154  lsls     r0, r0, #3      ; id*40
08096156  lsls     r1, r1, #3      ; expr*8
08096158  ldr      r2, [pc, #8]    ; r2 = 0x085A4DEC
0809615A  adds     r1, r1, r2
0809615C  adds     r0, r0, r1      ; 0x5A4DEC + id*40 + expr*8
```

**错位**：`0x5A5774 = 0x5A4DEC + 61*40 + 0*8`（第 61 行、表情槽 0），
在 8 字节平铺网格上就是 `+305*8`。

**落点**：`0x5A4DEC + 63*40 == 0x5A57C4`（63 行 × 5 个表情槽 × 8 字节），
正好是下一个活字面量。记录形态检查：315 个 8 字节槽里 310 个是 ROM 指针
（占比 0.984），前 10 个字是零（第 0 行的 5 个表情槽全空）。

**可证伪判据**

1. `0x08096158` 必须载入 `0x085A4DEC` 且按 `id*40 + expr*8` 索引；
2. `0x5A4DEC + 63*40 == 0x5A57C4`；
3. `0x5A5774 - 0x5A4DEC == 61*40 == 2440`；
4. 旧 bank 的 20 个字必须等于 `ROM[0x5A5774..0x5A57C3]`（实测相符）；
5. `ROM[0x5A57C4]` 之后必须仍是同构的 8 字节槽（实测是调色板源记录）。

**未闭合的部分**：第 61 行到底是不是「菜单 UI」**没有**被证明。基址、内容窗口
都成立了，但「menu UI」这个标签仍属旧 bank 的说法 —— registry 把同一张表
叫「头像指针表」。这一条按 `notes/evidence/legacy-table-base-correction-20261020.md`
的规矩应由 registry 的 `CONFLICTS` 去裁决，我没有改 registry。

### 2.6 `function-pointers` → `0x53D5F0`（u32 数组，13 槽）

```
0x53D5F0  FFFFFFFF  ← 槽 0
0x53D5F4  08061C8D 08061C99 08061CA5 08061CB1 08061CBD 08061CC9
0x53D60C  08061CD5 08061CE1 08061CED 08061CF9 08061D05   ← 槽 1..11
0x53D620  FFFFFFFF  ← 槽 12
```

读者 `0x08061DD4`（`fn 0x08061D8C`）：

```
08061DD4  ldr      r3, [pc, #0x24]   ; r3 = 0x0853D5F0
08061DD6  lsls     r0, r4, #2        ; idx*4
08061DD8  adds     r0, r0, r3
08061DDA  ldr      r0, [r0]
08061DDC  str      r0, [r1]          ; 拷进 76 字节/条的 WRAM 表
```

**错位**：`0x53D5F4 = 0x53D5F0 + 1*4 + 0`（槽 1）。旧 bank 记录的 11 条
正是槽 1..11。

**落点**：`0x53D5F0 + 13*4 == 0x53D624`（下一个活字面量，8 字节 ASCII 字符集表）。
注意 `0x53D620` 那个 `FFFFFFFF` 是**槽 12**，即**尾哨兵**，不是另一张表的第一个字。

**可证伪判据**

1. `0x08061DD4` 必须载入 `0x0853D5F0` 并按 `idx*4` 索引；
2. `0x53D5F0 + 13*4 == 0x53D624`；
3. `ROM[0x53D5F4 + 4*i] == 0x08061C8D + 12*i`，`i = 0..10`（实测全部相符）。

**未闭合的部分**：另一种读法（这张 u32 数组只有 12 槽 `0x53D5F0..0x53D61F`，
尾哨兵属于下一段结构）无法只靠落点判据排除。要排除它，需要一个把下标上界
卡在 12 的读者；目前唯一的读者没有显式上界。

### 2.7 `tile-assets` → `0x5A320C`（68 字节记录表）

真实基址 `0x5A320C` 有 **10 个**原生读者，全部推导出步长 68。记录是 17 个
u32（68 字节）：

```
+0   u32 标志
+4   u32 标志
+8   u32 小 id
+12  u32 × 6   ← 图块指针组（= 旧 bank 记录的 6 条）
+36  u32
+40  u32 × 3   ← 另一组指针
+52  u32
+56  u32
+64  u32
```

决定性原生代码（`fn 0x080983B8`，读者 `0x0809845C`）：

```
08098456  lsls     r0, r1, #4
08098458  adds     r0, r0, r1      ; idx*17
0809845A  lsls     r0, r0, #2      ; idx*68
0809845C  ldr      r1, [pc, #0xbc] ; r1 = 0x085A320C
0809845E  adds     r0, r0, r1
...
0809848C  mov      r1, r8
0809848E  ldr      r0, [r1, #0xc]  ; ← 读的就是 +12 偏移的图块指针
```

**错位**：`0x5A3218 = 0x5A320C + 0*68 + 12`（第 0 条记录的 +12 字段）。
这是**字段级**错位，不是记录级。

**落点**：`0x5A320C + 142*68 == 0x5A57C4`（下一个活字面量）。
另有一个同样精确的落点 `+288*68 == 0x5A7E8C`（`material_names`）；
两者只差一个同余（`0x5A57C4 ≡ 0x5A7E8C (mod 68)`），所以**只算一次巧合**。

**可证伪判据**

1. `0x0809845C` 必须从 `0x085A320C` 算出 `idx*68`，并读 `[记录 + 0xc]`；
2. `0x5A320C + 142*68 == 0x5A57C4`；
3. 旧 bank 的 6 个字必须等于 `ROM[0x5A3218..0x5A322F]`（实测相符）。

**未闭合的部分**：这张 68 字节表的**确切条数**没定。读者的下标是一个字节
（0..255），所以可达上限是 256 条（`0x5A320C + 256*68 = 0x5A760C`），而两个
精确落点给出 142 与 288。142 < 256 < 288。要收口需要找到一个把下标卡在
142 以内的读者，或者一个落在 `0x5A760C` 的已知结构。

### 2.8 `map-events` → `0x53E698`（**推翻旧结论**）

`notes/evidence/remaining-rebase-leads-20261021.md` 判定：
「**已判定为独立表**：47 项 u32 代码指针数组（0 值结尾于 `0x53EBC4`），
**不是** `0x53EE98` 的窗口」。**这一条被推翻。**

三条反证：

1. **地址在 ROM 里一次都没出现。** 把 `0x0853EB08` 按小端 4 字节在整个 ROM
   里搜，**0 命中**；`0x0853EBC4` 同样 **0 命中**。一张真的、代码要用的表，
   它的基址不可能连字面量池里都没有。
2. **那个「0 值结尾」不是结尾。** `0x53EBC4` 的零是**战斗处理程序表第 165 条
   记录（`0x53EBC0`）的第二个字**；紧接着 `0x53EBC8 = 0x0807ED21`，表继续往下走。
   按 8 字节看：`rec165 = (0x0807ED21, 0x00000000)`，`rec166 = (0x0807ED21, 0)`。
3. **47 个字里 23 个完全相同。** 旧 bank 记录的 47 条只有 6 个不同值，
   其中 `0x0807F065` 出现 **23 次**。用 4 字节步长去读一张 8 字节步长的表，
   恰好会得到这种「第 1、3、5… 个字是同一条记录的第 2 个字」的交错。
   （`map-events` 旧记录里的分布：`0x0807F065`×23、`0x0807EA7D`×11、
   `0x0807EC49`×6、`0x0807EAF9`×3、`0x0807EBA1`×3、`0x0807ED21`×1，
   恰好对应第 142..165 条记录的首字与次字。）

**结论**：`map-events` 和 `battle-handlers` 是**同一张表**
（`0x53E698`，8 字节记录，256 条）的两个窗口：

* `battle-handlers` 旧基址 `0x53E6D8 = 0x53E698 + 8*8 + 0`（第 8 条）；
* `map-events` 旧基址 `0x53EB08 = 0x53E698 + 142*8 + 0`（第 142 条）。

**可证伪判据**

1. `0x53EB08 - 0x53E698 == 142*8 == 1136`；
2. `0x0807F934` 必须载入 `0x0853E698` 并按 `id*8` 索引；
3. 旧 bank 的 47 个字必须等于 `ROM[0x53EB08..0x53EBC3]`（实测相符）；
4. `0x53EBC4` 的零**必须**是第 165 条记录的第二个字，即 `ROM[0x53EBC8] != 0`
   （实测 `0x0807ED21`）。

**未闭合的部分**：「地图事件处理程序」这个**语义**没有被证明；
旧窗口是 23.5 条战斗处理程序记录的**首字**。这一点按旧结论的说法反而是
被推翻的。

### 2.9 `sappy-engine` → **退役，不找基址**

旧基址 `0x079668` 是**文件偏移**，对应 ROM 地址 `0x08079668`。反汇编：

```
08079668  push     {lr}
0807966A  sub      sp, #4
0807966C  lsls     r0, r0, #0x18
0807966E  lsrs     r2, r0, #0x18     ; r2 = 参数 & 0xFF
08079670  cmp      r2, #0xe3
08079672  bhi      #0x8079704
08079674  movs     r0, #0x80
08079676  ands     r0, r2
...
08079680  cmp      r2, #0x65
08079684  cmp      r2, #0x64
0807968E  cmp      r2, #0x66
08079693  cmp      r2, #0x67
```

这是一个**按字符码分派**的 Thumb 函数（比较 `0x64/0x65/0x66/0x67/0xE3`），
不是音频分派器 —— `bank.json` 版本 2 里「已证伪」的判断成立。
`0x079668` 上下 `0x1000` 字节内**没有任何活字面量**，没有可重定位的对象。

**动作**：按既定裁决**退役该 bank**，不去追基址。

**可证伪判据**：`0x08079668` 必须是 `push {lr}` 开头、对 `r0 & 0xFF` 做上述
常量比较的函数，且 `0x079668` 在 `0x1000` 字节邻域内不出现为字面量。

## 3. 走过的弯路（死路）

1. **`menu-ui` 的 `0x5A57C4`**：读者数确实复现（12 个），但它是 12 字节的
   调色板源记录表，且在旧基址**上方**；旧 note 说「全量索引没复现」是误判。
2. **`map-events` 的「独立表 + 0x53EBC4 处 0 结尾」**：被 §2.8 的三条反证推翻。
3. **宽窗口带来的假候选**：`0x53E328`（7 个读者，步长 4）和 `0x53E014`
   （9 个读者，步长 4）对 `0x53E0xx` 一带的任何旧基址都「对得上」，
   因为它们的表尾也**正好**落在 `0x53E698`。判据是：这些表在旧基址**之前**
   就结束了（旧窗口装不下），因此排除。工具因此把「旧窗口装得下」做成
   优先级而不是硬否决。
4. **`tile-assets` 的 `0x5A2B08` / `0x5A2C44`**（步长 4，分别 452 / 373 条
   正好到旧基址）：它们的表尾就是 `0x5A3218`，即旧基址**在它们之外**，
   不是窗口。
5. **`data-table-b` 的 `0x5A1530`**（步长 8，`+382*8` 正好等于旧基址）：
   纸面关系成立，但它到下一个活字面量只有 6 条，`k = 382` 越界，排除。
6. **`fonts` 的 `0x53E496`**（5 个读者）：旧基址在其 256 字节表的**外面**
   （`k = 286 >= 256`），排除；真正的宿主是 `0x53E596`。
7. **只取第一个读者的步长**会漏掉信息：`menu-ui` 的 `0x5A57C4` 有 12 个读者、
   `tile-assets` 的 `0x5A320C` 有 10 个读者，步长要在**全部读者**上取并集。
