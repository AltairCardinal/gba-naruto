## 1. 指令层：哪个 op 设立绘、哪个 op 设名字

| op | 长度 | 语义 | handler | 证据 |
|---|---|---|---|---|
| `0x02` | 4 | **设立绘**：`(槽, 头像ID, 表情)` | `0x08097930` → helper `0x080967E8` | `0x08096882 mov r0,sb` / `0x08096884 adds r1,r6,#0` / `0x08096886 adds r2,r7,#0` → `bl 0x8096238` / `bl 0x8096168` |
| `0x04` | 4 | 同 `0x02`，另外重画边框与头像 | `0x08097958` → `0x08096A04` | 同族 |
| `0x08` | 2 | **只设说话人名字**（操作数 = 头像 id） | `0x080979E8` | `0x08097A0A ldrb r0,[r7,#1]` / `0x08097A0C lsls r1,r0,#1` / `0x08097A0E adds r1,r1,r0` / `0x08097A10 lsls r1,r1,#2`（= `id*12`）/ `0x08097A12 ldr r4,[pc,#0x2c]` → 名字表 `0x085A57C4` / `0x08097A18 bl 0x806626c` |
| `0x0E` | 3 | 设**两个**名字（与 `0x08` 同 handler） | `0x080979E8` | `0x08097A1C ldrb r0,[r7]` / `cmp r0,#0xe`；第二个名字写到 `obj+0x0C` |
| `0x11` | 2 | **清立绘**：操作数 = 槽号，`0xFF` = 两个都清 | `0x08097B58` | `0x08097B5A cmp r0,#0xff` → `bl 0x8096d8c`（全清）；否则 `bl 0x8096dd4`（单槽） |

### 1.1 与仓库既有笔记的冲突（须更正）

`notes/story-vm-opcodes-20261020.md` §3 把 `0x02/0x04` 的操作数写成「槽 / 台词行 / 台词格」，
并说 `0x085A4DEC` 是「台词/头像表」。**本轮的代码级证据表明它不是台词表**：

而 `0x08096138` 把 arg1 当**行**（×40）、arg2 当**格**（×8））。
**「台词行/格」是旧命名，语义是（头像ID, 表情）。**

同时更正两条：

- `notes/evidence/runtime-closures-20261021.md` F'.3「表情差分 36 张图块（2304 字节）」**作废** ——
  实测 ROM 里头像区是「[LZ77 流][128 字节调色板]」**严格背靠背**，
  `0x084098C4`（旧笔记当作差分块的地方）**是调色板**，不是图块。
- `notes/evidence/portrait-writeback-20261021.md` 的「表情差分」相关说法同样作废；
  但它的**表布局**（`0x085A4DEC`，行距 40、格距 8、项 = 8 字节）是对的。

## 2. 表项层：`0x085A4DEC` 的 8 字节项装什么
```
表基址 0x085A4DEC，id 行距 40 字节，表情列距 8 字节（每行 5 个表情）
地址计算（原生消费者 0x08096138）:
  0x0809613A lsls r0,r0,#0x18 / 0x0809613C lsrs r2,r0,#0x18   ; arg0 = id
  0x0809613E lsls r1,r1,#0x18 / 0x08096140 lsrs r1,r1,#0x18   ; arg1 = expr
  0x08096142 cmp r1,#5 / 0x08096146 ldr r0,[pc,#4]            ; expr==5 → 0x085A4DE4（本 ROM 未用）
  0x08096150 lsls r0,r2,#2 / 0x08096152 adds r0,r0,r2 / 0x08096154 lsls r0,r0,#3   ; id*40
  0x08096156 lsls r1,r1,#3 ; expr*8
  0x08096158 ldr r2,[pc,#8]                                    ; 0x085A4DEC
  0x0809615C adds r0,r0,r1
⇒ entry = 0x085A4DEC + id*40 + expr*8
```

**本轮独立判定（不照抄任何一边）：项 = `(u32 图形指针, u32 调色板指针)`。**

| 字段 | 判定 | 代码证据 | 数据证据 |
|---|---|---|---|
| `+0` | **LZ77(类型 0x10) 压缩的 8bpp 图形**，解压 = 6400 字节 = 100 张 8×8 图块 | `0x080961CC ldr r0,[r1]` → `0x080961D2 bl 0x0809C0EC`（`svc #0x11` = Lz77UnCompWram） | 项 (44,0) 的 `+0` = `0x08436278`，头 4 字节 = `10 00 19 00`（type=0x10, size=0x001900=6400） |
| `+4` | **128 字节 = 64 条 BGR555 调色板**（原始数据，未压缩） | `0x0809620C ldr r0,[r1,#4]` → `0x08096210 movs r2,#0x40` → `0x08096212 bl 0x0809C0E0`（`svc #0x0B` = CpuSet，64 字 = 256 字节） | 项 (44,0) 的 `+4` = `0x0843704C`；前 6 条 = `0000,0421,0c41,0842,1062,1083` → 深蓝灰渐变（合法 BGR555 阶调） |

**ROM 里头像数据的物理排布（实测）**：

```
[条目i的 LZ77 流][条目i的 128 字节调色板][条目i+1的 LZ77 流][条目i+1的调色板]...
例：项(1,0): gfx=0x08408BD8, pal=0x084098C4
    0x08408BD8 + 0xD6C = 0x08409944 = 项(1,1) 的 gfx ✓（流长 3436）
    0x08409944 + 0xD60 = 0x0840A6A4 = 项(1,1) 的 pal ✓（调色板恰 128 字节）
⇒ ROM 里**没有**「表情差分图块」这一块数据
```

### 2.1 「第 63 行是垃圾指针」**其实不是垃圾 —— 它就是名字表**

旧笔记（`portrait-writeback-20261021.md` §1.3、`story-vm-opcodes-20261020.md`）说
「行 63 的指针是垃圾（`0x9A9A5992` / `0xC8949892` / …），不是真数据」。**这是把两张表读串了。**

实测：

```
头像表基址 0x085A4DEC（文件偏移 0x5A4DEC）+ 63 × 40 = 0x085A57C4  ←── 正是**说话人名表**的基址
```

那 16 个字节是 `92 59 9a 9a 00 00 … 92 98 94 c8` ——
**名字表的第 0 条「没有」（字形码 0x9259、0x9A9A）与第 1 条「鸣人」（0x9298、0x94C8）**。

按 u32 指针读出来自然就是「垃圾」：`92 59 9a 9a` → `0x9A9A5992`
—— 正是旧笔记记下的**第一个**「垃圾值」。

⇒ **头像表只有 id 0..62 这 63 行**（id 0 是空槽，id 1..62 有效），
**第 63 行不是表的一部分，是紧跟着的说话人名表**。
旧笔记「行 63 无效」的结论**作废**（它不是无效，是**读错了表**）。

> 顺带：`0x085A4DEC` 这个字面量在**全 ROM 里只有一个读者**
> （`tools/consumer_locate.py --target 0x085A4DEC`）——
> ⇒ 这张表**只**是头像表，**没有**任何「台词表」的读者。
> 这条独立地裁决了旧笔记「台词指针 + 头像图指针」那个读法：**不成立**。

## 3. 加载器层：`0x08096168`（另有孪生变体 `0x08096238`）

```
入口参数: r0=槽, r1=头像ID, r2=表情, r3=VRAM 图块基址(单位 32 字节), [栈]=param
0x080961BE bl 0x08096138          ; → &entry[id*40 + expr*8]
0x080961CC ldr r0,[r1]            ; r0 = entry[+0] = 图形指针
0x080961CE ldr r4,[pc,#0x5c]      ; 0x02002880（WRAM 暂存）
0x080961D2 bl 0x0809C0EC          ; Lz77UnCompWram(图形, 0x02002880) → 6400 字节
0x080961D6 lsls r2,r6,#4          ; r2 = param << 4
0x080961DC ldr r3,[pc,#0x50]      ; 0x18FF（6144）循环上界
0x080961DE ldrb r0,[r4] / 0x080961E0 cmp r0,#0 / 0x080961E2 beq
0x080961E4 adds r0,r0,r2 / 0x080961E6 strb r0,[r4]     ; 非 0 字节 += param<<4 (mod 256)
0x080961FA ldr r0,[pc,#0x30]      ; 0x02002880
0x080961FC movs r2,#0xc8 / 0x080961FE lsls r2,r2,#3   ; 1600 字 = 6400 字节
0x08096202 bl 0x0809C0DC          ; CpuFastSet(0x02002880 → 0x06010000+r7*32, 1600 字)
0x08096206 ldr r0,[pc,#0x2c]      ; 0x05000200  ← **OBJ** 调色板 RAM
0x08096208 adds r5,r6,r0          ; 0x05000200 + param*32
0x0809620C ldr r0,[r1,#4]         ; entry[+4] = 调色板
0x08096212 bl 0x0809C0E0          ; CpuSet(调色板 → 0x05000200+param*32, 64 字)
```

字面量池实测：`0x08096224=0x03005E50`、`0x08096228=0x06010000`、`0x0809622C=0x02002880`、
`0x08096230=0x000018FF`、`0x08096234=0x05000200`。

### 3.1 `param` 是什么

静态：`0x08096198 adds r0,r6,r0`（`r0 = 槽*4`）⇒ **param = (栈参数) + 槽*4**；
剧情侧所有调用点写的栈参数都是 **0**
（`0x08096780` / `0x0809687c` / `0x0809698c` / `0x0809383a`）⇒ **param = 槽*4**：槽 0 → 0，槽 1 → 4。

用途两处，同一个 param：调色板槽 `0x05000200 + param*32`；像素索引整体抬高 `param*16`。

**两窗口正好对齐**：64 色被整段拷进 `0x05000200+param*32`（= 64 条 BGR555 = 256 字节），
于是「显示索引 i」落在 OBJ 调色板条目 `param*16+i`，而那里放的正是**调色板第 i 色**
⇒ **颜色查表等于 `调色板[i]`（平移在配色上是恒等变换）**。

> ⚠️ 场景 54 的实测显示，**该帧的有效 param 表现为 0**（槽 1 的立绘颜色也落回条目自己的调色板），
> 与静态公式 `槽*4` 冲突 —— 见 §6.1。

### 3.2 `6144 / 6400` 的分界

静态：平移循环只覆盖前 **6144 字节**（`0x18FF`），后 256 字节（图块 96..99）**不参与平移**。
实测：场景 54 的这块区域（254 个非零像素）显示的颜色 = `调色板[该处原始索引]` —— **与被平移的区域完全一致**。
⇒ **在本帧里 6144 的截断没有产生可见差异**（因为该帧的有效 param 表现为 0）。

## 4. 拼装层：拼块表 `0x084643C0` 怎么把 100 张图块变成 80×80

**这张表没有字面量读者，但它是原生可达的**：`0x0846443C` 这个**静态描述符**的首字就是它
（`0x0846443C = 0x084643C0`），而描述符地址被 7 处 `ldr rX,[pc,#imm]` 装载：
`0x08077D12 / 0x08089B06 / 0x0808B356 / 0x08091036 / 0x08091680 / 0x08093846 / 0x08096618`。
`0x08096618` 正在**立绘对象创建路径**上：

```
0x08096618 ldr r0,[pc,#0x40]      ; 0x0846443C（描述符）
0x0809661a ldr r1,[pc,#0x44]      ; 0x08464454
0x0809661c str r3,[sp] / 0x0809661e str r2,[sp,#4] / 0x08096620 str r3,[sp,#8]
0x08096622 movs r2,#0xa0 / 0x08096624 str r2,[sp,#0xc]
0x08096626 ldr r2,[pc,#0x3c] / 0x08096628 str r2,[sp,#0x10]
0x0809662e bl 0x080626b4          ; 对象工厂（返回对象指针）
```

**6 条 × 20 字节**：

| 块 | start_tile | x | y | w | h | 覆盖源图块 |
|---|---|---|---|---|---|---|
| 0 | 0 | 64 | 64 | 16 | 16 | 4 张 |
| 1 | 8 | 64 | 32 | 16 | 32 | 8 张 |
| 2 | 24 | 64 | 0 | 16 | 32 | 8 张 |
| 3 | 40 | 32 | 64 | 32 | 16 | 8 张 |
| 4 | 56 | 0 | 64 | 32 | 16 | 8 张 |
| 5 | 72 | 0 | 0 | 64 | 64 | 64 张 |

★ **本轮最关键的新结论（推翻旧笔记的直觉）**：
**拼块表里的 `start_tile` 不是 LZ77 缓冲里的图块号。**
缓冲区的 100 张图块是**按拼块表的顺序连续存放**的，装配规则是：

```
缓冲图块 0..3    → 显示 (64,64) 16×16   (拼块 0)
缓冲图块 4..11   → 显示 (64,32) 16×32   (拼块 1)
缓冲图块 12..19  → 显示 (64,0)  16×32   (拼块 2)
缓冲图块 20..27  → 显示 (32,64) 32×16   (拼块 3)
缓冲图块 28..35  → 显示 (0,64)  32×16   (拼块 4)
缓冲图块 36..99  → 显示 (0,0)   64×64   (拼块 5)
（每块内部按行优先铺）
```

拼块表 `start_tile`（0/8/24/40/56/72）指的是**另一片 136 槽的图块池**里的位置
（136 槽里有 36 个空槽：4..7、16..23、32..39、48..55、64..71），
它的用途（谁往那 36 个空槽里写、写的什么）**本轮没有闭合**（§6.4）。

## 5. 显示层：位置、尺寸、同时几个

- **尺寸**：80×80（拼块表 6 块面积 4096+512+512+512+512+256 = **6400 = 80×80**，无重叠）。
- **位置**：`(obj+0x30, 8)`。`obj+0x30` 是**X 位置码**：
  `0x080967AC movs r0,#0x90 / 0x080967AE mov r1,r8 / 0x080967B0 cmp r1,#0 /
  0x080967B4 movs r0,#0x10 / 0x080967B6 strh r0,[r4,#4]`
  ⇒ 槽 0 → **16**，槽 1 → **144**（`0x21` 指令的第 4 操作数可覆盖）。
  Y = 8（从截图实测；该常量的来源未定位，§6.2）。
- **同时能显示几个**：**2 个**。VM 侧只有槽 0/1 两套（`0x03005E50` 消息框指针表），
  对象侧每个立绘一个对象（`obj+0x2C` 起：`+0x2E`=ID、`+0x2F`=表情、`+0x30`=X 位置码、
  `+0x32`=可见标志、`+0x33`=param）。OBJ 数量充足（每立绘 6 个精灵 × 2 = 12 个）。
  实测：截图里两块 80×80 盒分别为 x=16..96 与 x=144..224，**互不重叠**，都在 y=8..87。
- **`0x11` 清的是什么**：把 `obj+0x32`（可见标志）写 0，并把该槽的调色板重新拷回它的 OBJ 调色板槽
  （`0x08096DA2 strb r0,[r1,#6]`、`0x08096DB4 ldr r0,[r0,#4]` → `bl 0x80635b8` 拷 128 字节）。
  ⇒ 清的是**该消息框槽上的立绘**。

## 6. 仍未闭合的点（不猜）

1. **param 的取值口径冲突**：静态公式是 `param = 栈参数 + 槽*4`（剧情侧栈参数恒 0 ⇒ 槽 1 → param 4），
   但场景 54 实测该帧的有效 param 表现为 **0**（槽 1 的立绘连「未平移尾段」都落回条目自己的调色板）。
   两者不能同时成立，**待动态读 VRAM / 调色板 RAM 定案**。
2. **OBJ 还是 BG**：证据倾向 OBJ（调色板进的是 **OBJ 调色板 RAM** `0x05000200`；
   图块号空间 136 < OBJ 的 8 位图块号上限 512；6 块的尺寸都 ≤ 64×64 = 单个 OBJ 的上限）。
   但**没找到写 OAM / 写 tilemap 的那段代码**，所以「OBJ 还是 BG」是**推定**，不是证明。
   Y = 8 这个常量的来源也没定位。
3. **栈参数读取的 4 字节口径**：三个原生函数（`0x08096168` / `0x08096238` / `0x080626B4`）都按
   「`ldr rX,[sp,#disp]`，disp = 帧长 + 偏移」读调用者的栈参数，三处**一律比 AAPCS 少 4 字节**。
   结论值不受影响（param 已由运行时实测独立钉死），但**指令级口径要复核**。
4. **拼块表 `start_tile` 指向的 136 槽图块池**：136 = 100（基础图块）+ 36 空槽
   （4..7、16..23、32..39、48..55、64..71）。谁往这 36 个空槽写、写的什么，**未闭合**。
5. **6144 截断在 param≠0 时是否可见**：静态上尾段 4 张图块（显示区 x=32..63, y=56..63）不平移
   ⇒ 应取错色；本帧实测无差异（因该帧 param 表现为 0）。**需要在 param≠0 的场景做一次运行时验证**。
6. **左边那个金发人物的调色板来源**：它的图块数据与条目 (1,1) **完全一致**（0/4659 冲突），
   但屏幕上的颜色**不是**任何一条头像项的调色板、也不是它的调色板的任何 0..63 旋转、
   也不是它的逐通道缩放（0.40..1.00 全试过）。且脚本在该帧前已 `0x11` 清掉槽 0。
   ⇒ 它**很可能不是消息框立绘**，而是过场 / 场景人物精灵（复用了同一份图块、但有自己的调色板）。
   **未闭合：这套调色板从哪来。**
7. `0x08` 的名字表 `0x085A57C4 + id*12` 的字形编码（名牌的画法见
   `notes/evidence/dialogue-font-render-20261022.md` §13）。

## 8. 浏览器端实现

`rom-editor/js/portraits.js`：

```js
// ① 表项：0x5A4DEC + id*40 + expr*8 → (图形指针, 调色板指针)
// ② LZ77 解压 → 6400 字节 = 100 张 8×8 8bpp 图块
// ③ 按拼块表把 100 张图块装配成 80×80（**连续取图块，不看 start_tile**）
// ④ 逐像素上色：索引 0 = 透明；其余查 64 色调色板
// 位置：槽 0 → (16, 8)，槽 1 → (144, 8)
```

**必须照抄的 3 条**：

1. **图块按拼块顺序连续消费**（`start_tile` 不能用）；
2. **颜色 = 调色板[原始索引]**，**不要**再做 `param*16` 平移（平移在配色上是恒等的）；
3. **索引 0 = 透明**；BGR555→RGB 用 `(c<<3)|(c>>2)`（与 mGBA 输出一致）。

门禁 `rom-editor/tools/verify_dialogue_view.mjs` 第 9 组把渲染出来的立绘
与 `notes/evidence/story-scene-l3.png` 的 (144, 8) 区域逐像素比：**6400 / 6400 全等**。
