# `fonts`（`0x0853E596`）与 `sprite-frame-descriptors`（`0x0853EE98`）的运行时证据（2026-10-22）

> 表基址（ROM 文件偏移写法，审计的标记按 6 位十六进制核对）：
> `0x53E596`（字宽表）/ `0x53EE98`（精灵帧描述符表）。

## 1. 关键发现：那不是「一张表」，是 **256 条 8 字节的回调记录**

`fn 0x0807F414` 的派发代码：

```
0x0807F934: ldr   r1, [pc, #0x100]   ; r1 = 0x0853E698   记录表基址
0x0807F936: movs  r0, #0xee
0x0807F938: lsls  r0, r0, #3         ; r0 = 0x770
0x0807F93A: add   r0, sb, r0         ; r0 = 下标字节的地址
0x0807F93C: ldrb  r0, [r0]           ; r0 = 下标字节
0x0807F93E: lsls  r0, r0, #3         ; 下标 * 8
0x0807F940: adds  r0, r0, r1         ; &记录[下标]
0x0807F942: ldr   r1, [r0]           ; 记录 word0  = handler_A
0x0807F944: cmp   r1, #0
0x0807F946: beq   0x0807F94E
0x0807F948: movs  r0, sb
0x0807F94A: bl    0x0809C114         ; ★ 调用 handler_A

0x0807F94E: movs  r0, #0xee
0x0807F950: lsls  r0, r0, #3
0x0807F952: add   r0, sb, r0
0x0807F954: ldrb  r0, [r0]
0x0807F956: lsls  r0, r0, #3
0x0807F958: ldr   r2, [pc, #0xe0]    ; r2 = 0x0853E69C = 同一张表的 word1 侧
0x0807F95A: adds  r0, r0, r2
0x0807F95C: ldr   r1, [r0]           ; 记录 word1  = handler_B
0x0807F960: cmp   r1, #0
0x0807F962: beq   0x0807F968
0x0807F964: bl    0x0809C114         ; ★ 调用 handler_B
```

⇒ **记录表基址 `0x0853E698`，每条 8 字节 = `(handler_A, handler_B)`，
共 256 条**（`0x0853E698` .. `0x0853EE98`）。
`0x0853E69C` 是同一张表的 word1 侧（条目 N 的 B 槽 = `0x0853E69C + N*8`）。

**旧笔记说的「256 × 8 字节的处理程序分派表」在「步长 8」上是对的，
但它没说出「每条是两个回调」这件事** —— 正是这一点让 `fonts` 的入口找错了。

## 2. `fonts` 的读者是 **168 条记录的 B 槽**

`build/probe_handlertable.py` 扫全表：**256 条里有 168 条的 B 槽是
`fn 0x0807F064`**（即字宽表 `0x0853E596` 的读者）。

```
entry   5: A=0x0807e86d  B=0x0807f065   ← fn 0x0807F064
entry   8: A=0x0807effd  B=0x0807f065
entry  10..13, 16..19, 27, 31, 32, 34..36, 41, 42, 48, 49, 53, 55, 57, 59..61,
entry  64..68, 70, 72, 74..79, ... 共 168 条
entry 159: A=0x0807ec49  B=0x0807f065
```

⇒ **`fn 0x0807F064` 是「关卡上带文字标签的对象」的通用绘制回调**，
不是某个特定类型的处理程序。（旧笔记「`0x0853E6C4` 是行为处理函数表」
把这一族完全看错了。）

## 3. 下标字节的地址（实测，不是猜的）

在 `0x0807F93C`（`ldrb r0,[r0]` 之前）读寄存器：

```
{"at": "0x0807F93C", "r0": "0x02027428", "r1": "0x0853E698",
 "r2": "0x02026BE0", "r3": "0x00005A67", ...}
```

* 断点命中时 `ldrb` **还没执行**，所以 `r0` 就是**下标字节的地址**；
* ⇒ 下标字节在 **`0x02027428`**，`sb`（基址）= `0x02027428 - 0x770` = `0x02026CB8`。

> **更正**：旧笔记（`notes/evidence/callback-dispatch-tables-20261021.md` §）
> 写的「`0x02027350` 是同时索引 `0x0853E596` 与 `0x0853E698` 的 u8 索引字节」
> **地址是错的**（差 `0xD8`）。同一个字节在**运行时实测**是 `0x02027428`。
> 旧笔记还把 `0x0853E596` 说成「1B 粒度」而 `0x0853E698` 是「8B 粒度」——
> 实际上**两者都是 8 字节记录的同一次派发**。

## 4. 运行时读数

路线：`tools/mgba_probe/unitslot_probe.py --groups 0 --force-dispatch
--watch-callbacks --index-byte 159`

### 4.1 `fonts`

```json
{"at": "0x0807F108", "what": "fonts 0x0853E596",
 "r0": "0x0853E635", "r1": "0x0000000D", "r2": "0x00000770",
 "table_base": "0x0853E596",
 "table_dump": "00 00 00 00 00 06 00 00 06 00 06 06 06 06 00 00 10 10 10 06 ..."}
```

寄存器对应关系逐条可算：

* `r0 = 0x0853E635` = **`0x0853E596 + 0x9F`**（字形下标 159）；
* `r1 = 0x0D` = 从字宽表读出的**那个字的宽度**（`ldrb r1,[r0]` 之后）；
* `r2 = 0x770` = 字符码在对象里的偏移；
* 紧前一条（`0x0807FE80`）里 `r1 = 0x0853E596`（表基址）、`r0 = 0x0853E635`
  —— 正是 `0x0807F0FC: ldr r1,[pc,#0x14]` 之后的状态。

表的 dump 也自洽：开头就是 `00 00 00 00 00 06 00 00 06 00 06 06 06 06 …`
这样的**字节宽度序列**（0x06 / 0x10 …）。

### 4.2 `sprite-frame-descriptors`

```json
{"at": "0x080806BA", "what": "sprite frame descriptors 0x0853EE98 (reader)",
 "r0": "0x0000000A", "r1": "0x0853EE98", ...}
{"at": "0x080806BC", "r0": "0x0000000A", "r1": "0x0853EE98",
 "r4": "0x0853EEA2", ...}
{"at": "0x080806BC", "r0": "0x0000001E", "r1": "0x0853EE98",
 "r4": "0x0853EEB6", ...}
{"at": "0x080806BC", "r0": "0x0000003C", "r1": "0x0853EE98",
 "r4": "0x0853EED4", ...}
```

* `r1 = 0x0853EE98` = **表基址**；
* `r4` = **基址 + 下标 × 10** ⇒ **步长 10 字节**
  （`0x0853EEA2 - 0x0853EE98 = 0x0A`；`0x0853EEB6 - 0x0853EE98 = 0x1E = 3×10`；
  `0x0853EED4 - 0x0853EE98 = 0x3C = 6×10`）。

### 4.3 干预是什么（写清楚，别让人以为是自然路径）

* `--force-dispatch`：打开 `fn 0x0806DF88` 的门控
  （`unit[0xC0] & 1` vs `ctrl[10]` 在战斗中恒不相等，详见
  `notes/evidence/callback-dispatch-runtime-20261021.md`）；
* `--index-byte 159`：把**一个字节** `0x02027428` 写成 `0x9F`，
  于是派发选到条目 159，其 B 槽就是 `fn 0x0807F064`。

**自然值实测是 `0x64`（100）**，条目 100 的 B 槽是 `fn 0x0807F149`（不是字体读者），
所以这条路线**必须**指定下标才能命中字体读者。
但下标字节是**游戏自己的字段**，写它只是「让游戏选中另一种对象类型」，
游戏其余部分照常按正常按键运行。

## 5. 判死检验

| 检验 | 期望 | 实际 |
|---|---|---|
| 记录表布局 | 256 条 × 8 字节 = `(A, B)` | ✅ `0x0853E698 + N*8` / `0x0853E69C + N*8` 两条装载指令互证 |
| 下标字节地址 | 断点处 `r0` 即地址 | ✅ `0x02027428`（旧笔记的 `0x02027350` **作废**） |
| 字体表下标 | `r0 = 基址 + 下标` | ✅ `0x0853E635 = 0x0853E596 + 0x9F` |
| 字宽读出 | `r1` = 表里那个字节 | ✅ `0x0D` |
| 精灵帧表步长 | `r4 = 基址 + 下标×10` | ✅ `0x0853EEA2` / `0x0853EEB6` / `0x0853EED4` |
| 不干预时 | 字体读者不触发（下标是 100） | ✅ 实测自然值 `0x64`，条目 100 的 B 不是字体读者 |
| 干预下标后 | 字体读者触发，`r0 = 基址 + 159` | ✅ |

**⇒ `fonts` 与 `sprite-frame-descriptors` 的 L2 / L3 缺口闭合。**
