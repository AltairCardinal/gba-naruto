## 3. 为什么「关卡模式进得去」

章节交接链（`notes/evidence/menu-answer-channel-20261021.md` §6）：

```
场景 1 → 剧情菜单代答 row 1（「认识卡多」）→ op 0x1A 0x08097C6C
      → state[0x16]=2, state[0x18]=1
      → 状态机 phase 0x30 的 0x0808F904 读 state[0x18]==1 → phase 0x100
      → phase 0x100 的 0x0808F928 → fn 0x08088F10（章节初始化）
      → 任务面板 fn 0x080884DC → 代答 row 1 → 返回 1
      → r4 == 0x20 → 0x08089008 → bl 0x08075184 → bl 0x0807509C（关卡战斗设置）
```

`fn 0x0807509C` 就是关卡模式的战斗入口，它依次调
`0x08068FF0`（地图载入）/ `0x08080EF0` / `0x0806B910` / `0x08080FA0` /
`0x0806B720` / `0x08080F18` / `0x0806EAB4` / `0x0806F10C` / `0x0806F210` /
`0x080694C4` / `0x08064700` / `0x0806921C` ——
**`0x0806B720`（精灵动作表）与 `0x0806E1B4`（编成矩阵）就在这条链上**。

## 4. 顺带发现：一张此前没被登记的函数指针表

`fn 0x0807EE50`（字宽表 `0x0853E596` 的唯一原生读者）**没有任何 `bl` 调用者**，
因为它是以**函数指针**形式存着的：

| 地址 | 值 |
|---|---|
| `0x0853ECB0` … `0x0853ECD7` | 6 条 `{0x0807EE51, 0x00000000}` 记录（8 字节/条） |
| `0x0853ECE0` … `0x0853ED7F` | 20 条 `{0x0807EF81, 0x00000000}` 记录 |
| `0x0853ED80` | `0x0807F1B1` |
| `0x0853ED84` | `0x00000000`（终止） |

**`0x0853ECB0` 这张表此前没有登记在 `tools/table_registry.py` 里**，
而且它自己的基址**没有任何 32 位字面量读者**（0 命中）——
所以「按字面量找表」这条路对它无效，和 `0x0853F140` 一样得靠调用链反推。

**它也是 `fonts`（`0x0853E596`）还差的那一步**：
`fonts` 的读表点 `0x0807F0FC` 在 `fn 0x0807EE50` 内部，
而 `fn 0x0807EE50` 只能通过这张表被调用 ⇒ 找到这张表的读者即可让
字宽表被游戏自己读出来。**本轮尚未定位到它的读者**，`fonts` 的 L2/L3 缺口保持开口。

## 4.5 点表修复后，`items` 的真读者落在哪

修好点表（把 30 个字面量池地址换成加载指令）之后，关卡模式里 `items` 标签下的
命中从 7 次涨到 **23 次**，其中 `0x0806E830` 一次命中 16 次 ——
但那个池里装的是 `0x000008A4`（**不是**表基址），
所以**不能**据此给 `items` 记证据（那会是假 L3）。

`0x08545BE4` 的**真**加载指令一共 5 处（用 `build/probe_poolref.py` 反查
「把常量加载进寄存器的 `ldr rX,[pc,#imm]`」得到）：

| 加载指令 | 所在函数 | 该函数怎么被调用 |
|---|---|---|
| `0x0806D91A` | `fn 0x0806D910` | **12 个 `bl` 调用者**：`0x08070334` `0x08070906` `0x0807139A` `0x080727E4` `0x080755A0` `0x08075C70` `0x08075D68` `0x08081CB4` `0x0808244C` `0x08083812` `0x0808422C` `0x08085456` |
| `0x08078EF8` / `0x08078F08` | `fn 0x08078E38`（**忍术列表 UI**） | **0 个 `bl` 调用者** ⇒ 指针调用 |
| `0x08095394` / `0x080953A4` | `fn 0x080952C8`（**道具/技能列表 UI**） | **0 个 `bl` 调用者** ⇒ 指针调用 |

**这修正了旧笔记的一句话**：「读者都在未打开的忍术列表模块里」——
`fn 0x0806D910` 这个读者**根本不在列表 UI 里**，它有 12 个普通 `bl` 调用者，
而且那些调用者就是旧笔记说的「剧情/地图事件函数」
（与事件链里的 `fn 0x08070DF8` / `fn 0x080722A8` / `fn 0x080851F8` 同族，
后三者的调用者正是关卡模式事件 switch 的 `case 0x4080`（`0x08074192`）
与 `case 0x6000`（`0x0807443C` / `0x0807425A`））。

⇒ **items 表是在关卡模式的事件链里被读的**，
门控是「事件 switch 要走到 `case 0x4080`」，
而不是「打开忍术列表界面」。上一轮关卡普查里 `0x08074192` 没命中，
说明那次的事件没走到那个 case —— 这是下一步要解决的。

⇒ `items` / `skills` 的 L2+L3（4 条缺口）由此变成一个具体问题：
**让关卡模式的事件 switch 走到 `case 0x4080`**。
两个列表 UI（`fn 0x08078E38` / `fn 0x080952C8`）是**指针调用**，
找它们的指针表是另一条路（与 `0x0853ECB0` 同类问题）。

### 4.6.2 `cutscene-scripts` 的加载点（2026-10-22 补充）

```
0x08072EDC: fn 0x08072EDC        ; 加载器
0x08072EEE: r0 = 0x0202680C      ; 战斗控制区
0x08072EF4: r0 = 0x02026A80      ; 一个指针槽
0x08072EF6: r2 = [r0]
0x08072EF8: cmp r2,#0
0x08072EFA: beq 0x08072F0C       ; ★ 指针为 0 才去读表
0x08072F0C: ldr r4, [0x0853DF70]  ; ★ 表基址
```

调用点 `0x0807363A`（`movs r0,#0; bl 0x08072EDC`）在**剧情战斗事件 switch 的
case `0x08073638`** 里 —— 该 case 由特定事件 id 选中，
所以「48 个战斗组都不命中」不是工具问题，而是**事件流里没有那个 id**。
表基址的加载点因此是 `0x08072F0E`（判定点）。

### 4.6.3 `runtime-state` 的 `story_config[0]`：旧笔记把两个地址说反了

旧笔记写：「`story_config[0]` 由调度器 `0x0808F5C8` 写入、`0x0808F5CC` 随即清零」。

**更正**：这两条指令写的是**两个不同的字段**：

```
0x0808F5A0: ldrb r1, [r6, #0x18]   ; r1 = state[0x18] = story_branch
0x0808F5A2: cmp  r1, #0
0x0808F5A4: beq  0x0808F5C0        ; branch==0 -> 「before」根表
0x0808F5A6..0x0808F5AC: 取「after」根表的脚本指针
0x0808F5AE: b    0x0808F5CA        ; ★ branch!=0 时**跳过**下面那次写
0x0808F5C8: strb r1, [r6, #0x19]   ; story_config[0] = r1（此处 r1 == 0）
0x0808F5CC: strb r5, [r6, #0x18]   ; ★ 清的是 **story_branch**，不是 story_config[0]
```

所以 `story_config[0]` **从不被清零**；它在「before」分支被写成 0，
在「after」分支**保留旧值** —— 那个旧值是**战斗 sub-config 字节**
（`state[0x19]` 同时是战斗的 sub-config）留下的，所以它**可能非零**。
判定点取 `0x0808F5CA`（写完、清 story_branch 之前）。

### 4.6.4 关卡对象系统：`fonts` / `sprite-frame-descriptors` 的最后一层结构（2026-10-22）

> **⚠️ 2026-10-22 晚更正**：本节初版把 `0x0853E6C4` 判成「关卡对象行为处理
> 函数表」，并把 `fn 0x0807F064` 当成它的一张表项。**这两条都作废** —— 它们
> 是在读者函数尚未真正跑起来时下的结论。下文「4.6.4 更正」小节给出复核后的
> 正确模型；本节保留原文以便对照。

**对象列表**：`0x02026604`，**32 条 × 16 字节**（WRAM）。
`fn 0x08080FA0` 只把每条的 **+0x0C 清 0**；`fn 0x08080F18` 遍历它，
按 **type 字节（+0x00）** 去 `0x08599274` 取 **u16 精灵属性**（`type*2` 索引），
再按 `type*12` 去 `0x0859924C` 取**精灵模板**，最后 `bl 0x080625A4` 建精灵。

**行为处理函数表**：`0x0853E6C4` 起（**紧接在处理程序分派表 `0x0853E698` 之前**，
两者相距 0xD4）。里面是**关卡对象按类型选出的行为函数指针**，
指针的值是 `0x0807E1C9` / `0x0807EFFD` / **`0x0807F065`** / `0x0807F149` / `0x0807F1B1`。
其中 **`0x0807F065` = `fn 0x0807F064` = 字宽表 `0x0853E596` 的读者**，
`0x0807F1B1` 那张表里也有 `fn 0x08080670`（精灵帧描述符 `0x0853EE98` 的读者）。

**⇒ 这两个结构的读法是：关卡里有一个「会画字」的对象。**
所以要闭合它们，**必须有一个带对应类型的关卡对象**。

**本轮做到的**：
* 确认**关卡对象列表不是空的** —— 章节路线进的那个关卡有 **1 条**记录
  （`type=3`，`sub=4`，`03 04 0E 00 02 00 01 00 20 00 00 00 14 58 00 03`），
  用 `build/probe_level_objects.py` 读出；
* 确认**关卡设置可以重跑**：在存状态里 poke 相位 `0x0100` 就能让
  `fn 0x08088F10` → `fn 0x0807509C` → `fn 0x08080F18` 再走一遍
  （哨兵 `0x08080F18` 命中，`build/probe_objtype.py`）；
* **但补写 type 0..15 的对象记录仍读不到目标表**（`build/probe_objtype.py`），
  ⇒ **派发的下标不是对象记录的那个 type 字节**，
  或者需要记录里别的字段（`+0x0C`、模板/属性表的下标范围等）。

**下一轮的第一步**：找出**索引 `0x0853E6C4` 那张行为表**的派发代码
（它既不是 `blx rN`，也不是 `ldr pc,[rn,rm,lsl#2]` 的普通形式，
多半是 Thumb-2 的 32 位 `ldr pc` 形式，需要**按 4 字节对齐**重扫
`build/probe_addpc.py` / `build/probe_blx.py`）。

### 4.6.4 更正（2026-10-22 晚）：读者函数的真实读法

复核方法：新写 `build/probe_litrefs.py`（**全 ROM 字面量引用扫描**，16 位
`ldr rN,[pc,#imm8]` 与 32 位 `ldr.w rN,[pc,#imm12]` 两种形式都收）和
`build/probe_callers.py`（`bl`/`blx` 调用者索引）。

**先修工具**：初版 `probe_litrefs.py` 把 ROM 地址当文件偏移用，
导致**连已知有引用的 `0x085461C4` 都扫不到**；`find_prologue` 又是从窗口
低端往上找，返回的是**窗口里最低的 `push {..,lr}`** 而不是最近的。
两个 bug 修好后（`build/probe_litrefs.py` 自检：对 `0x085461C4` /
`0x08545068` / `0x08596CCC` 都能扫出引用），得到的读者清单才是可信的。

**结论 1：`fn 0x0807F064` 是「关卡文字标签渲染器」，不是对象行为处理器。**

```
0x0807F0FC: ldr   r1, [pc, #0x14]   ; r1 = 0x0853E596   <- 字宽表基址
0x0807F0FE: movs  r2, #0xEE
0x0807F100: lsls  r2, r2, #3        ; r2 = 0x770
0x0807F102: adds  r0, r4, r2        ; r0 = r4 + 0x770
0x0807F104: ldrb  r0, [r0]          ; r0 = 当前字符码
0x0807F106: adds  r0, r0, r1        ; + 字宽表基址
0x0807F108: ldrb  r1, [r0]          ; r1 = 该字符的字宽
0x0807F10A: movs  r0, #1
0x0807F10C: bl    #0x0807C5E8       ; 按字宽推进光标
```

即 `width = 0x0853E596[字符码]`。它和 `0x0853E328`（字形度量）、
`0x0853E698`（处理程序分派）共用同一个 u8 索引字节。
**⇒ 闭合 `fonts` 的真正条件是「关卡里要画出一段文字/标签」，不是「有个某类型的对象」。**

**结论 2：`0x0853E6C4` 不是行为处理函数表。**
`0x0853E6A0` 起确实是一串函数指针（`0x0807E071` / `0x0807E649` /
`0x0807E775` / `0x0807E86D` / `0x0807F065` / `0x0807F1B1` / `0x0807E1C9` /
`0x0807EFFD` …），但**全 ROM 没有任何一条字面量指向 `0x0853E6C4`**，
所以它不可能是「被某个 dispatch 直接索引的表」——它自己是被别的表
（指针值在 `0x0853EBA4` 一带）间接引用的。**「`0x0853E6C4` = 关卡对象
行为处理函数表」这个判断没有证据支撑，作废。**

**结论 3：真正的「按类型分派」在 `fn 0x0806F210` 里，而且它不是关卡对象路径。**

```
0x0806F4CC: ldr   r0, [pc, #0x14]   ; r0 = 0x02026604   <- 关卡对象列表
0x0806F4CE: adds  r1, r6, r0
0x0806F4D0: ldrb  r1, [r1]          ; 对象记录的类型字节
0x0806F4D2: subs  r1, #1
0x0806F4D6: cmp   r1, #5
0x0806F4D8: bhi   #0x0806F552
0x0806F4DA: lsls  r0, r1, #2
0x0806F4DC: ldr   r1, [pc, #8]      ; r1 = 0x0806F4EC   <- 6 项跳转表
0x0806F4DE: adds  r0, r0, r1
0x0806F4E0: ldr   r0, [r0]
0x0806F4E2: mov   pc, r0            ; Thumb-2 switch 惯用法
```

跳转表 `0x0806F4EC`（`build/probe_table.py` 读出）：
`0x0806F504` / `0x0806F504` / `0x0806F528` / `0x0806F530` / `0x0806F552` /
`0x0806F544`，即 **type 1、2 → `0x0806F504`**，而 `0x0806F504` 正是
`ninjutsu-names` 表 `0x08599634` 的读者（`0x0806F504: ldr r2,[pc,#0x1c]`）。

**但 `fn 0x0806F210` 其实是「战斗单位生成」函数**（它从 `0x020240C0` 的
单位数组和阵型表 `0x0853DEFC` 取数据），所以这条 `0x02026604` 读取
**不在关卡对象的行走路径上**。实测（`build/probe_objgate.py`）：关卡模式存档
里 `fn 0x0806F210` 会被命中，但 `0x0806F4CC` 的类型分派**不会**被走到；
把对象 type 从 3 改成 1 之后**处理器依然不触发**（`build/probe_objgate.py
--patch-type 1`，对象表里 type 确实变成 1，但没有 handler 命中）。

**⇒ 旧结论「`fonts`/`sprite-frame-descriptors` 要靠关卡对象的 type 来选」
不成立；`0x0853E6C4` 与 `0x0806F4EC` 两张表都不是这两个结构的入口。**

**结论 4：这两个读者是「函数指针表」里的槽位。**
用**指针的值**（不是表的地址）反查（`build/probe_litrefs.py --ptr`）：

| 读者函数 | 指针值 | 出现在 |
|---|---|---|
| `fn 0x0807F064`（`fonts` `0x0853E596`） | `0x0807F065` | `0x0853EBA4`、`0x0853EBAC`、`0x0853EBB4`、`0x0853EBBC`、`0x0853EC24`、`0x0853EC2C`、`0x0853EC34` |
| `fn 0x08080670`（`sprite-frame` `0x0853EE98`） | `0x08080671` | `0x0853EF74` |
| `fn 0x08080764`（同表第二读者） | `0x08080765` | `0x0853EF8C` |
| `fn 0x08080814`（同表第三读者） | `0x08080815` | `0x0853F0F4` |

这三张表都**没有字面量读者**，说明它们同样是被别的结构间接引用的。
**⇒ 下一步不再猜「哪个 type」，而是去找这三张指针表的派发代码。**

**本轮新证据：关卡模式的完整链路被逐指令钉死。**
`build/probe_objgate.py`（在关卡模式存档 `build/l2-states/chapter.ss9` 上
poke 相位 `0x0100` 重跑关卡设置）实测命中顺序：

```
0x08080EF2  SENTINEL 关卡数据 DMA        (fn 0x08080EF0)
0x08080FA2  SENTINEL 对象表清零          (fn 0x08080FA0)
0x08080F1A  SENTINEL 对象表遍历          (fn 0x08080F18)
0x0806F212  SENTINEL fn 0x0806F210
```

⇒ **关卡对象表确实在关卡模式下被重建并遍历**，遍历时表里只有 1 条
（`type=3`、`sub=4`）。这条记录的所有 type 都不是上面那张 6 项跳转表的
1/2，所以 `ninjutsu-names` 不会在这条路径上被读到。

**判死检验（新增）**：

| 检验 | 期望 | 实际 |
|---|---|---|
| 字面量扫描器自检：`0x085461C4` / `0x08545068` / `0x08596CCC` | 每个都扫出全部引用点 | ✅ 26 / 1 / 7 条 |
| 关卡模式重跑：DMA → 清零 → 遍历 | 三个哨兵依次命中 | ✅ `0x08080EF2` → `0x08080FA2` → `0x08080F1A` |
| 把对象 type 改成 1 后重跑 | type 1/2 的 handler 命中 | ❌ 未命中（**证明 type 分派不在这条路径上**） |

## 5. 判死检验

| 检验 | 期望 | 实际 |
|---|---|---|
| 不进关卡模式（用 `battle.ss9` 跑同样的判定点） | `0x0806D9D8` / `0x0806E1FE` / `0x0806B770` 不命中或只命中战斗侧 | ✅ 战斗路线不命中这三处 |
