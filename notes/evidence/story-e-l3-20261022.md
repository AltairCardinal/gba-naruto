# `story-e`（声音 id 14 = `0x0853C3BC`）的 L3 证据（2026-10-22）

## 1. 旧结论与它的错处

旧笔记（`notes/evidence/l2-batch4-20261021.md`、`notes/evidence/m4a-songheader-l3-20261022.md`）写：

> sound id 14 的请求在地图/事件脚本（`0x0806ADF0` 等），剧情路线跑不到

**这条结论作废。** 声音 id 14 **根本不是**从「地图/事件脚本」来的 ——
全 ROM 扫「以常量 14 调用 `fn 0x08061E6C`（按 id 播曲）」，
**只有一个调用点**：

```
0x080894EE: adds  r0, r5, #1
0x080894F0: lsls  r0, r0, #0x10
0x080894F2: lsrs  r7, r0, #0x10
0x080894F4: asrs  r0, r0, #0x10
0x080894F6: cmp   r0, #9
0x080894F8: ble   0x0808947C          ; 还没走完
0x080894FA: movs  r0, #0xe            ; ← 声音 id 14
0x080894FC: bl    0x08061E6C          ; 播「任务列表到底」的提示音
0x08089500: movs  r0, #0x10
0x08089502: bl    0x080808Cbf4        ; 画面转场
```

它在 `fn 0x08089310`（**章节/任务列表**）里：计数器走完 10 项之后
才播这段 jingle。

## 2. 怎么走到那个函数

`fn 0x08089310` 的**唯一**调用者是 `0x0808A146`，而 `fn 0x0808A0F0`
是**章节菜单状态机**（`r4 == 0` 分支 → `bl 0x08089310`）。

`fn 0x0808A0F0` 的调用者只有两个：

| 调用点 | 所在函数 |
|---|---|
| `0x0808F644` | `fn 0x0808F618`（小函数） |
| `0x0808F9C0` | **`fn 0x0808F73C`（剧情状态机）** |

而状态机的相位分派（`0x0808F752` 起，二分比较）里：

```
0x0808F7C4: cmp   r1, r0            ; r0 = 0x200
0x0808F7C6: bgt   0x0808F7D2
0x0808F7C8: subs  r0, #0xe0         ; r0 = 0x200 - 0xe0 = 0x120
0x0808F7CA: cmp   r1, r0
0x0808F7CC: bne   0x0808F7D0
0x0808F7CE: b     0x0808F9C0        ; ← 相位 0x0120 = 章节菜单
```

⇒ **相位 `0x0120` 就是章节菜单**，它一直在相位扫描的 16 个相位里，
只是**之前没有盯 `0x080894FC` 这个点**。

## 3. 运行时读数

`tools/mgba_probe/phase_sweep.py --phases 0x120 --presses 60`：

```
phase 0x0120: 94 genuine hit(s) of 94
structures=['?', 'reward-table', 'runtime-state', 'sound-id-table', 'story', 'story-e']
```

关键两条：

```json
{"at": "0x080894FC", "label": "sound id 14 jingle (mission list end)",
 "pc": "0x080894FE", "r0": "0x0000000E", ...}
{"at": "0x0809AAD6", "label": "m4a song header (play by sound id)",
 "pc": "0x0809AAD8", "r0": "0x08465BE0", "r1": "0x08465B40", ...}
```

* `0x080894FC`：**`r0 = 0x0E` = 14** —— 游戏自己请求了声音 id 14；
* `0x0809AAD6`：`r0 = 0x08465BE0` = **`0x08465B70 + 14 × 8`** ——
  声音 id 表里 id 14 的条目地址，由游戏自己的算术得出。

## 4. id 14 → song header 的映射（由游戏自己的两条表算出）

`fn 0x0809AAC0(id)`：

```
0x0809AAC6: ldr  r1, [pc, #0x20]   ; r1 = 0x08465B70   声音 id 表
0x0809AACA: adds r0, r0, r1       ; r0 = &entry[id * 8]
0x0809AACC: ldrh r3, [r0, #4]     ; r3 = 条目第二个字（通道槽）
0x0809AD4: adds r1, r1, r2        ; r1 = 0x08465B40 + r3*12
0x0809AD6: ldr  r2, [r1]          ; 通道表项
0x0809AD8: ldr  r1, [r0]          ; r1 = 条目 word0 = song header
0x0809ADC: bl   0x0809B1F4        ; 交给 m4a 引擎
```

`build/probe_soundmap2.py` 按这两条表算出：

| 声音 id | 条目 | word0 = song header |
|---|---|---|
| 1 | `0x08465B78` | `0x08536368`（`story`） |
| 2 | `0x08465B80` | `0x08536BC4`（`story-b`） |
| 8 | `0x08465BB0` | `0x08538FEC`（`story-c`） |
| 11 | `0x08465BC8` | `0x0853AB74`（`story-d`） |
| **14** | **`0x08465BE0`** | **`0x0853C3BC`（`story-e`）** |

**⇒ 声音 id 14 播的就是 `0x0853C3BC`。** L3 闭合。

## 5. 顺带更正

* 旧笔记「id 14 的请求在地图/事件脚本」**作废** —— 全 ROM 只有
  `0x080894FC` 一处常量调用点，在**章节/任务列表**里。
* 旧笔记把声音 id 表的映射说成「表项是 song header」是对的，
  但**通道表 `0x08465B40` 里存的不是 song header**；
  song header 是**条目 word0**（`0x0809AD8` 读的才是它）。
  本轮初稿一度把两者搞反，已修正（`build/probe_soundmap2.py`）。

## 6. 判死检验

| 检验 | 期望 | 实际 |
|---|---|---|
| 相位 0x0120 | 章节菜单 ⇒ 任务列表 ⇒ 声音 14 | ✅ `0x080894FC` 命中，`r0 = 0x0E` |
| m4a 读到的条目地址 | `0x08465B70 + 14×8` | ✅ `r0 = 0x08465BE0` |
| 条目 word0 | `0x0853C3BC` | ✅ `build/probe_soundmap2.py` |
| 旧判定点（`0x0806ADF0` 一带） | 不是 id 14 的来源 | ✅ 该处是单位数组访问，不是声音请求 |

**⇒ `story-e` 的 L3 缺口闭合。**
