# 回调派发点的运行时读数（2026-10-21）

> **这份笔记推翻了本项目 2026-10-21 早些时候的一条结论。**
>
> 旧结论（`notes/evidence/callback-dispatch-tables-20261021.md` §5 与
> `docs/re-completion-criteria.md` §5.2）：
> 「回调派发点在 battle / save / sweep 三条路线上 **0 命中**，
> 所以这批表只属于剧情/战斗/存档之外的第四种模式（关卡/过场模式），
> 缺的不是「按某个键」，而是**一条会执行到该派发点的路线**。」
>
> **作废。** 派发点**确实可达**，而且就在**剧情战斗**里。
> 真正的阻塞点是三件事叠在一起（详见 §3），其中两件是**工装 bug**：
>
> 1. **按键释放从未发生**（探针 bug）：`frames 120 0x000`（松手）只在
>    「本轮没有命中任何断点」时才执行。而战斗路线的哨兵断点每次都命中，
>    于是**键一直按着不放**，游戏收不到「按下沿」，战斗过场永远不推进，
>    单位永远不被创建 ⇒ 门控条件永远不成立。
> 2. **门控的一个比较量在结构上不可能相等**：`unit[0xC0] & 1`（0 或 1）
>    与 `ctrl[10]` 原值（战斗中是 `0x0E` / `0x0F`）比较 ⇒ 永不相等。
> 3. 门控 case（回合 case）在 `fn 0x0808A588` 建单位**之前**跑，
>    所以「12 个槽全空」是**实测事实**，不是采样时机问题。

**这三条特别重要**（都是此前被写错过的）：

* `0x0853F298` 运行时读数就是 **u16 数组**（`00 00 01 00 02 00 …`），
  推翻旧的「步长 8 的重映射表」说法（已在
  `notes/evidence/callback-dispatch-tables-20261021.md` 更正）。
* `0x0853EF30` 运行时读数确认 **步长 24**（`r0 - 基址 = 0xC0 = 6×24`），
  推翻旧的「步长 20、20 字节对象类型记录」说法。
* `0x085459C8` 的 `+0` 字节是**类别字节**：`0x1D` 是本次命中用到的那一类。

### 2.5 第二个工装 bug：断点下在**字面量池**上（30 / 94 个点永远打不中）

`tools/mgba_probe/callback_census.py` 的 `WATCH` 里有 **30 个条目是字面量池地址**
（数据，不是指令）。断点下在数据上**永远不会命中** —— 那些条目等于没挂。

用原始半字扫出所有 `ldr rX,[pc,#imm]`（目标 = `((addr+4) & ~3) + imm8*4`），
再和点表求交，**30 个条目全部是池地址**：

| 结构 | 受影响的池地址条目 | 真正的加载指令 |
|---|---|---|
| `items` | `0x0806D960` `0x08078F04` `0x08078FC0` `0x080953A0` `0x0809545C` | `0x0806D91A` `0x08078EF8` `0x08078F08` `0x08095394` `0x080953A4` |
| `ninjutsu-names` | `0x0806F524` `0x08079700` `0x0807972C` `0x080816BC` `0x08081734` `0x0808EAE4` `0x080902BC` `0x080903A4` `0x080973A4` `0x0809740C` | 对应的 `ldr` 指令 |
| `tile-assets` | `0x08087E30` `0x0809851C` `0x08098840` `0x08098AF0` `0x08098DB0` `0x08098FC0` `0x08099464` `0x08099698` `0x08099D10` | 对应的 `ldr` 指令 |
| `battle-encounters` | `0x08087DB0` `0x08087E24` | `0x08087D00` `0x08087DE0` |
| `data-table-a` | `0x0808A704` | `0x0808A6BA` |
| `mechanism-effects` | `0x08081368` | `0x08081350` |
| `battle-handlers` | `0x0807FA38` | `0x0807F934` |

**修法**：把每个池地址换成「加载它的那条 `ldr` 的下一条指令」——
那里表基址已经在寄存器里、下标也在算，是最合适的判定点。
`build/probe_census_fix.py` 可以复核「点表里还有几个池地址」，
`build/probe_poolref.py` 可以把任意常量反查成加载指令。

**为什么重要**：这解释了为什么 `items` / `ninjutsu-names` / `tile-assets` /
`battle-encounters` / `data-table-a` 这些结构在**所有**路线上都是 0 命中 ——
它们的点从一开始就没挂对地方。

### 2.5.1 修好点表后的第一个战果：`tile-assets` 命中

用修好的点表跑**剧情路线**（55 场 sweep）：

```
python tools/mgba_probe/callback_census.py rom/base.gba \
    --route sweep --scenes 1-55 --presses 14 --json build/census-sweep-fixed.json
```

94 个点里只有 5 个命中，**全部是 `tile-assets`**（`0x085A320C`）：

| 断点 | 原（池地址） | 命中时寄存器 |
|---|---|---|
| `0x08099600` | `0x08099698` | `r1 = 0x085A320C`；`r0 = 0x085A37E4` = 基址 + **22×68**（第 23 条记录） |
| `0x08098D4C` | `0x08098DB0` | `r1 = 0x085A320C`（×4 次） |
| `0x0809845E` | `0x0809851C` | `r1 = 0x085A320C` |
| `0x08098EF0` | `0x08098FC0` | `r1 = 0x085A320C` |
| `0x080990D4` | `0x08099464` | `r0 = 0x085A320C` |

**每个命中的寄存器里都有表基址 `0x085A320C`**，而 `r0 = 0x085A37E4` 正好是
基址 + 22 × 68（68 字节/条 × 79 条），与 `tile-assets` 的格式证明一致
⇒ `tile-assets` 的 L3 成立。

**边界**：这条路线是**剧情路线**（逐场调度 + A 键推进），
没有做任何内存干预；`tile-assets` 的命中是**纯自然路径**。

### 2.5.2 第四个工装 bug：断点命中时**寄存器被错位归档**

一次 `frames` 运行里可以撞到**多个**断点，但调试器只停在**第一处**。
探针原来的写法是：

```python
out = probe.send("frames 8 <key>")        # 按键
found = hits_in(out)
out = probe.send("frames 120 0x000")      # 松手   <- 调试器被推进到下一个停靠
found = found + hits_in(out)
handle(found)                             # <- 这时才捕获寄存器
```

**第二次 `frames` 会把调试器推到下一个停靠**，所以捕获到的寄存器
永远属于**最后一次停靠**，而不是这次报告的地址 ——
于是「按报告地址归档」就等于**把别的站点的读数记到这个名字下**。

**修法（两条一起上）**：

1. **每次 `frames` 之后立刻捕获**寄存器（不要把两次调用合并后再捕获）；
2. 用程序计数器判定归属：mGBA 打印的是 `r13`/`r14`/`r15`（**没有 `pc:` 那一行**，
   程序计数器就是 `r15`），**`|pc - addr| <= 4`**（16 位或 32 位 Thumb 指令）
   才算真命中，否则归档为「无法归属」。

**为什么重要**：这会让「某张表被读到」这种**最关键**的结论看起来成立而其实不成立。
本轮就靠这条规则先否掉了 `reward-table` 与 `function-pointers` 的假命中，
修好捕获顺序后它们才拿到真读数（见 `notes/evidence/phase-route-l3-20261022.md` §3.6）。

**可复核**：`build/phase-sweep-verified.json` 里每条记录都带 `pc` 与 `genuine` 字段。

## 3. 门控的完整解剖（`fn 0x0806DF88`）

```
0x0806DFAE: ldrb r0,[r4]           ; unit[0]（角色 id）
0x0806DFB0: cmp  r0,#0
0x0806DFB2: bne  0x0806DFB6
0x0806DFB4: b    0x0806E194        ; ★ unit[0]==0 -> 跳过该槽
0x0806DFB6: adds r0,r4,#0
0x0806DFB8: adds r0,#0xC0
0x0806DFBA: ldr  r0,[r0]           ; unit[0xC0]（u32）
0x0806DFBC: movs r1,#1
0x0806DFBE: ands r0,r1             ; unit[0xC0] & 1
0x0806DFC0: cmp  r0,sl             ; ★ 与传入的 side 比较
0x0806DFC2: beq  0x0806DFC6
0x0806DFC4: b    0x0806E194        ; 不等 -> 跳过
0x0806DFC6: bl   0x0806DDA4        ; 解析该单位的「特性」
0x0806FDD4: cmp  r0,#0xFF
0x0806FDD6: beq  0x0806E02C        ; ★ 解析失败 -> 跳过
0x0806DFD8: adds r0,r4,#0
0x0806FDA: adds r0,#0xBE
0x0806DFDC: ldrb r1,[r0]           ; unit[0xBE]
0x0806DFE0: cmp  r1,#0
0x0806DFE2: bne  0x0806E01C
0x0806DFE4: ldrh r0,[r4,#0xC]      ; unit[0x0C]
0x0806DFE6: cmp  r0,#9
0x0806DFE8: bhi  0x0806E014
0x0806DFEA: bl   0x0806DE18        ; ★★ 派发：0x0807AB34 -> 0x0807AA8C
                                           -> fn 0x0807F414 -> 0x0853E698
```

`sl`（side）来自调用点：

```
0x080736B8: strb r2,[r1,#2]        ; ctrl[10] ^= 1     （每帧翻转）
0x080736DC: ldrb r0,[r4,#2]        ; ctrl[10]
0x080736DE: bl   0x0806DF88        ; sl = ctrl[10]
```

**结构性死因**：战斗进行中 `ctrl[10]` 是 `0x0E` / `0x0F` 交替
（`0x0E ^ 1 = 0x0F`），而门控比较的是 `unit[0xC0] & 1`（0 或 1）
与 `ctrl[10]` **原值** ⇒ **永远不相等**。
唯一的 `+0 == 0x1D` 的特性条目在 `0x085459C8` 的**索引 24**。

## 4. 打开门控的干预（必须写清楚，不能含糊）

`--force-dispatch` 在门控点 `0x080736DC`（`ldrb` 读 `ctrl[10]` **之前**）写入：

| 地址 | 值 | 为什么 |
|---|---|---|
| `unit[i]+0x00`（槽 1..11） | `1` | `unit[0] != 0` |
| `unit[i]+0x50` | `24` | 特性表 `0x085459C8` 唯一 `+0 == 0x1D` 的条目 |
| `unit[i]+0x51` | `1` | `r3 = 1-1 = 0`，非 `0xFE` / `0xFF` |
| `unit[i]+0xBE` | `0` | `unit[0xBE] == 0` |
| `unit[i]+0x0C` | `0` | `unit[0x0C] <= 9` |
| `unit[i]+0xC0` | `0` | `unit[0xC0] & 1 == 0` |
| **`ctrl[10]`（`0x0202680E`）** | **`0`** | 让 `sl = 0`，否则与 `unit[0xC0]&1` 永不相等 |

**边界声明（重要）**：

* **被证明的是「表被游戏的原生代码读取」这件事**：
  派发点是游戏自己的指令，读出来的是 ROM 里的真实字节，
  寄存器与表的对应关系逐条记录在 `build/callback-dispatch-evidence.json`。
* **未被证明的是「自然战斗会走到这条路径」**：
  自然战斗中 `ctrl[10]` 的取值让门控结构上不成立，
  上面这组写入是**为了让游戏自己的代码执行到那几条指令**而做的干预。
  因此这批证据是 **L2（原生定点）**，
  并且**不宣称**「关卡/过场模式是唯一入口」——旧结论已被本文件推翻。
* 这次干预**没有改 ROM**，只改 WRAM（`0x020240C0` 单位数组与
  `0x0202680E`），与仓库里已有的「条件位域补写」属于同一类操作。
