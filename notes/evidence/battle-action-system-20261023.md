# 战斗「动作（忍术）表」系统 —— 分身术改行为的落点（2026-10-23）

**目的**：回答「能不能改 ROM 行为，例如让影分身术一次造 5 个分身」。
本文给出**已证实的机制**（每一行都有指令级证据），以及**唯一还没闭合的那一环**。

**方法**：全部为静态反汇编 + 字面量池原始字节匹配（数据区线性反汇编会错位，
所以地址→常量的解析一律用 `build/probe_clone_path*.py` 里的原始字节扫描）。

---

## 0. 结论摘要

| 问 | 答 | 证据 |
|---|---|---|
| 战斗里「放忍术」由谁分派？ | `fn 0x0806C40C` 里的 **60 项 Thumb-2 跳转表，基址 `0x0806C478`** | §3 |
| 分派下标是什么？ | `(动作 id & 0x3F) - 4`，即 id 落在 **4..63** | §3 |
| 每个动作记录长什么样？ | **8 字节**：+0 = 动作 id，+1/+2 = 参数，+3..+7 未解 | §2 |
| 记录放在哪？ | 单位结构里 **两张平行表**：`unit+0xD4`（源）、`unit+0x154`（已生效） | §2 |
| 「分身」是生成**单位**吗？ | 是。`fn 0x0806F210` = **战斗单位生成**，会照抄目标格上那个单位的角色 id | §5 |
| 一个动作会造几个分身？ | **每个动作分支只调用 `fn 0x0806F210` 一次**（无循环）⇒ 数量**不是**代码里的循环计数 | §6 |
| 那数量在哪？ | **未闭合**（§8 台账 H1/H2） | — |

## 1. 单位结构（沿用既有结论）

| 位置 | 含义 |
|---|---|
| `0x020240C0` | 战斗单位数组基址（12 槽） |
| `+0x1D4` | 每槽步长（468 字节） |
| `+0x00` | 角色 id（u8） |
| `+0x01` | 阵营（u8） |
| `+0xC4/+0xC5` | 地图格坐标 x/y |

模板拷贝：`fn 0x0806AC70` → `fn 0x0806AA64`，从模板池 `0x02022E34`（24×`0xBC`）
拷 **`0xBC` 字节**到槽首（`0x0806AAA8: movs r2,#0xbc` → `bl 0x809c3ec`）。
⇒ **模板不带 0xBC 之后的字段**，动作表不在模板里。

## 2. 每个单位带两张 8 字节记录表

| 偏移 | 名称 | 谁写 | 谁读 |
|---|---|---|---|
| `unit+0xD4 + i*8` | **源动作表**（16 项，0 = 空） | 初始化时被清零（`0x0806AB50` `adds r0,#0xd4 / strb r2,[r0]`） | `fn 0x0806C160`（按 id 查）、`fn 0x0806C308` |
| `unit+0x154 + i*8` | **生效动作表**（16 项，0 = 空） | `fn 0x0806C1A4`（从源表搬运一条） | `fn 0x0806C40C`（分派） |

**记录的 8 字节布局（已证实的 3 个字节）**：

| 字节 | 含义 | 证据 |
|---|---|---|
| `+0` | 动作 id（低 6 位有效：`& 0x3F`） | `0x0806C182: movs r0,#0x3f; ands r0,r1`；`0x0806C45A: movs r0,#0x3f; ands r0,r2` |
| `+1` | 参数 A（写入 `obj[+5]`） | `0x0806C2BC: adds r1,#0xd7` / `0x08076658: adds r0,#0xd5` |
| `+2` | **蓄力/冷却计数** | `0x0806C330: adds r1,#0xd6` → `ldrb/strb` 递减 |
| `+3..+7` | 未解 | — |

**搬运函数 `fn 0x0806C1A4(dst_unit, src_index, flag)`**（`0x0806C1A4`）：

```
0x0806C1E6: lsls r0, r4, #3
0x0806C1E8: adds r0, r3, r0        ; r3 = 单位基址
0x0806C1EA: adds r0, #0xd4         ; ★ 源记录 = unit+0xD4+idx*8
0x0806C1EC: ldr  r1, [r0, #4]
0x0806C1EE: ldr  r0, [r0]
0x0806C1F0: str  r0, [r2]          ; → unit+0x154+空槽
0x0806C1F2: str  r1, [r2, #4]
0x0806C1F4: ...  strb r1, [r0]     ; 源项清零（搬完即失效）
```

## 3. 分派：60 项跳转表 `0x0806C478`

`fn 0x0806C40C`（战斗包装器 `0x080732B4` 在 `0x08073680` / `0x080736A4` 调用它）：

```
0x0806C40C: push {r4-r7, lr}
0x0806C418: movs r0,#0 / str r0,[sp,#0xC]      ; 计数器
0x0806C41C: movs r1,#1 / str r1,[sp,#8]
0x0806C420: movs r0,#0xea / lsls r0,r0,#1      ; 0x1D4 = 单位步长
0x0806C428: muls r1, r0, r1
0x0806C42A: ldr  r0,[pc,#0x44] → 0x020240C0    ; ★ 单位数组
0x0806C42C: adds r7, r1, r0                    ; r7 = &unit[slot]
0x0806C43C: r5 = 0                             ; 记录下标
0x0806C442: adds r0,#0xaa / lsls r3,r3,#1      ; 0x154
0x0806C448: ldrb r2, [r0]                      ; ★ 动作 id
0x0806C450: cmp  r2,#0 / bne ...              ; 0 = 列表结束
0x0806C458: movs r0,#0x3f
0x0806C45A: ands r0, r2
0x0806C45C: subs r0, #4                        ; ★ 下标 = id-4
0x0806C45E: cmp  r0, #0x3b                     ; 0..59
0x0806C460: bls  0x0806C466
0x0806C462: bl   0x0806D1A2                    ; ★ 默认分支
0x0806C466: lsls r0, r0, #2
0x0806C468: ldr  r1,[pc,#8] → 0x0806C478      ; ★ 跳转表
0x0806C46A: adds r0, r0, r1
0x0806C46C: ldr  r0, [r0]
0x0806C46E: mov  pc, r0
```

**有专门实现的 action id**（其余 6..12、16、19、20、23、24、26、28、29、38..60 全部落到默认 `0x0806D1A2`）：

| id | 实现地址 | id | 实现地址 |
|---|---|---|---|
| 4 | `0x0806C62C` | 27 | `0x0806D098` |
| 5 | `0x0806C568` | 30 | `0x0806CCE8` |
| 13 | `0x0806CC50` | 31 | `0x0806CD60` |
| 14 | `0x0806CB04` | 32 | `0x0806CDD4` |
| 15 / 17 / 61 / 62 / 63 | `0x0806D124` | 33 | `0x0806CE4C` |
| 18 | `0x0806CCE8` | 34 | `0x0806CEC0` |
| 21 | `0x0806CB9C` | 35 | `0x0806CF38` |
| 22 / 25 | `0x0806C62C` | 36 | `0x0806CFAC` |
| | | 37 | `0x0806D024` |

> 默认分支 `0x0806D1A2` 还会再分一次：对 id **18..37** 走 8 项子跳转表 `0x0806D26C`
> （`0x0806D21C: ldrb r1,[r0] / movs r0,#0x3f / ands / subs r0,#0x12 / cmp r0,#0x13`）。

## 4. 每个角色 5 个「忍术槽」

战斗初始化会把**每个单位**的 5 个槽位装进生效表（`0x0806B300` 起，调用
`fn 0x0806C1A4` 的 5 个连续点 `0x0806B33C / 0x0806B3BA / 0x0806B3FC / 0x0806B432 / 0x0806B45E`）：

| 槽号（被查表的 key） | 对应 action id | 查表点 |
|---|---|---|
| `0x0E` | 14 | `0x0806B312` `fn 0x0806C160(unit, 0x0E)` |
| `0x0F` | 15 | `0x0806B340` `fn 0x0806C160(unit, 0x0F)` |
| `0x3D` | 61 | `0x0806B3AA` `fn 0x0806C160(unit, 0x3D)` |
| `0x3E` | 62 | `0x0806B32C` `fn 0x0806C160(unit, 0x3E)` |
| `0x15` | 21 | `0x0806B438` `fn 0x0806C160(unit, 0x15)` |

`fn 0x0806C160(unit, key)`（`0x0806C160`）= 在 `unit+0xD4+i*8` 里找
`(byte & 0x3F) == key` 的下标，找不到返回 `0xFF`。

**⇒ 影分身术 / 多重影分身术必然落在这 5 个槽之一**（id 14/15/21/61/62）。

## 5. `fn 0x0806F210` = 战斗单位生成（分身的落点）

入参：`r0 = x`，`r1 = y`，`r2 = 施术者角色 id`，`r3 = ?`。

```
0x0806F226: ldr  r2,[pc] → 0x0202680C          ; 战斗控制块
0x0806F22C: adds r3, r2, #0x26C ; strb r0,[r3]  ; ctrl[0x26C] = x
0x0806F232: ...          #0x26D ; strb r1,[r0]  ; ctrl[0x26D] = y
0x0806F236: ldr  r4,[pc] → 0x02021E2C          ; 格子→单位查找表
0x0806F23E: muls r0, r1, r0
0x0806F242: adds r0, r0, r3
0x0806F244: lsls r0, r0, #1
0x0806F246: adds r0, r0, r4
0x0806F248: ldrh r5, [r0]                      ; 该格上的单位
0x0806F250: lsrs r0, r0, #0xb  (取 0x7800 位) ; 朝向
0x0806F258: ... #0x26B ; ldrb r0,[r2]         ; ★ ctrl[0x26B] = 待生成角色 id
0x0806F26A: cmp  r0, r8 ; beq 0x806f272       ; 与施术者同 id → 不生成
0x0806F26E: bl   0x0806B984                    ; ★ 生成单位
```

后半段（`0x0806F4CC` 起）按**关卡对象表 `0x02026604`（16 字节/条）**的 type 分派：

```
0x0806F4CC: ldr  r0,[pc] → 0x02026604
0x0806F4CE: adds r1, r6, r0
0x0806F4D0: ldrb r1, [r1]        ; 对象 type
0x0806F4D2: subs r1, #1
0x0806F4D6: cmp  r1, #5 / bhi default
0x0806F4DC: ldr  r1,[pc] → 0x0806F4EC        ; ★ 6 项跳转表
```

| type | 落点 | 行为 |
|---|---|---|
| 1 / 2 | `0x0806F504` | **播报忍术名**：`ldrh r0,[obj,#4] & 0x7F` → 忍术名表 `0x08599634` 的字符串指针 → `bl 0x08066758` 显示 |
| 3 | `0x0806F528` | 另一支 |
| 4 | `0x0806F530` | 另一支 |
| 5 | `0x0806F552` | 默认 |
| 6 | `0x0806F544` | 另一支 |

⇒ **type 1/2 的关卡对象 = 「在这里放一个单位 + 喊出忍术名」**，这是
「剧情战斗里演一次影分身术」的实现。

## 6. 关键否证：数量不在代码的循环里

对 `fn 0x0806F210` 的 **46 个调用点**逐个查了所属分支与是否落在循环内
（`build/probe_clone_path10.py`）：

* 落在 **60 项动作表分支**里的 **15 个不同调用点**，**每一个分支只调 1 次**，
  **没有任何一个调用点在回跳分支内**。
* 换句话说：**「造几个分身」不由 handler 里的循环次数决定**。

⇒ 数量要么在**数据**（记录参数字节 / 关卡对象表），要么靠**多次进入该动作**
（同一动作被触发 N 次）。

## 7. 蓄力计数（已证实的「时间型参数」）

`fn 0x0806C308`（战斗包装器 `0x0807367C` 调用，紧挨着分派器）：

```
for slot = 1..12:
  for i = 0..15:
    id = unit[0xD4 + i*8]                  ; 0x0806C328
    if id == 0: continue
    cnt = unit[0xD4 + i*8 + 2]             ; 0x0806C330  (adds r1,#0xd6)
    if cnt == 0: continue
    cnt -= 1 ; unit[...] = cnt             ; 0x0806C338
    if cnt == 0: bl fn 0x0806C1A4(...)     ; ★ 计数归零 → 该动作「装弹」
```

⇒ 记录 +2 是**冷却/蓄力计数**：归零那一刻动作才被装进生效表。
这是记录里**已证实的一个可调参数**（改大 = 忍术更晚可用）。

## 8b. 「选分身位置」交互的机制（UI 层）—— 决定 5 个分身要几次交互

**战斗帧主循环**（`fn 0x080732B4`）：

```
0x0807367C: bl fn 0x0806C308      ; 蓄力计数递减 → 动作装弹
0x08073680: bl fn 0x0806C40C      ; ★ 执行生效表里的动作（60 项跳转表）
0x08073684: bl fn 0x0806D440
0x08073688: bl fn 0x08081B70
0x0807368C: bl fn 0x08077C54
0x08073690: bl fn 0x0806B49C      ; ★★ 选位置 + 生成单位（= 分身）
0x08073696: bl fn 0x0807305C
0x080736A4: bl fn 0x0806C40C      ; ★ 再执行一次（第 4 步可能新装了动作）
```

`fn 0x0806B49C`（另一条路径 `0x08074448` 也调它）就是「选位置 + 造分身」那一步：

1. **在 12 个单位槽里找当前行动者**（`0x0806B4B6` 起：槽位 +0 非 0、+0xCA 为 0）。
2. **枚举合法候选格**（`0x0806B508`..`0x0806B56C`）：
   * 计数 `u16` @ **`0x02025E00`**（每帧先清零：`0x0806B50E strh r0,[r1]`）
   * 候选数组 `u8` 交错对 (x,y) @ **`0x02025E02`**（x 在 +0、y 在 +1，步长 2）
   * 循环范围 = 地图宽 × 高（`0x0806B528` / `0x0806B536`），占用判定读
     格子表 `0x02021E2C`（`ldrh` 非 0 表示这格不可用 → 跳过）
3. **挑一个下标**（三选一）：
   * **随机**：`0x0806B58C` `bl 0x809c110`（RNG）→ `r0 = (rng * count) >> 15` → 下标
   * **玩家交互**：`0x0806B5CC` → `bl 0x08085A40(sp, 2, 0x0812C868)`（发起选择请求）
     → `bl 0x08085A74`（轮询；未完成返回 0 就重试，完成返回**下标**）
   * 另一条 UI 路径：`0x0806B618` → `0x08085B8C` / `0x08085BC0`
4. **下标 → 坐标**：`0x0806B636` `0x02025E02 + index*2` → x、y。
5. **生成**：`0x0806B67C` `bl fn 0x0806F210(x, y, 0, 2)`。

**选择请求的全局量**（IWRAM，`fn 0x08085A40` 写的）：

| 地址 | 含义 |
|---|---|
| `0x03000999` | 选择标志（byte） |
| `0x03005E38` | 输出指针（结果写到这里） |
| `0x03005E40` | 选择模式（本次传 **2**） |
| `0x03005E48` | 「选择中」标志 |
| `0x03005E30` | 模式名表指针 → `0x0812C868` |

`0x0812C868` 是**选择模式的名字表**（4 字节 ASCII 片段：`"BOOT" "ORAN" "D" "RANT" "SPOS" … "POSD" "NONE"`），
模式 2 对应的就是「位置」类交互。

### ⇒ 关键结论：**交互产出的是「候选表里的一个下标」，不是一个坐标**

所以「5 个分身」**不需要 5 次交互**。补丁只要在拿到下标之后**多调几次
`fn 0x0806F210`**，把候选表里另外几格也用上：

```
0x0806B636  idx = 玩家选中的下标
+新增循环:
    for k = 0..4:
        j = (idx + k) % count              ; 环绕取候选表
        (x,y) = 0x02025E02 + j*2
        bl fn 0x0806F210(x, y, 0, 2)
```

* **UI 交互次数仍然是 1 次**（选择逻辑、UI、输入全部不动）。
* 5 个分身落在**候选表里的 5 个合法格**——候选表是游戏自己枚举出来的，
  天然不重叠、也不在敌人占的格上。
* 更稳的变体：以玩家选中的格为**锚点**，再取其上下左右 4 个邻格，
  逐个用同一张格子表 `0x02021E2C` 校验是否合法，不合法就跳过。

**代价与风险（必须写进补丁的判据）**：

* 单位数组只有 **12 槽**（`0x020240C0`）。5 个分身会吃掉 5 个槽位，
  可能导致敌方无位置可放 ⇒ 补丁必须在生成前数空槽。
* 候选表长度上限未闭合（枚举范围是整张地图，空格多时可能很大），
  运行时读 `0x02025E00` 即可知道；不足 5 格时要退回少造。

### 设计层结论（比补丁更重要）

**「多重影分身术」本来就是另一个忍术 id**（忍术名表 `0x0859937C`：id 7 = 影分身术，
id 9 = 多重影分身术）。正确的产品形态是：

* **影分身术** = 1 个分身（保持原样）；
* **多重影分身术** = 5 个分身（同一个交互，一次选位，其余 4 个自动补位）。

这样「数量」是**招式之间的差别**，而不是同一个招式里的重复交互。
实现上只需让两个忍术 id 映射到不同的 action id，而 action id 决定了
「生成 1 次」还是「生成 5 次」。

## 9. 「改 ROM 行为」在本题里的三条路（可行性已由本仓库其它成果证明）

| 层 | 手段 | 本题的具体落点 | 成本 |
|---|---|---|---|
| 数据层 | 改 ROM 里的表 | 关卡对象表（`0x02026604` 的 ROM 来源）、动作记录参数字节 | 分钟级，**改完即可跑** |
| 指令层 | 改一条 THUMB 立即数 / 替换一个函数体 | 60 项跳转表 `0x0806C478`（把某 id 指到别的实现）、handler 里 `fn 0x0806F210` 的调用参数 | 小时级，需要重新对齐（`0x0806F4EC` 表是 4 字节对齐的指针，改指向不占空间） |
| 宿主层 | 静态重编译工程的 `[[mod_function_hook]]` + native plugin | 直接替换 `fn 0x0806F210` 或某个 handler | 不重编译，但要写 C++ 插件 |

**「一次造 5 个分身」的可行实现（待 H1/H2 落定后二选一）**：

* 若数量是**数据**（H2/H3）→ 改一个字节，最省；
* 若数量是**代码**（无循环，§6）→ 把 handler 里那一次 `bl 0x0806F210`
  改成**循环 5 次**（换 5 个相邻格），或在 `fn 0x0806F210` 里加一个「生成 N 个」参数。
  代价：单位数组只有 **12 槽**（`0x020240C0`），5 个分身会挤占敌方槽位。

