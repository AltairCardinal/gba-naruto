# 描边色的每帧写入点：**`0x0806A7A0`**（第 25 轮，代理中断前抢出来的结果，已独立复核）

## 1. 结论

原版每帧改写单位 OBJ 调色板**第 15 项**（1 px 描边色）的那段代码在 **ROM `0x0806A7A0`** 附近：

- 写入目标：**PRAM `0x0500021E + bank*32`**（`0x0500021E` = OBJ 调色板 bank 0 的第 16 项，
  即 index 15；`+bank*32` 是换调色板 bank）；
- 写入值：`(v << 10) | (v << 5)`（BGR555，red = 0，green = blue = v）；
- `v = (global & 0xF) * 2 + 1` ⇒ **1, 3, 5, …, 31 的三角波，周期 32 帧**；
- 落笔指令在 **`0x0806A7EE`**；该函数**没有直接 BL 调用者**（间接分派）。

## 2. 独立复核（本轮自己验的，不采信代理自述）

在 `rom/base.gba`（sha256 `1198ece7…`）里搜字面量 `0x0500021E`：

```
literal 0x0500021E found at file offsets: 0x6a7f4, 0x6a808
  -> ROM addresses: 0x0806A7F4, 0x0806A808
```

⇒ 两处都在**同一个函数**的字面量池里（函数起点 `0x0806A7A0`），
且与代理报告的落笔地址 `0x0806A7EE`（在函数体内部、字面量池之前）一致 ⇒ **发现属实**。

## 3. 为什么这条重要

第 20 轮已确证：原版单位精灵的**每帧变化恰好是「持有同一调色板索引的像素集」**，
即描边色；屏上该色逐帧为 `(0, g, g)`，`g` = 1,3,…,31 的三角波、周期 32 帧。
⇒ 这条写入点就是**S49 单位动画那条「每帧 1 px 差异」的根**。

⇒ 重制侧要 1:1 复刻单位动画，**必须复刻这个三角波**（而不是只对齐帧序）：
帧序第 17 轮已闭合（= ROM 的 animation 3），**但描边色的每帧写入还没做** ⇒
这解释了「帧序对上了、像素仍差」的现象。

## 4. 仍未确立

- 该函数被**谁间接调用**（分派表在哪、每帧调用几次、作用于哪些单位）；
- `global` 那个计数器与场景时间的关系（是全局帧数、还是单位自身的动画计时）；
- 该写入是否**只对场上单位**做（还是对全部 128 个 OBJ 槽位都做）；
- 三角波的**相位起点**（`global` 的初值）⇒ 这直接决定「重制侧第一帧该是多少」。

## 5. 下一步

- 逆向侧：把 `0x0806A7A0` 的分派指针表找出来（代理已注意到它没有直接 BL 调用者）；
- 本树：写一个可复现的「PRAM 半字写入清单」导出器（扫 ROM 里所有写 PRAM 的 `STRH`，
  覆盖静态偏移与寄存器计算两种形式），把这条与其它候选一并钉住
  （`tools/export_rom_pram_halfword_writes.py`，代理中断前正在做这件事）。

## 6. 第 25 轮续：**已做成可复现的导出器 + 门禁，并逐字节坐实**

### 6.1 函数体的反汇编（Capstone 实测，`tools/export_rom_pram_halfword_writes.py` 落盘）

```
0x0806A7A0  push   {lr}                     ; 函数起点
0x0806A7A2  adds   r3, r0, #0
0x0806A7A4  ldrh   r0, [r3, #0x14]
0x0806A7A6  cmp    r0, #3
0x0806A7A8  bhi    #0x806a7d8
0x0806A7AA  ldr    r0, [r3]                 ; 单位记录
0x0806A7AC  movs   r1, #8
0x0806A7AE  ands   r0, r1
0x0806A7B0  cmp    r0, #0
0x0806A7B2  bne    #0x806a7d8
0x0806A7B4  ldr    r0, [pc, #0x1c]          ; 全局计数器指针
0x0806A7B6  ldr    r1, [r0]
0x0806A7B8  movs   r0, #0xf
0x0806A7BA  ands   r0, r1                  ; global & 0xF
0x0806A7BC  lsls   r0, r0, #1              ; * 2
0x0806A7BE  adds   r0, #1                  ; v = (global & 0xF) * 2 + 1
0x0806A7C0  adds   r2, r0, #0
...
0x0806A7E0  ldrb   r0, [r3, #0x12]         ; bank = 单位记录的一个字节
0x0806A7E2  lsls   r0, r0, #5              ; bank * 32
0x0806A7E4  ldr    r1, [pc, #0xc]          ; r1 = 0x0500021E
0x0806A7E6  adds   r0, r0, r1              ; 0x0500021E + bank*32
0x0806A7E8  lsls   r1, r2, #5              ; v << 5
0x0806A7EA  lsls   r2, r2, #0xa             ; v << 10
0x0806A7EC  orrs   r1, r2                  ; (v<<10)|(v<<5)
0x0806A7EE  strh   r1, [r0]                ; 写 PRAM
```

⇒ **三角波来源逐字节坐实**：`v = (global & 0xF) * 2 + 1`（global 来自一个 ROM 里的全局指针）。
⇒ **bank 来源也清楚了**：`ldrb r0, [r3, #0x12]`（单位记录的第 0x12 字节）。
⇒ 还有**两个前置条件**：`ldrh r0,[r3,#0x14]` 必须 ≤ 3，且单位记录首字的 bit3 必须为 0
（否则跳过写入）⇒ 这解释了「哪些单位/哪些状态会有描边色」。

### 6.2 工具与门禁

- `tools/export_rom_pram_halfword_writes.py`：普查 ROM 里所有**指向 PRAM 的 32 位字面量**
  （912 处、142 个不同值），并为每个字面量解出加载它的 Thumb `LDR` 与所属函数
  （候选 PUSH 会用反汇编复核，避免把字面量池数据误认成函数头）；
  同时解码已知写入点并把窗口指令落盘。
  **scope 明确写了覆盖范围**：覆盖「经字面量池到达 PRAM」的写法（本游戏就是这么写的），
  **不覆盖**「无字面量、纯寄存器算出来的 PRAM 地址」，GPU copy queue 另计。
- `tests/test_rom_pram_halfword_writes.py`（7 项全绿）：ROM 哈希闸门、收据逐字节可复现、
  已知写入点被确认、两个字面量解析到正确的 LDR 与函数、**三角波计算在收据自己的字节里可见**、
  scope 如实声明。
- 收据：`artifacts/rom-pram-halfword-writes-v1/pram-halfword-writes.json`。

### 6.3 仍未确立
