## 1. 审核 M1 / M2 / M3 是怎么落的

### M1｜条件指令的跳转语义（**改的是最要紧的一处**）

handler 的真实形状（`0x08097D4C` 起）：判定结果 == 1 → `b 0x08097B20`（跳到 u32 目标）；
落空 → 继续下一条指令。⇒ **u32 目标是「条件命中时跳到哪」。**

落地方式：

| 位置 | 改动 |
|---|---|
| `rom-editor/js/modules/battle-sections.js` | 条件表的列头由「不满足时」改成「**命中时跳到**」 |
| `rom-editor/js/battletriggers.js::polarityOf` | **逐条**标出极性：0x34/0x36/0x38/0x39 = 「成立才跳」，**0x35 = 「不成立才跳」** |
| `rom-editor/js/battletriggers.js::conditionDetail` | 0x35 的摘要是**两句**：「复合条件（三个参数未命名）成立时才继续；不成立就跳过本组。」 |
| `rom-editor/js/battletriggers.js::classifyTarget` + `targetText` | 跳转目标解析表补齐（见 §2 P1-4） |
| `notes/story-vm-opcodes-20261020.md` §3 / §7 | 补记「命中才跳」这条结论（仓库以前没写清楚） |

界面上给作者的读法写在列表顶部（一次性说明，不在每个块里重复）：
**守门条件成立就跳到「命中时跳到」那一列（多数是跳过本组），全部落空才会压入事件 id、触发那一段对白**；
0x35 反过来（复合条件成立才触发）。

### M2｜操作数的 `before_hex` —— 选了 **①**

**选 ①：扩 `storyvm.js::editableOperands`，让它一并产出 `before_hex`。**

- 落点：`rom-editor/js/storyvm.js` —— `editableOperands` 的每个操作数现在都带
  `before_hex`（原版字节，小端 hex）。
- 为什么选 ①：`common.js::operandInput` **不补** `before_hex`，它能用是因为内容包里的
  `pack.scripts[].operands` 自带这个字段；新算出来的操作数没有它就喂不进写回通路。
  ① 让「从 ROM 现场算出来的操作数」和「内容包里带的操作数」**同一种形状**，
  before / after 剧本与剧情触发条件共用一条路。
- 代价：`scriptview.js` 自己那份私有 `operandInput` 仍然在提交时用
  `bytesOf(ctx, operand)` 重算 `before_hex`（值相同），行为不变；本轮没有删它，
  只是让它不再是唯一的来源。

**写回通路没有新开**：仍然只有 `pack.setText` / `pack.setScriptOperand` / `pack.setBytesAt`。

### M3｜验收标准里三条会误判的

### 另两处按审核改写的措辞

- **1 基映射**：界面上不裸说「1 基」，写「**按 ROM 字节推定：压入的值 N 选中链上第 N 段（静态字节证据，未做运行期确认）**」
  （`battletriggers.js::ONE_BASED_NOTE`，列表顶部与模型里同一句）。
- **D5 的理由 3 重写**：设计稿原话「0x32 的载荷一动就要重划块边界」**不成立** ——
  段边界由**链的顺序**和每段尾部的 `0x00` 决定，改载荷只是把这一段的内容换成别处的字节。
  **结论保留**（这一轮不给 u32 目标输入框），但理由改成三条真的：
  ① 它是地址不是参数；② 可能指到非指令边界且不报错；③ 作者真正想改的「触发哪一段」
  由 `0x33` 的 value 控制，**已经可改**。

## 5. 学到的东西 / 现在重要的地址

| 项 | 值 |
|---|---|
| 1 基映射的字节证据 | `0x08097D1A: subs r0,#1` → `0x08097D1C: cmp r0,r4`（链游标 0 基，先比后增） |
| 0x34 的两个被读字节 | `byte[0x0202680C]`（**回合计数**，字面量在 `0x0808A1A0`）与 `byte[0x0202680E]`（**没有名字**，字面量在 `0x0808A1B8`，读的是 `+2`） |
| 0x35 的极性 | `a ≡ 0` ⇒ handler 的 `cmp r4,r0` 相等时跳 ⇒ **不成立才跳** |
| 条件指令跳转目标分布 | 1013 条：868 下一组首条 / 118 脚本末尾 / 19 本组内部 / 3 本组自己的 0x33 / 5 后面某一组的 0x33 / 0 其它 |
| 触发块数 | 407 = 400（选得到段）+ 7（场景 32..38 各多压一个 0） |
| 无条件触发块 | 33（场景 32..38 各 4 + 场景 7 的 4 + 场景 8 的 1） |
| 场景 32..38 的特殊结构 | logic 根 + 8 = events 根（同一段字节）；每关 4 条 0x33 压 0/1/2/3，链长 3 |

## 6. 还没解决的（别当成已定案）

1. **`0x0202680E` 的取值域** —— 仓库两种说法互斥（0/1 与 0x0E/0x0F），需要一次运行期读数。
2. **`0x0202680C` 的名字** —— 「回合计数」与「战斗阶段 / 子阶段」同址异名，界面已标争议。
3. **1 基映射的运行期确认** —— 静态证据齐了，动态没做。
4. **0x35 的 f(b,c,d)**、**0x36 的 b**、**0x37/0x38 的模式取值** —— 界面照实显示原始数字 + 「未命名」。
5. **场景 32..38 多压的那个 0** —— 静态上选不中任何一段，它为什么存在、还有没有别的消费者，仓库没有答案。
6. **u32 跳转目标的输入框** —— 这一轮不给（理由见 §2）；以后要开，必须同时满足：新目标在同一剧本内、新目标是该剧本里某条指令的起点、界面给一次确认并提示「这会改变触发顺序」。
7. **条件指令的执行频率**（每回合判一次还是每帧判一次）—— 没验证；界面上没写「每回合」这类话。

## 7. 真浏览器复核（第十二轮补做）—— 查出两个**只有像素能查出来**的布局 bug

实现子代理自己承认「载入真实 ROM 后的浏览器视觉复核：没有做」，只做了无头 DOM 桩。
这一轮把它补上，**查出两个真 bug**，都已修掉。

### 7.1 为什么编辑器里的「载入内置 ROM」在这台机器上一直失败

先查清了一件**既有的、与本轮无关**的事：在这台机器的内置 FilePanel 浏览器里，
点「载入内置 ROM」没反应，状态一直是「未载入原版 ROM」。

- `rom-editor/content/base-rom/rom-loader.html` 的注释写明了原因：
  **这个嵌入式浏览器单个文档只能下载约 1 MB**（实测值），
  而 ROM 压缩后是 2.7 MB。
- 现在的 `rom-loader.html` **忽略**父页面传来的 `from` / `count`（切片参数），
  一次把整个文件取走 ⇒ 必然超限、必然卡死。
  父页面（`js/romsource.js::loadRomSlice`）等的 `from`/`count` 参数其实**从来没被用过**。
- 兜底的 `fetch('../rom/base.gba')` 是 6 MB，同样超限 ⇒ 两条路都走不通。
- 顺带查到：`python -m http.server` **不支持 Range**（实测：请求 `Range: bytes=0-1023`
  仍返回完整的 2,702,839 字节、没有 `Content-Range`），
  所以「切片下载」这条设计**需要服务端支持 Range**，或者改成
  `content/base-rom/part-*.bin` 那种预切块（`js/romsource.js` 的注释里提到过，
  但仓库里**没有**这些文件）。
- **结论**：这是**既有的环境限制**（普通浏览器 Chrome / Edge 里没有 1 MB 上限，
  编辑器正常），**不是本轮引入的**，本轮也**没有改**它 ——
  改它要动 ROM 载入通路，属于另一件事。记在这里，别当成本轮的锅。

### 7.2 绕开它的办法：只给这一场关卡用得上的那几百字节 ROM

触发列表其实只需要**某一场关卡那两个剧本的字节**。于是：

| 新文件 | 干什么 |
|---|---|
| `tools/probe_battle_story_qa.mjs` | 抽出某一场用得上的 ROM 字节，写成 `build/battle-story-qa-scene-N.json`。**自校验**：拼出来的**稀疏 ROM** 必须与完整 ROM 产出**逐项相等**的触发模型（块数、每条条件的操作数、跳转目标、事件 id、摘要），不等就报错退出、不产出载荷 |
| `rom-editor/tools/qa-trigger-view.html` | 在真浏览器里用仓库**真正的模块**（`pack.js` / `storyvm.js` / `battletriggers.js` / `battle-sections.js`）与**真正的样式表**渲染那张卡片；只下载内容包（324 KB gzip）与那几百字节 |

实测第 40 场：**440 字节** ROM + 588 个 base64 字符的载荷，
稀疏 ROM 与完整 ROM 的模型**逐项相等**。

### 7.3 内置浏览器的截图不可信 —— 怎么绕过去的

- **DOM 查询是活的**：`query kind=dom` 拿到的 `#wide` 是**完整正确**的渲染结果
  （根指针表、1 基限定词、触发块行头、四列条件表、带字节预算的对白输入框，全在）。
- **截图是陈旧帧**：页面异步渲染完之后再截图，拍到的仍是「正在取回内容包…」。
  `query kind=editable` 在同一时刻返回 **0 个**可交互元素 ——

### 7.4 查出的两个布局 bug（都已修）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | **触发块里的三张表全塌成一条横线**（事件 id 表、条件表、对白表全没有内容） | `styles.css:144` 的 `.table-wrap { flex: 1 1 0; }` 是给**行向** flex 容器控制**宽度**用的；而 `.trigger-body` 是**列向** flex 容器，`flex-basis` 就落到了**高度**上。加上 `.table-wrap` 自带 `overflow: auto`（**自动最小尺寸因此归零**），表格被压成 0 高 | `rom-editor/css/battle-map.css` 加 `.trigger-body > .table-wrap { flex: 0 0 auto; }`（高度按内容算，宽度仍由 stretch 撑满） |
| 2 | 条件表最后一列「这条条件在测什么」是**长句**，被顶出容器、只能横向滚动才看得到 | `styles.css` 的 `table.grid td { white-space: nowrap; }` 是全局的 | 给条件表加一个类 `cond-table`，最后一列放开 `white-space: normal` + `min-width: 240px`。`common.js::summaryTable` 加了**可选**的 `rows.class`（不给就是原来的 `grid`，**向后兼容**） |

另外顺手修了一处：窄栏（战斗域侧栏 `var(--split-right, 420px)`）里条件表有四列，
**输入框被挤到十几像素**（点不进去、改不了）⇒ 给
`.trigger-body .num-input { min-width: 60px }` 与
`.trigger-body .text-input-inline { min-width: 180px }`，
宁可让 `.table-wrap` 横向滚动（编辑器里其它宽表都是这个规矩）。

**几何实测**（静态快照内置的测量脚本）：

| 栏宽 | 输入框 | 最窄输入框 | 条件表宽 | 容器宽 |
|---|---|---|---|---|
| 700px | 23 个 | 60px | 709px | 679px |
| 420px（真实侧栏） | 23 个 | 60px | 709px | 399px |

窄栏里条件表 709px > 容器 399px ⇒ `.table-wrap` 横向滚动；
这是**四列 + 长句说明**在 420px 里的必然结果，与编辑器其它宽表一致。
