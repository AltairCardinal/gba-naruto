# 木叶战记 ROM 编辑器：方法、结果与边界（2026-10-21）

> 本文记录本轮**把逆向成果做成 ROM 编辑器**的完整过程：试了什么、学到什么、
> 哪些文件与地址区间现在是重要的。目的是让后来的人能复核，而不是重走一遍。
> 面向使用者的说明在 `docs/rom-editor.md`；工程约定见 `AGENTS.md`。

## 0. 出发点

2026-10-20 的策略反转已经确定了工程形态：**单文件夹离线 ROM 编辑器**，
写回模型是「复制原生条目 + 只改已知字段 + 未知字段 raw 兜底」，
验收标准是「按需动态证据」。本轮把它落地。

目标（用户原话）：

> 根据逆向工程成果制作 ROM 编辑器……每一个编辑功能都要具备对原版 ROM 中所有内容的
> 呈现，即根据编辑器中的初始数据就可以构建一个完整的原版 ROM，并且可以对原版 ROM 中
> 任意内容都在编辑器中实现修改。

拆成三条可验证的命题：

| 命题 | 验收方式 |
|---|---|
| A. 六个域都能编辑，且呈现的是**全量**内容 | 浏览器内自检逐个模块渲染 + 面板打开 |
| B. **初始数据**可构建出**逐字节相同**的原版 ROM | `node rom-editor/tools/verify_pack.mjs` |
| C. 任意内容可改 | 结构化表 + 整卡带十六进制编辑器 |

## 1. 方法：把「内容」从 ROM 变成自描述的数据包

### 1.1 为什么要有「内容包」

编辑器要满足 B（初始数据即可构建完整 ROM），就不能在运行时去问 ROM 本身要内容，
必须有一份**自包含**的数据。这份数据就是 `content/pack.json`：

* 每条记录带 `raw`（原始字节）与 `values`（按字段解码的值）；
* 每张表的字段列表**精确铺满整条记录**：已知字段 + 未解字节的 `hex` 填充字段。

第二条是 B 的关键：**字段铺满 ⇒ 值能唯一还原字节 ⇒ 未改动即原样**。

### 1.2 导出器

`tools/export_content_pack.py` 从 `rom/base.gba` 导出：

* **40 张结构表 / 6,676 条记录**；
* 10 张文本表 / 2,199 条文本；
* 字形码表 4,261 项（解码用 `code_to_char` + 编码用 `char_to_code`）；
* 原版 ROM（gzip）随包一起提供，供编辑器直接重建。

**用仓库既有工具，不重新推导**：`tools/text_codec.py`（字形码）、
`tools/table_registry.py`（基址裁决）、`tools/character_templates.py`、
`tools/import_battle_config.py` 的字段定义。

### 1.2.1 记录模型的一条硬规则（踩过坑）

字段列表必须描述**单条记录**，不是整张表。

踩坑形态：字段按整张表展开（`value_0..value_42`、`ptr_0..ptr_55`…），
但记录模型是「一条记录 = 一行」。于是每条记录的 `values` 里塞进了
**跨越到后续记录**的字段，而 `tile()` 不报错。

后果有三层：

1. 包里同一张表的整行数据被复制到每一行（包体积虚胖）。
2. 编辑器 `recordBytes()` 把每个字段写进 `entry_size` 长的缓冲里，
   **偏移越界的字段被静默丢弃** —— 也就是**改了不生效**。
3. `values` 与 `raw` 不自洽，违反「只用字段值就能重建」这条不变量。

修复：每条记录只带属于自己那几字节的字段（`unit_slot_remap` / `unit_delta_table` /
`object_descriptors` / 四张剧情根表由「整表字段」改成单字段），
并给 `tile()` 加了越界检查，消息直接写明「字段必须描述【单条】记录」。

> 这条缺陷的完整证据与复现命令见
> `notes/evidence/content-pack-export-20261021.md` §3。

### 1.3 两条必须遵守的硬约束（踩过坑）

1. **字段列表不许重叠。**
   `tools/character_templates.py::JUTSU_RECORD_FIELDS` 里 `record_0x02_flags`
   声明成 `+0x02 u16`，同时又单列了 `+0x03 u8` —— 两者重叠。
   导出器直接报错拦下来了。实测 `+0x0F` 在 87 条记录里**恒为 0**，
   所以 `growth_per_level` 实际是 `+0x0E` 的**单字节**（仓库里记成 u16 是
   「高字节恒零」的等价写法）。`+0x02` 则确实是 u16（`&0x1800>>5` 要用高字节）。
   → 布局按 ROM 实测定，不按注释抄。

2. **字形码表的键要用十六进制、并且要带「规范码」。**
   最初导出器写的是十进制键（Python `str(code)`），JS 端按十六进制解析，
   整张映射全错——症状是编出来的字节解码回去是乱码，而「未改动的包重建 ROM」
   仍然逐字节相同（因为没改动的文本表根本不写回）。
   改十六进制后暴露第二层问题：**8 个字在 ROM 字库里有两个码位**，
   编码必须用「基本区」那个（`tools/text_codec.py::build_canonical_reverse_mapping`
   的规则），否则回读会变成另一个字。
   → 内容包因此同时带 `code_to_char` 与 `char_to_code`。

## 2. 结果：ROM 重建与写回

### 2.1 逐字节相同（B 命题）

`node rom-editor/tools/verify_pack.mjs`（25 项，全 PASS）：

```
[ PASS ] 写出字节与原版完全一致 — 重建 sha256=1198ece781aaf629…
[ PASS ] 逐字节比较无差异
```

未改动内容包 → 重建 ROM → **sha256 与 `rom/base.gba` 完全相同**。
内容包自身的等价校验：`python tools\export_content_pack.py --check` → `OK`。

更强的形式（探针 `build/content_pack_roundtrip.py`）：
**6,676/6,676 条记录都能只用字段值重建回原字节**（`values → bytes == raw == ROM`），
也就是「初始数据」与「ROM」之间的双向一致。

### 2.2 逐域落点（改一个字段，只动那几字节）

| 域 | 结构 | 落点 |
|---|---|---|
| 角色属性 | `character_template.hp_base` | `0x5424DA`（+0x0A，2 字节） |
| 道具 | `reward_table.gold` | `0x59EAE0`（2 字节） |
| 忍术 | `jutsu_record.growth_amount` | `0x5454B6`（+0x0E，1 字节） |
| 战斗 | `map_table.background_id` | `0x53D98C`（+0x1C，1 字节） |
| 战斗 | `battle_actors.x` | `0x566852`（+0x02，1 字节） |
| 剧情路线 | `mission_index.value` | `0x348DB0`（1 字节） |

每项都断言「改动的字节**全部**落在该字段区间内」。

### 2.2.1 原始字节补丁：任意字节都能改（C 命题的兜底通道）

「原始字节」模块把改动记成**显式补丁**（`pack.patches`：`offset` + `before_hex` +
`after_hex`），构建时按「原字节必须匹配」写回。三条断言已加进命令行自检：

| 断言 | 结果 |
|---|---|
| 单字节补丁落在指定地址 | ✅ 改动 1 字节 @0x76D |
| 原字节不匹配的补丁**被跳过并报告**（不写坏别处） | ✅ 警告「补丁 raw.stale 的原始字节不匹配（已跳过）」 |
| 多个补丁同时生效且互不干扰 | ✅ 改动 3 字节 |

同址二次修改会**合并进同一条补丁**（浏览器内自检断言补丁数不变）。

### 2.3 文本：两类长度策略

ROM 里的文本是**字形码流**（lead 0x80–0x9F 的双字节码），不是 Shift-JIS。
文本分两类，编辑器的行为也不同：

| 类别 | 判据 | 变长 |
|---|---|---|
| 可重定位 | 被**指针表**指向（人物名表、忍术名表、任务表、对白槽位表…） | 整表重新排布到空闲区并改写指针 |
| 等长改写 | 被代码里的**绝对地址**引用 | 只能等长，超长报错不截断 |

空闲区：`0x5DFBEC`–`0x600000`（实测 132 KB 连续 0xFF 填充区）。

**踩过的坑**：第一版把「可重定位」当成「整表 blob 原地重排」，
结果把人物名表散落的字符串之间的**空隙**也覆盖了——因为原表的字符串
并不连续（`0x1CD0`、`0x1CD5`、…，中间有别的数据）。
现在只有当记录**严格连续**时才原地重排，否则一律搬到空闲区。
另有一个更隐蔽的坑：空闲区分配器**没有记账**，第二张表会覆盖第一张表刚写进去的 blob。
→ 现在 `this.allocated` 记录本次构建已占用的区间。

### 2.4 改不动的部分（诚实边界）

| 不能改 | 为什么 |
|---|---|
| LZ77 压缩载荷（战场图块/调色板/图层/组合图块/通行值表、头像图像、资源记录里的图块） | 仓库里只有字面量编码器（`tools/lib/lz77.py::compress_literal`），没有与原版逐字节一致的压缩器；原地改写需要「压缩后长度 ≤ 原长 + 0..3 字节对齐余量」 |
| 故事 VM 剧本的**指令与文本** | 分支目标是**绝对 ROM 地址**，改长度会让全部分支失效；仓库既有写回路径（`tools/import_story_script.py`）也只改定宽操作数（编辑器同样只暴露这些） |
| 文本里的**控制码本身** | 编辑器的文本框只显示文字；控制码（`0x01`/`0x02`，带换行/分页的排版含义）**按原位置保留**但不可在文本框里改，要改请用「原始字节」模块。影响 2,953 条记录 / 9,729 个控制字节 |
| 道具记录 16 字节的字段语义 | 仓库里**没有任何一处**证明过它们是什么，所以按原始字节呈现与编辑，不臆造字段名 |
| 音频采样本体 | 音频是 m4a 格式；包里只有**描述符层**（歌曲头、轨道指针、sound-ID 分派表），采样数据要另走 m4a 导入流程 |
| 指针指向的资源本体 | 头像 / 关卡块 / 底图 / 资源记录指向的图形与调色板不在包里（同第一条：缺一致的 LZ77 压缩器） |

### 2.2.1 控制码：改写文本不得破坏排版（一个真的数据破坏 bug）

**症状**：编辑 `mission_descriptions` / `mission_hints` / `rom_text_index`
里的任意一条文本，构建报告却是 `errors=0, warnings=0`，但：

* 改 1 条 `mission_descriptions` 记录 → **改动 2,186 字节**；
* 该表 **77 条记录的控制码全部被抹掉**。

**成因链**（三处都错）：

1. `tools/export_content_pack.py` 用 `tools/text_codec.py::decode` 解码文本，
   而 `decode` **剥掉**控制码（`01 xx` / `02 xx yy`）→ `record.text` 里没有它们；
2. `rom-editor/js/textcodec.js` 的 `FontCodec.encode()` 只按字符串编码，
   **吐不出**控制码；
3. `rom-editor/js/rom.js` 的 `rebuildTextTable` 整表重新编码 →
   控制码被静默丢弃，而**排版含义（换行/分页）就这样没了**。

这直接违反仓库既定规则（`notes/font-encoding.md:133-143`：「控制码必须保留…改写已有
文本不能用纯字符串编码，否则会破坏排版」，要求走 token 流 `encode_tokens`），
也违反编辑器自称的写回模型。

**修法**（四处）：

1. **JS 侧补齐 token 流**（`rom-editor/js/textcodec.js`）：
   `scanTokens` / `encodeTokens` / `mergeTokens` / `countControlCodes`，
   与 `tools/konoha_font.py::scan_tokens` / `encode_tokens` 对齐。
2. **写回走 token 流**（`rom-editor/js/pack.js::setText`）：
   新文字按**原分段长度**切分塞回原来的文本段，控制码留在原位
   （`mergeTokens`：原流是 T0 C1 T1 C2 T2…，新文字按 T0/T1/T2 的原长度分配，末段吸收增减）。
3. **构建器逐条记录处理**（`rom-editor/js/rom.js::rebuildTextTable`）：
   放得下的记录**原地写、指针不动**；放不下的**单独**搬到空闲区并改写它自己的指针。
   → 改一条文本只动那一条记录，不再整表重排。
4. **构建器不再修改内容包**：摆放结果只记进 `report.movedTexts`。
   此前构建会把 `record.text_offset` 改掉，于是「导出 → 导入 → 再构建」得到的是
   **另一个** ROM；现在内容包保持原样，构建是确定性的。

**顺带发现并修掉的两个真 bug**：

* **悬空控制字节**：有些记录末尾是 `… 6a 01`，`01` 的载荷字节就是字符串结束符。
  扫描时按「缓冲区里实际有几个字节就记几个」处理，否则会给它补一个 0，
  往返就不逐字节相等了。（仓库的 Python 扫描器跑在整块 ROM 上，会把结束符吞掉
  并**串到下一条记录**——编辑器按记录切片，不犯这个错。）
* **固定槽位的零填充**：内联的说话人名表每条 12 字节，字符串后面是 0 填充；
  重新编码时要把填充补回去，否则槽位形状变了。

**校验结果**：

| 检查 | 结果 |
|---|---|
| 1,895 条文本记录「token → 字节」逐字节还原 | **0 条不一致** |
| 编辑一条带控制码的记录 | 控制码 **2 → 2**，一个不少 |
| 同表其它记录 | **0 条**被牵连（此前整表重排） |
| 改动量 | **29 字节**（此前 2,186 字节） |
| 导出内容包再导入后重建 | 结果**一致** |
| 控制码会不会变少 | 构建器会**拒绝写回并报错**（`errors` 非空） |

### 2.2.2 剧情路线：路线不在表里，在脚本里

**剧情路线**（哪个场景接哪个场景）**没有任何表**。它藏在剧情 VM 脚本的
「下一场景」指令里：

| 指令 | 处数 | 含义 |
|---|---|---|
| `0x16` | 48 | 转到该场景的 after 剧本，并记住下一场景 id（`state[0x1A]`） |
| `0x1A` | 15 | 直接推进路线游标（`state[0x16] = scene`） |

做法：复用仓库自己的扫描器（`tools/import_story_script.py::scan_script`），
把 4 根根表 × 全部场景的脚本扫一遍（**23,146 条指令，0 个坏根**），
只抽两样东西进内容包：

* **路线边**：`0x16` / `0x1A` 的出现位置与操作数（202 个剧本 / 63 条边）；
* **可改的定宽操作数**：`0x16/0x1A`（路线）、`0x1E`（载入地图）、`0x1F`（子配置）、
  `0x23`（队员），以及 `0x22`（把角色加入战斗配置）的 3 个原始字节
  ——它的字段含义还没钉死，所以按字节呈现而不臆造字段名。

**为什么这些能安全地原地改**：它们都是**定宽**的。改一个字节不移动任何后续字节，
因此脚本里那些**绝对地址**的分支目标依然指向原处。这正是仓库既有写回路径
（`tools/import_story_script.py`）成立的同一个前提——所以编辑器与它不会打架。

自检：命令行与浏览器内各有一条断言，确认「改一个「下一场景」值」只动
脚本里那**一个字节**。

### 2.2.3 战斗中的「角色出生」

战斗中的角色出生**没有单独的表**。剧本里的 `0x22` 指令「把角色加入战斗配置」
拿关卡 id 与变体 id 去**编成矩阵**里扫 12 个槽位，找角色 id 匹配的条目，
取出等级并把模板拷进战斗单位。所以：

* 编成矩阵（角色 id / 阵营 / X / Y / 等级）可改 ⇒ **战斗中谁出场、在哪出现**可改；
* `0x22` 的 3 个操作数字节可按字节改（含义未钉死）。

| 忍术 | 忍术记录表 `0x545458` | 忍术名表 `0x59937C` |
| 战斗 | 战场描述符 `0x53D910`、编成矩阵 `0x5461C4`、战场物件（编成组 +0x8A4）、战斗目标 `0x594758`、战斗遭遇记录 `0x54229C`、关卡数据块 `0x53DF70`、对象描述符 `0x53F140`、精灵动作表 `0x596CCC`、战斗/地图事件分派表 `0x53E698`、精灵帧描述符 `0x53EE98`、拾取分派表 `0x0815E4` | 战斗目标说明文字 `battle_objectives`（219 条，绝对地址引用） |

| 音频 | sound-ID 表 `0x465B70`、5 首 m4a SongHeader（`0x536368` 等）、函数指针表 `0x53D5F0` | — |
| 素材与资源 | 数据指针表 A `0x5A143C` / B `0x5A2034`、图块/精灵资源记录表 `0x5A320C` | — |

> 「音频」与「素材与资源」不是用户点名的六个域，但这些表在 ROM 里**已被证实**
> （`tools/table_registry.py` 标 `verified=True`），不摆出来就谈不上
> 「所有内容的呈现」。它们指向的**资源本体**不在包里（见 §2.4）。

### 战斗的「四件套」是按原生 id 串起来的

```
关卡 id N
  ├─ 战场布置   map_table[N]          = 0x53D910 + N×32
  ├─ 角色出生点 battle_actors[N][变体] = 0x5461C4 + N×0x1AAC + 变体×0x8E4 + 4 + 槽位×0xB8
  ├─ 战斗目标   battle_rules[N][变体]  = 0x594758 + N×0xCC + 变体×0x44
  └─ 战斗中的剧情 story_logic_root[N] / story_events_root[N]
```

**「战斗过程中触发的角色出生」没有单独的表**：剧本里的 `0x22` 指令
「把角色加入战斗配置」拿关卡 id 与变体 id 去编成矩阵里扫 12 个槽位，
找角色 id 匹配的条目，取出等级并把模板拷进战斗单位。
所以**改编成矩阵里的角色 id / 等级 / 出生点，就等于改了战斗中谁出场、在哪出现**。
编辑器因此把「角色出生点」做成战斗模块的核心视图。

## 5. 浏览器侧：一个环境坑与它的解法

### 5.1 现象

本机内置浏览器（Electron FilePanel）对**单页下载量**有上限，实测约 **6.3 MB**：

| 场景 | 结果 |
|---|---|
| 单独取 6.3 MB 的 ROM | ✅ 16 ms |
| 单独取 3.1 MB 的内容包 | ✅ |
| 两者都取 | ❌ 第二个永远不返回（不是报错，是挂住） |
| 取 3 个小文件后再取 6.3 MB | ❌ |

**服务器不是原因**：同样的 URL 用 `curl` 取，6.3 MB 只要 23 ms（271 MB/s）；
Python 直接读盘 2 ms。瓶颈在浏览器的网络层。

试过并**排除**的方案：

| 方案 | 结果 |
|---|---|
| 单个 8.4 MB base64 `<script>` | ❌ 卡住 |
| `DecompressionStream` 解 8.4 MB base64 | ❌ 卡住（多兆 `atob` 本身就慢） |
| 32 KB / 256 KB / 700 KB 分片 | ⚠️ 分片本身能取到，但**整包仍然超限** |
| 每个分片一个 iframe 文档 | ⚠️ 上限是**每个浏览器页会话**的，不是每文档 |
| 服务端 `Content-Encoding: gzip` | ❌ 反而多了一层解压 |
| `Connection: close` / keep-alive 切换 | ❌ 无差别 |

### 5.2 结论与设计

**上限是「一个页面会话」的总下载量（约 6.3 MB），不是每文档、也不是每请求。**
ROM 本身 6,291,456 字节 ≈ 6.3 MB，单独占满预算。

于是设计成：

* **内容包**（3.1 MB）由页面自己取（经一个专用载入器文档，保证它是该文档的第一次请求）；
* **原版 ROM**由作者提供：顶栏「载入 ROM」选文件（0 字节下载，永远可靠），
  或点「载入内置 ROM」让内置分片自己去取（普通浏览器可行，本机嵌入式浏览器可能失败，
  失败时明确提示改用文件选择）。

浏览器自检因此不下载 ROM，用**合成基底 + 参考构建**做相对断言；
「与原版逐字节相同」由 `node rom-editor/tools/verify_pack.mjs` 负责
（同一套 `js/rom.js`、`js/pack.js` 代码）。

### 5.3 附带发现：静态服务器的两个细节

* 目录路径要回落到 `index.html`（否则 `/rom-editor/` 404）；
* `res.end(body, () => res.socket?.end())` 与 `res.end(body)` 在
  `Connection: close` 下**行为不同**：前者能正常把 body 送完，后者的
  客户端会看到挂起的响应。实测同一份 `pack.json.gz` 在前者 15 ms 取完、
  在后者挂死。

## 5.4 第二轮（2026-10-21 晚）：战斗目标说明文字 + 一个真 bug + 一个环境坑

### 5.4.1 战斗目标的说明文字：从裸指针变成可读可改的原文

**试了什么**：战斗模块原来把胜负条件的说明文字只显示成一个十六进制指针
（`g0_0_text_ptr` = `0x080097E4`）。作者看不到那句话，也就无从改它。

**学到了什么**：那 230 个指针指向的句子**全都是真文本**，只是之前没有被
呈现出来 —— 其中 32 条还因为一个导出器的 bug 整块消失了（见 §5.4.2）。

**怎么做的**：给内容包加了一张**专用文本表** `battle_objectives`（219 条不重复的句子），
表里带 `bindings`（哪条条件用哪句话）。战斗视图直接显示那句话，并给出输入框就地改写。

**为什么不放进「全 ROM 文本索引」**：同一段字节只能有一个归属。
两张表都写同一个地址时，改动会互相覆盖（后写的赢）。
所以导出器现在把战斗目标说明文字的 219 个地址**从文本索引里剔除**，
并在自检里断言「两者零重叠」。

**结果**：230/230 个条件指针都能解析到原文；改一条说明文字只动那一条
（实测「打败业头・冥头了」→「打打业头・冥头了」= 2 字节 @0x7F1D）。

### 5.4.2 导出一个真 bug：`0x0A`（换行）被当成非法字节

**现象**：战斗目标里有 32 条说明文字**在文本索引里找不到**。它们的字节长这样：

```
97 cf 8c 5b 8b 62 8f b8 95 a1 95 fa 89 67 8b d1 8c 5b 8b dd 0a 00
```

**判死检验**：这些字节不是乱码 —— 每个两字节组合都落在字形段表的码位空间里
（`0x8AEF` / `0x8C5B` / `0x9169` …），而且句子结尾是 `0x0A`。
`notes/font-encoding.md` §2 的码位表写得很清楚：**`0x0A` = 换行，是合法码位 10**。
而导出器 `tools/export_content_pack.py::build_dominant_text_index` 的 `is_text()`
却写着 `if b < 0x20 or b > 0x7E: return False` —— **把换行当成非法字节，
整块字符串被丢掉**。

**影响面**：全卡带里所有含换行的文本块都从索引里消失，**共 1,126 条**
（16,008 → 17,134）。其中 32 条正是战斗目标说明文字。

**修法**：`is_text()` 显式放行 `0x0A`（与码位表对齐）。

**验证**：
* 17,134 条全部能「token → 字节」逐字节还原（新增的那些带换行）；
* 230/230 个战斗说明指针解析成功；
* 内容包重建 ROM 仍与原版逐字节相同。

### 5.4.3 条件类型的语义：type 2 不是「指定角色仍在场」

编辑器原来把 type 2 标成「指定角色仍在场」。但 `notes/battle-tables.md` §1.1.1
用无头 mGBA 探针在模拟器里跑过：**类型 2 根本没有读 `rule.a/rule.b`**，
它比较的是「回合上限 == `0x0202680C` 的首字节」。而 2026-10-21 的运行时读数
证实 `0x0202680C` **就是回合计数**（回合推进时 1 → 2）。

所以这一版 ROM 的 type-2 实际表达的是**「回合用尽」**，数据里那对
`(阵营, 角色ID)` 是冗余的。编辑器现在按**原生行为**标注，并把每个类型的
a/b 含义写出来（type 3 = 指定角色**已离场**，a=阵营、b=角色 id）。

### 5.4.5 覆盖面核对：审计的 47 个结构 vs 内容包的 40 张表

**试了什么**：完成度审计（`tools/completion_audit.py`）覆盖 **47** 个结构，
而内容包只有 **39** 张表（现已补到 **40**）。差的那些是什么？会不会漏了
「原版 ROM 里已证实的内容」？

**怎么核对的**：把审计条目按**基址**与内容包的结构对齐（同址不同名的算同一张）：

| 审计 key | 基址 | 内容包里的对应物 |
|---|---|---|
| `resource-pointers` | `0x596F0C` | `sprite_action_table` `0x596CCC` 的**窗口**（`+0x240` = 精灵 4 / 动作 0）——不是独立表 |
| `text-writeback` | `0x461CE8` | 文本表 `dialogue_slots`（同一个指针表） |
| `ninjutsu-names` | `0x599634` | 文本表 `ninjutsu_names` |
| `story-b/c/d/e`、`story` | `0x536368` 等 | 音频域的 5 个 m4a SongHeader |
| `sprite-animations` / `sprite-action-table` | `0x596CCC` | `sprite_action_table` |
| `levels` | `0x5459C8` | `character_perks`（角色特性表，同一张） |
| `character-stats` / `-b` | `0x545068` | `per_character_stats` |
| `units` | `0x53F298` | `unit_slot_remap` |
| `encounter-zones` | `0x53D910` | `map_table`（战场描述符） |
| `menu-ui` / `portrait-table` | `0x5A4DEC` | `portrait_table`（头像表） |
| `battle-config` / `skills` / `items` | `0x545458` / `0x545BE4` | `jutsu_record` / `item_record` |
| `map-sprites` | `0x53F140` | `object_descriptors` |
| `battle-handlers` / `map-events` | `0x53E698` | `battle_handler_table` |
| `mechanism-effects` | `0x0808136C` | **代码地址**，只读参考 |
| `runtime-state` | — | **WRAM 运行时状态**，不在 ROM 里，只读参考 |
| `sappy-engine` / `palettes` / `audio` | — | **已退役**（审计里 `retired=True`） |
| **`save-state`** | **`0x53D848`** | **原先缺！** → 已补进内容包（`wram_allocation`） |

**结论**：唯一真正漏掉的是 `save-state` `0x53D848` —— 它已被证实是
**WRAM 分配表**（10 组 `{u32 EWRAM 地址, u32 大小}`，4 个原生读者
`0x0806869A / 0x08068954 / 0x08068CC0 / 0x08068D98`），
**不是**存档描述符表（存档数据在 SRAM，不在 ROM）。
现在它作为 `wram_allocation` 进包（素材与资源域）。

补完之后，**审计覆盖的 47 个结构里，所有「在 ROM 里且未被裁决为只读/退役」的
结构都在内容包中**；剩下的 4 个是只读参考（2）与已退役（3），
外加 `resource-pointers` 那个窗口（已被精灵动作表覆盖）。

**验证**：内容包 40 结构 / 6,676 记录，`values → bytes == raw == ROM` 全部成立
（`build/content_pack_roundtrip.py`），重建 ROM 与原版逐字节相同。

### 5.4.6 角色出生点就地编辑（目标点名要的功能，原来得跳到结构编辑器）

**试了什么**：战斗模块的「按关卡」视图里，「角色出生点」那张表是**只读**的 ——
要看出生点在哪、谁出场可以，但改 X、改角色 id、改等级都得自己跳到结构列表里
找「角色出生点（编成表）」。而出生点正是目标里点名的功能
（*「战斗（战场的布置、角色的出生点、…）」*）。

**学到了什么**：编成矩阵的字段本来就带着语义（`character_id` / `x` / `y` /
`facing` / `level`，阵营是 `unit_flags` 的 bit 0），完全可以在视图里就地改。

**怎么做的**：视图里每一格换成输入框（阵营换成一个下拉框，改的是 `unit_flags`
的 bit 0 —— 因为编成路径**不读** +0x01 那个字节）。写回走
`pack.setValue()`，与结构编辑器同一套模型：只动被改的字段，其余字节原样保留。

**结果**：真实浏览器里 `#battle/stage/40/0` 的出生点表 12 行 × 5 个输入框 +
1 个下拉框都在；无头自检里改一个出生点的 X（4 → 9）后，构建结果证明
**只动了那一个字节**（`@0x588CAA`）。

### 5.4.7 环境坑：页面加载后约 210 ms 自动重载

**现象**：内置浏览器打开 `tools/selftest.html` 后，**约 210 ms 后页面被重新加载**，
自检跑到一半就被冲掉（服务器日志里能看到 `GET /selftest.html` 反复出现）。
这一轮之前的一次性通过记录（42 项）说明它不是常态，但本轮稳定复现。

**证据**（服务器日志带时间戳）：

```
12:10:15.475 GET /rom-editor/tools/selftest.html     ← 页面加载
12:10:15.506 GET /rom-editor/content/pack.min.json.gz ← 内容包
12:10:15.685 GET /rom-editor/tools/selftest.html     ← 210 ms 后重载
```

**怎么绕过去的**（两条都保留下来）：

1. **自检结果落盘**：静态服务器新增 `POST /__report`，自检每检查一项就把当前
   结果发上去，服务端追加到 `build/selftest-report.jsonl`。
   页面被刷新也留得住证据（`GET /__report` 可取回）。
2. **无头视图自检**：新增 `rom-editor/tools/verify_views.mjs` —— 用一个
   ~120 行的 DOM 桩在 Node 里渲染九个模块的视图并断言文字。
   它不依赖浏览器，可进 CI。

**结果**：本机浏览器内自检稳定跑到 **34 项全 PASS**（含新增的
「战斗目标说明文字指针 230/230 解析成功」「战斗视图显示说明文字原文
『得到宝箱了』」）后才被环境重载打断；剩余断言由
`verify_pack.mjs`（30 项）与 `verify_views.mjs`（30 项）覆盖，两者在 Node 里**全绿**。

## 6. 交互重设计：把每个编辑功能的操作流逐个重做（2026-10-21 晚）

> 用户反馈：**「当前版本非常不直观」**。目标是：检查每一项可编辑内容，
> 为每一项编辑功能用一个单独的子代理重新设计操作流，再据此重做交互设计，
> 最终把所有编辑功能的交互流程都迭代一遍。

### 6.1 方法

1. **盘点**：新增 `tools/editor_inventory.py`，把内容包里的**每一项可编辑内容**
   摊成清单（40 张结构表 / 11 张文本表：条数、字段数、分组、字段类型、
   每条记录的位置）。这一步先回答「到底有多少东西要改、哪些地方没人够得着」。
2. **任务书**：`notes/editor-ux-redesign-brief-20261021.md` —— 所有子代理的
   共同事实基准（现状、13 条有证据的摩擦点、产出格式、硬约束）。
3. **一个编辑功能一个子代理**：并发上限 4，分批派出。子代理**只读**，
   产出「可落地的操作流规格」（当前流程 / 摩擦点带文件:行 / 重设计流程 /
   控件类型映射 / 要改哪些文件 / 可断言的验收标准）。
4. **主代理统一落地**：避免多个代理互相改同一份文件。

### 6.2 盘点阶段就查出来的问题（不是子代理找的，是清单里露出来的）

### 6.4 交互层面的改动（按子代理的规格统一落地）

* **结构表编辑器**：记录按 `group` 拆成**可折叠分区**（角色定义表 175 个字段 →
  默认只展开 8 个基础属性字段）；重复槽位渲染成**一张表**（忍术 15 行 × 4 列、
  技能 24 行 × 4 列、道具 9 行、奖励 8 行、胜负条件 4 行、表情 5 行）；
  枚举给下拉 + 中文标签；跨表 id 显示**名字**并可**点着跳过去**；
  上一条/下一条/跳到 id；改过的行与字段都有标记；整表未解码时给**一个** hex 框。
* **文本表编辑器**：面板头写清**写回规则**（可重定位 / 等长 / 归属别处）；
  **字节账本**与构建器同源（超长立刻变红并说明「只能等长改写」）；
  **控制码分段条**（把 0x01/0x02 画成段之间的芯片 —— 文本框里看不见它们，
  但它们决定新文字落在哪）；列表加**标记列**（已改 / 共享 N 处 / ⊘ 无位置 / 控制码 ×N）；
  16,915 行的全 ROM 文本索引默认只渲染前 200 行；改完失焦即保存；
  「恢复原文」改成**字节级**还原。
* **域首页**：三块 —— **推荐入口**（这个域该从哪儿下手）、**本域可编辑内容**
  （表 · 条数 · 字段 · 改法 · 长度策略 · 已改 · 入口）、**一览**（只读，折叠）。
  清单由内容包的 `module` 字段推导：模块自己列的表排前面，**本域剩下的表一律追加**
  —— 一张够不着的表就是作者改不了的表（战斗域 7 张 + 字宽表由此补齐）。
* **导航**：**面包屑**（每层可点）；URL 可寻址到**表格与记录**
  （`#characters/structure/character_template/1`），浏览器后退键从此是在编辑器里后退；
  跨域引用可点着跳转。

### 6.5 这一轮修掉的 8 个真 bug

| # | bug | 后果 |
|---|---|---|
| 1 | 数值溢出被静默截断 | 往 u8 字段输入 999，ROM 里悄悄写成 231；现在按类型校验并**拒绝写回** |
| 2 | `s16` 被当成无符号读 | `unit_delta_table.delta = -4` 读成 65532，于是每条记录都挂「已改」 |
| 3 | 指针型 relation 查表用错键 | 拿绝对地址当下标用，「说明文字指针 → 那句话」永远解析不出来 |
| 4 | 编辑后不刷新 | 表格、字段标记、原值对照都要切走再切回才更新 |
| 5 | 容量判定用了补齐后的长度 | **改一条说话人名就构建失败**（32 条「文本超长：12 字节 > 槽位 12 字节」） |
| 6 | 跨表重复：索引永远覆盖具名表 | 1,808 条重叠，具名表的改动被静默覆盖（构建 0 错误） |

## 6.8 第四轮（2026-10-22）：把「关联」补到全包每一项可编辑内容

> 用户反馈：**「好一些了，但关联还是不够强，例如道具的奖励表，应当提供这些奖励的
> 所有出发来源的跳转和编辑。所有可修改内容都是这样，检查一遍。」**

### 6.8.1 先查现状，别急着改

新增 `tools/audit_crossrefs.py` 查内容包侧的关联，结果很扎眼：

> **116 张结构表里，只有 6 张能被反查到来源。**
> 奖励表、任务索引表、任务文本三表、忍术记录表、道具记录表、逐角色成长表、
> 战场物件、头像指针表、81 张乐曲描述符表……全部是「孤岛」。

原因有两层：

1. **内容包缺语义**：`relation` 只声明了 65 个字段，且没有「连续段基址」
   （任务索引表的 `value` 同时是四张表的起点）、没有「同一件事的两份记录」
   （战斗四件套按关卡对应）、没有「原生读者」。
2. **引擎只认一种关系**：`backReferences` 只扫 `field.relation`，
   指针类字段、表与表之间的 id 空间别名，一律查不到。

### 6.8.2 六条来源路径（全部由内容包驱动）

| 来源 | 机制 | 例子 |
|---|---|---|
| 字段引用 | `field.relation`（text / structure / pointer / by_category / **row_range**） | 角色出生点 → 角色名表 |
| 指针指向 | 指针值 == 某条记录的 ROM 起点 | sound-ID 表 → 81 张乐曲描述符表 |
| 连续段基址 | `relation.kind = "row_range"`（值是一段行的起点） | 任务索引表 → 奖励表 + 三张任务文本表，各 3 条 |
| 同一个 id | `structure.id_relation` 构成的 id 空间（并查集） | 忍术记录表 ↔ 忍术名表；角色定义表 ↔ 逐角色成长表 |
| 同一件事的两份记录 | `structure.peers`（按关卡号对应，双向） | 战场布置 ↔ 角色出生点 / 战场物件 / 战斗目标 |
| 原生读者 | `structure.consumers` / `table.consumers` | 奖励表 4 个、头像拼块表 7 个、说话人名表 12 个 |

### 6.8.3 三处踩坑（都查过才敢写）

1. **指针是 ROM 地址，记录的 `rom_offset` 是文件偏移** —— 两者差一个
   `0x08000000`。第一版按相等比较，81 张乐曲描述符表**一张都连不上**。
2. **`consumer-evidence.json` 里有一批表还挂在作废的旧基址上**
   （`legacy_items_or_skills` 在 0x546100，真基址是 0x545BE4），
   所以按名字对会认错表。改成**按文件偏移对**，并用
   `tools/consumer_locate.py --all` 按更正后的基址重扫了一份
   `notes/evidence/consumer-readers-20261022.json`（134 张表 / 85 张有读者）。
3. **有两处「看起来能连上、其实不能」**：
   - 剧情脚本里的 7,486 处文本引用，与对白槽位表**零命中** ——
     所以没有把对白槽位表接到脚本上（接了就是编造）。
   - op `0x08` 的字节取值 1..61，落在**头像指针表**的 64 条之内，
     而说话人名表只有 32 条 —— 所以它接的是头像表，不是名字表
     （仓库的 opcode 笔记对「名字」那一半本来就留了条件）。

### 6.8.4 结果

- **每一张结构表、每一张文本表，现在都能溯源**（`verify_sources.mjs` 断言）。
- 奖励表 #103 的详情写着：**「第40关 · 奖励下标起点」→ 跳过去**，
  另有 4 个原生读者地址可跳到原始字节。
- 界面上的「来源」块**每条记录都有**：没有来源的写「没有别的字段指向这条记录
  —— 改它只影响这张表自己」，不留白（空面板像功能坏了）。

## 6.10 第六轮（2026-10-22）：「技能表不支持配置么」—— id 空间的另一张表没有入口

> 用户反馈：**「技能表不支持配置么」**

### 6.10.1 先确认事实

技能表**是**支持的：「角色特性表（技能）」（`0x5459C8`，45 条）的
效果类型 / 基础值 / 次要值 / 每级成长 / 附加属性五个字段都能改，
在角色域首页里点「编辑」就能打开。

真正的问题在**入口**：从角色的技能槽点「跳过去」，以前只落到**技能名表**
（一张只有名字、没有参数的表）。参数明明在「角色特性表（技能）」里，
但没有任何入口指过去 —— 于是作者看到的效果就是「技能表不支持配置」。

### 6.10.2 根源：id 空间的别名只走了一半

`structure.id_relation` 已经把「同一个 id 在几张表里指的是同一个东西」记下来了：

| id 空间 | 成员 |
|---|---|
| 技能 / 技术 | 技能名表 `0x5A7060` ↔ 角色特性表 `0x5459C8` |
| 忍术 | 忍术名表 `0x59937C` ↔ 忍术记录表 `0x545458` |
| 角色 | 人物名表 ↔ 角色定义表 ↔ 逐角色成长表 |
| 忍具 | 忍具名表 ↔ 道具/忍具记录表 |

但界面的正向链接只认「字段声明的那张表」（名表），**没有给同一 id 的其它表**。
反向（谁引用了我）上一轮已经补上了（§6.8 的 id 空间别名），这次补的是正向。

### 6.10.3 改法

- 抽出 `rom-editor/js/idspace.js`：id 空间的并查集（无依赖，fields.js 与 xref.js 共用）。
- `fields.js::relationLinks` 在原有链接之外，给**同一个 id 的每一张表**各补一条。
- `slots.js` / `editors.js` 把多条链接都渲染出来（以前只渲染第一条）。

效果：

```
技能槽  跳到「锻炼」→        跳到角色特性表（技能） #1 →
忍术槽  跳到「分身术」→      跳到忍术记录表 #1 →
出生点  跳到「漩涡鸣人」→    跳到角色定义表 #5 →   跳到逐角色成长表 #5 →
```

**这不只修了技能**：忍术、忍具、角色的槽位都拿到了同一条路。

断言：`verify_views.mjs` 第 17 组。

### 6.11.2 「一个东西不拆成几张表」

存储怎么拆是 ROM 的事，**编辑时不该拆**。做法：

- `common.js::domainTableRows` 新增 `options.groups`：**几张表合成一行**，
  行下面列出「由 A / B / C 合成」，入口按钮打开统一视图。
- 六个统一视图（形状一致：**左边按主表列出，右边把其它表作为字段呈现**）：

| 视图 | 主表 | 其它表作为字段 |
|---|---|---|
| 任务 `#route/mission` | 任务索引表 48 关 | 标题 / 说明 / 提示 / 奖励 |
| 角色 `#characters/character` | 角色定义表 63 角色 | 属性 / 成长 / 特性 / 忍术 / 技能 / 道具槽 / 头像 |
| 场景 `#story/scene` | 四张剧本根表 55 场景 | 战前 / 战后 / 逻辑 / 事件 四个剧本指针 |
| 字库 `#story/font` | 字形段表 31 段 | 该段字段 + 256 行字宽表 |
| 忍具 `#items/item` | 道具记录表 94 条 | 名字 / 16 个未解字节 / 在哪几关掉落 |
| 奖励 `#items/reward` | 奖励表 112 条 | 金币 / 强化点 / 等级门槛 / 8 个掉落位 |

**一处更正**：`character_perks` 是**技能 id** 空间（`id_relation → training_names`），
不是角色 id 空间 —— 按角色 id 取会显示别的技能的参数。
所以角色的「特性」段列的是**该角色技能槽里各技能**的特性记录。

**顺带查出的一个数据事实**：掉落位**物品 id 写成 0 = 列表结束**，
所以 112 条奖励里真正被掉落的忍具只有 8 个（id 1/17/18/31/37/40/67/73）。
不认这条规则，会把占位的忍具显示成「掉了 568 次」。

### 6.11.3 剧情对白可改（对照木叶工房）

`notes/external-konoha-workshop-gap-20261020.md` 的 P0-1：第三方「木叶工房 v0.4.4」
（与本仓库**同一份 ROM**，SHA-256 一致）做到了「按场景浏览对白 / 改对白 / 加分支」。
本仓库原来只能改定宽操作数。

现在剧本里的文本段可以就地改写，**等长**：正文内联在脚本字节流里，
分支目标是绝对 ROM 地址 ⇒ 改长改短都会让后面的指令移位、全部分支失效。
界面写明字节预算（多了/少了当场拒收并回滚），控制码 0x01/0x02 原位保留，
写回走 `pack.setBytesAt()` 显式补丁（可撤销）。

顺带：
- **op `0x1B`（播音乐）的曲目 id 可改**（437 处）—— 对应木叶工房 P1-4（18 首曲子）。
- **更正**：op `0x20` 的第 2 字节**不是**游戏里的说话人。handler `0x08097A66`
  读的是对话框状态（由 `0x08` 写入）的名牌，根本不读这一字节
  （80 条实例该字节恒为 1）。界面照样显示，但标签与 title 写明证据。

**没做**：加分支 / 加新对白（要搬迁整段脚本并重写所有绝对分支目标）、不等长改写、控制码本身。

## 6.12 第八轮（2026-10-22 夜）：战斗地图 —— 直接看见地图，在地图上布置

> 用户反馈：**「将战斗部分做成直接可见战斗地图、并在战斗地图上布置编辑的形式。
> 先用独立子代理完成设计编辑流的设计然后落实」**
>
> 做法：**先派一个独立子代理只做设计**（`notes/specs/battle-map-editor.md`，693 行 12 节），
> 主代理定稿；**再派一个独立子代理只做实现**
> （`notes/battle-map-view-implementation-20261022.md`）。两次都不让同一个上下文既设计又实现。

### 6.12.1 先把「地图长什么样」测出来

设计之前先测像素事实（`tools/probe_battle_map.py`、`tools/probe_battle_map_tiles.py`，
结论落在 `notes/evidence/battle-map-render-facts-20261022.md`）：

| 事实 | 值 |
|---|---|
| 1 格 = | **32 × 16 像素** |
| 地形 | 每格 1 个 u16 |
| 图层 | 每格 2 个 u16（layer0 / layer1） |
| 坐标单位 | **格**，不是像素 |
| 关卡数 | 46 张（1..46） |

46 张图的格宽格高与 `map_table` 的 `raw_width >> 2` / `raw_height >> 1`
**逐张相等**；`px_w === cell_w × 32`、`px_h === cell_h × 16`。

**踩过的坑**：图层是「格行 × (格列 × 2)」的矩阵，所以行下标要用**格行**（`py >> 4`），
不是像素行 —— 写成像素行会把整张图错位。第一版就是这么错的，
靠「照第三方 `features.js` 另写一份独立实现对照」才发现。

### 6.12.2 素材方案：拆成独立二进制，不塞进内容包

内容包已经 300 KB+，再塞 46 张地图的像素会变成大文件，而且**内容包是 JSON** ——
像素塞进去既慢又没法压缩。

所以拆成两半：

- `rom-editor/content/maps/maps.bin.gz`（**174,584 字节**）= 像素本体，按需拉取；
- 内容包顶层 `map_assets` 段 = 46 张图的元数据（`cell_w` / `cell_h` / `px_w` / `px_h` /
  `tile_count` / `metatile_count` / `banks` / `has_layer1` / `blocks` 绝对偏移）。

**保住「不载入 ROM 也能编辑」** —— 素材缺失时地图视图照常打开：画布画格线底图、
顶部挂「未载入地图素材」提示条与「重新载入素材」按钮，**编辑功能一条不少**
（战场物件仍是 16 行、角色出生点仍是 12 行）。

导出器 `tools/export_content_pack.py::build_map_assets` 自带 8 条自检，`--check` 不写文件只比对。

### 6.12.3 只改「布置」，不改地形和图块

| 能改 | 不能改 |
|---|---|
| 战场物件 16 槽（`type` / `target` / `x` / `y`） | 地形 / 通行值 |
| 角色出生点 12 槽（`character_id` / `unit_flags` / `x` / `y` / `facing` / `level`） | 图块 / 调色板 / 图层 / 组合图块 |
| `map_table.background_id`（u8） | 地图尺寸 / 扩图 |

理由有两条，一条是工程、一条是事实：

- **工程**：图块、图层、调色板、组合图块都是 **LZ77 压缩载荷**，改了要重压缩 +
  改指针 + 找空闲区，是一整套搬迁工程。
- **事实**：战斗加载器 `0x08068FF0` **根本不读**地形块的 `+0x18`（通行值）——
  改它对游戏**没有任何效果**。不做「改了没效果」的功能。

### 6.12.4 写回与验收

写回只走 `pack.setValue()`，**没有新开通路**。

**整份 ROM 逐字节比对**（`buildRom` 的输出 vs `rom/base.gba`）：

- 改物件第 1 槽的 `x` → 整份 ROM **只有 1 个字节**不同（`0x58954A` = 7），
  同槽的 `type` / `target` / `y` 三个字节与原版逐字节相同；
- 改 `map_table[40].background_id` → 整份 ROM **只有 1 个字节**不同（`0x53DE2C` = 3），
  该记录其余 31 字节不变。

验收脚本 `rom-editor/tools/verify_battle_map.mjs` 跑**规格 §8 的 V1–V12**
（最强两条是 V5 / V12：逐字节比对整份 ROM）。
脚本自带最小 DOM 桩，并把 `fetch` 桩住端上**真实的** `content/maps/maps.bin.gz` ——
所以 sha256 校验、gzip 解压、素材解码这一整条路都在跑，不是假的。

渲染正确性另有两条独立证据：

1. 素材包（`maps.bin.gz`）与「从 ROM 现解」的结果 **46/46 逐字节相同**
   ⇒ 导出器与渲染器没有各说各话；
2. 渲染抽样（关卡 1 / 7 / 40 / 46，步长 3 像素，共 50,514 个取样点）与一份
   **独立实现**（照第三方 `features.js` 的算法重写，不共用 `maprender.js` 的代码）
   **0 处不同**。

### 6.12.5 顺手查出的两个事实

- **剧情底图不是战场地图**：它是指向底图表 `0x59903C` 的 id，是剧情画面**上半屏**那张
  240×80 的图 ⇒ 单列小面板，不叠在战场地图上。
- **底图可用的 id 是 1–7、9–13**（从内容包推出来的，不写死）：判据是「三个指针都非零」
  且「第 4 个 u32 是色深标志（0 或 1）」；14..35 那一批的同一个位置是指针，
  是另一种 32 字节调色板形态。**8bpp 的底图（9..13）预览不了**
  （调色板只有 192 色，索引会越界），界面显示占位与说明。

### 6.12.6 明确没做

不改地形 / 通行值 / 图块 / 调色板 / 图层 / 组合图块；不导入外部图片当地块；
不扩图 / 改地图尺寸；地图视图里不编辑战斗目标（条件参数里没有坐标），
只给一个指向关卡视图的链接；不在地图上画地形笔刷 / 复制底图图案；
**换角色不自动拷角色模板**（那要改槽内 168 字节未解数据）—— 改成确认弹窗 + 说明；
**一次拖动 = 两条撤销记录**（x 与 y 各一条）—— 状态行里写明「Ctrl+Z 撤销」。

## 6.13 第九轮（2026-10-22 夜）：一个域一个主界面，右边用页签收纳其它配置

> 用户反馈：**「战斗的编辑要将所有同一战斗的关联内容串联起来，以战斗地图的编辑为主界面，
> 右侧战场布置面板中用其他页签分类提供其他战斗相关配置的编辑，
> 例如胜利失败条件、相关剧情触发等等。其他模块也一样，全部检查一遍」**
>
> 规格：`notes/specs/tabbed-side-panels.md`（本轮的统一口径）。

### 6.13.1 统一的模式

```
┌──────────────────────────────┬───────────────────────┐
│  主界面（能看见东西的那个）    │  右侧：页签            │
│  地图 / 角色卡 / 任务 / 场景   │  [页签1][页签2][页签3] │
│                              │  ─────────────────    │
│                              │  当前页签的内容         │
└──────────────────────────────┴───────────────────────┘
```

这一轮把「一个东西不拆成几张表」（第七轮）再往前推了一步：
第七轮把**几张表合成一个主对象**（一行、一个统一视图），
第九轮把**一个主对象的各个侧面**按类收进页签 ——
这样「同一件事」在界面上是**一件事**：左边是它本身，右边是它的各个面。

### 6.13.2 通用机制：`rom-editor/js/tabs.js`

`TabPanel` 一次写好，各域共用。四条约定：

| 约定 | 为什么 |
|---|---|
| **懒渲染**：只有当前页签会构建 | 右侧面板里有几个几十行的表，一次性全建出来既慢又没必要 |
| **记住当前页签**（localStorage，按域分开） | 改完「胜负条件」切到「剧情触发」再回来，还停在原处 |
| **角标**：「这一类改了几处」 | 不用逐个点开找；按**字节**判定（改过又改回去不算改） |
| **订阅内容包变更** | `app.js` 的 `onChange()` 只标脏**不重绘** —— 靠它刷新角标不行，所以给内容包加了一条变更通知（`pack.onChange(fn)`），写完就通知 |

**踩过的坑**：`clear(host)` 会把页签面板一起清掉。
解法是把页签面板挂在一个**不被 clear 的容器**里（`detailHead` / `detailTabs` 两层），
换记录只 `tabs.refresh()` —— 页签选择与记住的页签都还在。

**另一个坑**：重建页签条（`renderBar()`）会把「当前是哪一页」的高亮弄丢。
`renderBar()` 末尾补 `syncBar()` 解决。

**第三个坑（子代理发现的）**：页签面板订阅了内容包的变更（角标要跟上），
但**从不退订** —— 来回切视图会越攒越多订阅者，
每次写回都在更新一个已经不在页面上的角标。
现在 `TabPanel.dispose()` + `tabs.disposeAllTabs()`，
`app.js::render()` 在清空主区之前把旧面板退订掉。
（通用编辑器还额外注意：**一个编辑器只建一个面板**，换记录时换的是**规格**不是面板。）

### 6.13.3 战斗域：地图升为主界面

**关卡视图整个没了** —— 它的内容全部搬进地图视图的右侧页签：

| 页签 | 装什么 | 原来在哪 |
|---|---|---|
| 战场布置 | 地图尺寸、剧情底图、六个 LZ77 资源指针 | 关卡视图 / 地图视图 |
| 战场物件 | 16 个槽：类别 / 触发目标 / 格坐标 | 两边都有 |
| 角色出生点 | 12 个槽：角色 / 阵营 / 格坐标 / 朝向 / 等级 | 两边都有 |
| **胜负条件** | 回合上限 + 4 胜 + 4 负 + 给玩家看的说明文字 | **只在关卡视图里**（还挂着一个「去关卡视图改」的链接） |
| **剧情触发** | 四个剧本入口 + 本关可改的定宽操作数 | **只在关卡视图里** |

旧深链 `#battle/stage/40/0` **不失效** —— 它现在解析成地图面板
（`routing.js` 里 `module === 'battle'` 的特判），地址统一成 `#battle/map/40/0`。

### 6.14.1 先量出问题有多大

第九轮之后，全包 1,006 个字段的说明里有一批是**证据日志**而不是**解释**。
新写 `tools/audit_field_wording.py` 按「内部词汇」打标：

| 打标 | 字段数 | 例子 |
|---|---:|---|
| **说明里塞了 ROM 地址** | **117** | 「…超了就不让选（0x080713B4 / 0x08071548，tag=1 时只取低字节）」 |
| label 带裸编号 | 10 | 「成长目标1」…「成长目标6」 |
| 偏移当主语 | 8 | 「字节 +0x04：随等级成长的初值」 |
| 交叉引用 | 6 | 「由下面的「成长目标」字段选中」 |
| 说明过长（>160 字） | 4 | |
| 裸公式 | 1 | 「值 = (类别−1)×4+20（0x08078F08 / 0x080953A4）」 |

**去重后只有 31 句不同的说明**（83 个音频表的同一个字段共用一句）。

**关键冗余**：界面上每个字段右边**已经**显示了 `+0x04`（`field-offset`），
说明里再写一遍偏移是纯噪音；地址更是只在笔记里有意义。

### 6.14.2 措辞的三条规则

1. **主语是作者关心的东西**，不是 ROM 的对象（「这个忍术加的第 1 项属性」而不是「字节 +0x04」）。
2. **不交叉引用**（「由下面的 X 字段选中」→ 同一张卡片里直接说清关系）。
3. **不塞地址、不裸公式、≤80 字**；证据（地址、反汇编）留在 `notes/` 里，
   界面上只说「已证明 / 还没证明」。

### 6.14.3 忍术那一组的改法（用户截图那一处）

| | 原来（看不懂） | 现在 |
|---|---|---|
| 六个槽 | 成长目标1…成长目标6 / 「字节 +0x04：随等级成长的初值；由下面的「成长目标」字段选中」 | **属性加成 1…6** / 「这个忍术加的第 1 项属性。角色等级越高、且这一项被「会成长的属性」挑中时，它就按「每级成长量」一起长。」 |
| 选择器 | 成长目标 / 「0/7 = 不成长；1..6 指向上面的成长目标1..6」 | **会成长的属性** / 「挑哪一项会跟着角色等级一起长。选「不成长」就六项都不长。」 |
| 每级成长量 | 「值 = (等级−1) × 本值；实测 87 条记录中 +0x0F 恒为 0，所以本字段是单字节（…）」 | 「角色每升 1 级，会长大的那一项就多这么多。实际加成 =（等级 − 1）× 本值。」 |

**为什么这六项不能直接叫「攻击力 / 防御力」**：
仓库只证明了「六个随等级成长的字节字段 + 成长类型挑一个来长」
（`notes/character-template-format-20261020.md` §7）；
第三方把某条记录的 `+0x04` 叫 `basicAttackPower`，但那是**项目配置**
（`third_party/.../runtime.c` 把第 5 条记录的 +0x04 设成「基础攻击力」），
不是字段语义。所以界面写「属性加成 1..6」，并在卡片末尾**明说**
「这六项分别对应角色的哪项能力，仓库还没证明」——
**说法改了，结论没改**。

**顺带修的一个词**：原来六个槽叫「成长目标」、选择器也叫「成长目标」——
同一个词指两个不同的东西，作者看到「成长目标=4」不知道说的是第 4 个槽还是那一格。
现在两个词分开了：「属性加成 1..6」与「会成长的属性」。

### 6.14.4 版式：页签 → 卡片纵排

```
┌──────────────────────────────────────────┐
│ 战场布置                        已改 0 处 │  ← 卡片头：类别名 + 改动数
│ 这张战场多大、剧情底图是哪一张…            │
└──────────────────────────────────────────┘
┌──────────────────────────────────────────┐
│ 战场物件                        已改 2 处 │
│  槽  类别  内容  X  Y  ↗                │
└──────────────────────────────────────────┘
```

**保留**：分类、角标（按字节判定）、「主界面 + 右侧收纳配置」的结构。
**去掉**：页签条、当前页高亮、记住上次停在哪、懒渲染。
**卡片全都同时在 DOM 里** —— 不藏内容，往下滚就是全部。

通用机制 `rom-editor/js/cards.js` 的 `CardStack`，规格形状与第九轮的
`TabPanel` **完全一样**（`{id, label, hint, badge, render}`），
所以各域的改动只是机械替换。`rom-editor/js/tabs.js` **删除**。

**角标要就地更新，不能整摞重画**：角标从「没有」变成「有几处」时如果重建卡片，
所有输入框都会重建 —— 用户刚改完的那一格就丢了焦点。
所以 `updateBadges()` 只在卡片头里增删那个小标签节点，**不碰卡片体**。
（子代理在转换时踩到了这个：素材域不得不自己加 focus 还原，
角色域则保不住「改完一格不重建内容」这条老断言 ——
现在改成断言「输入框还是原来那个节点」，比原来更强。）

各域的卡片清单见规格 §5（战斗 5 张 / 路线工作台 2 张 / 任务 5 张 /
场景 4 张 / 字库 2 张 / 角色 7 张 / 忍具 3 张 / 奖励 4 张 / 忍术 3 张 /
音频 3 张 / 接线表 3 张 / 内存图 2 张 / 通用编辑器 2 张）。

### 6.14.5 全包彻查的结果

31 句说明全部重写（125 个字段受益），另外把
「×100 存，除以 100 后加到体力上」这一类**没被规则抓到但同样看不懂**的
也一并改了（逐角色成长表的 7 个字段）。

**审计命中数：129 → 0**（`tools/audit_field_wording.py`）。

## 6.15 第十一轮（2026-10-22 夜）：战斗里的「剧情触发列表」（三步走）

> 用户反馈：
> 「战斗编辑的剧情触发需要关联上剧情，让玩家可以不跳转而在战斗编辑界面
> 直接查看剧情触发列表、编辑每个剧情。」
>
> 用户明确要求**三步走**：① 独立子代理做设计 → ② 独立子代理审核 → ③ 实现。
> 产物：设计 `notes/specs/battle-story-triggers-20261022.md`（670 行）·
> 独立证据 `notes/evidence/battle-story-trigger-structure-20261022.md` ·
> 审核 `notes/reviews/battle-story-triggers-review-20261022.md`（294 行）。

### 6.15.1 查清的结构（设计与审核两方各自用字节复核过）

| | 「战场事件逻辑」（logic） | 「战场事件表」（events） |
|---|---|---|
| 是什么 | 一串「条件 → `0x33` 压事件 id」 | 开头一条连续的 `0x32` 事件链 |
| 关键统计 | 压队合计 **407**、条件指令合计 **1013** | 链项合计 **400**、文本指令合计 **1118** |
| 条件指令 | 全部在 logic 侧（events 里 **0** 条） | 全部在 events 侧（logic 里 **0** 条） |

**链是 1 基的**（最吃重的一条，两方各自复核过字节）：
`0x08097CF8: movs r4,#0`（链游标从 0 起）→ `0x08097D1A: subs r0,#1`（字节 `01 38`）→
`0x08097D1C: cmp r0,r4`（字节 `a0 42`）⇒ **压入 V 选中链上第 V 段**。

**数量对账**：触发块 **407** = 能选到段的 **400** + 选不上的 **7**
（场景 32..38 各多压一个 `0`；`0−1 = 0xFF` 与游标 0/1/2 都不等 ⇒ 静态上选不中）。

**`0x34` 的 @+2（b）比的是回合计数**：`0x0808A198` 读的字面量在 `0x0808A1A0`
= `0x0202680C`，而 `0x0202680C` = 回合计数是仓库**已定案**的
（`notes/battle-tables.md` §「2026-10-21 追加：`0x0202680C` **就是回合计数**」）。

**剧情按场景索引，跟战斗变体无关** —— 同一关的三个变体共用同一份剧情。

### 6.15.2 审核查出的三处硬缺陷（设计稿有、实现里都改了）

1. **条件指令的 u32 目标语义被写反了**。handler 的形状是
   「判定结果 == 1 → 跳到 u32 目标；落空 → 继续下一条指令」，
   设计稿却写成「不满足时跳到」⇒ 界面上给作者看的那句话会反。
   而且**极性逐条不同**：`0x34`/`0x36`/`0x38`/`0x39` 是「成立才跳」，
   **`0x35` 相反**（`a ≡ 0` ⇒ 它的「命中」= 复合条件不成立）。
2. **写回通路会缺 `before_hex`**。`pack.setScriptOperand` 拿 `operand.before_hex`
   当补丁的「改前字节」；`storyvm.editableOperands` 产出的对象**没有**它
   ⇒ 补丁 `before_hex=''` 而 `after_hex` 非空 ⇒ 构建时「原字节必须匹配」的校验过不了。
3. **验收 V8 与设计决定 D7 自相矛盾**：V8 要求「无 ROM 时整张卡零输入框」，
   但 before/after 的操作数表在无 ROM 时照常渲染（那些是 `<input>`）⇒ 按字面写必红。

另查出**三类设计稿没写、但必须出现在界面上**的情形：
**33 个无条件触发块**（场景 32..38 每关 4 个 + 场景 7 的 4 个 + 场景 8 的 1 个）、
**19 条组内跳转**、**8 条「目标就是某条 `0x33`」**。

### 6.15.3 顺带订正的两处

- `0x0202680E`：设计稿说「仓库只有一处提到」**不成立**（至少 4 处）；
  且它把**地址末字节 0x0E 当成了观测值**（仓库自己的运行时 dump 是 `0x01`，
  另一处写「0/1 交替」）⇒ 据此得出的「整套触发机制是死的」**不成立**
  （`0/1` 与 `c ∈ {0,1}` 恰好相容）。
- `0x13` 的标签：十六进制 `0x13` 是**双段文本**，**调用子脚本是 `0x0D`**
  （`storyvm.js` 的 `OPCODE_NAMES` 用十进制键，容易看串）。

### 6.16 真浏览器目视复核（第十一轮补做）：查出两个只有像素能查出来的布局 bug

> 第十一轮的实现子代理**自己承认**「载入真实 ROM 后的浏览器视觉复核：没有做」——
> 只做了无头 DOM 桩。这一节记的是把这一步补上的**方法与结果**。
> 细节见 `notes/battle-story-triggers-implementation-20261022.md` §7。

**为什么必须补**：无头门禁断得了文本与结构，断不了**像素**。
第十一轮的实现里有两处 CSS 问题，无头门禁 74 条断言一条都没报，
因为它们**只在渲染时才存在**。

**方法**（三步）：

1. **查清环境限制**：这台机器的内置 FilePanel 浏览器**单个文档只能下载约 1 MB**
   （`content/base-rom/rom-loader.html` 的注释里量过），ROM 压缩后 2.7 MB
   ⇒ 编辑器自己的「载入内置 ROM」在这里必然失败。**这是既有问题，与本轮无关。**
2. **只取要用的字节**：触发列表只需要某一场那两个剧本的字节 ⇒
   新增 `tools/probe_battle_story_qa.mjs`，抽出该场用得上的 ROM 字节，
   并**自校验**「稀疏 ROM 与完整 ROM 的触发模型逐项相等」。
   实测第 40 场只要 **440 字节**。再用 `rom-editor/tools/qa-trigger-view.html`
   在真浏览器里用仓库真正的模块与样式表渲染那张卡片。
3. **绕开截图竞态**：内置浏览器里 **DOM 是新的、布局树是旧的**
   （`query kind=editable` 返回 0 个元素，截图拍到的是「正在取回内容包…」）。
   办法：把真浏览器渲染出来的 DOM **固化成静态 HTML**（内容在首帧里），
   再截图；并在页子里加**几何测量**脚本，把输入框宽度 / 表宽 / 容器宽写成一行文字。

**结果**：查出**两个真 bug**，都已修并钉进门禁。

1. **触发块里的三张表全塌成一条横线** ——
   `styles.css:144` 的 `.table-wrap { flex: 1 1 0; }` 是给**行向** flex 容器
   控制**宽度**用的；`.trigger-body` 是**列向** flex 容器，`flex-basis` 落到**高度**上，
   加上 `.table-wrap` 自带 `overflow: auto`（**自动最小尺寸因此归零**）⇒ 表格被压成 0 高。
   修：`.trigger-body > .table-wrap { flex: 0 0 auto; }`。
2. **条件表最后那列人话说明被顶出容器** —— 全局 `table.grid td` 是 `white-space: nowrap`。
   修：条件表加 `cond-table` 类、最后一列放开换行；
   `common.js::summaryTable` 加**可选**的 `rows.class`（向后兼容，不给就是原来的 `grid`）。
3. 顺带：窄栏（420px）里输入框被挤到十几像素 ⇒ 守住 `min-width`。

**门禁**：`verify_battle_story_triggers.mjs` 新增第 16 组 **7 条**源码级布局断言
（74 → **81 条**）。源码级断不了像素，但能把这两条修复**钉住**不被改回去；
像素级的复核路径留在上面那两个探针里。
