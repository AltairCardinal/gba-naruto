# 理论评估：完全定制化原 ROM 与 Butano 一比一复刻的可达性

日期：2026-10-20。本文件只做评估与记录，不修改严格 100% 证明政策，不晋升任何候选
结论，不改写 canonical / bank / 账本，不提交也不 push。

问题：基于完全的逆向成果，理论上能否实现对原版 GBA ROM 的完全定制化开发，并在
Butano 中完成完美的一比一复刻？

结论先行：两件事都可达，但可达性不由"逆向完成度"决定，而且两者的理论上限不同。
「完全定制化」在**内容层**可行且仓库已有真实构建闭环；在**程序层**等价于重写引擎，
那已经不是定制化。「完美一比一」只有先固定判定域才是可判定命题，且残差能否收敛到 0
取决于是否复刻原版的**帧级时间线与缺陷**，而不只是资源与规则。

---

## 1. 两个问题的性质不同，必须分开回答

| 问题 | 本质 | 可达性 |
| --- | --- | --- |
| 完全定制化原 ROM | 在已知 ROM 地址空间里替换内容 | 内容层可行；程序层不可行（=重写引擎） |
| Butano 完美 1:1 | 在另一个实现里复现原版行为 | 可达，但需固定判定域，且需复刻缺陷 |

把两者合成"等逆向做完了就自然都有"是错的：两者缺的东西不一样。

---

## 2. 「完全定制化」的必要条件分解

一次成功的定制至少需要六步闭环：

| 步 | 内容 | 逆向能提供吗 | 当前状态 |
| --- | --- | --- | --- |
| 1 定位 | 字段 → 唯一 ROM 偏移 | 能 | 32 个历史 bank（22 有效 / 10 已否证，2026-10-11 口径；2026-07-13 审计为 23/9） |
| 2 解码 | 字节 → 语义 + 编码 | 部分能 | 有效 bank 声明覆盖 23/2954 条记录；严格 typed 合同仍为 0 |
| 3 编码 | 新值 → 原版可接受的编码 | **不能** | 定长字段可行；变长文本与压缩资源**不可逆** |
| 4 容量/重定位 | 超槽位 → 重算全部指针 | **不能** | 原 ROM 6 MiB，仅 128 KB 已知空闲区且已被三方分区占用（`notes/free-space.md`） |
| 5 写回安全 | 改写不破坏其他引用 | 部分能 | 需要写者窗口 + 全 ROM 指针出现分母；仓库已有 10 个候选被否证为"不是独立物理 bank"的做法 |
| 6 运行时验证 | 自然运行中生效 | 不能 | 需要 A/B 自然运行路线，不能用中途快照续跑代替 |

**逆向只能保证第 1 步和第 2 步的一部分。** 第 3、4、5、6 步是**工程**：
编码器、重定位器、写回守卫、运行时验收。

### 2.1 编码不可逆是硬约束

GBA 的 LZ77 解压是单向的。即使完全逆出原版压缩格式，重新压缩仍需写一个
"原版解码器兼容"的压缩器（合法 Huffman / 字面量流，且解出相同字节）。
这是新工程，不是逆向产物。

### 2.2 重定位是重写而非定制

扩章、加地图、加单位、扩资源池都要动指针表与分母。逆向能告诉你"现在有哪些
指针"，不能生成"改完后的新地址图"。

### 2.3 已被真实证明的可达子集

- 地图候选：166 个去重内容、217 个物理槽、249 个引用；四个固定批次通过真实构建与
  完整重读，含 96 个原槽容量不足的变异资源迁移，输出 16 MiB ROM，另五类负例拒绝发布。
  证明的是**固定批次 + 空 fixture 父分配账本 + 对齐指针分母**，不是任意地图编辑。
- 内容层 import：`dialogue` / `dialogue_var` / `chapter_script` / `map` /
  `battle_config` 已有 importer 与安全门（0xFF 分区校验、独占上界、`before_hex` 校验、
  失败关闭）。
- 资源替换：角色战斗视觉 2,004/2,004 去重源空间帧静态验证通过；字形从原版截图
  逐格反推坐标后局部重建，**只有 5 格变化、39 格逐字节不变**。

## 3. 「完美 1:1」的前置：先固定判定域

"完美"在固定下列四要素之前**不是可判定命题**：

1. 起点状态（哪个 save / 哪次上电）
2. 逐帧输入序列（按键 + 保持帧数）
3. 判定分辨率（全屏逐像素 / 区域 / 语义）
4. 判定分母（哪些帧、哪些区域、哪些步骤）

固定后，1:1 = 有限帧序列的像素/语义比较。仓库已有
`tools/butano/capture_s49_pair.py` + `tools/butano/compare_s49_regions.py`
实现这一层，并在本轮**否定**了全屏同索引配对法（25×25 配对 `matched_steps=0`，
最优/次优仅差 0–147 像素，排名是噪声）→ 必须用区域差分 + 内容相同的基线。

### 3.1 残差不会自动收敛到 0

S49 实测：命令菜单残差从 1142 → 746，20↔20 从 1117 → 297。
本轮把残差归因到**动画相位差**（461 + 285 px），而相位差来源是
**回合横幅阶段消耗按键、把 `scene_frame` 推后**。

含义：像素级 1:1 要求 Butano 侧**逐 tick 复刻原版状态机**（counter 生命周期、
callback 节奏、每帧 tick 数）。这是有限状态机，理论上可做，但成本 ≈ 重写引擎，
且收益只在"画面一致"，不产生新玩法。

### 3.2 完美复刻要求逆向出**缺陷**而不是修正它

实证：character 26 / slot 2 / frame 2 的 `0xFBFF` 在原版 renderer 里按 signed u16
比较、**越过帧边界继续按 20 字节解释**；只有把 `0x0825A8E5` 从 `FB` 改成 `FF` 才会
在 `FFFF` 停止并产生唯一合法 OBJ。要 1:1，Butano 侧必须**故意实现同一缺陷**。

同类风险：原版 vs 重制出现"原版下方有水渠"的观察，实为移动范围网格的染色格
（可达=青、消耗=橙），地图与镜头实测**完全一致**（镜头偏移均 (240,24)，
底图模板匹配 89–93%）。差异的原因不等于差异的现象。

### 3.3 不可逆损失的边界

- 原 ROM 在手时，资源层基本可逆（字形、图块、调色板都能从 ROM 取回）；
  已知的一例硬损失是**8 个字形源截图从未进入 Git**，导致 56/100 字符不可重建
  （红门禁已钉死）——这是"逆向前就丢了"，不是"逆向没做到"。
- 真正不可逆的是 ROM 从不编码的东西：作者意图、废弃字段、未使用预留位。

### 3.4 音频 1:1 的额外要求

原版用 Sappy（GBA FIFO/DMA 混音）：硬件寄存器
`0x04000060 / 0x080 / 0x084 / 0x0A0 / 0x0A4`，`sound_id_dispatch = 0x0809AAC0`，
`sequel/content/sappy-engine/bank.json` 已绑定。Butano 侧是**重实现**的
`audio-runtime-bgm` / `audio-runtime-s3m`。要做到听觉 1:1，必须复现**混音器**
（定点舍入、每帧取样数、FIFO 下溢行为），只复现 PCM 数据不够。

## 4. 「完全逆向成果」这个前提的理论限制

ROM 是程序 P 的编码。逆向最多恢复 P 在给定输入下的行为；ROM 不含注释、不含类型、
不含意图，未使用的位仍是有效字节。因此"完全"只能是**操作性定义**。

本仓库采用的操作性定义：证据闭包 + 独立 verifier + 反例 + 失败关闭。在该定义下：

| 维度 | 核实结果 | 出处 |
| --- | --- | --- |
| ROM 字节分类（提交态） | 6,203,707 / 6,291,456 B = 98.605267%，未知 87,749 B | `notes/sequel-readiness-assessment-20261011.md` |
| 候选态 | 6,203,825 B = 98.607142%，未知 87,631 B、1,763 段 | `notes/remaining-reverse-plan-20260930-v2.md` |
| 未知段结构 | ≥1024 B 的 17 段占 42,880 B（48.93%）；1,349 个 <16 B 小洞仅占 6.24% | 同上 |
| formal 报告 | `complete=false`、175 blockers、32 bank 中 10 complete、107/107 合同通过 | `notes/remaining-reverse-plan-20260930.md` |
| 运行记录覆盖 | 23 / 2,954 条记录 | readiness assessment |

**字节覆盖率不是可定制度。** 可写回字段必须同时满足：唯一定位 + 语义闭合 +
存在写入者 + 写回安全。98.6% 的字节被分类，与"能改多少内容"不是同一个数。

**长度、零比例、邻接与熵只能给未知字节排序，不能证明它是代码、填充、空闲空间或
安全写入区**；覆盖率不能换算成工期比例。

---

## 5. 关键判断：当前 1:1 的瓶颈已经不是逆向缺口

S49 最近三轮残差逐条查下来，全部是**实现侧**问题，没有一条需要新的逆向成果：

- `battle_ai.h` 纯移动分支的 `candidate.facing` 取了"从终点看向焦点"，
  应为"面朝走的方向"（4.3.81）——真正的 AI 逻辑 bug。
- 流程顺序错：原版是「横幅 → 移动选格 → 战场 → 命令菜单」，重制是反的；
  且 `open_command_before_move = false` 分支会**整个跳过命令菜单**（4.3.82）。
- 横幅资产已做好但未接线；`scene_frame` 相位差随之而来。
- 字形/调色板问题（`0x5A7FCC` 混合表整段排除、8 个字形源截图未进 Git）。

仓库自己的评估也写着：把"未知字节归零"作为续作开发的统一前置条件，
"已经不能很好地反映下一步投入的价值"（`notes/sequel-readiness-assessment-20261011.md`）。

成果呈现侧同样未闭合：逆向成果族主干 85 个，展示页收录 9/85 = 10.6%，
补齐叶子导出器后 10.6% → 21.2%（`AGENTS.md` 任务模式登记表条目）。

## 6. 建议的可达目标与路线

### 6.1 把「完美 1:1」重定义为可验收的形式

> 在固定输入契约（ROM / 快照 / mGBA / 脚本 / SRAM 全部入 `inputs.json`）下，
> 指定步骤序列的**指定区域**逐帧差分为 0，且区域是显式输入而非整屏。

理由：整屏同索引配对已被实测否证；区域差分 + 内容相同基线是当前唯一可用分母。

### 6.2 双轨并行，而不是二选一

| 轨道 | 目标 | 需要的不是更多逆向，而是 |
| --- | --- | --- |
| 原 ROM 侧 | 内容级定制（对白/剧情/数值/地图/资源） | 编码器 + 重定位器 + 写回守卫 + 自然运行 A/B 验收 |
| Butano 侧 | 原创章节纵切（复用原版资源链） | 章节 DSL + 结算/存档/跨关生命周期 + 音画验收 |

### 6.3 明确不要做的事

- 不要为追求"完美 1:1"去重写原版引擎（成本 ≈ 全量逆向，收益只有画面一致）。
- 不要把 98.6% 字节覆盖率当成"可定制 98.6%"。
- 不要用中途快照续跑当作自然运行验收（历史证据可能全部来自续跑路径）。
- 不要把"未收录"当作"工作未完成"，也不要把条目总数当覆盖率主口径
  （条目单位不可比时必须同时给出含/剔除两个值）。

## 7. 一句话回答

**理论上可以，但两件事都不是"逆向做完了就自动得到"：**

- **完全定制化原 ROM**：内容层可行且已部分达成（地图批次真实构建通过、import 管线
  与安全门就位、128 KB 空闲区有分区账本）；但真正卡住它的是**写回工程**——编码器、
  重定位器、指针安全与自然运行验收，这些逆向给不了。程序级任意定制不可行，
  它等价于重写引擎。
- **Butano 完美 1:1**：可达，但前提是把判定域固定（起点/输入/分辨率/分母），
  并且要复刻原版的**帧级时间线和缺陷**（`0xFBFF` 越界解释、朝向规则、菜单顺序）。
  残差不靠更多逆向收敛，靠把流程、时间线和实现逐条钉平。
- **当前 1:1 的主瓶颈已经是实现侧而不是逆向侧**，所以下一步的投入方向应该是
  接横幅、修 `open_command_before_move = false` 分支、逐帧对齐 `scene_frame`，
  以及在原 ROM 侧把内容级定制做实，而不是把全 ROM 归零当作前置。

## 8. 归因：为什么 1:1 迟迟不来（2026-10-20 追加）

### 8.1 数量级反差是答案本身

| 指标 | 值 |
| --- | --- |
| 逆向：ROM 字节分类（提交态） | 98.605267%（未知 87,749 B / 1.4%） |
| 复刻：S49 全屏逐帧 1:1 | **0 / 384 帧**（2026-10-13 v5 收束，全部有差异） |

两者差约两个数量级。**1:1 的瓶颈不在逆向覆盖率。**

### 8.2 六个具体成因

1. **逆向闭合的是"数据层"，1:1 卡在"行为层"。**
   角色战斗视觉 2,004/2,004 源空间帧静态验证通过，但明确**不签发**最终屏幕坐标、
   相机、priority、运行时槽选择、blend、palette transform
   （`notes/character-battle-visuals-export-20260729.md:23-24`）。这 6 项每一项都直接
   决定屏幕结果。静态帧全对 ≠ 画面全对。

2. **1:1 是关于"时间"的，逆向的单位是"表"。**
   最接近的成果是 79 项战斗视觉运行时时间线（75 项可播放 × 106 linked tick，标准时长
   `84 + 6×binding_count` 帧），但只覆盖**标准 consumer 路径**。S49 残差 461+285 px 的
   根因是 `scene_frame` 相位；readiness assessment 明列未闭合项含"动画 flags、slot、
   **callback、counter 生命周期**"。要 1:1，需要的是**每个场景相位自己的 tick 节奏**，
   而不是任何一张表里的字段。

3. **Butano 侧是重实现，重写代码的分支数多于原版。**
   `battle_scene_phase` 有 24 个相位；手写 C++ 42,428 行 + generated 49,911 行 +
   1,814 张图。关键代价不是行数，而是**重写侧引入了原版没有的抽象与开关**
   （`has_focus_position`、`open_command_before_move`），每个抽象都造出原版不存在的一条
   路径。实证：改 `open_command_before_move = false` → 命令菜单被整个跳过（1142 → 5052）；
   改 AI 先后 → 1567（更差）；最终证明这两个开关**比它们的反面更接近原版**。
   ⇒ 要 1:1 必须**删抽象、逐条镜像原版**，而不是加开关试。
   ⇒ 这一整类差异**根本不来自逆向缺口**：原版没有 `has_focus_position` 这个决策点，
   "面朝焦点"是重写者的解读而非原版结论。

4. **判定分母本身在动，历史结论要重做。**
   全屏同索引配对被实测否证（25×25 配对 `matched_steps=0`，最优/次优只差 0–147 px）；
   原版 25 步 vs 重制 33 步（**同序号不等于同语义**）；底图不同时全屏差分既不能当验收
   闸门也不能选基线。判定方法从"整屏"改为"区域"后，全部历史结论作废重测。
   这是**验收面在动**，不是复刻变慢。

5. **完美复刻要求逆向出缺陷，而缺陷不在"完成"清单里。**
   `0xFBFF` 越过帧边界继续按 20 字节解释；逆向的完成标准是"解释正常语义"，缺陷语义是
   额外的发现成本。且现象 ≠ 原因：4.3.79 的"坐标系不可比"被 4.3.80 推翻。

6. **成本结构是乘性的。**
   逆向是 O(ROM 字节)，剩 1.4%；1:1 是 O(关卡 × 相位 × tick × 实体 × UI 元素)。
   原版 47 个地图、87 个 battle-config 条目、每关 24 个战斗相位。S49 一关就吃掉大部分
   工作量；**已验证的 S49 不会自动惠及 S50**，因为每关有自己的相位组合与 tick 节奏。

### 8.3 验收基础设施本身的硬约束

- 需 patched mGBA 0.10.5 + Qt script 回移补丁；本机 Homebrew mGBA 0.10.5 不支持
  `--script`，不能顶替。
- GBA 存档与 ROM 强绑定 → 重新构建后必须**从上电重录**，复用旧 `.ss9` 会得到黑屏加彩色
  噪块，极易误判成"构建炸了"。
- 磁盘余量 96–98%；重活默认 idle timeout 60 s 会静默杀掉正式 proof（exit 124）。

### 8.4 重要更正：相位分派其实已经**穷尽**闭合（2026-10-20 查证）

§8.2.2 的表述容易让人以为"相位本身不可知"。准确说法是：**相位"有哪些"已经完全可知，
且是穷尽的；缺的是语义命名、转移条件与跨模块闭合。**

原版战斗控制器是**16-bit 状态分派器**，已正式闭合：

| 项 | 值 |
| --- | --- |
| 产物 | 逆向树 `artifacts/rom-battle-controller-cfg-v1/` |
| 分派器区间 | ROM offset `0x0733A0..0x0735CA`（Thumb） |
| **输入分母** | **65,536**（全部 u16 状态） |
| **非默认状态** | **38**（默认 65,498 → `0x07504E`） |
| 映射 canonical SHA-256 | `ce5e8ea24e274c4456482611609ee90144d31e064fccf0d85bf8f4643f44ac15` |
| 闭合规模 | 38 roots、2,756 指令、739 block、6,172 reachable bytes |
| 残余 frontier | 5（decode_failure 1、indirect_pc_target 2、unsupported_armv4t 2） |
| 范围外 opaque edge | 227（跨模块调用未展开）+ 9（baseline opaque） |
| controller 区间 | `[0x0732B4, 0x07509C)` |
| 完整 38 项映射 | 逐项写在 `tests/test_export_rom_battle_controller_cfg.py` |

**历史教训**：旧的 `notes/battle-controller-states-20260723.json` 声称 36 个状态且结构闭合，
已被**独立逐状态解释推翻**——旧 `0x1020` / `0x3310` / `0x9200` 实际都走默认目标 `0x07504E`。
旧 controller 端点 `0x075082` 还截断在一条可达 4-byte BL 中间
（`0x075080` 是 `BL 0x06EAD8`）。⇒ **"逐状态跑真实分派器"是唯一可靠的穷尽手段，
手抄常量不可信。**

### 8.5 那么真正的落差在哪 —— 四条

1. **原版 38 态 vs Butano 24 phase，两套体系从未对齐。**
   原版是 16-bit 状态码（`0x0000`/`0x1210`/`0x4110`…），穷尽枚举。
   Butano 侧 `battle_scene_phase`（`battle_scene_controller.h:24-50`）是**重写者自设计的
   24 个枚举**。在 `butano-sequel/game/` 内检索原版 38 态常量：**零命中**。
   没有任何产物建立 38↔24 的对应。
   ⇒ 后果：D2-a「原版从入口相位进入五命令菜单的输入是什么」之所以成为阻塞点，是因为
   重制侧在**猜**原版相位语义，而原版相位表就在产物里躺着，只是没有被翻译成 Butano 侧常量。

2. **分派表给的是"状态 → handler 地址"，不是"状态 → 语义"。**
   artifact 里有 state→address→CFG blocks/指令，**没有** `0x1210 = 移动选格` 这类命名。
   命名要求读通每个 handler、知道它读哪些 RAM 字段 → 回到字段语义分母
   （有效 bank 覆盖 23/2,954 条记录，严格 typed 合同 0）。
   ⇒ "有哪些"已穷尽；"是什么"仍待语义闭合。两者不能互相替代。

3. **原版相位是嵌套的，不是一个平面。**
   已闭合的 battle controller 区间是 `[0x0732B4,0x07509C)`；
   而 `notes/s49-fidelity-handover-20261019.md` §4.3.30 用逐帧 PC 跟踪 + 断点定位的
   "相位切换例程" `0x080961F6` → ROM offset **614,902**，**远在 controller 区间之外**
   （471,732..479,388）。§4.3.31 已把它更正为"循环回边"。
   ⇒ 原版至少有 battle controller 38 态（场景级）+ `0x0809xxxx` 一层（演出/消息/事件级）
   + 各自独立 dispatcher（`rom-boot-state-dispatcher-cfg-v1`、
   `rom-story-state-callback-cfg-v1`、`rom-event-handler-cfg-v1` 等）。1:1 要对齐的是
   **整条嵌套链**，每层有自己的状态集。

4. **状态转移条件是运行时的，静态分派表给不了。**
   分派表是"状态 → handler"的**静态函数**；"按 A 后从 `0x1110` 转到 `0x1210` 还是留在原地"
   取决于运行时 RAM 状态（当前单位、是否已移动、能否行动）。
   ⇒ 需要"给定 RAM 状态 → 下一状态"的转移表，这是**混合**问题：静态给候选转移，
   运行时给实际转移。仓库现有做法（逐帧 PC 跟踪 + 断点 + 逐步更正）正处在这个混合区，
   代价可见：§4.3.30 的"跨模块相位切换例程"被 §4.3.31 推翻；§4.3.79 的"坐标系不可比"
   被 §4.3.80 推翻。

### 8.6 由本次查证得到的三条可执行下一步

1. **建 38 态 ↔ Butano phase 的映射表**：逐态读通 handler 并命名
   （`0x1210 → 移动选格`…），把原版状态码直接做成 Butano 侧常量，**替换**自造枚举。
2. **建原版状态转移表**：用分派表 + PC 跟踪，把"输入 → 下一状态（及其守卫条件）"落成
   可验收的表，用它替换 `has_focus_position` / `open_command_before_move` 这类自造开关。
3. **每相位帧数节奏单独做运行时收据**——这是唯一确实必须运行时的部分。

⇒ 由此**修正 §8 的整体框架**：1:1 迟滞的主因不是"逆向不够"，而是**逆向成果没有接到
Butano 侧**——一边是 38 态穷尽分派表，一边是 24 个自造 phase，中间没有映射与对齐层。
这三步的成本远低于继续加逆向。

### 8.7 投向前瞻

| 侧 | 该补什么 | 不该做什么 |
| --- | --- | --- |
| 逆向侧 | **上下文条件（guard）**：某条规则在何种上下文生效（纯移动分支不参与 focus）、**缺陷语义**、**每相位 tick 节奏表**、**38 态的语义命名与状态转移表** | 再加一批"字段是什么"却对帧级无用的表 |
