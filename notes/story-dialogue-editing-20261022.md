## 1. 目标

`notes/external-konoha-workshop-gap-20261020.md` 的 **P0-1** 说第三方编辑器
「木叶工房」有带回溯的字节码图遍历器（`E.graph`）+ `scanText` / `decode`，
所以能「按场景浏览对白 / 改对白 / 加分支」。

本仓库早已有遍历器（`js/storyvm.js::scanScript`）和查看器
（`js/modules/scriptview.js`），但**文本那一列是只读的**。本轮补上
「对白正文可就地改写」。

## 2. 走过的路与结论

### 2.1 文本是内联的，改写只能等长（硬约束）

> ⚠️ **第十七轮更新：这一节的结论已被「搬迁 + 重基」取代**（见文首）。
> 下面记的是**当时的考证过程**，结构事实（正文内联、分支目标是绝对地址）**仍然成立**。

剧情脚本的正文**内联在字节流里**（不是指针）；而脚本里的分支目标是
**绝对 ROM 地址**（`storyvm.js::BRANCH` / `SINGLE_TARGET`）。
所以改长改短都会让后面的指令移位、分支全部失效。

⇒ **只允许等长改写**：新文本编码后的字节数必须与原来完全一样。
这不是权宜之计，是数据布局决定的硬约束，界面上必须写清楚。

实测规模：四张根表（before / after / logic / events）共 **7,488 段正文**，
其中 op 0x01 = 7,217 条、op 0x05 = 51 条、op 0x20 = 80 条、op 0x13 = 28 条
（0x13 里 28 条里有两段正文的那些）。全部 7,488 段都通过
「token 流往返逐字节相等」的自检（0 段被拦下）。

### 2.2 正文落在指令的哪几个字节

新增 `storyvm.js::instructionTextRuns(rom, instruction)`（只新增导出，
既有函数一行没动）：

| op | 语义 | 正文起点 | 备注 |
|---|---|---|---|
| 0x01 | 显示文本 | `+1` | |
| 0x05 | 菜单选项文字 | `+2` | |
| 0x20 | 带说话人的对白 | `+2` | 第 2 字节是本指令自带的字段 |
| 0x13 | 双段文本 | `+4` | `+2` 非零则还有第二段 |

**0x13 的第二段起点是「第一段 NUL 之后再跳 1 字节」**（`notes/story-vm-opcodes-20261020.md`
§1.6 的第 6 条误判记录）。实测一对：正文起点 `44549` 与 `44577`
（中间隔着 1 个不属于任何一段的字节）。这一点与 `instructionLength`
走的路完全一致，所以两处不会打架。

### 2.3 控制码 0x01 / 0x02 必须原位保留

`01 xx`（2 字节）与 `02 xx yy`（3 字节）带着换行 / 分页的排版含义。
正文按 **token 流**处理（`js/textcodec.js` 是 `tools/text_codec.py` 的 JS 版），
写回时用 `mergeTokens` 把控制码放回原位。

⚠️ `js/textcodec.js::FontCodec.decode` **不能**用来显示这类正文：它把控制码
当成单字节字符，于是遇到 `01 00`（控制码的载荷正好是结束符）就**提前截断**。
本轮因此在 `js/scripttext.js` 里自己写了一个 `scanRun()`，分段规则与
`storyvm.js::textEnd` 逐条对齐（0x00 结束 / 0x01 占 2 / 0x02 占 3 /
0x80..0x9F 占 2），扫出来的 token 数与指令长度永远对得上。

实测：7,488 段正文里有 **51 段带控制码**（102 个 0x01、0 个 0x02），
全部在等长改写后**位置与内容原位不变**（`01 02|01 00` → `01 02|01 00`）。

### 2.4 编码按「码位」走，不按「字符 → 码位」反查表

`tools/text_codec.py::encode_tokens`（→ `tools/konoha_font.py::encode_tokens`）
是仓库的**字节精确**参考：码位 10 = 换行、ASCII 32..126 = 单字节、
其余 = 双字节字形码。

⚠️ `pack.font.encodeTokens()`（按字符查 `char_to_code`）**会丢掉 ASCII**：
内容包里的 4,253 个字**一个 ASCII 都没有**（实测 `char_to_code` 的键全是
非 ASCII）。而 `pack.font.missingCharacters()` 会把 ASCII 判成「缺字」——
那是文本表编辑器的既有行为，对**剧情脚本**不适用（脚本正文里确实没有 ASCII，
但作者写 ASCII 时应当能写进去）。

所以 `js/scripttext.js::encodeText()` 走码位：ASCII 直接写成单字节，
其余查字库，查不到就**报出来并拒收**（绝不默默丢掉那个字）。

### 2.5 op 0x20 的第 2 字节**不是**说话人 id（推翻了一个想当然的读法）

`notes/story-vm-opcodes-20261020.md` 把 0x20 记作「显示带说话人的对白」，
很容易顺手把「正文从 +2 起」读成「第 2 字节 = 说话人 id」。**不是。**

反汇编 handler `0x08097A66`（`tools/story_vm_ops.py` 也把它钉成 0x20 的
唯一 handler）：

```
0x08097A66: movs  r0, #0
0x08097A68: bl    #0x80971c0      ; 清对话状态
0x08097A6C: adds  r6, r0, #0
0x08097A6E: ldrb  r0, [r6, #0x13] ; 说话人 id 取自**对话框状态**
0x08097A70: bl    #0x8066d14      ; 显示名牌
0x08097A8C: adds  r1, r7, #2      ; 正文从 +2 起
0x08097A90: bl    #0x806626c      ; 渲染正文
```

handler **根本没有读 `[r7, #1]`**。实测 80 条 0x20 指令的该字节**恒为 1**，
而它前面常常是 0x11（清除头像）—— 若是头像 id 就自相矛盾。

界面上仍然把这一字节显示出来（作者要看到指令的每个字段），但标签写成
「说话人 #N（名字）」并在 title 里写清上述证据，不把它说成游戏里的名牌。

### 2.6 写回走显式补丁

`pack.setBytesAt(offset, beforeHex, afterHex, label)`（主代理刚加的 API，
`js/pack.js` 一行没动）：建/复用补丁、记一次撤销（撤销时把 `after_hex` 恢复）。
构建时按「原字节必须匹配」写回（`js/rom.js::applyPatches`），补丁在结构与
文本写回**之后**才写。

界面显示的字节要**把补丁叠上去**（`currentBytes()`，与 `js/modules/raw.js`
同一套做法），否则改完切走再切回来就变回原文了。

另外加了一道保险：若已有补丁**盖住**这段正文但又不正好等于这段
（`conflictingPatch()`），就拒改并提示先去「原始字节」撤销它 ——
否则写回会覆盖那条补丁，两处改动互相打架。

## 3. 界面怎么表达「等长才能改」

> ⚠️ **第十七轮更新：这一节描述的是旧界面**。
> 现在是：等长 → 绿色「等长，失焦即保存」；变长 / 变短 → **琥珀色**
> 「变长 N 字节：构建时整个剧本会搬到空闲区」（**不再拒收**）。
> 「当场拒绝并回滚」现在只发生在**字库缺字**与**孤儿代码（不属于任何剧本）**这两种情况。
> 下面保留旧写法作考证。

- 面板顶部的说明条：改写规则的来龙去脉（为什么必须等长）。
- 每个输入框下面一行预算：`已用 / 容量 字节`。
  - 超了 → 变红：`等长才能改：多了 N 字节，后面的指令会移位`
  - 少了 → 变红：`等长才能改：少了 N 字节，后面的指令会移位`
  - 相等 → 绿色：`等长，失焦即保存`
- 失焦即保存；长度对不上时**当场拒绝并回滚**（输入框恢复原文），
  toast 写明「等长才能改：现在要 N 字节，比原来的 M 字节多/少 K 个。
  后面的指令会移位，分支目标全部失效 —— 请改成同样长的文字。」
- 文本段旁边有「跳到原始字节」（`ctx.onJump({module:'raw', kind:'raw-offset',
  id:'raw', params:{offset}})` → `#raw/offset/0x…`）。
- 控制码在文本框里看不见（没有字形），另用 `⟦控制码 01 02⟧` 小标标出位置。
- 换行在输入框里显示成 `↵`（ROM 里是 0x0A 码位）。

## 4. 验收

> ⚠️ **第十七轮更新：第 3 条的验收方向反过来了** —— 不等长改写现在
> **被接受**（并在结果里标明 `relocated === true`），不再是「被拒绝」。
> 字库缺字仍然被拒。对应的新断言在
> `rom-editor/tools/verify_script_text.mjs` 第 3 组、
> `rom-editor/tools/verify_variable_text.mjs`（V1–V10，72 条）与
> `rom-editor/tools/verify_script_relocation.mjs`（14 条）。
> 下面保留旧验收项作考证。

`rom-editor/tools/verify_script_text.mjs`（无头，自带 DOM 桩）覆盖：

1. 文本段能被定位（文件偏移 + 字节长度 + 解码后的文本 + 换行显示成 ↵）；
2. 等长改写：`changedPatchCount()` +1、`after_hex` 等于新字节、
   `undo()` 后 `after_hex` 恢复且计数回落；
3. 不等长改写：被拒绝（不产生补丁、不改计数）、理由写明「等长」与
   「后面的指令会移位」；改短同样被拒；字库缺字同样被拒；
4. 改动后的字节**逐字节等于**字库编码出来的新文本（并且构建后
   `buildRom` 写进 ROM 的字节也逐字节相等、结束符仍在原位、
   后面的指令没有被移动）；
5. 界面：输入框、字节预算、变红文案、失焦即保存、拒绝时回滚、
   「跳到原始字节」跳转目标；
6. 控制码原位保留、0x13 的两段正文、0x20 的说话人字段。

## 5. 没做的（边界）

- **加分支 / 加新对白**：那要搬迁整段脚本并重写所有绝对分支目标，
  本轮不做。
  ⇒ **第十七轮更新**：**搬迁本身已经做了**（变长 / 变短时构建时把整个剧本搬到空闲区
  并重基内部地址），但**加分支 / 加新对白**仍然**没做** ——
  那要改的是**控制流**（新增分支目标 / 新增指令），不只是搬字节。
- **不等长改写**：会移位后面的指令、让分支失效，做不了。
  ⇒ **第十七轮更新**：**这一条已经不成立** —— 不等长改写**现在能做了**
  （构建时搬迁整个剧本 + 重基它内部的绝对地址）。
  见文首的「⚠️ 结论已更新（第十七轮）」。
- **控制码本身不可改**：要改控制码请用「原始字节」模块。
  ⇒ **这一条仍然成立**（控制码只能**原位保留**，不能新增 / 删除 / 挪位置）。
- **字库里 8 个「一个字两个码位」的字**：改写整段时会被统一成规范码位
  （与文本表编辑器同一套既有行为）。
