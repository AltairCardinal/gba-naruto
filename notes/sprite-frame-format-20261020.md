# 战斗人物精灵动画帧格式（动作表 0x596CCC）

> 记录时间：2026-10-20
> 工具：`tools/sprite_frames.py`（本仓库新增）
> 状态：布局与字段语义已在本仓库 ROM 上逐项复核；语义猜测项见第 7 节。

---

## 0. 结论摘要

《火影忍者 - 木叶战记》把每个战斗人物（id）的每个动作（action）的动画素材拆成
**四个 ROM 指针**，分别指向四类独立的资源：

| 指针 | 内容 | 编码 |
|---|---|---|
| `frames` | 帧指针表 | `u32[]`，指向帧描述符 |
| `animations` | 动画表 | `u32[]`，指向动画描述符 |
| `gfx` | 图块像素 | **原始 4bpp**，32 字节 / 8×8 图块 |
| `palette` | 调色板 | 16 × `u16` BGR555 = 32 字节 |

帧描述符是一串 **20 字节的"拼块"**，每片描述一个矩形贴图；拼块列表以
`tile == 0xFFFF` 结束。

本次在 `rom/base.gba` 上跑完全量扫描（62 个 id × 9 个 action = 558 个表项）的结果：

- **342 个 (id, action) 有素材**，共 **2674 帧**、**2861 片拼块**；
- **2860 / 2861 片拼块**完全符合格式（尺寸 ∈ {8,16,32,64}、缩放恒为 256/256、
  落在 128×128 模板内、列表有 `0xFFFF` 终止符）；
- **唯一的 1 片异常**来自 ROM 里一处**真实的字节损坏**（id 26 / action 2），
  详见第 5 节；
- 4bpp 假设（32 字节/图块）下 **341 / 342** 个动作的 gfx 字节跨度**正好落在下一个
  资源边界上**；同一检验在 8bpp 假设（64 字节/图块）下 **0 / 342** 通过。

## 2. 内存布局

### 2.1 动作表（action table）

```
地址        = 0x596CCC + id * 144 + action * 16
每项 16 字节 = 4 × u32 ROM 指针 = (frames, animations, gfx, palette)
```

指针都是 `0x08xxxxxx` 形式的 GBA ROM 地址（`BASE = 0x08000000`）。

**id 范围实测：1..62。** id 0 全 0（空槽）；id 63 全 0（表在此结束）；id 64 之后
是另一张表（指针值不再是合法的素材指针）。
第三方实现把范围写死成 `1..60`，**比实测少 2 个 id**。

**action 范围实测：0..8**，但并非每个 id 都有全部 9 个动作：

```
action 0: 62 ids, 帧数 [1, 5, 20, 24, 32, 48]
action 1: 62 ids, 帧数 [3, 5, 6]
action 2: 62 ids, 帧数 [5, 6]
action 3: 62 ids, 帧数 [3, 5, 6, 7, 9]
action 4: 62 ids, 帧数 [3, 4, 5, 6]
action 5:  8 ids, 帧数 [5]
action 6:  8 ids, 帧数 [5, 6]
action 7:  8 ids, 帧数 [5, 6]
action 8:  8 ids, 帧数 [5]
```

558 个表项里 216 个是**全 0 的空槽**（不是损坏）。

验证命令：

```
python tools/sprite_frames.py rom/base.gba --stats
```

### 2.2 帧指针表（frames pointer table）

`frames` 指向一个 `u32[]`，每个元素指向一个帧描述符。

**这张表没有自己的终止符。** 它恰好有 N 个指针，紧接着（偏移 `frames + N*4`）
就是动画描述符区。读表时"遇到第一个不是合法 ROM 指针的字就停"，因此那个字
实际上是被误读成指针的**第一个动画描述符的前 4 字节**。

实测：342 / 342 个动作满足"第一个动画描述符正好起始于 `frames + 帧数*4`"
（工具 `--check` 的 C8 项）。

验证命令：

```
python tools/sprite_frames.py rom/base.gba --check
```

### 2.3 帧描述符（拼块列表）

每个帧描述符是一串 20 字节的拼块，直到某片的 `tile == 0xFFFF` 为止。

### 2.4 拼块字段（20 字节）

| 偏移 | 类型 | 字段 | 实测取值 |
|---|---|---|---|
| +0 | `u16` | `tile` | 图块索引（相对该 action 的 gfx 块） |
| +2 | `u16` | `flags` | bit0 = X 翻转；实测只用 0 和 1 |
| +4 | `s16` | `x` | 拼块左上角 X（相对模板锚点） |
| +6 | `s16` | `y` | 拼块左上角 Y |
| +8 | `u16` | `w` | 宽，实测 ∈ {8,16,32,64} |
| +10 | `u16` | `h` | 高，实测 ∈ {8,16,32,64} |
| +12 | `u16` | 恒为 256 | 2860/2861 片全部 = 256 |
| +14 | `u16` | 恒为 256 | 2860/2861 片全部 = 256 |

实测尺寸分布（2861 片）：

```
      16x32 : 16        32x16 : 6         64x32 : 2
       16x8 : 58        32x32 : 161       64x64 : 547
       32x8 : 4        32x64 : 2046
       8x32 : 20    65520x65480 : 1   <- 损坏条目，见第 5 节
```

实测 `flags` 分布：`flags=0` 2543 片、`flags=1` 318 片。**Y 翻转（bit1）在本 ROM
中一次都没有出现**（`flip_y_parts: 0`），所以 bit1 的语义无法用本 ROM 证实。

### 2.5 gfx 图块数据

- **原始 4bpp**，未经压缩（不是 LZ77）。
- 一个 8×8 图块 = 32 字节。
- 拼块的 `tile` 是**图块索引**，字节偏移 = `tile * 32`。
- 一片拼块（`w × h`）占用的图块数 = `(w/8) * (h/8)`，字节数 = `w*h/2`。
- 因此该 action 的 gfx 块长度 = `max(tile*32 + w*h/2)`。

**判决性验证（4bpp vs 8bpp）**：每个 action 的 gfx 块在 ROM 里是紧挨着下一个
资源的，所以"gfx 块末尾"必须**正好等于**下一个资源的起始地址（该 action 的帧
描述符区 / 帧指针表 / 动画指针表里地址最小且大于 gfx 的那个）。

```
C1  gfx span ends exactly at the next resource (4bpp): 341/342 FAIL [(26, 2)]
C1' same test under the 8bpp hypothesis (64 B/tile): 0/342 PASS
```

4bpp 假设 341/342（唯一失败的是损坏条目），8bpp 假设 0/342。**这就是 4bpp 的判死检验。**

另一个独立佐证：同一 id 的相邻帧，`tile` 索引与拼块尺寸严格对应。
以 id 1 / action 0 为例（20 帧，每帧 1 片）：

```
帧  0..11 : tile = 0, 32, 64, ... 352      拼块 32x64 = 32 图块 = 1024 字节
帧 12,13  : tile = 384 (两帧共用同一段图块，只改 y: -52 / -48)
帧 14,15  : tile = 416 (共用，y: -60 / -64)
帧 16,17  : tile = 448 (共用，拼块 64x64 = 64 图块 = 2048 字节)
帧 18,19  : tile = 512 (共用，x: -52 / -56)
```

于是该 action 的 gfx 块长度 = `max(tile*32 + w*h/2)` = `512*32 + 2048` = **18432 字节**，
起点 `0x13E090` + 0x4800 = **`0x142890`**，而 `0x142890` 正是下一个资源
（帧描述符区）的起点 —— 与 C1 判据完全吻合。

> 注意：并非每帧都用新图块，部分帧是"同一段图块 + 不同偏移"的复用。
> 所以不能用"帧数 × 每帧字节"去推算 gfx 长度，必须用 `max(tile*32 + w*h/2)`。

**tile 索引从 0 连续无空洞**：342 / 342 个动作通过（工具 `--check` 的 C7 项）。

### 2.6 调色板

- `palette` 指向 **16 个 `u16` BGR555 = 32 字节**的原始数据（未压缩）。
- 实测 342 个动作只用到 **40 种不同调色板**（多数 id 的多个动作共用一张）。
- 调色板与 gfx 块不重叠：342 / 342（`--check` 的 C10 项）。

### 2.7 动画表（animations）

`animations` 指向一个 `u32[]`，每个元素指向一个**动画描述符**。
动画描述符是一串 **4 字节条目**，以 `FF FF 00 00` 结束：

| 偏移 | 类型 | 字段 | 实测 |
|---|---|---|---|
| +0 | `u16` | 帧索引 | 实测恒 `< 帧数`（C9，342/342 通过） |
| +2 | `u8` | `b2` | 实测取值 {1, 2, 4, 6, 8, 16} |
| +3 | `u8` | `b3` | 实测**恒为 0**（4246 / 4246） |

实测：1045 个动画描述符，每个描述符 1..16 个条目
（3 条目 281 个、4 条目 537 个、5 条目 125 个、6 条目 78 个 …）。

`b2` **看起来**是每帧的持续时间/权重（值都是 2 的幂附近），但本 ROM 无法证实
它的确切语义 —— 见第 7 节。

## 3. 像素取值公式

在 4bpp 图块内取像素 `(px, py)`（拼块局部坐标）：

```
若 flags & 1 : px = w - 1 - px      # X 翻转
若 flags & 2 : py = h - 1 - py      # Y 翻转
src  = gfx + tile*32
     + ((py >> 3) * (w >> 3) + (px >> 3)) * 32    # 图块内行主序
     + (py & 7) * 4 + ((px & 7) >> 1)             # 图块内字节
idx  = (rom[src] >> ((px & 1) * 4)) & 0xF         # 高/低半字节
```

拼块在 128×128 模板格内的位置：`(64 + x, 96 + y)` 为左上角。

**渲染验证**：用上面的公式 + 调色板把 id 1 / action 0 的 20 帧渲染成
5×4 的 128×128 拼版，得到**清晰可辨的人形角色精灵**（刺猬状头发 + 蓝红服装），
20 帧姿态连续、无错位。这说明 20 字节拼块布局、`tile*32` 寻址、4bpp 半字节顺序、
BGR555 调色板以及 (64, 96) 锚点是**同时正确**的 —— 任何一项错了都不会渲染出
正常角色。

```
python tools/sprite_frames.py rom/base.gba --id 1 --png-dir <输出目录>
```

（PNG 仅作验证辅助；仓库内不保存渲染产物。）

### 4.1 「一帧最多 32 片」的机械核实（2026-10-20）

对 id 1..62 × action 0..8 共 **342 个有素材的动作 / 2674 个帧**，
按"从 `frames` 起连续合法 ROM 指针的个数 = 帧数"取帧，再按 20 字节步长读拼块、
遇 `tile == 0xFFFF` 停，做全量扫描（结果与 `tools/sprite_frames.py --stats` 一致）：

```
每帧拼块数分布 : {1: 2562, 2: 70, 3: 26, 5: 16}
真实最大值      : 5
命中 32 的条目数: 0        ← 一个都没有
```

> 改坏字节前，多出来的那一帧是 (26, 2, 2)：它在缺终止符后失控读出 65 片，
> 被扫描上限截断。把它排除后分布就是上表。

**结论**：**"一帧最多 32 片"不是 ROM 约束**，是第三方的扫描窗口。
原生 ROM 的真实上限是 **5 片**（且从未接近 32）。

拼块尺寸分布见 2.4；`flags` 分布见 2.4。

## 5. 异常清单（全部实测，全部如实报出）

全量扫描的异常总数：**7 条，全部来自同一个 (id, action)**。

### 5.1 ROM 字节损坏：id 26 / action 2，帧 2 的拼块列表终止符

```
动作表项 : 0x597B8C  = 18 a9 25 08 | 48 a9 25 08 | a0 8c 25 08 | 98 2c 25 08
           frames=0x0825A918  anim=0x0825A948  gfx=0x08258CA0  pal=0x08252C98
帧 2 描述符 @0x0825A8D0:
  40 00 00 00 f0 ff c8 ff 20 00 40 00 00 01 00 01   <- 拼块 0 (合法, 16 字节)
  ff 00 00 00                                       <- 4 字节分隔
  ff fb 00 00                                       <- 终止符！tile = 0xFBFF
  60 00 00 00 f0 ff c8 ff 40 00 40 00 00 01 00 01   <- 下一帧的拼块 0
```

正常终止符应为 `ff ff 00 00`（u16 `tile == 0xFFFF` + u16 `0x0000`），
此处第 2 个字节是 **`0xFB`**，即 **ROM 偏移 `0x25A8E5` 处的字节被改成了 `0xFB`**（应为 `0xFF`）。

**2026-10-20 补：正确值已判定为 `0xFF`（三条独立理由）**

1. **结构不变量（机械扫描全 ROM）**：2674 个帧的终止符里，**2673 个逐字节等于
   `ff ff 00 00`**；把 `0x25A8E5` 改成 `0xFF` 后变成 **2674/2674**，异常归零
   （改之前唯一的失控帧就是 (26,2,2)）。
2. **取值域**：该 u16 是**图块索引**（相对该 action 的 gfx 块）。合法拼块里
   出现过的最大 tile 索引是 **768**；`0xFBFF` = **64511**，超出 84 倍，
   不存在能自洽解释 64511 的字段语义。
3. **邻域一致**：终止符的后两个字节已经是 `00 00`，与其它 2673 个终止符完全一致
   ⇒ 只有 tile 的高字节被破坏。

地址级证据见 `notes/evidence/mechanism-sprite-background-20261020.md` §2。

后果：按 `0xFFFF` 终止的解析器会认为该列表没有终止符，继续把后面的
**动画描述符字节**当成拼块读，得到 1 片 `65520 × 65480`、tile = 64511 的垃圾，
进而把该 action 的 gfx 跨度算成 2 GB。

**这是 ROM 自带的损坏，不是解析错误**：仓库根目录的原始汉化 ROM 与 `rom/base.gba`
逐字节相同（0 字节差异），两者的 `0x25A8E5` 都是 `0xFB`。

工具如何处理：**不静默吞掉**。它把这一片标为
`parts_terminator_corrupted`（给出偏移、实际值、期望值），并连带报出
`part_size_invalid` / `part_scale_invalid` / `part_out_of_template` /
`part_gfx_out_of_rom` / `gfx_out_of_rom` / `gfx_overlaps_metadata`，
共 6 条；`--check` 的 C2/C3/C4/C5 四项因这一条而判 FAIL。

**门禁用法**：这 5 条违规**全部**能归因到这一个已知 ROM 缺陷，因此工具把它们
单独列出（`attributed to known ROM defect (26, 2)`）但**不计入失败判定**，
`--check` 在基准 ROM 上因此可以当门禁用（exit 0）。
需要严格模式时加 `--strict-rom`（exit 1）。
缺陷清单集中在 `tools/sprite_frames.py` 的 `KNOWN_ROM_DEFECTS`，
新增 ROM 缺陷时在那里登记即可。

修复建议（若要修 ROM）：把 `0x25A8E5` 的 `0xFB` 改回 `0xFF` 即可，
一个字节。**本仓库未做此修改**（超出本次任务范围）。

| 8 | 4bpp、`tile*32`、`w*h/2` | 4bpp 由 C1/C1' 判死检验证实 | 一致 |

## 7. 沿用第三方说法但**未在本 ROM 复核**的条目

以下几条在本次工作中**没有**得到 ROM 侧证实，只能作为"合理推断"记录：

1. **索引 15（第 16 色）是阵营标记**。第三方源码注释如此。实测索引 15 确实被
   大量使用（125165 像素 ≈ 6%），但没有在模拟器里比对过它的运行时含义。
2. **动画条目的 `b2` 是持续时间（帧数/权重）**。实测取值集合 {1,2,4,6,8,16}
   且 `b3` 恒 0，形态很像时长，但**没有**和运行时播放速度对照过。
3. **拼块后两个 `u16` 是"缩放"（256 = 1.0）**。实测恒为 256；语义名称来自第三方，
   本 ROM 无法区分"缩放"和"预留/版本号"。
4. **游戏运行时的模板锚点就是 (64, 96)、格大小 128×128**。渲染出的角色在格内
   居中合理，与第三方一致，但未在模拟器里逐帧比对过。
5. ~~`0x25A8E5` 的 `0xFB` 是"损坏"而不是某种特殊语义。~~
   **2026-10-20 已闭合**：该字节是 4 字节终止符里 u16 `tile` 字段的高字节，
   正确值 = **`0xFF`**。证据：全 ROM 2673/2674 个终止符逐字节等于 `ff ff 00 00`；
   改回 `0xFF` 后 2674/2674 吻合、失控帧归零；合法 tile 索引上界 768，
   而 `0xFBFF` = 64511 超出 84 倍。见 §5.1。
   （仍未闭合的是**游戏自身**的终止判定到底比 u16 `0xFFFF` 还是只比低字节 `0xFF`，
   这只影响"原版运行时是否可见地出错"，不影响字节本身的正确值。）

## 8. 复现命令

```bash
# 总览（帧数/拼块数/gfx 字节/越界/异常分布）
python tools/sprite_frames.py rom/base.gba --stats

# 判决性不变量检验（C1..C10），失败时退出码为 1
python tools/sprite_frames.py rom/base.gba --check

# 单个 id / action 的完整解析
python tools/sprite_frames.py rom/base.gba --id 1 --action 0
python tools/sprite_frames.py rom/base.gba --id 26 --action 2      # 损坏条目

# 结构化输出（JSON；'--omit-frames' 可去掉逐帧明细）
python tools/sprite_frames.py rom/base.gba --json build/sprites.json

# 渲染 PNG 拼版（验证用，产物不要提交）
python tools/sprite_frames.py rom/base.gba --id 1 --png-dir build/png
```

工具默认扫描 id 1..62（`--min-id` / `--max-id` 可调），输出全部使用
`tools/lib/io.write_text` 写文件，保证 LF 换行。
