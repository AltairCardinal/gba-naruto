## 1. ⭐⭐⭐ G4：原版「战闘分」的**代码级**取证（D4 扫不到的那几处）

G4 换了搜法才命中：**原版用两条独立 `adds` 拼地址**（`adds r0,r2,#0` + `adds r0,#0xCE`）
⇒ D4 搜 `strh [rm,#0xCE]` 得到 **0 处**是**搜法问题**，不是「原版没有转移」。

| 项 | 地址 | 内容 |
|---|---|---|
| 单位数组 | EWRAM `0x020240C0`，步长 **`0x1D4`**(468)，结算扫 0..12 | `0x0808907E` |
| 战闘分字段 | **`unit+0xCE`**（u16） | `0x080890AA` |
| **种子写入** | `0x0806AD92..0x0806AD98`：`ldrh r0,[r5,#0xC]` → `strh r0,[unit+0xCE]` | 原样拷贝 |
| **击倒转移** | `0x0806B222..0x0806B230`（+2 份副本 `0x0806B29C`/`0x0806B2EC`） | **纯 u16 加法**（无缩放） |
| 结算公式 | `0x08089064` | `Σ同角色 carried + (Σ×value_a)/100` ⇒ **与重制侧逐位一致** |

### 1.1 被证伪的三条机制

| # | 机制 | 证伪 |
|---|---|---|
| 1 | 被动百分比（`value_a = −2`） | `ldrh` 恒为正 ⇒ 增量恒 ≥ 0 |
| 2 | ⭐ **按 `unit_parameter(+0x0E)` 缩放**（D4 的线索） | **`+0x0E` 实为状态特效 id**（消费点 `0x0806C71A` 与 `0xFF` 比较），与经验无关；group 9 的 `+0x0E`=2 实为 u16 `258=0x0102` 的**低字节**（高字节 = level 1） |
| 3 | 写侧减法 | **13 个写入点穷举**（2 种子 + 8 写 0 + 3 转移 + 1 条件 `+=25`）⇒ **无一处减法/缩放/取整** |

⇒ ⭐ **「59」只能来自「结算时 Σ carried 本来就是 59」**，而不是 60 被减了 1。

### 1.2 剩余 3 个候选 + 一步判别的办法

| # | 候选 |
|---|---|
| C-1 | 运行时阵型记录 ≠ ROM（group 9 三变体 = 30×5 / 全空 / 50×5，**都不给 29**） |
| C-2 | 有击杀记到了别的 character id |
| C-3 | 被动非零且基础和为 58（`58+1=59`、`30+0=30`） |

⇒ ⭐ **一次「结算瞬间的 EWRAM dump」即可同时判别**：读 `0x020240C0` 起 13 槽的 `+0x00`（character id）
/ `+0xC0` / `+0xCE`（carried）。

### 1.3 场景 46 的更正建议（**两处，不是一处**）

* `mgba_battle_campaign_route.lua:88` `scenario_46_completion and 60` → **`59`**
* `mgba_battle_campaign_route.lua:103` `scenario_46_completion and 185` → **`184`**（口径 = 第一位玩家合計，对照场景 49 的 225）
* ⛔ **不改产品侧**（公式与种子均已证实正确）；这两个期望值是**对原版 ROM 输出的断言**，
  现状下场景 46 完成路径会在断言处失败 ⇒ **建议同时加注释记录「59 来源未闭合」**。

## 2. ⭐⭐⭐ G2：**4bpp 不是「画面冻结」，是崩溃** —— 根因在 `battle_range_overlay`，不在黑场遮罩

### 2.1 ⭐⭐⭐ R-F1-3 的定位被更正（**F1 与父代理都找错了文件**）

> ⛔ **父代理的假设「按当前 BG 自己的调色板项数写回」——形状对，文件错。**
> `game/include/konoha/battle_black_field_star_mask.h`（359 行）**一次调色板都没写**
> （它是纯 OBJ 精灵遮罩）；`battle_black_field.h::apply()` 是空函数，
> 淡入淡出走的是整盘 `bn::bg_palettes::set_fade()`，**不是逐槽写回**。

**真实根因是两层**，都在 `game/src/battle_runtime_scene.cpp` 的 **`battle_range_overlay`**：

| 层 | 位置 | 失败断言 |
|---|---|---|
| **L1** | `:2643` 图块项写死 `bn::bpp_mode::BPP_8`，而 `:2651` **复用地图 BG 的调色板** | Butano `bn_bg_blocks_manager.cpp:1675`：**「Tiles and palette have different BPP: 1 - 0」**（tiles=BPP_8、palette=BPP_4） |
| **L2** | `:2822-2842`（`range_palette_first_color=224`、`action_palette_first_color=240`，断言 `colors.size() >= 256`）+ `battle_range_ui_style.h:19-32`（索引写死 225..235） | 本流自己的断言：**「Battle overlays require an 8BPP map palette」** |

⇒ overlay 借的是**地图调色板顶端的 32 个空闲槽**（8bpp 地图 256 项只用 47 项 ⇒ 224..255 空闲）；
4bpp 地图调色板只有 80 项 ⇒ **224..255 不存在** ⇒ 崩。
⇒ **崩溃时刻 step-28 = 行动/指令选择层出现的那一刻**（overlay 只在
`action_selection`/`command_selection`/`move`/`target` 相位创建）—— 与 8bpp 的 `step-28-A`「地图 + SELECT 面板」严丝合缝。

### 2.2 ⭐ L1 已修，且 **8bpp 下「逐字节 no-op」已实测**

* 重建 8bpp + L1 修的 ROM（12,258,628 B，sha `70dd9bf8…`），**同一探针、同口径**重录 35 帧 boot walk：
  * **35/35 帧 sha256 与 F1 的 8bpp 基线逐字节相同**
  * **25 帧 total = 54,959 px = 基线**（best offset +4 两侧一致）

### 2.3 五项判据逐项

| 判据 | 8bpp + L1 修 | 4bpp + L1 修 |
|---|---:|---:|
| 1. 25 帧 total 不上升（基线 54,959） | ✅ **54,959** | ❌ **82,831**（L2 未修，仍在 step-28 崩） |
| 2. 黑场纯黑帧 58 → ≤56 | ⛔ 未测 | ⛔ 未测（**F1 报的「58→56」在 L2 修完前不可信**） |

| 4. 单测 119/20 | ✅ **119/20**（零新增红） | 同左 |
| 5. 逐帧 sha256 与 8bpp 相同 | ✅ 35/35 | ✅ **step-00…27 = 25/25 逐字节相同**；⛔ step-28…34 仍是错误屏 |

### 2.4 ⭐ L2 的修法设计（**下一轮第一件事**）

overlay 借的应是**「地图调色板顶端 32 个*空闲*槽」**而不是绝对索引 224..255
⇒ 4bpp 地图调色板 80 项里只用 47 项 ⇒ **48..79 空闲** ⇒ 四个子项：

* **L2-a** `battle_runtime_scene.cpp:2822-2823`：两个 first_color 从写死改成按 `palette.colors().size()` 现算
  （8bpp ⇒ 224/240，4bpp ⇒ 48/64），`_restore_action_palette` 同步；
* **L2-b** `battle_range_ui_style.h:19-32` 的 225..235 与 `:3104-3113` 的行动面板索引一起重映射；
* **L2-c** ⭐ `_prepare_tiles()`（`:3043`）的图块字节排布要按 bpp 分别排（4bpp = 32 B/块、2 B/像素）；
  ⚠️ **改前必须先对着 Butano 的图块布局核实**；
* **L2-d** `_restore_action_palette()` 还原索引同 L2-a。

## 4. ⭐⭐⭐ G3：結算屏 **514 px → 0 px**（纯资产层，`battle_runtime_scene.cpp` 一行都不用改）

> 全量细节：`W24-G3-settlement-frame.md`（14 KB）

| 项 | 改前 | **改后** |
|---|---:|---:|
| 結算屏整屏 | **514 px** | ⭐ **0 px**（与原版真值图 sha256 相同） |
| 其余 7 屏 | 0 px ×7 | **0 px ×7**（逐字节相同） |
| 25 帧 total | 54,959 px | **54,959 px**（= 基线，零回归） |
| 判定台 | 38,047 px | **38,047 px**（= 基线，零回归） |
| 单测 | 119 / 20 | **119 / 20** |
| ROM | 12,258,628 B | **12,258,372 B（−256 B）** |

* 514 px = **上边框花纹 223 + 右边框线 131 + 合計行双色红 160**
* ⭐ **「双色红」机制 = 一个图块 + 两个调色板槽位**（不是两个精灵错位叠画，不是字形差，不是描边差）
  * 字形与描边**逐像素相同**（对称差 0）⇒ 只差着色
  * 同字符的 7 个实例给出**逐像素相同**的浅/深分布 ⇒ 双色是**图块属性**
  * ⭐ **最硬的一条**：姊妹字体 `battle_result_compact_font.bmp` 本来就是 `idx2 + idx5` 双色字块 ⇒ 合計行字块是**同机制被压成了单色**
  * 根因：`battle_ui_result_total_palette` 的 16 项里**没有**浅红 `(231,99,66)`
  * 着色规则：*一个笔画像素是深红 ⟺ 它左边紧邻的像素也是笔画像素*
* ⇒ **父代理已接线**（`tools/s49_w25/apply_settlement_assets.py`，sha 逐项核对后才拷进共享树）
