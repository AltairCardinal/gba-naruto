# Positions ROM Source Static Trace (2026-07-10)

## 结论

`positions` 并不位于场景图块表 `0x0853D910` 内。单位初始坐标来自 ROM
`0x085461C4` 起始的战斗编成矩阵；战斗初始化函数读取每个 `0xB8` 字节记录的
`+2/+3` 两个字节，并经 `0x0806AC70 -> 0x0806AA64` 写入运行时单位结构。

静态证据已经闭合到以下数据流：

```text
ROM record = 0x085461C4
           + battle_control[1] * 0x1AAC
           + battle_control[2] * 0x08E4
           + 4
           + record_index * 0xB8

record[+2] (x), record[+3] (y), record[+4] (parameter)
       |
       v
0x0806E41E..0x0806E434 / 0x0806E71E..0x0806E734
       |
       v
0x0806AC70 (wrapper) -> 0x0806AA64 (allocate/copy unit)
       |
       v
unit[+0xC4] = x; unit[+0xC5] = y
unit[+0xC7] = x; unit[+0xC8] = y
```

因此，现有 `sequel/content/positions/bank.json` 将 `0x53D914` 当作位置来源的
结论应撤销；`0x53D914` 是场景 0 的 `tile_gfx_ptr`，不是单位坐标。

## 尝试与证据

### 1. 直接引用 `0x02024294`

在基准 ROM 中搜索小端字面量 `94 42 02 02`，只有两处：

- file `0x06E598`（ARM `0x0806E598`）
- file `0x06E7E8`（ARM `0x0806E7E8`）

两处都属于 `0x0806E1xx-0x0806E7xx` 的同一战斗编成/单位创建流程，而不是
地图加载函数 `0x08068FF0`。相邻文字池同时包含：

- `0x020240C0`：单位数组物理基址
- `0x02021E2C`：另一战斗单位/查找缓冲区
- `0x02026804`：战斗控制字节
- `0x085461C4`：ROM 编成矩阵基址

### 2. 纠正单位 stride

代码反复使用：

```asm
movs rN, #0xEA
lsls rN, rN, #1
```

所以实际单位结构 stride 是 `0x1D4 = 468` 字节，不是 234 字节。
`0x02024294 = 0x020240C0 + 0x1D4`，即它是第一个可分配/常用单位槽，而
`0x020240C0` 是数组物理基址。旧文档中的“stride 234 bytes”把移位前常量
误当成了字节数。

`0x0806AA8C..0x0806AAA4` 从 slot 1 开始扫描空槽，进一步解释了为什么直接
文字池会同时出现 `0x020240C0` 与 `0x02024294`。

### 3. ROM 来源寻址

战斗初始化的两条近似分支（`0x0806E3C2..0x0806E434` 与
`0x0806E6C2..0x0806E734`）构造相同的记录地址：

- `r3 = 0x02026804`
- `r3[1] * 0x1AAC`
- `r3[2] * 0x08E4`
- 加 `0x085461C4`
- 首记录加 `4`
- 后续候选加 `record_index * 0xB8`
- 最多扫描 12 条（索引 `0..11`）

记录首字节用于选择/过滤。两条分支均在调用 `0x0806AC70` 前执行：

```asm
ldrb r1, [r5, #2]
ldrb r2, [r5, #3]
ldrb r3, [r5, #4]
ldr  r4, [r5, #8]
bl   0x0806AC70
```

基准 ROM 中可直接观察到合理坐标。例如矩阵块 `0x547C70` 的前六条为：

| 记录 | +0 | +1 | x (+2) | y (+3) | +4 |
|---:|---:|---:|---:|---:|---:|
| 0 | 1 | 0 | 10 | 9 | 3 |
| 1 | 2 | 0 | 10 | 6 | 3 |
| 2 | 3 | 0 | 4 | 6 | 1 |
| 3 | 31 | 0 | 6 | 7 | 1 |
| 4 | 25 | 1 | 11 | 4 | 2 |
| 5 | 26 | 1 | 11 | 10 | 0 |

这比 `0x53D914` 的 ROM 指针字节更符合地图格坐标，并由消费者代码证明。

### 4. 坐标最终写入位置

`0x0806AC70` 只是把参数裁剪为 u8 后转发给 `0x0806AA64`。后者分配
`0x020240C0 + slot * 0x1D4`，随后：

- `0x0806AADA`：参数 `r1`（源记录 `+2`）写至单位 `+0xC7`
- `0x0806AAEA`：同值写至单位 `+0xC4`
- `0x0806AAF0`：参数 `r2`（源记录 `+3`）写至单位 `+0xC8`
- `0x0806AAFA`：同值写至单位 `+0xC5`
- `0x0806AB02/0x0806AB0C`：参数 `r3`（源记录 `+4`）写至 `+0xC9/+0xC6`

这证明记录 `+2/+3` 是单位初始二维位置；两套字段很可能分别保存当前坐标和
初始/目标坐标，但两套字段的精确角色仍需运行时移动追踪确认。

## 与 `0x0853D910` 的关系

`0x0853D910 + 4 + scenario_id * 32` 是地图资源描述符。其首项
`0x0853D914 = 0x080B9F80` 指向图块数据。地图加载器 `0x08068FF0` 消费该表，
而上述单位创建路径没有从 `0x0853D910` 取坐标。因此场景 ID 会分别选择地图
资源与战斗编成，但不能把地图描述符自身当作 positions 表。

## 当前边界与后续验证

- 已静态确认 ROM 来源、两级索引、记录 stride、坐标字段和 WRAM 消费位置。
- `tools/extract_positions.py` 已将矩阵按 48 groups × 3 variants × 12 records
  可复现提取到 `sequel/content/positions/bank.json`。3 variants 的边界由
  `3 * 0x08E4 == 0x1AAC` 严格确定；48 groups 与现有 48 个角色/单位域及后续
  ROM 数据边界一致，但 battle-control 第一维的运行时最大值仍需断点确认。
- bank 为每条记录保留完整 `raw_hex`、`_index` 和 `_raw_offset`；编辑器通用
  ROM mirror 会生成 `rom_positions` 1728 行。`generate_unit_position_patches()`
  只接受该 mirror，并校验 index→矩阵地址公式及恰好 `0xB8` 字节后写回真实
  ROM。旧 `unit_positions` CRUD 表没有已证明的一行一 ROM 地址映射，明确不再
  被此真实回写函数读取，也不能作为完成证据。
- 尚未动态确认 `battle_control[1]` 与 `[2]` 的完整枚举语义。
- 尚未确认记录 `+0/+1/+4/+8` 的完整语义。
- 下一步应在首场战斗入口对 `0x0806E41E` 或 `0x0806E71E` 设断点，记录
  `r3[1:2]`、`r5` 和创建后的 slot，再将画面格坐标与 `record[2:3]` 对照。

## 重要地址范围

- ROM `0x5461C4` 起：战斗编成矩阵基址
- ROM 记录跨度：`0xB8`，每个选择块扫描 12 条
- ROM 第一维跨度：`0x1AAC`
- ROM 第二维跨度：`0x08E4`
- code `0x0806E3C2-0x0806E434`：第一条编成读取/创建分支
- code `0x0806E6C2-0x0806E734`：第二条编成读取/创建分支
- code `0x0806AC70`：单位创建包装器
- code `0x0806AA64-0x0806AC6E`：单位槽分配与坐标写入
- WRAM `0x020240C0 + slot*0x1D4`：实际单位数组
- WRAM `0x02024294`：slot 1（不是独立数组基址）
- ROM `0x53D914`：场景 0 图块指针，明确不是 positions 来源
