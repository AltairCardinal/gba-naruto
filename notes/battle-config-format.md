# Battle Configuration Format

## Status

**Substantially complete.** WRAM battle data layout identified via code analysis. ROM-based battle config tables located and documented. Runtime verification blocked by headless navigation limitation (no key input support in mGBA debugger). Both ROM patches and WRAM cheat patches are generated by `import_battle_config.py`.

## Key ROM Data Tables

### Unit ID Mapping Table

- **ARM address**: `0x0853F298`
- **File offset**: `0x53F298`
- **Size**: 128 bytes (u16[64])
- **Purpose**: Maps internal slot index → character ID used by the battle system

| Index Range | Values | Description |
|---|---|---|
| 0-9 | 0x00-0x09 | Player units (Naruto=0, Sasuke=1, Sakura=2, Sai=3, Kakashi=4, Shikamaru=5, etc.) |
| 10-29 | 0x19-0x2E | Special/enemy units |
| 30-42 | 0x0A-0x18 | Additional character units (Zabuza=10, Haku=11, etc.) |
| 43-55 | signed i16 | Movement offsets for 8-directional unit movement |
| 62-63 | 0x0C3D, 0x0808 | ROM data index marker |

### Battle Scenario Config Table

- **ARM address**: `0x0853D910`
- **File offset**: `0x53D910`
- **Entry size**: **32 bytes**
- **Total entries**: **47 valid entries (indices 0–46)**; index 47 onward is garbage
  (`raw_width = 513`, pointers outside ROM)
- **Index formula**: `entry_ptr = 0x0853D910 + chapter_id * 32`
  (the reader at `0x08069002` masks the index to 8 bits and computes
  `index << 5` at `0x08069044`)

> **CORRECTED 2026-10-20** — 本文件原先写"8 valid entries (0–7)"，是**旧误判**。
> 本轮用 LZ77 解压长度对**全部 47 条**逐条自证（见下），每一条都满足
> 4 个等式，无一例外 ⇒ 表长是 47，不是 8。
>
> 此前本文件与 `notes/chapter-flow-format.md` 各自给出一套互相矛盾的 32 字节布局
> （一份把 palette 放在 +0x10、flags 在 +0x18；另一份把宽高放在 +0x00 且把 gfx
> 放在 +0x04）。两套都**与实测不符**。
> 正确布局已由 `tools/probe_external_re_claims.py` 在本仓库 ROM 上按
> LZ77 解压长度逐字段验证，详见 `notes/external-konoha-workshop-gap-20261020.md` §2.1。

**Entry format (32 bytes) — CORRECTED 2026-10-20:**
| Offset | Type | Name | Description |
|---|---|---|---|
| +0x00 | u16 | raw_width | 原始宽（÷4 = 图块宽） |
| +0x02 | u16 | raw_height | 原始高（÷2 = 图块高） |
| +0x04 | u32 | tile_gfx_ptr | ROM 指针 → LZ77 压缩 tile 图形 (4bpp) |
| +0x08 | u32 | palette_ptr | ROM 指针 → LZ77 压缩调色板 (解压 384 字节) |
| +0x0C | u32 | layer0_ptr | ROM 指针 → LZ77 压缩图块层 0 (tilemap) |
| +0x10 | u32 | layer1_ptr | ROM 指针 → LZ77 压缩图块层 1（可为 0） |
| +0x14 | u32 | metatile_ptr | ROM 指针 → LZ77 压缩组合图块表（8 字节/项） |
| +0x18 | u32 | terrain_ptr | ROM 指针 → LZ77 压缩通行值表（每格 u16） |
| +0x1C | u8 | background_id | 剧情底图 ID（story background id） |

> **验证依据**：entry 0 的 terrain 解压长度 = **1472 = 23 × 32 × 2**，
> 与 图块宽(92/4=23) × 图块高(64/2=32) × 每格 2 字节 精确吻合；
> metatiles 解压长度 = 6160 = 770 × 8 字节，吻合 8 字节/项。
> entry 1、entry 3 同样吻合。
>
> **2026-10-20 补：47 条全部自证。** 每条都满足
> `len(layer0) = 2 × cells × 2`、`len(layer1) ∈ {0, 2 × cells × 2}`、
> `len(metatile) ≡ 0 (mod 8)`、`len(terrain) = cells × 2`
> （cells = (raw_width>>2) × (raw_height>>1)）。逐条数据见
> `notes/evidence/mechanism-sprite-background-20261020.md` §4.4。

### 原生读取器 `0x08068FF0`（2026-10-20 补）

```
0x08069040: ldr  r5, [pc, #0x98]     ; r5 = 0x0853D910（表基址）
0x08069044: lsls r6, r2, #5          ; index * 32
0x0806904A: ldr  r0, [r0]            ; entry+0x04 tile_gfx
0x08069056: bl   #0x809c0e8          ; LZ77UnCompVram → 0x06000000 + charblock*0x4000
0x08069060: ldr  r0, [r0]            ; entry+0x08 palette
0x08069066: bl   #0x809c0e8          ; LZ77UnCompVram → 0x05000000
0x08069070: ldr  r0, [r0]            ; entry+0x0C layer0
0x08069076: bl   #0x809c0ec          ; LZ77UnCompWram → 0x0201BE2C
0x08069080: ldr  r2, [r0]            ; entry+0x10 layer1
0x08069082: cmp  r2, #0
0x08069084: beq  #0x0806909e         ; ← NULL ⇒ 跳过整个 layer 1
0x08069096: adds r1, r4, r7          ; layer1 → 0x0201BE2C + 0x1000
0x0806909A: bl   #0x809c0ec
0x080690A4: ldr  r0, [r0]            ; entry+0x14 metatile
0x080690A8: bl   #0x809c0ec          ; LZ77UnCompWram → 0x0201DE2C
```

**「没有 layer 1」的判据 = `layer1_ptr` 是 NULL 指针（0）**，没有别的哨兵值。
47 条里 14 条非空（0,7,8,9,10,11,12,21,22,23,31,32,34,35），33 条为 0。

**metatile 缓冲与容量**：

| 项 | 值 | 证据 |
|---|---|---|
| 缓冲地址 | WRAM `0x0201DE2C` | `0x080690A6` 的字面量 |
| 条目大小 | **8 字节**（4 × u16 图块描述符 = 2×2 图块） | `0x08068F38 lsls r0, r0, #3` |
| 容量 | **2048 个 metatile** | 缓冲上界 0x4000 字节（见下） |
| 实测最大用量 | **770**（entry 0） | 47 条的 metatile 解压长度全是 8 的整数倍 |

缓冲的两端由**原生代码写过的其它结构**夹出：
下方是 layer 平面区（`0x0201BE2C`，layer1 在 `+0x1000`），
上方是地图格表 `0x02021E2C`（`0x08080FC8` / `0x08080FD4` 写入），
⇒ metatile 缓冲 = `0x0201DE2C .. 0x02021E2C` = **0x4000 = 16384 字节** = 2048 个 metatile。

> ⚠️ 2048 是**由上下两块原生结构夹出来的上界**，不是从一条显式的分配语句读出来的；
> 本轮未找到对该缓冲做 memset / 显式分配的代码。

### ptr1 Data Format (Tilemap)

Each ptr1 points to a block with a 12-byte header followed by tile data:

| Offset | Type | Description |
|---|---|---|
| +0x00 | u16 | Constant 0x0010 (16) |
| +0x02 | u16 | Stride/width parameter |
| +0x04 | u16 | Height parameter |
| +0x06 | u16 | Constant 0xF000 |
| +0x08 | u16 | Constant 0x9001 |
| +0x0A | u16 | Subtype/palette identifier |
| +0x0C | varies | Raw tile data (u16 per tile: lower 10 bits = tile ID, bits 10-15 = flip/palette) |

### ptr2 Data Format (LZ77 Compressed)

Each ptr2 points to LZ77-compressed data:
- **Header byte**: 0x10 (GBA LZ77 type)
- **Decompressed size**: 384 bytes (constant across all entries)
- **Content**: Palette or attribute data (BGR555 u16 values dominate)

Entries 2, 4, 6, 8 share identical compressed data, indicating a common palette/attribute set.

### Battle State Machine Function Pointer Table

- **ARM address**: `0x0853F1C0`
- **File offset**: `0x53F1C0`
- **Size**: 240 bytes (u32[60])
- **Content**: 60 function pointers to battle system handlers in ROM bank 0x0812Fxxx

### Memory Allocation Table

Located at ROM `0x0853D848` (file `0x53D848`). Contains `{u32 wram_addr, u32 size}` pairs.

### Unit Structure

- **Size**: **468 bytes (0x1D4)** per unit — CORRECTED 2026-10-20
  （此前本文件写 236 字节 / `0x02024294` 为 234×25 数组；实测
  `0x02024294 - 0x020240C0 = 0x1D4 = 468`，`docs/sequel-roadmap.md`
  与 `tools/extract_positions.py` 早已采用 468）
- **Max units**: 12（`0x020240C0 + n*468`，n = 1..12）
- **Loop bound**: Code at `0x06D46C` iterates 12 units

Known field offsets (battle slot, base `0x020240C0 + n*468`):
| Offset | Type | Evidence |
|---|---|---|
| +0x00 | u8 | 角色 ID（0 = 空位） |
| +0x01 | u8 | 等级 |
| +0x02..0x04 | u8×3 | 三维数值（可加成，敌方上限 99） |
| +0x0C..0x0D | u16 | 当前 HP |
| +0x0E..0x0F | u16 | 最大 HP |
| +0xC0 (192) | u8 | 标志位（bit4 被判定逻辑使用） |
| +0xC4 (196) | u8 | X 坐标 |
| +0xC5 (197) | u8 | Y 坐标 |
| +0xCC (204) | u8 | 守卫/无敌标志 |

## Runtime Verification

**Blocked**: mGBA headless debugger does not support key input injection. The game cannot be navigated to battle state without user input. Previous attempts:
1. 10000-frame advance: only 5 non-zero words in battle WRAM (general game state, not battle data)
2. WRAM force-write of battle flags: did not trigger battle state
3. Lua script (mgba_battle_walk.lua): system mGBA lacks `--script` support

**Recommended**: Use mGBA Qt with Xvfb and Lua scripting, or save a savestate during battle for headless analysis.

> **2026-10-20 方法论线索**：上述"无法注入按键"是 **CLI 调试器工具层限制**，不是游戏本身的限制。
> 第三方包用 **mGBA 0.11 的 C API**（`tools/gba_probe.c`，链接 mGBA 头文件与库，
> 编译时 `-DENABLE_DIRECTORIES`）在 C 层直接驱动模拟器，**可以注入按键**，
> 并把证据分为：正常按键操作 / 脚本协程注入事件 / 关卡对象生成定点 /
> 学习函数定点 / SAV 冷启动。移植思路见
> `notes/external-konoha-workshop-gap-20261020.md` §3 P3-1。
