## 0. 结论

游戏用一套**字节码 VM** 驱动剧情、战斗配置与条件事件。
本仓库此前完全没有这一层——只解出了 SJIS 文本块和渲染链，
不知道"哪段对白挂在哪个场景、谁说的、条件是什么"。

现在可以：

- 把 55 个场景的脚本全部解成节点图（**6184 行可读中文对白**）
- 解析战斗胜负条件、旗帜位、回合条件
- 把条件对白作为一等公民看待（可枚举、可改写）

## 1. 四张根表

每个场景最多四个根指针（u32 ROM 指针，按场景号索引）：

| 表 | 文件偏移 | 含义 | 场景范围 |
|---|---|---|---|
| before | `0x060C74` | 战前剧情脚本 | 1..55 |
| after | `0x060D54` | 战后剧情脚本 | 1..55 |
| logic | `0x060E34` | 战场事件逻辑 | 1..46 |
| events | `0x060EF0` | 战场事件表 | 1..46 |

实测 scene 1：before `0x08009F2E` / after `0x0800AEDC` /
logic `0x0804C64E` / events `0x0804C7FB`。

场景号 1..55 为剧情，1..46 同时也是战场（battle）与场景（story）两个编号空间。

### 1.1 VM 本体（2026-10-20 新增）

| 项 | 地址 | 说明 |
|---|---|---|
| 解释器入口 | `0x080977B8` | Thumb；`r0` = 脚本首地址，`r1` = 模式 |
| 指令分发表 | `0x080977F4` | 58 项 u32（opcode `0x00`..`0x39`），每项 = handler 地址 |
| 取指循环头 | `0x08097E2C` | 所有 handler 跑完回到这里重新取指 |
| 分发代码 | `0x080977D8` | `ldrb r0,[r7]` / `cmp r0,#0x39` / `lsls r0,#2` / `ldr r0,[r0]` / `mov pc,r0` |

调用点（谁在跑这个 VM）：

| 调用点 | 用途 |
|---|---|
| `0x0808F5D0` | 剧情调度器：按 `state[0x18]` 在 before/after 表之间二选一，场景号 = 参数 >> 14 |
| `0x0808A54C` / `0x0808A566` | 战场事件调度器：取 logic 表的脚本 |
| `0x0808A5FC` / `0x0808A67C` | 战场事件调度器：取 events 表的脚本 |

> 表格里的 `0x08060C74` 等是 **ROM 地址**（= 文件偏移 + `0x08000000`），
> 根表的文件偏移见上表。

## 4. 指令语义

标注说明：
**[证]** = 由原版说明文字/数据直接证实
**[推]** = 由操作数分布与上下文推断，尚未逐条验证
**[码证]** = **2026-10-20 起**：已追到 ROM 里的具体指令（handler 地址 + 证据指令），
详见 `notes/story-vm-opcodes-20261020.md`；未追到的部分在那一节第 4 节列明缺什么证据。

### 4.3 战斗条件（logic / events 脚本）

| op | 语义 | 证据 |
|---|---|---|
| 0x34 | 回合/相位条件：**[比较器, b, c, 指针]** | **[码证]** handler `0x08097D4C` → `0x0808A1A4`（比对 `0x0202680C`）；374 处 |
| 0x35 | 复合条件：**[a, b, c, d, 指针]** | **[码证]** handler `0x08097D86` → `0x0808A1C4`；196 处 |
| 0x36 | 指定人物在场：**[a, b, c, 指针]** | **[码证]** handler `0x08097DA6` → `0x0808A420`（遍历 `0x020240C0`）；213 处 |
| 0x37 | 置/清战斗标志：**[模式, 标志号]** | **[码证]** handler `0x08097DC4` → `0x0808A490`（改 `0x020311D4 + 4*(id>>29)` 的 bit(id&0x1F)）；196 处 |
| 0x38 | 测战斗标志：**[模式, 标志号, 指针]** | **[码证]** handler `0x08097DCE` → `0x0808A4D8`；204 处 |
| 0x39 | 配置(sub)匹配：**[a, 指针]** | **[码证]** handler `0x08097DF6`：`ldrb r0, [r0, #0x19]` / `cmp r0, r1`；26 处 |

**0x34/0x15 的比较器**（**本仓库自证**，2026-10-20：`0x08097230` 的 6 路分发表逐条反汇编）：
`0`=等于、`1`=不等于、`2`=大于、`3`=大于等于、`4`=小于、`5`=小于等于。
比较为**无符号** 8 位比较。旧版写的「0xFF=恒真」在 ROM 的分发表里**没有这一项**，
未在原版脚本中出现，特此更正。

**三套互不相同的标志位空间**（本次新发现）：

| 数组 | 寻址 | 用在 |
|---|---|---|
| `0x020314F0` | byte = id>>3，bit = (id>>16)&7 | 0x09 / 0x0A / 0x0B / 0x0C |
| `0x02031510` | byte = i>>3，bit = i&7 | 0x19（0x15 / 0x34 读同一片） |
| `0x020311D4` | word = id>>29，bit = id&0x1F | 0x37 / 0x38 |

**标志位占用**：原版脚本使用 0..11 与 127；新增事件可用 12..126。
（第三方编辑器据此实现；本仓库已确认原版确实在用 0xFF 与低位段。）

## 6. 正确性验证

`tools/decode_story_script.py` 走完 55 场景 4 张根表后：

```
=== issues: 0 ===
```

自校验包含两条硬条件：

1. **未知指令数为 0** —— 长度表覆盖了本 ROM 用到的全部指令。
2. **每个分支目标都必须落在指令边界上**（`validate()`）——
   任何一处长度算错，分支就会指向指令中间而被检出。
   47 个地图条目的 terrain 长度同样做了 47/47 穷举校验。

这两条同时成立，说明长度表不是"碰巧能走通"。

**2026-10-20 追加（`tools/story_vm_ops.py`）**：长度表不再只靠"走通"来背书，
而是从 ROM 的 handler 代码**符号执行推导**，并与本解码器逐条核对：

```
opcodes with a meaning : 44  (43 used in this ROM, 1 unused)
  proved                : 38 / 44
  inferred              : 6
  unproved              : 0
opcode slots proved void: 14 (0x24..0x31)
occurrences explained   : 19476 / 19476
walk issues             : 0
```

该工具同时核对：四张根表地址、`LENGTHS` 逐条长度、每条 `proved` 结论引用的
指令原文；任一处对不上即以非 0 退出。
