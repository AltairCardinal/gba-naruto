# 音频域交互重设计规格 + 反查可行性证据（2026-10-21）

> 子代理「音频」交付物。本文件只记录**规格与证据**，不含任何代码改动。
> 规格的落地方由主代理统一进行（见 `notes/editor-ux-redesign-brief-20261021.md` §6）。
>
> 证据等级说明：
> * **已证**：本轮在 `rom/base.gba` 上逐字节复核，或引用仓库里已有的 L2 运行时证据。
> * **推定**：静态推导合理，但**没有**运行时证据闭环；界面上必须标注。

---

## 0. 摘要

今天：侧边栏 → 音频 → 域首页一张 159 行的只读一览 + 一张「去改音效」卡 → 通用结构编辑器里
用**裸十六进制**改 `descriptor_ptr`，改完不知道动到了谁。

改成：音效分派表**按音效分组**（音乐 / 短音效 / 空）、描述符变成**带名字的下拉**、
每条音效直接显示它指向哪首曲子与几轨、**「谁指向这个描述符」可反查**、
**函数指针表 1..11 槽被认出是「播放音效 #1..#11」的入口**。

## 1. 本轮新证据（此前仓库里没有写下来）

### 1.1 159 个音效 id 的真实构成

方法：`python tools\audio_song_headers.py rom\base.gba`（该工具会遍历全部 159 行并解析 SongHeader），
再与 `rom-editor/content/pack.json` 的 `sound_id_table` 逐行对照。

| 事实 | 值 | 证据 |
|---|---|---|
| sound id 表 | `0x465B70`（ARM `0x08465B70`），159 行 × 8 字节 | 已证 |
| 描述符指针的**不同取值** | **81 个** | 已证（159 行去重） |
| 指向**同一个空哨兵描述符** `0x08466068` 的 id | **79 个**：id `0`、`19–50`、`55–100` | 已证 |
| 各自拥有独立描述符的 id | **80 个** | 已证 |
| 内容包里**已解码**的描述符 | **只有 5 个**：id `1`(`0x536368`)、`2`(`0x536BC4`)、`8`(`0x538FEC`)、`11`(`0x53AB74`)、`14`(`0x53C3BC`) | 已证（`pack.json`） |
| ⇒ **真实存在但编辑器里看不到**的描述符 | **75 个** | 已证（80 − 5） |

空哨兵描述符 `0x466068` 的字节（已证）：
`00 00 00 00 | 00 00 00 40 | 00 c0 da 00 | 09 29 00 00 | 35 51 00 00 …`
→ `track_count = 0`、`voicegroup_ptr = 0x40000000`，
与 `tools/audio_song_headers.py` 里的 `EMPTY_HEADER = 0x40000000` 判据一致
（该工具把它标成 `empty` 并从报告里剔除）。

### 1.2 80 个真实音效的分组（已证）

| id 区间 | 数量 | 轨道数 | 音色组 | 性质 |
|---|---|---|---|---|
| `1–18` | 18 | 4–10 轨 | `0x0846480C` 起连续 | 乐曲（其中 5 个有旧 bank 别名 story / story-b … story-e） |
| `51–54` | 4 | 4–7 轨 | `0x08465694` 起 | 乐曲 |
| `101–158` | 58 | **各 1 轨** | 全部 `0x08465778` | 短音效（同一个音色组，1 条轨） |

### 1.3 播放通道 / 播放配置两个字段（已证）

| 事实 | 值 |
|---|---|
| `+0x04`（pack 标「播放通道」）取值 | 只有 `0 / 1 / 2 / 3`；分布 `0→97 条`、`1→8 条`、`2→50 条`、`3→4 条` |
| `+0x06`（pack 标「播放配置」）取值 | 与 `+0x04` **在全部 159 行里逐行相等** |
| `+0x04` 的原生含义 | 仓库 L2 证据称它是 **voice 索引**（`notes/evidence/l2-runtime-evidence-20261021.md` §3.2：表项 `+0x04` = 1，与寄存器 `r3` 逐位相等） |
| 关联表 | 声音分派在 `0x0809AAC4` 读 `0x08465B40`（6 组 × 8 字节的 `{ptr,count}` 声音缓冲表，指 `0x0300xxxx` IWRAM）；`+0x04` 的 4 个取值落在它的下标空间里 |
| `+0x06` 的原生含义 | **未证实**（与 `+0x04` 恒等，但语义未证明） |

### 1.4 声音 id 是「运行时下标」，不是被存起来的值（已证）

* 分派函数 `0x0809AAC0`：`lsls r0,r0,#0x10` → `lsrs r0,r0,#0xd` → `id*8`，
  再 `+0x08465B70` 得表项地址（`notes/evidence/l2-runtime-evidence-20261021.md` §3.2 已给运行时命中）。
* 读表基址 `0x08465B70` 的**全部**静态读取点（9 个，来自该文件的 `LiteralIndex` 输出）：
  `0x08061E3A`、`0x08061E9E`、`0x08061F00`、`0x08061F2C`、
  `0x0809AAC6`、`0x0809AAF2`、`0x0809AB3E`、`0x0809AB92`、`0x0809ABC6`。
* ⇒ **整个内容包里没有任何一个字段存着 sound id**（已核对 40 张表的全部字段：
  `relation` 只指向 `jutsu_names` / `training_names` / `ninjutsu_names` /
  `character_names` / `material_names` / `battle_objectives` / `background_table`，
  没有任何一张表以音效 id 为值）。
  **推论**：`xref.js::backReferences` 对音效**必然返回空**，因为它只扫 `field.relation` 的**字段值**。

### 1.5 函数指针表 = 「播放音效 #1..#11」的入口（已证字节，推定语义）

`0x53D5F0` 的 13 个槽：

| 槽 | 值 | 字节（已逐条核对） |
|---|---|---|
| 0 | `0xFFFFFFFF` | 哨兵 |
| 1 | `0x08061C8D` | `B500 2001 F7FF FFE2 BC01 4700` → `push {lr}; movs r0,#1; bl 0x08061C5C; pop {r0,pc}` |
| 2 | `0x08061C99` | `push {lr}; movs r0,#2; bl 0x08061C5C; pop {r0,pc}` |
| … | 每槽 +12 字节 | … |
| 11 | `0x08061D05` | `push {lr}; movs r0,#11; bl 0x08061C5C; pop {r0,pc}` |
| 12 | `0xFFFFFFFF` | 哨兵 |

* **已证**：11 个槽是 11 个 12 字节的 thunk，每个的**第二条指令**就是 `movs r0,#k`（k = 1..11），
  11 个 thunk 跳向**同一个**共享例程 `0x08061C5C`（全 ROM 37,468 条 BL 指令扫描：
  `0x08061C5C` 的调用者恰好 11 个，就是这 11 条 thunk）。
* **已证**：表基址 `0x0853D5F0` 在 ROM 里只被引用一次，落在 `0x08061DFC`。
* **推定（未闭环）**：`k` 就是 **sound id**。依据是 k 的取值域 `1..11` 恰好落在
  §1.2 的乐曲段（id 1..18）里，且这些 thunk 与声音读表代码同处 `0x08061Cxx–0x08061Fxx`。
  **但仓库里没有运行时证据把「槽 k」与「sound id k」连起来** ——
  L2 证据闭环的是 `0x0809AAC0` 分派链（运行时下标 102 / 1 / 154），不是这条链。
  ⇒ 界面上只能写成「候选使用点（推定）」。

### 1.6 「换一个音效 id」在 ROM 里的真实语义

作者想改的通常不是「id 数字」，而是**「让 id N 播另一首歌」**。在 ROM 里这件事是
**改 `sound_id_table` 第 N 行的 `descriptor_ptr`**（8 字节行：`+0` u32 指针、`+4` u16、`+6` u16）。
这一行的 8 个字节是**定长**的（描述符指针换掉不改变行长度），写回安全。

### 1.7 音频采样本体为什么改不了（已证，与 brief 一致）

`notes/evidence/audio-song-export-20261021.md` §4 + `notes/evidence/m4a-block-table-20261021.md`：
轨数据是**压缩载荷**，仓库里没有与原版逐字节一致的压缩器；
`tools/import_audio_song.py` 只能**复用原生 block**。
⇒ 编辑器能改的是**描述符层**（SongHeader 字段、轨道指针指向哪条 block），
不能改采样本身。界面必须把这条边界写清楚。

## 2. 关键判断：sound-ID 的「反查」该怎么落地

### 2.1 结论

**不给 `sound_id_table` 加 `id_relation`；改为「描述符指针下拉 + 指针级反查 + 派生索引区段」。**

依据三条：

1. **`id_relation` 是「取名字」的机制，不是「找引用」的机制。**
   `fields.js::idRelationName`（`rom-editor/js/fields.js:215-231`）只做一件事：
   用记录下标去另一张表取名字。而 ROM 里**没有音效名表**
   （内容包 11 张文本表的 module 分布里没有 audio），所以 `id_relation` 最多只能得到
   `#0`/`#1` 这种零信息标签。
2. **`backReferences` 只认 `field.relation`，扫的是「字段值」**（`rom-editor/js/xref.js:33-49`）。
   而 §1.4 已证：全包**没有任何字段存着 sound id**。
   ⇒ 即使加了 `id_relation`，「被谁引用（0 处）」这一栏仍然会是空的，而且**看不出是空还是坏了**。
3. **音效 id 在 ROM 里的性质是运行时下标**（§1.4）。所以「谁引用了音效 #N」只有两类可查的入口：
   * **指针级**：谁把「等于该描述符地址的值」写在了表里（→ 同一描述符被哪些 id 共用；
     例如 79 个 id 共用空哨兵 `0x08466068`）。
   * **代码级**：谁在调用时把 N 当参数传下去（→ §1.5 的 11 条 thunk，以及 `0x0809AAC0` 的调用点）。
   这两类都**不是** `id_relation` 能表达的。

### 2.2 因此分三层落地

| 层 | 需要原版 ROM？ | 内容 | 证据等级 |
|---|---|---|---|
| **L1 描述符层**（默认，必须做） | 否 | 80 个描述符全部导出成结构；`descriptor_ptr` 变下拉；指针级反查；派生索引 | 全部已证 |
| **L2 全 ROM 指针扫描**（可选按钮） | **是** | 整个 ROM 里还有几处 4 字节指针指向这个描述符 | 已证（纯字节扫描） |
| **L3 代码级使用点**（本轮建议不做） | 是 | 「音效 id → 使用点」表 | 推定未闭环，需 mGBA 补证 |

**L1 的四个具体动作：**

1. **导出全部 80 个描述符**（`tools/export_content_pack.py`）。
   现在只有 5 个 → 75 个真实音效在编辑器里根本看不到。
   命名沿用 `audio_song_<id>`，与已有 5 个一致。
   ⚠️ 这些结构会被 `rom-editor/js/rom.js:102-121` **整段写回**；
   它们都在 `0x536368..0x53D584` 的音频区内，未改动的记录写回后与原 ROM 逐字节相同（安全）。
   ⚠️ `tools/table_registry.py` 与 `tools/alias_audit.py` 必须保持绿（registry 是仓库唯一权威基址表）。
2. **`descriptor_ptr` 从裸十六进制变下拉**（81 个取值，中文标签）。
   复用 `fields.js::fieldControl` 的 `field.relation` 分支，新增一种关系种类
   （指针型关系：按**地址**解析到目标结构记录），并在 `relationOptions` 里给出
   「该表出现过的全部指针值 + 已解码目标记录」的选项集。
   ⇒ 「换一个音效 id」从「手抄十六进制」变成「点一下」。
3. **指针级反查**（`rom-editor/js/xref.js` 新增一个函数）。
   扫全包 `type==='ptr'` 的字段，找值等于目标地址的记录 →
   「谁指向这个描述符」列出全部 id（同一描述符多 id 共用时会一次列全）。
   这是**前向 `describePointer`（`fields.js:124-162`）的反向半边**，两边合起来才完整。
4. **派生索引区段**（内容包新增顶层 key，例如 `pack.derived`）。
   放**不占 ROM 字节**的数据：描述符 → `{音效 id 列表, 轨道数, 块数, 是否空哨兵, 通道}`。
   ⚠️ **不能**把它做成 `pack.structures` 里的表 ——
   `rom.js::applyStructures` 会把**每一张**结构表的每条记录按 `record.rom_offset` 写回 ROM，
   合成表没有 ROM 字节 → 构建报错。
   `rom.js` 只访问 `pack.structures` / `pack.texts` / `pack.patches`，
   所以新增顶层 key 是安全的（`rom-editor/js/pack.js:28-51` 需要补一行透传）。

**L2 的做法**：载入原版 ROM 后，对 4 字节小端指针值做一次全 ROM 扫描
（6 MB，几毫秒），列出命中地址并标注落在哪张表 / 在代码段。
界面按钮：「扫全 ROM 找指向它的指针」。

**L3 的做法（建议下一轮）**：离线探针扫 ROM → 产出「音效 id → 使用点」→ 进 `pack.derived`。
界面必须标「推定」并把原始字节摆出来让作者自己核对。

## 4. 重设计后的操作流

### 4.1 音频域首页（`#audio`）

**布局**（沿用 `renderDomainIndex` 的三段式：`common.js:65-114`）：

```
┌ 面板头：音频 ──────────────────────────────────────────────┐
│ ROM 0x465B70（159 条）｜ m4a SongHeader 0x536368 等 5 首     │
├ 推荐入口 ────────────────────────────────────────────────────┤
│ [卡片1] 改音效分派                [卡片2] 乐曲描述符          │
│  159 条 sound id                    80 个描述符              │
│  80 个有内容 / 79 个空哨兵          18 首多轨 + 58 个单轨    │
│  [去改音效]                         [看描述符]               │
│                                     [卡片3] 函数指针表        │
│                                      13 槽 / 11 条播放入口    │
│                                      [看指针表]              │
├ 本域可编辑内容（表）─────────────────────────────────────────┤
│  表 │ 条数 │ 字段 │ 改法 │ 长度策略 │ 已改 │ 入口            │
│  音频 sound-ID 表 │ 159 │ 3 已知 │ 直接改 │ — │ ●0 │ [编辑]  │
│  音频曲 1（m4a SongHeader）│ 1 │ 13 已知 │ 直接改 │ …       │
│  …（80 行）                                                   │
├ 一览（只读参考）───────────────────────────────[折叠]───────┤
│  159 = 80 有内容 + 79 空哨兵（id 0、19–50、55–100）          │
│  80 = 乐曲 18（id 1–18）+ 乐曲 4（id 51–54）+ 短音效 58     │
│  播放通道分布：0 通道 97 条 / 1 通道 8 条 / 2 通道 50 条 /  │
│                3 通道 4 条（+6 播放配置逐行与 +4 恒等）      │
│  已解码描述符 5 个（id 1/2/8/11/14），其余 75 个在 ROM 里但  │
│  未解码 —— 编辑器改不了它们                                    │
└──────────────────────────────────────────────────────────────┘
```

**文案要点**：
- 卡片 2 的标题写「乐曲描述符」而不是「5 首」——因为 L1 落地后是 80 个；
  在 L1 没落地前必须写「5 首（另有 75 个描述符未解码，改不了）」。
- 一览**不再重复 159 行表**，改成上面的 5 行统计。

### 4.2 音效分派表（`#audio/structure/sound_id_table`）——主战场

**布局**：沿用 `editors.js:108-174` 的 `.split`（左表 + 右详情），但：

* 表格列改成**音频专用列**（`primary_columns` 由导出器给）：
  | 音效 id | 描述符 | 轨道数 | 通道 | 状态 |
  |---|---|---|---|---|

## 7. 验收标准（可被机器核对）

1. **打开 `#audio/structure/sound_id_table`，表格第一列的每一行都显示 `#0`…`#158`（0 基），
   且详情面板里不出现「第 N / 159 条」这种 1 基计数**；
   断言：表格 `#` 列文本集合等于 `{0..158}` 的字符串形式，且详情文本 `不包含 '第 '`，也不包含 '/ 159 条'`。
2. **`descriptor_ptr` 渲染成 `<select>` 而不是 `<input>`，且选项数 = 81**
   （80 个有内容描述符 + 1 个自定义项）；
   断言：`sound_id_table` 记录 0 的 `descriptor_ptr` 控件 `tagName === 'SELECT'`，
   选项数 `=== 81`，且存在一个选项文本同时含 `音频曲 1（m4a SongHeader）` 与 `0x536368`。
3. **指针反查可用**：选中音效 #1 后，详情里出现「被谁引用」块，且其中**至少 1 行**指向
   `音效 #1` 自己、`0` 行指向空哨兵（空哨兵那条应显示 79 行同址 id）。
   断言：`backReferencesByPointer(pack, 0x08536368)` 的结果里包含
   `{structureId:'sound_id_table', recordId:1}`；
   `backReferencesByPointer(pack, 0x08466068)` 的结果长度 `=== 79`。
4. **乐曲描述符的轨道指针渲染成一张表**：
   断言：`audio_song_2`（10 轨）打开后，`.slot-table` 的行数 `=== 10`，
   且表外（不在 `.slot-table` 内）的可编辑控件数 `< 10`（证明不是 10 个散装输入框）。
5. **空哨兵与未解码描述符被如实标注**：
   断言：音效 #19 的详情文本包含 `空哨兵` 与 `0x466068`；
   音效 #3 的详情文本包含 `未解码` 与 `0x5374B4`，且**不含**任何可编辑的轨道控件。
6. **域首页不再出现字面星号，且一览不再是 159 行**：
   断言：音频域首页文本 `不包含 '**'`；
   域首页「一览」区域内的 `<tr>` 数 `< 10`（统计表取代了逐行表）；
   文本包含 `79` 与 `空哨兵`。
7. **写回仍然只动该动的字节**（回归）：
   断言：把 `sound_id_table` 记录 3 的 `descriptor_ptr` 改成 `0x08536368` 后构建 ROM，
   `out.report.errors.length === 0`，且
   `out.bytes[0x465B70 + 3*8] === 0x68 && out.bytes[0x465B70 + 3*8 + 1] === 0x63`，
   同时 `0x465B70 + 3*8 + 4`（播放通道）与 `+6`（播放配置）两字节**保持原值**。

## 8. 附注：别的模块的问题（不在音频域范围内，未改）

* **`editors.js:284` 的 1 基计数**（F8）是通用编辑器的毛病，影响所有「记录下标本身就是 id」的表
  （音效 id、角色 id、忍术 id）。应由「结构表通用编辑器」那一块统一处理
  （加一个 `structure.id_is_index` 标记）。
* **`editors.js` 全文无键盘处理**（brief §4 的 G 条）：本规格要用的 `↑↓/Enter/Esc/J/K//`
  都得在通用编辑器层加，音频域只声明键位。

* **`fields.js` 没有「指针 → 结构记录」的关系种类**（F7）不止影响音频：
  `assets.js` 的指针表 A/B 同样是「指针指向结构记录」，补这个种类对素材域是同一笔收益。

* **`raw.js` 没有可寻址的 URL 形态**（今天只能靠 `ctx.state.view.params.offset` 读内存态），
  「在原始字节里看这个地址」的跳转要么补 `#raw/offset/<n>`，要么用 `ctx.openPanel` 传参。

## 9. 我最不确定的一个点

**「音效 id → 代码级使用点」要不要进本轮，以及为此需要的那个推定要不要先闭环。**

具体说：§1.5 已经逐字节证明函数指针表 1..11 槽是 11 条 `movs r0,#k` 的 thunk（k=1..11），
**但「k 就是 sound id」这一步是静态推定**，仓库里没有运行时证据（已闭环的是 `0x0809AAC0` 分派链的
运行时下标 102 / 1 / 154）。如果本轮就把它做成「音效 #k 的使用点 = 函数指针表第 k 槽」，
界面上必须标「推定」，而且一旦这个推定是错的，作者会被带偏。

我的建议：**本轮只做 L1（描述符层 + 指针反查 + 派生索引）与 L2（全 ROM 指针扫描，可选按钮），
把 L3（代码级使用点）单独留一轮**，并用仓库现成的 mGBA 探针
（`tools/l2_runtime_capture.py` 已有「sound-id-table」探针与 savestate 复用流程）
补一次运行时闭环：在这 11 个 thunk 上各下一次断点，读 r0 与命中时刻的表项，
确认 r0 = k 且命中的表项就是 `sound_id_table` 第 k 行。

请主代理拍板：**L3 是不是本轮做**（做的话是否接受「推定」标注，还是必须先补运行时证据）。
