## 1. 表几何（**修正旧版**）

```
0x54241C  角色定义表   id*0xB4   63 槽 (id 0..62)  -> 0x545068
0x545068  逐角色成长表 id*0x10   63 槽 (id 0..62)  -> 0x545458
0x545458  战斗记录表   16 字节   87 条             -> 0x5459C8
0x5459C8  12 字节「特性」记录表
```

- 三张表**首尾严格相接**：`0x545068 - 0x54241C = 0x2C4C = 63 × 0xB4`，
  `0x545458 - 0x545068 = 0x3F0 = 63 × 0x10`。
- **有效角色是 id 1..62（62 个）**，id 0 是**全 0 空槽**。
  旧版本文写「63 条有效（id 1..63）」是错的：id 63 落在 `0x545068`，
  那里已经是成长表的 id 0 槽（全 0）；成长表 id 1 在 `0x545078`
  （`AA 05 04 00 64 00 64 00 64 00 …`），即旧笔记里当作「id 1」的那条。
- 名字表 `0x599280` 是 **u32 指针表**（指向字体编码字符串），
  下标 0 = 「没有」占位，**下标 1..62 与模板 id 一一对应**
  （1 = 漩涡鸣人 … 62 = 岸本齐史），下标 63 又回到「没有」。
  `tools/character_templates.py` 已接 `tools/text_codec.py` 解名。

## 3. 12 字节头：字段语义

### 3.1 `+0x0A` = 体力（HP）基础值 —— **已证实**

```
0x0806DA3A: ldrh r0,[r1]              ; growth[0]  (1450/1480/1500)
0x0806DA3C: muls r0,r5,r0
0x0806DA40: bl   0x809c14c            ; /100
0x0806DA46: ldrh r1,[r2,#0xa]         ; 模板[+0x0A]
0x0806DA48: adds r1,r1,r0
0x0806DA4C: strh r1,[r6,#0xe]         ; 实例[0x0E] = 模板[0x0A] + growth[0]*(L-1)/100
0x0806DA92: ldrh r0,[r6,#0xe] ; ldr r1,[pc,#0xa8] (=999) ; cmp/bls/strh
```

鸣人 80 + 14.5/级，佐助 60 + 14.8/级，小樱 50 + 15/级；上限 999。
与 `notes/runtime-and-object-tables-20261020.md` 的旧推测一致，现在有指令级证据。

### 3.2 `+0x08` = 副属性 u16 —— **已证实（拷贝行为）**

```
0x0806DA4E: mov  r1,sb
0x0806DA50: ldrh r0,[r1,#8]           ; 模板[+0x08]
0x0806DA52: strh r0,[r6,#0xa]         ; 实例[0x0A]
```

取值 0..15（分布：0×12, 5×1, 6×5, 7×5, 8×1, 9×2, 10×20, 12×6, 13×8, 15×2）。
**它对应游戏里的哪项数值仍未证实**（只证明「是一个 u16、随角色不同、被 999 截断」）。

### 3.3 `+0x01..+0x06` = 六个属性的基础值 —— **已证实（拷贝+成长+上限）**

见 §2.2 表。分布：

| 字段 | 取值范围 | 分布 |
|---|---|---|
| `+0x01` | 3..25 | 3×1, 6×1, 7×1, 8×5, 10×29, 12×7, 13×6, 14×3, … |
| `+0x02` | 2..15 | 2×1, 5×1, 6×2, 7×8, 8×5, 10×37, 12×2, … |

## 4. 两段 4 字节条目区

每项 4 字节：`(id u8, 档位值 u8, 解锁等级 u8, pad u8)`。

两段的**区别只在第 1 字节指向的名字表**：

| 段 | 模板偏移 | 条目数 | 第 1 字节 = | 名字表 | 名表条数 |
|---|---|---|---|---|---|
| 忍术表 | `+0x0C` | 15 | **忍术 id** | `0x0859937C` | 87 |
| 技术表 | `+0x48` | 24 | **技术 id** | `0x085A7060` | 45 |

- 忍术表 id 实测范围 **1..86**（76 个不同值），正好落在 87 条名表内；
- 技术表 id 实测范围 **1..44**（44 个不同值），正好落在 45 条名表内。

### 4.1 第 3 字节 = 解锁等级（**本轮已证实**）

> **当 `档位值 == 0xFF`（未习得）且 `1 <= 解锁等级 <= 角色等级` 时，
> 实例里存的 `档位值` 被写成 `0`（= 已习得）；否则原样拷贝。**
> `解锁等级 == 0` 表示「没有等级门槛」，这类条目**永不**被这条规则改写。

建立函数（`0x0806D4A0`）在角色诞生时执行这条规则：

```
0x0806D4FA  ldrb r0,[r1,#0xd]     ; 模板[0x0D+4i] = 档位值
0x0806D4FC  cmp  r0,#0xff
0x0806D4FE  bne 0x806d518         ; 不是 0xFF -> 原样拷贝
0x0806D500  ldrb r0,[r1,#0xe]     ; 模板[0x0E+4i] = 解锁等级
0x0806D502  cmp  r0,#0
0x0806D504  beq 0x806d518         ; 门槛 0 -> 原样拷贝
0x0806D506  ldrb r1,[r5,#1]       ; 角色等级
0x0806D508  cmp  r0,r1
0x0806D50A  bhi 0x806d518         ; 门槛 > 等级 -> 原样拷贝
0x0806D50C  strb r3,[r2,#0x15]    ; 否则写入 0（已习得）
```

**升级时的同一条规则**在 `0x080899EC`（被 `0x08089B7E` 调用）里重演，
并且这次会**把新解锁的条目追加到列表**：

```
0x08089A0C  ldrb r2,[r1,#0x14]   ; 实例[0x14+4i] = 忍术 id
0x08089A10  cmp  r2,#0
0x08089A12  beq 0x8089a60        ; id == 0 -> 跳过
0x08089A14  ldrb r0,[r1,#0x15]   ; 实例[0x15+4i] = 档位值
0x08089A16  cmp  r0,#0xff
0x08089A18  bne 0x8089a60        ; 已习得 -> 跳过
0x08089A32  mov  r1,r8            ; r8 = &模板[id]
0x08089A34  adds r0,r1,r3         ; r3 = i*4
0x08089A36  ldrb r1,[r0,#0xe]     ; 模板[0x0E+4i] = 解锁等级
0x08089A38  cmp  r1,#0
0x08089A3A  beq 0x8089a60        ; 门槛 0 -> 永不自动解锁
0x08089A3C  ldrb r0,[r6,#1]       ; 角色等级
0x08089A3E  cmp  r0,r1
0x08089A40  blo 0x8089a60        ; 等级 < 门槛 -> 还没解锁
0x08089A48  strb r0,[r2,#0x15]    ; 档位值 0xFF -> 0（已习得）
0x08089A52  ldrb r0,[r2,#0x14]    ; 取出忍术 id
0x08089A54  strb r0,[r1]          ; 追加到输出列表
```

技术表那段（`i = 0..23`）完全同构（`0x08089A74`…`0x08089AA8`），
唯一区别是追加前会**置上最高位**：

```
0x08089AA2  ldrb r1,[r4]          ; 技术 id
0x08089AA4  movs r2,#0x80
0x08089AA6  orrs r1,r2            ; id | 0x80
0x08089AA8  strb r1,[r0]          ; 追加
```

升级界面用这个最高位区分两段（`0x08089DD2 ldrsb` 得到负数 = 技术）：

```
0x08089DD8  ldr  r0,[pc,#0x10]    ; 0x0859937C 忍术名表
0x08089DF0  ldr  r0,[pc,#0x30]    ; 0x085A7060 技术名表
0x08089DF4  ands r1,r2,#0x7f      ; 去掉 0x80 标记
```

**这解决了旧版本「门槛字节没有可观测效果」的疑问**：门槛就是解锁等级，
旧结论之所以看不到效果，是因为当时没有找到调用 `0x080899EC` 的升级路径。

`tools/character_templates.py --level N` 会算出该等级下的生效值。

### 4.2 第 2 字节 = 档位值（`0/1/3/0xFF`）

| 段 | 取值分布（全 62 条模板） | 含义 |
|---|---|---|
| 忍术表 | `0`×721, `1`×139, `3`×13, `0xFF`×57 | `0` = 空槽；`1`/`3` = 档位；`0xFF` = **未习得** |
| 技术表 | `0`×1027, `1`×3, `3`×26, `0xFF`×432 | 同上 |

- `0xFF` = 未习得（升级时按 §4.1 改成 0）。
- `1` / `3` 的**游戏内含义**（是「使用次数」「威力档」还是别的）**未证实**；
  只能证明它是 u8 档位值。
- 旧版本说「模板里 value = 1 / 3 / 5」——**5 是错的**，实测没有 5，
  取值只有 `0/1/3/0xFF`。

### 4.3 技术表的 id → 12 字节「特性」记录表 `0x5459C8`（**已证实**）

```
0x0806D6C8: ldrb r1,[r1]            ; 实例[0x50+4*i] = id A
0x0806D6CC: ldrb r0,[r0]            ; 实例[0x51+4*i] = 档位值 B
0x0806D6CE: subs r0,#1 -> r2        ; r2 = B - 1
0x0806D6E0: lsls r0,r1,#1 ; adds r0,r0,r1 ; lsls r0,r0,#2   ; A*12
0x0806D6E6: ldr  r1,[pc,#0x20]       ; 0x085459C8
0x0806D6E8: adds r1,r0,r1           ; rec = 0x085459C8 + A*12
0x0806D6EA: ldrh r0,[r1,#6]         ; rec.growth (u16)
0x0806D6EE: muls r3,r2,r3           ; growth * (B-1)
0x0806D6F2: ldrh r2,[r1,#2]         ; rec.base (u16)
0x0806D6F4: adds r0,r0,r2           ; 总量 = base + growth*(B-1)
0x0806D6FA: ldrb r0,[r1]            ; rec.type (u8)
```

12 字节记录布局：`(type u8, pad u8, base u16, pad u16, growth u16, pad u16)`。
例：`A=1 -> type=1 base=30 growth=30`；`A=2 -> type=3 base=1 growth=1`；
`A=15 -> type=0x14 base=30 growth=30`。

> 注意：**同一个技术 id 同时是 `0x5A7060` 名字表的下标和 `0x5459C8` 特性表的下标**。
> 名字侧由 `0x08089DF0` 证明，特性侧由 `0x0806D6E0` 证明。

`type` 的作用分**两个循环**（`0x0806D6B8` 对 24 个条目各算两遍）：

- **循环 1**（`0x0806D6C0`）：`type == 0x0E` → `0x0806D70C`；
  `type == 0x10` → `0x0806D72A`；其余 type 直接跳过。
- **循环 2**（`0x0806D760`）：`type - 0x0D <= 6` 时查跳转表 `0x0806D7B8`：
  `0x0D→0x0806D7D4`、`0x0F→0x0806D7F2`、`0x11→0x0806D7FC`、
  `0x12→0x0806D820`、`0x13→0x0806D832`；`0x0E` / `0x10` 在这里被跳过
  （已由循环 1 处理）。

**type 的具体含义未解。**

### 4.4 成长量与三个结算分支

成长量 `r2 = rec.base + rec.growth × (B − 1)`（见 §4.3 的指令序列）。

| 分支 | 作用 | 上限 |
|---|---|---|
| `0x0E`（`0x0806D732`，循环 1） | 属性 C **按百分比**成长：`属性C += r2 × 属性C / 100` | 99 |
| `0x0D` / `0x0F` / `0x11`（`0x0806D804`，循环 2） | 属性 C **绝对值**成长：`属性C += r2` | 99 |
| `0x12`（`0x0806D820`，循环 2） | 属性 C 绝对值成长，条件 `(stat[2..3] & 0x3F) == 0x1A` | 无 |
| `0x13`（`0x0806D832`，循环 2） | 属性 E 绝对值成长 | 999 |

`0x0F` / `0x11` 分支还带一条额外条件：把 `(角色id, 等级)` 拼成的 u16
与字面量 `0x0101`（id 1 / level 1，`0x0806D7F8`）或 `0x0105`
（id 5 / level 1，`0x0806D7C`-`0x0806D81C`）比较，相等才生效。

即技术表的 `档位值`（B）参与成长结算：`r2 = B − 1` 是 growth 的**档位倍率**，
成长量 = `rec.base + rec.growth × (B − 1)`。

> 旧版本在这里说「门槛字节没有可观测效果」——**该说法作废**（见 §4.1）。

### 4.5 忍术表的 id / 档位值消费者 —— **本轮已定位**

- **id**：升级界面 `0x08089DD8` 用它查忍术名表 `0x0859937C`；
  战斗配置搬运 `0x0809273C` 也用 `config[6]` 查同一张表。
- **档位值**：`0x08094564 ldrb r0,[r2,#0x15]`（实例 `+0x15+4i`）被读，
  用来筛掉「未习得」的忍术（`0x0809456E cmp r0,#0xff`）；
  `0x0809234E ldrh r0,[r4,#0xc]` 把它与实例 `+0x38` 的 u16 比较。
  **「1」和「3」分别代表什么，仍未证实。**

### 4.6 两段的 id 不是位置序号

- 忍术表 id 实测 1..86（不连续）；技术表 id 实测 1..44（不连续）。
- 旧版本写的「id 2 的条目区 2 最后一个 index 是 `0x19`（25）」与本轮实测
  （技术表最大 id = 44）不一致，说明旧读数有误。

## 5. 忍具列表 `+0xA8`（9 字节）—— **本轮已定案：是忍具 id**

- 9 个 u8，每项是一个**忍具 id**，`0` 表示空（`0x0806D594` 直接跳过）。
- 写入实例 `+0xB1..+0xB9`，同时 `+0xB0` 计数（`0x0806D5A6`/`0x0806D5AC`）。
- 每项在写入前会调用 `0x0808FA34`；返回非 0（背包满）则跳过。
- **id 空间 = 忍具 id（名表 `0x08599634`，94 条）**，因为
  `0x0808FA34` 正是奖励类别 0（忍具）用的同一个「入背包」函数
  （`0x0809736E bl #0x0808FA34`），它把 per-id 计数放在
  `0x02022E30 + 0x11A5 + id`，并用 `0x02022E30 + 0x11A4` 的字节做总件数上限（98）。
- 实测：**62 条模板里出现的忍具 id 只有 `1`**（= 十字手里剑），
  其余 8 个槽全是 0。

## 7. `0x545458` 的读法 —— **结论**

> **`0x545458` 是一张 16 字节记录表（87 条），不是 u32 指针表，也不是 u32 技能表。**

**证据（消费者 `0x0806D85C`）**：

```
0x0806D866: ldr  r2,[pc,#0x20]       ; r2 = 0x08545458
0x0806D868: lsrs r0,r0,#0x14         ; r0 = (arg0 & 0xFF) << 4 = arg0 * 16
0x0806D86C: adds r0,r0,r2           ; &record[arg0]
0x0806D86E: ldm  r0!,{r2,r6,r7}      ; 取 12 字节
0x0806D870: stm  r1!,{r2,r6,r7}      ; 写 12 字节
0x0806D872: ldr  r0,[r0]            ; 再取 4 字节
0x0806D874: str  r0,[r1]            ; 再写 4 字节   -> 共 16 字节
```

**交叉验证**：`0x545458 + 348*4 = 0x5459C8` —— 第三方所谓「348 个 u32」
复制的正好是这 1392 字节，即 **87 条 16 字节记录**（`0x545458..0x5459C7`），
而 `0x5459C8` 正是 §4.2 的 12 字节特性表起点。
第三方 `runtime.c` 里的 `R8(0x0203E900 + 5*16 + 4)` 也印证了 16 字节步长。

**记录字段表（本轮补全）**：

| 偏移 | 大小 | 语义 | 证据 |
|---|---|---|---|
| `+0x00` | u8 | **未解**（被搬到「已习得忍术」表项 `+0x04`） | `0x08094582 ldrb r0,[r0]` |
| `+0x01` | u8 | **未解**（被搬到「已习得忍术」表项 `+0x05`） | `0x08094592 ldrb r0,[r0,#1]` |
| `+0x02` | u16 | **位域**：取 `& 0x1800` 再 `>>5` 得到 0..0xC0 的档位/点数 | `0x080922D8 ldrh r0,[r0,#2]` → `0x080922DE ands r1,r0,#0x1800` → `0x080922E4 lsrs r5,r0,#0x1f` |
| `+0x03` | u8 | **未解** | — |
| `+0x04..+0x09` | 6×u8 | **六个随等级成长的字节字段** | `0x0806D8B2 / 0x0806D8C0 / 0x0806D8CE / 0x0806D8DC / 0x0806D8EA / 0x0806D8F8` |
| `+0x0A` | u8 | **未解** | — |
| `+0x0B` | u8 | **未解** | — |
| `+0x0C` | u8 | **成长类型**：`0`=不成长，`1..6`=分别成长 `+0x04..+0x09`，`7`=不成长 | `0x0806D876 ldrb r0,[r3,#0xc]` + 跳转表 `0x0806D890` |
| `+0x0D` | u8 | **未解** | — |
| `+0x0E` | u16 | **每级成长量** | `0x0806D8AC ldrh r1,[r3,#0xe]` |
| `+0x0F` | u8 | **未解** | — |

- 成长量 = `(等级 − 1) × 记录[+0x0E]`，写回被 `+0x0C` 选中的那个字段
  （`0x0806D8AC`：`ldrh r1,[r3,#0xe]` → `subs r0,r4,#1` → `muls r0,r1,r0`
  → `ldrb r1,[r3,#4]` → `strb r0,[r3,#4]`）。
- 第三方把「记录 5 的 `+0x04`」称作 `basicAttackPower`
  （`third_party/.../runtime.c`： `R8(0x0203E900+5*16+4)=CAMPAIGN_BASIC_ATTACK`），
  与「`+0x04` 是会被等级成长的数值」一致；**但本仓库不采信第三方命名**
  （仓库规则：第三方结论必须在本 ROM 上重新验证），所以仍叫
  `stat_growth_target_N`。
- `+0x0C` 的分布：0×41, 1×23, 2×1, 4×16, 5×3, 6×3（无 3、无 7）。
- 顺带：`notes/addresses.md` 记的「value 字段常含 612」其实是 `+0x06/+0x07`
  这两个字节凑出来的（记录 1：`01 05 02 04 00 01 64 02 …` → `0x64,0x02` = 612）。

### 7.1 记录表与角色模板的关系（本轮定案）

> **`0x545458` 的下标就是「忍术 id」**，与忍术名表 `0x0859937C`（87 条）
> 是同一个下标空间。

```
0x0809457C  ldrb r0,[r2,#0x14]     ; r2 = 实例 + i*4 -> 实例[0x14+4i] = 模板的忍术 id
0x0809457E  lsls r0,r0,#4          ; 忍术 id * 16
0x08094580  add  r0,r8             ; r8 = 0x08545458
0x08094582  ldrb r0,[r0]           ; record[+0x00]
0x08094584  strb r0,[r1,#4]        ; 写进「已习得忍术」表项
0x0809458C  ldrb r0,[r2,#0x14]     ; 同一个忍术 id
0x0809458E  lsls r0,r0,#4
0x08094590  add  r0,r8
0x08094592  ldrb r0,[r0,#1]        ; record[+0x01]
0x08094594  strb r0,[r1,#5]
```

**交叉验证**：
- 忍术名表 `0x0859937C` 有 **87** 条（`0x59937C + 87*4 = 0x5994D8`，
  正好是人物名表 `0x599280`（150 条）的末尾）；
- 忍术记录表 `0x545458` 有 **87** 条（`0x545458 + 87*16 = 0x5459C8`，
  正好接上 12 字节特性表）；
- 模板的忍术 id 实测 **1..86**，正好落在 0..86 里。

**仍未解**：`+0x03 / +0x0A / +0x0B / +0x0D / +0x0F` 五个字节的语义；
`notes/addresses.md` 里把它写成「8 个 u16」并给出「32 条」——**条数应为 87**，
且它更像**字节序**字段而非 u16
（`u16[3]` 在不同记录里出现 100 / 356 / 612 / 33631 等混合值，不是干净的 u16 量纲）。

## 9. 对续作写回的意义

- **模板可以整条复制**：`0x54241C + id*0xB4` 共 180 字节 = 12 字节头
  + 两段条目区 + 9 字节道具列表，与第三方编辑器的做法一致；
  但**只有 id 1..62 有效**，且 `0x545068 + id*16` 必须一起复制。
- **`0x545068` 的 u16[0]（体力增长）与 u16[1]（属性 F 增长）随 id 变化**，
  复用时必须按新 id 重算，不能照抄 —— 这一条现在有了确切语义（§6）。
- **不要**依据本文去改战斗配置的 `+0x10`：原版那里全是 0，
  游戏是运行时从模板套用的（见 `notes/runtime-and-object-tables-20261020.md`）。
- 改属性时要注意运行时 clamp：属性 A/B/C ≤ 99、D ≤ 5、E/F ≤ 9、体力/副属性 ≤ 999，
  **写大了会在运行时被截断**。
- 改条目区的「档位值」时注意 `0xFF` 语义：它是「**未习得**」，
  在角色等级 ≥ 解锁等级时会被写成 0（§4.1）。
- 改「解锁等级」时注意 `0` 的含义是「**没有等级门槛**」，不是「等级 0 解锁」。
- 改忍术 id / 技术 id 时必须同时保证 id 落在对应名表容量内
  （忍术 0..86 → `0x0859937C`；技术 0..44 → `0x085A7060`），
  否则运行时会读出乱指针（`0x08089DDC lsls r1,r1,#2` 无边界检查）。
- 改忍具 id 时必须落在 `0x08599634` 的 94 条内
  （`0x0808FA34` 的 per-id 计数数组按 id 索引）。
