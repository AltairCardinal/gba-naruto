## 0. 一句话

在「剧情触发」这张卡片里，渲染一份**按触发块**排列的列表：一行 = 「一组触发条件 → 它选中的那一段对白」；条件里的定宽操作数给输入框，对白用现有的 `scripttext.js` 改写（**第十六轮是等长改写；第十七轮起长度不限**）；没载入 ROM 时降级成指针表，视图不挂。

### 1.3 「战场事件表」的结构：**开头是连续的 0x32 事件链**

对 46 个场景逐个反汇编（`rom-editor/js/storyvm.js` 的 `scanScript`）：

| 项 | 数值 | 出处 |
|---|---|---|
| 每个 events 剧本开头的 0x32 链 | **46/46 关成立**（链是剧本的前缀，后面才是别的指令） | `build/battle-story-trigger-census.txt` 逐场景表 + 独立走查 |
| 链长（= 一关有几段剧情） | min **2** / 中位 **10** / max **17**，合计 **400** | census |
| 每个 0x32 的 u32 载荷 @+1 指向的地址 | **46/46 关都落在本剧本内某条指令的起点上** | 独立走查 |
| events 剧本里的文本指令（0x01 / 0x20） | min 3 / 中位 25 / max 66，合计 **1118** | census |
| events 剧本里的 0x33 / 条件指令 / 0x13 | **全为 0** | census |

**样例（场景 40，events，ROM 0x0805B0F6）**：

```
0x0805B0F6  0x32 事件链选择   载荷 0x0805B100   → 第 1 段
0x0805B0FB  0x32 事件链选择   载荷 0x0805B252   → 第 2 段
0x0805B100  0x12 设置对话框尺寸

0x0805B107  0x01 显示文本  …
…
0x0805B251  0x00 结束脚本
0x0805B252  0x02 选择对话框          ← 第 2 段开始
0x0805B256  0x08 设置头像与说话人
0x0805B258  0x01 显示文本  …
0x0805B288  0x00 结束脚本
```

⇒ **「一段剧情」= 链上的一条 0x32 指向的那块字节**，块尾是 `0x00 结束脚本`。块与块的边界由链给出，**不是猜的**。

### 1.4 「战场事件逻辑」的结构：条件 → 压一个**事件 id**

| 项 | 数值 | 出处 |
|---|---|---|
| 0x33 压队列值 | min 2 / 中位 10 / max 17，合计 **407** | census |
| 条件指令 0x34..0x39 | min 0 / 中位 26 / max 56，合计 **1013** | census |
| 0x37 置/清战斗标志 | 合计 **196** | census |
| 0x32 事件表项 | 合计 **21**（只出现在场景 32..38，见 §1.6） | census |
| 文本指令（0x01 + 0x20） | 合计 **21**（全是 0x01；0x20 = 0） | census + 独立走查 |
| 0x13 双段文本 | **0** | 独立走查 |
| 0x0D 调用子脚本 | **0**（本 ROM 一次都没用过） | 独立走查 + `notes/story-vm-opcodes-20261020.md` §3（「本 ROM 未使用此指令」） |

> **订正一处标签**：census 里那行写的是「0x13 子脚本」，**标签错了** —— 十六进制 `0x13` 是**双段文本**，**调用子脚本是 `0x0D`**（仓库的十进制编号习惯容易看串）。census 的 `count[0x13]` 实际数的是双段文本。两个操作码在 logic / events 剧本里**都是 0 次**，所以**数字不受影响**；但全 202 个剧本里 `0x13` 双段文本共出现 **28** 次（全在 before / after 里），`0x0D` 仍是 **0**。

**全量操作码普查（202 个剧本，logic / events 两类拆开）** —— 这张表是本次设计的总底账，也顺带钉死了「哪些操作码只出现在战斗剧本里」：

| opcode | 全部 202 个剧本 | logic（46 个） | events（46 个） |
|---|---|---|---|
| 0x32 事件链选择 | 421 | **21** | **400** |
| 0x33 压入事件队列值 | 407 | **407** | **0** |
| 0x34 回合条件 | 374 | 374 | 0 |
| 0x35 复合条件 | 196 | 196 | 0 |
| 0x36 指定角色在场 | 213 | 213 | 0 |
| 0x37 置/清战斗标志 | 196 | 196 | 0 |
| 0x38 测试战斗标志 | 204 | 204 | 0 |
| 0x39 子配置匹配 | 26 | 26 | 0 |
| 0x01 显示文本 | 7217 | 21 | 1074 |
| 0x20 带说话人的对话 | 190 | 0 | 44 |
| 0x13 双段文本 | 28 | **0** | **0** |
| 0x0D 调用子脚本 | **0** | 0 | 0 |

⇒ **0x34..0x39 只出现在 logic 剧本里，0x32 只出现在 events 剧本里（除了场景 32..38 那 21 条）**；⇒ logic / events 的职责分工是**数据层面就成立的**，不是推测。

**样例（场景 40，logic，ROM 0x0805B0D1）**：

```
0x0805B0D1  0x34 回合条件  比较器=3(>=) b=1 c=1  目标 0x0805B0F5
0x0805B0D9  0x34 回合条件  比较器=3(>=) b=2 c=0  目标 0x0805B0E3
0x0805B0E1  0x33 压入事件队列值  value=1
0x0805B0E3  0x34 回合条件  比较器=3(>=) b=3 c=0  目标 0x0805B0F5
0x0805B0EB  0x34 回合条件  比较器=5(<=) b=1 c=0  目标 0x0805B0F5
0x0805B0F3  0x33 压入事件队列值  value=2
0x0805B0F5  0x00 结束脚本
```

⇒ **「一个触发条件组」= 到下一条 0x33 为止的一段条件指令**；0x33 压进去的**值**就是它要触发的**事件 id**。

### 1.5 事件 id ↔ 剧情段：**链是 1 基的**（本设计最关键的一条）

0x32 的 handler 在 ROM 里长这样（capstone 反汇编 `0x08097CF8` 起的 0x30 字节）：

```
0x08097CF8: movs r4, #0              ; r4 = 链游标，从 0 开始
0x08097CFA: ldr  r1, [pc, #8]        ; 字面量 0x020311D4（剧情 state 块）
0x08097CFC: adds r2, r1, #0
0x08097CFE: adds r2, #0x1d           ; r2 = state + 0x1D（事件队列数组）
0x08097D00: b    #0x08097D0C
0x08097D0C: ldrb r0, [r7]            ; 取指
0x08097D0E: cmp  r0, #0x32
0x08097D10: beq  #0x08097D14
0x08097D12: b    #0x08097E2C          ; 不是 0x32 ⇒ 走出链
0x08097D14: ldrb r0, [r1, #0x1c]     ; state[0x1C]（队列读游标）
0x08097D16: adds r0, r0, r2
0x08097D18: ldrb r0, [r0]            ; 队列[读游标] = 压进去的值 V
0x08097D1A: subs r0, #1              ; ★★ V - 1
0x08097D1C: cmp  r0, r4              ; 与链游标 r4 比
0x08097D1E: bne  #0x08097D08         ; 不匹配 ⇒ 跳过这条 0x32（r7 += 5）
0x08097D20: adds r0, r7, #1
0x08097D22: bl   #0x8096ea4           ; 读 u32 载荷（绝对地址）
0x08097D26: adds r7, r0, #0           ; r7 = 目标 ⇒ 跳进那一段
0x08097D08: adds r7, #5               ; 链上前进一格
```

⇒ **压入的值 V 选中链上第 V 条**（V=1 → 第 1 条，V=2 → 第 2 条）。**1 基**，不是 0 基。

对账（46 关逐关核对）：

| 情形 | 关数 | 压入的值 | 链长 | 结论 |
|---|---|---|---|---|
| 一一对应 | **39** | {1..N}（顺序可以乱，例：场景 6 压 1,2,3,7,8,9,4,5,6,10,11,12） | N | 全部命中 |
| 多压一个 0 | **7**（场景 **32..38**） | {0,1,2,3} | **3** | 值 0 **选不中任何一段**（0−1 = 0xFF，与链游标 0/1/2 都不等） |

⇒ **407 = 400 + 7**：多的 7 个正好是场景 32..38 各多压的那个 0。

### 1.6 logic 与 events 是**同一段字节的相邻部分**

| 情形 | 关数 | 关系 |
|---|---|---|
| events 根指针 = logic 剧本的**结束地址**（delta = logic 剧本字节长度） | **39** | 紧挨着 |
| events 根指针 = logic 剧本**起点 + 8** | **7**（场景 32..38） | **指到 logic 剧本内部**（8 = 四条 0x33 压队列指令的长度，4×2） |

- 出处：用 `scanScript` 取 logic 剧本首末指令，与 `story_events_root` 的指针相减，逐关核对。
- ⇒ 设计含义：不能把 logic 与 events 当成两份互不相干的剧本。**场景 32..38 里，「事件表」就是「事件逻辑」的中间那一截**（logic = 4 条压队列 + 事件链 + 3 段对白；events 根指到事件链开头）。
  - 样例（场景 32）：logic 根 0x05A90C = `33 00 / 33 01 / 33 02 / 33 03 / 32…32…32 / 0x02 / 0x08 / 0x01 文本 / 0x00 / …`；events 根 0x05A914 = 三个 0x32 起（正好跳过那四条 0x33）。

### 1.7 条件指令的判定（逐条反汇编 `0x08097D4C` 起）

#### 0x34 回合/相位条件跳转（长度 8）

```
0x08097D4C: adds r0, r7, #4
0x08097D4E: bl   #0x8096ea4      ; 读 u32 目标 @+4 → r5
0x08097D54: ldrb r0, [r7, #3]    ; c @+3
0x08097D56: bl   #0x808a1a4      ; 相位检查
0x08097D5C: cmp  r4, #1
0x08097D5E: bne  #0x8097dc0      ; 不满足 ⇒ 不跳
0x08097D60: ldrb r0, [r7, #1]    ; 比较器 @+1
0x08097D62: cmp  r0, #0xff
0x08097D64: beq  #0x8097d7e      ; 0xFF ⇒ 跳过比较（只靠相位）
0x08097D66: adds r4, r0, #0
0x08097D68: bl   #0x808a198      ; 取「回合计数」
0x08097D6E: lsls/lsrs r1, #0x18  ; u8 截断
0x08097D72: ldrb r2, [r7, #2]    ; b @+2
0x08097D74: adds r0, r4, #0
0x08097D76: bl   #0x8097210      ; 比较器分发表
0x08097D7A: lsls/lsrs r4, #0x18
0x08097D7E: cmp  r4, #1
0x08097D80: bne  #0x8097d84
0x08097D82: b    #0x8097b20      ; 跳到 r5（= @+4 的 u32）
```

两个被读的字节（字面量池在 `0x0808A1A0` / `0x0808A1B8`，都是 **0x0202680C**）：

| 读点 | 读的是 | 是什么 |
|---|---|---|
| `0x0808A198`：`ldr r0,[pc,#4]` → `ldrb r0,[r0]` | **0x0202680C 的首字节** | **回合计数** —— 仓库已定案（`notes/battle-tables.md` §「2026-10-21 追加：`0x0202680C` **就是回合计数**」；`notes/completion-audit-20261020.md` 同条；运行时证据 `tools/closure_round_probe.py`） |
| `0x0808A1A4(c)`：`ldr r1,[pc,#0xc]` → `ldrb r1,[r1,#2]` | **0x0202680E** | **仓库没有名字**（见 §1.9） |

比较器：`0x08097210(comparator, value, b)` —— `cmp r0,#5 / bhi` ⇒ 比较器 id > 5 直接返回 0；否则走 `0x08097230` 的 6 项表。仓库已全解码（`notes/story-vm-opcodes-20261020.md` §3.1）：**0 `==` / 1 `!=` / 2 `>` / 3 `>=` / 4 `<` / 5 `<=`，无符号，两个操作数都按 u8 取值**。

⇒ **0x34 = 「相位字节（0x0202680E）== c，且 回合计数按比较器与 b 比较成立」时才跳转。** 比较器 0xFF 时只看相位。

> **与 `notes/evidence/battle-story-trigger-structure-20261022.md` §7 的分歧（以本文为准）**：那份证据笔记写「`0x34` 的 @+2（b）到底跟什么比：`0x0808A198` 取的是哪个值，**仓库没定案**」。
> 本文把这一步**做到了字节级**：`0x0808A198` 的 `ldr r0,[pc,#4]` 取的字面量在 **`0x0808A1A0`，值 = `0x0202680C`**，接着 `ldrb r0,[r0]` 读的就是 **`0x0202680C` 的首字节**。
> 而 **`0x0202680C` = 回合计数** 是仓库**已经定案**的（`notes/battle-tables.md` §「2026-10-21 追加：`0x0202680C` **就是回合计数**」，运行时证据 `tools/closure_round_probe.py`：回合真的推进时该字节从 1 变 2）。
> ⇒ **「跟什么比」不是没定案，是定案了**：比的是**回合计数**。真正没定名的只有 **c 那个字节（`0x0202680E`）**（见 §1.9）。
> 差异的来源：`0x0808A1A0` / `0x0808A1B8` 这两个字面量在 `0x0808A198` 附近的**字面量池**里，反汇编工具默认会把它们当指令显示，得手工读字节才能拿到。

本 ROM 数据里的取值域：**比较器 {3, 5}（>= / <=）、b {1..12, 14}、c {0, 1}**。

#### 0x35 复合条件跳转（长度 9）

```
0x08097D8E: ldrb r0, [r7, #2]   ; b
0x08097D90: ldrb r1, [r7, #3]   ; c
0x08097D92: ldrb r2, [r7, #4]   ; d
0x08097D94: bl   #0x808a1c4     ; f(b,c,d) → 0/1
0x08097D9A: ldrb r0, [r7, #1]   ; a
0x08097D9C: cmp  r4, r0
0x08097D9E: bne  #0x8097da2
0x08097DA0: b    #0x8097b20     ; 跳到 @+5 的 u32
```

⇒ **0x35 = 「f(b,c,d) == a 时跳转」**。本 ROM 里 **a 恒为 0** ⇒ 实际语义是「**复合条件不成立**时跳转」（else 分支）。
取值域：**a {0}（只有一个值）、b {0, 2}、c {1,2,3,7,12}（5 个值）、d {1..41, 55}（38 个不同取值）**。`f` 的三个参数的具名语义仓库未定案（仓库只定了「求值 3 元条件，与 @+1 的期望值比较」）。

#### 0x36 指定人物在场条件跳转（长度 8）

```
0x08097DAE: ldrb r0, [r7, #2]   ; b
0x08097DB0: ldrb r1, [r7, #3]   ; c
0x08097DB2: bl   #0x808a420     ; 在场检查(b, c) → 0/1
0x08097DB8: ldrb r1, [r7, #1]   ; a
0x08097DBA: cmp  r4, r1
0x08097DBC: bne  #0x8097dc0
0x08097DBE: b    #0x8097b20     ; 跳到 @+4 的 u32
```

⇒ **0x36 = 「在场检查的结果 == a 时跳转」**。仓库对这条的结论是 proved：「`0x808A420` 遍历战斗单位槽 `0x020240C0` 查该角色是否在场」（`notes/story-vm-opcodes-20261020.md` §3）。
取值域：**a {0,1}、b {0,1}、c {1..35}（25 个不同取值）**。
**注意**：仓库**没有**给 a / b / c 分别起名。a 可以读作「期望结果（1 = 在场）」，c 像角色 id；b 的作用未命名。

#### 0x37 / 0x38 战斗标志（长度 3 / 7）

- **0x37**（`0x08097DC4`）：`ldrb r0,[r7,#1]`（模式）、`ldrb r1,[r7,#2]`（标志）→ `bl 0x808a490` → 改 `0x020311D4 + 4*(id>>29)` 的 `bit(id&0x1F)`。取值域：**模式 {1}、标志 {0..11}**。
- **0x38**（`0x08097DCE`）：先读 u32 目标 @+3；模式 @+1；模式 == 0 走 `0x0808A4D8`，否则走 `0x0808A504`；结果 == 1 时跳转。取值域：**模式 {0}、标志 {0..11}**。
- ⇒ 本 ROM 里 **0x37 的模式恒为 1、0x38 的模式恒为 0**；**模式的具体取值（1 = 置还是清、0 = 测还是不测）仓库没有命名**，所以界面上只显示「模式 = 1」这类原始事实 + 一句说明。0x38 的行为是确定的：**读到的位域为 1 时跳转**（handler：读位域，返回 1 才跳）。
- ⇒ 这套标志位空间是**第三套**（`notes/story-vm-opcodes-20261020.md` §3.2）：`0x020314F0`（剧情标记，0x09/0x0A/0x0B/0x0C）/ `0x02031510`（0x19/0x15/0x34）/ **`0x020311D4`（战斗标记，0x37/0x38）** —— 三套分开，不要混。

#### 0x39 子配置匹配（长度 6）

`0x08097DF6` 起：读 u32 目标 @+2，取 `state[0x19]` 与 @+1 的 id 比较，相等才跳。仓库结论：0x1F 设的 `state[0x19]` 就是「子配置 ID」，0x39 用同一字段做匹配。取值域：**id {0, 1}**。

### 1.8 触发块的典型形态

绝大多数关卡的 logic 剧本是这个形状（场景 1 的前 20 条）：

```
0x34 0x36 0x36 0x36 0x36 0x34  0x33 push 1
0x36 0x36 0x36 0x34 0x34        0x33 push 2
0x36 0x36 0x36 0x34 0x34        0x33 push 3
0x35 0x38 0x37                   0x33 push 4
0x35 0x38 0x37                   0x33 push 5
…
```

读法（**人话**）：
- 一串条件指令 = 「这一组触发的前提」；每个条件指令自带一个**跳转目标**（绝对地址）。
- `0x35` 在本 ROM 里恒为「条件**不**成立就跳」；`0x38` 是「战斗标志已置就跳」；`0x37` 是「把战斗标志置上」。
- 于是 `0x35 0x38 0x37 0x33 push V` 读作：**「这一组条件都不成立、且战斗标志还没置上 ⇒ 置上标志并触发第 V 段剧情」**（一个「只触发一次」的常见写法）。
- 条件指令的跳转目标落在**下一个触发组之后**或**脚本末尾** —— 也就是「不满足就跳过这一组」。

### 1.9 一个**没有定案**的字节（必须照实说）

0x34 的 c 字节与 **0x0202680E** 比较。这个字节在仓库里**只有一处**提到：`notes/evidence/callback-dispatch-runtime-20261021.md` §3 —— 战斗主循环 `0x080736B0`..`0x080736B8` 每帧把它 `eors #1` 翻转一次（字面量 `0x0202680C`，写回 `r1+2` ⇒ `0x0202680E`），该次运行时观察到它在 `0x0E / 0x0F` 之间交替。

**但本 ROM 所有 0x34 指令里的 c 只有 {0, 1}**，与那个观测对不上 —— 若该字节在剧情 VM 判定时真是 0x0E/0x0F，所有 0x34 都不会成立，整套触发机制就是死的。所以「0x0E/0x0F」那次观测**不适用于剧情 VM 的判定时刻**，而仓库**没有**解释它为什么不适用。

⇒ **结论：0x0202680E 这个字节仓库没有可用命名。** 界面里只能照实写「相位字节」（仓库笔记对 0x34 的措辞是「回合/相位条件跳转」），并在提示里说明「这个字节仓库还没定名」。**不要**猜它是什么。

## 2. 设计决定

### D1. 「剧情触发列表」的一行 = **一个触发块**

**决定**：一行 = 「**一组触发条件** → **它选中的那一段对白**」。触发块由 logic 剧本的一组条件指令 + 那条 0x33 压的事件 id + events 剧本里被选中的那一段组成。

**理由**：

1. 作者的四个问题（什么条件下会触发 / 触发的是哪一段 / 这段有几句对白 / 改哪里）**只在这一层才有答案**。剧本级（logic 一条、events 一条）只能回答「触发的是哪一段」，答不出「什么条件下」。
2. 触发块**在数据上是可认的**，不是硬凑的：logic 剧本里「到 0x33 为止的一段条件指令」天然是一个条件组；0x33 的值 V 按 1 基规则选中 events 链上第 V 条（§1.5 已用字节证明）。
3. **两层都要，但分层不是「剧本 → 触发块」这种嵌套**：剧本级信息量太少（每关只有 2 条），做成行没有意义。它退化成**列表顶部的两个摘要**（「战场事件逻辑：16 个触发条件组」/「战场事件表：16 段对白」），真正的行是触发块。
4. 触发块的**顺序**用 logic 剧本里的出现次序（= 时间上的先后），**不是**链上的次序。理由：作者关心「什么时候会触发」；链上的次序只是「第几段」。每行同时标出它对应链上第几段，两者都能看到。

**触发块的数据模型**（实现时按此建模）：

```
trigger block = {
  index,            // 在 logic 剧本里的次序（0 起）
  value,            // 0x33 压入的事件 id（1 基）
  conditions: [     // 本组条件指令（0x34/0x35/0x36/0x38/0x39）
    { instruction, op, operands: [...], target: {kind, address} }
  ],
  setFlag,          // 本组里的 0x37（可能没有）
  push,             // 那条 0x33
  segment: {        // events 剧本里被选中的一段（value 越界时为 null）
    index,          // 链上第几条（1 基）
    start,          // 文件偏移
    instructions,   // 段内指令
    lines,          // 段里的文本指令（0x01 / 0x20）及其文本段
  } | null
}
```

**条件指令的跳转目标怎么显示**：目标地址 → 标签的解析规则（照实解析，解析不出来就照实显示地址）：

| 目标地址落在 | 显示 |
|---|---|
| logic 剧本的 `0x00 结束脚本` 处 | 「跳到末尾」 |
| 某条 0x33 的**下一条**指令 | 「跳到触发块 #k+1」 |
| 其它 | 「跳到 0x……（在本组之外）」 |

**样例（场景 40，第一组）**：条件 1 目标 = 0x0805B0F5 = 脚本末尾 ⇒ 「不满足就跳到末尾（这一关后面什么都不触发）」；条件 2 目标 = 0x0805B0E3 = 第一条 0x33 的下一条 ⇒ 「不满足就跳到下一个触发组」。**这两句就是作者要的「什么条件下会触发」。**

### D2. 每一行给作者看什么（作者心智模型，不是 ROM 的）

**行头（收起时）**：

```
触发 #4 · 第 4 段对白 · 5 句        [条件：回合数 ≥ 2、角色 #12 在场]
```

- 「触发 #4」= logic 剧本里的第 4 个触发组。
- 「第 4 段对白」= 它选中的 events 链上第 4 条。
- 「5 句」= 这一段里的文本指令条数。
- 「条件：…」= 人话条件摘要（见下）。

**展开后**：

1. **条件表**（来自 logic 剧本）—— 一行一条条件，带它的跳转目标：
   | 条件 | 参数（可改） | 不满足时 |
   |---|---|---|
   | 回合/相位条件 | 回合数 ≥ **2**；相位 = **0** | 跳到触发块 #3 |
   | 指定人物在场 | 角色 **12** 在场 | 跳到末尾 |
   | 置战斗标志 | 战斗标志 **#3** | — |
2. **对白表**（来自 events 剧本的那一段）—— 一行一句，输入框 + 字节预算：
   | 说话人 | 对白（可改，长度不限） | 预算 |
   |---|---|---|
   | 卡卡西 | 「…」 | 42 / 42 字节 |

**人话摘要的措辞**（每个数字都要有出处；没定案的地方照实说）：

| 指令 | 显示成 | 出处 / 边界 |
|---|---|---|
| 0x34 | 「回合数 ≥ 2」（比较器来自 §3.1 的表）＋「相位 = 0」 | 回合计数**已定案**；相位字节**未命名**（§1.9），措辞用「相位字节」并附说明 |
| 0x34 且比较器 = 0xFF | 「只看相位 = 0」 | handler 里 0xFF 分支跳过比较（§1.7） |
| 0x35 | 「复合条件不成立时」（a 恒为 0） | a {0} 的事实见 §1.7；f 的参数语义未定案 ⇒ 摘要里不编「在比什么」，只显示 b/c/d 的原值 |
| 0x36 | 「角色 #12 在场」（a=1）/「角色 #12 不在场」（a=0） | 「在场检查」proved；b 未命名 ⇒ 显示为原始数字并注明 |
| 0x37 | 「战斗标志 #3（置/清，模式 = 1）」 | 模式取值未命名（§1.7） |
| 0x38 | 「战斗标志 #3 已置则跳（模式 = 0）」 | 「已置则跳」proved；模式取值未命名（§1.7） |
| 0x39 | 「子配置 = 1」 | §1.7 |

**不编造**：0x35 的三个参数、0x36 的 b、0x0202680E 的名字 —— 三处都**照实显示原始数字 + 一句「仓库还没定名」**。

### D3. 分层 / 懒加载

**决定**：

- **列表默认只渲染行头摘要**（一行几行文字）。触发块的正文（条件表 + 对白表）在**点开那一行时**才渲染。
- **不把四个剧本的指令表一次全渲染**（`before` / `after` 最多 2123 条指令）。
- **不渲染 0x32 链本身**（它是「第几段」的索引，不是内容）；链上第几段由每个触发块自己标出来。

**理由与数字**：一关最多 **17** 个触发块（场景 20）、最多 **66** 句文本（场景 1）、events 剧本最多 **201** 条指令。全部铺开会让右侧面板变成第二个「原始字节」页；第十轮的版式原则是「一摞卡片，一眼看完这一关能改的东西」，不是「一屏塞满」。

**展开状态放在哪**：存在视图的临时状态里（不进内容包），切卡片 / 换关卡就清掉。理由：展开状态是「我现在在看哪一条」，不是内容。

### D4. 就地改：哪些能改、怎么改

| 东西 | 能不能改 | 怎么改 |
|---|---|---|
| **对白正文** | ✅ | 复用 `scripttext.js`：`textSegments` → `segmentBudget` → `commitSegment`（**第十六轮是等长**，超长 / 超短当场拒收并回滚；**第十七轮起长度不限** —— 变长 / 变短由「构建时搬迁整个剧本」兜住）。写回走 `pack.setBytesAt`（`commitSegment` 内部已经这么干） |
| **条件指令的定宽 u8 操作数**（0x34 的比较器/b/c、0x35 的 a/b/c/d、0x36 的 a/b/c、0x37 的模式/标志、0x38 的模式/标志、0x39 的 id） | ✅ | 给输入框，复用 `common.js::operandInput`（它已按 size 卡 0..255）；写回走 `pack.setScriptOperand` |
| **0x33 压入的事件 id**（value） | ✅ | 同上（`KNOWN_OPERANDS` 里已经有 `value`） |
| **u32 跳转目标**（0x32 的载荷、0x34/0x35/0x36/0x38/0x39 的目标） | ❌ **这一轮不给输入框** | 见 D5 |
| **战前 / 战后剧情的对白** | ❌ **这一轮不做** | 见 D6 |

**改定宽操作数不会破坏脚本结构**：这些指令的长度是固定的（0x34 = 8、0x35 = 9、0x36 = 8、0x37 = 3、0x38 = 7、0x39 = 6、0x33 = 2），改的是**指令内部的一个字节**，指令总长不变 ⇒ 后面的指令不移位 ⇒ **绝对地址的分支目标全部仍然有效**。

**一个必须注意的坑**：运行时算出来的操作数**必须带上 `before_hex`**（原版字节）。`pack.setScriptOperand` 用 `operand.before_hex` 作为补丁的「改前字节」，缺了它补丁就没有校验依据（现有 `scriptview.js` 的 `operandInput` 是现场从 ROM 拼 `before_hex` 的）。

**另一个坑**：`pack.setScriptOperand` → `ensurePatch` 命中已有补丁时会**直接改那条补丁的 `after_hex`**。条件操作数在条件指令里、对白在文本指令里，两者不重叠 ⇒ 实践中不会互相打架；但 `scripttext.js` 的 `conflictingPatch` 检查要保留（对白那一侧）。

### D5. u32 跳转目标：机制上合法，但**这一轮不给输入框**

**结论**：改 u32 目标**不会破坏脚本结构**（指令长度不变、不移位、其它分支目标不受影响），所以它是一次**合法的分支改写**；但**这一轮不开放输入框**。

**理由**：

1. **它是地址，不是参数。** 作者想改的是「第几回合触发」「哪个角色在场」「第几段剧情」这类**参数**，它们全在 u8 操作数里（0x34 的 b、0x36 的 c、0x37 的标志、0x33 的 value）。改地址解决不了作者的诉求。
2. **它可能指到非指令边界。** 脚本的分支目标必须是某条指令的起点；指到中间，VM 从中间开始取指 ⇒ 后面全跑飞，而且**不报错**。编辑器能验（`scanScript` 给出的指令起点集合），但那已经是「改控制流」，不是「编辑剧情」。
3. **0x32 的载荷是「段首地址」**：改它等于把某一段对白接到别处，**块边界要重划**（哪一段包含哪些句子会变），本设计不做这件事。
4. 想「跳过/合并某一段」这类需求，等有了明确的产品形态再说。

**如果以后要开放**，必须同时满足：① 新目标落在**同一个剧本**内；② 新目标是该剧本里**某条指令的起点**（用 `scanScript` 的 offset 集合验）；③ 界面上给一次确认，并提示「这会改变触发顺序」。本轮只把**只读地址显示出来**（已经在「分支」列里），方便作者复制到别处查。

### D6. 战前 / 战后剧情：这一轮**不**做就地编辑

**决定**：「剧情触发」卡片里保留战前 / 战后两根指针 + 可改操作数表（现状），**外加一个「在剧情页打开」的链接**；**不在**战斗编辑界面里就地编辑它们的正文。

**理由**：

1. 用户要的是「**战斗里的**剧情触发」。战前 / 战后是**过场对白**，不是触发器 —— 它们没有条件、没有事件 id，结构上跟「触发列表」不是一回事。
2. 它们的正文最长 **2123** 条指令（场景 1 的 before），跟事件链那套「一段 = 链上一条」的模型完全不适用；要在这一轮硬塞进来，等于把独立剧情页（`#story/script/<root>/<scene>`）整个搬进战斗视图。
3. 现状的「可改操作数」表（0x1E 地图 / 0x1F 子配置 / 0x23 队员 / 0x22 加入战斗配置）**保留不动** —— 它已经是等长定宽写回，且与「角色出生点」卡片联动。

**链接怎么走**：复用 `ctx.onJump({module: 'script', kind: 'script', params: {root, scene}, label})` 那条路（`rom-editor/js/modules/scriptview.js:26-33` 就是这个路由）。**这是「跳到独立页」，不是本轮要消灭的那种跳转**；本轮消灭的是「看/改战斗触发必须跳转」。

### D7. 没载入 ROM 时的降级

**决定**：「剧情触发」卡片**照常渲染**，只把需要 ROM 的部分换成说明文字：

| 部分 | 没有 ROM 时 |
|---|---|
| 四张根表 + 本关指针 | ✅ 照常显示（来自内容包 `structures`，**不需要 ROM**） |
| before / after 的可改操作数表 | ✅ 照常显示（来自 `pack.scripts[].operands`，**不需要 ROM**） |
| **触发块列表**（条件 + 对白） | ❌ 换成一行说明：「未载入原版 ROM —— 反汇编剧情脚本需要 ROM 字节。」 |
| 「跳到剧情页」链接 | ✅ 保留（那页自己会判 ROM） |

**理由**：反汇编要 ROM 字节，这是物理限制；但**卡片不能因此空掉或报错** —— 根指针表和操作数表是内容包里的事实，没有 ROM 也该给。`scriptview.js:35-40` 就是这个先例。

**另外**：`CardStack.render` 已经把每张卡片的渲染包在 try/catch 里（`cards.js:161-169`），所以即使这一块炸了，整摞卡片也不会白屏 —— 但**仍然要自己判 `ctx.rom`**，不能靠兜底。

### D8. 与「胜负条件」卡片的关系：**不合成，但互相引用**

**决定**：**不合并**成一张卡片。保持「胜负条件」「剧情触发」两张；「胜负条件」卡片里加一行**交叉引用**。

**理由**：

1. **编辑对象不同**：胜负条件是 `battle_rules` 结构表里一条 **0x44 字节**的记录（回合上限 + 4 胜 + 4 负 + 说明文字）；剧情触发是**剧本字节流**（在 ROM 里，改动只以补丁存在）。两者的写回通路、撤销粒度、角标统计全都不同。
2. **判定时机不同**：胜负条件是**战斗结算时**判一次；剧情触发是**战斗中逐帧**判的触发器。放在一张卡片里，作者会以为它们是一回事。
3. **版式原则**：第十轮刚落地的「一摞纵排卡片，一类一张」（`cards.js`）就是为了「一眼看完这一关能改的东西」。合成一张会让卡片过长、角标含义混乱（「这一类改了几处」没法算）。
4. **但它们确实共用一个东西**：`0x0202680C`（回合计数）既被胜负条件的类型 2 读（`0x0202680A` 回合上限 vs 计数），又被 0x34 的触发条件读（§1.7）。所以交叉引用**有实际价值**：在「胜负条件」卡片里写一行「本关有 **N** 处剧情触发按回合数判定（回合上限 = **X**）」，点一下跳到「剧情触发」卡片。

**交叉引用怎么实现**：「剧情触发」卡片在 DOM 上给每个触发块一个稳定的锚点（例：`data-trigger="3"`），「胜负条件」卡片里的链接用 `ctx.openPanel('map','map',{stage, variant})` + 页面内 `scrollIntoView` / 展开对应触发块。**这是可选项**：如果实现成本高，先只写文字引用，不做跳转。

### D9. 版式：**「剧情触发」那张卡片内部展开**，不另加卡片

**决定**：保留「剧情触发」这一张卡片，把触发块列表放进它的卡体。**不**另加一张「剧情触发列表」卡片。

**理由**：

1. 第十轮的机制是 `CardStack`（`cards.js`），卡片 id 固定、角标机制成熟（就地更新，不整摞重画）。另加一张卡片会让卡片数从 5 变 6，而两者讲的是**同一件事的两半**。
2. 「剧情触发」这个标题本来就该装「这一关在战斗里会触发的剧情」；触发列表正是它的内容。现在它只装了四行指针 + 一张空操作数表 —— **是卡片内容没填满，不是卡片不该存在**。
3. 卡片体里可以分层：第一段「战斗中触发」（本次的主体，触发块列表），第二段「战前 / 战后剧情」（指针 + 链接）。两段都在同一张卡里，往下滚就看完。
4. 卡片的 hint 一行要改文案，从「这一关在战斗里会触发的四个剧本与可改的操作数」改成能说清「条件 → 触发哪一段 → 就地改对白」。

**角标**：现在 `scriptsChanged()`（`battle-map.js:807-817`）只数 `script.operands`（before/after 的），**新加的对白补丁不会进角标** ⇒ 必须改：角标 = 本关触发块里被改过的处数（对白段 + 条件操作数）。判据复用 `scripttext.js` 的 `currentBytes` / `common.js` 的 `operandChanged` 那一套。

### D10. 界面文案（不出现字面 `**`）

编辑器不渲染 markdown ⇒ 界面文本里**不许**出现字面 `**`。现有「剧情触发」卡片那段（`battle-sections.js:168-171`）**有**，本轮重写时去掉。

**示例文案**（供实现时直接用，可再润色）：

- 卡片 hint：`这一关在战斗里会触发的剧情：什么条件下触发、触发哪一段、对白就地改`
- 列表头说明：`每一行是一处触发：左边是「什么条件下会触发」，右边是它触发的那一段对白。对白可以就地改，长度不限 —— 等长的直接原地改写；变长 / 变短的话，构建时会把整个剧本搬到 ROM 的空闲区，把它内部的绝对地址全部重基。`
- 条件说明（0x34）：`回合数达到设定值、且相位字节相等时才触发。相位字节（战斗控制块 0x0202680E）仓库还没起名字，这里按原始值显示。`
- 条件说明（0x35）：`复合条件不成立时触发。仓库只证明了它是「三个参数求值后与期望值比较」，三个参数分别是什么还没解。`
- 条件说明（0x36）：`检查指定角色是否在场，结果等于设定值时触发。`
- 降级说明：`未载入原版 ROM —— 反汇编剧情脚本需要 ROM 字节。下面是这一关的剧本指针与可改操作数。`

### D11. 触发块模型放在哪

**决定**：

- `rom-editor/js/storyvm.js` —— 补**字节码层**的东西：`KNOWN_OPERANDS` 的新字段、`OPERAND_LABELS`、`COMPARATOR_NAMES`（0..5 → `==` / `!=` / `>` / `>=` / `<` / `<=`）。
- **新文件 `rom-editor/js/battletriggers.js`** —— 放**战斗域**的模型：把 logic + events 两个剧本切成触发块与剧情段、配对、算人话摘要。纯计算，不碰 DOM。
- `rom-editor/js/modules/battle-sections.js` —— 只做视图。

**为什么单独开一个文件**：`storyvm.js` 是「字节码 → 指令」的通用层（before/after 剧本也用）；「触发块」是**战斗域**的语义（logic + events 这一对剧本才有的概念）。混在一起会让 `storyvm.js` 长出战斗专属的表。单独一个文件也便于 `tools/verify_battle_story_triggers.mjs` 直接 import 来做机器验收。

## 4. 验收标准（可落成 `tools/verify_battle_story_triggers.mjs` 的断言）

> 约定：`verify_*.mjs` 用 `node` 直接跑，退出码 0 = 全过；输出写到 `build/battle-story-trigger-verify.txt`（stdout 在 PowerShell 下会被 GBK 弄乱，同 `tools/probe_battle_story_triggers.mjs` 的做法）。

**V1 触发块与剧情段一一对应（数量对账）**

- 对场景 1..46：每个场景的触发块数 == logic 剧本里 0x33 的条数。
- 全 46 关合计：触发块 **407** 个；其中 `segment != null`（能选到剧情段）的 **400** 个；选不上的 **7** 个（场景 32..38 各一个，值 0）。
- 断言：`counts.blocks === 407 && counts.linked === 400 && counts.unlinked === 7`。

**V2 链是 1 基的（用 ROM 字节钉死）**

- `rom[0x08097D1A - 0x08000000] === 0x01`（`subs r0,#1`）且 `rom[0x08097D1C - 0x08000000] === 0xA0` 且 `rom[0x08097D1D - 0x08000000] === 0x42`（`cmp r0,r4`）。
- 语义断言：对每个场景，`trigger.value - 1` 必须落在 `[0, chain.length)` 内才允许 `segment != null`；`value === 0` 的触发块 `segment === null`。

**V3 events 剧本的结构**

- 46/46：events 剧本的**前 N 条指令全是 0x32**（N = 链长）。
- 46/46：每条 0x32 的 u32 载荷（`rom_offset+1` 起的 4 字节，减去 `0x08000000`）落在同一剧本的指令起点集合内。

**V4 压值与链长的对账**

- 39 个场景：压入的值集合（去重、去掉 0）== `{1..链长}`。
- 7 个场景（32..38）：压入的值集合 == `{0,1,2,3}`，链长 == 3，值 0 无对应段。

**V5 定宽可改：改操作数不移动任何字节**

- 对每个新增的操作数字段：改写前后，`storyvm.instructionLength(rom, offset)` 不变，且该指令之后所有指令的 offset 不变。
- 断言方式：拿改写后的字节流重新 `scanScript`，得到的 offset 数组与改写前**逐项相等**。

**V6 对白等长**（**第十七轮起改写** —— 下面是**当时**的验收项；现在断的是「新行为」）

- 对一段文本：改成**等长**文本 ⇒ `commitSegment` 返回 `ok === true`，段字节数不变，`scanScript` 的 offset 数组不变。
- 改成**多 1 字节** ⇒ `commitSegment` 返回 `ok === false`（`reason === 'length'`），且 **ROM 字节与补丁都没变**（回滚）。
- ⇒ **第十七轮**：第二条**反过来** —— 改成多 1 字节 ⇒ `commitSegment` 返回 `ok === true`
  且 `relocated === true`（**标明会搬动剧本**），补丁的 `after_hex` 比 `before_hex` 长 1 字节，
  正文字节确实变了。实际落地在
  `rom-editor/tools/verify_battle_story_triggers.mjs` 的 V6 组与
  `rom-editor/tools/verify_variable_text.mjs`（64 条，端到端）。

**V7 写回通路没有新开**

- 改一段对白、一次条件操作数之后，`pack.patches` 增长。
- ⇒ **第十七轮**：补丁的 `before_hex` 与 `after_hex` **不再要求等长** ——
  **变长的补丁由「剧本搬迁」兜住**（构建时把整个剧本搬到空闲区并重基地址）；
  但**不属于任何剧本**的变长补丁在构建时会**报错**（后面没有东西能给它让位）。
- 代码层面：`pack` 上**没有**新增写回方法（`setText` / `setScriptOperand` / `setBytesAt` 之外没有新的 `set*` 入口）—— 这条以 code review 为准，脚本侧只断言补丁落在预期位置。

**V8 降级不炸**

- `ctx.rom = null` 时调用 `renderScriptsTab(ctx, stage)`：不抛异常，返回的节点非空，且**不含任何输入框**（`node.querySelectorAll('input').length === 0`）。

**V9 界面文案不含字面 `**`**

- 把新增 / 改写的界面文案抽成常量表（建议放 `battletriggers.js` 或 `battle-sections.js` 顶部导出，便于机器验），断言每一段 `!text.includes('**')`。
- 附带断言：现有 `battle-sections.js:170` 那一段字面 `**` 已被清掉。

**V10 两处 `KNOWN_OPERANDS` 一致**

- 用正则从 `tools/import_story_script.py` 抽出 `KNOWN_OPERANDS` 的键与字段名，与 `rom-editor/js/storyvm.js` 导出的 `KNOWN_OPERANDS` **逐项相等**（键集相同、每个键的字段名集合相同、偏移与字节数也相同）。

**V11 角标不隐形**

- 改一段对白后，「剧情触发」卡片的角标计数 **+1**；改一个条件操作数后也 **+1**；撤销后回到原值。

**V12 人话摘要不许编**

- 断言摘要文本里出现「回合数」「相位」「角色」「战斗标志」「子配置」这些**有出处**的词；
- 断言摘要文本里**不出现**任何为 0x35 的 b/c/d、0x36 的 b、0x0202680E 编造的名称（例如不得出现「剩余体力」「HP」「敌我阵营」之类仓库没证实的词）。

| **0x36 的 b 是什么** | 仓库证了「检查指定角色是否在场」，但 a / b / c 没分别命名。a 读作「期望结果」、c 像角色 id，b 未解。 |
| **0x33 压入的值 0** | 场景 32..38 多压的那个 0 **选不中任何一段**（§1.5 已从字节证明）。**它为什么存在、还有没有别的消费者，仓库没有答案。** |
| **事件 id 与剧情段的对应是不是「一一触发」** | 数据上 39/46 关严格一一对应，7 关多一个不生效的 0。**但运行时是否真的「压入 → 立刻取对应段」没有动态取证**（`notes/story-vm-opcodes-20261020.md` §4 明列「0x32 事件链的『第 N 项』到底按什么编号」为未解）。本设计采用的 1 基规则是**从 ROM 字节反推的**，有判死检验（V2），但仍是**静态证据**，不是运行时证据。 |
| **logic 与 events 的执行时序** | 仓库没写清「先跑 logic 压队列、再跑 events 取段」的确切调度点（调度器在 `0x0808A54C` / `0x0808A566` / `0x0808A5FC` / `0x0808A67C`）。本设计只依赖「压入值 ↔ 链序号」的对应关系，不依赖具体时序。 |
| **战斗变体与剧情** | 剧情按**场景**索引、三个变体共用（§1.2 已核）。**没有**证据表明原版存在「按变体不同的战斗剧情」。 |
| **before / after 的就地编辑** | 本轮**不做**（D6），属于明确的范围裁剪，不是遗漏。 |
| **u32 跳转目标要不要开放输入框** | **与 `notes/evidence/battle-story-trigger-structure-20261022.md` §8 有分歧**：那份笔记倾向「u32 目标可以原地改，界面提示一下即可」；本文 **D5 主张这一轮不给输入框**（理由：它是地址不是参数；可能指到非指令边界且不报错；0x32 的载荷一动就要重划块边界）。若实现者选择开放，**必须**同时满足 D5 列的三条（限同一剧本、限指令起点、二次确认）。 |
| **0x34 的 b 跟什么比** | 那份证据笔记说「仓库没定案」；**本文用字节证明是回合计数**（`0x0808A1A0` 的字面量 = `0x0202680C`），而 `0x0202680C` = 回合计数 仓库已定案（§1.7）。**以本文为准。** |

## 7. 交付摘要

- **结构核实结论**：战斗触发是**一对相邻剧本** —— 「战场事件逻辑」算条件、压**事件 id**；「战场事件表」开头是一条**连续的 0x32 事件链**，每条指向一段对白。**事件 id 选中链上第 id 段（1 基）**（`subs r0,#1` @ `0x08097D1A`）。39/46 关严格一一对应；场景 32..38 多压一个不生效的 0。**407 = 400 + 7**。
- **一行是什么**：一个**触发块** = 一组条件指令 + 事件 id + 它选中的那一段对白。剧本级退化成列表顶部的两个摘要。
- **要改的文件**：`storyvm.js`（补操作数表与比较器名）、**新** `battletriggers.js`（触发块模型）、`battle-sections.js`（视图）、`battle-map.js`（角标 + hint）、`battle-map.css`、`tools/import_story_script.py`（同步操作数表）、**新** `tools/verify_battle_story_triggers.mjs`、两份笔记。
- **验收**：V1–V12（见 §4），全部可机器断言。
- **最大未解**：0x34 的相位字节 `0x0202680E` 仓库没有名字 —— 界面照实写「相位字节」，不猜。
