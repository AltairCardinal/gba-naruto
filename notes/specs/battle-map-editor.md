> 本文是**实现的依据**，不是聊天记录。
> 关联规格：`notes/specs/route-workbench.md`（剧情路线工作台）、`notes/specs/assets-domain.md`（素材域）。

## 0. 摘要：三个定论

| 问题 | 定论 | 依据 |
|---|---|---|
| 画真实像素还是画格子？ | **画真实像素**（原版图块原样合成），另加可开关的格线叠加层 | §2.1–§2.6；链路每一段都有本仓库 ROM 上的实测 |
| 坐标单位是什么？ | `battle_actors.x/y` 与 `battle_map_objects.x/y` 的单位是**格（cell）**，**1 格 = 32 × 16 像素**；地图整图 = `格宽 × 32` × `格高 × 16` 像素 | §2.3；47 张地图的坐标**无一越界**，且按 32×16 换算后每张图的最小边都 ≥ GBA 屏幕 240×160 |
| 素材能不能改？ | **不能**。图块 / 调色板 / 图层 / 组合图块 / 通行值都是 **LZ77 载荷**，改它们要「重压缩 + 改指针 + 找空闲区」= 一条全新的写回通路；且**通行值块战斗加载器根本不读** | §2.7、§4.6 |

另外两个必须先说清的判断：

- **剧情底图不叠在战斗地图上**。`map_table.background_id` 指向的是**剧情画面上半屏**（240×80）的那张底图，
  不是战场贴图。地图视图里它单列一块小面板，不叠图。依据见 §2.8。
- **战斗目标（`battle_rules`）不进地图视图**。它与地图没有空间关系（条件类型 1/2/3/6/7/8/9 里没有一个参数是坐标），
  留在现有的 `#battle/stage/<关卡>/<变体>` 四件套视图里。依据见 §4.5。

## 2. 事实核对（本轮在 `rom/base.gba` 上实测）

> 复现方式：本节每条都给了命令。凡是笔记与实测冲突的地方，本节以**实测**为准，并写明冲突在哪。
>
> 旁证：仓库里另有一份并行产出的事实笔记 `notes/evidence/battle-map-render-facts-20261022.md`
> （工具 `tools/probe_battle_map.py` / `tools/probe_battle_map_tiles.py`）。
> 本规格的地图表布局、1 格 = 32×16 像素、图层排布与合成算法与它**逐条一致**，互相独立地取了同样的结论。

### 2.1 地图表布局（47 条 × 32 字节）

文件偏移 `0x53D910`，条目 32 字节，**47 条有效（索引 0..46）**。

| 偏移 | 类型 | 含义 | 本轮实测 |
|---|---|---|---|
| +0x00 | u16 | 原始宽 | 36..92 |
| +0x02 | u16 | 原始高 | 30..64 |
| +0x04 | u32 | tile gfx（LZ77） | 解压长度 % 32 == 0（47/47）→ 4bpp 8×8 图块 |
| +0x08 | u32 | 调色板（LZ77） | 解压 **恒为 384 字节**（47/47）= 192 个 BGR555 = 12 组 × 16 色 |
| +0x0C | u32 | 图层 0（LZ77） | 解压长度 == 格数 × **4**（47/47） |
| +0x10 | u32 | 图层 1（LZ77，0 = 无） | 同上；**14 张图非空**（0,7,8,9,10,11,12,21,22,23,31,32,34,35），33 张为 0 |
| +0x14 | u32 | 组合图块表（LZ77） | 解压长度 % 8 == 0（47/47）→ **8 字节/项** |
| +0x18 | u32 | 通行值表（LZ77） | 解压长度 == 格数 × **2**（47/47） |
| +0x1C | u8 | 剧情底图 id | 1..7 |

**冲突澄清（以实测为准）**：

- `notes/map-format.md` 顶部的 2026-10-20 更正**正确**：`0x596D5C` 是精灵动作表 id=1 行，不是图块描述符表。
- `notes/battle-config-format.md` 的 32 字节字段顺序**正确**（+0 宽/+2 高/+4 gfx/+8 pal/+C/+10 层/+14 meta/+18 terr/+1C 底图）。
- `tools/extract_tileset.py` 的文档字符串把图层写成「metatile-index planes (2 x cells u16)」，
  **这是错的**（见 §2.4）—— 该工具的 `split_planes()` 把图层错切成两半，渲染出来的图是乱的。
  规格与实现都**不得**沿用这个切法。

### 2.2 图块 / 调色板 / 组合图块 的编码

- **图块 = 4bpp，8×8 像素，32 字节/块**。每行 4 字节，每字节两个像素，**低半字节是左边那个像素**。
- **图块号**：组合图块里的 u16 图块引用，bits 9-0（0..1023）。本 ROM 每张图 160..704 块。
- **翻转**：bit 10 = 水平翻转，bit 11 = 垂直翻转。
- **色卡号**：bits 15-12（0..15），色卡 = 调色板里连续 16 个 BGR555。
- **组合图块（metatile）= 8 字节 = 4 个 u16 图块引用，排成 2×2**（左上 / 右上 / 左下 / 右下），
  因此 **1 个 metatile = 16 × 16 像素**。
- **调色板 = 384 字节 = 192 个 BGR555**（bit0-4 = R，bit5-9 = G，bit10-14 = B），即 **12 组色卡**。
  原版 47 张图实际只用到 bank 0..10（bank 11..15 从未出现）。
- **透明**：GBA 4bpp 背景下，**色卡内第 0 号色透明**。因此合成时「像素值 0 = 透明」，
  图层 1 的透明像素**不遮住**图层 0。

### 2.3 「格（cell）」的尺寸：1 格 = 32 × 16 像素

```
格列数 = 原始宽 >> 2      格行数 = 原始高 >> 1
1 格 = 32 × 16 像素
整张地图 = 格列数 × 32 像素 宽  ×  格行数 × 16 像素 高
```

三条互相独立的证据（**以实测为准**，见 `notes/tile-asset-rules-20261020.md` §1.2 的双确认）：

1. **数据侧**：通行值块解压长度 == 格宽 × 格高 × 2（47/47 精确吻合）；图层块 == 格宽 × 格高 × 4（47/47）。
2. **代码侧**（`0x08068FB4`）：`raw宽 >> 2` 写进 `0x0201BE2A`、`raw高 >> 1` 写进 `0x0201BE2B`；
   同一函数把 `raw宽`、`raw高` 各存 1 字节（本 ROM 36..92 / 30..64，全部安全）。
3. **屏幕尺寸（本轮新增，最硬的一条）**：战斗舞台是 GBA 屏幕 240×160 像素。
   1–46 关的格宽 9..17、格高 15..32。
   - 按 **1 格 = 32×16** 换算：每张图 288..544 × 240..512 像素 —— **每张都 ≥ 240 宽、≥ 160 高**。
   - 按 **1 格 = 16×16** 换算：宽度 144..272 像素 —— **第 2/3/4/5/40..45 关只有 144 像素宽，撑不满 240 像素的屏幕**。
   ⇒ 只能是 32×16。

补充硬证据（**本轮新测**）：通行值网格的**外圈一整圈都是 15（边界/不可通过）**
（第 1、2、7、9、40 关实测外圈 100% 是 15；第 0 关外圈是 0，第 0 条没有对应的战斗关卡）。
这同时钉死了「格网格 = 格宽 × 格高、行主序」。

### 2.4 图层的排布：格行数 × (格列数 × 2)

图层是一张 u16 的 **metatile 索引**矩阵（不是 GBA tilemap 条目！），形状是
**格行数 行 × (格列数 × 2) 列**；即**每格横向占 2 个 metatile、纵向占 1 行 metatile**。

```
metatile 索引 = u16[ 图层[ (y * 格宽 * 2 + x * 2 + h) * 2 ] ]      h ∈ {0,1} = 左半 / 右半
```

- 图层 0 的条目数 = 格数 × 2（stage 0 = 1472、stage 1 = 450、stage 40 = 396）✔
- **所有**图层索引都 < 该图的 metatile 数（越界引用 0 处）✔
- 这条排布与第三方 `features.js:55`（`stampCell`）和 `features.js:59`（`renderMap`）逐字一致，
  仓库自己的 `notes/tile-asset-rules-20261020.md` §2.2 / §6 也已写成同一条规则。
- **不要**按「两片平面」切（`tools/extract_tileset.py::split_planes` 那样切会得到错乱的图）。

### 2.5 整张地图的合成链路（每一步都有出处）

```
地图表 0x53D910 + 关卡 id × 32
   ├─ +0x00 u16 raw宽, +0x02 u16 raw高           → 格宽 = raw宽>>2, 格高 = raw高>>1
   ├─ +0x04 ptr ──LZ77──▶ gfx        (4bpp 图块，每块 32 字节)
   ├─ +0x08 ptr ──LZ77──▶ palette    (384 字节 = 12 组 BGR555)
   ├─ +0x0C ptr ──LZ77──▶ layer0     (u16 metatile 索引，格高 × 格宽×2)
   ├─ +0x10 ptr ──LZ77──▶ layer1     (同上；指针为 0 = 没有第二层)
   ├─ +0x14 ptr ──LZ77──▶ metatiles  (每项 8 字节 = 4 个 u16 图块引用)
   └─ +0x18 ptr ──LZ77──▶ terrain    (每格 2 字节；仅作只读信息，见 §2.7)

合成： 对每个格 (x,y)、每个半块 h∈{0,1}：
        meta = layer0[(y*格宽*2 + x*2 + h)]
        取 metatiles[meta*8 .. +8] 的 4 个 u16（2×2 排布）
        每个 u16 → (图块号, hflip, vflip, 色卡)
        取 gfx[图块号*32 .. +32] 解出 8×8 的 4bpp 像素
        像素值 0 → 透明；否则 颜色号 = 像素值 + 色卡*16 → palette[颜色号*2]
   图层 1 覆盖图层 0（仅在图层 1 该像素非透明时）。
```

**渲染出的整图尺寸** = 格宽 × 32 像素 × 格高 × 16 像素
（stage 0 = 736 × 512；stage 1 = 480 × 240；stage 40 = 288 × 352；1–46 关的范围 288..544 × 240..512）。

### 2.6 LZ77 格式（GBA type 0x10）

```
+0x00  u8   = 0x10
+0x01  u24  解压后长度（小端）
+0x04  ...   数据：每 1 个标志字节管 8 个单元，从高位到低位
              标志位 0 = 1 个字面量（1 字节）
              标志位 1 = 回溯：2 字节 b0,b1 → 长度 = (b0>>4)+3，距离 = ((b0&0xF)<<8)|b1，回溯起点 = 当前位置 - 距离 - 1
```

- 仓库已有 **Python** 版：`tools/lib/lz77.py::decompress`（`compress_literal` 是纯字面量编码器）。
- 浏览器端需要 JS 版。**但本规格的主方案不依赖它**（素材已解压后随内容包分发，见 §6），
  JS 版只作为「从 ROM 现解」的兜底路径，属于 P2（§10）。

### 2.7 哪些能改、哪些不能改（写回边界）

| 东西 | 能不能改 | 为什么 |
|---|---|---|
| `battle_actors`（角色出生点） | ✅ 能 | 12 槽 × 0xB8 字节，逐槽原地写；仓库既有 `pack.setValue` 通路 |
| `battle_map_objects`（战场物件） | ✅ 能 | 16 槽 × 4 字节，原地写 |
| `map_table.background_id`（剧情底图 id） | ✅ 能 | u8，原地写 |
| `map_table` 的 6 个资源指针 | ⚠️ 只读 | 改了等于手工接线（指向别处的资源），不在这条编辑流里；通用表格编辑器里已可改 |
| **图块 / 调色板 / 图层 / 组合图块 / 通行值** | ❌ **不能** | 都是 LZ77 载荷。要改就必须：重压缩（仓库没有与原版逐字节一致的压缩器）→ 长度多半变化 → 改指针 → 在 ROM 里找空闲区安置新块 → 改写所有指向旧块的指针。**这是一条全新的写回通路**，与仓库「复制原生条目 + 只改已知字段 + 其余字节原样保留」的模型冲突。 |

**额外的硬理由（比「没有压缩器」更致命）**：

- `notes/tile-asset-rules-20261020.md` §9.1：**战斗地图加载器 `0x08068FF0` 只读 +0x04/+0x08/+0x0C/+0x10/+0x14，根本不读 +0x18（通行值块）**。
  ⇒ 就算我们能重写通行值块，游戏也不看它。**改通行值没有游戏内效果**。
- 图层 / 组合图块 / 图块的替换还要消耗图块数、色卡数、metatile 数三样配额
  （本 ROM 最紧张的是 map 9/11/12/35，各只剩 6 组色卡），而且 4bpp 背景下色卡 0 号色必须保持透明。
  这些规则第三方已经踩过一遍（`asset_imports.js`），仓库只在 `notes/tile-asset-rules-20261020.md` 里做了**试算**，
  没有做写回通路。

⇒ **本规格把「地形 / 图块 / 底图素材」全部定为只读**，地图视图里只显示，不提供编辑入口。

### 2.8 剧情底图：它不是战场贴图

- 底图表在 `0x59903C`，16 字节/条：`gfx_ptr / palette_ptr / tilemap_ptr / bpp_flag`。
- **只有 id 1..7 与 9..13 符合背景记录格式**（id 14..35 是另一种 32 字节调色板形态，含义不同）。
- 每条自带一张 **240 × 80 像素**的图（tilemap 640 字节 = 320 个 u16 = 32×10 个 8×8 图块；
  原生加载器 `0x08088348` 把它填进一个 32×32 的 GBA 背景，320 个真条目 + 704 个填充条目）。
- **240 × 80 正好是 GBA 屏幕 240×160 的上半屏** —— 这就是「剧情画面上方那张底图」，
  第三方编辑器也把它标成「实际剧情底图（对话区上方）」（`feature_ui.js:25`）。
- `map_table.background_id` 取值实测 1..7（第 1 关用得最多，22 张图），
  改它是**一个字节的原地写**，可以在地图视图里做成一个下拉。

⇒ **底图不叠在战场地图上。** 地图视图里它单列一块「剧情底图」小面板（240×80 预览 + 下拉改 id）。

### 2.9 地图 id ≠ 关卡 id？（未闭合，但要留口子）

- 原生：剧本指令 `0x1E`「载入地图/背景」写 `state[0x17] = 地图 id`，
  并查地图表 `0x0853D910`（步长 0x20）—— `notes/story-vm-opcodes-20261020.md:142`（已 proved）。
- `0x1F` 写 `state[0x19] = 子配置 id`（= 变体）—— 同上 `:143`。
- **本仓库的剧本操作数里只提取到 3 个场景带 `0x1E`**（场景 51 的 0/51/7、场景 53 的 30/53），
  而这三个场景都是「地点剧情」而不是战斗关卡。
- 动态侧：首战 `0x02026805 = 40`，地图表第 40 条原始头 `24 00 2C 00`（36×44）
  与 `notes/maps-runtime-fields-20260711.md` 预期的运行时 `[36,44,9,22]` 吻合。

⇒ **本规格按「地图 id = 关卡 id」处理**（与第三方编辑器一致），但**地图视图里必须提供一个
「地图」下拉**，允许作者手动改用地图表的另一条。理由：这是唯一一处「我们的假设可能压不住」的地方，
留个口子比将来返工便宜。

### 2.10 坐标合法域

- `x` ∈ 0..格宽-1，`y` ∈ 格高-1。**本轮实测：1–46 关全部角色槽与全部物件槽的坐标，无一越界**（越界计数 = 0）。
- 全局取值范围（1–46 关，非空槽）：角色 x 1..13 / y 3..26（476 个非空槽）；
  物件 x 1..14 / y 3..28（165 个非空槽）。
  量级与「格」一致（最小格的地图只有 9 列 15 行），**不是像素**。
- 因此地图视图的坐标输入框**应当做越界拦截**（现有 `battle.js` 的数字框只拦 0..65535）。
- `facing` 实测取值分布：0×153、1×97、2×140、3×86（四个值都在用）。
  第三方编辑器把枚举标成 **0 上 / 1 右 / 2 下 / 3 左**，并称「已用游戏内实际移动预览校验」
  （`third_party/konoha-workshop/editor/使用说明.txt`）。**这是外部证据**，本仓库没有独立复核。
  ⇒ 地图视图里朝向显示成「上 / 右 / 下 / 左」，并在说明里注明「枚举来自第三方编辑器的实机校验」。

### 2.11 阵营：真正生效的是 `unit_flags` bit0

- `battle_actors` 槽内 `+0x01` 那一字节（内容包里叫 `side`）**原生不读**；
  阵营真正生效的是 `+0x08` 的 `unit_flags` 的 bit0（`notes/battle-tables.md:127`：
  `unit+0xC0 = (位域 | 阵营 | 0x10)`）。
- 现有 `battle.js:481-498` 的 `sideCell` 已经是这么做的（改 `unit_flags` 的 bit0）。
  ⇒ 地图视图里的阵营控件**沿用同一套**，不要新造。

## 4. 编辑流

### 4.1 总体节奏

1. 作者进 `#battle/map/40/0` → 画布立刻出图（素材已随内容包分发，**不需要载入 ROM**）。
2. 在画布上**点一个格子** → 右侧面板高亮该格上的物件/角色；状态行给出格坐标 + 通行类型 + 该格上的东西。
3. 要挪一个物件 → **在画布上直接拖**金色标记；或在右侧表格里改 X / Y 数字框。
4. 要换角色 → 右侧「角色」列下拉（`character_names` 的中文名）。
5. 每改一下 → 立刻写回（`pack.setValue`）→ 顶栏「已改动 N」+1 → toast 说明改了什么。
6. 改错了 → `Ctrl+Z`（顶栏「撤销」按钮同效）→ 画布重绘。

### 4.2 选中格（只读）

- 点击画布 → 选中格 `(x, y)`。
- 状态行文案（示例）：
  `所选格 (3, 5) · 通行 0（可通行地面）· 该格上：物件 #2、角色 #4`
- 通行类型的名字表：仓库**没有**官方的地形名表。第三方把 0 标成「可通行地面」、7 标成「障碍（不可通过）」、
  15 标成「边界（不可通过）」，其余标「原有特殊地形」（`feature_ui.js:3-4`）。
  ⇒ 沿用这套**显示名**（标注来源为第三方），写回的仍是原始编号。
  但**通行值不可编辑**（§2.7），所以这个下拉在地图视图里是**纯只读标签**，不是控件。

### 4.3 拖动标记（写回路径）

**物件**：

| 步骤 | 行为 | 反馈 |
|---|---|---|
| 1 | 鼠标按在金色标记上 → 标记跟随指针 | 标记描边加粗，光标变 `grabbing` |
| 2 | 拖动时标记吸附到所在格（`cellFromPixel`） | 状态行实时显示目标格 `(x, y)` |
| 3 | 松开 → 若目标格与原格不同 → `pack.setValue(battle_map_objects, record, 'x'/'y', …)` | toast `已把 物件 #3 移到 (5, 7)`；顶栏「已改动 N」+1 |
| 4 | 若目标格越界（x ≥ 格宽 / y ≥ 格高） | **不写回**，标记弹回原位，toast（错误色）`X 坐标越界：这张地图只有 9 列（0–8）。` |

**角色**：同上，字段是 `x` / `y`；toast `已把 角色 #1 移到 (5, 7)`。

- 一次拖动 = **两条 `setValue`**（x 和 y 各一条）= 撤销栈里的**两步**。
  ⇒ 规格要求：**一次拖动只压一条撤销记录**。实现办法：先算好目标 x/y，
  再调 `pack.setValue` 两次；但 `pack.js` 的 `setValue` 每次都压栈。
  **本规格不改 `pack.js` 的撤销模型**（不动公共件），
  改为：**松手时才写回**（拖动过程中只改画布上的临时位置，不动 pack），
  于是「一次拖动 = 两条撤销记录」是可接受的（作者按两次 Ctrl+Z 就回去了），
  但**必须在状态行写明**：`已把 物件 #3 移到 (5, 7)（Ctrl+Z 撤销）`。
  ⇒ 明确取舍：**不做「一次拖动一步撤销」**，避免改动公共撤销模型。

## 5. 坐标换算：纯函数契约（可脱离 canvas 测）

新建模块 `rom-editor/js/maprender.js`，**不依赖 DOM**，导出以下纯函数。
无头验收脚本直接 `import` 它做断言（canvas 在无头环境里没有 2D 上下文，
所以**像素合成也必须做成纯函数**，只在最后一步 `putImageData`）。

| 函数 | 签名 | 契约 |
|---|---|---|
| `cellFromPixel` | `(px, py, cellW, cellH) → {x, y}` | `x = floor(px / 32)`，`y = floor(py / 16)`；越界返回 `null` |
| `pixelFromCell` | `(x, y) → {px, py}` | `px = x * 32`，`py = y * 16` |
| `cellRect` | `(x, y) → {x, y, w, h}` | `{x: x*32, y: y*16, w: 32, h: 16}` |
| `cellFromClientPoint` | `(clientX, clientY, rect, cellW, cellH) → {x, y} \| null` | `rect` = 画布元素的 `getBoundingClientRect()`；换算必须除以**显示缩放**（`rect.width / (cellW*32)`），不能假设 1:1 |
| `renderMapImage` | `(asset, opts) → {width, height, pixels}` | `pixels` 是 `Uint8ClampedArray(width*height*4)` 的 **RGBA**；`opts.layer1` = `false` 时只画图层 0，`true` 时图层 1 覆盖（仅非透明处） |
| `decodeMapAsset` | `(bytes, index) → asset` | 把 §6 的二进制块解成 `{cellW, cellH, gfx, palette, layer0, layer1, metatiles, terrain}` |
| `assetPixelColor` | `(asset, px, py) → [r,g,b,a]` | 取某个地图像素的颜色（测试用） |

**合成细节（写死，别自己发明）**：

- 图块像素：4bpp，块内第 `row` 行第 `col` 像素在 `gfx[tile*32 + row*4 + (col>>1)]`，
  取 `(col & 1) ? (b >> 4) : (b & 0x0F)`。**低半字节是左像素**。
- metatile 内 4 个 u16 的位置：`(tileRow & 1) * 2 + (tileCol & 1)`，
  其中 `tileRow = (py >> 3) & 1`，`tileCol = (px >> 3) & 1`（像素在 metatile 内的 8×8 格坐标）。
- 翻转：descriptor 的 bit10 → `col = 7 - col`；bit11 → `row = 7 - row`。
- 颜色：像素值 0 → **透明**（alpha 0）；否则 `颜色号 = 像素值 + 色卡号 * 16`，
  颜色 = `palette[颜色号*2]` 的 BGR555 → RGB（`r5 = v & 31`，`g5 = (v>>5)&31`，`b5 = (v>>10)&31`，
  8 位取 `c = (c5 << 3) | (c5 >> 2)`）。
- 图层 1 覆盖图层 0：**仅当图层 1 该像素非透明**。

## 6. 素材供给：结论与理由

### 6.1 两个方案的数据（**本轮实测**）

|---|---|---|---|---|

| B. 运行时从 ROM 现解 | 同上，但素材留在 ROM 里，浏览器解压时算 | 0（ROM 已有） | 0 | ❌ 不可用（ROM 未载入） |

（关卡 0 的第 0 条地图没有对应的战斗关卡，**不进素材包**；若主代理想连它一起带上，
再加 35,408 字节即可，gzip 后约 +6 KB。）

### 6.2 结论：**选 A**

理由：

1. **编辑器的卖点是「不载入 ROM 也能编辑」**（`js/romsource.js` 顶部的注释就是这么写的）。
   B 方案会让「看得见的战场」这个头号功能挂在「载入内置 ROM」（2.7 MB 下载）后面。
2. **A 的成本极小**：170 KiB，单独一个文件、**按需拉取**（只在打开地图视图时 fetch），
   初始加载体积**一点不变**（`pack.min.json.gz` 仍是 318 KB）。
3. **要改的东西本来就在内容包里**：物件 / 角色 / 底图 id 全在 pack 里，
   素材只是**只读上下文**。素材缺失时，编辑功能**一条都不少**（见 §6.4 兜底）。
4. **A 不需要浏览器端 LZ77 解码器**（素材已解压），比 B 少一个可能出错的环节。

**A 的已知代价（必须写进规格）**：导出的内容包 JSON **不含**那 170 KiB 的二进制。
分发时要带走 `content/maps/maps.bin.gz`。
⇒ 「导出内容包」按钮的说明行加一句：
`导出的内容包不含地图素材二进制（content/maps/maps.bin.gz），分发时请一并带上。`

### 6.3 素材文件与元数据（**主代理要在 `tools/export_content_pack.py` 里加的东西**）

**新文件**：`rom-editor/content/maps/maps.bin.gz`（gzip；也允许未压缩的 `.bin`，
编辑器用 `js/romsource.js::fetchMaybeGzip` 拉，它已经会看 `.gz` 后缀并用 `DecompressionStream` 解）。

**二进制布局**（一张图一块，按关卡 id 升序，块内 6 段按固定顺序紧挨着）：

```
每张图：
  [gfx      ] 图块 4bpp，tile_count × 32 字节
  [palette  ] 384 字节 = 192 个 BGR555
  [layer0   ] u16 × (格高 × 格宽 × 2)
  [layer1   ] u16 × (格高 × 格宽 × 2)     （无图层 1 的图写 0 字节）
  [metatiles] u16 × (metatile_count × 4)
  [terrain  ] u16 × (格高 × 格宽)
```

**pack.json 顶层新增一个键** `map_assets`：

```jsonc
"map_assets": {
  "format": "gba-map-assets-v1",
  "file": "content/maps/maps.bin.gz",
  "sha256": "<素材文件的 sha256>",
  "maps": {
    "1": {
      "cell_w": 15, "cell_h": 15,
      "px_w": 480, "px_h": 240,
      "tile_count": 320, "metatile_count": 144,
      "banks": [0, 1, 3, 4],
      "has_layer1": false,
      "blocks": {
        "gfx":      { "offset": 0,    "length": 10240 },
        "palette":  { "offset": 10240, "length": 384 },
        "layer0":   { "offset": 10624, "length": 900 },
        "layer1":   { "offset": 11524, "length": 0 },
        "metatiles":{ "offset": 11524, "length": 1152 },
        "terrain":  { "offset": 12676, "length": 450 }
      }
    }
    // … 1..46
  }
}
```

- `blocks` 里的 offset 是**相对该图块起点**的偏移（每张图在文件里的一段）。
  实现时要么给每张图一个 `base` 字段，要么把 offset 写成文件绝对偏移 —— 规格要求
  **用绝对偏移**（少一层换算，少一处错）。
- **导出器必须自检**（不通过就报错，不产出坏素材）：
  1. `len(layer0) == cell_w * cell_h * 4`
  2. `len(layer1) == 0 或 == cell_w * cell_h * 4`
  3. `len(metatiles) % 8 == 0`
  4. `len(terrain) == cell_w * cell_h * 2`
  5. `len(gfx) % 32 == 0`
  6. `len(palette) == 384`
  7. **所有**图层索引 `< metatile_count`（越界引用 0 处）
  8. `len(palette) / 2 / 16 == 12`
- 导出器顺带把 `tile_count` / `metatile_count` / `banks` 统计好写进元数据，
  免得浏览器再扫一遍。
- `map_assets.sha256` 用来判「素材文件与内容包是不是同一版」：
  不一致时地图视图只显示降级格线底图并给出提示。

### 6.4 兜底（没有素材时怎么办）

素材文件缺失 / 拉取失败 / sha256 不符 ⇒ 地图视图**照常打开**：

- 画布区域画**格线底图**（纯 CSS 网格：每 32×16 像素一格 + 行列号），标记照常显示、可拖。
- 顶部出现提示条（错误色描边）：
  `未载入地图素材 —— 只显示格线与标记。素材文件：content/maps/maps.bin.gz`
  后面跟一个按钮 `重新载入素材`。
- **所有编辑功能照常可用**（物件 / 角色 / 底图 id 都在内容包里，不依赖素材）。
- 状态行补一句：`（底图缺失）`。

**B 方案（从 ROM 现解）作为 P2**：素材文件实在拿不到时，
用 `js/romsource.js::loadBundledRom()` 拿 ROM + 一个 JS 版 LZ77 解码器现解。
**本规格不要求第一版就做**，但要求 `js/maprender.js` 的 `decodeMapAsset` 留一个
「从 ROM 解」的同构入口（`decodeMapAssetFromRom(rom, stage)`），
避免以后重写。

## 8. 验收标准（机器可断言，≥ 6 条）

> 探针写法参考 `rom-editor/tools/verify_audio_workbench.mjs`：
> 自建一个最小 DOM stub（`StubNode`），`globalThis.document` / `globalThis.window` 造假，
> 然后 `import` 视图模块并断言 DOM 文本与控件。
> **注意：canvas 在无头环境里没有 2D 上下文** ⇒ 一切像素断言必须走 §5 的纯函数
> （`renderMapImage` 返回 RGBA 缓冲，不碰 canvas），**不许**在断言里调 `getContext`。

| # | 断言 | 怎么判 |
|---|---|---|
| V1 | **像素渲染正确** | `renderMapImage(stage0)` 的 `width === 736 && height === 512`，`pixels.length === 736*512*4`；且 `assetPixelColor(asset, 0, 0)` 等于从 ROM 独立解出的第 0 个图块第 0 个像素的颜色（测试脚本自己用 `tools/lib/lz77.py` 的等价 JS 实现或硬编码期望值） |
| V2 | **坐标换算是 32×16，不是别的** | `cellFromPixel(0,0) = {0,0}`；`cellFromPixel(31,15) = {0,0}`；`cellFromPixel(32,0) = {1,0}`；`cellFromPixel(31,16) = {0,1}`；`cellFromPixel(32,16) = {1,1}` |
| V3 | **命中测试带缩放** | `cellFromClientPoint` 在显示宽 = 地图宽 × 2 时，点在画布 (64, 32) 处应落在格 (1, 1) |
| V4 | **格数与地图表一致** | 46 张图的 `cell_w` / `cell_h` 全部等于 `map_table` 记录里的 `raw_width >> 2` / `raw_height >> 1`；`px_w === cell_w*32`、`px_h === cell_h*16` |
| V5 | **写回只动该动的字节** | 在 `battle_map_objects` 第 (40 关, 变体 0) 的物件槽 #1 上把 `x` 改成 7，`buildRom` 后：编成组 +0x8A4 那一格的 `x` 字节 = 7，**同槽的 type/target/y 三个字节与原版逐字节相同**，整个 ROM 只有那 1 个字节与原版不同 |
| V6 | **撤销与改动计数** | 改完 `x` 后 `pack.changedCount()` +1；`pack.undo()` 后 `x` 恢复原值、`changedCount()` 回落；再改再撤两次（x、y 各一条）能完全回到原状 |
| V7 | **深链与面包屑** | `parseHash('#battle/map/40/0')` → `{module:'battle', panel:{kind:'map', params:{stage:40, variant:0}}}`；`hashFor` 反向得到同一个字符串；面包屑文本含「第 40 关 · 战场地图」 |
| V8 | **越界被拦** | 在地图视图里把某物件的 X 改成 ≥ 格宽，`pack` 里该值**没有**变，且视图出现错误 toast 文本 `X 坐标越界` |
| V9 | **阵营写的是 unit_flags bit0** | 在地图视图把某角色槽的阵营改成「敌方」后，`record.values.unit_flags & 1 === 1`，且 `record.values.side` **不变**（原生不读那一字节） |
| V10 | **素材缺失时降级但不瘫** | 把 `map_assets` 置空后渲染地图视图：DOM 里出现 `未载入地图素材` 提示条与 `.map-grid-fallback` 元素，**且**右侧「战场物件」表仍有 16 行、「角色出生点」表仍有 12 行（编辑功能不丢） |
| V11 | **战斗目标不在地图视图里** | 地图视图的文本里**不出现**「胜利」「失败」「回合上限」；只出现一个指向关卡视图的链接 |
| V12 | **底图 id 可改** | 把 `map_table` 第 40 条的 `background_id` 从 1 改成 3，`pack.setValue` 后 `record.values.background_id === 3`，且构建后 `0x53D910 + 40*32 + 28` 字节 = 3、**该记录其余 31 字节不变** |

> V5 / V12 的「整个 ROM 只有 N 个字节不同」是**最强**的一条：它同时证明写回没有走新的通路、
> 没有发明新的压缩、没有动到未解字节。**必须逐字节比对整份 ROM**（`buildRom` 的输出 vs `rom/base.gba`），
> 不能只比那一条记录。

## 9. 明确不做（并说明为什么）

| 不做 | 为什么 |
|---|---|
| **编辑地形 / 通行值** | 战斗加载器 `0x08068FF0` 根本不读 `+0x18`（§2.7）—— 改了没有游戏内效果 |
| **编辑图块 / 调色板 / 图层 / 组合图块** | 要重压缩 + 改指针 + 找空闲区 = 新的写回通路（§2.7）；本规格的写回模型是「复制原生条目 + 只改已知字段」 |
| **导入外部图片当地块** | 同上；第三方做到了（`asset_imports.js`），但它靠「重新生成整个 ROM」，不适用我们的补丁模型 |
| **扩图 / 改地图尺寸** | `raw_width` / `raw_height` 改了，六个 LZ77 块的长度关系全部破裂（47/47 的尺寸关系会立刻失配） |
| **在地图视图里编辑战斗目标** | 条件参数里没有坐标，与地图没有空间关系（§4.7） |
| **在地图上绘制地形笔刷 / 复制底图图案** | 那是第三方「编辑地形」的能力，依赖改 LZ77 块（§2.7）；我们只读 |
| **换角色时自动拷贝角色模板** | 会改槽内 168 字节未解数据，是新的写回语义；改成确认弹窗 + 说明（§4.5） |
| **一次拖动 = 一步撤销** | 要改 `pack.js` 的公共撤销模型；本规格不碰公共件（§4.3） |
| **把素材塞进 pack.json** | 会让 `pack.min.json.gz` 从 318 KB 涨到 ~500 KB，且每次开编辑器都要下；独立文件按需拉取更好（§6.2） |
| **地图 id 的自动推断（从剧本 0x1E 推）** | 仓库只提取到 3 个场景的 0x1E，且都不是战斗关卡（§2.9）；先用「地图 id = 关卡 id」+ 手动下拉 |
| **多地图拼贴 / 换图** | 不同地图的图块资源不同源，混贴在原版引擎里不成立（第三方也这么说） |

## 11. 建议的实现顺序

1. **先做纯函数模块** `js/maprender.js`（解码 + 坐标换算 + 像素合成），
   配 `tools/verify_battle_map.mjs` 的 V1/V2/V3/V4 断言。
   —— 这一步没有任何 UI，能独立证明「地图画得对不对」，是最容易出错也最该先钉死的一步。
2. **再让主代理的 `export_content_pack.py` 产出素材**（§6.3），
   顺带把 V4（46 张图的格数与 `map_table` 一致）跑起来。
3. **然后做视图外壳**（路由 + 面包屑 + 分栏 + 画布 + 缩放），先只显示图和格线。
4. **再叠标记**（角色 / 物件 / 选中 / 悬停）。
5. **最后接编辑**（拖动 + 右侧表格 + 越界拦截 + 撤销反馈），补 V5/V6/V8/V9/V12。
6. **兜底与说明**（素材缺失提示、降级格线底图、战斗目标链接、机关名/朝向/地形名的来源标注），补 V10/V11。
