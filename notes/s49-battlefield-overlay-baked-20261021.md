# 突破：原版的「移动网格覆盖层」是**每张地图烘焙好的一张静态布局图**（2026-10-21，第 22 轮）

## 1. 怎么发现的

第 21 轮换图块实验变差（2,917 → 4,086 / 5,026），说明缺的不是高亮块。
本轮回头看**原版 field 帧的 BG2 tilemap 本身**（此时 BG2 还关着，但 tilemap 已被写好），
按 16×16 逻辑格统计 2×2 图块签名，得到 **16 种签名**：

| 签名 | 格数 | 出现在哪 |
| --- | --- | --- |
| `(256,256,256,256)` | 64 | 整片空区 |
| `(278,278,280,280)` / `(278,279,280,281)` | 29 / 28 | **第 2 行的偶/奇列** |
| `(256,257,259,260)` / `(257,258,260,261)` | 42 / 48 | **第 3 行的偶/奇列** |
| `(256,256,280,280)` / `(256,256,280,281)` | 8 / 8 | 第 1 行的偶/奇列 |
| `(262,263,264,265)` / `(262,262,264,264)` | 7 / 5 | 第 5–6 行、第 0–1 列 |
| `(266,266,268,268)` / `(266,267,268,269)` | 3 / 3 | 第 7 行、第 0–5 列 |
| `(278,257,280,260)`、`(278,262,280,264)`、`(278,270,280,272)` | 6 / 2 / 1 | **第 14 列**（混合族） |

⇒ **每个逻辑格的「族」由它在战场上的位置决定**（第 2 行=族 10、第 3 行=族 0、
第 5–6 行=族 2、第 7 行=族 4、第 14 列混合），
而**变体由列奇偶决定**（偶列=无框、奇列=带框）——**与第 17 轮在高亮族上量到的规则完全一致**。

⇒⇒⇒ **BG2 的 tilemap 是原版在进入战斗时写好的一张「战场布局图」**
（移动范围区、攻击范围区、网格、受阻区、光标列…各用不同族画出来），
**移动范围屏只是把 `DISPCNT` bit 10 打开让它显现**（BG2 的滚动寄存器与地图一致）。
⇒ ⇒ **它不是运行时规则，而是每张地图一份的静态资产。**

## 2. 这解释了此前所有反常

- 第 21 轮「只换高亮块」为什么两头不讨好：原版屏幕上是「**整张布局图**」，重制侧只画了范围 ⇒ 本来就差一整张图；
- 第 13 轮「PNG 与 dump 不自洽」：不是混合色的问题，而是**把整张布局图当成了「只多了一层网格」**；
- 「dither mask」旧规则：同底色对应多种覆盖色，是因为**布局图上不同区域用了不同族**（族 0/2/4/6/8/10 填充色不同）。

## 3. 产物

`artifacts/s49-original-battlefield-overlay-v1/`：
- `bg2-tilemap-field.bin`（2048 B）：**烘焙好的静态布局图**（field 帧的 BG2 tilemap）；
- `bg2-tilemap-movegrid.bin`（2048 B）：打开 BG2 时的状态；
- `manifest.json`：两者 sha256、与 field 帧不同的 **212** 个条目、16 种签名统计。

⇒ 重制侧要 1:1 复刻覆盖层，正确做法是**把这份布局图作为静态资产接进覆盖层**，
再用重制自己的状态算那 212 个「会变」的格子 —— 而不是用规则去生成整张图。

## 4. 仍未确立

- 这张布局图是**进入战斗时按地图 ID 写好的**，还是**从 ROM 的地图数据算出来的**
  （前者 ⇒ 逆向侧需找到「战斗场景初始化时写 BG2 tilemap」的那段代码与它用的地图表）；
- 那 212 个「会变」的格子在原版里按什么状态重画（重制侧目前按 move/attack/target/blocked 四套位掩码画）。
