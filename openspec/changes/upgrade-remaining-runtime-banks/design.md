## Context

当前严格审计为 13 个 `runtime_verified`、10 个 `code_verified` 和 9 个 `disproved`。`levels` 由独立 change 处理；本 change 接续处理其余九个 `code_verified` bank。九项并非同一种结构：其中包含视觉 descriptor、文本指针、函数回调、精灵资源对、动作参数、嵌套资源 descriptor 和可执行音频引擎代码。历史 slug 多数已被纠正，因此“打开同名界面”不是有效证据，必须在真实消费者边界证明数据链。

项目已经具备可复用基础：scenario 41 自然战斗路线及保存状态、`runtime-formation-probe.js` 的输入/内存采集、原生 mGBA GDB RSP 探针、`build_battle_message_runtime_probe.py`、`build_resource_pointer_runtime_probe.py`、多个 call-site wrapper 构建器、`run_guarded.py` 与项目进程树资源守卫。现有负证据同时表明 `actionable-move-grid.ss9` 位于部分目标调用之后，保存状态只能加速重放，不能替代对调用时序的证明。

主要约束如下：

- ROM 基线及现有自然状态不得被不透明地修改；每个变体必须是可审计的单因素差异。
- 功能变化遵循红—绿—重构，模拟器集成点必须有能在 wiring 失效时失败的测试。
- 高开销操作必须有内存、墙钟和空闲超时守卫；异常清理仅限本项目登记的进程树。
- 结论必须写入仓库并同步路线图；聊天记录和临时 `build/` 输出不是持久证据。
- `runtime_verified` 是实验结论而不是无条件配额；对于代码区或不可安全 A/B 的对象，必须采用非修改式自然因果证据。若仍达不到门禁，则该项是明确阻塞而不是可接受的完成状态。

## Goals / Non-Goals

**Goals:**

- 对九个 bank 分别建立“自然 selector → 真实 ROM 目标 → 可观察结果”的可复现证据链，使每个有效 bank 达到 `runtime_verified`；若新证据证明其并非独立结构，则按严格负证据流程改为 `disproved`。
- 复用 scenario 41 和 mGBA 保存状态，优先闭合 `data-table-b` 与 `resource-pointers`，并尽量共享同一有效动作覆盖 `tile-assets` 与 `palettes`。
- 把快照谱系、ROM 变体、运行时捕获、截图/音频摘要和资源守卫报告整理为统一证据包。
- 在每个可独立验收的 bank 组完成后更新审计、提交并推送，避免把全部风险集中到最终批次。

**Non-Goals:**

- 不处理 `levels`、P2 audio cue 命名、legacy web、ROM mirror 或续作编辑器。
- 不恢复已被证伪的旧表身份，不为兼容历史 slug 恢复旧写回路径。
- 不以全 ROM 反汇编、无界搜索或长时间盲目重放替代有界探针。
- 不要求直接修改 `sappy-engine` 可执行代码，也不把音频 cue 语义纳入该 bank 的验收。

## Decisions

### 1. 使用逐 bank 的证据矩阵，而不是统一强制升级

每项调查维护以下状态：自然触发边界、selector、canonical ROM 基址/记录、消费者 PC、输出目标、可观察结果、A/B 可行性、负证据、最终等级。`runtime_verified` 只在三重门禁全部满足时写入；若暂时只能保留 `code_verified`，必须记录可执行缺口并让本 change 保持未完成，不能把它包装成合理终点。

选择这一方案是因为九项的可观测性和修改风险不同。把“九项全部 runtime”作为硬指标会诱导对函数指针或代码段做不安全修改。备选方案是只以断点命中升级，但断点只能证明控制流经过，不能证明具体表项和用户结果，因此不采用。

### 2. 建立带谱系的 mGBA 快照阶梯

快照按自然路线保存到关键调用之前，而不是只保存 UI 看起来方便的位置：

```text
基线 ROM + 自然保存/输入
          |
          +-- scenario41-pre-action.ss9
          |        +-- valid-message/action.ss9
          |        +-- visual-loader.ss9
          |
          +-- story-visual-selector.ss9
          +-- map-load-selector.ss9
          +-- natural-audio-command.ss9
```

每个快照旁的证据清单记录 SHA-256、mGBA 版本、父状态、形成输入、保存帧边界、关键 WRAM 状态和允许验证的目标。加载后先检查关键内存不变量；如果目标 hook 已经发生，则回退到父快照建立更早边界。

选择 mGBA 原生保存状态是为了减少重复导航和浏览器开销，并支持 GDB 精确断点/内存读取。备选方案是每次冷启动或仅依赖浏览器 WASM；前者浪费资源，后者适合输入自动化但不如原生 GDB 精确。浏览器仅在原生输入暂时不能复现某条自然路径时作为有资源守卫的兼容路径，随后仍需固化可由 mGBA 恢复的状态。

### 3. 复用现有探针骨架，按调用边界扩展统一事件格式

优先直接使用现有 `build_battle_message_runtime_probe.py` 和 `build_resource_pointer_runtime_probe.py`；其他 bank 先检查已有 wrapper、解码器和运行时驱动能否追加字段。只有调用约定、scratch 布局或触发域确实不同，才新增专属构建器。

每次命中写出固定头和 bank 专属字段：magic、schema version、hit count、selector、表项地址、关键原始字段、消费者 PC/参数、输出目标。写入顺序采用“清 magic → 写 payload → 发布 magic”，防止主机读到半写状态。变体构建器必须校验基线 ROM 哈希、原始 hook 字节、code cave 全零、目标记录边界和单因素 diff。

选择调用点 wrapper 是因为它能同时记录运行时寄存器和 ROM 来源，且项目已有成熟测试模式。备选方案是广泛 watchpoint；它容易捕获通用解压/拷贝噪音，只有在调用点未知时才用于定位，不作为最终结构证据。

### 4. 按共享自然事件分四批闭环

| 批次 | Bank | 共享路线与关键结果 |
|---|---|---|
| A | `data-table-b`, `resource-pointers`, `tile-assets`, `palettes` | scenario 41 有效攻击/技能；依次捕获文本 ID、嵌套 descriptor、`0x44` 视觉 descriptor、10-byte 动作参数，并分别做安全单因素对照 |
| B | `battle-encounters`, `cutscene-scripts` | 自然 story/过场视觉事件；捕获 story opcode 或资源 ID、LZ77/palette/sprite 目标及画面差异 |
| C | `map-events`, `map-sprites` | 自然地图加载与行为；捕获 `sb+0x770` 回调 pair、精灵 definition/animation pair 和随后行为/图像 |
| D | `sappy-engine` | 自然已识别音乐或音效；捕获命令字节、handler PC、声道状态及音频结果，不修改代码区 |

批次 A 优先，因为已有 scenario 41 快照和两套专属构建器，且有效动作可能一次覆盖四项。若 selector 实际在当前快照之前发生，只建立一个更早父快照，再派生各 bank 变体。批次之间可因触发路线发现而调整，但不得用一个 bank 的消费者代替另一个 bank 的证据。

### 5. 基线与变体必须在相同快照、输入和采样窗口下成对运行

每个 A/B 由一个不可变实验清单驱动：基线 ROM 哈希、变体 ROM 哈希、唯一修改范围、同一快照哈希、同一输入序列、同一采样帧/断点和同一解码器版本。结果比较既检查预期差异，也检查控制字段和非目标输出保持稳定。

选择成对重放是为了排除动画时序、随机性和残留 UI 状态。仅比较两张 PNG 哈希的备选方案不能证明差异来自目标表；因此截图必须与 selector/ROM 目标捕获共同存在。

### 6. `sappy-engine` 使用自然命令因果链，不执行代码 A/B

在已识别可重复的音乐或音效入口建立快照，记录 sound ID 到曲目/轨道初始化、轨道命令字节、命中的 Sappy handler、处理前后声道或 FIFO/DMA 状态以及音频捕获摘要。若这些环节能直接连接到 `0x09AE3C` 引擎代码，则按统一门禁判断；如果只能再次得到静态调用链，则记录阻塞并继续寻找非修改式自然证据，本 change 不得据此验收完成。

直接 patch 引擎代码或调度表的备选方案风险过高，也会把“引擎仍工作”与具体结构语义混淆，因此禁止。此处只验证引擎执行，不扩展到 72 个未知 cue 的语义命名。

### 7. 资源守卫包裹所有高开销运行，并使用有界静态分析

模拟器、浏览器、音频捕获和反汇编命令统一经 `run_guarded.py` 获取共享锁，设置项目进程树 RSS 上限、墙钟与空闲超时，输出 JSON 摘要。主流程在批次开始、每个基线/变体对结束和提交前检查可用内存及项目进程树。

静态定位只对已知函数附近或明确地址范围做有界反汇编；禁止再次把整个 ROM 交给 `disasm(..., count=0)` 或构造全 ROM 指令图。守卫只清理它创建并登记的 Job Object/进程组，绝不按进程名批量结束 Python、Chrome 或 mGBA。

### 8. 并行只用于互不写共享状态的工作

静态消费者复核、bank 元数据审计、测试覆盖检查和证据文档审查可按批次交给子代理并行；ROM 变体生成、mGBA 快照推进、共享 scratch 布局和路线图/审计文件更新由一个所有者串行完成。子代理使用独立输出路径并回报候选证据，不直接同时修改相同 bank 或公共驱动。调度接口支持模型选择时，重复性清单核对和格式验证使用能胜任的低开销模型，调用约定、ROM patch 安全和证据等级判断保留给高可靠审查。

选择此边界是因为模拟器状态与 code cave 是共享可变资源，并行写入会让证据不可归因。完全串行的备选方案会浪费静态审查吞吐，因此只串行关键路径。

### 9. 阶段提交以证据闭环为原子边界

每批至少在一个 bank 得出可审计结论后，同步 bank JSON、紧凑证据、调查说明、路线图与审计输出；运行针对性测试、集成重放、完成度审计和 `git diff --check`，经独立审查后提交并推送当前远端分支。临时 ROM、PNG、GDB 日志留在忽略目录，只有复现所需的最小证据和经验证快照进入版本库。

选择按闭环提交是为了让错误结论可单独审查和回退。按文件类型分批提交会把证据与元数据拆开，故不采用。

## Risks / Trade-offs

- [当前 scenario 41 快照已越过目标调用] → 校验 hook 时序和 scratch；从自然 pre-action 父状态重建一次更早快照，再派生所有战斗 bank 实验。
- [同一战斗动作并不触发四个批次 A bank] → 保留负证据，按实际消费者把路线分开，不把零命中解释为表无效。
- [单因素资源指针替换导致解压尺寸或布局不兼容] → 仅在已证明目标格式/大小兼容时替换相邻记录或字段；构建期校验边界，运行时设置短超时并保留基线。
- [动画或音频结果受帧时序影响] → 使用同一快照、输入和采样窗口，比较结构化内存/命令状态，同时把截图或音频作为结果层而非唯一证据。
- [历史 slug 继续诱导错误验收] → 所有文档与测试使用 canonical 地址、record shape 和实际语义，slug 仅作为迁移标识。
- [多个 wrapper 争用 code cave 或 scratch] → 建立集中分配表和重叠测试；同一 ROM 只组合明确验证过的 hook，其他实验使用独立 ROM 变体。
- [子代理并行修改共享文件] → 明确单一文件所有者；并行代理只读或写独立证据草稿，合并由主流程完成。
- [长时间模拟器运行再次引发内存异常] → 所有运行进入资源守卫，定期读取项目 PID 树峰值，超限只终止该次 Job Object。
- [最终仍有 bank 保持 code_verified] → 不降低证据标准；为每项给出已穷尽路线、剩余不确定性和下一条可执行调查路径，并让本 change 与最终完成门禁保持失败，直到获得运行时或严格否定证据。

## Migration Plan

1. 等待 `levels` change 完成并同步主线，记录本 change 的基线提交和九项初始审计。
2. 先补齐共享事件格式、code cave/scratch 分配检查、快照谱系清单和资源守卫集成测试，不改变 bank 等级。
3. 按 A→B→C→D 批次执行基线/变体实验；每项先产出负或正证据，再决定是否更新验证等级。
4. 每个批次同步 bank JSON、证据、路线图和审计，验证后提交并推送。
5. 最后重新运行九项逐项审计、全量相关测试与仓库完成度检查，确认无缺失结论和临时产物混入。

若阶段性结论被后续证据推翻，使用新的纠正提交恢复原验证等级并更新原调查说明，保留证据演进历史；不得删除旧结论而使交接失去上下文。快照或 ROM 变体若被证明不可靠，则从证据清单撤销其“可接受”状态并由父快照重建。
