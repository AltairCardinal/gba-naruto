## D2-b 入口相位的交互模型不同（不是「名单少一个」）

> ⚠️ **本节被自我更正过两次。**
> - 第一次：「`positions/bank.json` 把蜜蜂整组放在敌方，阵营划分错了」——**错**。
> - 第二次：「数据是对的，差异在 `cycle_roster_unit` 的 `side == current_side`
>   过滤」——**也错**。
> - 现在的结论见下。**不要改 `positions/bank.json`，也不要改
>   `cycle_roster_unit` 的过滤条件。**

### 内存证据：蜜蜂是敌方单位在自己行动

单位池里 `+0xC1` 是「**这个单位正在行动**」标记。对 `original-bcycle/` 的七个
连续快照做逐字节差分，整个单位池里只有这一个字段在动：

| 快照 | 按键 | 行动单位（`+0xC1 == 1` 的槽） | 阵营 |
| --- | --- | --- | --- |
| step-00 | 起始 | 1 (11,6) | 玩家 |
| step-01 | A | 2 (10,14) | 玩家 |
| step-02 | A | 3 (8,14) | 玩家 |
| step-03 | A | 4 (8,7) | 玩家 |
| step-04 | A | **5 (3,4)** | **敌方** |
| step-05 | B | 6 (4,8) | 敌方 |
| step-06 | B | 7 (3,11) | 敌方 |

槽 5–7 都是蜜蜂（character_id 55），状态栏因此一直显示「蜜蜂」，看起来像
「卡在蜜蜂不动」，实际是**依次换到不同的蜜蜂**。

原版的单位分布（`+0xCC`：0=玩家 / 1=敌方）是 **4 玩家 + 5 敌方**，坐标为
玩家 (11,6)、(10,14)、(8,14)、(8,7)，敌方 (3,4)、(4,8)、(3,11)、(6,6)、(5,13)，
与重制 `positions/bank.json` 的 `group_id=14, variant=0` **逐项相同**。

**所以 A/B 不是「选择可控单位」，而是「推进行动单位」，并且会推进到敌方单位上。
蜜蜂从来不是玩家可控的。**

### 真正的差异

| | 原版 | 重制 |
| --- | --- | --- |
| A/B | 推进行动单位（玩家 → 敌方） | 弹出五命令菜单 |
| 方向键 | 无效 | 循环玩家单位 |
| 涉及单位 | 全部 9 个 | 仅 `side == current_side` 的 4 个玩家单位 |

重制的 `side == current_side` 过滤对一个「玩家选人」机制来说是**合理的**，
但原版在这个状态上根本没有「选人」这回事。两边是**不同的交互模型**，
不是同一模型的参数不同。

### 4.3.6 第三次更正：这个入口状态很可能处在**开场脚本**里，不在战斗 UI

把 A 连按到 14 次（`original-a14/`），`+0xC1` 行动标记的轨迹是：

```
起始→槽1(玩家) A1→槽2 A2→槽3 A3→槽4 A4→槽5(敌) A5→槽6 A6→槽7
A7→槽8 A8→槽9(敌)  A9..A14 → 停在槽9 不动
```

推进到**最后一个敌方单位就停住**，再按也不回到玩家。

再做一次全局 EWRAM 差分（入口态 vs 按一次 A 之后），整块 256 KiB 里
**79 个区间发生变化**，最大的一簇是 `0x0200A900–0x0200A972`（约 115 字节）。

⚠️ **本节的「文本／对话缓冲」判断随后被自己的检查推翻**：该区域 256 字节里
**没有任何 UTF-8 前导字节**（0xE4–0xE9 计数为 0），内容是稠密的 16 位小端值序列
（`0xF008, 0xF00A, 0xF00C, 0xF00E…` 递增 + 大量重复的 `0x1E1C`），属于结构化
二进制列表（OAM / 显示列表一类），**不是文本**。

所以「开场脚本」这个解释目前**证据不足**，不能当结论。仍然成立的事实只有：

1. A 推进 `+0xC1` 行动标记，走过 9 个单位后停在最后一个敌方单位，再按不动；
2. 2,400 帧零输入期间什么都不动（`original-entry-timeline/`）；
3. 按一次 A 会让 79 个 EWRAM 区间同时变化，远超一次 UI 切换的规模。

第 3 条的规模更像是**整个场景/回合状态被重建**，而不是一次局部输入响应。

**已排除的简单假设**：在 EWRAM 全域按 4 字节小端扫描、找「每次 A 精确 +1」的
单调计数器（base → A1 → A2 → A3），**命中 0 个**；在 EWRAM 单位池邻域扫
0,1,2,3,4 的字节序号也**命中 0 个**；WRAM（`0x03000000`，32 KiB）同样扫不到，
但 **A 一次会在 WRAM 里改动 188 个区间、EWRAM 里 79 个区间**——两侧同时大面积
改写，形态更像**整块状态被重建**（相位切换），而不是一次局部输入响应。

所以不要再从内存里扫标量了。正确的下一步是**用 GDB 追踪 A 生效前后执行的
例程**：仓库里已有 `tools/mgba_gdb_probe.py`（支持 `--savestate` 从入口快照起、
`--breakpoint` / `--read` 读内存、`--timeout`），在断点上读回 phase 字段，
或直接从执行到的 ROM 地址反推这个相位结构到底是哪段代码。

下一步应该直接看这 79 个区间里有没有回合序号、阶段码之类的标量，而不是继续猜。
**已验证可行**：GDB 探针能从本项目的 `.ss9` 快照直接命中断点。实测命令与结果：

```bash
python3 tools/mgba_gdb_probe.py --mgba build/macos-mgba/build/qt/mGBA.app/Contents/MacOS/mGBA \
    --rom rom/base.gba \
    --savestate artifacts/s49-fidelity-20261019-v1/original-bcycle/step-00-base.ss9
    --output artifacts/s49-fidelity-20261019-v1/gdb-probe-entry-pc/probe.json \
    --breakpoint 0x0806112E --timeout 20
```

入口快照的 `saved_pc = 0x0806112E`（Thumb，`cpsr 0x2000003F`）。探针返回
`outcome: "verified"`，`actualPc == expectedPc`，并给出该地址前后 32 字节的
ROM 指纹。也就是说：**断点种子可以用「从存档读出的 PC」自动得到**，
不需要事先知道 ROM 里任何函数地址。

下一步因此可以自动化：先从快照读 PC 设断点拿基线，再对 A 按下前后分别取样，
对比两次的 `rawStop` / 寄存器 / 指纹，定位真正处理输入的例程。
收据见 `artifacts/s49-fidelity-20261019-v1/gdb-probe-entry-pc/probe.json`。

### 4.3.7 A 键的真实入口例程：`0x0806289E`

单断点 GDB 探针抓不到它——边界采样的 `saved_pc` 在 A 前后几乎相同
（`0x0806112E` / `0x0806112A`，同一主循环，`lr` 恒为 `0x080610AB`），
因为每一步都是等 60 帧后才存档，存档时早就回到主循环了。

改用逐帧 PC 采样（`tools/butano/mgba_pc_trace.lua`，走的是和其它录制脚本
同一条 Lua 管线）：同一入口快照各录 120 帧，一组不按键、一组在第 30 帧按 A。

| | 采样到的不同 PC |
| --- | --- |
| 空闲（无输入） | `0x0806112A`、`0x0806112C`、`0x0806112E`（主循环内部三点） |
| 按 A | 上述三点 **+ `0x0806289E`** |

**第 30 帧（正是施键那一帧）PC 跳到 `0x0806289E`，随后立刻回到主循环。**
这个地址在空闲态 120 帧里从未出现。46 帧的差异都发生在施键之后。

也就是说：**A 键的处理入口是 `0x0806289E`**，按下去只执行很短一段就回到主
循环，而它引起的状态重建才是后续 46 帧差异的来源。

下一步可以据此做定向分析：以 `0x0806289E` 为断点种子，看它调用了谁、
写了哪个字段——那才是入口状态的相位码所在。

> 注意：逐帧 PC 采样只捕捉到每帧的那一瞬间，**不是完整指令级 trace**。
> 要看清 `0x0806289E` 内部做了什么，仍需更细的追踪手段；但入口地址本身
> 已经是可复现的硬证据。

### 4.3.8 A 处理链的调用点：`0x0806296D` → `0x0806289E`

在 `0x0806289E` 下断点、同时用 Lua 脚本在第 30 帧按 A，探针命中并给出：

```
outcome: verified      actualPc: 0x0806289E
lr = 0x0806296D        sp = 0x03007E7C
r0 = 0x80  r1 = 0x10013A5  r2 = 0x1001365  r3 = 0x40
```

`lr` 即**返回地址 = 调用点**，所以 A 的处理是 `0x0806296D` 调 `0x0806289E`。
两处地址的 ROM 指纹分别是
`0x08000000 → 9c1f62e9…`、`0x0806289E → 467687fa…`（与主循环的 `95d0338a…` 不同）。

收据：`artifacts/s49-fidelity-20261019-v1/gdb-probe-a-handler/probe.json`。

**下一步已经很具体**：反汇编 `0x0806296D` 与 `0x0806289E` 附近，
看它读写了哪些地址——尤其它拿 `r0 = 0x80` 做什么（0x80 = 128，可能是
单位池之外的某个数组索引或字段偏移）。这是把入口状态的相位码钉死的最后一步。

> 取证说明：这条收据来自直接调用探针。经 `tools/run_guarded.py` 包一层时，
> `--read ADDR+OFFSET:SIZE` 这类带算术表达式的参数会让参数解析失败（退出码 2）。
> 复现时用 `--read 0x020240C0:64` 这种纯地址形式，并在受守卫执行下重跑收据。

### 4.3.9 处理器字节的粗看（未完成，勿当结论）

```
1840 131c 4546 2b40 9842 0fd3 9842 19d1 8023 db02 1940 ...
```

肉眼可见同一段模式**重复出现两遍**（`...4?46 1040 2268 131c 4?46...`），并且

下一步应当用真正的反汇编器（如 `objdump`/`radare2`/`capstone` 处理 Thumb）看这段，

### 4.3.10 反汇编：A 的调用链与「逐单位循环」

**先更正上一节的工具链结论**：仓库里本来就有 Thumb 反汇编工具——
`tools/disasm_thumb.py`、`tools/find_thumb_calls.py`、`tools/thumb_branch.py`。
我上一节只查了系统工具就说「无法反汇编」，**那个结论是错的**。系统
`objdump`（Xcode LLVM 版）确实不支持裸二进制，但项目自带工具可以直接对
`rom/base.gba` 反汇编。

**注意 Thumb 标志位**：GDB 报的 `pc` / `lr` 最低位为 1 表示 Thumb 模式，
真实指令地址要 `& ~1`。`lr = 0x0806296D` → 实际返回地址 `0x0806296C`。

调用点：

```
0x08062954: bl   #0x809c114
0x08062958: ldr  r1, [sp, #0x18]
0x0806295A: movs r2, #0x80
0x0806295C: lsls r2, r2, #9
0x0806295E: adds r0, r1, r2
0x08062960: lsrs r2, r0, #0x10
0x08062962: asrs r0, r0, #0x10
0x08062964: cmp  r0, #0x7f
0x08062966: ble  #0x8062932
0x08062968: bl   #0x80627b0        ← 返回地址 0x0806296C（= lr & ~1）
=> 0x0806296C: ldr  r3, [pc, #0xc8]
   0x0806296E: str  r3, [sp, #4]
   0x08062970: movs r4, #0
   0x08062972: str  r4, [sp, #0xc]
   0x08062974: movs r2, #0
   0x08062976: ldr  r0, [pc, #0xc4]
   0x08062978: ldrb r0, [r0]         ← 从一个固定全局地址读「单位总数」
   0x0806297A: cmp  r2, r0
   0x0806297C: blt  #0x8062982       ← 循环体：r2 从 0 数到「单位总数」
```

`find_thumb_calls.py rom/base.gba 0x0806289E` **匹配 0 个**，而
`find_thumb_calls.py rom/base.gba 0x080627B0` **匹配 1 个**（就是 `0x08062968`）。

所以断点处 `pc = 0x0806289E`、`lr = 0x0806296D` 的组合，含义是：

> `0x08062968` 调 `0x080627B0`；该函数**尾跳**（B/BX，不改 lr）到
> `0x0806289C`，于是我们在那里断下，而 `lr` 仍是上一层 bl 的 `0x0806296D`。

并且紧跟着的 `0x08062978` 就是一个**逐单位循环**：`r2` 从 0 数到一个从固定全局
地址读出的「单位总数」字节，`blt` 进入循环体。这与「按一次 A，`+0xC1` 标记
依次推进到 9 个单位后停住」的行为完全吻合——`0x08062978` 读出的那个「单位总数」
字节很可能就是 9。

下一步就很具体了：读出 `ldr r0, [pc, #0xc4]` 指向的那个全局地址（`pc+4+0xc4`
处存的字），确认它是不是「单位总数」，以及循环体 `0x08062982` 之后往哪个字段写
`+0xC1`。

### 4.3.11 「单位总数」全局变量：`0x03005BB8` = 13

把 4.3.10 里那条指令的常量池解出来：

```
0x08062976: ldr  r0, [pc, #0xc4]
常量池地址 = Align(0x08062976+4, 4) + 0xC4 = 0x08062A3C
该处字 = 0x03005BB8          ← 全局变量地址（IWRAM）
入口快照读回：byte = 13
```

所以那个循环是 `r2: 0 → 12`，遍历一张 **13 项**的表，而单位池里我们实际观察到
有内容的只有 9 个（槽 1–9）。表里的另外 4 项是空的——这也解释了为什么按到
第 9 次之后（`original-a14` 的 A9–A14）画面和 `+0xC1` 都不再变化：循环已经把
可推进的项走完了，剩下的是空项。

这条同时说明：**原版这个循环遍历的是一张 13 项的行动顺序表，而不是
「4 玩家 + 5 敌方」这 9 个在场单位**。`+0xC1` 只是这张表上「当前行动到第几项」
的投影。

⚠️ 仍未解答的核心问题不变：**玩家在这个状态里怎么出手**。现在知道 A 推进的是
行动顺序表，但还不知道玩家操作入口对应表里的哪一项、由什么输入触发。下一步是
看循环体 `0x08062982` 之后往哪个字段写 `+0xC1`，以及这张 13 项表的每一项
分别对应什么状态。

### 4.3.12 行动顺序表的真实形态：WRAM 里 13 条 60 字节记录

按 4.3.10 的循环体继续解常量池：

```
0x08062982: ldr  r1, [pc, #0xbc]
常量池 @ 0x08062A40 -> 表基址 0x030059B8
0x08062984: lsls r2, r2, #0x10 / asrs r0, r2, #0xe   → 索引 = r2 * 4
0x0806298A: ldr  r7, [r0]                            → 取第 r2 项
```

入口快照里把 13 项全部读出来，**每一项都是 WRAM 内的一个小结构地址**，相邻项
间距稳定为 **0x3C = 60 字节**：

```
[ 0] 0x030056AC   [ 1] 0x03005724   [ 2] 0x03005760   [ 3] 0x0300579C
[ 4] 0x030057D8   [ 5] 0x03005814   [ 6] 0x03005850   [ 7] 0x0300588C
[ 8] 0x030058C8   [ 9] 0x03005904   [10] 0x03005940   [11] 0x0300597C
[12] 0x030059B8
```

⚠️ 所以**它们不是指向 EWRAM 单位池（0x020240C0）的指针**，而是一张独立的、
位于 IWRAM 的 13 项 × 60 字节记录表。上一节我按「指针 → 单位结构」去解读
是错的，已更正。

同时 `0x030059B8` 恰好既是第 13 项的地址、又是表基址，说明 4.3.11 里那个
「单位总数」全局 `0x03005BB8` 就在这张表的上方不远处——**表和计数是同一个
结构体的两个字段**（表 `0x030059B8..`，13 项 × 60 = 780 字节，`0x030059B8+780
= 0x03005CC4`，计数 `0x03005BB8` 落在表内）。

下一步应当：读这 13 条记录里每条的关键字段（尤其能对应到「行动单位 / 阵营 /
已行动」的那几个偏移），弄清哪些项是玩家单位、哪些是敌方、哪些是空项——
这才是玩家操作入口真正对应的位置。

### 4.3.13 13 条记录的字段分布（语义未定，勿猜）

### 4.3.15 重构：这 13 条是**命令表**，不是单位记录

对 13 条记录做两轮关联：

1. 全 60 字节扫 32 位小端值，**没有任何值落在 EWRAM 单位池
   （0x020240C0，stride 0x1D4）范围内**——记录里没有单位指针。
2. 按 4.3.10 循环体的算法 `r1 = [记录+0x20] + ([记录+0x14] << 2)` 算「计算地址」，
   结果**全部落在 ROM 区**：

```
[ 0] +0x14=0x2 +0x20=0x0812d124 -> 0x0812d12c
[ 1] +0x14=0x1 +0x20=0x081651b0 -> 0x081651b4
[ 2] +0x14=0x1 +0x20=0x081548a8 -> 0x081548ac
[ 3] +0x14=0x2 +0x20=0x082f83c0 -> 0x082f83c8
[ 4] +0x14=0x2 +0x20=0x082f83c0 -> 0x082f83c8
[ 5] +0x14=0x2 +0x20=0x082f83c0 -> 0x082f83c8
[ 6] +0x14=0x2 +0x20=0x08291434 -> 0x0829143c
[ 7] +0x14=0x2 +0x20=0x082f83c0 -> 0x082f83c8
```

⚠️ **由此必须修正 4.3.10 的解读**：那段循环不是「把 `+0xC1` 标记推进到下一个
单位」，而更像**遍历一张命令表、逐条调用其处理例程**。`+0xC1` 的移动是这些
处理例程的**副作用**，不是循环体本身的工作。

这与仓库里已有的命令 VM 证据（`artifacts/audio/command-vm-evidence.json`、
`notes/command-vm-*.md`）方向一致，但**本轮没有验证二者是同一套机制**。

下一步应改成：反汇编 `0x082f83c0`（被 5 条共用，最可能是主干）和
`0x0834882c`，看它们各自做什么；以及查清「玩家操作入口」是否就是这张命令表
里的某一条命令。

### 4.3.16 更正 4.3.15：`+0x20` 指向的**不是**处理例程（未证实，勿照用）

反汇编 `0x082f83c0`（被 5 条记录共用的那个 `+0x20` 值）：

```
0x082F83C0: strh r0, [r4, #0x12]
0x082F83C2: lsrs r7, r5, #0x20
0x082F83C4: strh r4, [r4, #0x14]
...
0x082F83E0: movs r0, r0      ← 对齐填充
0x082F83E2: movs r0, r0
```

这是**数据表**的形态（重复 `strh/lsrs` + `movs r0,r0` 对齐填充），**不是可执行
的函数入口**。所以 4.3.15 里「`+0x20` 是 ROM 处理例程地址」的说法**不成立**。

已验证的只剩两点：
- 13 条记录等距 60 字节，起点 `0x030056AC`（由 `0x030059B8` 的 13 个指针解引用
  后排序得到，指针顺序 = 行动顺序）；
- `+0x20` 是一个落在 ROM 区（`0x0812xxxx`–`0x0834xxxx`）的 32 位值，且
  `+0x14` 是 0–3 的小值。

但**这些值的语义完全未确定**。它们可能是数据表的地址、也可能是别的什么；在有
更多证据前，**不要按「命令表」或「处理例程」去改任何代码**。

这是本会话第九次自我更正。到此为止，我在这条链上的推理已经连续三次（表的内容、
记录布局、+0x20 语义）被自己的后续实验推翻，说明**仅凭内存取值形状推断语义在这个
区域是不可靠的**。

**建议的替代路径**（不要再走内存形状猜测）：
1. 用 `tools/mgba_gdb_probe.py` 在 `0x082F83C0` 这类地址下断点，看它**是否真的会被
   执行**——不被执行就证明它是数据。
2. 若确认是数据表，则应去找**谁在读它**（在读取它的指令下断点），从读取方的代码
   反推结构，而不是从结构猜语义。

### 4.3.17 执行级确认：`0x082F83C0` 是数据，从未被执行

4.3.16 是从字节形态推断的（`strh/lsrs` 重复 + `movs r0,r0` 填充）。
现在用**执行证据**验证：在 `0x082F83C0` 下断点，同一入口快照 + 第 30 帧按 A，
跑满 20 秒超时。

```
outcome    : not-proven
expectedPc : 0x082F83C0
actualPc   : None
rawStop    : None
```

**断点从未命中。** 所以 `+0x20` 指向的确实是数据，不是可执行入口——4.3.16 的
判断由推断升级为**已验证**。

收据：`artifacts/s49-fidelity-20261019-v1/gdb-probe-datatable/probe.json`。

### 这条方法本身值得记住

判断「一个 ROM 地址是代码还是数据」，最可靠的做法不是看字节长什么样，而是
**在它上面下断点，看它是否会被执行**。本会话有三次误判（表的内容、记录布局、
`+0x20` 语义）都是因为只看了形状。`tools/mgba_gdb_probe.py --breakpoint` 加一次
超时运行就能给出是/否。

下一步仍然是「找谁在读 `0x082F83C0`」：这需要反向搜索对该数据区的引用，
或者在读取方指令下断点——但至少现在**数据属性已经确认**，不必再猜。

### 4.3.18 引用计数：A 键代码确实独占使用这张表

在 `rom/base.gba` 里全文搜这三个地址作为 32 位立即数出现的次数：

```
0x030059B8（指针数组）: 5 处 -> 0x080627FC 0x08062840 0x08062884
                                 0x0806291C 0x08062A40
0x03005BB8（计数）    : 5 处 -> 0x080627F4 0x0806283C 0x08062920
                                 0x08062A3C 0x0806333C
0x082F83C0（记录里的 +0x20 值）: 1 处 -> 0x08598BC0
```

**已验证**：

1. 指针数组 `0x030059B8` 的**全部 5 处引用都在 `0x0806xxxx`**——正是 A 键处理链
   所在的函数簇（0x080627xx–0x080629xx），与 4.3.10 反汇编出的循环体完全吻合。
   其中 `0x08062A40` 就是 4.3.12 解出的常量池。
2. 计数 `0x03005BB8` 同样 5 处，其中 `0x08062A3C` 已在 4.3.10 验证过
   （`ldr r0,[pc,#0xc4]`），另外 4 处给出更多后续可查的切入点。
3. `0x082F83C0` 在整个 ROM 里**只出现 1 次**，且是在 `0x08598BC0`（ROM 尾部静态
   数据区）——它只作为**数据被存放**，没有任何代码把它当地址引用。这与 4.3.17
   的断点实验（`not-proven`）互相印证。

**所以**：A 键每次执行都会去读 `0x030059B8` 那张 13 项指针数组 + `0x03005BB8`
的计数，然后经由记录里的 `+0x20` 去访问一张**只被存放、几乎不被引用的 ROM 数据
表**。这条链的每一环现在都有引用计数或执行实验支撑，不再是形状猜测。

下一步可以直接查另外 4 个计数引用点（`0x080627F4` / `0x0806283C` / `0x08062920` /
`0x0806333C`）——它们和 A 键函数簇相邻，极可能就是「读取这张表并驱动流程」的
其余分支，玩家操作入口很可能就在其中之一。

### 4.3.19 更正 4.3.18：字节出现次数 ≠ 引用次数

4.3.18 说「`0x030059B8` / `0x03005BB8` 各有 5 处引用」，**这个计数不可信**。

反查 5 个出现位置里的 `0x08062920`：反汇编显示那里是函数体中间

```
0x0806291C: ldr  r0, [r7, r6]
0x0806291E: lsls r0, r0, #0xc
=> 0x08062920: ldrh r0, [r7, r6]      ← 指令，不是常量池
```

即该处只是**指令编码恰好组成了同样的 32 位字节**，并非引用。其余几个
`0x080627xx` / `0x080628xx` / `0x0806333C` 位置同理可疑。

我随后写了个「扫 `ldr rX,[pc,#imm]` 并解常量池」的自动检查，结果对三个地址
**全部返回 0 命中**——包括我用反汇编**亲手验证过**是常量池的
`0x08062A3C` 与 `0x08062A40`。**说明那个自动检查本身也是错的**
（大概率是指令解码或对齐算错），不能用来断言「没有引用」。

⚠️ **两条都别信**：
- 「各有 5 处引用」——字节搜索不等于引用；
- 「0 处引用」——我的自动检查解码有 bug。

**目前唯一被反汇编验证过的引用就是 4.3.10 / 4.3.12 里的那两条**：
`0x08062976: ldr r0,[pc,#0xc4]` → 池 `0x08062A3C` = `0x03005BB8`（计数）
`0x08062982: ldr r1,[pc,#0xbc]` → 池 `0x08062A40` = `0x030059B8`（指针表）

**下一步**若要枚举引用，必须用仓库自带的 `tools/disasm_thumb.py` 逐条人工核对
（它在这两个地址上是准的），不能再用字节计数，也不能用我自己写的解码器。

### 4.3.20 用项目工具核对完毕：每个全局只有 **1 处**真实常量池引用

用 `tools/disasm_thumb.py` 逐个核对其余 4 个候选位置，全部落在函数体中间，
且呈现**同一对指令**的重复形态：

```
0x080627F4: ldrh r0, [r7, r6]      0x0806291C: ldr r0, [r7, r6]
0x080627F6: lsls r0, r0, #0xc      0x0806291E: lsls r0, r0, #0xc
0x0806283C: ldrh r0, [r7, r6]      0x0806333C: ldrh r0, [r7, r6]
0x0806283E: lsls r0, r0, #0xc      0x0806333E: lsls r0, r0, #0xc
```

**结论（已验证）**：

| 全局 | 字节出现次数 | 真实常量池引用 |
| --- | --- | --- |
| `0x030059B8`（指针表） | 5 | **1**（`0x08062A40`，4.3.12 已核对） |
| `0x03005BB8`（计数） | 5 | **1**（`0x08062A3C`，4.3.10 已核对） |

其余 4 处全是**指令编码恰好组成的相同字节**。

**所以 4.3.18 的「5 处引用」应更正为「1 处」**，且 A 键处理链里
`0x030059B8` / `0x03005BB8` 各只被**读一次**——这两张表在这个函数里是

由此也说明：**下一步不能再靠搜地址找别的分支了**，因为根本没有别的引用点。
要理解 A 键之后发生了什么，只能在 `0x08062968` 之后的代码路径里往下走
（`bl 0x080627B0` 的函数体本身），而不是横向搜地址。

### 4.3.21 完整解码：`0x080627B0` 是「按有效位压缩记录数组」的循环

常量池（已逐条核对）：

```
0x080627F4 = 0x03005BB8   计数（字节）
0x080627F8 = 0x03003BB8   源记录数组基址
0x080627FC = 0x030059B8   目标指针数组
```

函数体逐条：

```
0x080627BC: ldr  r1, [pc,#0x34]   ; r1 = 0x03005BB8
0x080627BE: movs r0, #0
0x080627C0: strb r0, [r1]          ; count = 0
0x080627C4: ldr  r5, [pc,#0x30]   ; r5 = 0x03003BB8（源数组）
0x080627C6: ldr  r4, [pc,#0x34]   ; r4 = 0x030059B8（目标指针数组）
0x080627C8: adds r3, r1, #0       ; r3 = 计数地址
--- 循环 ---
0x080627CE: lsls r0, r1, #4
0x080627D0: subs r0, r0, r1       ; r0 = i*15
0x080627D2: lsls r0, r0, #2       ; r0 = i*60        ← 60 字节步长
0x080627D4: adds r6, r0, r5       ; r6 = &src[i]
0x080627D6: ldr  r1, [r6]
0x080627D8: movs r0, #1
0x080627DA: ands r0, r1            ; r0 = src[i].w0 & 1   ← 有效位
0x080627DE: cmp  r0, #0
0x080627E0: beq  #0x8062800       ; 无效则跳过
0x080627E2: ldrb r0, [r3]         ; r0 = count
0x080627E4: lsls r0, r0, #2
0x080627E6: adds r0, r0, r4       ; r0 = &dst[count]
0x080627E8: str  r6, [r0]          ; dst[count] = &src[i]
0x080627EA: ldrb r0, [r3]
0x080627EC: adds r0, #1
0x080627EE: strb r0, [r3]         ; count++
```

**已验证的机制**：`0x030059B8` 是一张**筛选后的指针表**，由 `0x03003BB8`
起的**源记录数组**按 `word0 & 1`（有效位）压缩得到，60 字节步长；
`0x03005BB8` 是筛出来的条数。这同时**独立验证**了 4.3.12 / 4.3.20 的观察：
记录等距 60 字节、指针表在 `0x030059B8`、计数在 `0x03005BB8`。

按地址反推，源数组下标 115 落在 `0x030056AC`（`(0x030056AC-0x03003BB8)/60 = 115`），
即源数组至少有 116 项、其中 13 项通过有效位过滤——与 `count == 13` 吻合。

**这一步的意义**：A 键每次执行都会重跑一次这个「压缩有效记录」的循环，
所以每次看到的 13 项都是**当时有效**的那些，而不是固定名单。这也解释了为什么
`+0xC1` 会随每次按 A 而推进——每次都在重新构建这张表。

⚠️ `src[i].w0 & 1` 的 bit 0 具体代表什么（存活 / 已激活 / 阵营 / HP>0）**仍未确定**，
不要按字面猜。要定性应对照不同状态下这张表的差异（例如敌方单位被击倒前后）。

### 4.3.22 源数组结构与一个会翻转的位

用 4.3.21 解出的机制回读（源数组 `0x03003BB8`、步长 60、目标 `0x030059B8`、
计数 `0x03005BB8`）：

**已验证 1：源数组至少有 128 槽，通过有效位过滤的恰好是尾部 13 个**——
`src[115]` 到 `src[127]`，在 base 与 A4 两个状态里**完全相同**（都是这 13 个）。

**已验证 2：`word0` 的 bit 24（`0x01000000`）在两个状态之间会翻转。**

```
base: src[115]=0x01001365  src[125]=0x014410A9  src[122]=0x004410A9  src[120]=0x004410A9
A4  : src[115]=0x00001365  src[125]=0x004410A9  src[122]=0x014410A9  src[120]=0x014410A9
```

即随着 A 键推进，有的记录 bit24 由 1→0（`01…`→`00…`），有的由 0→1。

**已验证 3：目标指针表的下标顺序不等于源下标顺序。**
base 的下标序列是 `115,125,126,119,121,122,124,120,127,117,118,123,116`——
明显是某种**排序后的行动顺序**，而不是内存顺序。

⚠️ **bit 24 是什么仍未确定**。在 base 与 A4 之间它同时出现 1→0 和 0→1 两种方向，
所以它不是单向的「已行动」标志；更像「轮到谁」这类**当前指位**，
或某种随回合轮转而移动的标记。**不要按字面猜**，需要更多状态样本
（例如按 B、按方向键、敌方回合时）才能定性。

⚠️ 同时修正 4.3.21 末尾那句「每条记录投影到单位池 `+0xC1`」——那是我的推测，
**在 `0x080627B0` 里没有这个动作**，该函数只构建指针表。`+0xC1` 的写入发生在
调用方（`0x08062982` 之后的循环体），**尚未验证**。

下一步两条：
1. 补更多状态样本（B / 方向键 / 敌方回合），给 bit 24 定性；
2. 反汇编 `0x08062982` 之后的循环体，验证 `+0xC1` 到底在哪被写。

### 4.3.23 调用方循环体解码：按 `record.w0` 的标志位分派

`0x08062982` 起的循环体（逐条）：

```
0x08062982: ldr  r1, [pc,#0xbc]    ; r1 = 0x030059B8（指针表）
0x08062984: lsls r2, r2, #0x10
0x08062986: asrs r0, r2, #0xe      ; r0 = i * 4
0x08062988: adds r0, r0, r1       ; &dst[i]
0x0806298A: ldr  r7, [r0]         ; r7 = &record[i]
0x0806298C: ldrh r1, [r7,#0x14]
0x0806298E: ldr  r0, [r7,#0x20]
0x08062990: lsls r1, r1, #2
0x08062992: adds r1, r1, r0       ; A = rec+0x20 + (rec+0x14 << 2)
0x08062994: ldrh r0, [r7,#0x16]
0x08062996: lsls r0, r0, #2
0x08062998: ldr  r1, [r1]         ; r1 = [A]
0x0806299A: adds r1, r1, r0       ; 加上 (rec+0x16 << 2) 存入栈
0x0806299C: str  r1, [sp]
--- 标志位分派 ---
0x080629A2: ldr  r1, [r7]         ; r1 = record.w0
0x080629A4: movs r0, #0x80
0x080629A6: lsls r0, r0, #0xa     ; 掩码 0x00020000 = bit 17
0x080629A8: ands r0, r0, r1
0x080629AC: cmp  r0, #0
0x080629AE: beq  #0x80629b4
0x080629B0: bl   #0x806321c       ; bit 17 置位 -> 调 0x0806321C
0x080629B4: movs r0, #0x80
0x080629B6: lsls r0, r0, #0xe     ; 掩码 0x00200000 = bit 21
0x080629B8: ands r1, r0, ...
```

**已验证**：

1. `record +0x14`（半字）、`+0x16`（半字）、`+0x20`（字）不是数据值，而是
   **地址运算的组成部分**：`A = rec+0x20 + (rec+0x14 << 2)`，再取 `[A]`，
   加上 `(rec+0x16 << 2)`。这解释了为什么它们看着像 RAM／ROM 地址却取不到
   合理结果——**它们必须参与运算才是指针**。4.3.16 那个「反汇编看起来像数据表」
   的现象也需要在这个语境下重读。
2. `record.w0` 是**位域标志**：本段已确认 bit 17（`0x00020000`）和
   bit 21（`0x00200000`）被逐一测试并分派调用（bit 17 命中时
   `bl 0x0806321C`）。加上 4.3.21 的 bit 0（有效位）和 4.3.22 观察到翻转的
   bit 24，`w0` 至少是 4 个已知语义位的位域。
3. 这是一台**按标志位分派的调度器**：遍历行动顺序表，对每条记录按其标志位
   调用不同子程序。

⚠️ 各标志位分别对应什么行为**仍未确定**；`+0xC1` 的写入点也**仍未在这一段里
出现**，需要继续往下（`0x80629CE` 之后）或在 `bl 0x0806321C` 里找。

下一步：反汇编 `0x0806321C`（bit 17 的处理例程），并继续看 `0x080629CE` 之后的
代码，找 `+0xC1` 的写入点。

### 4.3.24 `0x0806321C` 消费 bit 24 —— 直接印证 4.3.22 的翻转

常量池核对：

```
0x0806327C = 0xFEFFFFFF   掩码（0x08063232: ldr r1,[pc,#0x48]）
0x08063280 = 0x03000075   全局字节（0x0806323A: ldr r0,[pc,#0x44]）
```

函数体：

```
0x08063230: ldr  r0, [r7]        ; r0 = record.w0
0x08063232: ldr  r1, [pc,#0x48]  ; r1 = 0xFEFFFFFF
0x08063234: ands r0, r1          ; 清 bit 24
0x08063236: str  r0, [r7]        ; 写回 record.w0     ← bit 24 被消费
0x0806323A: ldr  r0, [pc,#0x44]  ; r0 = 0x03000075
0x0806323C: ldrb r0, [r0]        ; 读该全局字节
0x0806323E: cmp  r5, r0          ; 循环上界
0x08063240: bge  #0x80632f8
0x08063244: movs r0, #8
0x08063246: ands r0, r1          ; 再测 bit 3
```

**已验证**：

1. **`record.w0` 的 bit 24 在这个例程里被清除并写回**——它是**一次性消费的
   待处理标志**。这**直接印证**了 4.3.22 观察到的 1→0 翻转：那不是状态抖动，
   是标志被消费掉了。
2. 随后它读一个全局字节 `0x03000075` 作为**循环上界**，并在循环里再测 **bit 3**。
   `0x03000075` 是**奇地址**——按 GBATEK 惯例奇地址通常代表**位域**
   （`0x03000074` 的 bit 1），很可能是「轮到哪一方 / 哪一方输入」这类全局标志。
   **这一条是惯例推断，未验证**，要验证得读 `0x03000074` 并看它是否只用到 bit 1。

3. 由此可以给 `record.w0` 一个统一模型：**它是一张事件位域**——生产者置位、
   分派器按位测试并**清除**。bit 0（有效位，过滤用）、bit 3、bit 17、bit 21、
   bit 24 都在这张位域里。

下一步（收敛了）：
- 读 `0x03000074`，确认它是否真的只用 bit 1；
- 找出**谁置位** bit 24（生产者）——那才是「一回合开始/单位行动开始」的源头，
  也更可能直接对应玩家操作入口。

### 4.3.25 断点确认：调用点执行、bit 17 处理例程不执行

两个断点，各跑一次「入口快照 + 第 30 帧按 A」：

| 断点 | 含义 | 结果 |
| --- | --- | --- |
| `0x08062968`（`bl 0x080627B0` 调用点） | A 键入口 | **verified**，命中 |
| `0x0806321C`（bit 17 处理例程） | 分派到 bit17 时的目标 | **not-proven**，`actualPc: null`，从未执行 |

**已验证**：

1. **A 键确实走 `0x08062968` → `0x080627B0`**（压缩循环）→ `0x08062982`
   起的调度器。与 4.3.10 / 4.3.21 / 4.3.23 的静态解码完全吻合。
2. **`0x0806321C` 从未被执行**——按 A 那一刻**没有任何记录置 bit 17**。所以 A 键的
   效果**不是**走 bit 17 分支来的，4.3.23 里那处 `bl` 在本次路径上没走。
   这也说明：`0x0806321C` 属于**别的**触发路径（例如敌方回合或脚本事件）。

3. 命中时的寄存器给出循环上界的直接证据：

```
r1 = 0x007F0000   r2 = 0x00000080 (= 128)   r3 = 0x0300597C   r7 = 0x0300597C
```

**`r2 = 128`** 与 4.3.21 的步长推算（源数组至少 116 槽、尾部 13 个有效）完全一致，
**独立印证源数组就是 128 槽**。`r7 = 0x0300597C` 是一个记录地址
（`(0x0300597C - 0x03003BB8) / 60 = 127`，即源数组最后一槽）。

**因此 A 键的完整链路现在是有执行证据的**：

```
A  →  0x08062968 (verified)
      bl 0x080627B0   压缩：遍历 128 槽，按 word0 bit0 过滤出 13 条
      → 0x08062982    调度：遍历 13 条，按 word0 的各位分派
      → (bit17 分支本次未走)
```

下一步：要么找出 A 键实际走的那条分派分支（从 `0x080629CE` 往下逐个断点
验证），要么从 `record.w0` 在按下瞬间的实际取值反推。**不要靠猜**。

### 4.3.26 调度器续段解码：`0x0806321C` 的真实触发条件

`0x080629CE` 起：

```
0x080629CE: movs r1, #0xc
0x080629D0: ldrsh r0, [r7, r1]   ; 有符号半字 record+0x0C
0x080629D2: cmp  r0, #0
0x080629D4: bne  #0x80629da
0x080629D6: bl   #0x806321c     ; +0x0C == 0 -> 调用
0x080629DA: movs r2, #0xe
0x080629DC: ldrsh r0, [r7, r2]   ; 有符号半字 record+0x0E
0x080629DE: cmp  r0, #0
0x080629E0: bne  #0x80629e6
0x080629E2: bl   #0x806321c     ; +0x0E == 0 -> 调用
--- 二级指针链 ---
0x080629EC: ldr  r1, [r7,#0x1c]  ; record+0x1C
0x080629F0: adds r0, r0, r1
0x080629F2: ldr  r0, [r0]        ; 解引用
0x080629F4: mov  r8, r0          ; r8 = 二级指针
0x080629FC: ldrsh r1, [r0, r2]   ; 有符号半字 [r8]
0x08063002: cmp  r1, r0          ; 与 -1 比较
0x08063004: bne  #0x8062a0a
0x08063006: bl   #0x8063220
```

**已验证 / 更正**：

1. **`0x0806321C` 的触发条件不是 `w0` 的 bit 17，而是 `record +0x0C == 0`
   或 `record +0x0E == 0`**（两个有符号半字字段）。4.3.23 里「bit 17 置位则调
   `0x0806321C`」是**错的**——那是 `0x080629A6` 的掩码 `0x00020000` 测试点，
   但它命中后调的是 `0x0806321C`，而 4.3.25 的断点证明**这条路没走**；
   真正走的是这两处 `+0x0C/+0x0E == 0` 的比较。
2. 结合 4.3.25 的断点结果（`0x0806321C` 从未执行）可得一条**确定的负结论**：
   **A 键那一刻，13 条记录的 `+0x0C` 与 `+0x0E` 全部非零。**
3. `record +0x1C` 是**二级指针**： `[record+0x1C] + (前面算出的下标)<<2` 解引用
   得到 `r8`，再检查 `[r8]` 的半字是否为 `-1`。这是一条**指针链遍历**，说明记录
   之间还互相引用。

⚠️ 4.3.23 的「bit 17 -> 0x0806321C」解读需要按本节更正为「+0x0C/+0x0E 判零」。
**再次印证：静态解码必须用断点验证，否则分支归属会搞错。**

下一步：既然 `+0x0C` / `+0x0E` 都有具体语义候选，最快的定性方式是**在不同按键
下 dump 13 条记录的 `+0x0C` / `+0x0E` / `+0x1C`**，看哪些键会让它们变 0。

### 4.3.27 给 `+0x0C` / `+0x0E` 定性的结果：它们是常量，这条线到此为止

在 base / A1 / A4 三个状态下 dump 全部 13 条记录：

```
   i  +0x0C  +0x0E   +0x1C
   0    256    256   0x0812D0B4
   1    256    256   0x08165080
   ...
   9    256    256   0x08348820
  12    256    256   0x0812D2C0
```

**已验证**：

1. **`+0x0C` 与 `+0x0E` 在所有记录、所有状态下恒为 256**——它们**不是状态字段**，
   而是固定配置值。4.3.26 建议的「dump 这两个字段做定性」这条路**到此为止**。
   这也解释了 4.3.25 的断点结果：`0x0806321C` 要 `+0x0C == 0` 或 `+0x0E == 0`
   才触发，而它们恒为 256，所以永远不会触发。

2. **`+0x1C` 在三个状态下也完全不变**，且是 ROM 地址（`0x0812xxxx`–`0x0834xxxx`）。
   结合 4.3.26 的用法（`[record+0x1C] + (半字<<2)` 后解引用），它是一个
   **ROM 查找表基址**，不是会随回合变化的指针。

3. 因此：**记录里真正随回合变化的只有 `w0`**（4.3.22 观察到 bit 24 翻转、
   4.3.24 证明它被 `0x0806321C` 消费清除）。其余字段在本次观测范围内是常量。

**收敛**：能给这些记录做状态定性的字段只有 `w0`。下一步应当针对 `w0` 逐位
取样（在多种按键/相位下 dump 全部 32 位），而不是继续追 `+0x0C`/`+0x0E`/`+0x1C`。

⚠️ 同时提醒：本节的结论只在「base / A1 / A4」三个**按键之后**的状态上成立，
**没有覆盖敌方回合、脚本事件、战斗结算等其它相位**，不能外推成「这些字段
在整局游戏里都是常量」。

### 4.3.28 大更正：13 项表**不是稳定的**，会缩到 2 项、涨到 15 项

把本轮录到的**全部 83 个快照**（`original-*/step-*.ss9`）过一遍压缩机制：

**这推翻了 4.3.22 的说法**（「通过有效位过滤的恰好是尾部 13 个」）——那只在

**已验证 2：跨 83 个状态，`record.w0` 有 13 个位在变化**：

比此前只知道 bit 0/3/17/21/24 多得多；其中 bit 21 在这批样本里**没有**变化，

**已验证 3：`w0` 的低位整体在换**：

**含义（已验证部分）**：A 键反复执行时，有效记录集合在**剧烈变化**——
某些记录被 `w0 & 1` 过滤掉。这与「A 键推进行动顺序、有些单位就此退场」相符，
但**具体对应什么**（已行动被清退 / 阵亡 / HP 归零 / 其它）仍未确定，
**不要按字面猜**。

### 4.3.29 有效记录集合的完整演化轨迹（沿 `original-a14` 14 次 A）

```
step00-08  n=13  {115..127}                    ← 稳定 9 次按压
step09     n=15  {113..127}   gained [113,114]
step10     n=13  {115..127}   lost   [113,114]
step11     n= 2  {126,127}    lost   [115..125]   ← 11 条同时退场
step12     n= 2  {126,127}
step13     n= 3  {125,126,127} gained [125]
step14     n= 3  {125,126,127}
```

**已验证的三段现象**：

1. **step00–step08 高度稳定**：按 8 次 A，有效集合一直是 `{115..127}`。
   这与 4.3.22「base 与 A4 是同一批 src 115..127」一致，也与 4.3.25 的断点
   （`r2 = 128`、压缩 128 槽得 13 条）一致。

2. **step09 的 113/114 是瞬时出现**：按下后立刻出现、下一按就消失。它们大概率
   属于**某个临时生成的事件记录**（例如一次性的回合事件），不是常驻单位。
   ⚠️ 语义未确定。

3. **step11 的 11 条同时退场是整条链上最关键的事件**：`115`–`125` 在同一步里
   集体从有效集消失，只剩 `{126,127}`。**一次退场 11 条**不像「单个单位阵亡」，
   更像**相位边界**——例如一轮结束、大批记录被统一回收。

   结合 4.3.25 已知 `+0xC1` 行动标记在 A8 之后就卡在最后一个敌方单位不动，
   **step09–step11 这段很可能就是从「玩家侧」过渡到「敌方／下一阶段」的边界**，
   也正是在这一段，玩家操作入口最可能出现。

**下一步（现在有精确窗口了）**：从 `step-10-A.ss9` 起做**逐帧 PC 跟踪**
（不是逐按压），对比 `step-10 → step-11` 之间 PC 走过哪些新地址——
那几步就是相位切换真正执行的代码，比继续解 13 条记录的字段有效得多。

### 4.3.30 相位切换例程定位到 `0x080961F6`（断点确认）

在 `step-10-A.ss9`（4.3.29 里 11 条记录即将同时退场的那一步）做逐帧 PC 跟踪，
各 150 帧，一组不按键、一组第 40 帧按 A：

```
按 A 与不按 A 的 PC 在第 40 帧（施键帧）起共 81 帧不同
但「只在按 A 时出现」的地址只有一个：
    0x080961F6   ← 第 58 帧
```

断点验证（同一快照 + 第 40 帧按 A，20 秒超时）：

```
outcome : verified          actualPc : 0x080961F6
lr = 0x080961D7              （调用点）
r0 = 0x00000001   r1 = 0x00000001   r2 = 0x00000000
```

**已验证**：

1. `0x080961F6` **确实被执行**，而且**只在这个状态按 A 时才执行**——它在空闲态
   150 帧里从未出现。
2. 它位于 ROM 的**另一个区段**（`0x0809xxxx`），与 A 键处理链（`0x0806xxxx`）
   完全不同，说明这是一次**跨模块的相位切换调用**，不是同一函数内的分支。
3. 调用点在 `0x080961D7`，参数 `r0 = r1 = 1`、`r2 = 0`。

**这是目前最有可能通向「玩家操作入口」的一条线索**：
它恰好出现在 11 条记录同时退场的那一步（4.3.29 的 step11），
而且参数形态像「以 (side=1, index=1, flag=0) 发起一次阶段切换」。

下一步：
1. 反汇编 `0x080961D7` 附近的调用点，看 `0x080961F6` 是被谁按什么条件调用的；
2. 再对 `0x080961F6` 本体反汇编，看它做什么；
3. 追它调用的下游——那里很可能就是「玩家回合真正开始」的地方。

⚠️ 参数含义（side/index/flag）**纯属形态猜测，未验证**。

### 4.3.31 更正 4.3.30：`0x080961F6` 是循环回边，不是相位切换入口

反汇编后看得很清楚：

```
0x080961F6: cmp  r0, r3
0x080961F8: ble  #0x80961de        ← 回跳到 0x080961DE
...
0x08096216: pop  {r3, r4}
0x08096218: mov  r8, r3
0x0809621A: mov  sb, r4
0x0809621C: pop  {r4, r5, r6, r7}
0x0809621E: pop  {r0}
```

**已验证**：

1. `0x080961F6` 紧跟一条 `ble` 回跳到 `0x080961DE`，所以它是**循环的回边**，
   不是函数入口。4.3.30 说它是「跨模块的相位切换例程」**是错的**。
2. `lr = 0x080961D7` 属于**更外层的调用者**；`0x080961F6` 只是我们在
   `0x0806xxxx → 0x0809xxxx` 这段代码里恰好采样到的循环回边。
3. 但**「按 A 会让这个循环跑起来」这件事仍然成立**，而且有意义：
   循环条件是 `r0 > r3`（`r0` 递增到 `r3`），说明 A 在这个状态下驱动了
   **一次按计数上限迭代的循环**——与 4.3.29 观察到的「11 条记录同时退场」
   在语义上吻合（循环把一批记录处理掉）。

⚠️ `r0`/`r3` 是循环上界与计数器，**具体处理什么仍未验证**。
要定性，应该在 `0x080961DE` 循环体内部下断点，而不是在回边上。

**教训**：**单帧 PC 采样很容易落在循环回边或任意中间点，不代表函数入口。**
本会话第 11 次自我更正。下次定位应优先在**调用点**（`bl` 指令）下断点，
或者对候选函数**首地址**下断点，而不是对逐帧采样到的 PC。

### 4.3.32 循环体确认：`r3 = 6143`，是一次约 24 KB 的缓冲区重建

在 `step-10-A.ss9` + 第 40 帧按 A，对**循环体** `0x080961DE` 下断点：

```
outcome : verified     actualPc : 0x080961DE
r0 = 0x084098C2   ROM（源表）
r1 = 0            r2 = 0            r6 = 0            r7 = 0
r3 = 0x000018FF   ← 循环上界 = 6143
r4 = 0x02002880   EWRAM（目标缓冲区）
r5 = 0x06010000   VRAM / 调色板区
r8 = 0x085A4E14   ROM
sp= 0x0300116C    lr = 0x080961D7
```

**已验证**：

1. 循环体确实执行（`verified`），印证 4.3.31 的结论——之前在回边
   `0x080961F6` 采样到的确实是这个循环。
2. **循环上界是 6143**，即 `0x17FF`，约等于 `0x1800 = 6144` 次迭代，
   每次处理 4 字节 → **约 24 KB**。
3. 寄存器形态是「**从 ROM 表（`0x084098C2`）向 EWRAM 缓冲区（`0x02002880`）
   搬运/写入，并触及 VRAM（`0x06010000`）**」。

**含义（已验证部分）**：按 A 在这个状态触发的不是「逻辑」，而是一次
**约 24 KB 的显示/数据缓冲区重建**。这与 4.3.29 观察到的「11 条记录同时退场」
以及画面在此刻大幅变化相符——**整块场景数据被重新生成**。

⚠️ 缓冲区重建的具体内容（精灵？字形？调色板？）**未验证**；
`0x02002880` 处到底是什么结构需要进一步 dump，不要按字面猜。

下一步：
1. 在 `step-10-A.ss9` 与 `step-11-A.ss9` 两个快照之间 dump `0x02002880`
   起约 24 KB，比较差异——差异区就是这次重建**真正写了什么**；
2. `r0 = 0x084098C2` 是 ROM 源表，对它做同样的前后比较，可以直接看出
   「重建用的是什么模板」。

第 1、2 步都不需要猜，是纯比较。

### 4.3.33 缓冲区前后比较：24 KB 里只变了 145 字节

`step-10-A.ss9` 与 `step-11-A.ss9` 之间 dump `0x02002880` 起 `0x6000`（24,576）字节：

```
differing bytes = 145 (0.6%)
变化范围 = 0x02002880 – 0x02002939（仅前 185 字节）
14 个连续区段
```

部分对比（前 8 段）：

```
0x02002880  before dc6b5c33b802b001f8   after 626767676767676567
0x0200288A  before ea4b693a40019f53b... after 6767676767676967...
0x020028C8  before 000000             after 6c6454
0x020028D0  before 150300             after 696854
0x020028E0  before 00000000           after 67694154
```

**已验证**：

1. 6144 次迭代的循环**并没有把 24 KB 全部改写**——只有开头 185 字节发生变化，
   其余 24 KB 完全一致。所以那个循环要么是**条件性写入**（只在值不同时写），
   要么 24 KB 里绝大部分本来就相同。**不要把「6144 次迭代」理解成
   「24 KB 都被重写」**。
2. 「after」值里出现大量 `0x67 0x67 0x67…`、`0x69 0x68 0x54`、`0x6C 0x64 0x54`、
   `0x69 0x69 0x41 0x54` —— 高字节集中在 `0x41`–`0x69`、低字节多为 `0x41/0x54/0x67`，
   形态上像**按 3 字节或 4 字节打包的数据**（例如压缩图块、调色板索引、
   或某种 12-bit/16-bit 打包值），**不是可读的 ASCII 文本**（虽然单看像字母）。

⚠️ **这块数据到底是什么仍未验证。** 上面只是字节形态描述，
不要据此断定它���精灵、调色板还是压缩图块。

下一步（仍是纯比较）：
- 把 ROM 源表 `0x084098C2` 起同样长度 dump 出来，和「after」逐字节比，
  确认循环是否真的是「ROM → EWRAM 的解码搬运」；
- 再看这 145 字节的变化是否与 `0x020240C0` 单位池里 `+0xC1` 的变化一一对应。

### 4.3.34 循环是解码不是搬运；且退场时行动单位没变

**已验证 1：`0x084098C2` 的 ROM 源表与 EWRAM 缓冲不是原始拷贝。**

```
相同字节 1088 / 24576 (4.4%)
4 字节对齐块相同 3 / 6144
```

所以 4.3.32 里那个「从 ROM 表向 EWRAM 搬运」的判断**是错的**——
循环做的是**解码／解包**（把 ROM 里的压缩或打包格式转成运行期格式）。

**已验证 2：step10 → step11 的记录批量退场时，行动单位没有变。**

```
step10: 单位池 +0xC1 设在槽 [9]
step11: 单位池 +0xC1 设在槽 [9]
```

槽 9 是最后一个敌方单位（`(3,11)` 那一批里的最后一个）。**A 键并没有推进行动
单位**——这与 step00–step08 期间 `+0xC1` 逐个前移的行为**不同**。

⚠️ 由此，4.3.29 里把 step11 的 11 条记录集体退场解读成「相位边界」**只是推断，
未被验证**——退场时行动单位没切换，说明触发原因另有其物。

**当前最硬的两条结论**：
- A 键在这个状态下驱动的是一次 **6144 次迭代的解码循环**，输出到
  `0x02002880` 起的 EWRAM 区域（本次只有 145 字节实际变化）；
- 同一时刻 `+0xC1` 停留在槽 9 不动。

**下一步应直接对比 `+0xC1` 逐个前移的那段（step01–step08）与这段（step10–11）
的差别**，而不是继续猜退场原因——前一段是已知的「推进」行为，两段对比能直接
指出「推进」与「不推进」的条件差异。

### 4.3.35 「推进」与「不推进」的条件差异（把 14 步对齐看）

| step | `+0xC1` 所在槽 | n | 缓冲头部是否变化 |
| --- | --- | --- | --- |
| 0 | 1 | 13 | — |
| 1 | 2 | 13 | no |
| 2 | 3 | 13 | no |
| 3 | 4 | 13 | no |
| 4 | 5 | 13 | no |
| 5 | 6 | 13 | no |
| 6 | 7 | 13 | no |
| 7 | 8 | 13 | no |
| 8 | 9 | 13 | no |
| 9 | **9（不动）** | **15** | no |
| 10 | **9（不动）** | 13 | no |
| **11** | 9（不动） | **2** | **YES** |
| 12 | 9（不动） | 2 | YES |
| 13 | 9（不动） | 3 | no |
| 14 | 9（不动） | 3 | YES |

**已验证的规律**：

1. **`+0xC1` 逐个前移只发生在 step01–step08**：槽 1→2→3→4→5→6→7→8→9，
   每按一次 A 走一格，**正好 8 次走完 9 个位置**。
2. **step08 之后 `+0xC1` 永久停在槽 9**，无论后续按多少次 A、无论 n 变成
   15 / 13 / 2 / 3 都**不再前移**。
3. **解码缓冲第一次变化恰好在 step11**，与「n 从 13 掉到 2」是**同一步**。
4. step09 出现 n=15（两条瞬时记录）时，`+0xC1` 也已经不前移——但缓冲未变。
   所以「前移停止」早于「缓冲重建」。

**含义（推断，未验证）**：A 键的「推进行动单位」行为有一个**明确的终止点**
（9 个位置走完）。走完之后 A 不再推进单位，而是转入另一套行为——先出现瞬时记录
（n=15），再重建缓冲并把有效集合压到 2 条。

**这很可能就是「玩家操作入口」的边界**：前 8 次 A 是**顺序预览/推进**，
之后才进入真正的操作阶段。**下一步应该验证这一点**——在 step09 之后的某个状态
上，逐键探测 B / 方向键 / Start / Select，看是否会出现原版特有的菜单画面
（而 step00–step08 期间已经证明任何键都不会弹菜单）。

⚠️ 「很可能是玩家操作入口」是**推断**。下一步的逐键探测能直接证实或推翻。

### 4.3.36 两个决定性对照实验

**实验 A：step-11 之后所有按键无效。**

从 `step-11-A.ss9` 出发，8 个键各录一遍，另录一遍**同帧数的空闲对照**
（150 帧），逐一与空闲对照比：

```
A 0   B 0   Up 0   Down 0   Left 0   Right 0   Start 0   Select 0   （差异像素全为 0）
```

但与「按下之前那一帧」比，每个键都差 12,399 像素——**说明这 12,399 像素是
游戏自己在动，不是按键造成的**。

**已验证：step-11 之后是彻底的输入锁定状态**，任何键都不改变画面。

**实验 B：只有 A 会推进行动单位，Start 不会。**

从入口 base 出发，按 12 次 **Start**（hold 2 帧、settle 120 帧）：

```
step00..step12   +0xC1 = [1]（始终不动）   n = 13（始终不变）
```

对比同样步数按 **A** 的结果（`+0xC1` 1→2→…→9）。**这是干净的差分对照：
Start 完全不推进，A 才推进。**

**所以此前基于 A 的分析没有被推翻**——`+0xC1` 的逐格前移确实由 A 引起，
不是游戏自动播放。

⚠️ 但实验 A 带来一个**必须正视的新问题**：既然 step-11 之后任何键都无效，
而 step-08 之后 A 也不再推进，那么「玩家可操作的状态」**在按 A 的这条路上
根本到不了**。

**可能的解释（本轮无法区分，不要当结论）**：
1. 入口快照 `scenario-49-battle-14-entry.ss9` 根本不是玩家回合，而是
   **自动战斗／演示／结算**之类的状态——那样「找玩家操作入口」就是找错地方了；
2. 玩家操作入口需要**另一个条件**才能进入（某个脚本事件、某个特定按键组合、
   或某个计时条件）；
3. 2,400 帧零输入没有等到某个长动画播完。

**下一步建议（优先级高于继续解记录字段）**：先判定入口快照到底是不是玩家回合——
例如对比 `step-11` 之后画面里是否有「本回合玩家可操作」的 UI 特征，
或者用极长零输入（10,000+ 帧）看游戏是否会自己走出这个状态。

### 4.3.37 决定性：入口快照会无限等待输入，不会自己走完

从 `artifacts/runtime-checkpoints/scenario-49-battle-14-entry.ss9` 直接录
**6,000 帧（100 秒）零输入**：

```
6000 帧（100 秒），> 2000 像素的场景切换次数：0
```

加上 4.3.x 里已有的 2,400 帧，累计 **8,400 帧 / 140 秒，零次切换**——
只有选中单位的待机动画在动。

**已验证**：

1. **这个状态不是「会自己播完的长动画」**，也不是「需要等某个计时才推进」的
   状态。它**无限期等待输入**。
2. 因此 4.3.36 里「入口快照可能是自动战斗／演示／结算」这条解释**基本可以排除**：
   自动战斗会自己推进，而这里 140 秒纹丝不动。
3. 结合 4.3.36 实验 B（A 推进、Start 不推进），现在可以确定地表述为：

> **入口快照是一个等待玩家输入的、按 A 会推进行动单位的对战状态；
> 但推完 9 个位置后进入一个任何键都无效的输入锁定状态。**

**剩下的唯一核心问题变成**：这个输入锁定状态**是怎么出来的、怎么出去**。

可能的方向（本轮都未验证）：
- 锁定是「本场战斗的某种自动推进阶段」，需要某种条件才解除；
- 或者 A 推进到第 9 个之后，正确做法不是继续按 A，而是**换别的输入序列**
  （例如先 B 后 A、或方向键与 A 组合）；
- 或者这个入口快照本身取自一个**特殊存档状态**（例如跳过了某个剧情节点），
  导致流程卡在一个本不该停住的相位。

下一步优先级：
1. 从 step-11 那个输入锁定状态出发，测试**按键组合**（如 A+B、方向+A、长按 A、
   双击 A）而不只是单键——单键已证明无效，组合还没试；
2. 同时用 `rom/base.sav`（已为空 sav）与不加载 sav 的两种情况复现 step-11，
   排除「SRAM 进度位」把流程卡住的可能（4.3.x 已证明 SRAM 不影响 A 序列，
   但还没证明它不影响**相位推进**）。

### 4.3.38 按键组合测试：**设计缺陷，结果不可用**

从输入锁定状态 `step-11-A.ss9` 出发测了 10 种组合
（A,A / A,B / A,Right / B,A / Right,A / Down,A / Left,A / Up,A / A,A,A / Start,A），
每种在 `zero_input=60, settle=90, hold=4` 下录，最后一张约在**第 240 帧**；
对照组 `combo-ref` 用 `settle=300`，最后一张在**第 360 帧**。

结果：

```
A,A / A,B / B,A / Right,A / Down,A / Left,A / Up,A / Start,A   →  10,167 px
A,Right                                                        →       0 px
A,A,A                                                         →   5,862 px
```

⚠️ **这组数据不可用。** 对照组与实验组的采集长度差 120 帧，10,167 px 主要是
**动画相位差**，不是按键造成的差异；`A,Right` 恰好为 0 也只是因为它在 240 帧时
动画恰好与 360 帧的对照组重合。**没有做等长对照，就不能得出任何按键结论。**

**仍然有效的结论只有 4.3.36 实验 A 的那一组**——那组做了同帧数空闲对照
（150 帧 vs 150 帧），8 个单键差异**全为 0**，所以「step-11 之后任何键都无效」
是可信的。

**教训（第七条）**：**比较按键效果时，对照组与实验组的采集长度必须严格一致**，
否则动画相位差会淹没按键差异。同样的错误今天已经犯了两次：
4.3.36 第一次比「按下前」而非「同时长空闲」、4.3.38 又比了不同时长。

**要做按键组合实验，正确做法是**：固定 `zero_input` 与 `settle`，
让每种组合都从**同一个初始状态**出发、录**同样帧数**，再用同样时长的空闲对照。
本轮因上下文耗尽未重做，**不要引用上面那组数字**。

### 4.3.39 重做（按键数对齐）：单键无差别，但双键有差别

上一节的对照组仍然不等长——`mgba_original_s49_ui_boundaries.lua` 的

正确对照必须是**按键数相同**。

| --- | --- |
| `A,A` vs `Right,Right`（都是 2 键） | **10,167** |
| `B,B` vs `Right,Right`（都是 2 键） | **10,167** |
| `A,A,A` vs `A,Right,B`（都是 3 键） | **10,520** |

**可复现性已验证**：`eq-a2/step-01` 与 `eq-ref/step-01` 的 difference bbox 为

**已验证的结论（与 4.3.36 并列，需要合并理解）**：

- **单键**：8 个键与等长空闲对照**全部为 0 差异**（4.3.36）。

也就是说：**按下第一个键时游戏对输入无反应，按下第二个键时输入开始起作用。**

⚠️ **这与「step-11 之后彻底输入锁定」的说法冲突，本轮无法判定哪个解释对。**
可能的读法（本轮都未验证，不要当结论）：
- 第一个键的响应被 120 帧 settle 吃掉了，差异要到第二个键之后才体现；
- 游戏有一个「按一次键才解除锁定」的门槛，第二次才是生效的那一次；
- 或者 10,167 px 仍然是动画相位差，只是这次两组恰好错开（但可复现性已验证，
  所以若真是相位差，它必须是**按键触发的确定性相位差**，而不是随机漂移）。

**下一步必须做的是带相位对齐的对照**：同一个初始状态、同一按键数，

### 4.3.51 本轮教训

**教训（第十条）**：**全屏同索引差分只有在两侧底图逐像素一致时才有意义。**
底图不同的情况下，它既不能当验收闸门，也不能用来选基线——排名会是噪声。
应先按**画面内容**选定语义相同的基线，再用**区域差分**衡量共享 UI，
并把「区域」写成显式输入而不是临时裁剪。

**教训（第十一条）**：**「重制做不到 X」要先确认输入路径**。本次差点把
「重制按 A 进不了战斗」写成产品缺陷，实际是入口需要 `Down,Down`。
必须从**上电**跑一条完整规范契约，不能从历史快照续跑后倒推。

### 4.3.52 字形缺陷的根因链：字模图集是**按坐标从截图里裁**的，而输入已被清理

4.3.49 的 D3（木叶丸→打木叶）与 D6（佐助→巨助）指向同一个缺陷类别。顺着
`battle_runtime_scene.cpp` 的字形取值往上查，链路是：

```
render_text → bn::sprite_text_generator → bn::sprite_font
    ├── battle_ui_font_utf8_characters   （401 个字符，索引 = 图集内位置）
    ├── battle_ui_font_character_widths  （496 = 1 + 94 + 401）
    └── battle_ui_font.bmp               （495 格 = 94 ASCII + 401 字符）
```

**先排除掉两个看似可疑的地方**（都排除了）：

1. **不是排序问题。** `battle_ui_font_utf8_characters` 开头是
   `没(6CA1) 有(6709) 漩(6F8C) 涡(6DA1)`，**不是码位升序**。但
   `bn::utf8_characters_map` 用的是**哈希表 + 线性探测**（`third_party/butano/
   butano/include/bn_utf8_characters_map.h:37`），与顺序无关，怀疑不成立。
2. **不是数量不一致。** 字符 401、宽度 496、图集 495 三个数字初看矛盾，实际
   正好满足 Butano 自己的断言（`bn_sprite_font.h:40` `minimum_graphics = 94`）：
   图集 = 94 + 401 = 495，宽度 = 1 + 94 + 401 = 496。**字体管线本身是对的。**

**真正的根因**在 `tools/generate_butano_battle_identity_content.py`：
`generate_ui_font_bitmap()` **不用字体文件画汉字**，而是对
`SCENARIO_41_ORIGINAL_GLYPH_SOURCES` 里的 **100 个字符**，按**硬编码的
(left, top) 坐标**从录下来的原版截图里裁 8×16 的格子；另外
`ORIGINAL_UI_ASCII_GLYPH_SOURCES` 用同样方式替换了 10 个 ASCII 格。

我们关心的字恰好在表里，而且**全都挤在同一行、8 像素间距**：

| 字符 | 来源截图 | 坐标 |
| --- | --- | --- |
| 助 | `scenario-41-prebattle-reference-v1/screens/menu-0.png` | (96, 8) |
| 木 | 同上 | (104, 8) |
| 叶 | 同上 | (112, 8) |
| 丸 | 同上 | (120, 8) |

**「坐标表整体错开一格」是一个尚未验证的假设，不能当结论用。**

它在表面上能解释 D3：只要这张表错开一格，木叶丸就会渲染成「打木叶」。
但**现有观测反过来否证它**：D6 里「助」渲染**正确**（只有「佐」错）。
如果是整体错位，「佐助」两个字应当**都**错。这说明缺陷**不是均匀的整体错位**，
更像是**个别字符的坐标取错**——而哪些字符取错，恰恰需要读源截图才能判定，
而源截图已经不在。

**所以当前可以确定的是「字形取值链路依赖一张已失效的坐标表」，
不能确定的是「具体哪几个字符取错了」。** 修复 D3 的前置条件是恢复
`menu-0.png` 并逐格复核那 4 个坐标，而不是直接改代码。

**而现在这张表已经无法验证，也无法修正**：生成器依赖的 10 个源截图在工作树里
已经不存在，`generate_ui_font_bitmap()` 直接抛 `FileNotFoundError`。

### 4.3.54 D6 的机制：说话者标签有**两条**渲染路径，与 D3 完全无关

4.3.49 把「佐助→巨助」记成 D3 的同类实例。**这是错的，现更正。**

对白说话者标签（`battle_runtime_scene.cpp:4263` 起）有两条路径：

  **与 `SCENARIO_41_ORIGINAL_GLYPH_SOURCES` 那套坐标表无关**。

**所以 D6 与 D3 不同源，修 D3 的坐标表不会修好 D6。**

### 4.3.55 D6 根因锁定在**准备字体图集**，且它比 UI 字体落后一代

继续查 D6，得到三个决定性事实。

**(1) 佐助走的是文本路径。**
`battle_unit_dialogue_label_frames` 里只有 `鸣人(id 1)→slot 0`、`小樱(id 3)→slot 1` 非 -1，
**佐助(id 2) 是 -1**，所以标签由 `story_text_generator` 画，
用的是 **`battle_preparation_sprite_font`**，不是 `battle_ui_font`。
这解释了为什么 4.3.53 修完 UI 字体后对白③ **288 像素完全没变**。

**(2) `battle_preparation_font.bmp` 的「佐」这一格里躺着「巨」。**
按 `94 + 字符下标` 取出该图集的格子逐一看：

| 字符 | 下标 | 图集格 | 内容 |
| --- | --- | --- | --- |
| 佐 | 9 | 103 | **巨**（错） |
| 助 | 10 | 104 | 助（对） |

**(3) 但 truetype 回退路径渲染出的是空白，不是巨。**
`_render_glyph` 用 `/System/Library/Fonts/PingFang.ttc`，在
`UI_FALLBACK_FONT_SIZE=8` 和 `FONT_SIZE=14` 两个字号下，
`佐` `助` 的渲染结果**都是全空白**。而 `佐`/`助` **不在 `PREPARATION_ORIGINAL_GLYPH_SOURCES` 里**，
按当前生成器重算，这一格应该是**空的**，不是「巨」。

**所以磁盘上的准备字体图集是旧一代坐标表的产物**——那一代里 `佐` 有裁剪坐标，
而那个坐标裁到了「巨」。现在生成器已经没有这个坐标了，于是直接重算反而会变成空白。

**已量出「佐助」的真值坐标**（原版 `walk-original-a24/step-13-A.png`，
对白③说话者标签，列投影得到精确 8 像素网格）：

| 字符 | x | y | 说明 |
| --- | --- | --- | --- |
| 佐 | **24** | 104 | 墨迹 y105–118 |
| 助 | **32** | 104 | 墨迹 y105–118 |

**(4) 更正 4.3.54 的一个说法。**
我当时写「精灵表 slot 0 里放的图不对」。那是因为我把 **32×16 的整张标签**
按 8×16 切成了 4 格再读——**切错了**。精灵表是 32×32、两行，每行是一张完整标签：
第 0 行读起来不是「鸣人」，第 1 行是「小樱」。sprite 表本身不是 D6 的来源，
**D6 来自准备字体的文本路径**。

**按硬编码坐标从截图裁字形，坐标错了就静默出货错字形**，
而且这里**跨了两套字体图集**——修 UI 字体不会修准备字体。

> **教训（第十四条）**：**修一张图集不等于修了所有图集**。
> `generate_preparation_font_bitmap` 先调 `generate_ui_font_bitmap` 再覆盖，

### 4.3.56 D6 修了一半：字形已正确，剩下是**调色板索引错位**

按 4.3.55 量出的坐标执行：

1. 把 `佐 → (24,104)`、`助 → (32,104)` 加进 `PREPARATION_ORIGINAL_GLYPH_LINES`
   （源指向原版对白③帧 `walk-original-a24/step-13-A.png`，
   已确认该裁剪区域只有三种颜色，全部能进现有分类）；
2. 把 `repatch_battle_ui_font_glyphs.py` 扩展出 `--kind preparation`，
   可重建 `battle_preparation_font.bmp`（它依赖 UI 图集基底 + 三张自有表）；
3. 局部重建：**86 个字符里只有 6 格变化**
   `佐(103) 助(104) 克(138) 拉(370) 吧(388) 力(337)`——后四个是继承自 UI 基底的同类错位；
4. 重建 ROM `ae576ca9…`，上电重录。

**结果：重制的对白③说话者标签现在渲染出正确的「佐助」**
（旧 ROM 是「巨助」）。

**但像素差异反而从 226 升到 271**——因为**缺陷换了一类**：
原来错在**字形**，现在字对了，错在**颜色**。

**颜色缺陷的根因**：生成器把裁剪结果按固定索引烘进图集
（`ORIGINAL_UI_FOREGROUND_INDEX = 2`、`ORIGINAL_UI_SHADOW_INDEX = 5`），
而说话者调色板 `battle_ui_dialogue_speaker_palette.bmp` 的索引分配完全不同：

| 索引 | 颜色 | 是否说话者标签该用 |
| --- | --- | --- |
| 2 | (57, 66, 57) 灰绿 | ✗ 这是当前烘进去的 |
| 5 | (173, 181, 156) 浅灰绿 | ✗ 这是当前烘进去的 |
| **6** | (189, 173, 222) **浅紫** | ✓ |
| **14** | (115, 33, 255) **深紫** | ✓ |

原版标签用的是 (115,33,255) 与 (189,173,222)，
生成器把它们判成前景(2)/阴影(5)，于是渲染成灰色。

**为什么不能简单改成 14/6**：准备字体图集被**多个 UI 元素共用**
（对白文本、目标状态、结果面板…），每个元素各有一套调色板，
把索引改成某一套专用的会破坏其它使用者。正确做法是给说话者标签
**单独一张按该调色板索引烘的图集**（就像现有的
`battle_ui_dialogue_speaker_label` 预烘焙表那样，只不过由字体生成而非手挑截图）。

**无连带回归**：其余四组基线像素数完全不变
（对白①62 / 对白②62 / 命令菜单 1740 / 结算 37）。

> **教训（第十五条）**：**像素差异变大不一定是变坏**。必须同时看**缺陷类别**：
> 「字错了」变成「颜色错了」，数字会上升但语义在改善。
> 报告差异时要区分「形状 / 颜色 / 布局 / 内容」，只报一个总数会误导。

**修好后**：`移／动／术／・／忍／具／休／息／行／动／结／束` 全部与原版帧**逐索引一致**，
命令菜单文字区 **489 → 252**。

### 4.3.61 「查克拉」是一个字、两种字号：**共享图集格子不可能同时满足**

剩下的 252 像素是命令菜单里的「查克拉」。原版在这里把它画成**16 行满高**，
而在**状态栏**里画成 **8 行紧凑**——而重制的状态栏已经与原版**逐像素一致**。

我第一次把 `查／克／拉` 从「紧凑」改成「满高」并重建，结果：

* 状态栏在**每一个非菜单帧**上凭空多出 252 像素差异（bbox `(136,144)-(160,160)`）；
* 命令菜单文字区虽然从 489 降到 0，但整体从 1448 涨到 **1564**。

**这是净负**，于是把共享格子**改回紧凑**并补测试钉死
（`test_chakra_stays_compact_for_the_status_hud`）。

**结论**：原版给这两个界面用了**不同的字形资源**（同一批字符、两套图集或两套渲染路径），
重制只有一张共享的 `battle_ui_font`，**结构上无法同时正确**。
真正的修法是给命令菜单单独做一张满高图集（新增 atlas + 新生成器条目 + 新 `bn::sprite_font`），
属于新增资产的工作，不在本轮「换图块/换坐标」的范围内。

> **教训（第十九条）**：**改共享图集格子前，先量它在别的界面上有没有已被验证正确的用法**。
> 本轮的差分数字本身没有报警——命令菜单的数字变好了，
> 是**逐帧回放所有其它步**（发现每一步的状态栏都多出 252 像素）才暴露的回归。
> 「某个区域变好」不能推出「整体变好」。

### 4.3.62 「查克拉」满高字形：**不用新做图集，换一张已有的字体**

4.3.61 留了个两难：共享的 `battle_ui_font` 里 `查/克/拉` 只能是紧凑（8 行）或满高（16 行）
二者之一，而原版两处都要。本轮的做法是**不新增第三张图集**，而是查清已有的
`battle_action_menu_font` 里那三格是什么。

**结论**：`battle_action_menu_font` 里的 `查/克/拉` **逐索引等于原版命令菜单画的那三格**
（16 行满高）。它本来就是满高的——动作菜单里那句红色的「消耗查克拉」在原版 step-21
是满高，而重制与原版在那一帧是 **0 像素**，说明这份满高字形早就被验证过。

**改法**：`render_command_menu_text()` 多收一个 `action_generator`，
只有 `battle_command_type::replenish_chakra` 这一条标签改用动作菜单字体，
其余标签照旧走 UI 字体；两者的**字符表顺序和字宽数组完全相同**
（`battle_ui_font` 与 `battle_action_menu_font` 共用同一份 401 字的
`utf8_characters`，宽度也一致），所以切换不需要任何额外对齐。

**为什么不用新做图集**：每张字库图集在 GBA 上占 31 KB VRAM
（495 格 × 64 字节），场景里已经同时构造了 9 个字体生成器。
再插一张会挤爆 OBJ VRAM，而「换用已有字体」是**零 VRAM 开销**。

**修复结果**：命令菜单文字区 **252 → 0 像素**；
整屏 1448 → **1196**（剩下的全是左侧单位精灵）。
状态栏全程保持 0 像素——共享格子没有被动过。

> **教训（第二十条）**：**同一个字在不同界面有两种字号时，先去看别的图集里有没有已经对的那一份**。
> 本轮一开始的判断是「需要新做一张满高图集」，那要动 VRAM 预算、生成器条目和
> `bn::sprite_font` 三层；而**现成的动作菜单字体里已经躺着那三格满高字形**，
> 并且因为动作菜单本身就是 0 像素差，这个事实**早就有验证**。
> 「共享资源不够用」的时候，先确认是不是**用错了那张**。

### 4.3.63 左侧单位精灵 1196 像素：**不是调色板问题，是另一张美术**

4.3.61 之前我把这 1196 像素记成「原版把佐助画成灰阶、重制是彩色」。
本轮做了定量判定，**这个说法不成立**。

**判定方法**：在命令菜单帧里取左侧单位区域 `(78,46)-(116,104)`，
把每个差异像素的 `(原版色 → 重制色)` 统计成映射表。
若是**纯调色板差异**（原版给同一个 OBJ 换了一个灰阶调色板），
每个原版色必须**只对应一个**重制色。

实测：29 个原版色里 **25 个都指向多个重制色**
（例如原版 `(33,33,33)` 分别落到 `(74,107,181)` 36 像素、`(49,49,115)` 19 像素、
`(255,255,255)` 17 像素……）。映射是**多义的** ⇒ **不是换调色板**。

**再看轮廓**：把原版帧里「够灰且够暗」的像素取出来当剪影，得到一个
`x≈80..105, y≈50..100` 的连通块；把两侧同一区域做红/绿叠加后，
红绿像素**在同一剪影内交错**，说明二者占用同一块地盘，但**内部结构不同**。

**结论**：原版这一帧的左侧单位是**另一张美术**（不同姿势/不同动画帧）**并且**是灰阶，
而重制画的是彩色正面站姿。两件事叠在一起，所以像素数大。

**还没查清的**：原版「非当前行动单位要去色」这条规则是否普遍成立
（鸣人作为当前行动者是彩色的，这支持该假设）；
以及原版那一帧对应的是 `field_idle_and_movement` 序列的**第几帧**——
这需要按帧回放原版录屏、定位动画相位。**本轮未取证，标为待查。**

### 4.3.64 左侧单位「去色」不是资源，是**运行时写 PRAM**（并推翻 4.3.63 的一半）

4.3.63 已确认命令菜单帧里左侧单位**不是纯调色板差异**。本轮继续查下去，结论比「另一张美术」更硬：

**第一步：位移不是原因。** 在 `(76,30)-(130,106)` 上穷举 `dx,dy ∈ [-6,6]`，
最低差异出现在 **`dx=0, dy=0`**（1058 像素），其它任何位移都是 2935 像素以上。
⇒ 不是 D1 站位偏移造成的假象。

**第二步：把判据收窄到精灵自己的像素。** 之前那张映射表混进了草地（两侧布景本就不同），
不能作数。改为只取「原版里够灰够暗、且与重制不同」的像素（712 个），
统计 `原版色 → 重制色`：14 个原版色里 **13 个指向多个重制色**
（`(33,33,33)` 指向 20 个，`(0,8,8)` 指向 19 个……）。
⇒ 在精灵自身像素上也不是纯调色板映射。

**第三步（决定性）：扫描全部单位图集的调色板。**
`butano-sequel/graphics/battle_unit_*.bmp` 共 62 个角色 × 9 个 slot。
逐张读调色板，检查「非透明条目里 `r==g==b` 的条数」：
**灰阶调色板 0 张**。

**结论**：原版把非行动单位画成灰阶这件事，**不是**提取出来的美术资源——
提取阶段（`generate_butano_battle_unit_visual_content.py` 按 slot 的 `palette_pointer`
读 PRAM）根本没有拿到任何灰阶调色板。所以原版是**在运行时改写 OBJ 调色板 RAM**
（典型的「非当前单位去色」做法），而重制**从来没有这一步**。

**顺带更正 4.3.63 的另一半**：我说「是另一张美术」下得太满。
在精灵自身像素上映射仍然多义，除了「美术不同」还有一个未排除的解释——
重制按 `component_track_count` 把单位拆成**多个 OBJ 部件**绘制，
部件之间的像素落位只要有 1 像素偏差，就会让名义同位置的像素取到不同颜色，
同样表现为映射多义。**这一条本轮未取证，标为待查。**

**因此下一步是两件事，不是一件**：
1. 实现运行时去色（需要先从 ROM 取证原版的去色算法：是和 `r+g+b>>2` 之类的
   固定混合，还是查表）；
2. 把两侧的单位精灵按部件逐层对齐，确认美术是否真的不同。

### 4.3.65 D4 精确化：**回合横幅的完整实现规格**（已量好，未开工）

### 4.3.66 **单位去色机制查清：原版有一条专用的灰阶 OBJ 调色板组**

4.3.64 只说「是运行时写 PRAM」。本轮**直接把 PRAM 读出来了**。

**探针**：mGBA 的 Lua 暴露了 `emu.memory[<区域名>]:readRange(偏移, 长度)`
（区域名见 `src/gba/core.c` 的 `_GBAMemoryBlocks`：`palette`/`vram`/`oam`/`io`）。
新增两个工具：

* `tools/butano/mgba_gpu_state_dump.lua`——载入存档、跑 N 帧、导出
  `pram.bin`/`vram.bin`/`oam.bin`/`io.bin` 与清单；
* `tools/butano/capture_s49_gpu_state.py`——驱动层，把存档/ROM/mGBA/Lua/守卫的
  **哈希全部写进 `inputs.json`**，并在缺文件、尺寸不对、没写完成标记时**失败关闭**。

> 踩过的坑：区域是 `emu.memory["palette"]`，**没有** `emu.memory.domains` 子表。
> 写成 domains 会让 Lua 报错、脚本中止、mGBA 继续空跑到守卫判定 idle 超时——
> 表现为「exit 124」而不是脚本错误，很有迷惑性。

**结果**（原版 `walk-original-a24/step-18-A.ss9`，即命令菜单帧）：
OAM 在用的调色板组是 `{1, 2, 3, 14, 15}`，其中 **bank 3 的 16 项里有 15 项是灰阶**：

| 索引 | bank 1（彩色，佐助） | **bank 3（灰阶）** |
| --- | --- | --- |
| 0 | `(198,132,255)` 透明 | `(165,165,165)` |
| 1 | `(33,33,33)` | `(33,33,33)` |
| 2 | `(82,90,99)` | `(90,90,90)` |
| 3 | `(41,41,99)` | `(99,99,99)` |
| 4 | `(255,0,0)` | `(49,49,49)` |
| 5 | `(239,189,165)` | `(198,198,198)` |
| 6 | `(198,132,107)` | `(148,148,148)` |
| 7 | `(132,82,49)` | `(90,90,90)` |
| 8 | `(123,132,115)` | `(107,107,107)` |
| 9 | `(74,74,74)` | `(74,74,74)` |
| 10 | `(74,107,206)` | `(214,214,214)` |
| 11 | `(49,49,115)` | `(156,156,156)` |
| 12 | `(255,255,255)` | `(255,255,255)` |
| 13 | `(206,206,206)` | `(206,206,206)` |
| 14 | `(165,165,165)` | `(165,165,165)` |

**两条 bank 是逐索引的孪生体**：1/9/12/13/14/15 六项在两边完全相同
（那就是描边与高光的灰阶梯），其余十项被换成灰。

**帧验证**：原版帧那个窗口里出现的 **13 种灰阶色，全部**由这条 bank 解释，
无法解释的为 **0**。

**三个要点**

1. **索引 0 不再是透明洋红**，而是浅灰 `(165,165,165)`。
   但帧里并没有出现浅灰矩形底——实测该窗口内 `(165,165,165)` 只有 41 个**散落**像素
   （重制版同窗口有 48 个），所以精灵 tile 并不用索引 0 作透明像素。
2. **不是亮度公式**：4.3.64 试过 `max`、`(r+g+b)/3`、亮度加权，最多复现 14 色里的 8 色。
   这条 bank 是**随 ROM 携带的调色板**。
3. **提取阶段拿不到它**：`battle_unit_visual_catalog.json` 里每个 slot 各有
   `palette_pointer`，62 角色 × 9 slot 一张灰阶的都没有。灰阶 bank 不被任何 slot 引用，
   只在运行时被切上去——这就是重制版「从来没有这一步」的根本原因。

**产物**：`butano-sequel/graphics/battle_unit_dimmed_palette.bmp`（16 色）
由 `tools/butano/generate_unit_dimmed_palette.py` 从 PRAM **读出**并落盘，
收据 `artifacts/s49-original-gpu-20261020-v2/dimmed-palette-receipt.json`
记录探针输入哈希与 bank 号。门禁 `tests/test_s49_unit_dimmed_palette.py`（10 项，全绿）
把这 16 个数和 PRAM 绑在一起，**不允许它们退化成一对手抄的常量**。

> **教训（第二十三条）**：**「是运行时行为」是可以被读出来的**。
> 本轮之前三轮都在从渲染结果反推机制（映射是否多义、灰阶是否服从某个公式），
> 而 mGBA 的 Lua 一直就开着 `readRange`——**直接读 PRAM 一分钟就能定案**。
> 判断机制类问题，凡涉及调色板/图块/VRAM，**先找能不能把硬件状态读出来**，
> 再考虑从像素反推。

> **教训（第二十四条）**：**脚本失败不一定表现为脚本错误**。
> Lua 里一句 `emu.memory.domains[...]` 拿不到值，会让脚本中止而 **mGBA 继续空跑**，
> 最后由守卫判成 `exit 124` 的 idle 超时。排查时要意识到「超时」可能是
> 「脚本早就死了」而不是「脚本跑得慢」。

### 4.3.67 bank 3 就是灰阶单位——用「清零一组调色板再渲染」判定，并查出接线的前置阻塞

4.3.66 找到了灰阶调色板，但「PRAM 里有这条 bank」还不等于「这条 bank 画的就是那个单位」。
本轮用**最便宜的办法**判定：把 bank 3 的 32 字节清零，用仓库里现成的

bbox `(109,34)-(145,89)`——鸣人的位置，差在动画相位（探针取 savestate 后 2 帧，

**接线的前置阻塞（本轮的新发现）**

把 bank 3 全清零之后，那个单位变成**纯黑剪影**——**轮廓一模一样**，
而且**空隙处仍然是草地**。

如果精灵 tile 里有索引 0 的像素，清零后那些像素会变黑（索引 0 变成了 `(0,0,0)`）。
空隙没变黑 ⇒ **原版的单位 tile 根本不引用索引 0**。

而重制版这边：

```
butano-sequel/graphics/battle_unit_01_idle.bmp
  palette[0] = (197,131,255)   ← 透明洋红
  索引 0 的像素占 1045/2048 ≈ 51%（用得最多的索引）
```

**原版的透明索引与重制版不同。** 灰阶 bank 的索引 0 是浅灰 `(165,165,165)`，
所以**直接把这条调色板套到重制版的单位精灵上，会给每个被去色的单位画上一个灰底矩形**。

⇒ **调色板已经备好，但接线被一个更底层的差异挡住**：
先要弄清原版单位 tile 的透明索引到底是什么、重制版为什么是洋红。
这条差异本身就是要修的，而且它同时关系到「美术是否真的不同」那个未决问题（4.3.63/4.3.64）。

门禁 `tests/test_s49_unit_dimmed_palette.py`（**12 项全绿**）把这件事钉住：
其中一项**专门记录这个阻塞点**，并写明「一旦重制版图集不再用索引 0，
这条门禁就会失败，提醒去接线而不是继续假设它被挡住」。

> **教训（第二十五条）**：**调色板的「身份」要靠消融实验确认，不能靠读 OAM 猜**。
> 本轮按 OAM 字段算出的坐标与实际渲染位置差了 16 像素，一度以为单位不在 OBJ 里；
> 而「把这一组 32 字节清零再渲一次」一分钟就把「是谁画的」和「画在哪」同时钉死，
> 还顺带测出了透明索引这件只有消融才能看出的事。

### 4.3.68 **左侧单位精灵的真正根因：重制版摆错了人（原版是木叶丸，重制是佐助）**

4.3.63/4.3.64 把这 1196 像素记成「美术不同」，本轮把它查到底了。

**第一步：把原版那个单位变回彩色。** 用探针拿到的 PRAM，把灰阶 bank 3 整段替换成
彩色 bank 1 重渲同一帧——那个单位立刻变成**彩色**。于是可以直接看它是什么。

**第二步：它长这样。** 黑发、**白色护额**、**红色领口**、**黄衣蓝裤**、**前倾前冲的姿势**。

**第三步：重制版提取的全部美术里没有它。**
`battle_unit_02`（宇智波佐助）9 个 slot 共 **54 帧**全部铺开看过：
**全是同一套蓝衣白裤的正面/微侧站姿**，没有前倾红蓝造型。

**第四步：遍历全部 62 个角色找匹配。** 把原版那个单位（彩色化后）取剪影，
对每个角色每个 slot 的每一帧做 IoU 匹配：

| 候选 | 最佳 IoU |
| --- | --- |
| **character 30（木叶丸）** | **0.917** |
| character 2（宇智波佐助） | 0.670 |
| 重制版自己画的那个 | 0.778 |

**character 30 = 木叶丸**（`unit-identities.json`：30 → 木叶丸），
其 idle 第 6 帧正是那个前倾、黄衣蓝裤的造型。

**结论**：**两侧在同一位置站着的是不同的人。**
原版：右边是当前行动者鸣人（彩色，带选择框），**左边是木叶丸**（去色）。
重制：右边鸣人，**左边是佐助**（彩色）。

这不是美术问题，也不是调色板问题，而是**单位池／站位数据的差异**——
重制版把队友摆在了原版摆被保护对象的位置上。S49 的任务本来就是
「保护木叶丸不被蜜蜂攻击」，木叶丸才是场上那个要被保护的人。

**因此前两轮的两处定性都要更正**：
- 4.3.63 说「是另一张美术」——**部分成立**（画确实不同），但**根因是画错了角色**；
- 4.3.64 说「原版运行时写 PRAM 去色」——**成立**，但它只是**症状**；
  把角色摆对了之后，还需要单独实现去色才能逐像素一致。

**顺带钉死的两条事实**（可复用）：
1. **去色只在「单位选定并落位之后」出现**：14/15/16 步（蜜蜂待机、回合横幅、移动选格）
   的 PRAM 里**没有**灰阶 bank，17 步起才有。
2. **原版的单位 tile 不引用索引 0**：把 bank 3 全清零后，单位变成**纯黑剪影、
   轮廓不变、空隙仍是草地**——说明空隙不是「索引 0 被清零」的结果。
   而重制版单位图集的**索引 0 是透明洋红且占全部像素的 51%**。
   ⇒ 灰阶 bank 的索引 0 是浅灰，**直接换调色板会给每个去色单位画出灰底矩形**。
   这是接上去色之前必须先解决的**更底层差异**。

**新增工具**：`tools/butano/compare_s49_unit_silhouette.py`（剪影 IoU）、
`tools/butano/identify_s49_unit_slot.py`（在 9 个 slot 里找）、
`tools/butano/identify_s49_unit_character.py`（在 62 个角色里找）。
门禁 `tests/test_s49_inactive_unit_identity.py`（3 项，全绿）把「原版去色的是木叶丸、
不是佐助」钉死。

> **教训（第二十六条）**：**像素不一致时，先问「画的是不是同一个人」**。
> 本轮为这 1196 像素花了三轮（判定是不是调色板 → 是不是公式 → 是不是另一张美术），
> 答案却是**角色就摆错了**。而判据早就在手边：
> 原版 OAM 里那个单位用的是 **bank 1**——而 bank 1 的调色板与重制版的
> `battle_unit_02_idle`（佐助）**几乎逐项相同**，
> 说明原版**给木叶丸配了佐助的调色板**（同一套 16 色布局），
> 这才让人误以为是「同一个角色的不同美术」。
> **调到色板那一层时，顺手确认这个调色板属于谁**。

结论比单个单位严重得多。

**证据其实一直在录屏里，只是被结算面板的同名列掩盖了**：

> 不是「面板上有没有那一行字」。

我当时只对比了**两个移动范围网格帧**（原版 step 16 / 重制 step 19），

**所以真实差别是**：重制版的蜜蜂在**流程推进到命令菜单阶段之前一直都在**，
进入命令菜单阶段后**从画面上消失**；原版的蜜蜂则一直留在场上

⇒ **D2-b 仍然结案，但结案方式不同**：蜜蜂**在场上**、**不在轮转里**，

### 4.3.71 场面差异的机制层根因：场景 14 的三个变体 + 战役名册只登记了 1/2/3

把重制版的数据层翻出来，场面差异的机制就清楚了。

**S49 指向 battle_id 14**（`battle_campaign_route.h`：
`{ 49, 14, 0, 50, battle_campaign_party_policy::team_seven, "S49" }`，
第 3 个字段是 **variant = 0**）。

**battle 14 的三个变体**（`generated_battle_scenario_content.h`）：

| 变体 | 内容 |
| --- | --- |
| **0** | 固定：鸣人(1)@(11,6)、**佐助(2)**@(10,14)、小樱(3)@(8,14)、**木叶丸(30)**@(8,7)、**蜜蜂(55)×5**（敌）@ (3,4)/(4,8)/(3,11)/(6,6)/(5,13) |
| 1 | 空 |
| **2** | 部署：3 个 `deployment_placeholder`（255/254/253）@(11,6)/(10,14)/(8,14) + **木叶丸(30)**@(8,7) + **蜜蜂(55)×5** |

**两个变体都带木叶丸和 5 只蜜蜂**，区别只在「我方那三格是固定角色还是玩家部署」。

**但重制版的名册里根本没有木叶丸**：

* `ensure_battle_campaign_character()` 在整条路线里**只对角色 1/2/3 调用过**；
* `battle_campaign_party_capacity = 3`；
* `team_seven` 策略强制 `party = {1, 2, 3}`（鸣人/佐助/小樱）。

⇒ **重制版的 S49 玩家必定是鸣人/佐助/小樱三人**，而原版那一场
（命令菜单里鸣人在右、**木叶丸**在左）显然是**两人 + 被保护对象**的阵容。

**这解释了三件事**

1. **左侧单位是佐助而不是木叶丸**（4.3.68）：名册里没有 30，
   部署/固定位只能填上 1/2/3。
2. ~~**蜜蜂在流程推进后消失**（4.3.70）~~〔**已被 4.3.72 更正**〕：
   原版在命令菜单阶段**同样**看不到蜜蜂，两侧一致，**不是差异项**。
3. **地图不一样**（水渠缺失）：场景 14 的 `grid_width/height` 与布景资产
   属于另一套，镜头自然对不上。

**因此下一步不是改像素，是改阵容**：

* 让 S49 走 **variant 2**（玩家部署 + 木叶丸 + 蜜蜂），
  并把 `request.load_policy.placeholder_characters` 填成玩家实际带的三人；
* 让战役名册能登记 **30（木叶丸）** 与 **55（蜜蜂）**；
* `battle_campaign_party_capacity` 从 3 放宽到能装下「三人 + 木叶丸」。

这三处改完，场面才会对；场面不对之前，任何逐像素验收都只是在一张错的底图上比对。

### 4.3.72 **再更正 4.3.69–4.3.71：蜜蜂不是差异项，差异只剩「木叶丸 vs 佐助」**

把蜜蜂模板扫完**两边全部帧**之后，4.3.69 与 4.3.70 的说法都要收回。

| 帧 | 原版 | 重制版 |
| --- | --- | --- |
| 02–07 | 有（42/42） | 06 起有 |
| 08–09 | — | 有 |
| 10–13 | 有（26–36/42） | 有 |
| 14–15 | — | 有 |
| 16（移动网格） | **有（42/42）** | **有（36/42）** |
| 17 起（命令菜单阶段） | **没有** | **没有** |

**结论**

1. **两侧都有蜜蜂**，都在移动阶段可见；
2. **两侧都在进入命令菜单阶段后看不到蜜蜂**——所以「蜜蜂消失」是**共同行为**，
   **不是差异项**。4.3.70 说的「原版的蜜蜂一直留在场上」是错的；
3. **4.3.69 说的「重制版一只都没有」也是错的**——
   错因是**只对比了两帧就推广到全场**（这已是本会话第三次犯同类错误）。

**因此 D2-b 的正确结论**：蜜蜂**在场上**（移动阶段可见）、**不在轮转里**
（命令菜单阶段两侧都不在场），结算面板里那列「蜂 3 / 蜜蜂 1」是**敌方统计**，
不是轮转成员。**两侧一致 ⇒ D2-b 不是差异项，从差异台账里移除。**

**那么命令菜单那 1196 像素到底是什么？**
**只剩一处：原版那个位置站着木叶丸，重制版站着佐助。**
（4.3.68 的剪影 IoU 0.917 vs 0.670 是直接证据。）

**以及场面差异的机制（4.3.71）**依然成立：S49 走 battle 14 variant 0，
但重制版的战役名册只登记角色 1/2/3、`party_capacity=3`、`team_seven` 强制三人，
所以**木叶丸排不进玩家的三格**。

> **教训（第二十八条）**：**「某一帧没有」≠「这一战没有」**。
> 这是本会话第三次犯同一个越界错误（4.3.45 的步号表、4.3.69 的蜜蜂、
> 以及更早的「结算面板同名列」）。
> 代价是三份需要作废的结论。
> **凡是要下「全场」结论的断言，扫描范围必须覆盖全场**——
> 本轮把蜜蜂模板扫完两边全部帧，只花了 20 分钟，就把这三份结论一次性订正了。

### 4.3.73 **去色接线的关键一步：索引 0 必须换成透明色**

4.3.67 指出接线被一个更底层差异挡住：原版的单位 tile **不引用索引 0**
（清零调色板后单位是纯黑剪影、空隙仍透草地），而重制版单位图集
**用索引 0 作透明洋红**且占全部像素的约 51%。

**原版 bank 3 的索引 0 是浅灰 `(165,165,165)`**。如果直接把它套到重制版的单位精灵上，
那个索引 0 就会把**精灵的透明像素画成浅灰**——每个被去色的单位背后都会多一个灰底矩形。

**解法**：接线用的调色板**把索引 0 换成重制版的透明洋红 `(197,131,255)`**，
索引 1–15 原样用 bank 3 的灰阶。

理由：原版那个浅灰索引 0 **在原版里从来不会被渲染**（原版的 tile 不引用它），
所以「索引 0 是什么颜色」在原版是**无关量**；而重制版的索引 0 **必须透明**。
把无关量换成重制版需要的值，画面结果与原版一致。

`tools/butano/generate_unit_dimmed_palette.py` 产出的
`butano-sequel/graphics/battle_unit_dimmed_palette.bmp` 就是这样：
索引 0 = `(197,131,255)`，索引 1–15 = bank 3 的灰阶。

**接线路径**（`battle_runtime_scene.cpp`）

* 新增 `dimmed_unit_palette()`：用
  `bn::sprite_palette_items::battle_unit_dimmed_palette.create_palette()`
  建**一份共享**调色板（不是每单位一份），避免 VRAM 浪费；
* `update_unit_sprites()` 增加 `dim_inactive_units` 开关；
* 条件：`dim_inactive_units && !palette_selected && state.selected_unit != unit.id`；
* 开关由 UI 层决定：命令菜单或动作菜单在场时为真。

**为什么条件里带 UI 层**：原版只在**命令菜单/动作菜单阶段**把非行动单位去色
（4.3.70 实测：移动选格阶段两边都没有去色，命令菜单阶段开始有）。
重制版流程顺序不同（它的移动网格在命令菜单**之后**），
所以用「命令菜单/动作菜单在场」来对齐是直接可用的判据。

### 4.3.78 回合横幅的施工单（已查清六字来源、面板约束与裁剪陷阱）

**木叶丸那 860 像素纹丝不动**。

「原版 = slot 0 sequence 2（帧 6）」与「重制 = sequence 1（帧 3/4/5）」那件事，

> 本轮用底图模板匹配把镜头坐标直接量出来，5 分钟就证明了两侧是同一张图、同一镜头；
> 而在此之前，我已经基于「地图不同」这个误读，推导出了「坐标系不可比」这个错误结论，
> 并据此否掉了一个本该先做的方向。
> **「差很多」的第一反应应该是「先把坐标系量出来」，而不是「那肯定是底图不同」。**

### 4.3.81 **修好一个真正的 AI 逻辑 bug：单位走完后面朝走的方向，而不是盯着目标点**

4.3.80 把 1142 像素拆成「木叶丸 ~860 + 鸣人 ~285」两笔，并指出木叶丸那笔
**既不是站位也不是朝向**（AI-OFF 时他确实换到了 (8,7)+right，差异却没变）。
本轮顺着「坐标怎么换算」把最后一层剥开了。

**先解坐标**：镜头偏移实测 (240,24)，而 S49 的场景网格只有 15 宽、地图有 30 列
⇒ **场景格 → 地图格 要 +10 列**。于是：

* 原版木叶丸屏幕 x 80..111 → 地图格 20 → **场景格 (10,7)**
* 重制版木叶丸场景格 (10,7) → 屏幕 x 80..111（与调试输出一致）

**⇒ 两侧木叶丸在同一格 (10,7)**，他确实从起点 (8,7) 走了两格——
**站位从来就不是差异**。那 860 像素是**朝向**，而朝向又取决于
**AI 选的那个方向**。

**根因在 `battle_ai.h` 的纯移动分支**：

```cpp
candidate.facing = objective.has_focus_position ?
    facing_toward(destination, objective.focus_position, acting_unit.facing) :
    facing_toward(acting_unit.position, destination, acting_unit.facing);
```

**有焦点位置时，朝向取「从终点看向焦点」**。
木叶丸的焦点是 (12,3)、终点 (10,7) ⇒ `dy = -4` 比 `dx = +2` 大 ⇒ 判成 **`up`**。
而原版给他的是 **`right`**——**他走了两格向东，所以面朝东**。

**⇒ 规则应是：单位走完后面朝它走的方向；焦点位置只决定他往哪走，不决定他看哪。**

**改动**（`battle_ai.h`，只删掉焦点分支）：

```cpp
candidate.facing = facing_toward(
        acting_unit.position, destination, acting_unit.facing);
```

**影响范围可控**：全仓库只有 battle 14（S49）给 AI 单位设了 `has_focus_position`
（`battle_mission_rules.h` 里用 `battle_id == 14 ?` 条件开），
所以这条规则改动**只影响 S49**。

**实测结果**（重录 + 区域差分收据 `region-diff-moveface/`）

| 基线 | 改前 | 改后 |
| --- | --- | --- |
| 对白①小樱 / ②鸣人 / ③佐助 | 0 | **0** |
| 动作菜单 21↔21 | 0 | **0** |
| **命令菜单 18↔18** | 1142 | **746** |
| **命令菜单 20↔20** | 1117 | **297** |

木叶丸的姿态现在与原版**一致**（两边都是前倾侧身）；
剩下的 461 像素是**动画帧的相位差**（同一条 sequence 里的第几帧），
另 285 像素在**鸣人**身上（他的动作姿势/相位）。

门禁 `tests/test_s49_ai_move_facing.py`（2 项）把这条规则钉住：
纯移动分支里不得再出现 `focus_position`，并且必须从 `acting_unit.position` 起算。

> **教训（第三十五条）**：**「差很多」要先拆成互斥的几笔，再逐笔找根因**。
> 1142 像素拆成 860/285 两笔之后，860 那笔因为「换到 (8,7)+right 差异不变」
> 而被证明**不是站位也不是朝向**——这个反证直接指向了**朝向的来源**，
> 顺着 `candidate.facing` 一路查到 `battle_ai.h` 的纯移动分支，
> 才找到一个真正的 AI 逻辑 bug。
> 一开始直接调 AI 参数（4.3.77/4.3.79）是在**没有拆账**的情况下试的。

### 4.3.87 **M2 对齐层：原版 38 态常量 + 相位↔原版态绑定（可机器核验）**

原版战斗场景按 **16-bit 状态码**分派，逆向侧已穷尽 38 个非默认态
（`rom-battle-controller-cfg-v1`，65,536 输入分母，canonical 映射 `ce5e8ea2…`）；
重制侧跑的是自造的 24 值 `battle_scene_phase`，**两者之间没有任何映射层**。
本轮补上这一层：

* 新生成器 `tools/butano/generate_battle_original_states.py` ⇒
  `butano-sequel/game/include/konoha/battle_original_states.h`：
  * `enum class battle_original_state : std::uint16_t` —— 原版 38 个状态码；
    **26 个有名字的保留名字，12 个语义未定的只留码**（`unknown_0010` 等），
    **不编造语义**；
  * `battle_scene_phase_binding`（`direct` / `sub_phase` / `remake_only` / `candidate`）
    与 24 行绑定表，**按重制枚举的声明顺序**排列 ⇒ 相位的序号即行号；
  * 头部注释写明来源族与 manifest 哈希 ⇒ 与逆向成果的血缘可查。
* `battle_scene_controller.h` 引入该头文件，并让 `battle_scene_snapshot`
  暴露 `original_state_code` 与 `phase_binding` ⇒ **运行时能看见对齐关系**。
* 门禁 `tests/test_battle_scene_phase_mapping.py`（6 项）：生成头与状态表一致、
  24 个相位逐一映射、绑定种类与状态表一致、**12 个未定态仍只有码**、
  17 个「原版有、重制无」的状态有记录。

**⇒ 本轮没有把 24 个相位**换成** 38 个原版状态码**，原因要写清楚**：
8 个重制相位是原版一个态的**子相**、4 个是重制新增、12 个原版态语义未定、
17 个原版有而重制还没有 ⇒ 现在硬换会把「未定的语义」编进运行时。
**正确的顺序是：先补齐逆向侧缺的证据（12 个未定态的 handler 级断言 + 哈希绑定 checkpoint），
再把子相结构（`原版态 × 子相`）落进控制器。**
对齐层已经把这件事变成可核验的清单，而不是一次大重构。

### 4.3.88 **0xFBFF：原版 ROM 里唯一的损坏终止符（已让重制侧记录，不再静默吞掉）**

#### 4.3.88.1 事实

原版 ROM 全表只有**一处**损坏的 component 终止符：角色 26 / 视觉槽 2 / 帧 2，
`0x0825A8E4` 的四个字节是 `fffb0000`（signed = **-1025**）。
渲染器只认 **-1**（`0xFFFF`）作为组件链结束，于是它**不在这里停下**，
而是继续每 20 字节一个 component 往后读——原版的运行期轨迹确实读到 4 个指针。
逆向侧用**一字节 A/B**（`0x0825A8E5` 的 `0xFB` → `0xFF`）闭合并给出 control ROM 哈希。

#### 4.3.88.2 重制侧原来的行为

`tools/generate_butano_battle_unit_visual_content.py` 的终止检查只看**低 10 位**
（`next_tile_index & 0x3FF != 0x3FF`）：`0xFBFF & 0x3FF == 0x3FF` ⇒ **检查通过，损坏被静默吞掉**，
生成产物里什么痕迹都没留。

#### 4.3.88.3 改法与门禁

生成器现在把缺陷**写进产物**（与逆向侧导出器的词汇一致）：

```json
"frame_trailer_raw_hex": "fffb0000",
"frame_trailer_signed_value": -1025,
"renderer_terminator": false
```

* 全表 62 角色 × 342 个有效视觉槽里**只有这一帧**的终止符非法 ⇒ 与逆向侧「只有一处」一致。
* 门禁 `tests/test_s49_rule_fbff.py`：**10 项全绿**（原为 8 绿 + 2 expectedFailure）。

**⇒ 故意不应用那一字节修复**：原版确实越界渲染，**修了就与原版不一致**。
剩下的未闭合项是**重制运行时不会越界**（重制只画列出的 component），
该角色不在 S49 出场 ⇒ 对 S49 像素无影响，但已进台账
（`s49-fbff-corrupt-terminator`）。

> **教训（第四十条）**：「修好一个缺陷」要看**原版是不是也这样**。
> 这里的 `0xFBFF` 看着像数据损坏，但原版**带着它运行**、并且因此多画了 4 个 component；
> 一份 1:1 复刻必须保留这个行为，**记录**它，而不是**修掉**它。

### 4.3.89 **更正：「隐/年 加粗笔画」缺陷不存在**（取证脚本错标）

台账里那条「动作菜单 17 格中 2 格仍差（105/128、69/128）」是**取证脚本的错标**：

### 4.3.90 移动网格：覆盖色规则两侧已经一致，缺的是「不可达区域」的暗化罩（**4.3.93 撤回了本节末尾那条「不是切调色板」的结论**）

W8 的 P2 门禁把「移动范围网格是抖动遮罩、19 个底色各对应多于一种覆盖色」钉成了规则。
本轮逐像素复核后的结论更细：

| | 原版 step-19 | 重制 step-20 |
| --- | --- | --- |
| 战场区青色覆盖色种类 | **18** | **19** |
| 与对方**共有**的覆盖色 | **18**（全部） | **18**（全部） |
| 出现最多的 6 种覆盖色 | (123,236,190) 2530、(138,252,200) 1415、(97,246,190) 1251… | (123,236,190) 2411、(138,252,200) 1353、(97,246,190) 1195… |

⇒ **覆盖色的规则与颜色两侧完全一致**（同样的 18 种、同样的主色、计数只差可达格数量）。
⇒ 「染色规则不同」这个说法**不成立**；W8 的门禁记的是**覆盖色**这层。

**真正差的是不可达区域**：在原版里，**不可达格整体被蒙了一层冷色**（连岩石都蒙了），
在重制里不可达格保持原色：

| 同一屏幕像素 | 原版 | 重制 |
| --- | --- | --- |
| 草地 | (132,189,49) | (132,189,49) |
| 同一点（蒙罩后） | (128,164,76) | (132,189,49) |
| 岩石 | (255,222,148) | (255,222,148) |
| 同一点（蒙罩后） | (205,185,138) | (255,222,148) |

⇒ 蒙罩**不是**「一个固定色按 alpha 混合」：用 14 组 (底色→蒙罩色) 反解，
单一 (T, alpha) **无解**（绿/蓝通道各自要求的 alpha 不一致）⇒
它要么是**两层叠加**，要么原版用的是**同一批地图图块的暗化副本**。

⚠️ **4.3.93 撤回本节最后那条推论**：「PRAM 里搜不到这 9 个暗化色 ⇒ 不是切调色板」。
那个搜索**在错误的色彩空间里做**：PNG 的颜色与调色板 RAM 的颜色**不是同一个空间**
（同一帧里 PNG 162 色中有 97 色不在该帧调色板里），而且当时比对的 PNG 与 PRAM
**来自不同的 mGBA 构建**、甚至不是同一帧。
⇒ 「不是切调色板」只能算**未被证明**，不能算已被否证。
（4.3.93 同时给出了新的、可复算的原版渲染结构证据。）

⇒ 重制侧其实已经有这一档图块（`battle_range_ui_tile_kind::blocked`，
颜色 RGB5(9,9,9)/(4,4,4)），只是移动网格**没有把不可达格画成 blocked**。
⇒ **下一轮的具体目标**：确认原版的不可达区暗化是「暗化图块副本」还是「叠加蒙罩」，
再在 `battle_range_ui_style.h` 里补上（当前移动网格基线 2917 像素里 1024 像素是这一项）。

### 4.3.93 **移动网格：原版的 GPU 状态（同帧收据）+ 撤回 4.3.90 的「不是切调色板」**

4.3.90 把「移动网格的暗化罩」判成「不是切调色板」，理由是
「在原版 step-19 的 PRAM 全部 256 项里用 |Δ|≤6 搜这 9 个暗化色，全部无命中」。
本轮把这个论证**推翻为「未被证明」**，并给出新的、可复算的原版渲染结构。

#### 4.3.93.1 先把证据链修好：**同帧收据**

问题出在证据本身：仓库里归档的 **PNG** 与 **PRAM/VRAM dump 来自不同的 mGBA 构建**
（PNG 来自 `2cc5c36d…`，dump 来自 `d1a9c231…`），而且 dump 与 PNG **不是同一帧**。
颜色是**跨空间**比较的。

本轮新增 `tools/butano/mgba_frame_palette_sequence.lua` +
`tools/butano/capture_s49_frame_palette.py`：**一次运行、同一帧**里同时落
截图 + 调色板 RAM + VRAM + 显示寄存器（收据在
`artifacts/s49-original-movegrid-frame-v1/` 与 `artifacts/s49-original-banner-frame-v1/`）。
两个坑已留痕：mGBA 的调色板域名是 **`palette`** 不是 `pram`；
探针早死时外部只看到**守卫 idle-timeout exit 124 且零输出**（像「跑得慢」，其实是脚本早死了）。

#### 4.3.93.2 同帧自洽性检查：横幅帧自洽，移动网格帧不自洽

| 帧 | 画面颜色数 | 其中是本帧调色板条目的 | 不在调色板里 |
| --- | ---: | ---: | ---: |
| 回合横幅（step-15） | 81 | **81** | **0** |
| 移动网格（step-19） | 162 | 65 | **97** |

且六帧里 `BLDCNT` 恒为 `0x0000`（**没有 alpha 混合**）、调色板逐帧几乎不变
（每帧至多 1 项变化、最大差 2）。

⇒ 移动网格帧里有 **97 个颜色既不在调色板、也不是混合产物**。
**GBA 画不出这种颜色** ⇒ 截图与调色板**在同一帧内也不在同一个色彩空间**
⇒ 任何「在 PRAM 里搜 PNG 颜色」的论证（包括 4.3.90 那条）**方法上就不成立**。

#### 4.3.93.3 原版移动网格的 GPU 结构（可复算的硬事实）

| 项 | 移动网格帧 | 回合横幅帧 |
| --- | --- | --- |
| `DISPCNT` | `0x1D40` | `0x1940` |
| 差异位 | **bit 10**（`0x0400`）⇒ **BG3 的字符基址在 `0x00000` 与 `0x10000` 之间切换** | — |
| `BLDCNT` | `0x0000` | `0x0000` |
| BG3 屏基址 | `0x1800` | `0x1800` |
| BG3 tilemap | **1024 格全部非零**，两枚主图块 `57792`×764、`448`×140 ⇒ **整屏一层** | — |
| 镜头 | `BG0HOFS=240 / VOFS=24` | 同 |

#### 4.3.93.3.1 **更正本节自己的一版解读**：「BG3 换了图块」是错的

最初据 `DISPCNT` bit 10 翻转写成「同一张 BG3 tilemap 在两屏读到不同图块数据」。
**本轮用本机 mGBA 源码与 VRAM 实测把它否掉了**：

- mGBA 渲染器里背景的字符基址**只来自 BGxCNT**
  （`src/gba/renderers/video-software.c`：`bg->charBase = GBARegisterBGCNTGetCharBase(value) << 14`），
  **DISPCNT 在 mode 0 下不参与字符基址** ⇒ bit 10 的差异**不改变画出来的东西**；
- BG3 引用的图块在**两帧里都是空的**（主图块 `0xE1C0` 的 32 字节全是 0）
  ⇒ **BG3 根本没画东西**。

⇒ bit 10 的翻转只是游戏自己写的一个**软件标志位**（硬件在 mode 0 下忽略它），
**不是机制**。这一版解读已撤回。

#### 4.3.93.3.2 真正在变的是 **BG2**：移动网格是画在 BG2 上的一层

逐层比两帧的 tilemap（VRAM 屏基址：BG0 `0x0000` / BG1 `0x0800` / BG2 `0x1000` / BG3 `0x1800`）：

| 层 | 两帧之间改动的格子 | 优先级 |
| --- | ---: | ---: |
| BG0（地图） | **1** / 1024 | 3 |
| BG1 | **0** / 1024 | 1 |
| **BG2** | **706** / 1024 | **2** |
| BG3 | 175 / 1024（但图块为空 ⇒ 不画） | 0 |

⇒ **地图层几乎没动（BG0 只差 1 格），动的是 BG2**；
而 BG2 的优先级 2 **高于**（压在其上于）BG0 的优先级 3。
⇒ **移动网格的覆盖层和「暗化」都是 BG2 的一层图块画在地图之上**，
**不是给 BG0 的调色板染色**。

⇒ 这一条**对重制侧是可执行的**：重制现在用 `battle_range_ui_style.h` 的
`blocked` 图块去表达「不可达」，若要 1:1，应当按**BG2 覆盖层**的语义去对齐
（层、优先级、覆盖图块的颜色集合），而不是继续在 BG0 调色板上找暗化。

#### 4.3.93.3.3 再进一步：**地图层在两帧之间逐字节相同** ⇒ 「给底色加冷色」在硬件层被否证

| 项 | 横幅帧 vs 移动网格帧 |
| --- | ---: |
| BG0（地图）调色板（PRAM bank 0–3） | **0 项变化** |
| BG0 的图块数据（VRAM `0x4000`，BGCNT 字符基址块 1） | **0 字节变化** |
| BG1/BG0 共用的同一块图块区（`0x4000`） | **0 字节变化** |
| **BG2 区域（VRAM `0x1000–0x1800`）** | **706 字节变化** |

⇒ **地图层画出来必然一模一样**（调色板与图块都没动）
⇒ **「不可达区被蒙了一层冷色」不可能是给地图底色加的冷色**——地图层压根没变。
⇒ 冷色只能来自**另一个层**（两帧之间被重写的那 706 字节所在的层）。
⇒ 这也解释了 4.3.90 那条「单一 (T, alpha) 无解」：如果冷色来自**另一个层**的像素，
它就不是「同一批底色的颜色混合」，而是**空间上的一层覆盖** ⇒ 单色 α 解自然不成立。

⚠️ 仍未定：那 706 字节属于**哪一层**的哪一部分。本轮**两次否掉了自己的读法**：

1. 「是 BG2 的仿射参数」——否：`0x1000` 处是**重复的 16 位图块模式**
   （`0xC100` / `0xC180` 交替），**不是**仿射参数；且 `BG2CNT=0x0202` 的
   size=0、仿射寄存器 PA/PD=`0x0100`、X/Y=0 在两帧完全相同。
2. 「是 BG2 的 tilemap」——也存疑：mode 0 下 BG2 应当是**仿射层**，
   它的屏基址里放的却是图块样式的数据。

⇒ 能负责任地登记的只有三条：
① **地图层（BG0 调色板 + 图块）逐字节未变**；
② **被重写的是 `VRAM 0x1000–0x1800` 这一带**（706 字节，分布在 `0x10C0–0x167E`，
其中 409 字节落在 `0x1000–0x13FF`）；
③ **该区域的数据形态是重复的 16 位模式**（`0xC100/0xC180`）。
⇒ 剩下的是把「这条 2 KB 区间到底属于谁」查清（可能需要回到 ROM 侧的资源指针反查）。

#### 4.3.93.3.4 **又撤回一条**：「覆盖层 = 3 个精灵」站不住

上一节把「移动网格帧比横幅帧多 3 个 OAM 槽位」写成「覆盖层是精灵画的」。
**复核后不成立**：OAM 的槽位编号会被游戏重新分配，必须按**条目**（图块/调色板/位置）比：

| | 回合横幅帧 | 移动网格帧 |
| --- | --- | --- |
| 单位 A（2 个 64×64 + 2 个 16×16） | y20/16 tile136、y21/15 tile128、标记 tile109 | 同上 |
| 单位 B（护送单位） | **y41/y35 tile138**、标记 tile110 | **y40/y36 tile136**、标记 tile112 |
| 顶部 y=4 的 16×16 | 无 | tile216(pal4)、tile208(pal0)、tile192(pal4) |

⇒ 那 3 个「多出来的槽位」= **移动了一格的护送单位 + 它的两个标记**（图块号随动画帧变），
**不是一个覆盖层**；真正的差异只剩**顶部 y=4 的三个 16×16 标记**。
⇒ 同时核对：两帧的 **WININ=0x00F0 / WINOUT=0xFFFF / MOSAIC=0x3F3F / BLDCNT=0x0000 完全相同**
⇒ 暗化**不是窗口、也不是 alpha 混合**（而且两帧都开着 mosaic——
这正是「截图里有些颜色不在调色板里」的原因：mosaic 会把像素与邻格混合）。

⇒ **能负责任登记的**：
① 地图层（BG0 调色板 + 图块）逐字节未变 ⇒ 暗化**不是**给地图调色板染色；
② 窗口/混合/马赛克两帧一致 ⇒ 不是窗口、不是混合；
③ OAM 差异 = 护送单位移动 + 顶部三个 16×16 标记。
⇒ **暗化层的归属仍未定**：候选只剩「顶部那三个标记精灵」与「`VRAM 0x1000–0x1800` 那 706 字节」，
需要再采一帧（比如 step-17 战场帧）把「单位移动」与「覆盖层出现」分开才能定案。
⇒ **在定案之前不要改重制实现**——上一节写的「重制侧应按精灵覆盖层实现」**一并撤回**。

#### 4.3.93.3.5 **正确的对照基线 + 单 bit 定案**

前面拿「回合横幅」当基线是**错的**：横幅本身是整屏覆盖物，会把别的东西全盖住
（横幅帧 vs 移动网格帧截图差 24154 像素，其中大头就是横幅）。
**正确的基线是「战场帧」**（walk 的 step-17）。

同存档、同构建、同帧收据下，**战场帧 vs 移动网格帧**：

| 项 | 结果 |
| --- | --- |
| 截图差异 | **21956 像素**，且**整幅地图区（第 0–127 行）全变**；状态栏（128 行以下）**完全相同** |
| **显示寄存器** | **只有 `DISPCNT` 不同**：`0x1940` → `0x1D40`（**只差 bit 10**）；BG0–BG3 的 CNT、四个 HOFS/VOFS、`BLDCNT`/`BLDALPHA`/`BLDY`、`WININ`/`WINOUT`/`MOSAIC` **全部相同** |
| 地图调色板 | PRAM **只差 1 个字节**（bank 16，一个 OBJ 调色板项）；**bank 0–3（BG0 的调色板）完全相同** |
| 图块数据 | VRAM 只在 **0x1198–0x103CF** 变（1491 字节）——**BG0/BG1 的图块区（`0x4000–0x7FFF`）完全相同** |
| 精灵 | 两帧**都是 20 个**，差异只是护送单位移动了一格 + 动画帧变化 |

⇒ **⇒ 暗化的成因被压缩到一个位：`DISPCNT` bit 10。**
（mode 0 下这一位是某个 BG 的**字符基址选择位**；mGBA 的渲染器把字符基址只按
`BGxCNT` 计算，**具体它在本作里切的是哪一层、对应 ROM 里的哪份图块，仍需按
GBATEK 精确解码 + ROM 侧反查**——这正是下一问。）

⇒ **对重制侧的含义**（在解码定案前**不要动手**）：既然原版的暗化是「切一个背景层的
字符基址」而不是「给地图调色板染色」，重制侧应当对齐的是**层与图块**，
而不是调色板数值；具体怎么对齐，取决于下一问的答案。

#### 4.3.93.3.6 **第二个实例独立确认**：覆盖层跟 `DISPCNT` bit 10 走，与镜头无关

walk 里移动网格屏出现**两次**：step-16（镜头平移到 **152/40**）与 step-19（镜头回到 **240/24**）。
再采 step-16 的同帧收据后：

| 帧 | `DISPCNT` | BG0 镜头 | 与战场帧的截图差 |
| --- | --- | --- | ---: |
| 战场（step-17） | `0x1940`（bit 10 **清**） | (240,24) | 0 |
| **网格（step-16）** | `0x1D40`（bit 10 **置**） | (152,40) | 36323 |
| **网格（step-19）** | `0x1D40`（bit 10 **置**） | (240,24) | 21956 |

⇒ **两个网格实例都是 bit 10 置位，战场实例是清位**；而 step-16 换了镜头，
覆盖层照样在 ⇒ **覆盖层跟这个位走，不是镜头造成的错觉**。
（顺带也解释了 4.3.85 里记的「原版 step-16 相机 (152,40)」：那是**同一屏**的另一次出现。）

⇒ 机制结论（可机器复核）：**移动网格的覆盖层 = `DISPCNT` bit 10 置位**；
在 mode 0 下这一位是某个 BG 的**字符基址选择位**，所以原版是用「切一个背景层的图块集」
来实现覆盖/暗化，**不是**给地图调色板染色、也不是窗口、也不是 alpha 混合。
⇒ 剩下的一问仍是同一个：**这一位切的是哪一层、对应 ROM 里的哪份图块**（需 ROM 侧反查资源指针）。

**整条 walk 的交叉验证**（按「青绿覆盖色像素数」统计，覆盖色是原版覆盖层的特征色）：

| walk 帧 | 屏 | 覆盖色像素 |
| --- | --- | ---: |
| step-14 | 战场 | **0** |
| **step-16** | **移动网格** | **3207** |
| step-17 | 战场 | **0** |
| **step-19** | **移动网格** | **8374** |
| step-21 | 动作菜单 | **0** |

⇒ 覆盖层**只**出现在两帧网格屏上 ⇒ 与 `DISPCNT` bit 10 的取值 **4/4 一致**。
⇒ 两次网格的覆盖色像素数不同（3207 vs 8374）⇒ **覆盖范围**不一样（第一次网格还带着镜头平移），
这是重制侧残差里「覆盖区域大小」那部分，与机制本身无关。

#### 4.3.93.4 仍然没闭合的部分
