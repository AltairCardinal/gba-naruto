这是复刻过程中的**长期记忆**。目标里的要求是：复刻途中对木叶战记的所有理解都要
记录在这里，核对录屏后理解变化或补充时迭代这套文档，并按职能拆分成一系列文档、
设计好关联与引用关系。

本文件是**索引与关系图**，不是内容本身。

## 铁律

1. **只写有证据的结论。** 每条结论必须能追到具体的 ROM 帧、快照哈希或运行收据。
   推断要标成「待验证」，被推翻的旧解读要保留并标注推翻它的证据（见
   `../notes/s49-fidelity-handover-20261019.md` 的 4.3.3）。
2. **像素等价优先于观感。** 「看起来一样」不算通过；结论以同索引全屏逐像素比对
   为准（工具见 `../../tools/butano/compare_frame_sequences.py`）。
   > ⚠️ **2026-10-19 更正**：全屏同索引比对**只在两侧底图逐像素一致时才有意义**。
   > 实测两侧战场底图不同，25×25 全配对的最优/次优只差 0–147 像素（满分 38,400），
   > 排名是噪声，**既不能当验收闸门也不能用来选基线**。改用**区域差分**
   > （`../../tools/butano/compare_s49_regions.py`，配对作为显式输入）。见 4.3.48。
3. **模型结论必须回原图复核。** Gemini 等外部模型只能用来回答「画面上看起来
   怎样」，不能作为坐标、单位身份或字形取值的证据。
4. **快照不是全部。** GBA 存档不包含卡带 SRAM，`rom/base.sav` 属于输入契约，
   任何录制都必须记录它的哈希。

## ⚠️ 重大更正：入口快照处在**开场对白**，不是战斗回合

4.3.40 用画面证据证明：入口快照是带立绘的对白画面，A 与方向键在**推进台词**，
状态栏显示的是**说话者**，`+0xC1` 标记的是**正在发言的单位**。
因此 4.3.10–4.3.39 中「A 键推进行动顺序 / 相位切换 / 事件位域」的整套解读
**描述的是对白驱动，不是回合驱动**。原版与重制的这段开场对白**逐句一致**。
D1/D2-a/D2-b/D3 的结论都必须在「两侧推进到同一句对白」的新基线下复核。

> **2026-10-19 已完成复核**：两侧三句对白已配对（原版 11/12/13 ↔ 重制 14/15/16），
> 头像区**逐像素相同**。详见 4.3.46–4.3.51。

## A 键处理链（2026-10-19 定位；已被 4.3.40 重新定性为对白驱动）

```
A 键
 └─ 0x08062968  bl   0x080627B0            ← 返回地址 0x0806296C（GDB 报的 lr 去 Thumb 位）
     └─ 尾跳（不改 lr）到 0x0806289C        ← 断点命中处
         └─ bl 0x080627B0：按「有效位」压缩记录数组
             ├─ 源数组 0x03003BB8，60 字节步长，筛 word0 & 1
             ├─ 目标指针数组 0x030059B8（下标 = 行动顺序）
             └─ 计数 0x03005BB8 = 13
                 └─ 每条记录投影到 EWRAM 单位池 0x020240C0 的 +0xC1「行动中」标记
```

取证工具：`tools/disasm_thumb.py`、`tools/find_thumb_calls.py`（**项目自带，
不要因为系统 objdump 不支持裸二进制就说无法反汇编**）、
`tools/butano/read_rom_unit_pool.py`、`tools/butano/mgba_pc_trace.lua`、
`tools/mgba_gdb_probe.py`。

详细推导与仍未定性的部分见 [01-battle-s49.md](01-battle-s49.md) 的 4.3.x 各节。

## 一个必须记住的教训

本次会话对 D2-a/D2-b 的根因**连续判断错了十二次（其中三次已被证明正确）**（数据阵营划分、过滤条件、
开场脚本、工具链可用性、13 项表的内容、记录布局、一次**因为测试断言写错
而误撤回正确实现**、把数据表地址误当成函数入口、把字节出现次数误当成引用次数、把循环回边误当成函数入口、把「推进对白」误读成「推进行动顺序」），每一次都是被内存、PC、反汇编或测试证据纠正的。

两条结论：

1. **从按键表象反推状态机在这个项目上不可靠**——只有硬证据算数。
2. **从内存取值形状推断语义同样不可靠**：本会话在这一区域连续三次（表的内容、
   记录布局、`+0x20` 语义）被自己的后续实验推翻。
3. **判断 ROM 地址是代码还是数据，靠下断点看是否被执行**，不要看字节形状。
   `python3 tools/mgba_gdb_probe.py --breakpoint 0xADDR --timeout 20`：
   `outcome: verified` = 是代码，`not-proven` + `actualPc: null` = 是数据。
4. **字节出现次数 ≠ 引用次数；自写的解码器也可能比项目工具更差。** 枚举引用
   一律用 `tools/disasm_thumb.py` 人工核对。
5. **单帧 PC 采样容易落在循环回边或中间点，不代表函数入口。** 要定位函数，
   应在调用点（`bl` 指令）或候选函数首地址下断点，不要直接用采样到的 PC。
6. **比较按键效果时，实验组与对照组的采集长度必须一致**，否则动画相位差会淹没
   按键差异。本轮已因此产生两次不可用数据。注意 `mgba_original_s49_ui_boundaries.lua`
   的 `settle` 是**按每次按键各算一次**，所以「按键数不同」＝「长度不同」，
   对照必须按**按键数**对齐，不能只对齐单次 settle。
7. **配对基线必须按画面内容对齐，不能按操作步数对齐**——两侧输入脚本长度不同，
   步数相同的画面往往不是同一状态。本会话已因此作废两次配对差分。
   > 2026-10-19 补充：不仅步数不同，**路径长度也不同**——原版从对白结束到命令菜单
   > 要 4 次 A，重制只要 2 次（缺回合横幅，D4）。所以「同序号」比「不同步数」更危险。
8. **不要从接触表/网格缩略图上推断文件序号与内容的对应**。判断某一帧是什么，
   要单独打开那一帧看。本会话因此连续三次取错基线帧。
   > 2026-10-19 补充：4.3.45 因此把 4.3.41/4.3.43 的步号表**整体作废**，这一步是
   > **过度反应**——重录后证明 step-00..20 与旧序列**逐字节相同**，那张表内容一直是对的。
   > 作废的是我的读取方式，不是那张表。见 4.3.46 的更正记录。
9. **红测不一定意味着产品错**：先确认断言对不对，再决定改产品还是改测试。
10. **全屏同索引差分只有在底图一致时才有意义**；底图不同就先选语义相同的基线，
    再用区域差分衡量共享 UI，并把「区域」写成显式输入而不是临时裁剪。
11. **「重制做不到 X」要先确认输入路径**。本轮差点把「重制按 A 进不了战斗」写成
    产品缺陷，实际是入口需要 `Down,Down`。必须**从上电**跑一条完整规范契约，
    不能从历史快照续跑后倒推——历史证据里的战斗画面全都来自中途续跑。
12. **硬编码的像素坐标是不可见的缺陷面**。字形裁剪表里的坐标没有任何自检，
    「整行错开一格」能一路进到 ROM。必须从源图反推坐标，并把「图集那一格 == 源图
    那一格」写成测试。
13. **GBA 存档与 ROM 强绑定**：把旧 ROM 的 `.ss9` 载入重新构建的 ROM 会得到
    黑屏加彩色噪块，像「构建炸了」。实际上源码是好的——重新构建后必须**从上电重录**。
14. **修一张图集不等于修了所有图集**：其余 9 张字体图集都继承 UI 字体基底，
    必须按依赖顺序整批重建并整批验证。
15. **像素差异变大不一定是变坏**：要同时看缺陷类别（形状／颜色／布局／内容）。
16. **同一个图集被多个调色板共用时，调色板必须按图集实际烘进去的索引说话**；
    先找同类里已经正确的那一个当参照（`TEXT_ACCENT_PALETTE`）。
17. **精灵坐标要确认是中心还是角点**：`create_sprite` 取中心，文本生成器取左上角，
    混用会差 8px；放错时差异数字会**上升**，那是个可靠信号。
18. **先确认「哪一帧是哪一屏」，再谈差异**。差分收据的**文件名和标签也会骗人**——
    本轮有一份 `result-panel.json` 实际比的是动作菜单，结论（「结算光标颜色」）
    顺着这个错标签一路错到底。判定内容只能靠**单独打开那一帧**。
19. **改共享图集格子前，先量它在别的界面上有没有已被验证正确的用法**。
    本轮把「查克拉」从紧凑改成满高后，目标区域从 489 降到 0，
    但**每一步的状态栏**都凭空多出 252 像素，整体反而更差。
    「某个区域变好」推不出「整体变好」——改完必须**逐帧回放所有步**。
20. **同一个字在不同界面有两种字号时，先去看别的图集里有没有已经对的那一份**。
    本轮先判「需要新做一张满高图集」（要动 VRAM 预算 + 生成器 + `bn::sprite_font`），
    实际上**现成的动作菜单字体里已经躺着那三格满高字形**，
    而且因为动作菜单本身就是 0 像素差，这个事实**早就有验证**。
    「共享资源不够用」的时候，先确认是不是**用错了那张**。
27. **「同名」不等于「同物」，「有这一栏」不等于「有这个东西」**：D2-b 卡了三轮，
    因为结算面板两边都写着「蜂 3 / 蜜蜂 1」，我据此判断「蜜蜂在轮转里」，
    于是认定**证据不足**。真相是蜜蜂在**场面**上而不在**轮转**里，那一列同名列**恰恰是误导**。
    判据要落在**能区分两者的那个维度**上：这里是有没有那只虫，不是有没有那一行字。
26. **像素不一致时，先问「画的是不是同一个人」**：这 1196 像素为它花了三轮
    （是不是调色板 → 是不是公式 → 是不是另一张美术），答案却是**角色就摆错了**。
    而判据早就在手边：原版那个单位用的 bank 1 调色板与重制版的 `battle_unit_02_idle`
    **几乎逐项相同**——原版给木叶丸配了佐助的调色板（同套 16 色布局），
    于是「同一角色的不同美术」的错觉成立。**调到色板那一层时，顺手确认这调色板属于谁**。
25. **调色板的「身份」要靠消融实验确认，不能靠读 OAM 猜**：本轮按 OAM 字段算出的坐标与
    实际渲染位置差 16 像素，一度以为单位不在 OBJ 里；而「把这 32 字节清零再渲一次」
    一分钟就把「是谁画的」「画在哪」同时钉死，还测出了只有消融才能看出的透明索引。
24. **脚本失败不一定表现为脚本错误**：Lua 里一句 `emu.memory.domains[...]` 取不到值，
    会让脚本中止而 **mGBA 继续空跑**，最后由守卫判成 `exit 124` 的 idle 超时。
    「超时」要先怀疑「脚本早就死了」。
23. **「是运行时行为」是可以被读出来的**：连续三轮从渲染结果反推机制
    （映射是否多义、灰阶是否服从某个公式），而 mGBA 的 Lua 一直开着 `readRange`，
    **直接读 PRAM 一分钟定案**。涉及调色板/图块/VRAM 的机制问题，
    先找能不能把硬件状态读出来，再考虑从像素反推。
22. **「缺一个横幅」和「缺一整屏」的工作量差一个数量级**。D4 一直只记成
    「原版 4 次 A、重制 2 次 A」，看着像一块面板；逐帧单独打开原版 14→16 才发现
    是一屏带几何的 UI，还带一次状态切换。差分数字只说明**节奏不同**，不说明缺多少。
21. **判定「是不是换调色板」必须先排除两个污染源：位移和背景**。
    本轮先把差异框里的草地算进映射表，得到「多义⇒不是调色板」的结论；
    收窄到精灵自身像素、并排除 `dx,dy` 位移后结论不变，**才站得住**。
    随后扫描全部单位图集发现**灰阶调色板 0 张**，才真正定位到
    「原版是运行时写 PRAM，提取阶段拿不到」。

被推翻的判断保留在 01 里并标注推翻依据，不要删，也不要照着改。
