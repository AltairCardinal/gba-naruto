# 木叶战记续作 Roadmap

## 目标

把当前仓库从"已建立续作工作区和逆向基础"推进到"可以持续生产续作内容并稳定回写 ROM"的状态。

**执行策略：~~先完成逆向工程，再建网页编辑器。~~**

> **2026-10-20 — 该执行策略已被证伪并推翻。**
> 与第三方剧情编辑器包的对比复盘（`notes/why-external-editor-shipped-20261020.md`）显示：
> 对方在**未完成全量逆向**的前提下，用"复制原生条目 + 只改已知字段 + hook 原生函数"
> 的写回模型，产出了可用的编辑器与 26 场可玩 DEMO；而本项目走了 3.5 个月、
> 105 次提交、32 个结构全量静态入库，最终**可玩新内容为 0**。
>
> 改用：
> 1. **写回模型**：复制原生条目 + 覆盖式改写，未知字段 raw 兜底、不再要求命名
> 2. **验收标准**：按需动态证据（仅对本次改动涉及的结构），不再全量门禁
> 3. **工程形态**：单文件夹离线 ROM 编辑器，暂停 Web 服务/认证/多用户方向
> 4. **逆向定位**：作为功能产出的副产品，按需推进，不作为开工前置条件

> **2026-10-20 — 平台约束（macOS → Windows 迁移后）**
> 新机接入与验真记录见 `notes/windows-migration-20261020.md`。要点：
> - 两条工作线（`codex/reverse-engineering` / `codex/butano-foundation-research`）
>   已落地为独立工作树，工作区字节与 git blob 逐字节一致，交接文档钉死的
>   账本/审计器/spec 三个 SHA-256 本机复算吻合。
> - **本机 `core.autocrlf` 必须保持 `false`**：仓库用文件 SHA-256 当证据身份，
>   换行符一改全部钉死失效，且 `git status` 不会报脏。
> - **重活仍需 POSIX 宿主或等价改造**：账本重建 / formal / D0 采集链上的工具
>   用了 `os.O_DIRECTORY` / `dir_fd` 等 POSIX 原语（`tools/` 下 47 个文件），
>   其中 D0 契约钉死的两个模块不能直接改。mGBA 运行时链在本机需按 Qt +
>   `d8bad14b` 重建才能做 D0 采集。
> - 结论：**续作编辑器的开发不受此阻塞；逆向重活需要单独决策。**

|---|---|---|

* **工具**：`tools/item_record_fields.py` —— 扫全 ROM 的 7 个读者，

### 一、先修自己的工装（否则一切结论都不可信）

新写的 `build/probe_litrefs.py`（全 ROM 字面量引用扫描）**初版有两个 bug**，
而且都是「让结论看起来很干净」的坏 bug：

1. 把 **ROM 地址当文件偏移**用 ⇒ 连**已知有引用**的 `0x085461C4` / `0x08545068` /
   `0x08596CCC` 都扫不到；自检失败后改成「先减 `0x08000000`」。
2. `find_prologue` 从窗口**低端**往上找 `push {..,lr}` ⇒ 返回的是窗口里**最低**的
   函数入口而不是**最近**的，函数归属全错；改成从目标地址**向下**逐条回溯。

修好后重扫，结论与旧笔记**大幅不同**（下面第二节）。

### 二、6 个结构的读者函数，终于知道各自在读什么

| 结构 | 表 | 读者 | 读法（逐指令证） |
|---|---|---|---|
| `fonts` | `0x0853E596` | `fn 0x0807F064` | `width = 表[字符码]`，**关卡文字标签渲染器**；函数内部 `0x0807F0C8` 还会调忍术名读者 |
| `sprite-frame-descriptors` | `0x0853EE98` | `fn 0x08080670` / `0x08080764` / `0x08080814` | 三个读者都是**函数指针表**里的槽位（`0x0853EF74` / `0x0853EF8C` / `0x0853F0F4`） |
| `items` / `skills` | `0x08545BE4` | `fn 0x0806D910` | `记录 = 表 + (id & 0xFF) * 16` ⇒ **16 字节/条**，与旧笔记一致（但下标公式之前没钉死） |
| `ninjutsu-names` | `0x08599634` | 12 个读者 | 剧情 VM 的 **opcode `0x1D`**（`0x0809734C`，操作数字节 1 = 模式，**模式 0 才读表**） |
| `resource-pointers` | `0x08596F0C` | `fn 0x0807AE04` | 读者在 `0x0807B220`，位于一个大 switch 的汇合点 |
| `mechanism-effects` | `0x0808136C` | `fn 0x080812DC` | **不是数据表，是 13 项函数指针跳转表**（`cmp #0xc` + `lsls #2` + `mov pc, r0`） |

**推翻了旧笔记的一条结论**：旧笔记说「`0x0853E6C4` 是关卡对象行为处理函数表」。
重新扫字面量后确认 —— `0x0853E6C4` **全 ROM 没有一个字面量引用**，
它自己是被别的指针表间接引用的，**不可能**是「被某个 dispatch 直接索引的表」。
真正的按类型分派是 `fn 0x0806F210` 里的 **Thumb-2 switch 跳转表 `0x0806F4EC`**
（type 1/2 → `0x0806F504` → 读忍术名表），而 `fn 0x0806F210` 其实是
**战斗单位生成**函数 ⇒ 那条 `0x02026604` 读取**不在关卡对象路径上**。
实测（`build/probe_objgate.py --patch-type 1`）把对象 type 改成 1 后处理器依然不触发，
**证明旧归因错误**。更正已写进 `notes/evidence/level-mode-l3-20261022.md` §4.6.4。

### 三、`story_config[0]` 的非零读数（闭合一个 evidence 缺口）

旧归因是「调度器 `0x0808F5C8` 写入、`0x0808F5CC` 随即清零，所以任何快照都拍不到」。
**逐指令核对后发现这个归因是错的**：

* `0x0808F5C8` **只**在「before」路径上执行，而那条路径的前提正是
  `state[0x18] == 0` ⇒ **调度器恒写 0**；
* 真正的写入者是剧情 VM 的 **opcode `0x1F`**（`0x08097C40: strb r0,[r1,#0x19]`），
  操作数就是**战斗 sub-config**；场景 **2/3/4/6/7** 的 before 脚本都写 `1F 01`；
* 实测（`tools/mgba_probe/runtime_state_probe.py`，场景 2 + 作答行 1）：
  `0x08097C40` 命中、`r0 = 1`、内存 `0x020311ED` 读回 **`0x01`** ⇒ **非零读数成立**。

顺带钉死了同一字段的另外两个读者：VM opcode `0x39`（`0x08097E00`）
与状态机战斗相位（`0x0808F942` → `ctrl[2]` = `0x02026806`）。

### 三之二、忍术名表 `0x08599634`：12 个读者，剧情 VM 的 opcode `0x1D`

旧笔记只押了 `fn 0x0806F210` 一个判定点，还把 `fn 0x080794F4` 当成读者
（**它不是**）。全 ROM 重新扫描后确认有 **12 个读者**，
其中剧情 VM 的 **opcode `0x1D`**（`0x08097CC4` → `fn 0x080972F8`）
在**模式 0**（操作数字节 1 = 0）时读表，下标是操作数字节 2。

38 处脚本用了 `0x1D`，14 处是模式 0。实测（场景 43 的 `1D 00 49`）：

* `0x0809734C` 命中（表基址 `0x08599634`）；
* `0x08097352` 命中，`r0 = 0x08599758` = **`0x08599634 + 0x49 × 4`**、
  `r6 = 0x49` = 脚本里的忍术下标。

**场景 43 全程没有出现任何菜单** ⇒ 这是**纯正常按键**得到的读数（L3）。

### 三之三、声音 id 14（`story-e`）：章节菜单里的「任务列表到底」提示音

旧笔记说「id 14 的请求在地图/事件脚本，剧情路线跑不到」——**作废**。
全 ROM 扫「以常量 14 调 `fn 0x08061E6C`」只有**一个**调用点
`0x080894FC`，在 `fn 0x08089310`（**章节/任务列表**）里；
而章节菜单是状态机的**相位 `0x0120`** ⇒ `fn 0x0808A0F0` ⇒ `fn 0x08089310`。

实测（`tools/mgba_probe/phase_sweep.py --phases 0x120`）：

* `0x080894FC` 命中，**`r0 = 0x0E` = 14**；
* 随后 `0x0809AAD6` 读到 `r0 = 0x08465BE0` = **`0x08465B70 + 14 × 8`**，
  该条目的 word0 = **`0x0853C3BC`** = `story-e` 的 song header。

顺带更正：song header 是**条目 word0**，不是通道表 `0x08465B40` 里那一项
（通道表存的是通道槽位）。

### 三之四、关卡数据块表 `0x0853DF70`：相位 `0x0118` 就能触发

旧注记「55 个剧情场景、开机流程、真实战斗里加载器一次都没命中，属于剧情/战斗
之外的第四种模式，本轮探针能到达的范围内**无法触发**」**作废**。

* 状态机相位 **`0x0118`**（`0x0808F94A`：置战斗标志 bit 1 → `bl 0x080732B4`
  跑剧情战斗 → 清标志）就能命中判定点 `0x08072F0E`，
  此时 **`r4 = 0x0853DF70`**，表首 32 字节被 dump 出
  （4 条 8 字节记录，word0 = ROM 源地址 `0x0812xxxx`）。
* 同时更正：**表读取没有前提条件** —— `0x08072EEE` 处的
  `cmp r2,#0 / beq 0x08072F0C` 只决定要不要顺手置标志，
  `beq` 直接跳到装载指令，两条路径都会读表。
  旧注记把 `0x02026A80` 当成了前置条件，其实它只是被读的另一个量。

### 三之五、`fonts` 与 `sprite-frame-descriptors`：那张「表」其实是 256 条回调记录

`0x0853E698` 不是一张处理程序表，而是 **256 条 8 字节的回调记录
`(handler_A, handler_B)`**：

```
0x0807F934: ldr  r1, [pc, #0x100]  ; r1 = 0x0853E698
0x0807F936: movs r0, #0xee
0x0807F938: lsls r0, r0, #3         ; 0x770
0x0807F93A: add  r0, sb, r0         ; ★ 下标字节的地址
0x0807F93C: ldrb r0, [r0]           ; ★ 下标字节
0x0807F93E: lsls r0, r0, #3
0x0807F940: adds r0, r0, r1
0x0807F942: ldr  r1, [r0]           ; handler_A
0x0807F94A: bl   0x0809C114         ; 调用 A
0x0807F958: ldr  r2, [pc, #0xe0]    ; 0x0853E69C = 同表的 B 侧
0x0807F95C: ldr  r1, [r0]           ; handler_B
0x0807F964: bl   0x0809C114         ; 调用 B
```

* **下标字节实测在 `0x02027428`**（断点处 `r0` 就是它的地址）——
  旧笔记写的 `0x02027350` **作废**（差 `0xD8`）。
* `fn 0x0807F064`（字宽表 `0x0853E596` 的读者）是 **168/256 条**记录的 B 槽
  ⇒ 它是通用的「带文字标签的对象」绘制回调。
* 实测（`--force-dispatch` + 把下标字节写成 159）：
  字体内读者处 `r0 = 0x0853E635` = 表基址 + 159、`r1 = 0x0D` = 字宽；
  精灵帧描述符处 `r1 = 0x0853EE98`、`r4 = 0x0853EEA2 / 0x0853EEB6 / 0x0853EED4`
  = **基址 + 下标 × 10**（**步长 10 字节得到运行时证实**）。

### 三之六、`mechanism-effects`：那张「效果表」其实是 13 项**函数指针跳转表**

```
0x08081346: subs  r0, r5, #1        ; 下标 = 传入值 - 1
0x08081348: cmp   r0, #0xC
0x08081350: ldr   r1, [pc, #0x14]   ; r1 = 0x0808136C   ← 跳转表
0x08081352: adds  r0, r0, r1
0x08081354: ldr   r0, [r0]
0x08081356: mov   pc, r0            ; Thumb-2 switch 惯用法
```

⇒ 下标必须落在 **0..12**，表项是**代码指针** —— 旧注记把它当「13 项效果表」
**作废**。

路线：剧情战斗 `fn 0x080732B4` → `0x0807498C` → **`fn 0x08081544`**
（**第二个关卡对象处理器**：按 `record+4` 做 7 路分派，下标由单位字段推出，
范围 0..15）→ `0x08081ADE`（`ldrb r0,[r7,#6]` = 机制下标）→ `fn 0x080812DC`
→ 读 `0x0808136C`。

实测（场景 10，相位 `0x0110`）：判定点 `0x08081350` 命中，
**`r2 = 1` = 机制下标**（= `record[+6]`）。

### 三之七、`items` / `skills`（`0x08545BE4`）：剧情战斗的单位扫描

```
0x08074200: 扫描单位槽 1..12，过滤条件：
             unit[0] != 0 · unit[0xCC] == 0 · unit[0xC0] & 0x70 == 0
             unit[0xCD] ∉ {0, 0xFF}
0x0807425A: bl fn 0x080851F8        → fn 0x080833A8 → 0x08083812: bl fn 0x0806D910
```

分岔点是每条道具记录的**标志字节（`0x0202D4CD + r4*6`）的 bit 7**：
`0x080837C6` 读它，`0x080837CA` 与 `0x80`，
`0x080837CE: bne 0x08083804` —— **置位才走读者那一臂**。

实测（场景 10，相位 `0x0110`）：判定点 `0x0806D91A` 命中 **3 次**，
`r0 = id × 16` = 表内字节偏移（id 1 / 0x4A / 5），
**步长 16 字节得到运行时证实**。

### 四、方法上的一条新规矩（写进探针协议）

* **mGBA 的 `status` 打印的是 `r15`，而且命中断点时 `r15 = 断点地址 + 2`**
  （断点指令已经执行过）。所以**归属要靠 mGBA 自己报的命中地址**
  （`Hit breakpoint N at 0xADDR`），不能靠 `|r15 - addr| <= 4` 去猜 ——
  相邻两条指令会互相冒名顶替（本轮就因此把 `0x0808F93E` 误记成 `0x0808F942`）。
* **「实测 0 命中」必须先自证路线跑起来了**：`0x08097C40` 的真命中靠的是
  「VM 入口 → 对话 → 菜单 → branch2 → opcode 0x1F」这一串哨兵；
  没有哨兵时，看板上的 0 命中和「路线没跑」是同一件事。

### 五、剩余缺口（20 条，全部是 labelled 的已满足项）

**所有 L2 / L3 / 文档 / 证据类缺口已清零，阻塞缺口 0；字段语义面还剩 2 处未解字段**（`battle_actors` +0x14 起、`tile_asset_records` +0x34 起）—— 见 `tools/audit_claims.py`。

剩下的 20 条全是审计自己定义的 **labelled** ——「未知字段已显式标注」的
**已满足**项（非阻塞）。也就是说：**没有一个缺口还是「开着」的。**

最后一个结构 `resource-pointers`（`0x08596F0C`）的裁决见
`notes/evidence/resource-pointers-deadcode-20261022.md`：
它是精灵动作表 `0x596CCC` 的 `+0x240` 窗口，
**唯一的引用 `0x0807B220` 在死代码里**（`fn 0x0807AE04` 的 case 7，

- **结构查清了**（设计 + 审核两方独立用字节复核）：
  - 「战场事件逻辑」= 一串「条件 → `0x33` 压事件 id」；

## 2026-10-22（夜）｜**ROM 编辑器第十二轮**：真浏览器复核，查出两个只有像素能查出来的布局 bug

> 第十一轮的实现子代理自己承认「载入真实 ROM 后的浏览器视觉复核：没有做」，只做了无头 DOM 桩。
> 这一轮把最后这一步补上。方法与结果见
> `notes/battle-story-triggers-implementation-20261022.md` §7。

- **先查清一件既有的事**：这台机器的**内置 FilePanel 浏览器单个文档只能下载约 1 MB**
  （`rom-editor/content/base-rom/rom-loader.html` 的注释里量过），
  而 ROM 压缩后 2.7 MB ⇒ 编辑器自己的「载入内置 ROM」**在这台机器上一直是失败的**
  （`rom-loader.html` 忽略了父页面传的切片参数 `from`/`count`，一次取整个文件）。
  顺带查到 `python -m http.server` **不支持 Range**（实测），
  所以切片下载要么服务端支持 Range，要么用 `content/base-rom/part-*.bin` 预切块（仓库里没有）。
  **这是既有的环境限制**（普通浏览器里没有这个上限），**不是本轮引入的，本轮也没改**。
- **绕开它的办法**：触发列表只需要**某一场那两个剧本的字节** ⇒
  新增 `tools/probe_battle_story_qa.mjs`：抽出该场用得上的 ROM 字节，
  **自校验**「稀疏 ROM 与完整 ROM 的触发模型逐项相等」，相等才产出载荷。
  再新增 `rom-editor/tools/qa-trigger-view.html`：在真浏览器里用仓库**真正的模块**
  与**真正的样式表**渲染那张卡片。实测第 40 场只要 **440 字节** ROM。
- **内置浏览器的截图是陈旧帧**（DOM 是新的、布局树是旧的）⇒
  把真浏览器渲染出来的 DOM **固化成静态 HTML** 再截图，
  并在页子里加**几何测量**（输入框宽度 / 表宽 / 容器宽），**数字说话**。
- **查出两个真布局 bug**（无头门禁断不了，只有像素能断），都已修：
  1. **触发块里的三张表全塌成一条横线** ——
     `styles.css` 的 `.table-wrap { flex: 1 1 0; }` 是给**行向** flex 容器控制**宽度**用的，
     而 `.trigger-body` 是**列向** flex 容器，`flex-basis` 落到**高度**上，
     加上 `overflow:auto` 让自动最小尺寸归零 ⇒ 表格被压成 0 高。
     修：`.trigger-body > .table-wrap { flex: 0 0 auto; }`
  2. **条件表最后那列人话说明被顶出容器** —— 全局 `table.grid td` 是 `nowrap`。
     修：条件表加 `cond-table` 类、最后一列放开换行；
     `common.js::summaryTable` 加**可选**的 `rows.class`（向后兼容）。
  3. 顺带：窄栏（420px）里输入框被挤到十几像素 ⇒ 守住 `min-width`，
     宁可让 `.table-wrap` 横向滚动。
- **门禁**：`verify_battle_story_triggers.mjs` 新增第 16 组 **7 条布局断言**（74 → **81 条**，全过）。
- **仍然没验证的**：游戏侧行为（改完真的改变触发吗）、1 基映射的运行期确认、
  以及**编辑器本体**里的目视复核（受上面那个 1 MB 上限限制，这台机器上编辑器自己装不上 ROM）。

## 2026-10-21（凌晨）｜**m4a block 表格式逐字段拆解完成**，并修掉解码器的一个真 bug

> 关掉了 6 条审计缺口（5 条「轨数据块级格式未逐字段拆解」+ 1 条「块级轨道重写不支持」）。
> 详细记录见 `notes/evidence/m4a-block-table-20261021.md`。

- **「block 表」就是 SongHeader 本身**：
  `+0x00` u8 轨道数、`+0x01` u8（本 ROM 全为 0 且引擎不读）、`+0x02` u8 优先级、
  `+0x03` u8 标志（bit7 = 混响）、`+0x04` u32 voicegroup 指针、
  `+0x08` 起 `u32 track_ptr[轨道数]`。
  每个 `track_ptr[i]` 指向一个**无头**的 block：扁平命令流，以 **FINE（`0xB1`）**结束，
  其后是 `0x00` padding。
- **命令编码**：`0x00-0x7F` 是**续写字节**（running opcode 的操作数）、
  `0x80-0xB0` 是 WAIT、`0xB1-0xCE` 是命令表（`0x08464534`，30 项，索引 `op-0xB1`）、
  `0xCF-0xFF` 是 NOTE（0~3 个可选参数字节）。
  循环：GOTO `0xB2`（4 字节**小端**目标）、PATT `0xB3`（栈深 3）、
  PEND `0xB4`（空栈 = 继续）、REPT `0xB5`（`count` + 目标，count 0 = 无限）。
- **往返自检**：5 首曲子 **45 个 block（9952 字节 / 6333 条命令）逐字节相同 45/45**；
  独立的引擎级走读（按读指针走）与之吻合；所有 GOTO/PATT/REPT 目标都落在命令边界上。
- **修掉一个真 bug（`tools/extract_audio.py::decode_track`）**：
  引擎的 `0x0809A4F8 cmp r1,#0xbd` 表明 **所有 `>= 0xBD` 的 opcode 都更新
  running opcode**，而旧解码器只在音符时更新 —— 于是把 MOD/EOT 的参数读成了
  **key=0 的假音符**（101 字节 / 11 条轨道；sound id 2 track 2 会多出 28 个音符，
  其中 7 个 key=0）。四条独立证据判定**旧解码器错、ROM 对**。
  修完后两个独立解码器**零分歧**。
- **顺带修**：渲染器把「无 key 音符」的 key 记成 0，ROM 的语义是**沿用上一个音**。
- **块级重写已可用**：`tools/import_audio_song.py --block trackN=json[,offset]`
  （就地重写 / 停在自由区并改指针），并新增可执行写回自检 case `audio-block-1`
  —— 写回路径自检 **19/19 PASS**。
- **审计变化**：加固缺口 **114 → 108**；等级分布不变（L4=3 / L3=2 / L2=4 / L1=35 / 已裁决=3）。

```asm
08080B2C  ldr   r1, [pc, #0x2c]   ; 0x0853F298   本表

08080B32  ldrh  r0, [r0]          ; V = 表值

08080B36  adds  r0, r0, r2        ; V + B
08080B38  lsls  r0, r0, #0x10
08080B3A  lsrs  r0, r0, #0x10     ; (V + B) & 0xFFFF  → 64 KB 窗口内的索引
```

## 网页编辑器架构（逆向完成后）

**技术方案：** FastAPI + Vue + SQLite

**服务器：** 14.103.49.74:443（Debian 12，2核/4GB）

**架构图：**
```
用户浏览器 (Vue)
    │ HTTPS
[FastAPI 服务]
    │
 ┌──┼──┐
 │     │
SQLite  ROM文件
(队列)  (本地)
 │
WebSocket
(协作编辑)
```

**功能模块（逆向完成后按序开发）：**

| 模块 | 说明 |
|------|------|
| 对话编辑器 | 文本表单，调用 import_dialogue.py |
| 地图编辑器 | Canvas 瓦片地图，调用 import_map.py |
| 角色编辑器 | 数值表单，调用 import_battle_config.py |
| 技能编辑器 | 效果链配置 |
| 道具编辑器 | 表格编辑 |
| 剧情编辑器 | 分支对话树 |
| 构建验证 | build_mod.py 输出可下载 patch ROM |

**优先级：** 对话 > 地图 > 角色 > 技能 > 道具 > 剧情
