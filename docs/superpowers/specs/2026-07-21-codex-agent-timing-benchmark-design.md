# Codex 单代理 Butano 开发计时基准设计

日期：2026-07-21

## 1. 目标与估算对象

本基准用于回答：在需求已经由现有逆向资料给定、不再计入逆向补证的前提下，由当前
Codex 模型单代理、内联、连续完成《木叶战记》全部基础系统的功能等价开发，需要多少实际墙钟时间。

最终结果使用以下单位，不再使用人周：

- Codex 连续墙钟小时；
- 按每天可自主运行 8、16、24 小时折算的日历天数；
- 乐观、基准、保守三档区间。

“完全由 Codex 完成”包括需求落到设计、TDD 红绿重构、代码、集成、构建、调试、文档和自动化验收。人工只负责首次给出需求和最终产品验收，不承担中间编码或测试工作。

## 2. 明确排除项

用户已确认不计入以下时间：

- AI 优先级、伤害公式、章节条件等尚缺信息的逆向补证；
- 全篇剧情、全部地图、全角色/技能数值、美术和音频内容生产；
- 等待用户审批、外部账号、发行审核和真机人工操作；
- 旧存档兼容。若以后要求兼容，单独追加模型时间。

现有仓库资料被视为实现规格。资料间矛盾造成的代码返工仍计时，但为了补齐未知行为而运行原作、开展新逆向不计入本估算。

## 3. 执行模式

- 只使用当前 Codex 模型和当前主代理，不调用子代理、MiniMax 或其他模型。
- 在当前 `codex/butano-foundation-research` 分支内联执行。
- 基准代码隔离在 `butano-sequel/benchmark/`，避免误报为正式游戏进度。
- 代码遵守 GBA 约束：固定容量、无异常、无运行时堆分配假设，可由宿主机测试并由 devkitARM 编译。
- 所有功能任务按红→绿→重构执行；涉及 Butano wiring 的任务必须有 ROM 构建集成测试。
- 不自动 commit、push 或合并。

## 4. 计时方法

先实现一个很小的计时 harness；harness 开发时间单列为“测量设施开销”，不参与基础系统吞吐率外推。

每个任务在写第一个失败测试之前记录开始事件，在相关测试和重构验证全部通过后记录结束事件。记录内容包括：

- UTC 开始、结束和总墙钟秒数；
- 红测命令、退出码和失败原因；
- 绿测命令、退出码和命令运行秒数；
- 修改/新增文件数和有效代码行数量；
- 编译或 ROM 构建秒数；
- 中间失败次数、根因和返工分类；
- 是否达到该任务的完成定义。

墙钟时间覆盖模型思考、文件检查、代码编辑、编译和调试，最接近用户实际等待时间。Docker 首次镜像下载已经在部署阶段完成，不重复计入每项开发速度；最终报告会单列冷缓存差异。

原始事件写入唯一目录 `build/butano-agent-benchmark-20260721-01/`，汇总写入仓库内的
`notes/butano-agent-timing-benchmark-20260721.md`。原始事件不覆盖，失败尝试同样保留。

## 5. 六个实测任务

### B1：回合与行动状态机

实现选择单位、移动预览、移动提交、行动菜单、目标选择、动作提交、取消回退和回合结束的纯逻辑状态机。

完成定义：正常路径、每个可取消边界、非法输入和提交后不可回退均有测试；状态机不依赖渲染层。

### B2：地图、占位与寻路

实现固定尺寸网格、地形移动成本、单位占位、移动范围和确定性最短路径。

完成定义：障碍、不同成本、不可达、占位阻挡、预算边界、同成本稳定 tie-break 和固定容量溢出均有测试。

### B3：技能效果与战斗结算

实现数据驱动的伤害、治疗、资源消耗、状态添加和位移效果链，以固定的示例公式代替尚未补证的原作公式。

完成定义：效果顺序、资源不足、目标非法、数值上下限、事务失败不产生半提交均有测试。

### B4：章节脚本 VM

实现最小字节码 VM，覆盖对白事件、设 flag、条件跳转、启动战斗、等待和结束。

完成定义：正常分支、等待/恢复、非法 opcode、越界跳转、缺少结束和 step budget 防死循环均有测试。

### B5：版本化存档 codec

实现固定布局的存档 header、payload、版本、CRC、默认新档和损坏拒绝；以字节 buffer 模拟 SRAM，不实现旧 ROM 存档兼容。

完成定义：往返、截断、CRC 错误、未知版本、默认值、确定性编码和掉电前旧槽仍可读均有测试。

### B6：Butano ROM 集成

把五个内核编入基准 ROM，启动时运行确定性自检并显示每项 PASS/FAIL 与总结果；错误必须留在可见画面，不得静默黑屏。

完成定义：宿主机测试通过；固定 devkitARM 镜像完成干净 ROM 构建；ROM header 和内核符号存在性由集成测试验证。受当前 Homebrew Qt/Cocoa 限制，自动 mGBA 画面验证仅在可用 CLI frontend 时执行，否则保留守卫失败证据且不宣称运行通过。

## 6. 外推方法

### 6.1 基准工作单元

五个逻辑任务分别代表高频工作类型：状态机、图算法、事务规则、解释器和持久化。每项实测时间归一为一个“已测试内核单元”；B6 单独给出一次跨层集成单元的时间。

### 6.2 映射到 13 个基础系统

最终报告逐项列出：

- 最接近的实测样本；
- 预计内核单元数量；
- UI/资源 wiring 数量；
- 集成边界数量；
- 回归和 GBA 预算验证次数；
- 由此计算出的 Codex 墙钟小时。

核心场景、外围流程和 UI 主要引用 B1/B6；地图引用 B2/B6；单位、技能、成长和 AI 引用 B2/B3；章节引用 B4；存档引用 B5；内容转换、调试和音频引用实际部署构建样本及 B6。

### 6.3 系数

三档估算不凭空使用固定人类生产率，而从实测时间计算：

- 乐观：同类任务实测吞吐，复用公共层，集成一次通过；
- 基准：实测吞吐 + 30% 跨系统集成 + 20% 回归/文档；
- 保守：使用样本中较慢任务速度 + 60% 集成/调试 + 30% GBA 资源与回归储备。

公式和逐项输入必须出现在报告中，使后续新增样本能够重算。不得把模型推理 token、工具 CPU 时间或人周混入墙钟小时。

## 7. 误差与可信度

样本只能测量“规格清楚时”的开发速度。以下因素会让真实时间超过区间：

- 长上下文压缩造成重新读取和重新定位；
- 多系统组合后出现样本未覆盖的状态爆炸；
- mGBA frontend、Docker、工具链或资源转换的不稳定；
- 需要视觉判断但当前自动化不能可靠观察；
- 需求资料内部矛盾，且不能仅靠已有证据裁决。

最终报告必须给出样本量、观测时间、外推倍率和误差等级，不能把一次快速实现直接线性乘到整个项目并表述为承诺工期。

## 8. 测试与验收

- 计时 harness 有单元测试，确保未结束任务、重复 task ID、负时长和覆盖原始事件均失败关闭。
- 每个 B1–B5 任务先记录正确原因的红测，再记录绿测和重构复验。
- B6 通过锁定 Docker 镜像进行干净构建，并验证 GBA header。
- 运行本次新增测试、相关 Butano 部署测试、`git diff --check` 和 setup verifier。
- 更新 `docs/butano-konoha-systems-cost.md`：旧人周估算标记为已取代，主结论改为 Codex 墙钟时间。
- 更新 `docs/sequel-roadmap.md`：只追加实测估时结论，不覆盖用户已有内容。

## 9. 用户可见边界

本基准的可见产物是可构建的自检 ROM 和可复核的计时报告，不是可玩的木叶战记纵切片。B1–B5 的代码只证明当前模型在代表性任务上的完成速度；除非后续经过正式架构评审，不把 benchmark 目录直接宣布为生产实现。

## 10. 完成条件

- 六项任务均有未覆盖的原始计时证据；
- 五项逻辑内核完成红绿重构，B6 完成 ROM 构建集成；
- 报告可从样本时间重算 13 个基础系统的乐观/基准/保守模型工期；
- 报告明确不计逆向补证和内容生产；
- 所有范围内测试通过，范围外既有失败单独披露；
- 未自动提交或推送。
