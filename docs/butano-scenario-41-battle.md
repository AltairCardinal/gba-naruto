# Butano scenario 41 战斗关卡

## 用户可见结果

ROM 冷启动后直接调用 `run_battle_41_scene()`，通过通用 `battle_runtime_scene` 装载
9×22 战场、condition variant、鸣人 `(4,10)` 与 character 30 `(4,4)`。部署、移动、
动作浏览、目标、朝向、防御、AI、条件结算和单位表现均与 battle 9/11/32/43 共用同一套
controller/resolver，而不是读取 scenario 41 私有截图状态。

当前默认 scenario 41 是共享架构验收，不是四回合黄金路线，也不再声称旧教学对白、
结果页和战后世界地图已经接到默认入口。原纵切片源码与整屏攻击帧仅保留为离线研究参考；
生产 ROM 的交互战斗不链接 `scenario_41_attack_animation_frames.h`。

## 地图交互与镜头约束

- 剧情对白使用原 ROM 解码的 8×16 字形；战斗菜单、状态和数值使用独立的小字形，二者
  不能再共用缩放或行高。
- 进入移动选择时，pathfinder 的当前可达格实时投影为青色范围；进入动作目标选择时，
  当前动作射程投影为橙色范围，合法目标格使用更亮样式。范围层不得自行复制移动或目标
  规则。
- 选择人物、移动预览、命令、动作、目标和面向阶段都以当前光标/行动单位格为镜头焦点。
  原作按完整 240×160 视口居中，底部 HUD 不参与重算“可见地图中心”；地图边缘才进行
  夹取。因此位于下方的佐助等单位不会再沿用上一名角色的镜头而落到 HUD 后方。
- 面向阶段用 `selected_facing` 同时预览单位朝向和头顶四向指示；方向键只改预览，A
  提交后才进入防御确认。底部状态栏在此阶段替换为“请选择人物面对的方向”说明框。
  技能、补充查克拉、休息和行动结束都必须经过这一尾部，不能由某条命令绕过。
- “行动结束”先打开无副作用的“可以吗？”是/否框；只有“是”才进入朝向。“否”或 B
  返回命令菜单。朝向提交后，防御确认默认选择“是”：是进入共用防御动作浏览器，否才
  完成当前单位，B 返回朝向。确认框、游标和文字均读取 controller snapshot，不使用截图。
- 决斗画面按阵营固定屏幕位置：玩家单位始终在左侧朝右，敌方单位始终在右侧朝左。
  发起者只决定动作角色，不交换双方站位；敌方发起攻击时敌方仍从右侧朝左攻击。
- 单位地图层级按视觉 y 坐标排序；位置越靠下，z-order 越靠前，避免重叠时下方单位被
  上方单位覆盖。
- 第一回合敌方行动结束后，原 ROM 的 battle 41 selector 2 会在第 2 回合玩家侧阻塞
  地图输入并显示教程对白。头像、表情、焦点、说话者姓名和正文均读取 presentation
  script；对白窗由四个无文字面板切片动态组合，A 逐页推进，不能用整屏截图代替。

当前同一 ROM 的静音截图与遥测证据位于
`artifacts/butano-battle-ui-projection-20260729-37/`。该确定性路线的敌方只移动、不
发起决斗，因此本关本身不签发敌方决斗；共享投影按原作证据固定为“玩家左、敌人右”。

## 操作

| 按键 | 行为 |
|---|---|
| 方向键 | 移动光标；在任务、行动、是/否菜单中移动选项；选择人物面对方向 |
| A | 确认当前选项、推进对白或结算；防御确认“是”进入防御动作列表 |
| B | B 取消当前层级；防御确认返回朝向，行动结束确认返回命令菜单 |
| START | 返回当前开发场景 |
| SELECT | 结束当前共享运行时样本并进入下一个开发战场 |

## 可执行验收路线

自动路线由 `tools/butano/mgba_battle_41_shared_runtime.lua` 固定：

1. 依次确认部署，进入第 1 回合单位选择。
2. 前三回合分别移动到 `(4,10)`、`(4,7)`、`(5,6)`，选择行动结束，逐次验收行动结束
   确认、朝向说明框和防御确认；防御确认用 Down 选“否”后 A 提交。
3. 第 4 回合移动到首个活动敌人下方，动作菜单选择 ID 5“忍者组合拳”，目标为该敌人。
4. 观察目标确认、移动、蓄力、近战槽、目标受击槽和归位；演出期间输入锁定。致死目标仍显示到
   表现事务结束，随后 condition 进入结果态。
5. 审计应为 battle 41、round 4、phase 13、action 5、控制错误 0、玩家错误 0。

最新静音实机证据位于
`artifacts/butano-battle-ui-projection-20260729-37/`。自动化只签发状态机、图形和资源
安全，不签发主观音质。

### 起爆符对象验收路线

scenario 41 的角色 1 在本开发夹具中把忍具 67 装入 slot 0，用于验证原作 type 1
战场对象链；slot 1 另装忍具 11，用于验证有效命中后的毒状态 follow-up：

1. 选择角色并确认原地移动，打开行动菜单；
2. 在动作列表向下移动到忍具 67，确认后把目标移到上方合法空格；
3. 确认放置后，目标格出现对象标记；它不是即时伤害，完成面向与防御时仍应存在；
4. 敌方行动结束进入 round 2 时，对象按原作阵营结束计时到期，以对象格为中心调用统一
   resolver，伤害范围内单位并释放 slot；
5. 本次确定性路线的审计结果为 slot 1、type 1、23 点伤害、对象数 0、控制/玩家错误 0。

最终证据位于
`artifacts/butano-battlefield-object-runtime-20260726-12/`。自动化会等待对象事件实际
进入 renderer 的 active presentation，而不是只观察领域摘要。当前标记和到期文字是通用
调试表现，尚不是原作起爆符专属动画。

### 毒状态验收路线

1. 角色 1 向上移动三格，打开正式行动目录并选择忍具 11；
2. 对上方敌人确认，动作经 controller、目标 preview、正式 resolver 与忍具消耗事务；
3. 有效命中后，目标领域状态新增 `0x1F/0x21/0x23` 三条记录；单位 HUD 的 `ST` 显示
   当前活动状态总数；
4. 当前 scenario 41 的低属性敌人在逐步 `floor(value×10/100)` 后数值差为 0，这是原公式
   的低值边界，不是状态未写入；20 点属性领域测试确认三项均降到 18；
5. 静音 mGBA 自动路线在 frame 202 读到 action 11、target 2、HP 0、inactive、
   status count 3，控制和玩家错误均为 0；这也验证原 ROM 的致死后 follow-up 顺序。
   最终证据为 `artifacts/butano-effect-flag-runtime-20260726-07/`。

当前 HUD 只显示状态总数，不显示三条原作名称；专属图标、逐状态文本和动画仍待资产证据闭合。

### scenario 43 开发验收入口

在 scenario 41 共享战场按 SELECT 可进入第二个可见战场。该入口通过同一个
`battle_encounter_runtime` 加载 scenario 43 的 ROM 编队、地图、条件和 12 个稳定单位槽。

1. 初始画面显示 1 名玩家、3 名敌人和 `ACTIVE 4/12`，每个活动槽都有独立动态单位 sprite 与 `P1/E2/E3/E4` 标记。
2. 选择鸣人 action 7“影分身”，把目标移到合法空格并确认；查克拉从 5 降到 2，reserve 槽 5 激活，画面变为 `ACTIVE 5/12` 并出现 `C5`。
3. 完成朝向和“不使用防御”后进入敌方阶段；`AI DONE` 从 `0/3` 依次推进，每个敌方单位通过共享 AI/resolver/turn-flow 完成行动。
4. 三名敌人结束后画面显示 `ROUND 2 PLAYER`，召唤单位仍在领域会话中；START 返回 scenario 41。

移动和技能表现由领域事件驱动的插值、突进、命中震动/闪烁完成。场景只读取 snapshot 和 presentation pose，不直接写单位位置、HP、查克拉或召唤状态。

### `SELECT: BATTLE 9` 多单位开发验收入口

在 scenario 43 释放进入该场景的 SELECT 后再次按 SELECT（场景底部以 `SEL:NEXT` 提示；
开发路线记为 `SELECT: BATTLE 9`），进入同一个 `battle_runtime_scene` 装载的 battle
row 9。该场使用原 ROM 重建的 16×32、512×512 地图，不复用 scenario 41/43 截图背景。

1. 初始 roster 是 3 名玩家对 5 名敌人，HUD 显示 `8/12 SELECT UNIT`；P1、P2、P3 都是
   可选择、可移动和可完成行动的领域单位。
2. 三名玩家分别移动一格并结束行动；前两名完成后仍停留玩家阶段，第三名完成后才进入
   `ENEMY TURN`。
3. 五名敌人通过共享 AI flow 逐个执行，HUD 的完成计数依次变化；表现期间摄像机跟随当前
   敌人，领域状态和镜头演出由 `presentation_busy` 分开记录。
4. 最后一名敌人推进回合后，场景等待其演出真正结束，再回到第二回合 P1 和玩家镜头。
   START 返回 scenario 41；非法移动或命令返回稳定错误，领域状态不被部分写入。

## 加载、空状态与错误

- 加载：地图图形由 ROM tile 资源构建，`generated_battle_map_content.h` 保存 47 张图的 12,151 个原始碰撞 word；图形、音乐和音效随 ROM 编译，运行时不访问网络或外部文件。
- 空状态：scenario 41 固定包含两名部署记录；动态 `0xFA..0xFF` 槽必须由调用者提供角色策略，
  不会静默填默认角色。基础系统自检失败时在进入关卡前断言停止。
- 错误：越界、阻挡、占用、超移动力和非法目标会返回稳定错误，不改变已提交状态。
- 权限或数据缺失：GBA 无权限模型；缺失编译期资产会让构建失败，不在运行时静默使用占位资源。

## 音频路线

仓库仍保留原 cue 与 Maxmod 资产研究，但本轮自动 mGBA 路线全部静音，只验证战斗状态、
图形与资源安全，不能据此声明音频撕裂已修复或主观听感通过。音频需单独以用户实际模拟器
和非静音采集验收。

## 功能边界

- 2026-07-22 在线录屏复核确认：当前生产 ROM 错误跳过了双方亮相、“开始”标题、可见战前对白和手里剑转场。此前“确认是后直接进入单位选择”的验收结论已撤销；在入口序列按原作补齐前，本关不得标记为完整 1:1。
- 默认入口暂不包含战前“队伍·装备 / 查看地图 / 保存”、教学对白和战后章节脚本；这些属于
  后续章节层，不允许重新接回旧 screenshot scene 冒充完成。
- 本关可见 UI 开放共享部署、完整命令/动作浏览、目标、朝向、防御、AI 与 condition；
  角色自然可用技能仍由生成槽和资格策略决定。旧存档兼容与章节结算尚未接入。
- scenario 41 已删除六个截图时代的手写障碍格，地图与 scenario 43 通过同一个
  `battle_map_loader` 读取。低四位 `0xF` 作为已证明的完全封闭格；`1/3/7` 等部分属性原样
  保留，但当前通用寻路不会猜成双向墙。原作对这些部分属性的特殊递归处理与 AI 排序仍需
  运行时差分闭合，因此这次只签发地图内容/占用架构，不签发完整碰撞功能等价。
- scenario 43 已有真实角色 component sprite、影分身和完整一轮玩家/三敌/下一玩家回合
  闭环；尚无原章节脚本与完整结果表现，因此仍是可操作架构验收场，不等于 47 场完成。
- battle row 9 已用同一 renderer/controller 完成 3v5 的真实移动、三名玩家阶段门和五名
  敌方 AI 回合；它是多单位架构压力样本，不等同于原作对应章节已经具备最终角色图、技能
  演出、部署对白、胜负脚本或结算。
- 旧路线的 39 个稳定画面没有覆盖正确入口序列，不能再作为完整流程验收；旧 264 帧整屏攻击
  已移出生产 graphics。当前表现使用 534 个角色 component 资产、ROM duration、行动事件和
  受影响单位 ID；招式特效、章节转场和主观音频仍需后续独立闭合。
