# 木叶战记 ROM 编辑器（`rom-editor/`）

> 离线网页版 ROM 编辑器。纯 HTML + 原生 ES Module，**没有构建步骤**，
> 也没有后端、数据库或账号体系——打开一个静态服务器就能用。
>
> 编辑器的内容全部来自仓库里已经证明过的逆向成果（`docs/rom-reverse-engineering-results.md`、
> `notes/evidence/`），并且**可以从它自己的初始数据重建出与原版逐字节相同的 ROM**。

---

## 1. 快速开始

```powershell
# 1) 导出内容包（改过 tools/export_content_pack.py 或换 ROM 时才需要重跑）
python tools\export_content_pack.py

# 2) 起一个静态服务器
node rom-editor\tools\serve.mjs 8765
#   → http://localhost:8765/rom-editor/

# 3) 浏览器自检（29 项：所有模块渲染 + 面板打开 + 构建与落点 + 原始字节补丁）
#    打开 http://localhost:8765/rom-editor/tools/selftest.html

# 4) 命令行自检（15 项：重建 ROM 与逐域落点，不需要浏览器）
node rom-editor\tools\verify_pack.mjs
```

## 2. 它凭什么算「ROM 编辑器」

| 承诺 | 怎么保证 |
|---|---|
| **初始数据即可构建完整原版 ROM** | 内容包 `content/pack.json` 含有原版 ROM 中**所有可证实结构的全量内容**（39 张结构表 / 6,666 条记录 / 10 张文本表 / 2,199 条文本 / 4,261 个字形码）；`node rom-editor/tools/verify_pack.mjs` 现场证明「用未改动的内容包重建的 ROM 与原版逐字节相同」 |
| **任意内容都能改** | 结构化编辑器覆盖 39 张表 / 6,666 条记录；剧情脚本的定宽操作数（路线、地图、子配置、队员）可改；「原始字节」模块给出整张卡带的十六进制编辑器，兜住其余每一个字节——改动记成**显式补丁**，构建时按「原字节必须匹配」写回，不匹配就跳过并报告 |
| **改完能出 ROM** | 「构建 ROM」用内容包重写原版 ROM 并下载；改写遵循仓库既有模型：**复制原生条目 + 只改已知字段 + 未知字节原样保留** |
| **不会写坏** | 文本分两类：指针表驱动的（可重定位、可变长）与被代码用绝对地址引用的（只能等长改写）；越界会报错而不是悄悄截断 |

| 音频 | sound-ID 表、5 首 m4a 歌曲描述符、函数指针表 | `0x465B70`、`0x536368` 等、`0x53D5F0` |

### 剧情路线：路线其实在脚本里

**路线不在任何表里** —— 它藏在剧情脚本的「下一场景」指令里：

| 指令 | 处数 | 含义 |
|---|---|---|
| `0x16` | 48 | 转到该场景的 after 剧本，并记住下一场景 id |
| `0x1A` | 15 | 直接推进路线游标（`state[0x16] = scene`） |

编辑器把这两类指令抽出来做成**路线边表**（202 个剧本 / 63 条边），
并把它们的操作数做成可改输入框。这些操作数都是**定宽**的，
改它们是原地写，**不会移动任何字节**，因此脚本里的分支目标依然有效 ——
这正是仓库既有写回路径（`tools/import_story_script.py`）成立的同一个前提。

战斗侧同理：`0x1E`（本关载入哪张地图）、`0x1F`（用哪个子配置）、
`0x23`（队员是谁）、`0x22`（把角色加入战斗配置）都在战斗模块的
「本关战斗剧本里可改的操作数」里列出。

### 深链接

每个视图都能用 URL 直接定位，便于分享与复核：

```
#overview                 概览
#route                    剧情路线
#route/stage/3            剧情路线的第 3 关
#battle/stage/40/0        战斗的第 40 关、变体 0
```

### 战斗的「四件套」是按原生 id 串起来的

```
关卡 id N
  ├─ 战场布置   map_table[N]            = 0x53D910 + N*32
  ├─ 角色出生点 battle_actors[N][变体]   = 0x5461C4 + N*0x1AAC + 变体*0x8E4 + 4 + 槽位*0xB8
  ├─ 战斗目标   battle_rules[N][变体]    = 0x594758 + N*0xCC + 变体*0x44
  └─ 战斗中的剧情 story_logic_root[N] / story_events_root[N]
```

战斗中的「角色出生」没有单独的表：剧本里的 `0x22` 指令「把角色加入战斗配置」
就是拿关卡 id 与变体 id 去上面那张编成矩阵里扫 12 个槽位找角色 id 匹配的条目。
所以**改编成矩阵里的角色 id / 等级 / 出生点，就等于改了战斗中谁出场、在哪出现**。

## 5. 内容包格式

```jsonc
{
  "format": "naruto-konoha-content-pack",
  "version": 1,
  "rom":  { "name": "base.gba", "size": 6291456, "sha256": "1198ece7…" },
  "font": {
    "code_to_char": { "8140": "　", … },   // 字形码 → 字符（解码用）
    "char_to_code": { "　": "8140", … }    // 字符 → **规范**字形码（编码用）
  },
  "structures": [{
    "id": "character_template", "module": "characters",
    "rom_offset": 5415452, "entry_size": 180, "entry_count": 63,
    "fields": [ { "key": "hp_base", "offset": 10, "size": 2,
                  "type": "u16", "label": "HP 基础", "group": "基础属性" } ],
    "records": [{ "id": 1, "rom_offset": 5415452, "raw": "<base64>", "values": { … } }]
  }],
  "texts": [{
    "id": "character_names", "module": "characters",
    "pointer_table_offset": 5866624, "relocatable": true, "nul_terminated": true,
    "records": [{ "id": 1, "pointer_offset": 5866628, "pointer": 134234384,
                  "text_offset": 7408, "capacity": 13,
                  "text": "漩涡鸣人", "original_text": "漩涡鸣人", "raw": "<base64>" }]
  }],
  "patches": []
}
```

### 两条硬约束

1. **字段列表必须铺满整条记录。** 已知字段之外，未解码的字节以 `hex` 字段原样保留。
   所以「未改动的内容包」重建出的 ROM 与原版逐字节相同。
2. **字形码表要带规范码。** 8 个字在 ROM 字库里有**两个码位**；编码时必须用
   「基本区」的那个（`tools/text_codec.py::build_canonical_reverse_mapping` 的规则），
   否则回读会变成另一个字。内容包因此同时带 `code_to_char` 与 `char_to_code`。

## 6. 文本的两类长度策略

| 类别 | 判据 | 变长怎么办 |
|---|---|---|
| **可重定位** | 文本被**指针表**指向（人物名表、忍术名表、任务表、对白槽位表…） | 变长时把整张表的文本重新排布到 ROM 空闲区（默认 `0x5DFBEC`–`0x600000` 的 0xFF 填充区），并改写指针 |
| **等长改写** | 文本被代码里的**绝对地址**引用（全卡带文本索引里的绝大多数） | 只能等长；变长会在构建时报错，不会静默截断 |

## 7. 已知的边界

- **LZ77 压缩资源不可改。** 战场图块 / 调色板 / 图层 / 组合图块 / 通行值表都是
  LZ77 压缩载荷，而仓库里只有「字面量」编码器（`tools/lib/lz77.py::compress_literal`），
  没有与原版逐字节一致的压缩器。结构化编辑器因此**只暴露指针与尺寸字段**，
  载荷本身按原始指针呈现。详见 `notes/evidence/`。
- **故事 VM 剧本的指令与文本不可改。** 脚本里的分支目标是绝对 ROM 地址，
  改文本会移动后续指令、让全部分支失效；所以剧本只暴露**已证明的定宽操作数**
  （下一场景、地图、子配置、队员等，见 §4），指令本身与文本仍不可改。
- **道具记录的 16 个字节没有字段语义。** 仓库里没有任何一处证明过它们的含义，
  所以按原始字节呈现与编辑，不臆造字段名。
- **浏览器下载上限。** 某些嵌入式浏览器对单页下载量有上限（本机实测约 1 MB/文档），
  因此原版 ROM 以 32 KB gzip 分片、由若干个载入器文档分片取回。
  桌面 Chrome / Edge / Firefox 不受此限制。

## 8. 与仓库既有工具的关系

编辑器是**仓库既有写回路径的前端**，不是另起炉灶：

| 编辑器的能力 | 仓库里的对应物 |
|---|---|
| 角色 / 成长 / 忍术记录写回 | `tools/import_character_template.py` |
| 奖励表写回 | `tools/import_reward.py` |
| 战场 / 编成 / 对象描述符 / 关卡块写回 | `tools/import_battle_config.py` |
| 精灵动作表写回 | `tools/import_sprite_action.py` |
| 剧情脚本根表写回 | `tools/import_story_script.py` |
| 文本编码 | `tools/text_codec.py`（唯一的字形码编解码入口） |
| 表基址裁决 | `tools/table_registry.py`（`CONFLICTS` 是裁决结果，编辑器按它取基址） |
| 往返自检 | `tools/writeback_paths.py`（17 条写回路径）、`tools/completion_audit.py` |

编辑器的写回模型与它们一致：**复制原生条目、只改已知字段、未知字节原样保留**。
