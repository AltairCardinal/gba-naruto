# 木叶战记 ROM 编辑器（`rom-editor/`）

> 离线网页版 ROM 编辑器。纯 HTML + 原生 ES Module，**没有构建步骤**，
> 也没有后端、数据库或账号体系——打开一个静态服务器就能用。
>
> 编辑器的内容全部来自仓库里已经证明过的逆向成果（`docs/rom-reverse-engineering-results.md`、
> `notes/evidence/`），并且**可以从它自己的初始数据重建出与原版逐字节相同的 ROM**。

---

## 1. 快速开始

```powershell

#   → http://localhost:8765/rom-editor/

# 3) 浏览器自检（45 项：所有模块渲染 + 面板打开 + 构建与落点 + 原始字节补丁 + 剧情 VM + 控制码 + 战斗目标说明文字）

#    （结果同时落盘到 build/selftest-report.jsonl，页面被刷新也留得住）

# 4) 命令行自检（34 项：重建 ROM + 逐域落点 + 原始字节补丁 + 剧情 VM + 控制码 + 战斗目标说明文字）
node rom-editor\tools\verify_pack.mjs

# 5) 无头视图自检（128 项：九个模块渲染 + 战斗视图 + 文本表视图 + 域首页 + 导航 + 指针/复合键/深链）
node rom-editor\tools\verify_views.mjs

# 6) 路线工作台专项自检（剧情路线域的 6 条验收标准）
node rom-editor\tools\verify_route_workbench.mjs

# 7) 音效工作台专项自检（音频域的 7 条验收标准）
node rom-editor\tools\verify_audio_workbench.mjs

# 8) 来源自检（每张表都能溯源 + 几条关键跨域链路）

# 9) 字段标签自检（没有占位名 / 每个字段都有说明 / 属性用游戏里的名字）

python tools\audit_field_labels.py

# 附：字段说明的可读性现状（哪些说明还是 ROM 的内部视角）
python tools\audit_field_wording.py
```

### 启动时会发生什么

顶栏的进度条会依次显示三个阶段，**每个阶段都有字样**：

```
正在下载内容包（压缩）…  249 KB / 249 KB      ← 下载（带字节数与百分比）
正在解压内容包…                                ← 解压（gzip → 2.9 MB）
正在解析内容包…                                ← 解析（JSON）
内容包 40 结构 / 11 文本表 · 未载入原版 ROM      ← 完成
```

内容包有**降级链**，每个来源 20 秒超时：
`content/pack.min.json.gz` → `content/pack.json` → 专用载入文档。
**任何一环卡住都不会再无限等下去**：超时一定会触发（用「会 reject 的计时器
与请求竞速」实现，而不是只靠 `AbortController.abort()` —— 有些浏览器在
响应体卡住时不会因为 abort 而 reject，那样的超时等于没有）。

全部来源都失败时，界面会给出**可执行的**提示并出现「重试」按钮：

> 内容包载入失败 —— 内容包（压缩）：超过 20 秒没有响应；内容包（明文）：……
> 请确认是用 `node rom-editor\tools\serve.mjs` 起的服务器，并且从
> `http://localhost:<端口>/rom-editor/` 打开（直接双击 index.html 会被浏览器的
> 同源策略拦住）。

### 原版 ROM（构建基底）

原版 ROM 是 6,291,456 字节，而某些浏览器对**单页下载量**有上限
（本机内置浏览器实测约 6.3 MB，ROM 本身就占满了）。
所以 ROM 由作者提供，两个入口：

| 入口 | 说明 |
|---|---|
| **顶栏「载入 ROM」** | 选一个文件（`rom/base.gba`）。**不走网络，一定能成功**，推荐用这个 |
| 顶栏「载入内置 ROM」 | 从编辑器自带的压缩 ROM 里取（2.7 MB gzip）。普通浏览器可用；受下载量限制的环境可能失败，失败时界面会提示改用文件选择 |

编辑功能**不需要** ROM：内容包自带全部可编辑内容。只有「构建 ROM」和
「原始字节」模块需要它。

## 2. 它凭什么算「ROM 编辑器」

| 承诺 | 怎么保证 |
|---|---|
| **初始数据即可构建完整原版 ROM** | 内容包 `content/pack.json` 含有原版 ROM 中**所有可证实结构的全量内容**（116 张结构表 / 6,752 条记录 / 11 张文本表 / 2,418 条文本 / 4,261 个字形码）；`node rom-editor/tools/verify_pack.mjs` 现场证明「用未改动的内容包重建的 ROM 与原版逐字节相同」 |
| **任意内容都能改** | 结构化编辑器覆盖 116 张表 / 6,752 条记录；剧情脚本的定宽操作数（路线、地图、子配置、队员）可改；「原始字节」模块给出整张卡带的十六进制编辑器，兜住其余每一个字节——改动记成**显式补丁**，构建时按「原字节必须匹配」写回，不匹配就跳过并报告 |
| **改完能出 ROM** | 「构建 ROM」用内容包重写原版 ROM 并下载；改写遵循仓库既有模型：**复制原生条目 + 只改已知字段 + 未知字节原样保留** |
| **不会写坏** | 文本分三类：指针表驱动的（**9 张表**，可重定位、**可变长**）、定长内联槽的（说话人名表，槽的大小写死在表里）、被代码用绝对地址引用的（战斗目标说明文字，搬不动）—— 后两类**只能等长**，界面会说明**为什么**；**剧情对白正文现在也能变长**（构建时整个剧本搬到空闲区并重基内部地址）；越界会报错而不是悄悄截断 |

### 剧情路线：路线其实在脚本里

**路线不在任何表里** —— 它藏在剧情脚本的「下一场景」指令里：

| 指令 | 处数 | 含义 |
|---|---|---|
| `0x16` | 48 | 转到该场景的 after 剧本，并记住下一场景 id |
| `0x1A` | 15 | 直接推进路线游标（`state[0x16] = scene`） |

编辑器把这两类指令抽出来做成**路线边表**（202 个剧本 / 63 条边），
并把它们的操作数做成可改输入框。这些操作数都是**定宽**的，
改它们是原地写，**不会移动任何字节**，因此脚本里的分支目标依然有效 ——
这正是仓库既有写回路径（`tools/import_story_script.py`）成立的同一个前提。

战斗侧同理：`0x1E`（本关载入哪张地图）、`0x1F`（用哪个子配置）、
`0x23`（队员是谁）、`0x22`（把角色加入战斗配置）都在战斗模块的
「本关战斗剧本里可改的操作数」里列出。

### 剧情路线：一屏一关的「路线工作台」

`#route/stage/40` 打开的不是一屏只读汇总，而是**一关改完**的三块：

1. **路线走向** —— 本关的出边、**谁会跳到本关**（两行都能点着跳过去）、
   全游戏 63 条路线边收在默认折叠的一览里；
   「下一场景 id」是**下拉**（只列 `story_after_root` 里真有 after 剧本的场景 1..55，
   不是裸数字框），「相位标志」也是下拉。
2. **任务文案** —— 3 个子任务的标题 / 说明 / 提示**就地可改**。
   行脚注写明「文本表下标 #103 · 同时是第 41 关子 1」与「这段字被 27 处共用」——
   任务下标**不是** `3×(关卡−1)`，有 18 个槽位跨关共用，不说清楚作者会误改隔壁关卡。
3. **本关奖励** —— 金币 / 强化点 / 等级门槛 + 8 个掉落位**就地可改**，
   并给一个「在道具域打开这一条」的入口（奖励表本身归属道具域）。

另有 `#route/graph` 整条路线总览。规格与落地记录：
`notes/specs/route-workbench.md`、`notes/route-workbench-20261021.md`，
验收脚本 `rom-editor/tools/verify_route_workbench.mjs`。

### 音频：81 个描述符第一次全部看得见

sound-ID 表有 159 条，其中 **79 条共用同一个空哨兵**（`0x08466068`，没有轨道）。
今天编辑器只导出了 5 个描述符，另外 75 个作者根本看不到。

现在内容包导出**全部 81 个地址**（80 个真实描述符 + 1 个空哨兵），
音效工作台给出：描述符**带名字的下拉**（81 项，带轨道数与共用情况）、
**「谁指向这个描述符」**（空哨兵被 79 个音效共用这件事写在界面上）、
乐曲描述符的轨道成表、函数指针表 1..11 槽标成「播放入口 · 音效 #k（推定）」。

**「推定」两个字不能省**：那 11 条 thunk 的第二条指令确实是 `movs r0,#k`，
且全 ROM 只有这 11 条 BL 调用者，但「k 就是音效号」目前只是**静态推定**，
运行时证据留到下一轮（`tools/l2_runtime_capture.py`）。

### 素材与资源：改指针 = 换资源，载荷本身动不了

域首页第一屏是**结论横幅**，不是免责声明：

> 结论：改指针能换资源，载荷本身动不了。

三个入口：改指针接线（两张 u32 指针表，46 + 90 槽）、
看 79 条图块/精灵资源记录（6 个图块指针 + 3 个脚本指针，**31 种**不同的图块组合）、
改子系统分到多少内存（10 行只有 **7 段**不同的 EWRAM）。
另有**指针接线总表**（847 个指针槽，可搜索，同址计数告诉你改一处会动几处）。

指针目标是什么由内容包在导出时判定（`derived.pointer_targets`）：
「LZ77 块（解压后 N 字节）」或「未压缩原始数据」——
**不是所有指针都指向压缩载荷**（实测数据指针表 A 的 46 个目标全是未压缩原始数据）。

### 「来源 / 被谁引用」：每条记录都能说出自己从哪儿来

> 用户反馈：**「关联还是不够强，例如道具的奖励表，应当提供这些奖励的所有出发来源的
> 跳转和编辑。所有可修改内容都是这样，检查一遍。」**

改一条记录之前，作者要知道的不是「这一格是什么」，而是**「我改了它会动到谁、
它是从哪儿来的」**。所以结构表与文本表的详情面板里都有一个「来源 / 被谁引用」块，
**每一条记录都有**（没有来源的也要写清楚「没有」，空着会像功能坏了）。

来源有六条路，全部由内容包驱动：

| 来源 | 怎么来的 | 例子 |
|---|---|---|
| **字段引用** | 字段声明了 `relation`（下标 / 绝对地址 / 连续段基址） | 角色出生点的 `character_id` → 角色名表 → 角色定义表、逐角色成长表 |
| **指针指向** | 指针的值恰好是某条记录的 ROM 起点 | sound-ID 表的 `descriptor_ptr` → 81 张乐曲描述符表 |
| **连续段基址** | `relation.kind = "row_range"`：值是一段行的起点 | 任务索引表的 `value` → 奖励表 + 任务标题/说明/提示，各 3 条 |
| **同一个 id** | 两张表共享 `id_relation` ⇒ 同一个 id 在两张表里指的是同一个东西 | 忍术记录表 #37 ↔ 忍术名表 #37；角色定义表 #5 ↔ 逐角色成长表 #5 |
| **同一件事的两份记录** | `structure.peers`：按关卡号对应 | 战场布置 ↔ 角色出生点 / 战场物件 / 战斗目标 |
| **原生读者** | `structure.consumers` / `table.consumers`：ROM 里的代码在哪读这张表 | 奖励表 4 个读者、头像拼块表 7 个、说话人名表 12 个 |

每一条来源都有「跳过去」按钮 —— 跳过去直接落在**那条来源记录**上，
作者可以当场改；原生读者给的是「跳到原始字节」。

界面上标签写的是**来源记录自己的名字**（任务索引表那条写「第40关 · 奖励下标起点」），
不是表名 —— 因为作者认的是「第 40 关」。

断言脚本：`rom-editor/tools/verify_sources.mjs`（覆盖「每张表都能溯源」+
几条关键跨域链路）；内容包侧的现状用 `python tools/audit_crossrefs.py` 查。

### 标签要说人话

> 用户反馈：**「存在没有关联为用户能看懂的说明的情况，例如角色属性的编辑，
> 有属性A~F，却不说明这些是什么。核对这些属性并改为使用游戏语义的说明，
> 并核查一遍这类情况。」**

角色定义表的六项属性以前叫「属性A 基础 … 属性F 基础」，逐角色成长表跟着叫
「属性A 成长 …」。现在它们是游戏里的名字：

| 字段 | 现在的名字 | 运行时实例 | 出处 |
|---|---|---|---|
| `stat_a` | **攻击力** | `+0x02` | 名字来自第三方逆向 `notes/character-stats-addresses.md`；仓库自己的指令级分析只证明了偏移 |
| `stat_b` | **防御力** | `+0x03` | 同上 |
| `stat_c` | **敏捷度** | `+0x04` | 同上 |
| `stat_d` | **移动力** | `+0x05` | 同上 |
| `stat_e` | **忍具数** | `+0x06` | 同上 |
| `stat_f` | **查克拉** | `+0x08` | 同上 |
| `aux_stat` | 副属性 | `+0x0A` | 拷贝行为是本仓库证的；第三方观察到它与手印数相同 |
| `hp_base` | 体力（HP）基础 | `+0x0E` | 本仓库证的（`0x0806DA46`） |

**两边的证据等级不同，所以标签给名字、说明给出处** ——
「运行时实例 +0x02。第三方逆向记作『攻击力』，仓库自己的指令级分析只证明它进实例 +0x02。」

同一轮里改掉的还有一批「看不懂但没说清为什么看不懂」的标签：

| 原来 | 现在 |
|---|---|
| `字节00` … `字节0F`（道具记录表） | `未解字节 +0x00` … `+0x0F` →（2026-10-22）**逐字节钉死**：`忍具类别` / `效果 id` / `效果类别` / `效果数值` / `投掷数量（推定）` / `命中率 %（推定）` / `动画 id` / `变体号（推定）` / `效果标记（推定）` / `特效分类 id` / `特效槽键` / `分类匹配字节（高/低）` + 三格 `保留` |
| `未知00` / `未知0A`（忍术记录表） | `未解字节 +0x00` / `+0x0A` |
| `frames_ptr` / `gfx_ptr` / `tilemap`（标签直接是英文 key） | `帧指针` / `图块图形` / `tilemap 图层` |
| `指针0` / `指针1`（战斗遭遇表） | `指针 0（效果表下标）` / `指针 1` |
| `X` / `Y`（战场物件） | `X 坐标` / `Y 坐标` |
| `保留16` | `保留 +0x16` |
| 空 desc（胜负条件的参数 A、字形段的填充、头像拼块的坐标…） | 全部补上说明 |

**每个字段现在都有 desc**：116 张结构表里没有一个字段是「点开也看不懂」的。

断言脚本：`rom-editor/tools/verify_labels.mjs`（占位名 / 空 desc / 属性改名 /
未解码字节的统一说法 / 记录级标签，五条都要过）；扫描现状用
`python tools/audit_field_labels.py`。

### 同一个 id 的其它表也要能跳过去

> 用户反馈：**「技能表不支持配置么」**

技能表**是**支持的 —— 「角色特性表（技能）」（`0x5459C8`，45 条）里
效果类型 / 基础值 / 次要值 / 每级成长 / 附加属性五个字段都能改，
在角色域首页里也能直接打开。

问题在于**入口**：从角色的技能槽点「跳过去」，以前只落到**技能名表**
（一张只有名字、没有参数的表）。于是作者看到的效果就是「技能表不支持配置」——
参数明明在那张表里，只是没人指给他看。

根源是 id 空间：技能名表 #12 与角色特性表 #12 是**同一个技能**，
忍术名表 #37 与忍术记录表 #37 是**同一条忍术**，
人物名表 #5 与角色定义表 #5 / 逐角色成长表 #5 是**同一个角色**。
`structure.id_relation` 已经把这个关系记下来了，但界面只认「指向名字表」这一条路。

现在每个字段的「跳过去」会给**同一个 id 的每一张表**各一条链接：

```
技能槽  跳到「锻炼」→            跳到角色特性表（技能） #1 →
忍术槽  跳到「分身术」→          跳到忍术记录表 #1 →
出生点  跳到「漩涡鸣人」→        跳到角色定义表 #5 →   跳到逐角色成长表 #5 →
```

实现：`rom-editor/js/idspace.js`（id 空间的并查集，无依赖），
`fields.js::relationLinks` 用它补出链接，`slots.js` / `editors.js` 把多条链接都渲染出来。

断言：`verify_views.mjs` 第 17 组（技能槽有 ≥2 条链接 / 有一条指向角色特性表 /
点它落到 `characters/character_perks #1` / 忍术槽指向忍术记录表）。

### 一个东西不拆成几张表

> 用户反馈：**「光一个任务表就分了索引、标题、说明、提示表来呈现，过于细碎繁琐，
> 应当按统一的任务编辑来呈现，然后按索引表列出，将其他表的内容都作为字段呈现。
> 其他模块也要做同样思路的修改」**

ROM 里任务确实是四张表（索引表给基址，三张文本表各存一段话）——
**存储怎么拆是 ROM 的事，编辑时不该拆**：作者要的是一个任务。

现在域首页的「本域可编辑内容」里：

| 原来 | 现在 |
|---|---|
| 任务索引表 / 任务标题表 / 任务说明表 / 任务提示表（四行） | **任务（索引表 + 标题表 + 说明表 + 提示表）**（一行） |
| 角色定义表 / 逐角色成长表 / 角色特性表 / 头像指针表 / 头像拼块表（五行） | **角色**（一行） |
| 道具记录表 / 忍具名表 | **忍具**（一行）；奖励表单独一行（它本身是另一个主对象） |
| 四张剧情脚本根表 | **场景**（一行） |
| 字形段表 / 字宽表 | **字库**（一行） |

统一视图的形状都一样：**左边按主表列出，右边把其它表的内容作为字段呈现**。
任务视图（`rom-editor/js/modules/mission.js`）的样子：

```
左：# | 关卡 | 标题摘要 | 已改        ← 任务索引表的 48 条
右：第 40 关
    本关的基址（索引表）[103]
    子任务 1
      标题  [得到宝箱！]        保护达兹纳先生不被鬼兄弟攻击！ · 30 字节
      说明  [练习移动。鸣人站到宝箱之上]
      提示  [拿到宝箱]
      文本表下标 #103 · 同时是第 1 关子 0、第 47 关子 0
      奖励  金币[100] 强化点[25] 等级门槛[2] + 8 个掉落位
```

机制在 `common.js::domainTableRows` 的 `options.groups`：一个分组 = 一行。

**六个统一视图**：

| 视图 | 深链 | 左边（主表） | 右边（其它表作为字段） |
|---|---|---|---|
| 任务 | `#route/mission` | 任务索引表 48 关 | 标题 / 说明 / 提示 / 奖励 |
| 角色 | `#characters/character` | 角色定义表 63 角色 | 属性 / 成长 / 特性 / 忍术 / 技能 / 道具槽 / 头像 |
| 场景 | `#story/scene` | 四张剧本根表 55 场景 | 战前 / 战后 / 逻辑 / 事件 四个剧本指针 |
| 字库 | `#story/font` | 字形段表 31 段 | 该段字段 + 256 行字宽表 |
| 忍具 | `#items/item` | 道具记录表 94 条 | 名字 / 16 个记录字段 / 在哪几关掉落 |
| 奖励 | `#items/reward` | 奖励表 112 条 | 金币 / 强化点 / 等级门槛 / 8 个掉落位 |

**掉落位的一个坑**（道具域实现时查出来的）：物品 id 写成 `0` = **列表结束**，
所以 112 条奖励里真正被掉落的忍具只有 8 个（id 1/17/18/31/37/40/67/73）。
不认这条规则，会把占位的忍具显示成「掉了 568 次」。

### 剧情对白可以改了（长度不限）

> 用户反馈：**「任务和剧情的可调性太低，参考木叶工房那个项目去补全」**。
>
> 随后（第十七轮）：**「修改时必须等长的要求太麻烦了，我希望能解决，
> 特别是对于对白文本。当然别处的文本也一样」**。

`notes/external-konoha-workshop-gap-20261020.md` 的 **P0-1**：第三方「木叶工房 v0.4.4」
（与本仓库**同一份 ROM**，SHA-256 一致）实现了带回溯的字节码图遍历器（`E.graph`），
配套 `scanText` / `decode`，因此能做到「按场景浏览对白 / 改对白 / 加分支」。
本仓库原来只能改定宽操作数，**对白本身改不了**。

现在剧本里的文本段可以就地改写，**长度不限**。界面上把两种情况分开说：

| 情况 | 界面 |
|---|---|
| 字节数相等 | 绿色「等长，失焦即保存」—— 原地落地 |
| 多了 N 字节 | 琥珀色「变长 N 字节：构建时整个剧本会搬到空闲区」（**不再拒收**） |
| 少了 N 字节 | 琥珀色「变短 N 字节：构建时整个剧本会搬到空闲区」（**不再拒收**） |

变长的正文在**构建时**落地。构建顺序是
**结构 → 文本 → 剧本搬迁 → 补丁最后写**（`rom-editor/js/rom.js::applyScriptRelocations`）：
把**整个剧本**搬到 ROM 的空闲区，把它内部的绝对地址**全部重基**，
再改根表里**指向它**的指针。旧位置原样留着（**不回收** —— 回收会把
「未改动也能重建出同一个 ROM」这条不变量弄丢）。

**前提**：这段正文必须**属于某个能搬迁的剧本**。不属于任何剧本的正文（孤儿代码）
后面没有任何东西能给它让位，仍然**只能等长**。

写回走显式补丁（`pack.setBytesAt`），撤销时恢复 `after_hex`。
控制码 `0x01` / `0x02` 按 token 流**原位保留**。

#### 为什么以前必须等长、现在为什么不用了

**旧结论（第十六轮之前）**：正文**内联**在脚本字节流里，而脚本里的分支目标是
**绝对 ROM 地址** ⇒ 改长改短都会让后面的指令移位、全部分支失效 ⇒ **只能等长改写**。

这条结论**结构上仍然成立**（正文还是内联的，分支目标还是绝对地址），
变的是**应对手段**：

| | 以前 | 现在 |
|---|---|---|
| 变长 / 变短 | 当场拒收并回滚 | **构建时把整个剧本搬到空闲区** |
| 分支目标怎么办 | —— | **全部重基**：`storyvm.js::planRelocation` 按「操作码 + 槽偏移」白名单（`ADDRESS_SLOTS`：**12 个操作码 / 13 个槽**）逐个改成新地址 |
| 根表指针 | —— | 改掉**所有**指向它的根槽 |
| 别的剧本 | —— | **不重叠的那些一条都不受影响**（只写新地址，旧字节没动）；**字节重叠的整组一起搬**（见下面的坑 3） |

**三个容易踩的坑**（都已处理，门禁里有断言）：

1. **重基白名单不能漏也不能多。** 判据是「**操作码 + 槽偏移**」这张白名单，
   **不是**「值落在剧本范围内就 += Δ」—— 本 ROM 实测后一种判据会误伤
   30 处（指令内部）与 1,119 处（原生代码里 `12 xx xx xx` 这类操作数字节
   凑出来的 `0x08xxxxxx` 巧合值）。全 ROM 一共 **1,716 处**地址槽要重基，
   **指向本剧本之外的：0 处** ⇒ 每个剧本自包含，搬一个不影响别的。
2. **`before` 与 `after` 可能指向同一个剧本。** 实测**场景 32..38 / 48..50 / 54 / 55
   共 12 个根**被 `before` 与 `after` 同时指向 ⇒ 搬迁时**两个槽都要改**，
   漏一个就有一场戏走丢了。
3. **有些剧本的字节互相重叠。** 实测 **11 对**：例如 `after.53` 就是 `before.53`
   去掉第一条指令后的后缀（`0x47F40` / `0x47F42`），共享的那 **7,987 字节**里
   有 **141 段对白**（两个剧本扫到的是同一段）。⇒ **必须按字节重叠把剧本分组**
   （`storyvm.js::scriptComponents`），**整组一起搬** —— 搬两份的话两个剧本各留一份
   同一段对白，改了其中一个另一个不变。

**实现落点**：

| 文件 | 干什么 |
|---|---|
| `rom-editor/js/storyvm.js` | `ADDRESS_SLOTS`（必须重基的 12 个操作码 / 13 个槽）、`scriptFragments`（把剧本拆成连续字节段）、`mergeFragments`（把多个剧本的段合并去重）、`scriptComponents`（按字节重叠把剧本**分组**）、`planRelocation`（**纯函数**：规划搬迁 + 重基） |
| `rom-editor/js/rom.js` | `applyScriptRelocations()`；构建顺序改成 **结构 → 文本 → 剧本搬迁 → 补丁最后写**（补丁要折进搬走的那份字节里，所以必须排在补丁之前） |
| `rom-editor/js/scripttext.js` | `commitSegment` **不再拒绝不等长**；新增 `scriptOwner`（这段正文属于哪个剧本）、`segmentBudget` 报出 `delta` |
| `rom-editor/js/pack.js` | 新增 `patchOriginalExtent`（补丁的**原始范围**，`after_hex` 与 `before_hex` 长度可以不同）与 `textSlotKind`（判定文本表是 pointer / fixed / absolute 三种形态） |
| 界面 | `rom-editor/js/modules/scriptview.js`、`rom-editor/js/modules/dialogueview.js`：说明条改写；字节预算行改成「变长 N 字节：构建时整个剧本会搬到空闲区」（**琥珀色**，不是红色） |

顺带两件事：
- **「播音乐」指令（op `0x1B`）的曲目 id 现在可改**（437 处），
  对应木叶工房的 P1-4（18 首曲子）。
- **更正一处说法**：op `0x20` 的第 2 字节**不是**游戏里的说话人 ——
  反汇编 handler `0x08097A66` 显示它读的是对话框状态（由 `0x08` 写入）的名牌，
  根本不读这一字节（80 条实例该字节恒为 1）。界面照样显示，但标签写「说话人 #N（名字）」
  并在 title 里写明证据。

**没做**：加分支 / 加新对白（那要改的是**控制流**，不只是搬字节）、
**控制码本身**（控制码只能**原位保留**，不能新增 / 删除 / 挪位置 ——
要改控制码请用「原始字节」模块按字节改）。

自检：`rom-editor/tools/verify_script_text.mjs`（54 条断言）、
`rom-editor/tools/verify_script_relocation.mjs`（14 条，搬迁本身对不对）、
`rom-editor/tools/verify_variable_text.mjs`（72 条，写回通路端到端）。
测量脚本：`tools/probe_story_relocation.mjs`。
依据：`notes/evidence/story-script-relocation-20261022.md`。

### 分栏宽度可调

> 用户反馈：**「左侧列表与右侧编辑的分栏应该做成宽度可调」**

列表与详情面板之间是一条**可拖动的分隔条**（`rom-editor/js/split.js`）：

### 战斗地图：直接看见地图，在地图上布置

> 用户反馈：**「将战斗部分做成直接可见战斗地图、并在战斗地图上布置编辑的形式。
> 先用独立子代理完成设计编辑流的设计然后落实」**
>
> 设计由**独立子代理**产出（`notes/specs/battle-map-editor.md`，693 行），
> 实现由**另一个独立子代理**产出（`notes/battle-map-view-implementation-20261022.md`）。

以前战斗域只有三张表（战场布置 / 角色出生点 / 战斗目标）的数字，
作者得自己在脑子里把「第 40 关、变体 0、槽 3、坐标 (4, 2)」换算成画面上的位置。
现在**地图直接画出来**，格子就是格子：

```
战斗域首页  →  [打开战场地图]  →  #battle/map/<关卡>/<变体>
```

| 操作 | 效果 |
|---|---|
| 拖动地图上的标记 | 改战场物件 / 角色出生点的格坐标，实时写回 |
| 悬停 | 状态行报出「第 X 列 第 Y 行」 |
| 滚轮 | 缩放（1× / 2× / 3× …） |
| 按住空格拖 或 中键拖 | 平移 |
| 右侧面板 | 战场物件 16 行 + 角色出生点 12 行，逐字段改 |

**像素是真的**，不是示意图：1 格 = **32 × 16 像素**，46 张关卡图全部按 ROM 里的
图块 / 调色板 / 图层 / 组合图块逐像素合成。合成算法照第三方「木叶工房」的
`features.js` 复刻，再用一份**独立实现**抽样对照 50,514 个像素点 —— 0 处不同。

素材走**独立二进制**：`content/maps/maps.bin.gz`（174,584 字节）按需拉取，
内容包顶层 `map_assets` 段只放元数据（格宽格高 / 图块数 / 块偏移）。
这样**不载入 ROM 也能编辑**。素材拉取失败时地图视图照常打开：
画布退化成**格线底图**，顶部挂「未载入地图素材」提示条与「重新载入素材」按钮，
**编辑功能一条不少**。

**只改「布置」，不改地形和图块**：

| 能改 | 不能改（以及为什么） |
|---|---|
| 战场物件 16 槽（`type` / `target` / `x` / `y`） | 地形 / 通行值 —— 战斗加载器 `0x08068FF0` **根本不读** `+0x18`，改了没效果 |
| 角色出生点 12 槽（`character_id` / `unit_flags` / `x` / `y` / `facing` / `level`） | 图块 / 调色板 / 图层 / 组合图块 —— **LZ77 压缩载荷**，改了要重压缩 + 改指针 + 找空闲区 |
| `map_table.background_id`（u8） | 地图尺寸 / 扩图 |

**写回是逐字节可验的**：改一个坐标后重建整份 ROM 与原版比对，
**只有 1 个字节不同**（`0x58954A`），同槽的其它三个字节逐字节相同。

**顺带查清两件事**：

- **剧情底图不是战场地图** —— 它是指向底图表 `0x59903C` 的 id，
  是剧情画面**上半屏**那张 240×80 的图 ⇒ 单列小面板，不叠在战场地图上。
- **底图可用的 id 是 1–7、9–13**（从内容包推出来的，不写死）。
  **8bpp 的底图（9–13）预览不出来**（调色板只有 192 色，索引会越界），
  界面显示占位与说明；4bpp 的 1–7 可以从 ROM 现解预览。

自检：`rom-editor/tools/verify_battle_map.mjs`（V1–V12 + 入口与文字 13 组）。

### 战斗里的「剧情触发列表」

> 用户反馈：**「战斗编辑的剧情触发需要关联上剧情，让玩家可以不跳转而在战斗编辑界面
> 直接查看剧情触发列表、编辑每个剧情。」**
>
> 三步走：独立子代理设计（`notes/specs/battle-story-triggers-20261022.md`）
> → 独立子代理审核（`notes/reviews/battle-story-triggers-review-20261022.md`）
> → 实现。

「剧情触发」卡片里现在是一份**触发块列表** —— 一行 = 一处触发：

```
触发 #4 · 第 4 段对白 · 5 句        条件：回合数 ≥ 2、角色 #12 在场
```

点开那一行，看到**条件表**（每条条件带它的跳转目标，参数可改）与**对白表**
（输入框 + 字节预算，就地改）。

**对白长度不限**：正文内联在脚本字节流里，而脚本里的分支目标是绝对 ROM 地址 ——
所以等长的改写**原地落地**；变长 / 变短的话，构建时会把**整个剧本**搬到 ROM 的空闲区、
把它内部的绝对地址**全部重基**，再改根表里指向它的指针
（`rom-editor/js/rom.js::applyScriptRelocations`）。
每个输入框旁边写着「现在多少字节 / 原来多少字节」，以及这一改会不会搬动剧本。

**结构是什么**（设计 + 审核两方各自用字节复核过）：

| | 「战场事件逻辑」 | 「战场事件表」 |
|---|---|---|
| 是什么 | 一串「条件 → 压一个事件 id」 | 开头一条连续的事件链（每条 5 字节） |
| 合计 | 触发块 **407** | 链项 **400** + 文本指令 **1118** |

- 链是 **1 基**的（ROM 字节钉死：`subs r0,#1` → `cmp r0,r4`，游标从 0 起）
  ⇒ **压入的值 N 选中链上第 N 段**。
  这一条只有**静态字节证据**，没有运行期取证 —— 界面上照实标「按 ROM 字节推定」。
- 407 = 400 + 7：多出的 7 个是场景 32..38 各多压的一个 `0`，
  而 `0−1 = 0xFF` 与链游标 0/1/2 都不等 ⇒ 静态上**选不中任何一段**。
- 条件里的「回合数」比的是 `0x0202680C`（仓库已定案是回合计数）。

**不编**：仓库还没定名的东西照实说没定名 —— 复合条件的三个参数、
「指定人物在场」的那一格、以及每回合翻转一次的那个字节
（仓库对它有两种互相矛盾的说法）。

**剧情跟变体无关**：剧情按关卡（场景）编号，**本关的三个战斗变体共用同一份剧情**。

**没载入原版 ROM 时**：触发块列表换成一句说明（反汇编需要 ROM 字节），
但剧本指针表与战前/战后的可改操作数**照常显示** —— 那些是内容包里的事实。

自检：`rom-editor/tools/verify_battle_story_triggers.mjs`（V1–V12 + 第 16 组布局断言，共 **82 条**）。

### 目视复核：真浏览器 + 真 ROM（第十二轮）

无头门禁断得了**文本与结构**，断不了**像素**。这一轮补了目视复核，

| 现象 | 根因 | 修法 |

| 触发块里的三张表（事件 id / 条件 / 对白）**全塌成一条横线** | `styles.css` 的 `.table-wrap { flex: 1 1 0; }` 是给**行向** flex 容器控制**宽度**用的；而 `.trigger-body` 是**列向** flex 容器，`flex-basis` 落到**高度**上，加上 `overflow:auto` 让自动最小尺寸归零 | `.trigger-body > .table-wrap { flex: 0 0 auto; }` |

### 载入 ROM 门禁：没载入就不让往下走

> 用户反馈：**「把载入ROM做成编辑器的前置操作：需要载入ROM时，先只弹出窗口要求用户选择
> 载入内置ROM或者上传本地ROM，不允许直接关闭这个窗口或是透过窗口操作下方内容」**

载入状态条是**状态**，门禁是**入口** —— 两者分工，不重复：

| | 什么时候在 | 能不能关 |
|---|---|---|
| **载入状态条** | 一直都在（顶栏下面） | 一直能点 |
| **载入 ROM 门禁** | 需要 ROM 而还没有 ROM 时 | **不能关** |

门禁（`rom-editor/js/romgate.js`）的规矩：

- **窗口里只有两个选择**：「载入内置 ROM」/「上传本地 ROM」。
- **不可直接关闭**：没有 × 按钮；Esc 无效（`preventDefault` + `stopPropagation`）；
  点遮罩无效；没有「稍后再说」。**唯一的出路是成功载入一个 ROM。**
- **不能透过窗口操作下方的内容**：遮罩覆盖整个视口；应用外壳（`#app-shell`）
  同时被置 `inert` —— 不可聚焦、不可点击、Tab 也进不去；焦点锁在窗口里。
- **失败不关窗**：错误显示在**窗口里**（顶栏的进度条在门禁升起时是 inert 的，看不见），
  两个按钮恢复可用，可以换一条路重试。

升起门禁的三个时机：内容包装好之后（启动即升起）、点「构建 ROM」而没有 ROM 时、
「原始字节」域没有 ROM 时（那一页给的是一个能升起门禁的按钮，不是干巴巴一句提示）。

> 踩过的坑：`inert` **不能加在 `<body>` 上** —— inert 子树里的 `input.click()` 会被浏览器
> 吞掉，「上传本地 ROM」会**点不开文件选择框**。所以文件输入框长在门禁窗口里，
> 而应用外壳 `#app-shell` 只包住界面。

### 交互约定（2026-10-21 重做）

| 约定 | 说明 |
|---|---|
| **记录按分组折叠** | 内容包的 `field.group` 决定分几段。角色定义表 175 个字段 → 默认只展开「基础属性」8 个字段，其余折叠，标题上写着有多少项 |
| **重复槽位是表格** | 内容包的 `field.array`+`index`+`item` 决定。忍术 15 行 × 4 列、技能 24 行 × 4 列、奖励 8 行 × 2 列、胜负条件 4 行 × 5 列 —— 不是上百个输入框 |
| **取值域已知就给下拉** | 阵营 → 我方/敌方；条件类型 → 全灭敌方 / 回合用尽 / 指定角色已离场…；奖励类别 → 忍具 / 强化素材 / 认识卡 / 技术；档位 → 未习得… |
| **id 显示名字，并可点着跳过去** | 忍术 id 显示「变身术」，点一下跳到忍术名表那一条；**越界的 id 明确标出来**，不再静默 |
| **列表显示记录名** | 内容包的 `structure.id_relation`（忍术记录表 ↔ 忍术名表、道具记录表 ↔ 忍具名表…）让列表多一列名字，搜索也认名字 |
| **「谁引用了我」** | 详情面板顶部给「被谁引用（N 处）」，可直接跳过去。改一个忍术，最想知道的就是会动到谁 |
| **对白按组显示** | 对白指针表 1,524 槽 = **305 组**「一道题 + 三个选项」，由数据里的空指针分隔槽自动切出，详情里是「题干 / 选项 1 / 选项 2 / 选项 3」四个固定位置的文本框 |
| **剧情脚本能反汇编** | 「看剧本」入口把剧情 VM 的字节码拆成指令表：ROM 地址 · 指令（中文名）· 操作数 · 文本 · 分支目标。定宽操作数可以原地改；**对白正文可以改，长度不限**；指令本身不可改 |
| **改回原值就不算改动** | 「已改」按**字节**判定，不是「碰过就算」；字段旁有 ↺ 可单独恢复 |
| **越界被拒绝** | 按字段类型校验取值域（u8 0–255 / u16 0–65535 / s16 −32768–32767），不静默截断 |
| **写不下当场说清为什么** | 11 张文本表里 **9 张是指针表驱动**（正文在别处、靠指针指过去）—— 变长**写得进去**，界面说明「构建时会搬到空闲区并改写指针」；剩下 **2 张结构上就变不了**：**说话人名表**（定长内联槽，槽的大小写死在表里）与**战斗目标说明文字**（地址在代码里写死，搬不动）—— 这两条当场拒绝并回滚，并把**原因**写在界面上，不只说「只能等长」 |
| **共用同一段字要一起改** | 任务标题表有 27 个槽位共用同一串全角空格；改一处会一起变，界面标出「共享 27 处」 |
| **一段字节只能有一个归属** | 全 ROM 文本索引里与具名表重叠的 1,808 条标为「已归属」，默认不显示、也不参与写回 |
| **域首页列出本域全部表** | 一张够不着的表就是作者改不了的表。清单由内容包的 `module` 字段推导，本域剩下的表一律追加 |
| **整块可点，不用瞄准那个小按钮** | 列表的一行/一张卡**本身就是入口**：点行里任何没有别的功能的地方（空白、说明、序号）都跟点那个「打开 / 编辑」按钮一样。**自带别的功能的地方不抢** —— 输入框、按钮、链接（`xref-link`）各走各的 |
| **表说明摆在面板头上** | 内容包里写好的分组规则、内联槽、同址另一种读法，现在都看得见 |
| **补丁最后写** | 原始字节的补丁在结构与文本写回**之后**才写：落在记录里的补丁能生效；与结构化改动冲突时会被跳过并在构建报告里点名 |
| **指针一律十六进制** | 列表与详情用同一种写法（`0x0859F988`）。以前详情给的是十进制框（140114312），抄地址必然抄错 |
| **指针会说清它指向什么** | 内容包在导出时判定每个指针目标是 LZ77 块 / 未压缩原始数据（`derived.pointer_targets`），**不载入原版 ROM 也能回答** |
| **指针也能反查** | 「谁指向这个地址」扫全包指针字段得出（音效描述符被 79 个音效共用这类事实才看得见） |
| **搜索吃十六进制也吃十进制** | 作者照着列表抄地址进搜索框，一定命中 |
| **复合下标说人话** | 「第 12 关 · 变体 1 · 槽 3」由内容包的 `index_scheme` 分解出来，作者不用自己手算 id |
| **原生不读的字节降级为只读** | 改了没有任何效果的字节会标出来并禁用，不让作者白改 |
| **位域是位域** | 已知的位给下拉，其余位原样保留（其余位单独显示出来） |
| **空记录默认藏起来** | 大表里绝大多数记录是全零的（战场物件 1,692 条里 1,216 条是零），默认不渲染，页脚写明藏了多少条 |
| **大表只渲染前 200 行** | 行数上限是**真的**上限（以前返回整份列表，476 行全画出来） |
| **每条记录都有「来源」** | 结构表与文本表的详情里都有「来源 / 被谁引用」块：字段引用、指针指向、连续段基址、同一个 id、同一件事的两份记录、原生读者 —— 六条路，每条都能跳过去直接改 |
| **来源写的是记录自己的名字** | 「第40关 · 奖励下标起点」而不是「任务索引表 · value」—— 作者认的是关卡 |
| **没有来源也要说清楚** | 「没有别的字段指向这条记录 —— 改它只影响这张表自己」，不留白 |
| **标签说人话** | 角色定义表的六项属性叫**攻击力 / 防御力 / 敏捷度 / 移动力 / 忍具数 / 查克拉**，不是「属性A~F」；成长表跟着改名 |
| **每个字段都有说明** | 116 张结构表的**每一个字段**都有 desc —— 点开也看不懂等于没写 |
| **未解码的字节说「未解字节 +0xNN」** | 不叫「字节00」，也不叫「未知0A」；该诚实的地方诚实，该有名字的地方给名字 |
| **名字标出处** | 属性名来自第三方逆向，说明里写明「第三方逆向记作…，仓库自己的指令级分析只证明它进实例 +0x02」 |
| **记录标签也说人话** | 战斗目标说明文字的标签是「第1关 · 变体0 · 胜利条件0 等 2 处」，不是裸地址 `0x08007F1D`；任务文本三表分别叫「标题 / 说明 / 提示」 |
| **同一个 id 的其它表也能跳过去** | 角色的技能槽除了「跳到『锻炼』→」（技能名表），还给「跳到角色特性表（技能） #1 →」——**技能自己的参数**（效果类型 / 基础值 / 每级成长）在那张表里 |
| **分栏宽度可调** | 列表与详情之间的分隔条**可以拖动**，双击复位；宽度记在浏览器里，下次进来还是这个宽度 |
| **一个东西不拆成几张表** | 任务是「索引表 + 标题表 + 说明表 + 提示表」四张表，域首页里合成**一行**，点进去左边按索引表列关卡、右边每个子任务的标题/说明/提示与奖励一起改 |
| **战斗直接看得见地图** | 战场地图按 ROM 里的图块**逐像素**画出来，拖动标记就改坐标；1 格 = 32×16 像素，坐标单位是格 |
| **地图上只改布置** | 战场物件 16 槽 + 角色出生点 12 槽 + 底图 id 1 字节；地形与图块是 LZ77 载荷且战斗加载器不读通行值 ⇒ 不提供「改了没效果」的编辑 |
| **地图素材缺失也能编辑** | 素材拉取失败时画布退化成格线底图 + 提示条，编辑功能一条不少 |
| **改过的位置有标记** | 地图上被改过的物件 / 角色带角标，点开有 ↺ 可单独恢复（按字节判定，「改回原值就不算改动」） |
| **一个域一个主界面** | 战斗域的主界面是**战场地图**；这一关的胜负条件、剧情触发就在地图右边的卡片里，不再要跳到另一个页面 |
| **右边的配置按类分卡片** | 角色 7 张、任务 5 张、奖励 4 张、场景 4 张…… **全都同时可见**，不用在一条长滚动里找，也不用切来切去 |
| **卡片角标写着改了几处** | 不用逐个点开找；按字节判定，「改回原值」角标就灭 |
| **说明说人话** | 字段说明写「这个东西在游戏里是干嘛的」，不写「字节 +0x04」与 ROM 地址；没证明的照实说没证明 |

### 战斗的「四件套」是按原生 id 串起来的

```
关卡 id N
  ├─ 战场布置   map_table[N]            = 0x53D910 + N*32
  ├─ 角色出生点 battle_actors[N][变体]   = 0x5461C4 + N*0x1AAC + 变体*0x8E4 + 4 + 槽位*0xB8
  ├─ 战斗目标   battle_rules[N][变体]    = 0x594758 + N*0xCC + 变体*0x44
  └─ 战斗中的剧情 story_logic_root[N] / story_events_root[N]
```

战斗中的「角色出生」没有单独的表：剧本里的 `0x22` 指令「把角色加入战斗配置」
就是拿关卡 id 与变体 id 去上面那张编成矩阵里扫 12 个槽位找角色 id 匹配的条目。
所以**改编成矩阵里的角色 id / 等级 / 出生点，就等于改了战斗中谁出场、在哪出现**。

按关卡的视图里，**角色出生点那张表可以直接改**：角色 id、阵营、X、Y、朝向、等级
都是输入框/下拉框（阵营改的是 `unit_flags` 的 bit 0 —— 编成路径不读 +0x01 那个
字节）；战场物件的触发目标与 X/Y 同样可改。写回遵循仓库既有模型：
**只动被改的那个字段，其余字节原样保留**。

### 战斗目标：条件语义与「条件」页那句话

战斗目标的每条胜负条件（8 字节）= `type u8, a u8, b u8, c u8, 说明文字指针 u32`。
编辑器把「类型」按**原生行为**呈现，而不是照抄数据里的意图：

| type | 原生语义 | a / b |
|---|---|---|
| 1 | 全灭敌方（a=1）/ 我方全灭（a=0） | a=阵营 |
| **2** | **回合用尽** | **原生根本不读**（数据写着「指定角色仍在场」，代码执行的是「回合耗尽」） |
| 3 | 指定角色**已离场** | a=阵营、b=角色 id |
| 6 | 获得指定道具 | a=道具序号 |
| 7 / 8 / 9 | 剩余体力 / 击杀数 / 收集数比较 | a=阵营 |

> type 2 的判定在 `0x0807790C`：`回合上限 == 0x0202680C 的首字节` 才成立。
> `0x0202680C` 就是回合计数（2026-10-21 用真实战斗逐轮读数证实：回合推进时
> 它从 1 变 2）。详见 `notes/battle-tables.md` §1.1.1。

**说明文字**（游戏内「条件」页显示的那句，如「打败业头・冥头了」）被收进
内容包的专用文本表 `battle_objectives`（219 条），战斗视图里**直接显示并可改**。
它们被 ROM 里的代码用**绝对地址**引用，所以**只能等长改写**：超长时编辑器
拒绝并提示，不会悄悄截断。

> 这些句子**不在**「全 ROM 文本索引」里 —— 同一段字节只能有一个归属，
> 否则两张表会写同一个地址、互相覆盖。

**另一张同样只能等长的表是说话人名表**（`speaker_names`），但**原因不同**：
它是**定长内联槽**（12 字节一条，正文直接写死在表里），**没有指针可以改** ⇒
结构上就放不下更长的字。

这两类现在在界面上**分别说明原因**，不再只说一句「只能等长」：
「这条是定长内联槽，槽的大小写死在表里」/「这条的地址在代码里写死，搬不动」。
判定在 `rom-editor/js/pack.js::textSlotKind`（pointer / fixed / absolute 三种形态），
文案在 `rom-editor/js/editors.js::slotReason`。

### 字段与结构上的机器可读语义

界面只渲染，不硬编码语义。下面这些键是内容包与界面之间的契约：

| 位置 | 键 | 含义 |
|---|---|---|
| 字段 | `group` | 字段属于记录的哪一段（决定折叠分区） |
| 字段 | `array` + `index` + `item` | **重复槽位**（决定渲染成一张表） |
| 字段 | `enum` | 取值域 → 中文标签（下拉） |
| 字段 | `relation` | 这个值是另一张表的 id / 指针（`kind: text/structure/pointer/by_category`） |
| 字段 | `bits` | 位域（已知的位给下拉，其余位原样保留） |
| 字段 | `not_read` | 原生代码**不读**这一字节（界面降级为只读并说明） |
| 字段 | `ptr_kind: "code"` | 这个指针指向**代码**（不适用「载荷」说法） |
| 结构 | `raw_only` | 整张表没有已知字段 |
| 结构 | `id_relation` | 记录下标本身就是一个 id |
| 结构 | `id_is_index` | 记录下标是**基数为 0**的 id（详情不写「第 N 条」） |
| 结构 | `index_scheme` | 复合下标的分解方案（「第 12 关 · 变体 1 · 槽 3」） |
| 结构 | `hide_empty` | 绝大多数记录是全零的，默认藏起来 |
| 结构 | `consumers` | 原生读者地址（改这张表会动到谁） |
| 结构 | `record_labels` | 记录的名字（战斗状态结构 / 战斗控制标志…） |
| 文本记录 | `owned_by` / `shared_with` | 这段字节属于别的表 / 同表内多记录共用同一段字节 |

### 两条硬约束

1. **字段列表必须铺满整条记录。** 已知字段之外，未解码的字节以 `hex` 字段原样保留。
   所以「未改动的内容包」重建出的 ROM 与原版逐字节相同。
2. **字形码表要带规范码。** 8 个字在 ROM 字库里有**两个码位**；编码时必须用
   「基本区」的那个（`tools/text_codec.py::build_canonical_reverse_mapping` 的规则），
   否则回读会变成另一个字。内容包因此同时带 `code_to_char` 与 `char_to_code`。

## 6. 文本的长度策略（11 张表 + 剧情对白）

11 张文本表各有各的形态，剧情对白正文又是另一回事。
形态由 `rom-editor/js/pack.js::textSlotKind` 判定（`pointer` / `fixed` / `absolute`）：

| 类别 | 判据 | 变长怎么办 | 表 |
|---|---|---|---|
| **可重定位（pointer）** | 正文**在别处、靠指针表指过去** | 放不下的那条记录**单独**搬到空闲区并改写它自己的指针；放得下的**原地不动** | **9 张**：人物名表、技能名表、忍术名表、忍具名表、强化素材名表、任务标题表、任务说明表、任务提示表、对白槽位表 |
| **定长内联槽（fixed）** | 正文**写死在表里**一个固定大小的槽中（12 字节一条），**没有指针可以改** | 只能等长 —— 结构上就放不下更长的字 | **1 张**：说话人名表 `speaker_names` |
| **绝对地址引用（absolute）** | 地址是**代码里写死的**，没有第二处指针可以改 | 只能等长 —— 改地址就得改代码 | **1 张**：战斗目标说明文字 `battle_objectives` |
| **剧情对白正文** | 正文**内联在剧本字节流**里，分支目标是绝对 ROM 地址 | **可以变长** —— 构建时把整个剧本搬到空闲区、重基它内部的绝对地址、改根表指针（见 §3「剧情对白可以改了（长度不限）」） | 四张剧情根表的 **202 个根槽** → **190 个不同的剧本** |

界面上现在会把**后两类为什么不能变长**说出来
（「这条是定长内联槽，槽的大小写死在表里」/「这条的地址在代码里写死，搬不动」），
不再只说一句「只能等长」——作者才知道这是 ROM 的结构决定的，不是编辑器偷懒。
逐表验收：`rom-editor/tools/verify_variable_text.mjs`（9 张逐张验证变长能落地、
2 张例外表被拒）。

### 6.1 控制码：排版含义必须活下来

ROM 里的文本是**字形码流**，其中 `0x01 xx` / `0x02 xx yy` 是**控制码**，
带着换行/分页的排版含义。解码成字符串时它们被剥掉（所以文本框里看不到），
**写回时必须原样放回去** —— 这正是仓库 `notes/font-encoding.md:133-143` 与
`tools/text_codec.py::encode_tokens` 要求的。

因此编辑器的写回**走 token 流，不走纯字符串编码**：

| 环节 | 做法 |
|---|---|
| 解码 | 记录里保留**原始字节**（`raw`），控制码就在里面 |
| 编辑 | 文本框改的是文字；控制码按**原位置**留在原处（`mergeTokens`：新文字按原分段长度切分，末段吸收增减） |
| 写回 | 由 token 流重新编码；若某条记录的控制码数量会变少，**构建拒绝写回并报错** |
| 校验 | 1,895 条文本记录全部通过「token → 字节」逐字节还原 |

**影响面**（本 ROM 实际数据）：带控制码的记录共 **2,953 条 / 9,729 个控制字节**
—— `mission_descriptions` 77/112、`mission_hints` 85/112、
`rom_text_index` 2,791/16,008。`dialogue_slots` 1,524 条**没有**控制码，不受影响。

**已知限制**：文本框里**看不到也改不了**控制码本身（编辑器只显示「含 N 个控制码
（已保留）」）。要改控制码，请用「原始字节」模块按字节改。
另外，个别记录的末尾是**悬空控制字节**（`0x01` 后面直接是字符串结束符），
此时控制码只有 1 字节；编辑器按原样保留，不会给它补一个 0。

**改一条文本的代价**：现在只动那一条记录（+ 它的指针 + 它在空闲区的新副本），
不再把整张表连同指针表一起重排。实测改 1 条 `mission_descriptions`：
改动 **29 字节**（此前是 2,186 字节，且会把该表 77 条记录的控制码全部抹掉）。

## 7. 已知的边界

- **压缩载荷本身不可改（但不是所有指针都指向压缩载荷）。** 仓库里只有「字面量」LZ77
  编码器（`tools/lib/lz77.py::compress_literal`），没有与原版逐字节一致的压缩器，
  所以**载荷字节**改不了。哪些指针指向压缩载荷、哪些指向原始数据，
  由内容包在导出时逐个判定（`derived.pointer_targets`），
  界面上逐个指针写明「LZ77 块（解压后 N 字节）」或「未压缩原始数据」。
  实测：数据指针表 A 的 46 个目标全是未压缩原始数据，B 表 79/83 也是；
  图块记录里 `tile_ptr_0/1/3/4` 与 `script_ptr_0/1` 才是 LZ77 块
  （`tile_ptr_2`、`tile_ptr_5`、`script_ptr_2` 指向的根本不是压缩块）。
  详见 `notes/evidence/`。
- **能改的永远是「用哪一份」。** 想改画面内容：去「原始字节」按字节改
  （那里是显式补丁，构建时按「原字节必须匹配」写回），或者把指针接到另一份现成资源上。
- **故事 VM 剧本的指令不可改；文本可以改，而且长度不限。** 剧本只暴露**已证明的定宽操作数**
  （下一场景、地图、子配置、队员等，见 §4）。对白正文能改，是因为**变长时构建会把
  整个剧本搬到空闲区并把它内部的绝对地址全部重基**（`rom.js::applyScriptRelocations`），
  分支不会失效；指令本身（新增 / 删除 / 改操作码）仍然改不了。
- **忍具记录的 16 个字节已逐字节定案（2026-10-22）。** 7 个原生读者分别读哪些格、
  读成什么宽度都有指令级依据；原生代码不读的三格（`+0x01` / `+0x0E` / `+0x0F`）
  明写「保留」并只读；四格只到取值分布的标「（推定）」。
  证据：`notes/evidence/item-record-fields-20261022.md`，
  工具：`tools/item_record_fields.py`（对不上就 exit 1）。
- **战斗目标的说明文字只能等长改写。** 那句话被 ROM 里的代码用绝对地址引用，
  没有第二处指针可以搬到空闲区（编辑器虽然能改那个指针字段，但那是
  「手工接线」，不是「改文本」）。超长时编辑器拒绝并提示。
  **说话人名表（定长内联槽）同样只能等长** —— 它没有指针可以改。
  这两条现在在界面上分别说明了原因。
- **浏览器下载上限。** 某些嵌入式浏览器对单页下载量有上限（本机实测约 1 MB/文档），
  因此原版 ROM 以 32 KB gzip 分片、由若干个载入器文档分片取回。
  桌面 Chrome / Edge / Firefox 不受此限制。

## 8. 与仓库既有工具的关系

编辑器是**仓库既有写回路径的前端**，不是另起炉灶：

| 编辑器的能力 | 仓库里的对应物 |
|---|---|
| 角色 / 成长 / 忍术记录写回 | `tools/import_character_template.py` |
| 奖励表写回 | `tools/import_reward.py` |
| 战场 / 编成 / 对象描述符 / 关卡块写回 | `tools/import_battle_config.py` |
| 精灵动作表写回 | `tools/import_sprite_action.py` |
| 剧情脚本根表写回 | `tools/import_story_script.py` |
| 文本编码 | `tools/text_codec.py`（唯一的字形码编解码入口） |
| 表基址裁决 | `tools/table_registry.py`（`CONFLICTS` 是裁决结果，编辑器按它取基址） |
| 往返自检 | `tools/writeback_paths.py`（17 条写回路径）、`tools/completion_audit.py` |

编辑器的写回模型与它们一致：**复制原生条目、只改已知字段、未知字节原样保留**。
