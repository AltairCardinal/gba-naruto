| 状态 | 判据 | 含义 |

**索引机制被排除**：`tools/build_reverse_results_index.py` 与
`artifacts/reverse-results-index-v1/` 按构造会提到每一个成果族，计为消费会让数字虚高，
因此排除且在收据里公开。

### 0.1 这个数字是下界，不是真值

名字引用只能证明"**引用**"，不能证明"**数据血缘**"。反例已经实测到：
`butano-sequel/game/include/konoha/generated_battle_unit_visual_content.h` 带有全部
2,004 帧视觉数据，头部只写 `// Generated by tools/generate_butano_battle_unit_visual_content.py.`，
**不写它来自 `character-battle-visuals-v1`**。所以：

> `build = 33` 是"至少消费了 33 个族"的下界；真实数据血缘消费数更高，但目前**没有任何
> 机器可读的方式**把生成产物绑回来源族。

⇒ 这本身是本 roadmap 的 **M0**：先让生成产物带上来源声明，之后所有覆盖率才有真值。

### 0.2 自指必须排除（2026-10-20 核验时发现并修复）

本 roadmap 和差异报告都会**逐个列出**缺口族的 id。若测量口径是"名字出现即算引用"，
那么**写这份文档本身就会把缺口族抬成"已提及"**——实测首轮核验正是如此：15 个
`none` 族全部因为本文件列了它们而变成 `doc`，看起来像 M4 已完美收口。

因此测量工具的排除清单里，除索引机制外还必须排除：
`artifacts/butano-reverse-gap-v1/`、`docs/butano-reverse-gap-roadmap.md`、
`notes/full-customization-and-fidelity-theory-20261020.md`，
并在收据的 `excluded_prefixes` 里公开。守卫测试：
`tests/test_measure_butano_reverse_gap.py::test_the_roadmap_and_theory_note_are_not_references`。

**通用教训**：任何"清单型产物"（差异报告、roadmap、覆盖表、索引）都会枚举被测对象；
测量工具必须把自身产物与引用清单排除在外，否则**写清单会提高清单的分数**。

> **2026-10-20 03:40 补记**：会话产出 `docs/reverse-results-index/notes-index.md`
> 后出现同类偏差——该文件逐条列出全部 427 条 note，使 `notes none` 从 213 假降到 10。
> 排除清单已新增该文件（守卫测试
> `test_the_notes_index_is_not_a_reference`）。**判据不是"哪个文件写的"，
> 而是"它是否枚举了被测总体"**：`battle-controller-states.md`（命中 6 条真实引用）

## 2. 修正 Roadmap

每个里程碑都写明：改什么、用哪份逆向成果、怎么验收、失败怎么关。
**验收命令必须能由第三方独立复跑。**

### M0 · 给生成产物补来源声明（让覆盖率从下界变成真值）

- **问题**：§0.1。生成头文件不声明来源族 ⇒ 覆盖率无法核算。
- **做法**：给 `tools/generate_butano_*.py` 的每个产物写一行机器可读来源声明，
  形如 `// reverse-source: <artifact-family> @ <manifest-sha256>`；`generated_*.h`
  头注释、`butano-sequel/graphics/*.json` 的 `provenance` 字段二选一，全库统一。
- **产出**：新增 `tools/audit_butano_reverse_provenance.py`，输出"生成产物 → 成果族"映射。
- **验收**：`python3 tools/measure_butano_reverse_gap.py` 的 `build` 计数上升，
  且新增映射条目与生成文件一一对应；**不接受**"名字命中"冒充血缘——
  声明必须带 manifest 哈希，由 `tools/audit_butano_reverse_provenance.py` 回查逆向树校验。
- **失败关闭**：逆向树缺该 manifest ⇒ 审计器 exit 非 0。

### M1 · 消除无逆向依据的重制侧自造行为

- **问题**：§1.2。`rom` 类 124 族 `build = 0`，而重制侧引入了原版没有的抽象。
- **已知实例（已被实测定位）**：
  1. **青色选中描边**。`battle_runtime_scene.cpp` 的
     `battle_unit_selected_palette_color(0, 23, 23)` 把选中单位调色板第 15 项改成青色；
     **原版 25 帧里青像素数为 0**。反向门禁
     `tests/test_butano_battle_unit_animation_runtime_wiring.py` 目前把这个行为**钉死**了，
     修的时候必须连门禁一起改（门禁钉的是"存在这个覆盖"，不是"原版有这个覆盖"）。
  2. **`has_focus_position`**（`battle_ai.h`）：原版没有"焦点决定朝向"这条路径，
     原版真相是**走完面朝行进方向**。
  3. **`open_command_before_move`**（`battle_mission_rules.h`）：原版顺序是
     「横幅 → 移动选格 → 战场 → 命令菜单」，重制是反的；且该开关置 false 会
     **整个跳过命令菜单**（残差 1142 → 5052）。
     〔**注（2026-10-20 复核）**：「置 false 会跳过命令菜单」是**因为确认移动后
     `movement_selection_confirmed` 置位、`移動` 被隐藏**，只剩「術・忍具 / 行動結束」
     两项，**不是流程顺序本身有缺陷**。所以正确的组合是
     `open_command_before_move = false` **且** `confirm_move_consumes_movement = false`
     —— 4.3.79 那次只改了前者；后来那次「两个开关一起改」的实验
     **录的是与对照实验同一个 ROM（`992e56f8…`，见 4.3.83.1 的哈希核对），
     等于没测**。原版顺序另由逆向侧状态机独立证实：
     `sequel/content/battle_controller_states.json` 里 `move_selection → 0x3110`
     「原版 0x3110 打开可移动格选择」，`command_selection → 0x3000`，
     原版走的是 0x2010 → 0x3110 → 0x3000。〕
- **做法**：逐条比对原版行为，**删抽象**而不是加开关；每个删改都要有原版帧证据
  （PRAM/OBJ/像素差分三者之一）。
- **验收**：受影响的区域差分归零，且**原版侧录像不变**（用同一 `inputs.json` 重录比对）。
- **失败关闭**：若某条原版行为无法判定，标 `unknown` 并停止，**不得**用"看起来像"代替。

### M2 · 把原版状态机接进 Butano（38 态 → 替换自造 24 phase）

- **问题**：`battle_scene_phase` 24 个枚举是重写者自设计；原版是 16-bit 状态分派器，
  **38 个非默认状态**（`rom-battle-controller-cfg-v1`，65,536 输入分母穷尽，
  映射 canonical SHA-256 `ce5e8ea2…`，38 项逐项在
  `tests/test_export_rom_battle_controller_cfg.py`）。
- **做法**：
  1. 逐个读通 38 个 handler，给状态命名（`0x1210 → 移动选格`…），
     产出 `docs/reverse-results-index/battle-controller-states.md`。
  2. 建 **38 ↔ 24 映射表**；**Butano 侧改用原版状态码常量**替换自造枚举。
  3. 用分派表 + PC 跟踪产出**状态转移表**（输入 × RAM 状态 → 下一状态 + 守卫条件），
     落成可验收的 JSON + 门禁测试。
- **验收**：转移表逐条有原版运行收据支撑；`battle_scene_controller.h` 中不再出现
  与原版无关的自造 phase；由门禁测试钉住。
- **注意**：原版相位是**嵌套**的——`0x0809xxxx` 一层（演出/消息/事件级）另有独立
  dispatcher（`rom-boot-state-dispatcher-cfg-v1`、`rom-story-state-callback-cfg-v1`、
  `rom-event-handler-cfg-v1`）。**先做战斗场景这一层**，不外推到整条嵌套链。

### M3 · 接入已闭合的 pixel-A/B 与 relocation/writeback 家族

这是**性价比最高**的一批：逆向侧已经做完，Butano 侧完全没用。

- **pixel-A/B 家族**（20+，全部停在 `doc`）：`battle-effect-group*-pixel-ab-v1`、
  `battle-effect-*-natural-pixel-ab-v1`、`cutscene-obj-id1-pixel-ab-v1`、
  `map41-primary-layout-pixel-ab-v1`、`map-sprites-definition-id1-pixel-ab-v1`、
  `residual-wram-tilemap-pixel-ab-v1` 等。
  这些是**现成的逐像素对照**。⇒ 用它们替换自建差分，作为 1:1 的验收基线。
- **relocation / writeback 家族**（11，全部停在 `doc`）：
  `map-resource-relocation-v1`、`map-resource-writeback-v1`、
  `menu-portrait-relocation-v1`、`menu-portrait-writeback-v1`、
  `story-visual-resource-relocation-v1`、`cutscene-obj-bundle-relocation-v1`、
  `direct-image-palette-relocation-v1`、`generic-sprite-bundle-relocation-v1`、
  `residual-*-relocation-v1`（5 个）、`world-map-background-relocation-v1`。
  这些是**"完全定制化原 ROM"路线**的写回依据：重定位规则、指针重算、容量迁移、
  写回安全门。⇒ 接入后原 ROM 侧的内容级定制才有工程依据。
- **验收**：每个接入项在 Butano 侧留下**可复跑的对照或导入器**，并让
  `tools/measure_butano_reverse_gap.py` 的 `build` 计数相应上升。
- **边界**：只接已签 manifest 的成果；`candidate`/`disproved`/`superseded` 一律不接。

### M4 · 补齐 5 个真正未触及的最终成果

`rom-boot-interwork-continuation-v1`、`rom-cfg-seeds-v1`、
`rom-chapter-script-unbound-tail-v1`、`rom-fast-audit-four-packet-baseline-v1`、
`rom-sprite-component-source-v1`。

- **做法**：逐个判定"对本复刻是否必要"。必要的写消费路径并升级为 `build`；
  不必要的**显式标注 `not-applicable` 并写明理由**（不留空白）。
- **验收**：`gap.json` 中这 5 项的 `status` 不再是 `none`。

### M5 · 消化 213 个无引用 notes

- **做法**：不要求全读。按 §1.1 表格，把 notes 归入四类：
  1. **已落进代码的**（`build` 17 个）——补一句反向链接即可；
  2. **需要转成门禁的**（guard 条件、缺陷语义、tick 节奏）——这是 M1/M2 的原料；
  3. **对本复刻无关的**——显式标注并给出理由；
  4. **仍缺证据的**——进逆向侧待办。
- **验收**：每条 note 落在 1/2/3/4 之一；`notes/` 与 `docs/` 有分类索引，
  覆盖率由脚本统计而非人工登记。

### M6 · 收口 5 项台账 `missing`

`s49-action-menu-glyphs`、`s49-move-grid-cost-colors`、`s49-select-prompt`、
`s49-status-standby-state`、`s49-unit-idle-sequence`。

- **做法**：每项二选一——**从原版 ROM/存档重新取证并落成可复现产物**（更新台账为
  `reconstructed` 并写明取证件），或**证明原版也没有**（更新为 `not-applicable` 并写明
  证据）。**不得留在 `missing`**。
- **验收**：`docs/reverse-results-index/ledger.json` 无 `missing`；由
  `tools/build_reverse_results_index.py` 重跑验证。

### M7 · 建立差异回执的持续门禁

- 把 `tools/measure_butano_reverse_gap.py` 接进常规回归：
  **任何一次声称"已消费某逆向成果"的提交，必须让对应族的 `status` 从 `doc` 升到 `build`。**
- 差异收据入 `artifacts/butano-reverse-gap-v1/`，随每次复刻轮次更新并留版本。
- **禁止**用"名字命中"冒充血缘（见 M0）。

### 7.6 第 10 轮（2026-10-20）：P3 移动网格——**撤回一条旧结论** + 原版 GPU 结构钉出

| 项 | 结果 |
| --- | --- |
| 撤回 | 4.3.90 的「暗化罩**不是**切调色板」**未被证明**（方法不成立）：归档的 PNG 与 PRAM dump **来自不同 mGBA 构建且不是同一帧**；更关键的是**同一帧内**截图与调色板也不在同一色彩空间（移动网格帧 162 色里 **97 色不在该帧调色板**，而 `BLDCNT=0x0000` 无混合 ⇒ GBA 画不出这种颜色） |
| 新工具 | `tools/butano/mgba_frame_palette_sequence.lua` + `tools/butano/capture_s49_frame_palette.py`（**同帧**落截图+调色板+VRAM+寄存器）+ `tools/butano/analyze_s49_movegrid_mechanism.py`；收据 `artifacts/s49-original-{movegrid,banner}-frame-v1/`、`artifacts/s49-original-movegrid-mechanism-v1/` |
| 原版结构 | **移动网格是画在 BG2 上的一层**：逐层比两帧 tilemap ⇒ BG0（地图）只差 **1** 格、BG1 差 **0** 格、**BG2 差 706** 格（BG3 差 175 但图块为空 ⇒ 不画）；BG2 优先级 2 压过 BG0 的优先级 3 ⇒ **覆盖层与「暗化」是 BG2 图块，不是 BG0 调色板染色**。`BLDCNT=0`（无混合）⇒ 暗化来自**图块+调色板**，不是混合。⚠️ 本轮**撤回自己一版解读**：「DISPCNT` 差 bit 10 ⇒ BG3 换图块」是错的——mGBA 渲染器里字符基址只来自 BGxCNT（`charBase = BGCNT.CharBase << 14`），mode 0 下 DISPCNT 不参与，bit 10 只是游戏写的软件标志位 |
| 门禁 | `tests/test_s49_movegrid_mechanism.py` **6 OK**（钉住寄存器差异、整屏层、无混合、**横幅帧自洽 81/81** 与 **移动网格帧不自洽 97/162** 这两个数字） |
| 再进一步 | **地图层在两帧之间逐字节相同**（BG0 调色板 bank 0–3：0 项变化；BG0 图块 VRAM `0x4000`：0 字节变化）⇒ **「给底色加冷色」在硬件层被否证**；冷色来自**另一个层**（`0x1000–0x1800` 区域 706 字节变化）⇒ 也解释了旧「单一 (T, alpha) 无解」：那不是颜色混合，是**空间上的一层覆盖**。⚠️ 仍未定：BG2 在 mode 0 下是**仿射层**，`0x1000` 是仿射参数而非 tilemap，其仿射寄存器两帧相同 ⇒ 需按仿射层布局再解 |
| **第二个实例独立确认** | walk 里移动网格屏出现**两次**：step-16（镜头平移到 152/40）与 step-19（镜头 240/24）；**两帧都是 `DISPCNT=0x1D40`（bit 10 置位）**，而战场帧是 `0x1940`（清位）；step-16 换了镜头覆盖层照样在 ⇒ **覆盖层跟这个位走、与镜头无关**（也解释了 4.3.85 记的「step-16 相机 (152,40)」＝同一屏的另一次出现） |
| **单 bit 定案** | 用**正确基线**（战场帧 walk step-17，而不是整屏覆盖的回合横幅）后：**战场帧 vs 移动网格帧的全部显示寄存器只有 `DISPCNT` 不同**（`0x1940`→`0x1D40`，**只差 bit 10**），BG0–BG3 CNT / 四个滚动 / `BLDCNT` / `WININ` / `WINOUT` / `MOSAIC` **全同**；PRAM **只差 1 字节**（bank 16 的 OBJ 调色板项），**BG0 调色板（bank 0–3）完全相同**；VRAM 只在 `0x1198–0x103CF` 变，**BG0/BG1 图块区 `0x4000–0x7FFF` 完全相同**；精灵两帧**都 20 个**（护送单位移动 + 动画帧）⇒ **暗化的成因被压缩到一个 `DISPCNT` 位**（mode 0 下是某 BG 的字符基址选择位）。⚠️ 上一版「覆盖层 = 3 个精灵」**已撤回**（OAM 槽位会被游戏重排，那 3 个其实是移动了的护送单位）。**下一问（给逆向侧）**：这一位切的是哪一层、对应 ROM 里哪份图块？**定案前不要改重制实现** |
| **机制仍未定** | ⚠️ 上一版写的「覆盖层 = 3 个精灵」**已撤回**：OAM 槽位会被游戏重新分配，按**条目**比后，那 3 个多出来的槽位 = **移动了一格的护送单位**（tile138→136、标记110→112）+ 它的两个标记，**不是覆盖层**；真正的差异只剩**顶部 y=4 的三个 16×16 标记**（tile216/pal4、tile208/pal0、tile192/pal4）。且两帧 **WININ/WINOUT/MOSAIC/BLDCNT 完全相同**（`0x00F0/0xFFFF/0x3F3F/0x0000`）⇒ 暗化**不是窗口、不是 alpha 混合**（两帧都开着 mosaic，这也解释了「截图颜色不在调色板里」）。已钉住的事实：地图层逐字节未变 ⇒ 暗化不是给地图调色板染色；暗化层归属待再采一帧（step-17 战场帧）定案 |
| 给逆向侧 | 请反查：**BG2 在移动网格屏的那套图块**（VRAM `0x1000` 的 tilemap、字符基址 `0x00000` 侧、调色板 bank 8–11）来自哪个 ROM 资源指针？与地图图块（BG0 用的那套）是副本还是同一资源的两份？——这决定「暗化」是**独立的一套暗色图块**还是**同一图块配另一组调色板** |
